# Учёт часов разработки → портал TinyCIO

Каждая задача уходит в портал закрытым тикетом на исполнителя `john_dow` (работы по задаче)
или `ivan_gurkin` (время владельца). Месяц закрывает владелец; скилл только
пишет задачи. 

## Когда

**Перед каждым коммитом** в репозитории продукта: оцени то, что сделано с прошлой записи, и отправь. Без
записанной задачи коммит не делать. Ещё — по просьбе владельца («что за день», «учти», «куда ушло время»).

Не учитываются: репозиторий **tinycio** (сам портал) и **chatben** — там скилл ничего не отправляет.
Продукт определяет `push.py product` по корню репозитория (работает и в worktree):

| Репозиторий | product |
|---|---|
| maOptique | maOptique |
| maTransports | maTransports |
| shukranpay | ShukranPay |
| MaRessources | maRessources |
| maBoutique | maBoutique |
| maERP | maERP |

## Шаг 1. Факты, а не план

```bash
git status --short; git diff --stat; git diff --staged --stat
D=$(date +%Y-%m-%d); N=$(date -v+1d +%Y-%m-%d)
git log --format='%h %ad %s' --date=format:'%H:%M' --after="$D 00:00" --before="$N 00:00" | cat
python3 ~/.claude/skills/task-time-tracking/push.py list --from $D --to $D   # что уже записано сегодня
```

Границы дня — полной формой `--after="ГГГГ-ММ-ДД 00:00"` (короткое `--since=` на этой машине отдаёт пустоту).
Тело коммита — главный источник «почему так»: читай целиком.

- Каждая подзадача привязана к реальному файлу, коммиту или выполненной команде. Пустой diff — оценивать нечего.
- Что не сделано — не приписывать; план — намерение, учёт — факт.
- То, чего не видно в git, тоже работа: разведка, отвергнутый заход, проверка на проде, разбор чужого бага.
- Не повторять уже записанное (сверься с `push.py list`).

## Шаг 2. Задача и подзадачи

**Одна задача = один логический блок работ** (тема дня, фича, сборка maERP), а не коммит: волна модуля — одна
задача с 4–8 подзадачами; пять коммитов по одной странице — одна подзадача. Заголовок задачи — коротко, о чём
блок («Обмен между базами: HTTPS и диспетчер»). Подзадачи дробить мелко (10–90 минут), граница — смена роли
или предмета.

**Роли — закрытый список:** Бэкенд · Фронтенд · QA · Продакт · Девопс · Архитектура · Дизайн.
**Категория** — бизнес-цель («Интеграция с …», «Новая фича …», «Починка данных», «Приёмка», «Документирование»).

## Шаг 3. Оценка «как делал бы человек»

Человек читает код, переключается, дебажит, обсуждает. К чистому кодингу: вникание +30–50 %, отладка и тесты
+20–40 %, переключение контекста +10–15 %. Ориентиры: мелкая правка 00:20–00:45, средняя (2–5 файлов) 01:00–02:30,
крупная 02:30–06:00. Больше двух часов на подзадачу — не разбита. Не округлять (00:47, 01:23, а не 01:00).
Сопутствующие подзадачи, когда они реально были: постановка и декомпозиция, ревью, мерж, выкат и проверка, документация.
Объём диффа калибрует, но не задаёт оценку: лок-файлы и переводы — тысячи строк за полчаса, найденная дыра — три строки за час.
Часы одной задачи — **не больше 24**; больше — значит это несколько задач.

## Шаг 4. Заказчик (billto) и исполнитель

- `billto` — `TinyCIO` (собственный продукт) или код заказчика, если работа делается под него. У **maERP** —
  по правилу «Текущий клиент» в `~/Dev/maERP/CLAUDE.md` (Drissotex, 2MZL, Afnan, FlyCDI, Isofroid, Socassif…).
  Неясно, под кого работа, — **спроси владельца**, не гадай.
- `executor` — **кто делал работу, а не кто за неё отвечает** (решение владельца 15.11):

  | Чья работа | executor |
  |---|---|
  | Работы по задаче: код, разведка, планы, ревью, тесты, сборки, выкат, документация | `john_dow` |
  | Управленческая работа владельца: постановка задач, ответы на вопросы и решения, проверки и приёмка, согласование с заказчиком | `ivan_gurkin` |

  Не смешивать в одной задаче: работа исполнителя и работа владельца — **две разные задачи** с разными `executor`.
  Работу, которую владелец **явно** взял на себя («это я делал сам», «запиши на меня»), — тоже на `ivan_gurkin`.

### Время владельца — отдельной задачей на `ivan_gurkin` (обязательно, решение 15.11)

Время владельца в сессии тоже записывай. К каждой отправке разработки добавь
**вторую задачу** на `ivan_gurkin` с заголовком «Постановка и контроль: <тема задачи>» (тот же `billto`), если в
сессии были сообщения владельца. Подзадачи — по реальной переписке этой сессии, не по шаблону:

| Подзадача | Ориентир |
|---|---|
| Постановка: сформулировал задачу, промпт, вставил материалы | 00:05–00:20 на постановку (длинная, с файлами — до 00:40) |
| Ответы на вопросы и решения (выбор варианта, правила, цифры) | 00:03–00:10 на короткий ответ, 00:10–00:25 на решение с обдумыванием |
| Приёмка: прочитал отчёт, проверил результат, вернул на доработку | 00:10–00:30 на круг |
| Проверка на стенде/проде своими руками (если была) | по факту, 00:10–00:40 |
| Прочее управление: согласование с заказчиком, приоритеты, переписка по задаче | по факту из переписки |

Считай сообщения владельца в сессии: короткие реплики («да», «выкатывай») — по 2–3 минуты, а не 0. В `descr`
перечисли, что именно владелец решал (по-русски, в прошедшем времени: «решил: доли партнёров не исключаем»).
Если владельца в сессии не было (автономный запуск) — второй задачи нет. Задача «Постановка…» отправляется тем же
`push.py send` отдельным JSON.

- Нет маршрута «продукт × заказчик» (ответ 422 «нет маршрута») — посмотри `push.py targets`; новый маршрут
  (только НОВЫЙ — существующий меняет владелец) заводится `push.py target-put '{"product":"maERP","billto":"FlyCDI","client_id":<id>,"service_object_id":<id>,"initiative_id":<id>,"competency_code":"1С"}'`
  (объект и инициатива обязаны принадлежать заказчику — сервер проверит). id спроси у владельца.

## Шаг 5. Отправка

Собери JSON и отправь:

```bash
cat > /tmp/task.json <<'EOF'
{
  "billto": "TinyCIO",
  "date": "2026-11-15",
  "title": "Обмен между базами: HTTPS и диспетчер",
  "source": "maERP develop 1a2b3c4..5d6e7f8",
  "subtasks": [
    {"task": "HTTP-сервис обмена с техпользователем и подписью", "hours": 1.4, "role": "Бэкенд",
     "category": "Интеграция между базами", "descr": "Проблема и предпосылки: … Что сделано: … Файлы: …"},
    {"task": "Ревью и правки по замечаниям", "hours": 0.6, "role": "QA", "category": "Приёмка", "descr": "…"}
  ]
}
EOF
python3 ~/.claude/skills/task-time-tracking/push.py send /tmp/task.json
```

- `hours` — десятичные часы (01:23 → 1.38). `date` — день работы, не старше 7 дней и не в будущем.
- `descr` — в прошедшем времени, от лица программиста, с решением и причиной или числом; файлы и компоненты
  перечисляй. Проверка: человек через год узнает что-то, чего нет в заголовке коммита?
- `ref` считается сам (продукт, заказчик, дата, заголовок): **повтор с тем же заголовком в тот же день вернёт
  тот же тикет** и ничего не изменит. Продолжение работы в тот же день — новый заголовок.
- Ответ 409 «ref уже записан … с другим содержимым» — та же дата и заголовок уже заняты другой задачей:
  дай новый заголовок (часы не теряются молча).
- Ответ — номер тикета. **Покажи номер(а) в итоге сессии.**
- Нет сети / портал недоступен — задача ляжет в `~/.config/tinycio/devcost-outbox/` и уйдёт при следующем
  `send` или `push.py flush`. Отказ 4xx (кроме 404) — исправь задачу; из очереди отказанные уходят в `rejected/`.

## Режим агента: задачи из «Моих задач» владельца (решения 15.11)

Владелец ведёт агента **в чате этой сессии**; в портале агент действует штатными механизмами, как живые
исполнители: передачи, таймер «идёт», шаги со временем, заметки, сдача стадии. Наблюдающий в портале видит,
у кого задача, на какой она стадии и идёт ли работа.

| Кто | В портале |
|---|---|
| Агент (разбор, ресерч, схема, код, проверки) | исполнитель `john_dow`, его таймер и шаги |
| Владелец (постановка, ответы, решения, приёмка) | исполнитель **Иван Гуркин** (ждёт его решения); его время — шагами `owner_steps` |

**Цикл по задаче:**

1. «Прочитай мои задачи» → `push.py agent my-tasks`. Покажи владельцу в чате задачи **продукта этого
   репозитория** (номер, заголовок, заказчик, стадия, суть в одну строку; что неясно — пометь). Ничего не бери сам.
2. Владелец называет номера → по каждому `push.py agent take N` с `{"note":"Беру в разбор: <что понял>"}`:
   тикет передаётся с владельца на `john_dow`, таймер «идёт». Бери **только явно названные**, не из стока.
3. Разбор: `push.py agent ticket N` — сохраняет карточку **целиком** (все поля, свойства стадий, вся лента
   переписки с авторами, шаги, учёт времени) в `~/.cache/tinycio/tickets/N/ticket.json` и **скачивает все
   вложения** (скрины, файлы, голосовые с расшифровкой, PDF) в ту же папку. Прочитай `ticket.json` полностью
   (описание, свойства, каждое сообщение ленты) и **открой каждое вложение Read** — скрины ошибок обязательно:
   текст ошибки часто только на картинке. Не можешь открыть файл — скажи владельцу, а не додумывай.
   Затем код репозитория. В **чат** — вопросы и схема реализации (что меняется, где, риски, оценка), и
   `push.py agent handover N` с `{"note": "<те же вопросы и схема, кратко>", "john_steps": [<шаги разбора с
   минутами>]}` → пауза, тикет передан на Ивана Гуркина.
4. Владелец отвечает в чате. Есть ещё вопросы — снова в чат, тикет остаётся у владельца.
5. «Делай» / аппрув → `push.py agent resume N` с `{"owner_steps": [<время владельца по переписке>],
   "note": "Схема утверждена: <что решили>"}` → возврат на `john_dow`, таймер. **Аппрув = возврат на `john_dow`**,
   других меток нет.
6. Выполнение. Крупный этап или час работы — `push.py agent steps N` с `john_steps`. Новый вопрос по ходу —
   снова шаги 3–5.
7. Сдача → `push.py agent complete N` с `{"report": "<отчёт о работе>", "john_steps": […], "owner_steps": […],
   "note": "коммиты, ветка, что проверено"}` → поле «Отчёт о работе» стадии, «Выполнено», приёмка у владельца
   (`to_status` по умолчанию `ACCEPTANCE`). Принимает **владелец** по умолчанию. Если владелец в чате сказал
   «на приёмку заказчику» — добавь `"acceptor": "customer"`: тикет ждёт заказчика (исполнитель `john_dow` остаётся).
   Уведомление заказчику «передана на проверку» на проде выключено — скажи владельцу, что заказчика нужно позвать самому.

   **Отчёт о работе** (`report`, обязателен, от 300 символов; короче — портал не выпустит стадию, шлюз откажет)
   **видит заказчик** — в чате и в акте. Пиши для него, на языке заказчика, развёрнуто, без внутренней кухни
   (без учёта времени, исполнителей, внутренних заметок). Разделы:
   - **Что было** — проблема/запрос своими словами (со ссылкой на ошибку со скрина, если была);
   - **Что сделано** — по пунктам, конкретно: какие формы, документы, отчёты, роли изменены;
   - **Польза** — что теперь может пользователь, что больше не мешает;
   - **Техническое описание** — версия/сборка (например 2.0.17.23), изменённые объекты конфигурации, миграции данных;
   - **Как проверить** — шаги для заказчика: где открыть, что нажать, что должно получиться;
   - **Что осталось / ограничения** — если есть.

**Правила:**
- `minutes` — оценка «как делал бы человек» (Шаг 3 выше), целые минуты, 1–600 на шаг. `owner_steps` — по
  реальной переписке (таблица «Время владельца» выше): постановка, каждый ответ и решение, проверки.
- Работа, записанная шагами в тикет, **не отправляется ещё раз** через `push.py send` — это задвоило бы часы.
  `send` — только для работы вне тикетов из «Моих задач».
- Агент трогает только тикеты, где исполнитель — владелец или `john_dow` (иначе 409). Отмену не делает.
- Ошибка вызова (`push.py agent …` вернул не 200) — покажи владельцу текст ошибки, не повторяй вслепую: часть
  действий уже сделана (поле `done` в ответе).
- Агентские команды ходят под **отдельным агентским токеном** (`DEVCOST_AGENT_TOKEN` в `~/.config/tinycio/devcost.env`;
  выпускает владелец). Обычный токен учёта часов их не открывает (403).
- Частичный сбой: в ответе `done` — что успело пройти. Повтор того же вызова с теми же шагами безопасен (сервис
  не задваивает одинаковые шаги). Если передача уже прошла, а шаги нет (тикет теперь у владельца) — дозапиши их
  `push.py agent steps N`. Закрытые тикеты (DONE/CANCELLED) агент не трогает, время на них не пишется.
- Заметки (`note`) — внутренние, заказчику не уходят. Заказчик получает «назначен исполнитель» только при первой
  передаче на `john_dow` (`take`); передачи на вопросы и аппрув — без уведомления. Вопросы всё равно копи пачкой.

## Чего не делать

- Не писать md-отчёты в `reports/` и xlsx в «Загрузки» — старый путь (архив, его больше не разбирают).
- Не выдумывать задачи ради ровного дня и не округлять всё до 01:00.
- Не класть токен в репозиторий: он только в `~/.config/tinycio/devcost.env` (`DEVCOST_TOKEN=…`).
