# План: избранная номенклатура в РМК

Задача владельца (2026-09-24): в рабочем месте кассира (`DataProcessors/VentesEnDetail`,
форма `Forms/Form`) завести механизм избранной номенклатуры.

Требования дословно:

1. Быстро указать номенклатуру в избранное — прямо из РМК.
2. Кнопка, открывающая список избранного **в виде меню кнопок**; клик по кнопке
   добавляет номенклатуру в чек.
3. На кнопке видно **название и цену**, отформатированные так, чтобы выбирать было
   визуально удобно и быстро.
4. Всплывающее меню **большое** — чтобы помещалось достаточное количество кнопок.
5. Возможность быстро убрать из избранного.
6. В идеале **и пометка, и снятие избранного — из контекстного меню мышью**, чтобы не
   занимать место лишними кнопками.
7. **Заголовок формы РМК убрать совсем** — заголовка в закладке интерфейса достаточно.
8. Добавить описание механизма для портала **в виде кейса ISO FROID**.

Исходное состояние проверено: кнопки избранного нет ни в текущих исходниках, ни в истории
git с первого импорта (`6c197b0`, 2026-08-20), ни в выгрузках баз клиентов
(`build/{drissotex,ahmed,rayssouni,base143}`) — набор кнопок формы РМК везде идентичен.
Механизм делается с нуля.

## Статус плана

Обязательный гейт `ai-review-plan` внешним ревьюером (Codex) **не прошёл технически**:
`You've hit your usage limit … try again at Sep 26th`. По регламенту `.ai/README.md`
(«Codex в лимите — обязательные шаги выполняют субагенты Claude») разбор выполнил субагент
`architecture-critic`; отчёт — `.ai/reviews/rmk-izbrannoe/01-plan-review-claude.md`. Вердикт:
approve_with_changes, 8 обязательных правок — все внесены в этот план ниже.

Когда Codex снова доступен (после 26.09), этот план стоит прогнать через
`.ai/bin/ai-review-plan` ещё раз: платформенные выводы подтверждены по модели EDT, но
поведение контекстного меню на надписи-гиперссылке в тонком клиенте проверяется только
руками в базе.

## Решения владельца (2026-09-24)

| Развилка | Решение |
|---|---|
| Константа `ЗапретитьРучнойВводТовара` | Кнопка «Избранное» показывается **всегда**: избранное — не ручной ввод произвольного товара, а заранее согласованный короткий список |
| Повторный клик по плитке | **+1 к количеству** существующей строки, **без диалога** количества и цены |
| Серии номенклатуры | **Не заполнять** — так же ведёт себя выбор двойным кликом в подборе |
| Кейс ISO FROID | У клиента есть прилавок — кейс пишем **про РМК**, по-французски |

## Уровень изменения

Существенное (новый объект метаданных — регистр сведений, новая форма, права ролей).
Порядок: план → `ai-review-plan` → реализация → `ai-test` → `ai-review` (обязателен) →
`ai-database` (новый регистр, права) → `ai-final-check` → отчёт
`.ai/reports/rmk-izbrannoe.md`.

## 1. Хранение избранного

Новый регистр сведений **`ИзбраннаяНоменклатураРМК`** (без префикса — правило CLAUDE.md;
свой uuid, не из drissotex: у клиентов объекта нет, конвертировать нечего).

| Свойство | Значение |
|---|---|
| Режим записи | Независимый |
| Периодичность | Непериодический |
| `useStandardCommands` | **false** |
| Измерение `Пользователь` | `CatalogRef.Пользователи`, ведущее |
| Измерение `Номенклатура` | `CatalogRef.Номенклатура`, ведущее |
| Измерение `Характеристика` | `CatalogRef.ХарактеристикиНоменклатуры`, ведущее |
| Ресурс `Порядок` | Число (5.0) — порядок плиток |

Почему регистр, а не реквизит справочника: реквизит `Номенклатура.Избранное` был бы общим
на всех кассиров и потребовал бы реструктуризации справочника с данными клиентов; регистр
сведений даёт «избранное каждого кассира» и не трогает существующие таблицы.

Почему не `НастройкиПользователей`: это регистр «ключ-значение»
(`Пользователь` + `Настройка` → `Значение`) для одиночных настроек, список в него не ложится.

**`useStandardCommands` = false — обязательно.** Ведущие измерения при включённых
стандартных командах добавляют команду перехода в формы `Номенклатура`,
`ХарактеристикиНоменклатуры` и `Пользователи`; `menucheck.py` этого не ловит (он сверяет
состав подсистем), то есть интерфейс поменялся бы молча.

Ведущие измерения оставляем: запись уходит при удалении любого из трёх объектов. Но
**пометка на удаление запись не убирает** — в запрос плиток идут отборы
`Номенклатура.ПометкаУдаления = ЛОЖЬ` и `НЕ Номенклатура.ЭтоГруппа`.

Склад, касса и организация в ключ не нужны: склад берётся из
`РегистрыСведений.НастройкиПользователей.СкладПользователя()` по текущему пользователю
(`Form/Module.bsl:8`), организация — из `ПараметрыСеанса.Пользователь.Организация`
(`:12`), то есть уже производные от пользователя.

Собственных форм у регистра нет. **В подсистемы не включается** — служебный регистр.

Образец файла `.mdo` — `InformationRegisters/НастройкиПользователей` (измерение
`Пользователь` типа `CatalogRef.Пользователи`, `mainFilter` + `master`).

### Права ролей

Фактический набор прав регистра сведений в ролях проекта — **`Read`, `Update`, `View`**
(«Добавление» и «Удаление» у регистров сведений нет; образец — блок
`InformationRegister.НастройкиПользователей` в `Roles/PDV/Rights.rights`).

Права на `DataProcessor.VentesEnDetail` есть у трёх ролей — `PDV`, `Казначей`,
`МенеджерПоЗакупкам`, у всех трёх `setForNewObjects = false`, поэтому права на новый регистр
им прописываются явно.

Роль `Администратор` собрана как «полные права минус исключения»
(`Roles/Администратор/Rights.rights:3` → `setForNewObjects = true`) — её **не трогаем**,
новый регистр получит права автоматически.

### Запись

Менеджером записи по **полному ключу** (`Пользователь` + `Номенклатура` + `Характеристика`),
не набором записей с отбором по одному измерению: иначе две параллельные сессии одного
кассира затрут список друг друга. Управляемые блокировки не нужны — остатки не читаются.

`Порядок` при добавлении — `max + 1` по пользователю; сортировка плиток —
`Порядок, Наименование` (при незаполненном ресурсе сортировка иначе недетерминирована).

Обработчик обновления **не нужен**: таблица новая и пустая, ни одного существующего
реквизита не трогаем, реструктуризации нет.

## 2. Пометка и снятие избранного — контекстным меню

Требование 6: без лишних кнопок на форме.

**Где помечают:** в РМК — контекстное меню таблицы чека `TabularSection` (у таблицы уже есть
`TabularSectionContextMenu`, `Form.form:2719`). Пункты **объявляются статически в `Form.form`** —
два: «В избранное» и «Убрать из избранного». Программного создания пунктов контекстного меню в
конфигурации нет ни одного примера.

**Видимость пунктов не переключается** — изменение относительно первой редакции плана, по итогам
гейта кода. Проверка «лежит ли позиция в избранном» — серверный вызов, а активация строки в РМК
случается на каждый клик кассира. Поэтому оба пункта видны всегда, обработчики идемпотентны, а
**сообщение формируется по факту изменения**: серверная функция возвращает, изменился ли состав,
и кассир видит «Товар уже в избранном» вместо ложного «Товар добавлен в избранное».


**Форму подбора `FormProduitsOnStock` в этой итерации не трогаем.** Там динамический список
с произвольным запросом (`Form.form:1045`, `:1074`) плюс
`УстановитьОграничениеДинамическогоСписка` — правка ради одного пункта меню тянет
`listcheck.py`, урок forms-011 и риск workflow-009. Требование «быстро пометить избранное»
полностью закрывается контекстным меню чека.

Побочный эффект решения: источник пометки один — строка чека, у которой характеристика
заполнена. Дублей плиток «товар с характеристикой» / «товар без характеристики» не будет.

**Где снимают:** контекстное меню самой плитки в форме избранного (п. 3).

## 3. Форма избранного — «меню кнопок»

Новая форма `DataProcessors/VentesEnDetail/Forms/ФормаИзбранного`, открывается новой кнопкой
`Избранное` в группе `GroupMenu` формы РМК (рядом с `Ajouter`).

**Режим открытия — `LockOwner`**, заданный свойством самой формы, а не `БлокироватьВесьИнтерфейс`,
как у подбора: перечисление `РежимОткрытияОкнаФормы` в 8.5.1 объявлено устаревшим, и вызов
`ОткрытьФорму` режим не передаёт вовсе. Из-за этого вывод первой редакции плана про сканер
(«при `БлокироватьВесьИнтерфейс` событие сканера до РМК не дойдёт») к коду не относится:
поведение сканера при открытом окне избранного **не проверено** — это пункт ручной проверки
владельцем.

Размер окна задан в `Form.form` явно: `width` 112, `height` 34 — четыре плитки по 24 знакоместа
в ряду и до десяти рядов (требование 4).


### Видимость и доступность кнопки

- **Видимость — всегда** (решение владельца), в отличие от `Ajouter`, который при
  `Константы.ЗапретитьРучнойВводТовара` скрывается у роли PDV (`Form/Module.bsl:25`).
- **Доступность — `ЭтоНоваяПродажа`**, как у `Ajouter` (`Form/Module.bsl:868`): иначе кассир
  добавит позицию в уже проведённый чек. Та же проверка **дублируется в обработчике клика по
  плитке** — кнопка могла быть доступна на момент открытия окна и недоступна на момент клика.

### Конструкция плитки

`КнопкаФормы` в управляемых формах **не имеет контекстного меню** (модель форм EDT:
`class Button extends DataItem, ExtendedTooltipHolder`, без `ContextMenuHolder`), а
требование 6 просит снимать избранное именно контекстным меню. У **декорации** (`ДекорацияФормы`)
контекстное меню есть, и она не требует ни реквизита формы, ни `ИзменитьРеквизиты`.

Поэтому плитка — **группа-карточка с двумя декорациями-надписями**, ровно по образцу
`DataProcessors/Дашборд/ManagerModule.bsl:290-307` (`ДобавитьКарточку`: группа + две
`ДекорацияФормы` со `ЦветаСтиля`/`ШрифтыСтиля`):

```
ГруппаПлиткиN (ОбычнаяГруппа, Вертикальная, фиксированная ширина, представление карточки)
├── ДекорацияНаименованиеN  (надпись, Гиперссылка = Истина, крупный шрифт стиля)
├── ДекорацияЦенаN          (надпись, Гиперссылка = Истина, акцентный цвет стиля)
└── контекстное меню декорации: «Убрать из избранного»
```

Отвергнутый вариант — `ПолеФормы` + реквизиты формы: 40 плиток × 2 поля = 80 реквизитов и
80 элементов, плюс удаление реквизитов при перестроении. Лишний и хрупкий путь.

Карточное представление таблицы (`FormTableType.Cards`) на десктопе 8.5.1 недоступно — оно
привязано к `mobileDeviceTableType`.

Цвета и шрифты — только `ЦветаСтиля` / `ШрифтыСтиля`, не `WebЦвета` и не `Новый Шрифт(…)`.

Отступление от `docs/FORMS-STYLE.md` п. 1 (рамок нет): у плитки рамка-карточка есть — это
осознанно, так же сделаны карточки дашборда.

**Проверить руками в базе** (смок этого не видит): всплывает ли контекстное меню по правому
клику именно на надписи-гиперссылке в тонком клиенте и не «съедает» ли клик гиперссылка.
Запасной вариант, если нет: таблица формы в одну колонку с многострочной ячейкой
«наименование + цена», высота строки 2–3, контекстное меню у таблицы штатное, выбор — по
событию `Выбор`.

### Как строятся плитки

`&НаСервере`, в `ПриСозданииНаСервере`, по образцу `Дашборд.ДобавитьКарточку` и
`ЛичныйКабинетПартнера/ФормаНоменклатура/Module.bsl`:

1. `Элементы.Добавить("ГруппаПлитки" + Индекс, Тип("ГруппаФормы"), ГруппаСетки)`;
2. `Элементы.Добавить("Наименование" + Индекс, Тип("ДекорацияФормы"), ГруппаПлитки)`,
   `Гиперссылка` = Истина, `УстановитьДействие("Нажатие", "<ИмяОбработчика>")` — сигнатура
   обработчика `(Элемент, СтандартнаяОбработка)`; префикс `Подключаемый_` не требуется;
3. команда снятия — `Команды.Добавить("УбратьИзИзбранного" + Индекс)` с общим действием,
   кнопка команды кладётся в `Элементы.<Декорация>.КонтекстноеМеню`; общий обработчик
   разбирает `Команда.Имя` (образец — `ЛКП/ФормаНоменклатура/Module.bsl:436-444`, `:578-582`).

**Перестроение после «Убрать из избранного»:** элементы и команды удаляются в правильном
порядке — сначала элементы, потом команды (образец `ЛКП/ФормаНоменклатура/Module.bsl:368-393`),
иначе второе удаление упадёт на дубле имени.

Соответствие «плитка → номенклатура» хранится в реквизите формы — таблице значений
(`Номенклатура`, `Характеристика`, `Наименование`, `Цена`), индекс берётся из имени элемента.

Лимит плиток (40) с понятным сообщением, если избранного больше.

### Данные плиток

Один запрос на открытие формы: избранное текущего пользователя
(`ПараметрыСеанса.Пользователь`), упорядоченное по `Порядок, Наименование`, с отборами по
`ПометкаУдаления` и `ЭтоГруппа`. Артикул не выбирается: на плитке он не показывается.

**Цены — как в подборе, а не «по договору».** Проверено: `FormProduitsOnStock/Module.bsl:4-9`
берёт `ТипЦен = Справочники.ВидыЦен.Розничная`, переопределяя его типом цен **контрагента**
(`Параметры.Контрагент.ТипЦены`, контрагент — `Константы.РозничныйКлиент`, передаётся из
`Form/Module.bsl:70`). Договор `РозничныйДоговор` в цене подбора не участвует вовсе.

**Дедупликация цены обязательна** (находка P1 гейта кода). Ключ регистра `ЦеныНоменклатуры` —
четыре измерения: `ТоварнаяГруппа, ВидЦены, Номенклатура, Характеристика`, и товарную группу
документы заполняют по-разному (`УстановкаЦенНоменклатурыВручную/ObjectModule.bsl:6-11` не
заполняет вовсе). Без свёртки на одну позицию избранного приходит несколько строк среза: в окне
появляются дубли плиток с разными ценами, в чек уходит та, на которую случайно нажали, а лимит
плиток срабатывает не на тех данных. Поэтому цена сворачивается до одной строки на пару
`Номенклатура` + `Характеристика`, из записей с **самым поздним периодом**.

**Запасная цена по одной номенклатуре.** Подбор соединяет цену только по номенклатуре
(`FormProduitsOnStock/Module.bsl:44-46`), и в чек из подбора позиция попадает без
характеристики. Поэтому если цены на пару `номенклатура + характеристика` нет, берётся цена по
одной номенклатуре: иначе товар, показанный в подборе с ценой, в избранном оказался бы без цены
и `Payer` запретил бы продажу (`Form/Module.bsl:101-104`).

**Лимит плиток считается по той же выборке, что строит плитки**, а не отдельным счётчиком по
регистру: счётчик разошёлся бы с выборкой, и предупреждение о лишних позициях не сработало бы.

Позиция без цены получает `Цена = 0`, плитка показывает явное «нет цены», а не пустоту. На
плитке стоит **ровно та цена, которая уйдёт в чек**: `РассчитатьСтроку` в РМК вызывается с
`ЦенаВключаетНДС = Истина` (`Form/Module.bsl:316`).


### Клик по плитке

Форма избранного возвращает результат **`Закрыть(Структура)`**, как подбор
(`FormProduitsOnStock/Module.bsl:65-66`), со структурой `Номенклатура, Количество, Цена`.
`Упаковку` в структуру не кладём: `РаботаСДокументамиКлиентСервер.РассчитатьСтроку` считает
`Сумма = Цена * КоличествоУпаковок`, и семантика количества разошлась бы с подбором.
`Серия` не заполняется (решение владельца) — так же ведёт себя выбор двойным кликом в
подборе (`VTSelection`, `:65-66`).

В РМК результат принимает **новый обработчик**, а не существующий `AfterChoiceProduit`:

- `AfterChoiceProduit` при уже имеющейся строке **не переставляет** `CurrentRow` на найденную
  и затем безусловно зовёт `Modifier(Undefined)` — то есть открывает окно редактирования
  **произвольной текущей строки** (`Form/Module.bsl:309-323`, `:76-88`). Для подбора это
  редкий случай, для плиток — основной сценарий;
- решение владельца для плитки: **+1 к количеству без диалога**, значит `Modifier` не
  вызывается вовсе.

Новый обработчик: ищем строку по `Номенклатура` + `Характеристика`; нашли — `Количество + 1`;
не нашли — добавляем строку, `СтавкаНДС = GetVATRateArServer(Номенклатура)`; затем в обоих
случаях `РаботаСДокументамиКлиентСервер.РассчитатьСтроку(Стр, Истина, "Цена")`,
`CalculateSumTotal()`, `RefreshInfo()` и перевод `Items.TabularSection.CurrentRow` на эту

**Существующий `AfterChoiceProduit` и поведение подбора не меняются** — это отдельный код,
общий клиентский путь не трогается.

### Сканер

Пока окно избранного открыто в `БлокироватьВесьИнтерфейс`, событие сканера до РМК не дойдёт
(`ОбработкаОповещения` РМК реагирует только на `"ScanData"`, `Form/Module.bsl:294-306`).
Это осознанно: окно закрывается первым же кликом по плитке. Сказать владельцу в отчёте.

## 4. Заголовок формы РМК

Требование 7. Свойство `ОтображатьЗаголовок` управляемой формы в 8.5.1 **доступно на запись**
(`ClientApplicationForm.type`: `readable="true" writable="true"`, окружения `SERVER,
THIN_CLIENT`). Поэтому правим кодом, без риска для XML формы:

`ЭтотОбъект.ОтображатьЗаголовок = Ложь;` в **`OnCreateAtServer`**, не в `НастроитьФорму()`:
последняя вызывается 8 раз и переустанавливает только `Заголовок` (`Form/Module.bsl:879`).

Заголовок окна и закладки остаётся — убирается только строка заголовка внутри формы.

Если по факту правка XML всё же понадобится: по схеме EDT порядок свойств формы —
`… enabled → verticalScroll → scalingMode → scale → showTitle → showCloseButton →
conversationsRepresentation → collapseItemsByImportanceVariant → … → attributes`. В форме
РМК корень сейчас `enabled(4111) → scalingMode(4112) → collapseItemsByImportanceVariant(4113)
→ attributes(4114)`, значит `<showTitle>false</showTitle>` встаёт **между `scalingMode` и
`collapseItemsByImportanceVariant`**. Живой образец соседства —
`ЛичныйКабинетПартнера/Forms/ФормаЗаявкиНаПоискТовара/Form.form:96-99`.

## 8. Кейс ISO FROID для портала

Кейсы портала хранятся не в лендинге, а в БД портала (`kb_cases`); в репозитории лежат
**черновики в Markdown** — `docs/cases/`, образец `2mzl-production-fr.md`.

Делаем `docs/cases/isofroid-rmk-fr.md`:

- язык **один** (`kb_cases.lang`) — французский;
- структура под поля `kb_cases`: `Le client` → `client_display`/`summary`, `Le défi` →
  `problem`, `Ce que nous avons fait` → `solution`, `Résultat` → `result`, `Pourquoi maERP`
  → `utp`, CTA → `cta_kind`/`cta_url`; `product_codes` = `["maerp"]`;
- **цифры без измеренного источника не публикуются** — `{{…}}` и блок «À confirmer avant
  publication» (запрет — `docs/ai/features/landing-seo.md:168` в репозитории
  **`~/Dev/tinycio`**, не в maERP);
- `client_display` = «Iso Froid» — только с письменного согласия клиента;
- завести кейс в портале и опубликовать — действие владельца.

## 9. Риски

1. **Контекстное меню на декорации-гиперссылке** — проверяется руками в базе; запасной
   вариант (таблица) описан в п. 3.
2. **Смок не видит визуальные дефекты** (урок forms-012): раскладку плиток смотрит владелец
   глазами, скриншот нужен от него.
3. **Пустое избранное у нового кассира** — форма открывается с понятным текстом, это же
   состояние встретит смок.
4. **Цена на открытии формы** — один пакетный запрос, не цикл по позициям.
