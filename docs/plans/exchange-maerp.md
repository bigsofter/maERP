# План волны 6: типовой обмен между базами maERP — `exchange-maerp`

Дата: 2026-11-11. Мастер-план — `docs/plans/retail-chain.md`, «Волна 6»; решение владельца №4 от 2026-11-09
(обмен типовой: план обмена, регистрация, контроль, статусы, блокировки). Часы — FlyCDI, «Внедрение maERP».

## Задача

Две базы maERP (центр и торговая точка/покупатель группы) обмениваются документами: **реализация** продавца
приходит покупателю **поступлением**, **установка цен** продавца — установкой цен покупателя. Обмен запускается
вручную, по расписанию и при проведении; виден статус, ошибки, отложенные объекты; повторный запуск не задваивает
данные. Транспорт — HTTP-сервис maERP (основной) и общий каталог (запасной). COM не используем.

## Что есть сейчас (разведка 2026-11-11)

- Межбазового обмена нет: планов обмена, HTTP-сервисов, подписок регистрации нет.
- Мёртвые заготовки предка: общий модуль `ВнешнееСоединение` (`V83.comconnector`, вызовов нет — TECHDEBT
  строки 3196–3199), регистр `ПараметрыОбменаДанными` (Сервер, БазаДанных, Пользователь, **Пароль открытым текстом**,
  Файловая; измерения Организация × `ПриложенияДляОбмена`; чтение есть у 11 ролей, включая MobileClient, PDV),
  `ИсторияОбменаДанными`, `ОшибкиОбменаДанными` (вызовов нет), обработка БСП `РегистрацияИзмененийДляОбменаДанными`
  (работает по `Метаданные.ПланыОбмена`, которых нет). В базе клиента регистры пусты.
- У клиента обмен — COM «точка-точка», параметры в карточке контрагента-покупателя; выгружаются реализация
  (в чужой базе — непроведённое поступление, организация по ICE) и установка цен; запуск — подписка на проведение
  и команда «Выгрузить к клиенту». Перенос реквизитов клиента — волна 7.
- Строку поступления считает `РаботаСДокументамиКлиентСервер.РассчитатьСтроку` (`Module.bsl:30`), итоги —
  `ПередЗаписью` поступления через `РаботаСДокументами.ЗаполнитьИтогиДокумента` (`ObjectModule.bsl:362`); строки
  `ПередЗаписью` не считает.
- Ключи сопоставления: `Организации.ICE/NIF`, `Контрагенты.ICE/NIF`, `Номенклатура.Артикул`, регистр
  `ШтрихкодыНоменклатуры` (Штрихкод → Номенклатура, Характеристика, Упаковка, Серия). ICE заполнен не везде —
  организация и контрагент узла задаются **в узле явно**, ключи ICE/NIF только проверяются.
- Образца обмена в УНФ-адаптации нет (`docs/UNF-ADOPTION.md`); образец секретов — привилегированный модуль
  `ИзбранныеОтчетыПолныеПрава` (роли прав на регистр не имеют).

## Поиск готового

Проверено: в maERP нет плана обмена и HTTP-сервиса; механизм БСП «Обмен данными» не адаптирован и избыточен
(конвертация, правила, мастера на сотни объектов). Делаю свой узкий механизм на платформенном плане обмена: нумерация
сообщений и квитирование — платформой (`ПланыОбмена.СоздатьЗаписьСообщения/СоздатьЧтениеСообщения`), содержимое —
своё. Штатная обработка `РегистрацияИзмененийДляОбменаДанными` о ревизиях не знает — план `ОбменМеждуБазами` она
не обслуживает (проверка в обработке: для этого плана — сообщение «используйте команду монитора обмена»); ручная
регистрация — команда монитора «Зарегистрировать документы за период» через ту же процедуру регистрации события
(ревизия +1; повторная регистрация уже отправленного — «как новое», новая ревизия).

## 6.1. Ядро обмена

### Объекты

1. **План обмена `ОбменМеждуБазами`** (не распределённая ИБ, без авторегистрации в составе — состав: документы
   `РеализацияТоваровУслуг`, `УстановкаЦенНоменклатуры`, авторегистрация **выключена**, регистрирует подписка).
   Реквизиты узла:
   - `Контрагент` (СправочникСсылка.Контрагенты) — база партнёра как контрагент этой базы;
   - `Организация` (СправочникСсылка.Организации) — наша организация в обмене;
   - `ВыгружатьРеализации`, `ВыгружатьЦены` (Булево) — что отправляем партнёру;
   - `ВидыЦенВыгрузки` — табличная часть (`ВидЦены`): установки цен каких видов цен (вид цены — реквизит **шапки**
     `УстановкаЦенНоменклатуры.ВидЦены`) отправлять;
   - `ПриниматьРеализации`, `ПриниматьЦены` (Булево) — что принимаем;
   - `МестоХранения` (СправочникСсылка.МестаХранения) — склад приёма поступлений;
   - `ОтветственныйЗаПриемку` (СправочникСсылка.Пользователи) — назначение кладовщика в созданном поступлении
     (пусто — без назначения); заполнять может только тот, у кого есть полномочие назначения (правило 2.0.17.16,
     `МобильнаяПриемка.ПравоНазначенияКладовщика`), проверка в `ПередЗаписью` узла;
   - `ВидыЦенПриема` — табличная часть (`ИдВидаЦеныПартнера` Строка 36, `НаименованиеУПартнера` Строка,
     `ВидЦены` СправочникСсылка.ВидыЦен): **явный** список разрешённых соответствий; при `ПриниматьЦены` хотя бы одна
     строка обязательна (проверка записи узла). Строку, по которой уже загружены установки цен (есть входящие
     соответствия «УстановкаЦен» с этим `ИдВидаЦеныПартнера`), изменить или удалить нельзя (`ПередЗаписью` узла —
     отказ с перечнем документов); перенос истории на другой вид цен — не в первой версии. Тест: две установки,
     попытка изменить соответствие между их ревизиями — отказ; два вида цен партнёра на один свой — запрет
     относится к каждой строке отдельно. Вид цен партнёра без строки — объект отложен; поиск по наименованию —
     только подсказка администратору в форме узла, загрузчик по имени не ищет. Партнёр не может выбрать изменяемый
     вид цен — только из таблицы узла;
   - `ПроводитьПоступление` (Булево) — проводить созданное поступление **товаров** на ордерный склад сразу (для
     мобильной приёмки); проведённое считается принятым — последующие изменения реализации откладываются;
   - `ВидТранспорта` (ПеречислениеСсылка.`ВидыТранспортаОбменаМеждуБазами`: `Каталог`, `HTTP`), `КаталогОбмена`
     (Строка), `АдресСервиса` (Строка, только `https://`; 6.2), `ИнициаторHTTP` (Булево; 6.2 — HTTP-обмен пары
     запускает только сторона с флагом, вторая только отвечает), `ПользовательСервиса` (Строка — имя пользователя
     ИБ **этой** базы, под которым партнёр вызывает наш HTTP-сервис; 6.2);
   - `ОбменПриПроведении` (Булево; 6.2 — запуск после проведения), `Расписание` — регламентное задание (6.2);
   - `ДатаНачалаОбмена` (Дата, обязательна) — **граница истории**, только для **первого включения** документа:
     документ без исходящей записи для узла регистрируется, только если его дата ≥ границы. Уже отправленные ключи
     (есть исходящая запись) обрабатываются независимо от даты: изменения, отмена, удаление, выход из предиката —
     как обычно. Изменение границы увеличивает `ПоколениеФильтров` (сверка): сдвиг раньше — вновь попавшие в
     диапазон документы включаются; сдвиг позже — ранее отправленные остаются в обмене (не отзываются), новых из
     выпавшего диапазона нет. Тест переноса даты в обе стороны. История до границы автоматически не отправляется
     никогда (мастер предлагает дату включения). Документы до границы, уже отражённые у покупателя вручную, не
     дублируются. Отдельный старый
     документ включается в 6.2 двумя командами по порядку: покупатель — «Сопоставить с существующим поступлением»
     (соответствие Ид реализации → его поступление, `СозданОбменом = Ложь`, документ не создаётся; **взаимно
     однозначно**: под блокировкой поступления проверяется, что на это поступление нет другого входящего документного
     соответствия ни в одном узле, иначе отказ; поступление, объединяющее несколько реализаций, в первой версии
     автоматически не сопровождается; тест последовательного и конкурентного двойного сопоставления); продавец —
     «Включить документ вне границы» в мониторе для конкретной реализации (исходящая запись получает
     `РазрешенВнеГраницы`, регистрируется новая ревизия; общая дата не меняется). Тест: одна старая поставка при
     других несопоставленных исторических — уходит только она. Интеграционный тест: подключение двух непустых баз с уже отражённой поставкой — новых поступлений и
     обязательств нет;
   - `ДатаЗапретаОбмена` (Дата, необязательный) — см. «Дата запрета для обмена»;
   - `ПоколениеОбмена` (Число) — см. «Восстановление базы из копии»; `ВерсияПравилКонвертации` (Число) — см.
     «Отпечаток содержимого»;
   - `ОбменВключен` (Булево) — **пауза транспорта**: выключенный узел не обменивается (регламент, диспетчер,
     сервис кроме `ping` его пропускают), но **регистрация изменений продолжается** — после включения уходит всё
     накопленное; `ПоколениеФильтров` (Число). Тест: изменение строк при выключенном узле, включение — документ
     уходит без повторной записи.
   Код узла — 9 символов, `ЭтотУзел` получает код при первой настройке (UUID-фрагмент, показывается в форме узла
   для передачи партнёру). Узел партнёра заводится с кодом, который показала база партнёра.
2. **Перечисление `ВидыТранспортаОбменаМеждуБазами`**.
3. **Регистр сведений `СоответствияОбъектовОбмена`** (непериодический): измерения `Узел` (ПланОбменаСсылка),
   `ТипОбъекта` (Строка 50: «Реализация», «УстановкаЦен», «Номенклатура», «Характеристика», «Упаковка»),
   `ВнешнийИд` (Строка 36 — uuid объекта в базе партнёра; для исходящих — uuid своего документа), `Направление`
   (Строка 10: «Входящий», «Исходящий»); ресурсы `ТипОбъектаБазы` (Строка — полное имя метаданных своего объекта),
   `ИдОбъектаБазы` (Строка 36 — uuid своего объекта; ссылка восстанавливается `ПолучитьСсылку`) — **ссылок на
   объекты регистр не хранит**, поэтому штатное удаление помеченных с контролем ссылочной целостности его не
   блокирует, а исходящая запись (ключ, ревизия) переживает удаление документа и даёт состояние «Удален»;
   `ОтпечатокСодержимого` (Строка 64), `ДанныеПрименения` (ХранилищеЗначения, входящие), `ВерсияПримененныхПравил`
   (Число, входящие), `ИдВидаЦеныПартнера` (Строка 36 — для входящих «УстановкаЦен», пишется
   атомарно с применённой ревизией; основа запрета изменения строки `ВидыЦенПриема`), `ПоколениеОбмена` (Число — поколение применённой ревизии, входящие),
 `Ревизия` (Число 15 — номер события обмена: у исходящей
   записи — последний выданный, у входящей — последний **успешно применённый**), `СостояниеИсточника` (Строка —
   «Проведен», «НеПроведен», «Удален», «Отозван»), `Отправлен` (Булево, исходящие), `ПодтвержденнаяРевизия`
   (Число 15, исходящие), `РазрешенВнеГраницы` (Булево, исходящие; 6.2); реквизит `СозданОбменом` (Булево). **Исходящая запись не удаляется никогда** — она хранит
   счётчик ревизий ключа; квитанция только отмечает подтверждённую ревизию и снимает `Отправлен` после
   подтверждённого отзыва, если `ПодтвержденнаяРевизия` = `Ревизия` (квитанция старого отзыва не затрагивает уже
   зарегистрированное восстановление). Индекс по `ИдОбъектаБазы` (отбор эха и поиск). Тест: штатное удаление помеченного документа после квитирования — удаляется,
исходящая запись остаётся, уходит «Удален». Исходящие записи — кому документ уже
   отправлен (основа отзыва при смене получателя).
4. **Регистр сведений `ВходящиеОбъектыОбмена`** (непериодический): измерения `Узел`, `ТипОбъекта`, `ВнешнийИд`;
   ресурсы `Данные` (ХранилищеЗначения — структура объекта из сообщения), `ПоколениеОбмена`, `Ревизия` (Число —
   поколение и ревизия отложенных данных), `Статус` (Строка: «Отложен», «ОжидаетСверки»), `ТекстОшибки` (Строка неогр.), `ДатаПолучения`, `ДатаПопытки`. Объект сообщения, который не удалось
   применить (нет сопоставления номенклатуры, склад закрыт датой запрета, поступление уже принято), не теряется:
   сообщение квитируется, объект ждёт в регистре и применяется кнопкой «Повторить» или следующим обменом.
   Применённые записи удаляются при успешном применении (журнал — `СостояниеОбменаМеждуБазами`).
5. **Регистр сведений `СостояниеОбменаМеждуБазами`** (непериодический): измерение `Узел`; ресурсы
   `ДатаВыгрузки`, `ДатаЗагрузки`, `РезультатВыгрузки`, `РезультатЗагрузки` (Строка: «Успешно», «Ошибка»,
   «Предупреждения»), `ТекстОшибки`, `ОтправленоОбъектов`, `ПринятоОбъектов`, `ОтложеноОбъектов`;
   `ПоколениеСобытий`, `ПоколениеОбработано` (Число), `ПоколениеСверки`, `ПоколениеЗавершеннойСверки` (Число), `СтатусСверки`, `ЭтапСверки`,
   `КурсорСверки` (Строка), `ВыполняетсяС` (Дата), `СеансВыполнения` (Число), `НачалоСеансаВыполнения` (Дата),
   `ТокенВыполнения` (Строка 36) —
   блокировка запуска **уже в 6.1** (см. «Блокировки»). Старые `ИсторияОбменаДанными` и
   `ОшибкиОбменаДанными` не используются (разные измерения, нет узла) — см. 6.3.
6. **Регистр сведений `ЖурналОтправкиОбмена`** (непериодический): измерения `Узел`, `НомерСообщения` (Число),
   `ТипОбъекта`, `ВнешнийИд`; ресурсы `Ревизия` (Число), `Состояние` (Строка). Пишется одной транзакцией после
   `ЗакончитьЗапись` и **до** публикации сообщения (не опубликовано — записи с этим номером перезапишет следующая
   выгрузка с тем же номером). Квитанция с `НомерПринятого` = N накопительная: все записи узла с номером ≤ N
   проставляют `ПодтвержденнаяРевизия` исходящих записей (максимум из подтверждённых) и удаляются. Переживает
   перезапуск; тест задержанной квитанции после перезапуска.
7. **Регистр сведений `УчетныеДанныеОбмена`** (6.2, создаю в 6.1 вместе с узлом): измерение `Узел`; ресурсы
   `Пользователь` (Строка 64), `Пароль` (Строка 256), `КлючПодписи` (Строка 64 — hex; 6.1). **Ни у одной роли нет прав на регистр**; чтение и запись —
   только общий модуль `ОбменМеждуБазамиПолныеПрава` (сервер, привилегированный): `УстановитьУчетныеДанные(Узел,
   Пользователь, Пароль)` — проверяет право `Изменение` на план обмена у текущего пользователя до привилегированного
   режима; `ЕстьПароль(Узел)`; `УчетныеДанные(Узел)` — **не экспортируется на клиент**, вызывается только из
   серверного модуля транспорта. Форма узла показывает пользователя и «пароль задан», пароль не возвращает.
8. **Общие модули**: `ОбменМеждуБазами` (сервер: регистрация, выгрузка, загрузка, конвертация, монитор),
   `ОбменМеждуБазамиВызовСервера` (команды форм с проверкой прав), `ОбменМеждуБазамиПолныеПрава` (учётные данные).
9. **Подписки на события**: `РегистрацияОбменМеждуБазами` — `ОбработкаПроведения` и `ОбработкаУдаленияПроведения`
   реализации и установки цен, `ПередУдалением` обоих → `ОбменМеждуБазами.ЗарегистрироватьДокумент(Источник)`;
   плюс `ПередЗаписью` — **контракт «отправляется состояние проведения»**: обычная запись (`РежимЗаписи = Запись`)
   проведённого документа, который принадлежит хотя бы одному узлу или уже отправлялся (исходящая запись), **с
   изменениями** (своя экспортная функция `ОбменМеждуБазами.ИзмененыДанныеОбмена(Объект)` с явным набором полей:
   реализация — `Дата`, `Организация`, `Контрагент`, `Договор`, `Валюта`, `ВВалюте`, `КурсВалюты`,
   `ЦенаВключаетНДС`, `ТЧТовары` и `ТЧУслуги` построчно (номенклатура, характеристика, упаковка, серия, количества,
   цена, скидки, ставка, суммы); установка цен — `Дата`, `ВидЦены`, `ХозяйственнаяОперация`, `ТЧЦены` построчно) —
   отказ «Документ передан по обмену: проведите
   его заново или отмените проведение» (движения при такой записи не меняются — у установки цен
   `ЦеныНоменклатуры` пишется только проведением, у реализации на неордерном складе запись без проведения
   допускается). Запись без изменений проходит и не регистрируется. Тесты: запись без изменений; замена услуги при
   неизменных итогах — отказ. Тест: обычная запись с изменением проведённой
   установки цен и реализации, участвующих в обмене, — отказ; срезы цен обеих баз совпадают.
10. **Формы**: форма узла (настройки, код этой базы, кнопки «Выполнить обмен», «Проверить подключение» (6.2),
   «Задать пароль»), обработка `МониторОбменаМеждуБазами` (узлы со статусом, датами, счётчиками; закладка
   «Отложенные» — `ВходящиеОбъектыОбмена` с ошибкой и командами «Повторить», «Сопоставить номенклатуру»,
   «Удалить»), команда документа реализации «Отправить по обмену» (регистрирует и запускает обмен узла).
11. **Роль `ОбменМеждуБазамиНастройка`** (допуск): план обмена — чтение/изменение/добавление, монитор, регистры
   `СоответствияОбъектовОбмена`, `ВходящиеОбъектыОбмена`, `СостояниеОбменаМеждуБазами`, `ЖурналОтправкиОбмена` —
   **только чтение**. Записывают эти регистры только серверные модули обмена в привилегированном режиме: соответствия
   документов — только загрузчик и регистрация; ручное «Сопоставить номенклатуру» — серверный метод
   `ОбменМеждуБазамиВызовСервера.СопоставитьОбъект(Узел, ТипОбъекта, ВнешнийИд, Объект)`: право изменения узла до
   привилегий, `ТипОбъекта` только «Номенклатура»/«Характеристика»/«Упаковка» (единицы — `СопоставитьЕдиницу`), тип `Объект`
   соответствует типу; характеристика — владельца номенклатуры строки отложенного объекта; упаковка — допустима для
   номенклатуры строки по той же функции, что ограничивает выбор упаковки в строке формы документа (у
   `УпаковкиЕдиницыИзмерения` нет владельца-номенклатуры), затем совместимость коэффициента. Тест: общая единица и упаковка из набора нескольких товаров. Отрицательный тест: пользователь
   с ролью настройки не может записать регистр соответствий напрямую (`ПравоДоступа("Изменение")` = Ложь) и не
   может через метод сопоставления указать документ.
   Остальным ролям: чтение `СостояниеОбменаМеждуБазами` — тем, кто видит реализации (статус в документе).
   **Команда «Отправить по обмену»** — серверный метод `ОбменМеждуБазамиВызовСервера.ОтправитьДокумент(Документ)`:
   проверка права `Изменение` на **эту** реализацию до привилегий, узлы вычисляет сервер по предикату
   принадлежности (пользователь узлы не выбирает), регистрация и `ПоколениеСобытий` — привилегированно, запуск —
   диспетчер/фоновое задание; права настройки узлов пользователю не нужны. Инварианты ролей проекта (ввод по
   строке) соблюдаются.

### Регистрация (что и кому)

`ЗарегистрироватьДокумент(Документ)` (привилегированно, без транзакции своей — в транзакции записи документа):
- **Реализация**: узлы с `ВыгружатьРеализации`, у которых `Контрагент = Документ.Контрагент` и
  `Организация = Документ.Организация`, кроме `ЭтотУзел` и помеченных на удаление. **Налоговые документы на
  основаниях** (`НалоговыеДокументыНаОснованиях.ЭтоДокументНаОснованиях` — переклассифицируют движения оснований,
  товар не отгружают) в предикат не входят — ни регистрации, ни сверки, ни выгрузки; их обмен — TECHDEBT.
  Интеграционный тест: обычная реализация + покрывающая налоговая — у покупателя одна поставка.
- **Установка цен**: узлы с `ВыгружатьЦены`, в `ВидыЦенВыгрузки` которых есть вид цены **шапки** документа.
  Поддерживаемая хозяйственная операция — только `ХозяйственныеОперации.УстановкаЦенНоменклатуры` (при ней
  `ОбработкаПроведения` пишет `ЦеныНоменклатуры`, `ObjectModule.bsl:21`); операция входит в общий предикат
  принадлежности документа узлу: документ с иной операцией (планируемые цены закупки) узлу не принадлежит — если
  он уже отправлялся (исходящая запись с `Отправлен`), прежним получателям уходит новая ревизия «Отозван», если
  нет — не регистрируется. Тест: смена операции на неподдерживаемую и обратно после квитирования.
- **Смена фильтров узла** (`Контрагент`, `Организация`, `ВыгружатьРеализации`, `ВыгружатьЦены`, `ВидыЦенВыгрузки`):
  `ПередЗаписью` узла с изменёнными фильтрами увеличивает реквизит узла `ПоколениеФильтров` (Число). Состояние
  сверки узла: `ПоколениеСверки` (поколение текущего прохода), `СтатусСверки` («Выполняется»/«Завершена»),
  `ЭтапСверки` («Подходящие»/«Отзывы»), `КурсорСверки`, `ПоколениеЗавершеннойСверки`. Обмен узла до выгрузки:
  `СтатусСверки` = «Выполняется» — **продолжить** проход с курсора (если поколение узла с тех пор выросло —
  начать заново); иначе `ПоколениеФильтров` > `ПоколениеЗавершеннойСверки` — начать проход (статус
  «Выполняется», этап «Подходящие», курсор пуст, `ПоколениеСверки` := поколение узла). Перед каждым пакетом
  поколение узла перечитывается — изменилось — проход заново. «Завершена» и `ПоколениеЗавершеннойСверки` :=
  `ПоколениеСверки` — только после обоих этапов. Этапы:
  документы, подходящие под новые фильтры, без исходящей записи в актуальном состоянии — регистрация новой ревизии;
  исходящие записи с `Отправлен`, документ которых больше не подходит, — новая ревизия «Отозван». Так же работает
  восстановление принадлежности без изменения документа. Тест: исключение и повторное включение вида цен после
  полного квитирования — без записи исходного документа; изменение фильтра между пакетами — проход начат
  заново, состав соответствует последним фильтрам; авария до первого пакета и между пакетами — следующий обмен
  продолжает проход, статус «Завершена» только после этапа отзывов.
- **Смена получателя**: кроме текущих узлов документ регистрируется на узлы из исходящих записей
  `СоответствияОбъектовОбмена` (кому уже отправлен). При выгрузке принадлежность документа узлу проверяется заново:
  не принадлежит — узлу уходит объект с состоянием «Отозван» (только Тип, Ид и Ревизия, без коммерческих данных);
  после квитанции отзыва исходящая запись **остаётся** (счётчик ревизий), снимается только `Отправлен` при
  `ПодтвержденнаяРевизия` = `Ревизия`; принадлежит — актуальное состояние, исходящая запись обновляется.
- **Эхо и транзит**: документ, созданный обменом (`СозданОбменом` в соответствии или `УзелИсточникОбмена` в
  `ДополнительныеСвойства` при первой записи), **не регистрируется ни на какой узел** — транзита в первой версии
  нет (кольцо баз и доставка одного источника двумя маршрутами исключены). Установку цен центра точки получают
  только напрямую от центра. Транзит с сохранением исходного Ид — TECHDEBT.
- Регистрация при **проведении**, **отмене проведения** и **удалении** — сообщение несёт состояние документа.
- **Ревизия события**: каждая регистрация документа на узел (проведение, отмена, удаление, смена получателя)
  в той же транзакции увеличивает `Ревизия` исходящей записи (Узел, Тип, uuid документа, «Исходящий»; запись
  создаётся при первой регистрации и переживает удаление документа — ключ uuid). Ревизия передаётся у **каждого**
  объекта, включая «Удален» и «Отозван»; восстановление принадлежности узлу без изменения документа — новая ревизия.
  Изменения непроведённой реализации не регистрируются (черновики продавца покупателю не нужны).

### Формат сообщения

Платформенная оболочка: `ПланыОбмена.СоздатьЗаписьСообщения()` над `ЗаписьXML` (от, кому, номер сообщения, номер
принятого) — квитирование и повторная отправка неподтверждённого платформой. Тело — элемент `ОбменМеждуБазами`
с атрибутом `ВерсияФормата="1"`, внутри объекты, сериализованные **своей** структурой в JSON-строку элемента
`Объект` (`ЗаписьJSON` от структуры примитивов — без ссылок базы-источника):

```
Объект: { Тип: "Реализация" | "УстановкаЦен", Ид: <uuid>, Состояние: "Проведен" | "НеПроведен" | "Удален",
  Ревизия: <число, обязательно у всех состояний>, Номер, Дата,  // ПоколениеОбмена — атрибут оболочки тела
  Организация: {ICE, NIF, Наименование}, Контрагент: {ICE, NIF, Наименование},
  Валюта: <код>, ЦенаВключаетНДС,
  Строки: [{ Номенклатура: {Ид, Артикул, Штрихкоды: [{Штрихкод, УпаковкаИд}], Наименование,
                            Единица: {Ид, Наименование, Код, МеждународноеСокращение}},
             Характеристика: {Ид, Наименование}, Упаковка: {Ид, Наименование, Коэффициент},
             Серия: {Наименование} | null, Количество (базовые), КоличествоУпаковок,
             НДС: {Режим: "БезНДС" | "Ставка", Процент},
             СуммаИтог, СуммаНДС  // окончательные: СуммаИтог = СуммаСНДС строки реализации, если ЦенаВключаетНДС,
                                   // иначе СуммаСНДС − СуммаНДС (Сумма реализации — до скидки, не передаётся)
           }],
  Услуги: [{ Номенклатура: {Ид, Артикул, Наименование, Единица: {Ид, Наименование, Код, МеждународноеСокращение}},
             Количество (в базовой единице услуги источника), НДС: {Режим, Процент}, СуммаИтог, СуммаНДС }],
  Итоги: {СуммаСНДС, СуммаНДС},  // товары + услуги, как ЗаполнитьИтогиДокумента; доп. расходы реализации в сумму
                                  // документа не входят и не передаются
  // установка цен:
  ВидЦены: {Ид, Наименование, Валюта: <код>, ЦенаВключаетНДС}, Цены: [{Номенклатура: {...}, Характеристика,
  Упаковка, Цена}] }
// Количество — в базовых единицах источника; коэффициент упаковки — относительно базовой единицы источника
// отзыв и удаление: { Тип, Ид, Ревизия, Состояние: "Отозван" | "Удален" }
```

Серии (IMEI) в первой версии не передаются: строка с серией приходит без серии. Товары с IMEI на ордерный склад не
принимаются (решение волны 4) — такое поступление отложится ошибкой проведения; на неордерном складе поступление
остаётся непроведённым, IMEI кладовщик указывает при приёмке. Передача IMEI — пункт TECHDEBT.

### Загрузка (конвертация)

`ЗагрузитьСообщение(Узел, ЧтениеXML)`:
0. **Закрепление идентичности**: до квитанции и первого объекта отдельной транзакцией сохраняется (узел, поколение,
   номер) → SHA-256 всего входящего сообщения со статусом «Принимается» (после `ЗакончитьЧтение` — «Принято»). Любая
   повторная попытка с тем же поколением и номером (в том числе выше принятого, после частичного применения)
   сверяет хеш: другой — остановка обмена до сверки. Тест: восстановление отправителя после частичного применения
   сообщения получателем.
1. `ЧтениеСообщения.НачатьЧтение(ЧтениеXML, ДопустимыйНомерСообщения.Любой)` — режим «любой номер» задаю явно (по
   умолчанию платформа сама отвергает уже принятый номер раньше загрузчика); затем модуль проверяет: отправитель =
   узел, для которого вызвана загрузка (каталог узла или узел URL с проверкой пользователя, 6.2), получатель =
   `ЭтотУзел`; иначе исключение, ничего не применяется. **Уже принятое сообщение** (`НомерСообщения` ≤
   `ПринятыйНомер` узла) — не ошибка, принятый номер не уменьшается: квитанция (п. 2) обрабатывается,
   тело не применяется, ответ формируется как обычно. Так обмен восстанавливается после сбоя между приёмом и
   публикацией ответа (файл ответа не записан, HTTP-ответ потерян — партнёр пришлёт то же сообщение).
2. **Квитанция**: по `ЧтениеСообщения.НомерПринятого` (и по ACK) — пообъектное снятие регистраций по журналу
   отправки (см. «Регистрации без платформенной нумерации»); по объектам подтверждённого сообщения (номер сообщения → ревизии, записанные в
   `ЖурналОтправкиОбмена`) исходящие записи получают `ПодтвержденнаяРевизия`.
3. Каждый `Объект` → `ПрименитьОбъект(Узел, Данные)` в **своей** транзакции; ошибка применения → в **отдельной**
   транзакции запись в `ВходящиеОбъектыОбмена` (Отложен, данные, версия, текст).
4. Сбой **сохранения** отложенного объекта (а не применения) — `ЧтениеСообщения.ПрерватьЧтение`, приём прерывается,
   номер принятого не продвигается, результат «Ошибка»; уже применённые объекты при повторной доставке
   пропускаются по версии.
5. `ЗакончитьЧтение` — только когда каждый объект либо применён, либо сохранён отложенным.
Объект, по которому уже есть отложенная запись, заменяет её данные (последняя версия выигрывает) и пробуется заново.

**`ПрименитьОбъект` — атомарность и повтор.** В одной транзакции: исключительная управляемая блокировка
`РегистрСведений.СоответствияОбъектовОбмена` по (Узел, ТипОбъекта, ВнешнийИд, «Входящий») **до** чтения
соответствия → под той же блокировкой читаются применённая ревизия (соответствие) и ревизия отложенной записи:
входящая ревизия ≤ применённой или < отложенной — выход «без изменений», документ и отложенные данные не
меняются (повтор отзыва и удаления — тоже); равна отложенной — повтор применения сохранённого состояния;
больше — применение → блокировка документа-приёмника (для поступления — та же исключительная блокировка
`Документ.ПоступлениеТоваровУслуг` по ссылке, что берёт мобильная приёмка, затем её порядок) → проверки и
изменение документа → запись соответствия с ревизией и состоянием → удаление отложенной записи, **только если её
ревизия ≤ применённой**. Тест: N+1 отложена (частичный приём), затем доставлена N — N не применяется, N+1 цела.
**Документ-приёмник физически удалён** (соответствие есть, `ПолучитьСсылку(ИдОбъектаБазы).ПолучитьОбъект()` =
Неопределено): создан обменом (`СозданОбменом`) — восстанавливается новым документом с **тем же uuid**
(`УстановитьСсылкуНового`), ревизия продолжается; сопоставлен вручную — объект откладывается «сопоставленный
документ удалён — сопоставьте заново». Тест для поступления и установки цен со штатным удалением между отзывом и
восстановлением. Тот же путь — для
ручного «Повторить» и любого транспорта. **Контракт ошибки — откат целиком**: любая ошибка (в том числе
проведения) откатывает транзакцию — документа нет, ревизия не продвинута; данные лежат только в отложенных и
применяются заново после исправления причины (без второго документа: соответствие пишется только при успехе).
**Происхождение до записи**: новый документ получает ссылку заранее (`УстановитьСсылкуНового`), соответствие
(`СозданОбменом`) пишется в той же транзакции **до** записи и проведения документа, а в
`ДополнительныеСвойства` объекта кладётся `УзелИсточникОбмена` — подписка регистрации пропускает этот узел уже
при первом проведении. **Дата запрета для обмена — своя политика**, не зависящая от исполнителя: обмен меняет документ-приёмник
(поступление, установку цен), только если и прежняя, и новая дата документа позже **общей** даты запрета базы
(строки регистра дат запрета этой организации и без организации, кроме видов «по пользователю», «по роли», «по
группе пользователей»), позже даты **автозакрытия периода** (`Константы.АвтозакрытиеПериода`: начало текущего дня
минус N дней — оба документа-приёмника подпадают под автозакрытие; уточнение 2.0.17.19) (без персональных
разрешений и исключений пользователя сеанса — `МожноРедактироватьДокумент` смотрит на
пользователя и его разрешения, поэтому для обмена не используется) и позже `Узел.ДатаЗапретаОбмена` (необязательный
реквизит узла). Одинаково при ручном, фоновом и HTTP-запуске. Иначе — объект откладывается «закрытый период».
Тест: один закрытый документ под менеджером, администратором и техническим пользователем — везде отложен.
**Подключение к записи**: `ПередЗаписью` поступления сейчас вызывает пользовательскую
`РаботаСДокументами.МожноРедактироватьДокумент`; для записи загрузчиком (серверный признак
`ДополнительныеСвойства.ЗаписьОбменом`, ставится только привилегированным модулем обмена, из формы недоступен)
вместо неё вызывается общая проверка периода обмена `ОбменМеждуБазами.ПериодОткрытДляОбмена(Объект, Узел)`;
остальные проверки записи сохраняются. Тест: открытый общий период при персональном запрете у менеджера и у
технического пользователя — загрузка проходит; закрытый общий — отложено.
У установки цен своей проверки в `ПередЗаписью` нет (общая доработка — TECHDEBT).

**Реализация → поступление** (`ПриниматьРеализации` узла):
- Поиск существующего: `СоответствияОбъектовОбмена` (Узел, «Реализация», Ид).
- Сопоставление номенклатуры: соответствие по Ид → штрихкод (`ШтрихкодыНоменклатуры`, одна позиция) → артикул
  (ровно одна номенклатура) → нет — объект откладывается с перечнем несопоставленных строк. Найденное по штрихкоду и
  артикулу запоминается в `СоответствияОбъектовОбмена` (Номенклатура, Ид партнёра). Характеристика и упаковка —
  соответствие по Ид → наименование у найденной номенклатуры → нет: характеристика — отложить, упаковка — базовая
  единица с пересчётом `Количество` (по коэффициенту партнёра). Автосоздания номенклатуры нет (TECHDEBT —
  опция «создавать номенклатуру»).
- Сверка ключей: ICE/NIF контрагента из сообщения против `Узел.Организация`, организации — против `Узел.Контрагент`
  (если оба заполнены и различаются — откладываю с ошибкой «реквизиты сторон не совпадают с узлом»).
- **Валюта**: по коду из сообщения; валюта ≠ основной — `ВВалюте = Истина`, `Валюта`, `КурсВалюты` (и кратность) —
  по курсам **базы покупателя** на дату поступления, курса нет — отложить; основная — `ВВалюте = Ложь`, курс 1.
  Устанавливается до расчёта строк (иначе `РаботаСВалютами.ПроверитьВалютуДокумента` в `ПередЗаписью` молча
  подменит валюту основной). Тест EUR → MAD: валюта, курс, регламентированные суммы и движения.
- **Характеристика**: на **каждом** применении (в том числе по сохранённому соответствию) проверяется, что владелец
  характеристики = текущая сопоставленная номенклатура строки; не совпал (сопоставление товара сменили) —
  соответствие характеристики недействительно, ищется заново по наименованию у текущей номенклатуры (только
  единственный результат), иначе объект откладывается. Тест: смена сопоставления A → B после успешной загрузки
  цен — характеристика A не используется.
- Новое поступление: `Организация`, `Контрагент` — из узла, `Договор` — основной договор контрагента с организацией
  (`ДоговорыСКонтрагентами`, `Основной`; нет — отложить), `МестоХранения`, `ОтветственныйЗаПриемку` — из узла,
  `НомерВходящегоДокумента`/`ДатаВходящегоДокумента` — номер и дата реализации, `ЦенаВключаетНДС`, валюта (по коду;
  нет — отложить), дата поступления — дата приёма (`ТекущаяДатаСеанса`); строки: номенклатура, характеристика,
  упаковка, количества, ставка НДС: «БезНДС» — предопределённая ставка без НДС (`SansTVA`); «Ставка» — единственная
  ставка `СтавкиНДС` с этим процентом, кроме `SansTVA` (нет или несколько — отложить). Тест: в базе есть и
  `SansTVA`, и ставка 0 % — каждая строка получает свою. **Суммы — окончательные, после
  скидок**: `Сумма` поступления = `СуммаИтог` из сообщения (скидки у покупателя нет — его цена эффективная),
  `СуммаНДС` — из сообщения, `СуммаСНДС` — по `ЦенаВключаетНДС`; `Цена` — эффективная цена упаковки = `СуммаИтог`
  / `КоличествоУпаковок`, округлённая до точности цены; затем общая процедура заполнения строки формы (`РассчитатьСтроку` и зависимые поля — `КодСтроки`,
  `СуммаРегл`; вынести из формы, если форма делает больше) и **восстановление сумм строки из сообщения** (разница
  округления не меняет сумму документа). Перед записью — итоги поступления = `Итоги` реализации, иначе отложить.
  **Услуги** — в `ТЧУслуги` поступления: сопоставление услуги по Ид → артикулу → точному наименованию (одна
  услуга); количество пересчитывается тем же сопоставлением единиц (единица источника → `Номенклатура.Единица`
  услуги приёмника, без подтверждённого коэффициента — отложить), цена — эффективная от окончательной суммы;
  суммы так же; обязательные колонки строки услуги, которых нет в сообщении, — по умолчанию строки,
  не заполнились — отложить. Тесты: смешанная реализация и только услуги; услуга «дни → часы» (K = 8) отдельно
  и в смешанном документе.
  **Единицы**: базовое количество источника переводится в базовые единицы приёмника через коэффициент
  **сопоставления единиц** — отдельный регистр сведений `СопоставлениеЕдиницОбмена`: измерения `Узел`,
  `ИдЕдиницыИсточника` (Строка 36), `ЕдиницаПриемника` (СправочникСсылка.УпаковкиЕдиницыИзмерения),
  `Номенклатура` (СправочникСсылка.Номенклатура приёмника; пустая — для всех товаров, 2.0.17.19); ресурс
  `Коэффициент` (Число 15.6 — сколько единиц приёмника в единице источника). Коэффициент пары единиц может
  зависеть от товара («шт» источника — «кг» приёмника): строка с номенклатурой важнее общей; монитор
  сохраняет общую строку, а при заданной в строке своей номенклатуре — строку этого товара. Тест: общая пара
  «шт → кг» с K=1 и строка товара Б с K=0,5 — товар А получает 1, товар Б — 0,5. Пишет только серверный метод
  `ОбменМеждуБазамиВызовСервера.СопоставитьЕдиницу(Узел, ИдЕдиницыИсточника, ЕдиницаПриемника, Коэффициент,
  Номенклатура)` (номенклатура необязательна: пустая — общая строка; заполнена — строка этой позиции, товара
  или услуги, базовая единица позиции = `ЕдиницаПриемника`)
  (право изменения узла до привилегий, коэффициент > 0); роль настройки — чтение. Тест: обе пары одной единицы
  источника сохраняются, документ с обеими строками загружается. При каждом применении целевая единица = `Номенклатура.Единица` сопоставленной номенклатуры
  приёмника; для этой пары нет подтверждённого коэффициента — объект откладывается. Тест: два товара с общей
  единицей источника и разными базовыми единицами приёмника — у каждого свой коэффициент. Автоматического подтверждения нет: код
  справочника `УпаковкиЕдиницыИзмерения` локальный, предопределённых элементов и классификатора нет, поэтому
  совпадение кода или сокращения — только **подсказка** в мониторе. Сопоставление делает администратор один раз на
  пару единиц (единиц мало); строка с несопоставленной единицей — объект откладывается «сопоставьте единицу
  „шт“ партнёра». Номенклатура берёт K из сопоставления своей базовой единицы источника. Тест: одинаковые локальные
  коды при разных единицах — без ручного сопоставления не применяется. Штрихкод
  упаковки: если штрихкод источника привязан к упаковке, а у приёмника тот же штрихкод — к другой упаковке или
  базовой единице, сопоставление по штрихкоду номенклатуры не подтверждает единицы — коэффициент проверяется
  по-прежнему. **Единые формулы** (K = `КоэффициентЕдиниц`): базовое количество приёмника = базовое количество
  источника × K; упаковка приёмника совместима, если её коэффициент = коэффициент упаковки источника × K;
  `КоличествоУпаковок` не меняется; без совместимой упаковки — базовая единица приёмника, `КоличествоУпаковок` =
  базовое количество приёмника, цена = цена упаковки источника / (коэффициент упаковки источника × K). Количество
  приёмника считается этими формулами напрямую, а не `РассчитатьКоличество` от локальной упаковки; контроль перед
  записью — базовое количество строки = количество источника × K. Тесты с K ≠ 1 для поступления и установки цен.
  **Упаковка**: на **каждом** применении, в том числе по сохранённому соответствию по Ид, проверяются владелец
  упаковки для номенклатуры строки (та же функция допустимости, что в форме) и совместимость коэффициента по
  формуле выше; соответствие по Ид → упаковка номенклатуры с
  тем же наименованием **и совместимым коэффициентом** → нет (или коэффициент разошёлся):
  базовая единица — `Упаковка` пустая, `КоличествоУпаковок = Количество` (базовое), цена — за базовую единицу
  (20 шт. по 10 вместо 2 уп. по 100 при K = 1), суммы те же. Перед записью — контроль количества по формуле,
  иначе отложить. Запись **обычная** (без `ОбменДанными.Загрузка`): срабатывают
  проверки, итоги, дата запрета.
- **Проведение**: поступление создаётся **непроведённым** — проведение (движения товаров при неордерном складе и
  взаиморасчёты с поставщиком всегда) делает покупатель, проверив документ; для мобильной приёмки менеджер
  проводит поступление на ордерный склад. Исключение — опция узла `ПроводитьПоступление`: поступление **только
  товаров** на ордерный склад проводится сразу (появляется к оформлению и в мобильной приёмке 2.0.17.16).
  Поступление с услугами (только услуги или смешанное) не проводится автоматически никогда. Ошибка проведения —
  откат объекта целиком, объект в отложенных с текстом ошибки.
- **«Принято»** (проверяется под блокировкой поступления) = поступление **проведено** (кем угодно — его
  проведение уже дало взаиморасчёты) **или** есть оформленные ордера/черновик мобильной приёмки. Принятое
  обменом не изменяется, не распроводится и не помечается — изменения реализации откладываются с текстом; чтобы
  принять исправление продавца, покупатель отменяет проведение своего поступления и нажимает «Повторить».
  Сценарий: услуги → проведение покупателем → оплата → изменение и отзыв реализации — отложены, поступление и
  оплата не тронуты.
- **Повтор/изменение** (тот же Ид, новая версия): не принято — шапка и строки перезаполняются, документ
  перепроводится по правилу выше; принято — объект откладывается: «Поступление уже принимается — изменение
  реализации не применено», поступление не трогается.
- **Отмена проведения/удаление/отзыв** реализации: не принято — поступление помечается на удаление (с отменой
  проведения); принято — отложить с текстом. Новая ревизия «Проведен» после отзыва — пометка снимается,
  документ перезаполняется.

**Установка цен → установка цен** (`ПриниматьЦены`): вид цен — строка `Узел.ВидыЦенПриема` по Ид вида цен партнёра
(нет строки — отложить); у вида-приёмника **та же валюта и тот же режим `ЦенаВключаетНДС`**, что у вида из сообщения, иначе объект откладывается
(молчаливого переноса числа между несовместимыми видами нет, пересчёта валюты и НДС в первой версии нет);
номенклатура — тем же сопоставлением, несопоставленные строки — объект откладывается целиком;
`ХозяйственнаяОперация` = `УстановкаЦенНоменклатуры`. **Порядок установок одной даты**: `ЦеныНоменклатуры`
подчинён регистратору (позиция регистратора — дата и ссылка), поэтому новая установка цен получает **ссылку с
uuid источника** (`ПолучитьСсылку(Новый УникальныйИдентификатор(Ид))` + `УстановитьСсылкуНового`): порядок
установок одной даты от одного источника совпадает с исходным при любом порядке доставки. Документ с такой
ссылкой уже есть и не наш (нет соответствия) — объект откладывается. Тест: две установки одной даты, доставка в
обратном порядке, затем отмена действующей — срез совпадает с базой источника. **Единица цены**: цена в сообщении — за упаковку строки
(`Упаковка: {Ид, Наименование, Коэффициент}`, пустая — базовая единица); упаковка сопоставляется как в поступлении
(Ид → наименование **и** совместимый коэффициент); не сопоставлена — строка в базовой единице приёмника с ценой
/ (коэффициент упаковки источника × K).
Переходы по соответствию:
- «Проведен», соответствия нет — новая установка цен, записать и провести;
- «Проведен», есть — снять пометку удаления (если стоит) в той же транзакции, перезаполнить строки, перепровести;
  цепочки Проведен → Отозван → Проведен и Проведен → Удален → Проведен — в тесте `ОбменЦеныСостояния` (пометка,
  проведение, срез цен);
- «НеПроведен» — отменить проведение своей установки (срез цен возвращается к прежним установкам);
- «Удален»/«Отозван» — отменить проведение и пометить на удаление.
После каждого перехода тесты сверяют срез `ЦеныНоменклатуры`. Эхо — см. регистрацию.

### Выгрузка

**Размер пакета**: сообщение ограничено 500 объектами и 5 МБ сериализованного тела (константы модуля); лимит
проверяется **до** фиксации исходящего слота, остальные регистрации уходят следующими сообщениями. Кандидаты
просматриваются **страницами с курсором** (лимит просмотра отдельно от лимита сообщения); ревизия, которая не
помещается в сообщение даже одна, получает отметку «слишком велика» в исходящей записи и исключается из выборки до
новой ревизии (регистрация сохраняется). Тест: первая страница — только слишком большие объекты, допустимый
документ на следующей — уходит. Одиночный
объект больше лимита — не выгружается: ошибка в состоянии узла и мониторе («документ слишком велик для обмена»),
прочие объекты идут дальше. Интеграционный тест начальной синхронизации через HTTP с уменьшенным лимитом тела.

**Регистрации без платформенной нумерации**: `ПланыОбмена.ВыбратьИзменения` и
`УдалитьРегистрациюИзменений(Узел, НомерСообщения)` **не используются** — платформа присвоила бы номер сообщения
всем выбранным регистрациям, и квитанция сняла бы и те, что не вошли в пакет. Кандидаты — запросом к таблицам
изменений (`Документ.РеализацияТоваровУслуг.Изменения`, `Документ.УстановкаЦенНоменклатуры.Изменения`, отбор по
узлу, упорядочено, с лимитом пакета) — чтение номеров не присваивает. Квитанция номера N: для каждой записи
`ЖурналОтправкиОбмена` с номером ≤ N — `УдалитьРегистрациюИзменений(Узел, Ссылка)` **только если** текущая
`Ревизия` исходящей записи = отправленной (изменение после отправки остаётся зарегистрированным). Каждая строка
журнала обрабатывается **одной транзакцией** с блокировками в порядке регистрации — документ (разделяемая) →
исходящий ключ (исключительная): перечитать ревизию, обновить `ПодтвержденнаяРевизия`, условно снять регистрацию,
удалить строку журнала. Интеграционный тест (два сеанса): перепроведение между чтением ACK и снятием регистрации
— регистрация остаётся. Интеграционный
тест: два объекта по 3 МБ при лимите 5 МБ — после ACK первого сообщения второй остаётся зарегистрированным и
уходит следующим.

`ВыгрузитьСообщение(Узел, ЗаписьXML)`: `ЗаписьСообщения.НачатьЗапись` (только оболочка: от, кому, номер), по
отобранным кандидатам — для каждого документа **согласованный снимок**: короткая транзакция с разделяемой управляемой
блокировкой документа и затем его исходящей записи (тот же порядок, что у регистрации: документ → исходящая
запись), в ней читаются содержимое, проведённость, принадлежность узлу и `Ревизия`, формируется неизменяемая
структура объекта, транзакция завершается до записи в поток и транспорта. `УдалениеОбъекта` → состояние «Удален»
с ревизией исходящей записи; `ЗакончитьЗапись`. Номер сообщения и отправленные ревизии пишутся в `ЖурналОтправкиОбмена`
(для квитанции). Регистрация снимается платформой после квитанции партнёра.

### Отпечаток результата конвертации (решение 23-го круга)

Отпечаток считается не по сообщению, а по **результату конвертации** — нормализованным шапке и строкам документа-
приёмника, полученным текущими правилами и справочниками (номенклатура, характеристика, упаковка и её
коэффициент, базовая единица, ставка НДС, вид цен, суммы). Изменение любой локальной зависимости (коэффициент
упаковки, базовая единица, валюта или режим НДС вида цен) даёт другой отпечаток, и быстрый выход её не пропускает.
Конвертация выполняется во временный объект; совпал с сохранённым при существующем документе — только ревизия;
иначе — проверки «Принято» и запись. Тест: изменение локального коэффициента упаковки и затем неизменное
содержимое — применяется новый коэффициент. `ВерсияПравилКонвертации` остаётся для монитора («Применить заново»).

**Тип номенклатуры** (решение 23-го круга): строки товаров сопоставляются только с номенклатурой типа «Товар»,
услуги — только «Услуга»; проверка — при автоматическом и ручном сопоставлении и при каждом использовании
сохранённого соответствия. Отрицательные тесты: товар на услугу и наоборот.

### Отпечаток содержимого

Новая ревизия не всегда значит новое содержимое (перепроведение неизменной реализации). Входящее соответствие
хранит `ОтпечатокСодержимого` — SHA-256 нормализованной структуры объекта без `Ревизия` **плюс
`ВерсияПравилКонвертации` узла** (реквизит узла, растёт при любом изменении локальных правил: сопоставления
номенклатуры, характеристик, упаковок, единиц) — и `ДанныеПрименения` (ХранилищеЗначения — последняя применённая
структура объекта). Совпадение отпечатка = то же содержимое **и** те же правила:
новая ревизия с тем же отпечатком и состоянием **при существующем документе-приёмнике** — обновляется только
ревизия (и поколение) соответствия и удаляется отложенная запись, если её пара (поколение, ревизия) не новее
принятой — атомарно; документ не пишется, отложенный объект не создаётся (и у принятого поступления тоже). Тест:
применено A → отложено B → снова A — отложенная B закрыта. **Владение установками цен из обмена**: установку цен,
созданную обменом (`СозданОбменом`), локально изменить, распровести или пометить нельзя — `ПередЗаписью` (подписка
обмена) отказывает всем, кроме записи загрузчиком (`ДополнительныеСвойства.ЗаписьОбменом`); поэтому совпадение
отпечатка означает и актуальность документа. Свои цены поверх — новой установкой цен. Поступление из обмена
локально правит покупатель — правка непроведённого его право, проведённое считается принятым (см. «Принято»).
Тест: локальное изменение и отмена проведения установки цен из обмена — отказ.
**Повторное применение после смены правил**: входящее соответствие хранит отдельным ресурсом
`ВерсияПримененныхПравил` (из хеша её не извлечь); монитор показывает объекты с `ВерсияПримененныхПравил` <
`ВерсияПравилКонвертации` узла и команду «Применить заново» — **отдельный серверный путь**
`ОбменМеждуБазамиВызовСервера.ПрименитьЗаново(Узел, ТипОбъекта, ВнешнийИд)`: право изменения узла до привилегий,
те же блокировки (настройки узла → ключ → документ), берёт `ДанныеПрименения`, отказывает при наличии более нового
отложенного состояния, ревизию источника не трогает, после успеха пишет новый отпечаток и
`ВерсияПримененныхПравил`:
установки цен пересчитываются обычным путём `ПрименитьОбъект` (дата запрета, владение); непринятые поступления —
перезаполняются; принятые — конфликт в отложенных («правила изменились после приёмки»). Тест: изменение K после
успешной загрузки цен → повторная доставка неизменного содержимого с новой ревизией применяет новый K; «Применить
заново» без новой ревизии — тоже, движения цен фактически меняются.
Существование документа проверяется **до** сравнения отпечатков: документа нет — ветка «физически удалён» (тест:
удаление без отзыва, затем неизменное содержимое — документ восстановлен). Тест: повторное проведение неизменной реализации
после принятия поступления — не отложено.

### Неизменяемое исходящее сообщение (stop-and-wait)

Номер сообщения не должен расти от неудачных отправок. Сформированное сообщение сохраняется в регистре
`ИсходящееСообщениеОбмена` (Узел; ресурсы `ПоколениеОбмена`, `НомерСообщения`, `Тело` — ХранилищеЗначения,
`Хеш`) **до** первой попытки доставки; пока партнёр не подтвердил этот номер, каждый обмен повторяет **то же**
сообщение (тот же номер и байты; файл каталога остаётся, HTTP отправляет сохранённое тело), новые изменения ждут
квитанции. Новое сообщение формируется только после подтверждения предыдущего. **Квитанции — отдельный канал**:
чистая квитанция — подписанный ACK (`Ack_<от>_<кому>_<поколение>_<принятый номер>.xml/.sig` в каталоге; в HTTP —
элемент ответа и/или отдельный `POST /ack/{Код}`), несёт `ПринятыйНомер`, поколение и состояние пары; отправляется
**в любой момент**, в том числе при занятом слоте данных, и сам подтверждения не требует (новый ACK заменяет
старый, старые ACK-файлы удаляются получателем после обработки). Тесты: одновременная отправка данных обеими
сторонами — оба слота освобождаются ACK-ами; новые изменения у стороны, ранее отправившей чистую квитанцию, —
уходят новым сообщением с данными. Так восстановленная база не может
«обогнать» номер партнёра неудачными попытками. **Наблюдения состояния партнёра**: каждое исходящее сообщение и
каждый ACK несут снимок состояния пары отправителя (`ПринятыйНомер`, `ОтправленныйНомер`, поколение) с
`НомерНаблюдения` — счётчиком отправителя, который растёт при **формировании** каждого снимка (сохранённое
неизменяемое сообщение несёт свой старый номер наблюдения). Получатель учитывает снимок, только если его
`НомерНаблюдения` больше последнего учтённого (более старый снимок, например замороженное сообщение после свежего
ACK, состояние не обновляет и регрессию не проверяет). Регрессия в более свежем снимке или уменьшение самого
`НомерНаблюдения` — **подозрение на откат**: обмен данными приостанавливается, подозрение подтверждается свежим
служебным запросом состояния (HTTP `GET /state/{Код}`; каталог — следующий ACK партнёра, сформированный после
запроса `State_*`), подтвердилось — обмен останавливается до восстановления пары, ничего не применяя. Тест:
ACK доставлен раньше ранее сформированного, но ещё не принятого сообщения — без остановки. **Порядок классификации** (после проверки подлинности): поколение →
номер → хеш. Номер ≤ принятого и хеш совпадает с сохранённым — идентичный повтор: не обновляет наблюдаемое
состояние партнёра и не проверяет его регрессию (только квитанция/ответ). Хеши хранятся для последних 100 принятых
номеров; номер старше окна — устаревший повтор: игнорируется без обновления состояния (запись в журнал узла). Номер ≤
принятого с другим хешем — признак отката (см. ниже). Новый номер — обычная обработка с проверкой регрессии.
Тест: повторная доставка №10 после успешного №11 — без остановки. Интеграционный тест: восстановление A → B недоступна несколько опросов →
связь восстановлена — обмен остановлен для сверки до применения новых документов.

### Восстановление базы из копии

Номера сообщений и ревизии монотонны, пока ни одна база не откатывалась. Узел хранит `ПоколениеОбмена` (Число,
одинаковое у пары), оно передаётся в оболочке каждого сообщения; сообщение другого поколения не применяется.
**Обнаружение отката**: (а) партнёр подтверждает номер больше нашего `ОтправленныйНомер`; (б) поколение меньше
нашего; (в) **идентичность принятого сообщения**: состояние узла хранит для последних принятых сообщений
(поколение, номер) → SHA-256 тела; сообщение с тем же поколением и номером, но другим хешем — не повтор, а признак
отката отправителя (повторно выданный номер), квитанция по нему не обрабатывается. При (а)–(в) узел останавливается (`ОбменВключен = Ложь`) с ошибкой «Вероятно, одна из баз восстановлена из
копии: выполните восстановление пары». **Восстановление пары** — команда монитора на обеих сторонах (по
инструкции, права настройки), **переход поколения возобновляемыми шагами** под захватом узла с отметкой шага в
состоянии узла (авария на любом шаге — повтор команды продолжает с отмеченного шага): (1) диагностика прежнего
поколения (счётчики, исходящий слот, журнал) сохраняется в запись журнала узла; (2) сбрасываются
`ИсходящееСообщениеОбмена`, счётчики сообщений и `ЖурналОтправкиОбмена` прежнего поколения; (3) новое поколение и
инициализация сверки ключей. Тест: восстановление с заполненным исходящим слотом, авария после каждого шага.
Далее: узел переходит в **режим восстановления** (`РежимВосстановления` в состоянии узла): диспетчер и
аутентифицированный сервис пропускают только сообщения сверки ключей и их ACK, документы не выгружаются и не
применяются; обычный обмен — после двустороннего завершения сверки, автоматически. Тест: восстановление только
штатными командами, без ручного изменения флагов и регистров. Затем: `ПоколениеОбмена` := согласованное новое значение (вводится
одинаковым на обеих сторонах); счётчики сообщений узла обнуляются (`ОтправленныйНомер`, `ПринятыйНомер`);
ревизии сравниваются только внутри поколения — входящее соответствие хранит `ПоколениеОбмена` применённой
ревизии, объект нового поколения применяется как более новый (с учётом отпечатка — без лишних записей); полная
сверка состава (все документы ≥ границы и все исходящие записи) перерегистрирует отправленное; соответствия не
удаляются. **Двусторонняя сверка ключей — сохраняемый этап протокола**: регистр `СверкаВосстановленияОбмена`
(Узел, ИдСверки; ресурсы — пакеты ключей, `ОтправленПеречень`, `ПереченьПодтвержден`, `ПолученПеречень`,
`Завершена`). Пока свой перечень не подтверждён партнёром, **каждое** сообщение нового поколения несёт объект
«ПереченьКлючей» (пакетами) с ИдСверки, независимо от номера транспортного сообщения; получатель отвечает
объектом «ПереченьКлючейПринят». Восстановление завершено (обычный обмен документов разрешён) только после
подтверждения перечней обеих сторон. Тест: потеря первого HTTP-ответа — перечень уходит повторно. Перечень —
**объединение** входящих соответствий и отложенных объектов узла (включая ни разу не применённые): Тип, Ид,
поколение и ревизия. Источник
сравнивает его со своим составом. **Каждый** документный ключ перечня обрабатывается: документ существует, но
исходящей записи нет (утрачена откатом) — исходящая запись восстанавливается (с отметкой прежнего участия в
обмене и, если нужно, `РазрешенВнеГраницы`), затем выдаётся актуальное состояние или отзыв по предикату
принадлежности (с учётом того, что ключ уже участвовал в обмене — граница истории к нему не применяется). Тест:
восстановление после расширения границы истории и после включения отдельного старого документа. Ключ, которого у
источника нет (документ создан и доставлен после копии
восстановленного источника), — источник выдаёт для него ревизию «Отозван» нового поколения (исходящая запись
создаётся по ключу); получатель применяет отзыв обычным правилом — принятое поступление не отменяется, а
откладывается конфликтом «документ источника утрачен при восстановлении»; ключ, который у получателя только
отложен (документа нет), закрывается терминальным результатом «Утрачен у источника» — отложенная запись
удаляется, документ не создаётся. Тест: утраченный источником документ, у получателя впервые отложенный. **Файлы и журнал по поколениям**: имена
`Message_<от>_<кому>_<поколение>_<номер>.xml/.sig`, получатель **сначала** просматривает все адресованные ему файлы любых поколений: файл другого поколения после
проверки подписи — старше текущего и не новее последнего принятого старого поколения — устаревший (в карантин);
иначе (старшее поколение партнёра, чем наше, или младшее, чем ждём, с номером, которого мы не принимали) —
свидетельство рассогласования: диагностика в состоянии узла, обмен останавливается до восстановления пары, тело и
квитанция не применяются; к загрузке идут только файлы текущего поколения. Интеграционный тест: восстановление
одной стороны из копии, предшествующей последней смене поколения; при
восстановлении файлы прежних поколений переносятся в подкаталог `quarantine` каталога обмена; `ЖурналОтправкиОбмена`
получает измерение `ПоколениеОбмена`, записи прежнего поколения удаляются процедурой восстановления. **Отложенные
прежнего поколения**: `ВходящиеОбъектыОбмена` хранит `ПоколениеОбмена`; сравнение везде — по паре (поколение,
ревизия); при восстановлении отложенные прежнего поколения получают статус «ОжидаетСверки» — не применяются
автоматически и не повторяются кнопкой, пока объект нового поколения их не заменит или сверка ключей не отзовёт.
Интеграционные тесты: восстановление каждой стороны из копии, сделанной до успешно квитированного обмена, — состав
совпадает, дублей нет; документ, созданный, доставленный и квитированный после копии источника, — отозван/конфликт;
оставшиеся XML, SIG и неквитированные записи журнала прежнего поколения — в карантине; большая отложенная ревизия
старого поколения заменяется меньшей ревизией нового.

### Блокировки (уже в 6.1)

- **Запуск обмена узла**: захват `СостояниеОбменаМеждуБазами.ВыполняетсяС/СеансВыполнения` под управляемой
  блокировкой записи узла с **токеном владельца** (`УникальныйИдентификатор`, ресурс `ТокенВыполнения`); запись
  живого сеанса (`ПолучитьСеансыИнформационнойБазы`, номер и начало сеанса) — отказ «обмен уже выполняется» **без
  ограничения по возрасту**; сеанс завершён — захват. Перед `ЗакончитьЧтение`, перед публикацией ответа (файл,
  HTTP-ответ) и при снятии токен сверяется: не наш — работа прерывается, чужой захват не снимается. Снятие — в
  `Попытка/Исключение`. Тем же захватом
  пользуются ручной запуск, «Повторить» отложенные, регламентное задание и HTTP-обработчик (6.2).
- **Объект**: блокировка ключа соответствия и документа-приёмника — см. `ПрименитьОбъект`.
- **Настройки узла**: загрузчик берёт **разделяемую** управляемую блокировку узла (`ПланОбмена.ОбменМеждуБазами`,
  Ссылка) от чтения соответствия до фиксации документа; запись узла с изменением `ВидыЦенПриема` берёт
  **исключительную** блокировку узла до проверки использования строк и записи. Интеграционный тест: гонка первой
  загрузки с изменением/удалением строки двумя сеансами.
- Порядок: захват запуска (вне транзакции, флаг) → настройки узла → ключ соответствия → документ-приёмник →
  блокировки самого документа.

### Подлинность сообщений «Каталога»

Код отправителя в оболочке — адресация, а не подпись. Для каталога каждое сообщение **подписывается**:
HMAC-SHA256 (`ХешированиеДанных` + ключ узла, побайтовая схема HMAC — общая функция с тестом на эталонных векторах
RFC 4231) по байтам файла сообщения; подпись — в файле `<имя>.sig`. Ключ — 32 случайных байта, общий для пары,
хранится в `УчетныеДанныеОбмена.КлючПодписи` (без прав у ролей), генерируется мастером одной стороны и вводится на
второй. Проверка подписи — **до** `НачатьЧтение`, квитанции и применения: нет подписи или не совпала — файл не
читается, результат «Ошибка: подпись не подтверждена». Отрицательный интеграционный тест: участник A кладёт файл
от имени B — не применяется. Рекомендация в инструкции: отдельный каталог на пару с правами только двух служебных
учётных записей серверов (ACL — мера окружения, подпись — мера maERP). HTTP подписи не требует: TLS +
аутентификация пользователя, привязанного к узлу.

**Настройка ключа — в 6.1**, командами формы узла (серверный метод `ОбменМеждуБазамиПолныеПрава.УстановитьКлючПодписи`
с проверкой права изменения узла до привилегий): «Создать ключ подписи» — генерирует ключ и **один раз** показывает
его для передачи партнёру (повторный показ невозможен, только пересоздание); «Ввести ключ подписи» — на второй
стороне. Узел «Каталог» без ключа не включается (проверка записи узла). Приёмочный тест 6.1 настраивает пару этими
командами, без прямой записи регистра.

**Публикация пары файлов**: тело, номер и состав журнала отправки атомарно сохранены в исходящем слоте
**до** публикации (см. «Неизменяемое исходящее сообщение»); публикация из слота: оба файла пишутся во временные
имена, сначала переименовывается `<имя>.sig`, **последним** — `<имя>.xml` (признак готовности). Получатель
рассматривает только окончательные `.xml` (временные имена и `.sig` без `.xml` игнорирует). Сбой между
переименованиями — следующая попытка **повторяет публикацию той же пары** (тот же номер, те же байты, тот же
состав журнала), номер не пропускается. Интеграционный тест: сбой между каждым переименованием — номер, байты и
состав журнала неизменны.

### Транспорт «Каталог» и ручной запуск

**Квитанции — только ACK-каналом** (см. «Неизменяемое исходящее сообщение»): файл `Message_*` всегда несёт данные
(объекты), пустых нумерованных сообщений нет; чистое подтверждение — только ACK, который не занимает платформенный
номер, исходящий слот и журнал отправки. Ответ после загрузки: ACK — всегда, если входящее сообщение содержало
объекты; сообщение с данными — только если у узла есть зарегистрированные изменения и слот свободен. На ACK ответа
нет. **Завершение приёма**: файл `Message_*` удаляется после публикации ACK; ACK-файл — после фиксации его
обработки (сбой — повтор обрабатывает его как уже учтённый и удаляет). Тесты: после доставки одного документа и
подтверждения каталог пуст несколько циклов опроса; «данные A → ACK B → новые данные B» при пустых очередях
между шагами.

`ВыполнитьОбмен(Узел)`: имена файлов **неизменяемые, с номером сообщения** —
`Message_<от>_<кому>_<поколение>_<номер>.xml`, отправитель никогда не перезаписывает файл (новое сообщение — новый номер, запись
во временный файл и переименование). Получатель читает входящие файлы по возрастанию номера (загрузка,
`ЗакончитьЧтение`), затем выгружает ответ своим файлом и **только после публикации ответа** удаляет прочитанные
экземпляры по их точным именам (файлы с номером ≤ принятого); чужие и новые номера не трогает. Сбой между приёмом
и удалением — следующий запуск читает тот же файл как уже принятый (тело не применяется) и публикует ответ. Тест
двух баз: остановка между публикацией ответа и удалением входящего. Каталог — на сервере 1С (путь сервера). Ошибка чтения файла (чужой
отправитель, номер) — результат «Ошибка», файл не удаляется. Права: запуск — роль `ОбменМеждуБазамиНастройка` или
право `Изменение` на план обмена; сама работа — привилегированно в модуле, проверка права — до.

### Тесты (6.1)

Транспорт не нужен: тесты гоняют `ДанныеОбъекта` → `ПрименитьОбъект` на узле в одной базе. `ТестыДокументов`
выполняют сценарий во внешней транзакции, поэтому сценарии с **настоящим откатом** (ошибка проведения → документа
нет → отложенный объект в независимой транзакции → «Повторить»), частичным приёмом сообщения, квитанциями,
перезапуском, файлами двух баз и фоновыми заданиями — **интеграционный прогон** `scripts/exchange-it.sh`: две
копии базы (`build/ib-kp` и вторая одноразовая копия) без внешней транзакции раннера, обработка-сценарий через
`/Execute`, результат — следующим вызовом. В `ТестыДокументов` — только сценарии, проверяемые внутри одной
транзакции (конвертация, суммы, упаковки, валюта, сопоставление, регистрация, эхо, права).
- `ОбменРеализацияПоступление`: реализация → данные → поступление создано непроведённым; с `ПроводитьПоступление`
  на ордерный склад (только товары) — проведено; строки и окончательные суммы совпадают, `КодСтроки`, назначение
  кладовщика из узла, соответствие записано; смешанная реализация с опцией — не проведена.
- `ОбменПовторИзменение`: та же версия — без изменений; новая версия до приёмки — строки перезаполнены; после
  оформления ордера — отложено, поступление не изменено.
- `ОбменНетНоменклатуры`: штрихкода и артикула нет — отложено, перечень строк в ошибке; добавили штрихкод →
  «Повторить» — применено, отложенная запись удалена.
- `ОбменУдалениеРеализации`: «Удален» до приёмки — поступление помечено на удаление.
- `ОбменЦены`: установка цен с видом цен узла → проведённая установка, цены в регистре.
- `ОбменРегистрация`: проведение реализации регистрирует на узел своего контрагента и организации, на чужой — нет;
  непроведённая — нет.
- `ОбменСообщениеКаталог`: выгрузка в каталог создаёт файл с оболочкой и объектом (чтение файла собственной
  базой — отказ платформы по отправителю → результат «Ошибка», файл на месте).
- `ОбменСкидкиУпаковки`: реализация с процентной и суммовой скидкой — суммы поступления равны суммам реализации,
  цена — эффективная; упаковки нет у покупателя — базовая единица (20 по 10), одноимённая упаковка с другим
  коэффициентом — не сопоставляется.
- `ОбменСменаПолучателя`: реализация отправлена узлу A, контрагент сменён на B — A получает «Отозван», B — документ;
  у A непринятое поступление помечено на удаление.
- `ОбменПринято`: проведённое покупателем поступление (любой склад) — изменение и отзыв реализации отложены,
  поступление не тронуто; после отмены проведения покупателем «Повторить» применяет изменение.
- `ОбменКвитанция`: после чтения ответа партнёра регистрации по подтверждённому номеру сняты, изменение, сделанное
  после отправки, осталось зарегистрированным; сбой сохранения отложенного — номер принятого не изменился.
- `ОбменЦеныНесовместимые`: вид-приёмник в другой валюте или с другим режимом НДС — отложено; цена упаковки без
  сопоставленной упаковки — в базовой единице (цена / коэффициент), одноимённая упаковка с другим коэффициентом —
  не сопоставляется.
- `ОбменЭхо`: установка цен из обмена не зарегистрирована **ни на один** узел — при первом проведении, повторной
  загрузке и локальном перепроведении.
- `ОбменПовторСообщения`: сообщение с уже принятым номером — тело не применяется, ответ формируется; файл ответа не
  записан после приёма (сбой) — следующий запуск восстанавливает ответ.
- `ОбменРевизии`: повтор отзыва — без действий; удаление и отзыв с ревизией; новая ревизия после отзыва
  восстанавливает документ; ошибка проведения — документа нет, после исправления причины «Повторить» создаёт один
  документ.
- `ОбменРевизииОтзыва`: отзыв → квитанция отзыва приходит после регистрации восстановления — восстановление
  уходит с новой ревизией; исходящая запись сохраняется.
- `ОбменСнимок`: проведение документа фоновым заданием (второй сеанс) между чтением документа и ревизии
  невозможно — разделяемая блокировка; если файловая база не даёт фоновое задание в тесте — проверка порядка
  блокировок ревью и регресс человека.
- `ОбменДатаЗапрета`: изменение поступления и установки цен в закрытом периоде из обмена — отложено.
- `ОбменЦеныСостояния`: «НеПроведен» и «Удален» возвращают срез цен.
- `ОбменЗапуск`: второй запуск обмена узла при живом первом — отказ; запись мёртвого сеанса — захват.
- `ОбменУчетныеДанные`: пароль пишется и не читается ролью без привилегированного модуля (`ПравоДоступа` на регистр
  у всех ролей — нет).
- Смок: форма узла, монитор. Живая проверка двух баз — на копиях `build/ib` и `build/ib-kp` (обмен через каталог)
  мной headless-обработкой, результат — в отчёте фазы.

## 6.2. HTTP, расписание, мастер

- **HTTP-сервис `ОбменМеждуБазами`** (корневой URL `exchange`), шаблон `/message/{Код}`; метод `POST`: тело —
  сообщение партнёра → загрузка → ответ — исходящее сообщение для этого партнёра (один вызов = обмен в обе стороны).
  **Технический пользователь — один на узел**: узел хранит `ИдПользователяСервиса` (Строка 36 — УникальныйИдентификатор
  пользователя ИБ, не имя); запись узла под исключительной блокировкой «назначение пользователей сервиса» проверяет,
  что этот пользователь не назначен другому узлу (отказ). Отрицательный тест: один пользователь двум узлам —
  отказ записи. **Одна проверка для всех методов** (`message`, `poll`, `ack`, `state`, `ping`) — до чтения тела:
  роль `ОбменМеждуБазамиСервис`, узел по коду URL существует, `ПользователиИнформационнойБазы.ТекущийПользователь()
  .УникальныйИдентификатор` = `Узел.ИдПользователяСервиса` (технический пользователь привязан к узлу; пользователь узла A не может говорить от
  имени B); затем отправитель оболочки = узел URL. Ответы: 200 — сообщение, 403 — нет роли или пользователь не
  этого узла, 404 — нет узла, 409 — обмен узла уже выполняется, 500 — текст ошибки без стека. Тест: пользователь
  узла A вызывает URL узла B — 403, тело не читается.
- **Роль `ОбменМеждуБазамиСервис`** (технический пользователь базы-приёмника): только право на HTTP-сервис и чтение
  плана обмена; обработчик проверяет `РольДоступна` и вызывает модуль приёма в привилегированном режиме. Пользователь
  с этой ролью интерактивно не входит (роль без прав на интерфейс, в отчёте — инструкция: аутентификация 1С, без ОС,
  «Запрещено изменять пароль» снято не будет — пароль меняет администратор).
- **Транспорт HTTP** у инициатора: **только HTTPS** — адрес не `https://` отклоняется при записи узла и перед
  соединением; `ЗащищенноеСоединениеOpenSSL` с проверкой сертификата сервера (`СертификатыУдостоверяющихЦентровОС`);
  ответы 3xx — ошибка, перенаправление не выполняется (учётные данные не уходят на другой адрес); Basic из
  `УчетныеДанныеОбмена` (только серверно, привилегированно), таймаут 120 с; ответ → загрузка входящего.
- **Обязательный опрос каталога**: регламентное задание-диспетчер включено, пока есть хотя бы один включённый
  узел «Каталог», HTTP-инициатор или узел с `ОбменПриПроведении` — независимо от пользовательских флагов и
  расписаний (включение/выключение — при записи узла). Диспетчер обходит **все включённые** узлы «Каталог» и
  HTTP-инициаторы каждый запуск (запись узла с изменёнными фильтрами дополнительно будит его фоновым заданием):
  `ПоколениеФильтров` > `ПоколениеЗавершеннойСверки` или `СтатусСверки` = «Выполняется» — обмен со сверкой;
  есть входящие файлы — обмен узла; `ПоколениеСобытий` > `ПоколениеОбработано` — обмен; есть неподтверждённые
  регистрации и последняя выгрузка старше 15 минут — повторная выгрузка (квитанции партнёру уходят тем же
  ответом); HTTP-инициатор — не реже раза в 15 минут. Не зависит от пользовательского расписания. Интеграционный
  тест: меняется только A, `ОбменПриПроведении` и пользовательские расписания обеих сторон выключены — документ и
  квитанция доставляются автоматически; исключение вида цен и расширение границы истории на полностью квитированной
  паре без новых записей документов — сверка запускается диспетчером.
- **Опрос HTTP**: `POST /poll/{Код}` — тело: ACK инициатора (без платформенного номера и исходящего слота);
  ответ: ACK отвечающей стороны и, если у неё есть, её **сохранённое** исходящее сообщение данных (то же самое при
  повторе); пустая очередь — только ACK. Подтверждение полученного ответа — ACK инициатора в следующем запросе;
  потерянный ответ — следующий опрос получит то же сообщение. Данные инициатора уходят `POST /message`. Тесты:
  изменения только у B при пустой очереди A доставляются опросом; потеря первого ответа.
- **Встречные запуски**: HTTP-обмен пары запускает только сторона с `ИнициаторHTTP` (один POST — оба
  направления); у второй стороны регламентное задание узел пропускает. Поэтому у инициатора **опрос обязателен**:
  для узла с `ИнициаторHTTP` регламентный обмен идёт по расписанию (не реже раза в 15 минут) независимо от
  `ПоколениеСобытий` и не выключается, пока узел HTTP-инициатор (форма узла и мастер не дают снять); изменения
  неинициирующей стороны уходят ближайшим опросом. Тест: меняется только неинициирующая сторона, пользовательское
  расписание выключено — изменения доставляются опросом. Обе стороны берут один и тот же захват
  узла — инициатор перед POST, отвечающий в обработчике (занят — 409, инициатор повторит позже). Тест —
  одновременный ручной запуск и входящий вызов.
- **Регламентное задание `ОбменМеждуБазами`**: обходит узлы с включённым расписанием (реквизит `ОбменПоРасписанию`,
  интервал — расписание задания, по умолчанию 15 мин, выключено).
- **Обмен при проведении** (`ОбменПриПроведении`): регистрация документа в той же транзакции увеличивает
  `СостояниеОбменаМеждуБазами.ПоколениеСобытий` узла; запуск — после фиксации (`ПослеЗаписиНаСервере` формы и
  команда «Отправить по обмену») фоновым заданием с ключом узла — ускорение, а не гарантия. **Гарантия —
  регламентное задание-диспетчер `ОбменМеждуБазамиПоТребованию`** (раз в минуту; включается само, когда хотя бы у
  одного узла `ОбменПриПроведении`, независимо от периодического расписания): обходит узлы, у которых
  `ПоколениеСобытий` > `ПоколениеОбработано`. Рабочий цикл: под захватом узла запоминает `ПоколениеСобытий` в
  начале прохода, выполняет обмен и **только после успешной публикации** записывает `ПоколениеОбработано` :=
  запомненное; снова сравнивает и повторяет (до 5 проходов). Ошибка, предел проходов или аварийное завершение
  процесса ничего не теряют: `ПоколениеОбработано` не продвинулось — диспетчер возьмёт узел снова (захват мёртвого
  сеанса — по правилу блокировок). Интеграционные тесты: проведение после последнего сравнения, на пятом проходе и
  принудительное завершение процесса между началом прохода и публикацией.
- **Мастер «Настройка обмена с базой партнёра»**: шаги — контрагент и организация → что отправлять/принимать,
  склад и виды цен → транспорт (каталог/адрес, пользователь, пароль, пользователь сервиса этой базы) → код этой
  базы и код партнёра → **сохранить узел выключенным** (`ОбменВключен = Ложь`: не регистрирует, регламент и
  обработчик обмена его пропускают, сервис отвечает только на проверку; регистрация идёт) → после того как партнёр сделал то же
  у себя — «Проверить подключение»: `GET /ping/{Код}` — аутентификация, роль, привязка пользователя к узлу, код
  отправителя; документов не применяет, квитанции не трогает → «Включить обмен» (запускает сверку состава).
- `ai-security` обязателен: публикация, технический пользователь, пароли, привилегированный приём.

### 6.2 в реализации: две сборки и уточнения (2026-11-12)

**Цена установки цен из обмена — за базовую единицу** (2.0.17.19): строка приёмника без упаковки, цена =
цена источника / коэффициент источника (упаковка × K); контроль цен продажи читает регистр как цену базовой
единицы. Положительная цена, округлившаяся до нуля, — ошибка строки (объект откладывается). **Локальные зависимости вне версии правил** (режим НДС и валюта вида цен, коэффициент упаковки):
отпечаток результата меняется при следующей ревизии источника; принудительная перепроверка принятых объектов —
«Применить заново» 2.0.17.20 (по всем входящим соответствиям узла, не только по версии правил).

**Обязательное условие 2.0.17.20 (4-й круг ревью 6.2, P0)**: восстановление пары должно восстанавливать
ручное соответствие «Сопоставить с существующим поступлением» — перечень ключей получателя несёт Ид документа-
приёмника и признак ручного сопоставления, а источник после отката не создаёт второе поступление по такому ключу.
План 2.0.17.20 проходит своё ревью с этим пунктом.

**Конфликт после «Применить заново»** (уточнение к «Повторному применению после смены правил»): запись
`ВходящиеОбъектыОбмена` по принятому поступлению получает `Статус` = «Конфликт» (не «Отложен») с той же

«Конфликт»). Команда «Применить заново» и «Закрыть конфликт» — сборка 2.0.17.20 (монитор и мастер); в 2.0.17.19

- **2.0.17.20 — восстановление и мастер**: восстановление пары, сверка ключей, возобновляемая сверка состава

Уточнения 2.0.17.19 относительно текста 6.2 выше:

1. **Один метод данных вместо `message`/`poll`/`ack`/`state`.** `POST /message/{Код}`: тело — пакет
   `{ACK, Сообщение}` (ACK — квитанция инициатора с его принятым номером; Сообщение — его сохранённое исходящее
   сообщение данных или пусто); ответ — такой же пакет отвечающей стороны (её ACK и её **сохранённое** исходящее
   сообщение, повтор запроса — тот же слот). Опрос = пакет без сообщения. Потерянный ответ: инициатор повторяет
   запрос — его сообщение принимается как повтор (идентичность по хешу), ответ содержит тот же слот. `GET
   /ping/{Код}` — проверка подключения: аутентификация, роль, привязка пользователя к узлу, код отправителя;
   ответ — код этой базы и поколение пары, ничего не применяет.
2. **Подпись пакета HMAC сохраняется и в HTTP**: заголовок `X-Exchange-Signature` — HMAC-SHA256 тела ключом
   пары; запрос без подписи или с неверной подписью — 403 до разбора JSON; ответ подписывается так же и
   проверяется инициатором. Размер тела запроса — не больше `ЛимитФайлаСообщения` × 2 (пакет несёт два текста),
   больше — 413.
3. **Обработчик сервиса**: `РольДоступна("ОбменМеждуБазамиСервис")` → узел по коду URL (привилегированно) →
   `ОбменВключен` (выключен — `message` отвечает 409 с текстом, `ping` отвечает) → `ИдПользователяСервиса` узла =
   УникальныйИдентификатор текущего пользователя ИБ → подпись → захват узла тем же `ЗахватитьУзел` (занят — 409)
   → пакет → освобождение. Ответы 403/404/409/413/500, текст ошибки без стека. Уникальность
   `ИдПользователяСервиса` среди узлов — в `ПередЗаписью` узла под исключительной блокировкой пространства
   «назначение пользователей сервиса»: при смене значения — исключительная блокировка всей таблицы
   `ПланОбмена.ОбменМеждуБазами` (у ссылочных объектов поле блокировки — только `Ссылка`) **до** блокировки
   своей строки, затем запрос других узлов с тем же значением — отказ. Смена пользователя сервиса — редкое
   действие администратора, загрузки на время записи ждут.
4. **Диспетчер — одно регламентное задание `ОбменМеждуБазами`**, раз в минуту, предопределённое; включается
   при записи узла, если есть хотя бы один включённый узел (Каталог или HTTP-инициатор), выключается, если нет.
   Обходит включённые узлы: Каталог — обмен, если есть входящие файлы этой пары, `ПоколениеСобытий` >
   `ПоколениеОбработано`, не завершена сверка состава или последняя выгрузка старше 15 минут при занятом
   исходящем слоте; HTTP-инициатор — то же условие событий/сверки или последний обмен старше 15 минут (опрос
   обязателен); HTTP-неинициатор — пропуск. Узел занят — пропуск без ошибки; ошибка узла — в его состоянии,
   остальные узлы обходятся. До 5 проходов по узлу, пока `ПоколениеСобытий` > `ПоколениеОбработано`.
   Отдельные `ОбменПриПроведении`, `ОбменПоРасписанию` и задание `ОбменМеждуБазамиПоТребованию` не
   вводятся: минутный диспетчер даёт ту же гарантию доставки, фоновый запуск из форм документов — лишняя связь
   форм с обменом (пункт TECHDEBT «запуск сразу после проведения»).
5. **Реквизиты узла 2.0.17.19**: `АдресСервиса` (Строка 500, только `https://`, проверка при записи и перед
   соединением), `ИнициаторHTTP` (Булево), `ИдПользователяСервиса` (Строка 36). Логин и пароль партнёра —
   `УчетныеДанныеОбмена` (`Пользователь`, `Пароль`), вводятся командой формы узла, на клиент не возвращаются.
   Выбор пользователя сервиса — команда формы узла (список пользователей ИБ с ролью `ОбменМеждуБазамиСервис`,
   только администратору).
6. **Клиент HTTP**: `HTTPСоединение` с `ЗащищенноеСоединениеOpenSSL(, Новый СертификатыУдостоверяющихЦентровОС)`,
   таймаут 120 с, Basic из `УчетныеДанныеОбмена` (привилегированный модуль, только сервер); ответ 3xx — ошибка
   без перехода; код ≠ 200 — ошибка с текстом ответа (обрезанным); до 5 пакетов за запуск, пока одна из сторон
   отдаёт данные. Тесты документов работают на одной базе (код этой базы один, пару изнутри не собрать), поэтому
   проверяют разбор и подпись пакета,
   авторизацию обработчика (роль, привязка пользователя, подпись, выключенный узел), уникальность пользователя
   сервиса, отказ `http://`, условия диспетчера; живой обмен двух баз по HTTP — регресс человека и
   интеграционный скрипт 2.0.17.20.
7. **Роль `ОбменМеждуБазамиСервис`**: право `Use` HTTP-сервиса и чтение плана обмена; без интерфейса. В роли
   `ОбменМеждуБазамиНастройка` — Use/View формы выбора пользователя не нужно (команда формы узла).

## 6.3. Договор внутри группы и уборка

- **`ДоговорыСКонтрагентами.ПродажаПоСебестоимости`** (Булево): в реализации по такому договору цена строки при
  заполнении — из **того же порога себестоимости, которым проверяет контроль цены**
  (`КонтрольЦенПродажи.ДобавитьПорогиСебестоимостиСклада` — максимальная себестоимость единицы среди партий-кандидатов
  склада, с допрасходами и ордерами так, как считает контроль; выношу расчёт порога строки в функцию, которую зовут
  и заполнение, и проверка): порог за базовую единицу без НДС → в валюту документа по курсу документа → ×
  коэффициент упаковки → + НДС по ставке строки, если `ЦенаВключаетНДС`. Для такого договора проверка «не ниже
  вида цен» заменяется проверкой «не ниже себестоимости» тем же порогом, **с приоритетом над режимом контроля
  склада**: для такого договора пороги себестоимости строятся и при `НеКонтролировать` у склада (сейчас
  `КонтрольЦенПродажи.ПорогиСклада` для этого режима возвращает пустую таблицу). Действующий допуск «продажа ниже
  минимальной цены» (роль-допуск) на договор группы не распространяется — продажа ниже себестоимости внутри
  группы не допускается; нет оценённой себестоимости — отказ проведения с причиной. Тест: рост себестоимости на
  складе с отключённым контролем — отказ. **Скидки** в строках по такому договору
  обнуляются при заполнении цены (`ПроцентСкидки`, `СуммаСкидки`) — продажа по себестоимости скидки не допускает,
  проведение (`ОбработкаПроведения`, не только проверка заполнения — программная запись её не вызывает) отказывает
  строке со скидкой. Цена — **минимальная представимая** (2 знака, округление
  вверх), при которой сумма строки проходит `КонтрольЦенПродажи.СравнитьСПорогами` (допуск не меняю): после
  расчёта строка проверяется общей функцией контроля; отказ по округлению — +0,01 и повтор, не более 3 поправок;
  прочий отказ контроля (нет себестоимости, ошибка порога) — сразу сообщение с причиной, цена не заполняется; при перепроведении
  после роста себестоимости — отказ как обычно. Дополнительные тесты: дробная себестоимость единицы × большое
  количество; переключение договора на строке со скидкой 100 % — скидка обнулена, цена по себестоимости. Тесты: несколько партий с
  разной себестоимостью (берётся максимальная), перепроведение, оба режима НДС, небазовая упаковка, валюта
  документа ≠ регламентированной.
- **Мёртвые заготовки**: удалить общий модуль `ВнешнееСоединение` (кода, вызывающего его, нет; закрывает TECHDEBT
  `V83.comconnector`); у регистра `ПараметрыОбменаДанными` снять права чтения со всех ролей (пароль открытым
  текстом), форма списка — только администратору; сам регистр и `ИсторияОбменаДанными`/`ОшибкиОбменаДанными`
  не удаляю (у других клиентов могут быть записи — удаление объекта с данными требует обработчика переноса; пункт
  TECHDEBT «удалить после проверки баз клиентов»). Перечисление `ПриложенияДляОбмена` остаётся (измерение регистра).

## Права и безопасность (сводно)

- Пароли — только `УчетныеДанныеОбмена`, без прав у ролей, доступ — `ОбменМеждуБазамиПолныеПрава` (сервер,
  привилегированный, не вызывается с клиента напрямую, право на изменение узла проверяется до привилегий).
- HTTP: только HTTPS с проверкой сертификата, без перенаправлений; технический пользователь привязан к узлу.
- Вид цен-приёмник — только из таблицы `ВидыЦенПриема` узла (отрицательный тест: сообщение с Ид чужого вида
  цен / наименованием существующего вида не меняет его цены).
- Применение входящих объектов — привилегированно (технический пользователь не имеет прав на документы), но
  содержимое сообщения ограничено форматом: создаются только поступления/установки цен на склад/вид цен **из узла**,
  организация и контрагент — **из узла**, не из сообщения. Сообщение не может указать склад, организацию, пользователя.
- Чужой узел и чужой получатель отвергаются загрузчиком; уже принятый номер — тело не применяется (квитанция и
  ответ — да).
- Дата запрета действует (обычная запись, не `Загрузка`).

## Риски

- Ручное создание `.mdo` плана обмена и HTTP-сервиса: формат EDT сверяю по модели метаданных EDT (`~/.p2`, jar
