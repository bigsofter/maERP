## Открытые вопросы владельцу — задать ДО плана

1. **Какие отборы в каких колонках.** Предложение по умолчанию (подтвердить или поправить):
   - «Продукция» верха и `ТЧТовары` заказа на производство — `Продукция` и `Полуфабрикат` (ПФ бывает конечным заказом?);
   - материалы — «Заказы поставщику», «Поступления» — закупаемое (`Товар`, `Сырье`, `Полуфабрикат` со способом
     пополнения «Закупка»/«Оба»?); «Переработка» и `ТЧМатериалы` — `Сырье`, `Полуфабрикат`, `Товар`;
   - услуги и комплекты — нигде.
2. **Как устроен подбор.** а) **отбор по типу в стандартной форме выбора** через `ПараметрыВыбора` колонки
   (рекомендация: дёшево, работает и при вводе текстом, не требует правки формы выбора); б) **свой список выбора**
   по образцу `ПродукцияЗаказаДляВыбора` (`ПоказатьВыборИзСписка`) — удобно для «материалы этого заказа», но не
   заменяет выбор из всего справочника; в) и то и другое: список «из заказа» + пункт «Выбрать из справочника…».
3. **«Материалы этого заказа» в закупках.** В «Заказах поставщику» и «Поступлениях» материал сейчас вводится
   свободно. Предлагать первым списком материалы заказа с дефицитом / остатком к поступлению (данные уже есть в
   `МатериалыЗаказа`)? Разрешать ли материал вне заказа?
4. **«Последние созданные» — где и сколько.** Варианты: а) пункты «последние N созданных» вверху списка выбора
   в колонках продукции (рекомендация: N = 10, по `ДатаСоздания`, все авторы); б) только созданные этим
   пользователем (`Автор`); в) не делать — отбор по типу уже сужает список.
5. **Отбор — жёсткий или мягкий.** Жёсткий (`ПараметрыВыбора`) не даст ввести позицию другого типа вовсе; мягкий
   (список по умолчанию + «Показать все») оставит лазейку. Для материалов, где тип номенклатуры в базах клиентов
   может быть заполнен небрежно, жёсткий отбор спрячет нужную позицию. Рекомендация — жёсткий для продукции,
   мягкий для материалов.
6. **Генератор формы.** а) правка `Form.form` руками, отставание генератора растёт до четырёх сборок
   (рекомендация, если правка формы — только `choiceParameters` колонок; ещё дешевле — задать их программно в
   `НастроитьЭлементы` и форму не трогать вовсе); б) сначала `gen8.py`, догоняющий генератор до формы.

## Ловушки, каждую проверить чтением кода до правки

1. **`ПараметрыВыбора` колонки таблицы-реквизита формы** задаются на `ПолеФормы`, а не на колонке реквизита; для
   `ValueTable` рабочего места это единственный путь (`choiceParameters` в `Form.form` сейчас нет ни одного —
   `workflow-005`: собирать по работающему образцу; образец — `ПереработкиПоставщик.ПараметрыВыбора`).
2. **Отбор по типу и ввод по строке.** Автоподбор номенклатуры (`РаботаСДокументамиКлиент.АвтоподборНоменклатуры`)
   может строить свой запрос и не учитывать `ПараметрыВыбора` — проверить и, если так, передать отбор в
   `ПараметрыПолученияДанных`.
3. **Форма выбора с `customQuery`** (`ФормаВыбора/Form.form:612`) — отбор платформы накладывается на поле основной
   таблицы; убедиться на клиенте, что `Отбор.ТипНоменклатуры` его не ломает (`forms-008/009` — динсписки на закладках
   уже роняли клиента 8.5; смок форму выбора открывает, но отбора не накладывает).
4. **Группы справочника**: отбор по типу у иерархического списка прячет группы, если у групп тип не заполнен —
   проверить, что выбор по-прежнему возможен (или список переключается в плоский, как в `УстановитьПараметрыСписка`).
5. **Данные клиентов** (drissotex, `docs/MERGE-DRISSOTEX.md`): тип номенклатуры может быть не заполнен или заполнен
   иначе — жёсткий отбор спрячет рабочие позиции. Сверить на копии базы клиента, сколько номенклатуры с пустым или
   «Товар» типом используется в заказах на производство.
6. **Колонки «Выпуск» / «Отгрузки» / «Поступления из переработки»** уже выбирают из списка — не навесить поверх
   `ПараметрыВыбора`, которые конфликтуют с `СтандартнаяОбработка = Ложь`.
7. **Генератор** (п. 6 состояния): не запускать `gen7.py` поверх формы.
8. **«ё»** в новых именах не использовать (`YoLetterUsage`); `git add -u` + `git show --stat` для путей с «ё»
   (`workflow-007`).
9. **Headless**: `ib-sync.sh`, по одному тяжёлому процессу, не параллелить с субагентами. `build/ib` может держать
   EDT владельца — тогда копия базы.

## Сценарии уровня 3

Интерфейсный отбор сценарием не проверить (форма выбора — клиент). Уровень 3 проверяет **правило** и серверную
страховку, если она будет:
- функция правила отбора: колонка → типы, для каждой колонки рабочего места и заказа;
- «последние созданные»: порядок по `ДатаСоздания`, предел N, помеченные на удаление не попадают;
- серверная страховка (по ответу 5): строка продукции с сырьём / услугой — отказ без записи.
Расширять существующие сценарии (`АРМПроизводство`, `АРМЗакупки`, `ВидОперацииЗаказа`), новых не заводить.
Интерфейс — ручная приёмка на клиенте со скриншотами развёрнутого окна для базы знаний tinycio.
