# План волны 7: обновление базы клиента на maERP — `retail-client-update`

Мастер-план — `docs/plans/retail-chain.md`, волна 7 и приложения Б, В. Анализ базы — `docs/drissotex-analysis/flycdi-2026-11-09.md`.
Решение владельца 2026-11-12: волна 7 идёт **раньше** сборок обмена 2.0.17.20–21 (восстановление пары, мастер,
договор по себестоимости) — «делай вперёд и отдавай базу». Сборка волны — **2.0.17.20**; восстановление пары и
мастер обмена сдвигаются на 2.0.17.21, договор внутри группы — на 2.0.17.22. Часы — FlyCDI, «Внедрение maERP».

## Задача

Перевести рабочую базу клиента (старая ветка 1C:Commerce, общий корневой uuid с maERP) на maERP загрузкой нашего CF
с реструктуризацией, без потери данных, которые клиент ведёт, и отдать владельцу:

1. **пробную обновлённую базу** — `.dt` из копии выгрузки 2026-11-09 (`build/ib-flycdi`) для проверки владельцем;
2. **комплект переноса для боевой базы**: внешняя обработка выгрузки «до» (запускается на старой конфигурации),
   обработка загрузки «после» в maERP, порядок действий и сверка — клиент работал после 09.11, боевой перенос
   делается на свежей базе тем же комплектом.

### 2. Защита перенесённой истории `Убытки`

Мастер-план, приложение Б: у клиента ПКО по прочим расчётам и расчётам с физлицами пишет отрицательный убыток, в
maERP такой ветки нет — перепроведение молча изменит историю. Замер регистраторов `Убытки` у клиента: РКО ~2 950
(выплата зарплаты, прочий расход, без операции), ПКО ~580 (все с отрицательной суммой — прочее поступление, без
операции), `СписаниеТоваров` 10. **Защищаются только ПКО и РКО** с восстановленным набором: они не входят в
последовательность `Основная`, пересчёт себестоимости их не перепроводит. **Списания** (ревью плана, круг 1, P0):
maERP убыток списания не пишет вовсе (`Убытки.СформироватьДвижения`, ветка списания закомментирована), а списание
входит в `Основная` — его перепроведение сотрёт восстановленный набор. Поэтому записи `Убытки` списаний
переносятся в **один документ `КорректировкаРегистров`** «Перенос убытков списаний из старой редакции» (ручные
движения с периодами исходных строк; документ не проводится и в последовательность не входит — пересчёт его не
трогает), а наборы `Убытки` самих списаний очищаются (иначе после перепроведения — расхождение, до него —
задвоение). Документ корректировки тоже пишется в `ПеренесенныеДокументы`. Поэтому:

- Регистр сведений **`ПеренесенныеДокументы`** (независимый): измерение `Документ` (ДокументСсылка.ПриходныйКассовыйОрдер,
  ДокументСсылка.РасходныйКассовыйОрдер, ДокументСсылка.КорректировкаРегистров), ресурсы `ДатаПереноса`, `Основание` (Строка 100 — «Убытки»). Пишет только
  обработка загрузки переноса (привилегированно), роли — только чтение у администратора.
- **Списания с перенесённым убытком** (круг 3, P0): их убыток живёт в корректировке, поэтому сами списания —
  под **мягкой** защитой (основание «УбыткиСписания»): проведение разрешено (пересчёт себестоимости перепроводит
  их, убыток maERP по списанию не пишет), отмена проведения, пометка удаления и удаление — отказ; набор `Убытки`
  списания можно только очистить (платформа очищает его при перепроведении). Правка товарных строк старого
  списания убыток не меняет — он исторический, в корректировке.

**Обработчик переноса себестоимости продаж (2.0.16.121)** на данных другой ветки: излишек исторических возвратов
и расхождение сверки с регистром продаж — предупреждения с перечнем в журнале регистрации, а не остановка
(пробный прогон: 6 излишков, расхождения по возвратам — себестоимость истории посчитана логикой старой ветки).
Собственные базы maERP эту версию прошли до 2.0.16.150.
- Подписки `ПередЗаписью` и `ПередУдалением` на ПКО, РКО, `КорректировкаРегистров` и `СписаниеТоваров` (общий модуль `ПеренесенныеДокументы`): для
  документа из регистра — отказ **любой** записи объекта (проведение, отмена, запись, пометка удаления — в том
  числе непроводимой `КорректировкаРегистров`, чья форма правит `Объект.Движения` напрямую) и удаления **всем**,
  включая полные права; `ОбменДанными.Загрузка` — пропуск (загрузка истории). Дополнительно — подписка
  `ПередЗаписью` **набора записей `Убытки`**: набор с отбором по защищённому регистратору записывается только с
  `Загрузка` (запись набора в обход объекта). Снятие защиты — удаление записи регистра администратором (форма списка регистра, команда «Снять
  защиту» с подтверждением).
- **Перепроведение по механизмам** (разведка кода 2026-11-12): ПКО и РКО программно перепроводят/отменяют/помечают
  только пользовательские групповые операции — `ГрупповоеИзменениеРеквизитов` (`ОпределитьРежимЗаписи`) и
  «Связанные документы» (`FilterCriteria.СвязанныеДокументы`, проведение, отмена, пометка). Для них отказ с текстом
  «перенесённый документ защищён» — правильное поведение (пользователь видит причину, остальные документы операции
  обрабатываются). Последовательность `Основная` (регламентное `ПерепроведениеДокументов`), каскады налоговых
  документов (`НалоговыеДокументыНаОснованиях.ПерепровестиПокрывающиеДокументы`,
  `ПодпискиНаСобытия.ПерепровестиНалоговыеНакладныеПоОплате` — перепроводят налоговые накладные, не сам платёж),
  автовыпуск, обмен между базами, касса — ПКО/РКО существующие не перепроводят. Обработчики обновления, которые
  пишут платежи (`ЗаполнитьДанныеОплатВВалюте`), выполняются **до** загрузки переноса (регистр ещё пуст) и пишут
  с `Загрузка` — защита их не задевает. Новые механизмы перепроведения платежей — проверять
  `ПеренесенныеДокументы.Защищен(Ссылка)` (пункт в TECHDEBT с проверкой).
- Тесты: проведение, отмена, удаление, пометка защищённого — отказ; запись с `Загрузка` — проходит; механизм
  перепроведения пропускает защищённый без ошибки.

### 3. Обработка загрузки переноса (maERP) `ЗагрузкаПереносаСтаройРедакции`

Обработка в подсистеме «Администрирование», только полным правам. Читает файл выгрузки (JSON, формат ниже) и
применяет шагами, каждый шаг — своя транзакция на пакет (до 500 объектов), повтор шага идемпотентен:

1. `МестоХранения` ПКО, РКО, касс — запись объекта с `ОбменДанными.Загрузка = Истина` (без перепроведения, без
   проверок), только если значение пустое или равно переносимому;
2. наборы `Убытки` по регистратору: набор заменяется записями выгрузки (все измерения и ресурсы, период, вид
   движения) с `Загрузка`; регистратор пишется в `ПеренесенныеДокументы`;
3. статусы `ПересчётТоваров` — по имени значения;
4. `Контрагенты.СрокОплаты`, `СпособРасчётаОтсрочки` — запись с `Загрузка`;
5. роли пользователей — по таблице «Роли»;
6. узлы обмена с партнёрами — выключенные узлы и учётные данные (см. ниже);
7. **сверка «после»**: те же итоги, что в выгрузке «до», расхождения — в отчёт.

Ссылки в файле — уникальные идентификаторы и полное имя типа; объект, которого нет в базе, — строка отчёта, не
ошибка шага. Итог — отчёт (табличный документ + файл): перенесено / пропущено / расхождения сверки.

### 4. Внешняя обработка выгрузки «до» `ВыгрузкаДляПереносаНаMaERP`

Исходник — `tools/migration/`, сборка EPF скриптом `scripts/build-epf.sh` (из раннера `build/`, перенесённого в
репозиторий без путей клиента). Работает на старой конфигурации через метаданные: отсутствующий у конкретной
базы реквизит пропускается. Пишет JSON: значения из раздела 3, наборы `Убытки` полностью, роли пользователей,
реквизиты обмена контрагентов (пароль — в том же файле; файл удаляется после загрузки, в отчёте напоминание) и
**итоги сверки «до»**:

- остатки `ТоварыВНаличии` (по складу: количество, сумма), `ДенежныеСредстваОрганизаций` (по месту хранения и типу
  денежных средств), `ВзаиморасчётыСПокупателями` и `ВзаиморасчётыСПоставщиками` (по контрагенту); обороты
  `Убытки` (по складу и операции; по организации и статье ДДС), `Продажи` (по хозяйственной операции: выручка,
  количество; склада у старой ветки в `Продажи` нет), остатки товаров — по складу и номенклатуре;
  наборы `Убытки` пишутся из файла по регистратору один в один (все поля и активность), `ДвиженияПоКассе` (по месту
  хранения и типу денежных средств) — ключ сверки — `XMLСтрока` ссылки или значения перечисления (представления
  у веток различаются);
- количество документов по видам (отпечаток).

### 5. Роли

| Роль клиента | Пользователей | В maERP |
|---|---|---|
| `PDVПросмотрРеализаций` | 8 | ничего не давала сверх `PDV` (мастер-план) — снимается, у пользователей остаётся `PDV` |
| `РуководительПродаж` | 2 | у клиента — «всё для новых объектов» с запретом записи денежных документов (ПКО, РКО, безналичные) и удаления; чтение денег разрешено. Замена — роли maERP **без прав записи** денежных документов и регистра `ДенежныеСредстваОрганизаций` (проверяется загрузчиком по правам ролей, не списком в коде): `Кладовщик`, `МенеджерПоПродажам`, `Руководитель`, `СкладскиеОрдера`, `ПотребностиТорговыхТочек`, `РеализацииИзменениеПроведенных`, `РедактированиеНоменклатуры`, `РедактированиеКонтрагентов`, `РедактированиеПоступлениеТоваровУслуг`. `МенеджерПоЗакупкам` (запись РКО), `PDV`, `Казначей` — не назначаются. Пользователь, у которого уже есть `PDV` (запись ПКО/РКО у клиента у него была через `PDV`), её сохраняет. Итог по каждому пользователю — в отчёт |
| `COM_ОсновнаяРоль` | 1 | роль расширения `МароккоCOM`, расширение удаляется — снимается |

Проверка «ни один пользователь не остался без ролей» — шаг загрузки, нарушения — в отчёт. Живая проверка кассира
(`PDV`) и мобильного пользователя (`MobileClient`) на пробной базе — по `memory`-регламенту живой проверки ролей.

### 6. Обмен с партнёрами на переходный период

Партнёры (базы контрагентов) остаются на старой редакции; наш обмен 6.1–6.2 работает только между базами maERP.
Расширение COM-обмена со старой редакцией (мастер-план, волна 7) **в эту сборку не входит** — оно не нужно, чтобы
отдать базу. В 2.0.17.20 реквизиты обмена контрагентов переносятся в **выключенные** узлы `ОбменМеждуБазами`
(контрагент, организация, склад, что отправлять — реализации/цены), логин и пароль — в `УчетныеДанныеОбмена`;
сервер, база и признак файловой базы — в комментарий узла (без пароля). Пока расширения нет, обмен с партнёрами
после обновления идёт вручную; это решение владельца — пункт отчёта. Расширение — следующая сборка волны 7 или
обновление баз партнёров на maERP.

### 6а. Боевой перенос: окно простоя и повторная проверка условий (ревью плана, круги 1 и 3)

- **Перенос — на копии, рабочая база не трогается** (круг 3, P0/P1): (1) вход в рабочую базу блокируется
  (блокировка сеансов кластера / закрытие файловой базы, регламентные задания и внешние соединения партнёров
  отключены); (2) снимается полная копия рабочей базы (`.dt` или файл `1Cv8.1CD`) — она и резерв; (3) скрипт
  `tools/migration/client-update.sh` работает на копии; (4) успех (условия, отпечаток, пообъектная полнота, сверка
  без расхождений) — копия становится рабочей базой; неуспех — блокировка снимается, клиент работает на прежней
  базе, перенос повторяется после исправления. Монопольный режим и выключение заданий внутри копии не нужны: в
  копию никто, кроме скрипта, не входит.
- **Отпечаток базы**: выгрузка пишет число документов по видам и наибольшую дату документа вида (без версий данных:
  обработчики обновления правят существующие документы, но не создают и не удаляют их — пробный прогон это
  проверяет); загрузка до первого шага сверяет отпечаток по видам, существующим в maERP, — расхождение (кто-то
  создал или удалил документ между выгрузкой и загрузкой) — остановка без изменений. При повторном запуске
  корректировка, созданная переносом (по её комментарию), из счёта `КорректировкаРегистров` вычитается.
- **Повторная проверка условий потерь**: выгрузка «до» заново замеряет на свежей базе все условия, на которых
  держатся строки «ничего не теряется» и «осознанные потери» таблицы (нулевые и малые количества, ссылки на
  значения перечислений, заполненность реквизитов с другим типом, роли без замены). Условие изменилось (например,
  появились `ЗаказПокупателя.МестоХранения` больше порога, ссылки на `НакладнаяПоОтгрузкамТовара`, заполненная
  `Категория`) — выгрузка завершается с отказом и перечнем, CF не загружается до решения.

### 7. Пробный прогон на копии (скрипт `scripts/client-update-trial.sh`, пути клиента — параметрами)

1. Копия `build/ib-flycdi` → `build/ib-flycdi-trial`.
2. Выгрузка «до» (EPF) → файл.
3. Удаление расширения `МароккоCOM` (`/DeleteCfg -Extension`).
4. Загрузка CF maERP 2.0.17.20 (`/LoadCfg` + `/UpdateDBCfg`), реструктуризация.
5. Обработчики обновления (запуск клиента с обновлением), журнал — в отчёт.
6. Загрузка «после» (обработка) → отчёт и сверка.
7. Дата запрета редактирования на дату переноса.
8. Смок (формы, печать) на пробной базе; тесты документов — нет (пишут данные; прогон на `build/ib`).
9. `.dt` → `build/dist/flycdi-trial-<дата>.dt` (не в git), владельцу — путь.

Критерий готовности: (1) **пообъектная полнота** — по каждому разделу файла применено ровно столько объектов,
сколько выгружено; пропуск допустим только для объекта, которого нет в базе после обновления (перечень — в отчёт,
владельцу), а «значение не пустое и отличается» — остановка шага, не пропуск; (2) сверка итогов «до/после» без
расхождений, кроме перечисленных осознанных потерь; (3) число документов по видам совпадает с отпечатком, кроме
созданной переносом `КорректировкаРегистров` (её ссылка — в отчёте) и видов, которых нет в maERP; (4) все
обработчики обновления прошли; (5) смок чист; (6) роли проверены живьём.

Секция «Что нового» 2.0.17.20 на четырёх языках — обязательна (реквизиты с uuid клиента, строковый код трёх
справочников, файлы у перемещений и банковских документов, защита перенесённых документов, обработка загрузки
переноса).

## Права и безопасность

- Обработка загрузки — только полные права; файл выгрузки содержит пароли чужих баз — после загрузки удаляется
  (обработка предлагает удалить, отчёт напоминает); в git не попадает (`build/`).
- `ПеренесенныеДокументы` — запись только обработкой переноса; снятие защиты — администратор.
- Обработка выгрузки — внешняя, запускается администратором клиента на его сервере.

## Данные и обновление

Новые объекты maERP: регистр `ПеренесенныеДокументы`, общий модуль защиты, подписки, обработка загрузки, два
реквизита с uuid клиента — у других клиентов без данных, реструктуризация без переноса. Обработчик обновления не
нужен.

## Тесты (`ТестыДокументов`)

`ПереносЗащитаИстории` (проведение/отмена/удаление/пометка защищённого — отказ, `Загрузка` — проходит),
`ПереносЗагрузкаКассы` (файл с ПКО и наборами `Убытки` «петлёй» на тестовых документах — склад и измерения
восстановлены, документ защищён, повтор не меняет), `ПереносРоли` (замена ролей по таблице — на тестовом
пользователе ИБ не делается: проверка функции сопоставления ролей), `ПереносСрокПеремещения` (запись реквизита).

## Не делаю

Расширение COM-обмена со старой редакцией (следующая сборка), перенос `ТоварыДляЗаказа`, `ОтгрузкаТовара`,
`ТоварнаяГруппа` пересчётов, обмена с сайтом; боевой перенос — владельцем/с владельцем по комплекту.

## Тип кода справочников (найдено пробной загрузкой 2026-11-12)

`Бренды`, `ВидыЦен`, `TypesDePayment` у клиента — код строковый, в maERP — числовой (с первой выгрузки EDT).
Реструктуризация копии клиента падает: «Error SDBL: тип поля Code несовместим с литералом STRING». Опыт на копии:
со строковым кодом этих трёх справочников реструктуризация проходит. Но и обратная смена (строковый код в maERP)
не проходит на базах maERP с числовым кодом: «тип поля Code несовместим с литералом NUMERIC» (копия тестовой базы,
2026-11-12) — менять тип кода в maERP нельзя. **Решение — промежуточный шаг переноса**: (4а) в базу клиента
грузится вариант CF maERP со строковым кодом трёх справочников (XML maERP, `CodeType` заменён скриптом), (4б)
обработка `tools/migration/codes.bsl` приводит коды к цифрам нужной длины (цифровой код без дублей сохраняется,
остальным — следующий номер), (4в) грузится CF maERP с числовым кодом — строки из цифр переводятся в числа. maERP
не меняется.

## Определяемые типы (найдено пробной загрузкой)

Сверка составов определяемых типов клиента и maERP: значение реквизита с типом, которого нет в maERP, при
реструктуризации молча очищается.
- `ВладельцыПрисоединенныхФайлов`: у клиента ещё `ПеремещениеТоваров`, `ПоступлениеБезналичныхДенежныхСредств`,
  `СписаниеБезналичныхДенежныхСредств` — без них записи `ПрисоединённыеФайлыНаличие` теряют владельца и
  реструктуризация падает на неуникальности. У клиента файлы — на поступлениях (~240) и списаниях (1) безналичных
  денег и РКО (~75), на перемещениях — нет. **Решение: добавить в тип maERP два банковских документа**; право
  прикрепить и изменить их файлы — только с правом изменения документа (`ПраваНаФайлы.ПравоИзмененияВладельца`).
  Давняя слабость подсистемы файлов (чтение регистра ролями, удаление без проверки владельца) — TECHDEBT, отдельной
  сборкой.
- `ОбъектРасчётовОбщий`: у клиента ещё `ДоговорыСКонтрагентами`; используется только в `КорректировкаДолга` (1
  документ 2024 г.). Проверяется сверкой взаиморасчётов «до/после» и условием выгрузки «до» (число строк с
  договором в объекте расчётов — осознанная потеря при значении 0, иначе — остановка).
- Предупреждение реструктуризации: предопределённые элементы `ВидыНастроекПользователей` с типом, которого нет в
  типе значений плана, — проверить после обновления (характеристики настроек пользователей).

## Риски

- Обработчики обновления 1.0.11.x–2.0.17.x на данных старой ветки — первый реальный прогон; падение обработчика —
  исправление в этой же сборке.
- Длительность записи ~72 тыс. кассовых документов в файловой базе — шаги пакетами с отметкой выполненного.
- Перепроведение истории сторонними путями (групповое перепроведение, восстановление последовательности) — закрыто
  защитой раздела 2 только для регистраторов `Убытки`; прочие ранние документы живут по обычным правилам (мастер-план).
