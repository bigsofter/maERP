# Бриф: стадии заказа клиента на производство (E8)

## Задача

У заказа клиента на производство появляется стадия, которая считается сама по данным контура: проведение (E6),
потребности `ПотребностиПроизводства` (E7), выпуск, отгрузка и оплата. Стадия — значение существующего перечисления
`СтатусыЗаказовПокупателя` в том же регистре истории `ИсторияЗаказовПокупателейПоСтатусам` (решение владельца 1 от
2026-09-09). У продаж статусы считаются как сейчас. Основание — `docs/plans/production-2mzl.md`, этап E8, и
обязательства разделов E6 и E7 (раздел E7 дописывается при сдаче E7 — перед началом сверить).

Что появляется:

- **перечисление** `СтатусыЗаказовПокупателя` — новые значения `Черновик`, `ФормируетсяПотребность`, `ЗаказПоставщику`,
  `ВосполнениеПотребности`, `ОжидаетОтгрузки`, `ОжидаетОплаты`, `Выполнен` (новые uuid, синонимы ×4); `ВПроизводстве`
  переиспользуется как стадия производства. Порядок значений существующих не менять;
- **регистр** `ИсторияЗаказовПокупателейПоСтатусам` (независимый, периодичность «секунда», измерение `ЗаказПокупателя`,
  ресурс `СтатусЗаказаПокупателя`, реквизиты `ДокументПродажи`, `СрокОплаты`) — новые реквизиты долей выполнения
  `ДоляОбеспечения`, `ДоляПоступления`, `ДоляВыпуска`, `ДоляОтгрузки`, `ДоляОплаты` (число 0–1) и `Индикатор` (строка
  из кружков). Новые uuid, существующие поля не трогать;
- **общий модуль** `ПроизводственныеЗаказы` (сервер): `РассчитатьСтадию(Заказ)` по каскаду плана волны —
  1) не проведён или помечен на удаление → `Черновик`; 2) материалов нет → `ФормируетсяПотребность`; 3) по какому-то
  материалу `Заказано` < `Потребность` → `ЗаказПоставщику`; 4) `Пришло` < `Потребность` → `ВосполнениеПотребности`;
  5) выпущено меньше заказанного → `ВПроизводстве`; 6) отгружено меньше заказанного → `ОжидаетОтгрузки`; 7) долг > 0 →
  `ОжидаетОплаты`; 8) иначе `Выполнен`. Плюс доли и индикатор. `ОбновитьСтадию(Заказ)` пишет запись истории, **только
  если** стадия или доли изменились, под исключительной управляемой блокировкой регистра истории по заказу;
- **ветвление существующего расчёта**: `ЗаказПокупателя.ПриЗаписи` (Новый/ВРаботе), `РеализацияТоваровУслуг.ПриЗаписи`
  (Собран), `РаботаСДокументами.ОбновитьПроизводственныйСтатусЗаказа` / `ОбновитьСтатусЗаказаПоСвязанным` — для заказа
  на производство вызывают `ПроизводственныеЗаказы.ОбновитьСтадию`, для продажи работают как сейчас;
- **точки пересчёта**: запись и проведение (и отмена) заказа клиента, заказа поставщику, поступления, возврата
  поставщику, выпуска продукции, реализации, возврата от покупателя и денежных документов оплаты покупателя (состав —
  по исследованию: ПКО, поступление безналичных, прочие, что гасят `ВзаиморасчётыСПокупателями` по заказу или его
  реализации). Заказ клиента ищется явной функцией по пути основания, а не общим `ПолучитьДокументРодительПоТипу`
  (урок E7: цепочка через реализацию уводит в чужой заказ);
- **форма заказа**: декорация `ДекорацияСтатусаЗаказа` (`Form.form:166–194`, группа `ГруппаНомерДата`) у заказа на
  производство показывает стадию и индикатор — одна декорация с форматированной строкой, без новых картинок;
- **список заказов** (`ФормаСписка`): колонки «Стадия» и «Индикатор» из среза последних (запрос списка
  `Form.form:3506–3619`), условное оформление по стадии; **мёртвое условное оформление** вычищается
  (`ConditionalAppearance.dcssca` ссылается на несуществующие поля `Отгружено`, `ОтгруженоСумма`, `Оплачено`,
  `ОплаченоСумма`); в панели «Детали» — строка стадии;
- **перечни статусов** в `ВЫБОР … КОГДА Статус В (…)`: запрос списка заказов (`Form.form:3559–3564`), `Дашборд`
  (`ManagerModule.bsl:773–796`), `АРМПроизводство` (`Module.bsl:94`) — новые значения разложить по корзинам явно, иначе
  заказы молча уйдут в ветку «иначе»;
- **сценарий уровня 3** `СтадииЗаказа` и строки в `docs/TESTING.md`, `docs/TESTS.xlsx`.

## Почему сейчас

E7 дал регистр потребностей — первую опору стадий 3–4. Без стадий заказ на производство в списке выглядит «Новым» до
отгрузки, а E9 (автовыпуск) должен двигать стадию «В производстве» и «Ожидает отгрузки». E12 (АРМ производства) строит
очередь по стадиям.

## Границы (чего НЕ делать)

- **Автовыпуск и `ИзОстатка`** (E9) — не делать; стадия «В производстве» считается по ручным выпускам с основанием-заказом.
- **Исторические заказы** не пересчитывать и не проводить (решение 2): обработчика обновления для стадий нет, стадия
  появляется при следующей записи заказа или связанного документа.
- **Продажи** — алгоритм статусов прежний, без новых значений.
- **ECommerce-форму не менять**; регистрацию карт E6 и движения E7 не трогать.
- **Новых картинок нет** — индикатор строкой.
- Попутно найденное — в `docs/TECHDEBT.md`, не в этот коммит.

## Уроки последних сборок — обязательны

- **Отказ записи внутри транзакции сценария** портит её: проверки — через экспортные функции без записи
  (`РассчитатьСтадию` возвращает структуру, не пишет), настоящий отказ — последним шагом (E5–E7).
- **Вложенная транзакция**: `ОтменитьТранзакцию` во вложенной отменяет внешнюю — не бросать ожидаемые отказы из-под
  `НачатьТранзакцию` (E6, N1). Пересчёт стадии идёт внутри транзакции записи документа — своей транзакции не открывает.
- **Порядок блокировок** один для всех путей: карты продукции → регистры заказа (E6, E7) → регистр истории статусов
  последним; пересчёт — после формирования движений документа.
- **Привилегированный режим** не заменяет проверку права; `ПравоДоступа` без пользователя в привилегированном режиме
  права не проверяет (E6). Запись истории из документов ролей без права на регистр — узким привилегированным режимом с
  комментарием, чтение для формы и списка — под пользователем.
- **Кнопка внутри таблицы динамического списка на закладке роняет клиент 8.5** (forms-009): таблица заказов лежит на
  странице `СтраницаЗаказы` группы `ГруппаСтраницыДокументов` — только колонки, кнопки рядом с таблицей. Видимость по
  опции — на сервере (bsl-009); запрос списка — `listcheck.py`; элементы Form.form копировать с образца целиком
  (forms-001, без `<visible>` элемент скрыт).
- **Изменение запроса списка** проверять диффом всей `Form.form` (workflow-009, затёртый запрос поступлений).
- **Реструктуризация регистра сведений** и новые значения перечисления — полное обновление `build/ib` по уроку E4.
- **Смок форму не рисует** — в отчёте явный список «что посмотреть глазами».
- **Проверка на базе — сам**: копия `build/ib`, `scripts/smoke.sh` и `scripts/doctests.sh` на копии; шаг 1б смока
  ложно срабатывает — шаг 2 отдельно.
- **Оркестрация**: обязательные гейты — Codex; при его лимите — субагенты Claude, не OpenCode (`.ai/README.md`).
  Зависший прогон снимать по PID своего процесса.

## Вопросы владельцу

1. **Размер этапа.** E8 крупный: расчёт и история, шесть-восемь точек пересчёта, форма, список, дашборд. Одной сборкой или
   двумя: E8а — перечисление, регистр, модуль, точки пересчёта, сценарий; E8б — декорация, колонки и оформление списка,
   панель «Детали», корзины дашборда и АРМ? Предлагается — двумя: расчёт проверяется на базе до правки форм.
2. **Долг по заказу (стадия 7).** `ВзаиморасчётыСПокупателями.ОбъектРасчётов` принимает и заказ (аванс), и реализацию.
   Долг заказа — сумма положительных остатков по объекту «заказ» и по реализациям на основании заказа, с зачётом аванса
   на заказе? Предлагается — да: долг = остаток по заказу + остатки по его реализациям, стадия 7 при сумме > 0.
3. **Откат стадии.** Отмена проведения поступления, возврат поставщику или возврат от покупателя возвращают стадию назад
   (например, из «Ожидает оплаты» в «Восполнение потребности»), в истории — новая запись? Предлагается — да, стадия всегда
   равна расчёту по текущим данным.
4. **Индикатор.** Пять кружков — обеспечение (`Заказано/Потребность`), поступление (`Пришло/Потребность`), выпуск,
   отгрузка, оплата; `○` — ноль, `◐` — частично, `●` — полностью. Устраивает или нужен другой набор этапов/символов?
   Предлагается — так.
