# Производственный контур maERP (клиент 2mzl)

## Контекст

Клиент 2mzl (заказчик в CRM tinycio, Марокко, инициатива «Внедрение maERP») работает по цепочке:
коммерческое предложение → заказ клиента на готовую продукцию → заказ поставщику на материалы →
приходная накладная материалов под заказ → производство → реализация. Производственные документы
вводить некому, поэтому выпуск продукции должен появляться сам при отгрузке, а материалы списываться
по составу заказа или по партиям поступлений под этот заказ.

Задача — переложить процесс на maERP так, чтобы решение осталось тиражным: клиент получает
преимущественно нашу схему, дополненную универсальными объектами, полезными другим клиентам.
Побочная цель — закрыть развилку Р10 (две константы про выпуск, которые код не читает) и перевести
технологические карты из табличной части справочника в регистр с историей.

План сохраняется в проект первым шагом исполнения: `docs/plans/production-2mzl.md` (новый каталог),
промпт волны — `docs/plans/production-2mzl-prompt.md` по образцу `wave12-prompt.md`.

## Решения владельца (2026-09-09)

| # | Решение |
|---|---|
| 1 | Стадии заказа на производство — **расширением существующих статусов**, в том же регистре истории |
| 2 | Исторические заказы в базах клиентов при включении проведения **не трогаем**, обработчика нет |
| 3 | Скилл учёта времени заводим в maERP своим каталогом, ретроспектива — **все 18 дней с коммитами** |
| 4 | Кейс 2mzl — **на французском, с раскрытием имени** заказчика; публикует владелец |
| 5 | Всё остальное из постановки принято как написано |

## Архитектура

**Новые объекты.** Документы `КоммерческоеПредложение` (uuid Rayssouni), `ТехнологическаяКарта`.
Регистр сведений `СоставТехКарты` (периодический по регистратору). Регистр накопления
`ПотребностиПроизводства` (остатки). Перечисления `СпособыПополненияЗапасов`,
`ВидыОперацийЗаказаПокупателя`. Общие модули `ТехнологическиеКарты`, `Производство`,
`ПроизводственныеЗаказы`. Отчёт `ПотребностиПроизводства`. Общая команда `ЗаказыНаПроизводство`.

**Ключевые принципы.** Единственная точка чтения техкарт — модуль-фасад `ТехнологическиеКарты`.
Версия техкарты — это её регистратор, он же хранится в скрытой колонке `Техкарта` строки заказа.
Стадии — значения существующего перечисления `СтатусыЗаказовПокупателя`, расчёт разветвляется по виду
операции заказа. Автовыпуск создаётся в проведении реализации, ищется по основанию через критерий
отбора «Связанные документы», отдельного реквизита-ссылки нет.

### E1. Технологические карты в регистр (L)

**Состояние на 2026-09-11:** реализация 2.0.15.6 принята владельцем на обновлённой базе.
Перенос, выбор дня версии, расчёт показателей и пять сценариев уровня 3 завершены;
история проверки — `production-2mzl-e1-check.md`.

- Регистр `СоставТехКарты`: периодичность по позиции регистратора, подчинение регистратору.
  Измерения Продукция, Материал, Характеристика. Ресурсы Количество (на единицу продукции), Упаковка.
  Форма списка с отбором по продукции — это и есть «история техкарт».
- Документ `ТехнологическаяКарта`: Номенклатура, табличная часть материалов, проведение пишет регистр.
- Общий модуль `ТехнологическиеКарты`: `СоставТехкарт`, `ТекущиеТехкарты`, `СоставТехкартыПоРегистратору`,
  `КоэффициентыТехкарт`, `ЗаполнитьМатериалыПоТехкартам`, `ЗаписатьТехкарту`, `СоставОтличается`.
  Правило «нет карты хотя бы у одной позиции → все веса равны единице» воспроизводится буквально,
  иначе поедет себестоимость мультивыпусков.
- Форма номенклатуры: таблица становится реквизитом формы, добавляются поле «Действует с», надпись с
  версией и кнопка «История техкарт». Запись — в `ПослеЗаписиНаСервере` через фасад. Повторная запись
  в тот же день перезаписывает документ этого дня.
- Переводятся на фасад четыре читателя: [ManagerModule.bsl:388](src/cf/src/AccumulationRegisters/ТоварыВНаличии/ManagerModule.bsl:388),
  [Module.bsl:176](src/cf/src/Documents/ВыпускПродукции/Forms/ФормаДокумента/Module.bsl:176) (там же
  закрывается падение на несуществующем поле характеристики), два места в тестах документов.
- Функциональная опция `ИспользоватьУпаковку` (решение владельца 2026-09-10, ответ на вопрос о
  заполнении упаковки по карте): константа, переключатель в «Настройка → Номенклатура», содержимое —
  реквизиты `Упаковка` табличных частей документов. По умолчанию выключена, и пока она выключена
  `ЗаполнитьМатериалыПоТехкартам` возвращает упаковку пустой: иначе `РассчитатьСтроку` пересчитала бы
  количество по коэффициенту упаковки и сдвинула суммы привычных выпусков.
- Обработчик обновления создаёт документ техкарты по каждой номенклатуре с непустой табличной частью,
  дата — дата создания элемента, иначе начало 2000 года. Идемпотентность по отсутствию записей регистра.
  Будущая версия и маркер отмены тоже запрещают перенос; дополнительно пропускается продукция
  с любым существующим документом техкарты, чтобы сохранить черновики и помеченные на удаление карты.
  Историчность коэффициентов принята владельцем (2026-09-10): после перевода перепроведение старого
  выпуска берёт карту на дату документа. Расхождение сумм по старым выпускам разбирается как ошибка
  переноса в конкретной базе, а не как ожидаемое изменение поведения.
- Табличная часть справочника **остаётся** в этом релизе. Её удаление — отдельный более поздний релиз,
  после подтверждения, что базы клиентов прошли релиз с переносом. Запись об этом в `docs/RELEASING.md`
  и `docs/TECHDEBT.md`.

### E2. Способ пополнения запаса (S)

**Состояние на 2026-09-12:** реализация завершена в 2.0.15.7. `lint`, `refcheck`,
`listcheck`, `CheckConfig`, смок 396 форм и 16 сценариев уровня 3 прошли на обновлённой
`build/ib`; остаётся ручная приёмка видимости и поведения поля в карточке.

Перечисление `СпособыПополненияЗапасов` (Закупка, Производство, Оба), реквизит номенклатуры,
умолчание в модуле менеджера справочника, страховка в `ПередЗаписью`, видимость поля через
функциональную опцию «Производство», обработчик обновления для существующих элементов.

- Продукция и полуфабрикат получают «Производство»; товар, сырьё, комплект и услуга — «Закупка».
  Значение «Оба» выбирается вручную и не перезаписывается при записи или обновлении базы.
- При смене типа форма ставит соответствующее умолчание. Обычное открытие и повторная запись
  заполненное значение не меняют.
- Монопольный обработчик 2.0.15.7 заполняет только пустые значения элементов, пропускает группы
  и повторно ничего не меняет. Запись выполняется в режиме загрузки, поэтому значение задаётся
  обработчиком явно, независимо от раннего выхода в `ПередЗаписью`.
- Сценарий уровня 3 `СпособыПополненияЗапасов` проверяет шесть типов, страховку записи,
  ручное «Оба», миграцию, пропуск групп и повторный запуск в транзакции с откатом.

### E3. Коммерческое предложение (M)

**Состояние на 2026-09-12:** реализовано в 2.0.15.8. Добавлены отдельный документ,
статусы, формы документа и списка, печать через общий Devis A4, ввод заказа на
основании, автоматический статус «Выигран», связанные документы, меню и права.
Семнадцатый сценарий уровня 3 проверяет документооборот в транзакции с откатом.

Соответствие образца Rayssouni реализации maERP:

| Rayssouni | maERP 2.0.15.8 | Решение |
|---|---|---|
| `КоммерческоеПредложение` | `Документ.КоммерческоеПредложение` | UUID документа, реквизитов и ТЧ сохранены; заглушки исключены |
| ТЧ товаров предложения | `ТЧТовары` + `Описание` | UUID исходных колонок сохранены; описание добавлено для E3 |
| Модуль объекта с отсутствующей операцией | собственный модуль объекта | умолчания, контроль описаний и синхронизация номенклатуры |
| три копии печати Devis | общий `PrintDevisA4` реализации | в общий запрос добавлены две ветки объединения |
| ввод заказа на основании | `ЗаказПокупателя.Основание` | данные и строки переносятся, после записи предложения получает «Выигран» |

- Документ с uuid Rayssouni, без реквизитов-заглушек. Табличная часть и реквизиты берут их uuid.
  Модуль объекта пишем свой: у них обращение к несуществующему реквизиту операции.
- Статусы КП: перечисление `СтатусыКоммерческихПредложений` (Черновик, Отправлен, Доставлен, Проигран,
  Выигран), реквизит документа. «Выигран» ставится автоматически при вводе заказа на основании.
- Список по стилю 8.5: панель сведений справа со страницами Фильтры и Клиент, все новые поля в фильтрах,
  тумблер статуса, условное оформление строки по статусу (образец —
  [ConditionalAppearance.dcssca](src/cf/src/Documents/ПоступлениеТоваровУслуг/Forms/ФормаСписка/ConditionalAppearance.dcssca)).
- Поле «Описание» справа от табличной части: многострочное, синхронно с текущей строкой, при записи
  документа переносится в реквизит `Описание` номенклатуры.
- Вторая закладка в списке заказов клиентов со списком КП и кнопкой «Создать заказ» в командной панели
  таблицы. Кнопку внутрь таблицы не класть и группу пользовательских настроек списку на закладке не
  задавать — оба приёма роняют клиент 8.5.
- Печать — через существующий вывод коммерческого предложения: две ветки объединения в
  `ТекстЗапросаDevisBL`, а не 443 строки чужого модуля.
- Меню «Продажи», критерий связанных документов, роли. Решение об отмене прежнего «КП не переносим»
  записывается в `docs/TECHDEBT.md` и `docs/ROADMAP.md`.

### E4. Вид операции заказа (M)

**Состояние на 2026-09-13:** реализовано в 2.0.15.9, бриф — `production-2mzl-e4-vid-operacii.md`,
план и ревью — `.ai/plans/production-2mzl-e4.md`, `.ai/reviews/production-2mzl-e4/`. Решения владельца
2026-09-13: смена вида операции у записанного заказа разрешена (запрет — в E6), название — «Заказ
клиента на производство». Отклонения от текста ниже: умолчание задано значением заполнения реквизита
(`fillValue` + `fillFromFillingValue`) и страховкой в `ПередЗаписью`; команда выдана ролям
`ОператорПроизводства` и `Кладовщик` (роли с доступом к разделу «Производство»); при выключенной опции «Производство» заказ
по КП — всегда «Продажа».

**Инвариант для E6–E9:** пустой вид операции в базе возможен и после обновления — запись в режиме
загрузки обходит страховку (`ТестовыеДанные`, режим разработчика `ГрупповоеИзменениеРеквизитов`).
Поэтому продажа в отборах, запросах и ветках кода — это «не производство» (`<> Производство`), а не
`= Продажа`.

Перечисление `ВидыОперацийЗаказаПокупателя` (Продажа, Производство) и реквизит `ВидОперации`, а не
общее перечисление хозяйственных операций: там три десятка денежных значений и своя форма выбора.
Представление документа меняется через получение представления в модуле менеджера, заголовок формы —
через существующую установку заголовка. Поле видно по функциональной опции. Заполнение по КП ставит
операцию «Производство», если хотя бы одна позиция предложения пополняется производством.
Общая команда «Заказы клиентов на производство» в разделе «Производство» открывает список с
недоступным отбором; сам документ в подсистему не добавляем, иначе в разделе появится второй пункт.
Создание из этого списка сразу проставляет операцию. В общем списке — тумблер операции в фильтрах.
Обработчик обновления проставляет «Продажа» существующим заказам.

### E5. Материалы в заказе (M)

**Состояние на 2026-09-13:** реализовано в 2.0.15.13; `lint`, `refcheck`, `listcheck`, CheckConfig, смок
398 форм и 19 сценариев уровня 3 прошли на обновлённой копии `build/ib`; остаётся ручная приёмка формы.
Бриф — `production-2mzl-e5-materialy.md`, план и
ревью — `.ai/plans/production-2mzl-e5.md`, `.ai/reviews/production-2mzl-e5/`. Решения владельца
2026-09-13: заказ по КП заполняет материалы сразу; у заказа не на производство материалы очищаются
при записи; разный состав одной продукции (номенклатуры, без характеристики) в двух строках —
отказ записи уже в E5. Отклонения от текста ниже и брифа: колонки количества — `КоличествоЗаЕдиницу`
(имя колонки выпуска), `КоличествоУпаковок` и базовое `Количество`; общая логика заполнения — в модуле
менеджера над коллекциями строк (данные формы не теряют дополнительные колонки); в фасаде техкарт
добавлена экспортная `КлючСоставаСтрок`.

**Обязательства для следующих этапов:**
- E6 сравнивает составы, а не ссылки: `ЗаписатьТехкарту` перезаписывает документ дня, ссылка
  «Техкарта» не фиксирует состав. Ключ состава — `ТехнологическиеКарты.КлючСоставаСтрок(Материалы,
  "КоличествоЗаЕдиницу")`, тот же, что у отказа записи E5.
- E7 читает потребность из базового `Количество` материалов.
- E9 считает долю автовыпуска от базового количества продукции (`ТЧТовары.Количество`): количество
  за единицу задано на базовую единицу продукции.
- Связь материала со строкой — `КодСтрокиПродукции` = `ТЧТовары.КодСтроки`; запись заказа на
  производство с материалами разводит повторяющиеся коды, нулевые коды строк без материалов не трогает.

Табличная часть `ТЧМатериалы` (код строки, код строки продукции, номенклатура, характеристика,
упаковка, количество, количество на единицу, комментарий) под таблицей товаров на той же странице.
Фильтрация по выделенной строке товаров — через отбор строк таблицы. Команда «Заполнить по техкарте»
для текущей строки и для всех товаров. Скрытая колонка `Техкарта` в товарах включается через «Ещё».
Пересчёт количества материалов при изменении количества продукции, очистка при смене номенклатуры.

### E6. Проведение заказа и регистрация техкарты (M)

**Состояние на 2026-09-13:** реализовано в 2.0.15.14, бриф — `production-2mzl-e6-provedenie.md`, план и
ревью — `.ai/plans/production-2mzl-e6.md`, `.ai/reviews/production-2mzl-e6/`. Решения владельца 2026-09-13:
версия карты, зарегистрированная заказом, становится текущей; дата версии — день проведения;
`Кладовщик` заказы не проводит. Отклонения от брифа: регистрация карты и колонка «Техкарта» — в
`ПередЗаписью` при проведении (в `ОбработкаПроведения` изменения объекта не сохраняются), там же отказ
продаже, `ОбработкаПроведения` — страховка; права ролей не менялись (у `ОператорПроизводства` всё было);
новая версия карты через заказ — только при праве на карты; проверка заполнения при записи из формы
перенесена на сервер (у проводимого документа форма проверяет только при проведении); отказ «строка
без материалов» — только у продукции со способом пополнения «Производство»; фасад техкарт получил
блокировку карт продукции (находка ревью данных, экспортная `ЗаблокироватьКартыПродукции`). Сборка 2.0.15.14 не
загружалась в базу (стандартная команда `WriteAndClose` у проводимого документа), исправлено в 2.0.15.16. Сценарий
`ПроведениеЗаказа` пройден на копии `build/ib` 2.0.15.19; формы — ручная приёмка.

**Обязательства для следующих этапов:**
- Заказ на производство проводится только при `Документы.ЗаказПокупателя.ЗаказПроводится(ВидОперации)`;
  продажа не проводится никаким путём — движения E7 пишутся только заказом на производство.
- «Техкарта» строки — ссылка на документ карты дня, а не снимок состава: состав заказа — только
  `ТЧМатериалы`; E7–E9 не сравнивают `Техкарта` с материалами для решений.
- Перепроведение (E7, E8) с неизменным составом версию карты не регистрирует и право на карты не
  требует; с изменённым — регистрирует, поэтому перепроведение кодом идёт под пользователем с правом на
  карты или с неизменными материалами.
- Исключительная блокировка `СоставТехКарты` по продукции (`ТехнологическиеКарты.ЗаблокироватьКартыПродукции`)
  берётся всеми путями записи карты: фасад `ЗаписатьТехкарту` (в своей транзакции), проведение заказа,
  `ПередЗаписью` документа карты. Блокировки регистров E7 — после неё, в той же транзакции.
- Проведённый заказ с изменёнными материалами в режиме «Запись» не записывается: состав фиксируется
  только проведением.

Проведение разрешается для документа целиком, движения формируются только при операции
«Производство»; для продаж кнопки проведения скрыты, поведение продаж не меняется. Исторические
заказы остаются непроведёнными и стадий не получают (решение 2). При проведении заказ регистрирует
новую версию техкарты, только если состав материалов отличается от зафиксированного регистратора или
колонка «Техкарта» пуста. Одна продукция в двух строках с разным составом — отказ с сообщением.

### E7. Потребности производства (L)

**Состояние на 2026-09-13:** реализовано в 2.0.15.15, бриф — `production-2mzl-e7-potrebnosti.md`, план и ревью —
`.ai/plans/production-2mzl-e7.md`, `.ai/reviews/production-2mzl-e7/`. Решения владельца 2026-09-13: одна сборка;
«Заказано» и «Пришло» сверх потребности — фактическое количество; закупка под продажу или непроведённый заказ
движений не пишет; без колонки «Продукция» — в порядке строк продукции. Отклонения от брифа: основание заказа
поставщику ставится вводом на основании заказа на производство и полем «Заказ клиента» в форме (раньше не
ставилось); признак «потребность сформирована» для закупок — движения заказа в регистре, а не опция; поступление по
заказу поставщику распределяется по «Заказано» этого заказа, возврат — по «Пришло» своего поступления; строки из
предварительных заказов не участвуют; отчёт — и в разделе «Закупки»; колонка списка поступлений — только при праве
чтения заказов поставщику; проверка записи проведённого заказа сравнивает и базовые количества. Прогон на базе нашёл
переменную-реквизит `Менеджер` и зарезервированные псевдонимы запросов (2.0.15.17) и два дефекта теста отчёта
(2.0.15.18–19); на копии полностью обновлённой `build/ib` 2.0.15.19 — 21 сценарий без ошибок, смок на 2.0.15.16 без
ошибок; формы — ручная приёмка.

**Обязательства для следующих этапов:**
- Стадии «Заказ поставщику» и «Восполнение потребности» (E8) считаются по сумме материала и характеристики заказа,
  а не по строкам продукции: излишек закупки ложится на последнюю продукцию, явная продукция пределом не ограничена.
- «Потребность сформирована» — есть движения регистра с регистратором-заказом; от опции «Производство» не зависит.
- Заказ клиента закупки — только основание «заказ клиента» или «заказ поставщику под заказ клиента»
  (`РегистрыНакопления.ПотребностиПроизводства.ЗаказКлиентаДокументаЗакупки`), не общий `ПолучитьДокументРодительПоТипу`.
- Блокировка регистра по заказу — `УправляемыеБлокировки.ПотребностиПроизводства`; заказ клиента берёт её после карт
  продукции, закупки — вместе со складскими регистрами; E9 (автовыпуск, `ИзОстатка`) — тем же порядком.
- Отмена проведения заказа клиента со связанными закупками не запрещена — решение по стадиям E8 (TECHDEBT).

- Регистр `ПотребностиПроизводства` — остатки. Измерения Заказ, Продукция, Материал, Характеристика.
  Ресурсы Потребность, Заказано, Пришло, ИзОстатка.
- Заказ клиента пишет Потребность, заказ поставщику — Заказано, приходная накладная — Пришло, возврат
  поставщику сторнирует. Ресурс «ИзОстатка» пишет автовыпуск, когда партий под заказ не хватило.
- Продукция для строки материала — новая скрытая колонка в товарах заказа поставщику; при пустой
  колонке распределение идёт по остатку потребности в порядке строк продукции.
- Кнопка «Заполнить по потребности» над табличной частью заказа поставщику: дефицит из регистра, а не
  из текущей техкарты. Ввод на основании заказа без сформированной потребности отклоняется с внятным
  сообщением (требование 3.6).
- Приходная накладная получает тип основания «Заказ клиента», ввод на основании, колонку «Заказ
  клиента» в списке. Колонка ставится после починки затёртого запроса списка.
- Блокировка регистра добавляется в общий модуль управляемых блокировок.
- Отчёт `ПотребностиПроизводства`: группировки заказ → продукция → материал, четыре ресурса, дефицит
  и «к заказу», флаг «только дефицит».

### E8. Стадии заказа (L)

**Состояние на 2026-09-14:** реализовано в 2.0.15.20, бриф — `production-2mzl-e8-stadii.md`, план и ревью —
`.ai/plans/production-2mzl-e8.md`, `.ai/reviews/production-2mzl-e8/`. Решения владельца 2026-09-14: одна сборка; долг —
остаток по заказу и его реализациям; стадия всегда равна расчёту (откаты); индикатор из пяти кружков; отмена проведения
заказа со связанными закупками разрешена; поздняя веха закрывает ранние стадии. Отклонения от брифа: пришедшее без
заказа поставщику считается заказанным; «выпущено всё» проверяется раньше «потребности нет»; оплата — начислено
реализациями минус долг (аванс ПКО «на основании заказа» виден после зачёта); колонка стадии — существующая «Статус»,
новая — «Индикатор»; пересчёт и из РКО, списания безналичных, корректировки долга и сертификата; отмена проведения
документов контура очищает движения явно под блокировками проведения; индексы `Основание` у реализации, выпуска и
возврата от покупателя; отбор «Заказы к отгрузке» списка реализаций и кабинет партнёра; чтение истории статусов ролям,
пишущим заказы (находка ревью безопасности). На копии полностью обновлённой `build/ib` 2.0.15.20 — 22 сценария уровня 3
и смок без ошибок с первого прогона; формы — ручная приёмка.

**Обязательства для следующих этапов:**
- Стадию пишет только `ПроизводственныеЗаказы`: документ зовёт `ЗапомнитьЗаказыДокумента` в `ПередЗаписью`,
  `ОбновитьСтадииПослеПроведения` последней строкой `ОбработкаПроведения`, `ОбновитьСтадииПриЗаписи` в `ПриЗаписи`,
  `ОтменитьПроведениеДокумента` в `ОбработкаУдаленияПроведения` с тем же набором блокировок, что при проведении.
  Автовыпуск E9 — тем же путём; `ИзОстатка` добавить в «пришло» стадии 6 и долю поступления.
- История статусов блокируется последней в транзакции; данные для расчёта читаются после её блокировки.
- Признак записи стадии — заполненный `Индикатор`; продажи пишут статусы с пустым индикатором.
- Очередь АРМ производства (E12) строится по стадиям и индикатору среза последних.

Расширяем перечисление `СтатусыЗаказовПокупателя` значениями Черновик, ФормируетсяПотребность,
ЗаказПоставщику, ВосполнениеПотребности, ОжидаетОтгрузки, ОжидаетОплаты, Выполнен. Существующее
значение «В производстве» переиспользуется как стадия производства. Хранение — тот же регистр
`ИсторияЗаказовПокупателейПоСтатусам`, дополненный реквизитами долей выполнения (обеспечение,
поступление, выпуск, отгрузка, оплата) и готовой строкой-индикатором из кружков для списка.

Расчёт разветвляется по виду операции: для продаж работает нынешний алгоритм по последнему связанному
документу, для производства — новый, в общем модуле `ПроизводственныеЗаказы`:

1. не проведён или помечен на удаление — Черновик;
2. материалов нет — Формируется потребность;
3. по какому-то материалу заказано меньше потребности — Заказ поставщику;
4. по какому-то материалу пришло меньше потребности — Восполнение потребности;
5. выпущено меньше заказанного — В производстве;
6. отгружено меньше заказанного — Ожидает отгрузки;
7. долг больше нуля — Ожидает оплаты;
8. иначе — Выполнен.

Пересчёт вызывается при записи заказа, заказа поставщику, поступления, выпуска, реализации и трёх
денежных документов. Кружки в форме — одна декорация с форматированной строкой, без новых картинок.
В списке — колонка стадии и колонка индикатора, условное оформление по стадии; мёртвое условное
оформление списка заказов вычищается.

### E9. Автовыпуск при отгрузке (L)

**Состояние на 2026-09-14:** реализовано в 2.0.15.21, бриф — `production-2mzl-e9-avtovypusk.md`, план и ревью —
`.ai/plans/production-2mzl-e9.md`, `.ai/reviews/production-2mzl-e9/`. Решения владельца 2026-09-14: одна сборка;
переключатель на форме «Производство» в E9; нехватка материалов — отказ; продукция без состава — по техкарте, без неё и
«Оба» — не выпускать; привилегированная запись; выпуск строго один на реализацию, реализация списывает продукцию по ФИФО
(партия автовыпуска в строки не ставится); константу при обновлении не трогать. Отклонения от брифа: совпадение секунды —
подсказка к отказу, а не отказ (проба на самом объекте); к выпуску — за вычетом выпущенного и не отгруженного документами,
предшествующими реализации по моменту времени; строки готовой продукции по сериям строк реализации; материалы из общего
остатка — по сериям; «Из остатка» учитывают дефицит, остаток к поступлению и отчёт; колонки «Авто» в списке выпусков нет —
основание-реализация видна в колонке «Основание» и в «Деталях»; `ПередУдалением` реализации. Прогон на копии полностью
обновлённой `build/ib` нашёл переменную `Документы` (свойство глобального контекста) и ошибку теста — 2.0.15.22; 23
сценария уровня 3 и смок без ошибок; формы — ручная приёмка. Выпуск по техкарте срабатывает только у непроведённого
заказа: проведение (E6) не пропускает продукцию со способом «Производство» без материалов.

**Обязательства для следующих этапов:**
- Автовыпуск пишет только `Производство.ОбеспечитьАвтовыпуск` из проведения реализации; признак — основание-реализация;
  ручная правка отклоняется в `ПередЗаписью`/`ПередУдалением` выпуска.
- E10 (настройки, ручной выпуск): переключатель уже на форме «Производство»; `ИспользоватьУпрощенныйВыпускГП` не тронута.
- E11 (демо-данные): документы контура — с шагом две секунды; реализации по заказам на производство создают автовыпуски
  при включённом переключателе.
- E12 (АРМ): автовыпуск связан с заказом через реализацию, критерий `СвязанныеДокументы` заказа его не показывает.

- Общий модуль `Производство`: создание, перезаполнение, распроведение и пометка автовыпуска, проверка
  «это автоматический выпуск».
- Точка вызова — проведение реализации, после блокировок и до формирования движений товаров. В
  «перед записью» нельзя: у нового документа ещё нет ссылки, и выпуск появлялся бы даже при записи
  черновика.
- Условия: обе константы включены, основание — заказ с операцией «Производство», есть строки с типом
  «Продукция» или «Полуфабрикат» либо со способом пополнения «Производство»/«Оба».
- Количество — отгружаемое минус уже выпущенное по этому заказу вручную и прошлыми автовыпусками.
  Если к выпуску ничего не осталось, существующий автовыпуск распроводится.
- Дата выпуска на секунду раньше реализации. Если поступление материалов датировано той же секундой,
  проведение отклоняется с просьбой сдвинуть дату: порядок внутри секунды не определён.
- Материалы: по составу заказа или техкарте, доля отгрузки считается по каждой позиции продукции
  отдельно. Партии — остатки партий поступлений, привязанных к заказу напрямую или через заказ
  поставщику, в порядке даты партии; непокрытый остаток идёт строкой без партии и попадает в ресурс
  «ИзОстатка». Без состава и без техкарты списываются партии поступлений пропорционально доле
  отгрузки, хвост — на последней отгрузке. Механизм списания менять не нужно: он уже умеет смесь
  «часть по партии, часть по общей очереди».
- Тип основания выпуска расширяется реализацией. Партия готовой продукции в движениях реализации
  проставляется автовыпуском, иначе очередь съест старую партию ручного выпуска и себестоимость
  отгрузки перестанет соответствовать её материалам.
- Отказ выпуска пробрасывается в отказ проведения реализации вместе с сообщениями.
- Отмена проведения реализации распроводит выпуск (первый в конфигурации обработчик удаления
  проведения), перепроведение перезаполняет, пометка удаления переносится на выпуск.
- Ручная правка автовыпуска запрещена: отказ в «перед записью» и форма только для чтения с пояснением.

наполнена поведением ещё в E9. Прогон на базе ждёт полного обновления `build/ib`.

**Обязательства для следующих этапов:**
- E11 (демо-данные): материалы ручных выпусков — `Документы.ВыпускПродукции.ЗаполнитьМатериалыПоТехкартам`.
- E12 (АРМ): форма ручного выпуска без пустых серверных вызовов; совет перезаполнить выпуски — только ручные.
- E13 (drissotex): константы `ИспользоватьУпрощенныйВыпускГП` в базе drissotex нет — удаление перенос не задевает.

Чек-лист по ручному выпуску: заполнение по техкарте через фасад, удаление мёртвого кода (проверка
веса, доли стоимости, закомментированная установка цены). Бухгалтерские проводки выпуска не трогаем,
это развилка Р1: записываем в техдолг, что готовая процедура проводок не подключена к диспетчеру.
Константа «Автоматический выпуск ГП при продаже» наполняется поведением и выносится на форму настроек
«Производство» под общий переключатель. Константа «Упрощённый выпуск ГП» удаляется, пункт Р10
закрывается в дорожной карте.

### E11. Тесты и демо-данные (M)

- Новые сценарии тестов документов: техкарта (версии на дату), заказ на производство (полная цепочка
  со стадиями и потребностями), способ пополнения, производственный контур с автовыпуском.
  Проверки контура: потребности по трём ресурсам, остатки материалов и продукции, себестоимость,
  прибыль, стадии, повторное проведение не дублирует выпуск, отмена проведения распроводит его.
  Шаг между документами — две секунды.
- Отдельным пунктом (требование шага 9) — функциональный тест бизнес-процесса: записываемые
  демо-данные контура «2mzl». Новый экспорт в обработке тестовых данных, режим запуска и флаг в
  скрипте фикстур, строки в `docs/TESTING.md` и `docs/TESTS.xlsx` (уровень 3 для сценария, уровень 2
  для демо-набора с ручной приёмкой).

### E12. АРМ производства (M)

Развиваем существующее рабочее место, а не пишем новое: сверху таблица заказов на производство со
стадией, индикатором и колонками потребность, заказано, пришло, выпущено, отгружено, оплачено; снизу
две существующие справочные таблицы (состав заказа и связанные документы). Кнопки «Заказ поставщику»,
«Поступление», «Отгрузка», «Открыть заказ» — в командной панели формы по выделенному заказу.
Вариант с одной таблицей теряет список связанных документов, сводная сетка «заказ × стадия» — это
отчёт, а не рабочее место, и к ней не прикрутить действия.

### E13. Совместимость с базой drissotex (M)

Проверки: ни один uuid не изменился и ни одна табличная часть не удалена (диффом по метаданным);
журнал реструктуризации на копии базы содержит только изменение типов реквизитов и создание регистров;
тесты документов и смок-тест зелёные; перепроведение двух-трёх десятков выпусков, особенно
мультивыпусков, даёт те же суммы прихода готовой продукции, что и до перевода техкарт в регистр;
регресс владельца по чек-листам волн плюс новый чек-лист производственного контура.

### E14. Кейс и пресс-релиз 2mzl (M)

Кейсы на лендинге не файловые: их заводят в портале, лендинг тянет их запросом. Поэтому готовится
текст на французском в структуре карточки кейса (задача, что сделали, результат, УТП, призыв к
действию) с раскрытым именем заказчика, плюс методическая часть «как организовать производство в
maERP». Черновик кладётся в `docs/cases/2mzl-production-fr.md`, заводит и публикует владелец.
Список скриншотов даётся отдельно, чтобы владелец подготовил их заранее.

### E15. Скилл учёта времени (M)

Свежая редакция скилла копируется из соседнего проекта в `.claude/skills/task-time-tracking/` и
адаптируется под maERP (пути, категории, калибровка). Ретроспективно восстанавливаются все 18 дней с
коммитами, от 2026-06-28 до 2026-09-09, по журналу и статистике изменений; каждый файл помечается как
восстановленный задним числом. Выполняется последним шагом, чтобы в него попала и работа по этой волне.

## Порядок и зависимости

E0 → E1 → E2 → E3 → E4 → E5 → E6 → E7 → E8 → E9 → E10 → E11 → E12 → E13 → E14 → E15.

E3 не зависит от E1 и может идти параллельно. E7 ждёт починки запроса списка поступления. E9 требует
E1, E5, E6 и E7. E13 выполняется после всех изменений метаданных.

## Проверка

После каждого этапа: `scripts/lint.sh` без новых замечаний против базовой линии, `scripts/refcheck.py`
без новых расхождений, сообщение владельцу о необходимости обновления и проверки конфигурации в EDT.

После этапов с движениями и формами:

```bash
scripts/smoke.sh && scripts/doctests.sh
```

Перед передачей на тест: версия в свойствах конфигурации поднята, секция версии в общем макете
описания изменений заполнена на четырёх языках, отчёт по часам за день записан.

Ручная приёмка владельцем на демо-данных: предложение → заказ на производство → заказ поставщику по
потребности → приходная накладная → отгрузка с автовыпуском; проверяются стадии в списке и в форме,
отчёт по потребностям, рабочее место производства, себестоимость и прибыль по отгрузке.

## Риски

- **Запись документа внутри проведения** — приём в конфигурации новый. Ошибка выпуска обязана
  становиться отказом проведения реализации с читаемыми сообщениями, а не исключением.
- **Совпадение секунд** между поступлением материалов и автовыпуском даёт молчаливую недостачу.
  Закрывается явной проверкой и шагом в две секунды в тестах и демо-данных.
- **Коэффициенты техкарт через фасад** меняют распределение себестоимости мультивыпусков, если
  правило воспроизведено неточно. Ловится только сверкой сумм до и после на копии базы клиента.
- **Расширение перечисления статусов** затрагивает список заказов, рабочее место и дашборд: у них
  появляются значения, которых они раньше не видели. Проверяются картинки и оформление во всех трёх.
- **Удаление табличной части техкарты** запрещено до отдельного релиза: иначе данные клиента теряются
  безвозвратно, а клиент, обновляющийся «через версию», получит обработчик переноса по уже удалённой
  колонке.

## Побочная находка

Пароль тестовой базы лежит открытым текстом в `.claude/settings.local.json`, что расходится с
правилом из `docs/TESTING.md` («в файлы и скрипты они не попадают»). Файл закрыт глобальным
`~/.config/git/ignore`, в публичный репозиторий не попадает, поэтому это не утечка, но правило стоит
либо соблюсти, либо смягчить формулировкой «кроме локальных настроек, закрытых от git».
