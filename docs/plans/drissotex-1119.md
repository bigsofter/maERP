## 1. 2605479 — свойства ГП на закладке передачи и в акте

### 1.1 «<>» вместо значений свойств (найдено на копии базы Drissotex)

Проба на `build/ib-dris-props`: `Метаданные.Справочники.ЗначенияДополнительныхРеквизитов.ОсновноеПредставление =
ВВидеКода`. В `.mdo` свойство не задано, умолчание перечисления — первый литерал (`AsCode`); код у значений не
заполняется (автонумерации нет) — представление пустое, платформа рисует «<>». То же у
`НаборыДополнительныхРеквизитов`.

Правка: `<defaultPresentation>AsDescription</defaultPresentation>` у обоих справочников; у значений — ввод по строке
ещё и по наименованию (`inputByString` Description перед Code). Реструктуризации нет — свойство метаданных.
Остальные справочники без явного свойства (`НомераГТД`, `ЗначенияСвойствНоменклатуры`, `ДоговорыСКонтрагентами`) не
трогаю: у них код осмысленный или справочник не используется — проверю `refcheck`/поиском и запишу в TECHDEBT, если
вид представления там тоже ошибочный.

### 1.2 Панель «Свойства» на закладке передачи — свойства ГП

Сейчас `ПродукцияСвойствСтроки`: указан ПФ/ГП строки — он сам (ПФ — свойства ПФ); не указан — единственный родитель
материала по дереву (для материала ПФ это ПФ, а не ГП); несколько — пусто.

Новое правило (по задаче: «должны отображаться из ГП»): функция возвращает **готовую продукцию заказа** —
номенклатуру строки `ТЧТовары`:
1. Указанная продукция есть среди строк товаров заказа — она.
2. Иначе строки материалов заказа с номенклатурой = указанный ПФ (или, если ПФ не указан, = материал строки) →
   их `КодСтрокиПродукции` → номенклатура строки товаров с этим `КодСтроки`. Одна различная — она.
3. Иначе в заказе одна различная номенклатура товаров — она. Иначе пусто (панель с подсказкой, как сейчас).

Функцию с этим правилом кладу в `Документы.ПередачаВПереработку` (там уже `СтрокиЗаказа`), `ПродукцияСвойствСтроки`
вызывает её. Запись свойства (`СтрокаПередачиСвойств` → та же функция) пишет в карточку ГП; проверка
`ТекстЗапретаЗаписиСвойства` (продукция из `ПродукцияЗаказа`) ГП пропускает — проверю, что ГП в `ПродукцияЗаказа` есть.
Заголовок панели уже называет изделие.

### 1.3 Акт передачи — свойства ГП отдельным крупным блоком, строки компактнее

- Строки обеих групп («Передано», «Ожидаемая продукция») печатаются без свойств под строкой: `ДанныеСтрокДокументов`
  без `ЯзыкСвойств`. Вес под строкой (2.0.16.125) уходит вместе со свойствами — строки компактные, как просил
  владелец 01.11.
- После таблицы — новый блок «Свойства изделия»: на каждую ГП передачи заголовок с наименованием ГП и строки «Свойство: значение» шрифтом крупнее
  строк таблицы. Нет заполненных свойств — блока нет.
- Изделия акта собирает **отдельная множественная функция** (ревью плана, P2): по каждой строке передачи (заказ строки
  или основание) — все ГП, к которым ведёт строка по правилу 1.2 (шаги 1–2 без условия «одна различная»; при пустом
  результате — все строки товаров заказа), объединение без повторов в порядке строк. Скалярная функция 1.2 остаётся
  только для панели и записи свойства: там несколько ГП — честный отказ от выбора карточки, а в печати — все изделия.
- Макет: новые области `СвойстваИзделияЗаголовок`, `СвойстваИзделияСтрока` в `scripts/mxlxgen/branded.py` по образцу
  `СверкаТекст`, перегенерация `Template.mxlx`. Данные — необязательное поле `СвойстваИзделий` в
  `ДанныеТоварногоДокумента` (Неопределено у всех остальных документов) — накладные, BL, Facture не меняются.
- BL и расходный ордер продолжают печатать свойства под строкой (2.0.16.125) — их не трогаю.

### 2.2 Общие итоги отчёта

После цикла по переработчикам — блок «Итого по отчёту»: отправлено / получено / остаток по единицам (`ИтогиСтрокой`),
из тех же таблиц пакета без отбора по переработчику.

Дедупликация «Принято» (ревью плана, круг 2, P1): нынешний ключ переработчика «документ + номенклатура +
характеристика» склеивает строки одного поступления, закреплённые за разными заказами (`ТЧГотоваяПродукция.Заказ`
заполнен), — итог переработчика занижен уже сейчас. В выборку «Принято» добавляю колонку `ЗаказСтроки` (`ГП.Заказ`,
пустая у нераспределённых строк; у хвостов — тоже фактический `ГП.Заказ` строки поступления: хвост означает отсутствие списания сырья по заказу, а не отсутствие заказа у строки — ревью плана, круг 3, P1) в выбор и группировку обеих веток объединения; ключ дедупликации — документ +
номенклатура + характеристика + `ЗаказСтроки`. Повтор убирается только у нераспределённой строки смешанного
поступления, показанной в нескольких заказах. Тот же ключ — у итога переработчика (исправление) и у общего итога;
тест — поступление с двумя строками одной ГП под разными заказами: итог = сумма обеих. Сроки (средний срок, старейшая незакрытая передача) — по всем парам.

### 2.3 Номер и дата документа подрядчика

- `ПоступлениеИзПереработки`: реквизиты `НомерВходящегоДокумента` (Строка 30) и `ДатаВходящегоДокумента` (Дата, только
  дата) — копия пары `ПоступлениеТоваровУслуг` (синонимы ru/fr/en/es «Документ подрядчика №» / «от»). Новые колонки,
  данных нет, обработчик обновления не нужен; атрибутных прав у документа нет.
- Форма документа: группа `ГруппаНомерДатаВходящего` в `ГруппаШапкаПравая` рядом с контрагентом, по образцу
  `ПоступлениеТоваровУслуг` (ширина 12, без растягивания, шрифт шапки колонок не нужен — не таблица). АРМ производства
  создаёт поступления строками — реквизит заполняют в форме документа; в таблицу АРМ колонку не добавляю.
- Отчёт: колонка поступления — номер подрядчика и его дата; пустой номер — наш номер и дата документа (решение
  владельца). Тест сценария переработки (строки 12465, 12467) — проверка нового правила: заполненный номер подрядчика
  в тексте отчёта, без номера — наш номер.

## 3. 2605508 — новый вариант «Долги по отгрузкам» отчёта «Деньги и статусы заказов клиентов»

Решения владельца: вариант A — заказчик → отгрузка (номер, дата) → товар и количество, долг по документу; отгрузка —
реализация (BL); новый вариант рядом со старыми.

- Долг — только из регистра, без правил покрытия (ревью плана, круг 4: покрытие бывает частичным, а проведённая
  налоговая переносит расчёты не всегда — отсечка, защищённые документы). Группировка: **Заказчик → Документ расчётов
  → Отгрузка → Товар**.
  - «Документ расчётов» — каждое значение `ОбъектРасчётов` регистра `ВзаиморасчётыСПокупателями` по заказчику с
    ненулевым остатком на конец периода или оборотом за период (BL или налоговая): номер, дата, начислено (приход за период только собственными движениями документа: регистратор = сам объект расчётов;
    сторно переноса — регистратор налоговая, объект BL — в «Начислено» не входит, ревью плана, круг 6, P2; у налоговой
    её принимающая запись переноса — её начисление), оплачено (расход за период без переноса и без `КорректировкаДолга`), корректировки (расход регистратора `КорректировкаДолга` — отдельной колонкой, как в действующем отчёте, строки 339–350), долг (остаток на конец периода). Долг выводится только на этом
    уровне; на долях не делится (правило `order-money-status.md`).
  - «Отгрузки» документа расчётов: у объекта-BL — сама BL (её непокрытый остаток, если покрытие частичное); у
    объекта-налоговой — BL, чей долг фактически перенесён на неё: движения регистра с регистратором = эта налоговая,
    `ОбъектРасчётов` = BL и датой не позже конца периода (сторно переноса). Частично покрытая BL видна в обоих местах
    со своим остатком у каждого объекта — двойного долга нет, долг у каждого объекта свой.
  - Под отгрузкой — товары BL с количеством и суммой строки (справочно, без долга).
- Строки — из `ТЧТовары`/`ТЧУслуги` BL, попавших в отчёт как отгрузки документов расчётов (дата BL не ограничена началом периода: переходящий долг расшифровывается своими товарами, ревью плана, круг 5), плюс проведённые BL периода без долга и без оборота расчётов не нужны — вариант про долги (склад любой: долг ведётся на
  реализации и при ордерном складе; расходные ордера в этом варианте не участвуют). **Реализации с заполненной
  табличной частью «Основания»** (налоговые и сводные документы на основаниях, `НалоговыеДокументыНаОснованиях`) —
  не отгрузки: исключаются тем же условием, что в `ВТ_РеализацииЗаказов` (`ObjectModule.bsl` 103–155), иначе их строки
  задвоили бы строки исходных BL (ревью плана, P1). Их долг виден на уровне «Документ расчётов» как у объекта расчётов. Заказ — колонка уровня отгрузки (не
  группировка), заказа строки у реализации нет (ревью плана, круг 3, P2): заказ документа определяется как в
  действующем отчёте — `Основание` шапки, иначе единственный заказ по обратной связи (`ВТ_ОбратныеСвязи`/
  `ВТ_РеализацииЗаказов`); заказов несколько или ни одного — колонка пустая, строки отгрузки остаются в отчёте.
- Реализация: второй внешний набор `Отгрузки` в `ObjectModule` (функция `ДанныеОтгрузок` по образцу
  `ДанныеЗаказов`), новый `dataSet` и `settingsVariant` «ДолгиПоОтгрузкам» в `Template.dcs` с
  `AppearanceTemplate = Античный`; внешний набор передаётся всегда (иначе ошибка компоновки других вариантов). Запрос
  отгрузок выполняется, только если набор `Отгрузки` попал в скомпонованный макет (`МакетКомпоновки.НаборыДанных`
  после `КомпоновщикМакетаКомпоновкиДанных.Выполнить` — компоновщик включает только используемые наборы); так же
  для набора `Заказы`. Работает и для пользовательских сохранённых вариантов с любыми ключами (ревью плана, круг 2,
  P2); иначе — пустая таблица с колонками.
- Тест: сценарий уровня 3 — заказчик с двумя BL (одна оплачена частично) и одной налоговой на две BL: долг документа
  расчётов по остатку регистра, BL под налоговой по движениям переноса, отчёт на дату до налоговой — BL своими
  документами расчётов; строки товаров с количеством; смок открывает все варианты отчёта.

### Поправки по ревью кода и базы (реализация)

- Обороты документа расчётов — **нетто, вместе со сторно переноса** (ревью базы, P1): у BL, перенесённой на налоговый
  документ, начисление и оплаты гасятся сторно и переходят к налоговому; полностью перенесённая BL без остатка в отчёт
  не попадает, итог по заказчику не задваивается. Сторно служит только связью BL → налоговый документ.
- Деньги документа — отдельной строкой без отгрузки и товара (ревью кода, P2): итоги не зависят от того, какая строка
  товара прошла отбор. Отбор по отгрузке или товару строку денег не пропускает — осознанно: долг документа к отдельной
  BL или товару не относится (BL одной Facture делят долг, долями не делим).
- Сумма строки отгрузки убрана (ревью базы, P2: валюта документа рядом с деньгами в основной валюте) — под отгрузкой
  товар и количество, как просил владелец.
