## Целевое меню (§3 плана, уточнить в плане этапа)

```
Продажи
[В] Заказы покупателей +   Продажи +   Возвраты от покупателей
├─ Опт            Коммерческие предложения + (ФО КП) · Неотгруженные заказы · Задачи по заказам (ФО Задачи)
│                 Заявки на поиск товара (ФО Заявки; один раз)
├─ Розница        (ФО ИспользоватьРозничныеПродажи) Рабочее место кассира · Кассовые смены
├─ Цены           Цены продажи · Установка цен + · Установка цен вручную · Правила ценообразования (ФО Правила)
│                 Виды цен · Надбавки на себестоимость ⟵ (ФО Правила) · Отчёт «Цены номенклатуры»
├─ Клиенты        Покупатели · Договоры с покупателями · Кураторы договоров ⟵
│                 Категории клиентов · Роды деятельности · Условия оплаты · Причины возвратов
├─ Отчёты         Анализ продаж (ведомость / по дням / ABC — §4) · Ведомость расчётов с покупателями · Долги
│                 покупателей · Просроченные долги покупателей ⟵ · Неоплаченные продажи · История клиента
│                 · История товара · История заказов по статусам · Реестр продаж (из Казначейства)
└─ Справочники    Товары и услуги для продажи (Номенклатура, отбор) · Товарные группы
```

Решения этапа (без владельца, с записью в план):
- **Налоговые отчёты** (правило 7 §2): «Расчеты с покупателями» и «Ведомость по продажам (налоговая)» — из
  «Продаж» убрать (в Бухгалтерии уже есть); «Проданный товар без накладной» и «Налоговые накладные: нехватка
  товара» — перенести в корень «Бухгалтерии» сейчас (раздел «Налоговые документы» — этап 5), иначе их не будет
  в меню. Проверить, кто из ролей «Продаж» теряет пункт (права на отчёт + View на Бухгалтерию).
- **«Анализ продаж»**: три отчёта на регистре `Продажи` — в один с вариантами, **только если** ABC-анализ
  укладывается в СКД без потери смысла и без правки других разделов; иначе три отчёта под понятными именами в
  «Отчётах», объединение — в TECHDEBT. Удаление отчётов — нет (ссылки, права, пользовательские варианты).
- **«Опт» под опции**: группа с объектами разных опций — подсистема в составе ФО видна, если включена любая
  (`menu-restructure.md` §6 п. 2). Решить, в какие ФО включать группу, чтобы при выключенных заказах, КП, задачах
  и заявках не оставался пустой заголовок, а при включённых не пропадало ничего.
- **Заказ покупателя** — и в ФО `Производство` (заказ на производство); список в «Продажах» показывает и заказы на
  производство — оставить как есть или отбор по виду операции: решить и записать.
- **Виды оплат** (`TypesDePayment`) — в «Розницу» или в «Казначейство / Оплаты клиентов» (этап 5): решить; до
  этапа 5 пункт не должен пропасть из меню.
- **Уходят из «Продаж»**: «Поставщики» и общий список контрагентов; «Перевозчики» → «Склад» (этап 4 — до него
  оставить в «Продажах», если иначе пропадут из меню); «История поиска в ЛКП» → CRM, «Виды и настройки заданий» →
  «Настройка» (этап 6 — то же правило: не оставлять без меню).
- **Реестр продаж** — из «Казначейства» в «Отчёты» (как реестр поступлений в этапе 2); роль Оператор и другие без
  View на «Продажи» — проверить потери.
- **«Создать»**: заказ, продажа, КП, установка цен (если начинает цепочку), правило ценообразования; без возвратов
  и справочников.

## Ловушки (из этапа 2 — не повторять)

1. **Подсистемы** — шесть мест на переименование, uuid сохранять, `git mv`. **`git mv` сразу стейджит** — коммит
   плана делать `git commit <пути>` или до переименования, иначе переименования уедут в коммит плана.
   Сборку стейджить `git add -A`, после — `git show --stat` и проверка NFC/NFD (workflow-007).
2. **Новая команда справочника протекает во все разделы**, где лежит справочник (P1 этапа 2): «Товары и услуги для
   продажи», «Договоры с покупателями» скрыть `<visible/>` в `.cmi` Закупок, Склада, Производства, Казначейства.
   `menucheck.py` — по всем разделам, не только по «Продажам».
3. **Необъявленный параметр формы платформа отбрасывает** (так не работают «Сырьё/ПФ/ГП» и не работал
   `Заголовок` договоров). Объявленный — всегда есть в `Параметры`: `Параметры.Свойство(...)` становится истиной,
   проверять `ЗначениеЗаполнено`. Отбор по реквизиту, которого нет в произвольном запросе списка, через `Отбор` не
   работает — параметр запроса (образец `СпособыПополнения`).
4. **Явная видимость каждой команды**; своя команда и стандартная `OpenList` не вместе (mdo-005); группа
   `ActionsPanelCreate` допустима (сверено по модели EDT).
5. **Отчёт, скопированный с другого**, проверять полем к полю против источника: в этапе 2 схема держала поля,
   которых функция не возвращает. Вариант — схемой из файла до базы (`build/menu/run.sh` или сборка epf на пустой
   базе, если `build/ib` занят); если отчёт на внешнем наборе — подать набор в проверке.
6. **Права**: перечислить, кто что **получает и теряет** в меню, а не только потери; права на данные не расширять.
7. **`build/ib` может держать конфигуратор EDT** (агентский режим) — синхронизировать копию (`cp -R build/ib
   build/ib-stage3`, `scripts/ib-sync.sh build/ib-stage3`, смок и doctests с тем же аргументом) и написать это в
   отчёте. CLI EDT может зависнуть на «Waiting for permission to execute operation 'External export'»
   (`~/EDT/ws-maERP/.metadata/.log`) — снять **свой** процесс по PID и повторить.
8. Значения ФО кэшируются на серверный вызов (bsl-023) — в сценарии не переключать опцию дважды.
9. Не трогать: Склад (этап 4), Бухгалтерию сверх переноса двух налоговых отчётов (этап 5), CRM/Настройку (этап 6).
