## Ответы владельца (2026-10-08, вопросы волны 5)

1. **Станки для продукции — список допустимых станков у продукции; пустой — любой** действующий станок.
2. **Автоплан — по дате отгрузки:** самая ранняя отгрузка — на станок, который закончит её раньше всех. Переналадка
   одна на станок и закладывается между любыми двумя загрузками (решение 4), порядок её не уменьшает.
3. **Автоплан уже запланированное не трогает:** ставит только неразмещённое в свободные окна.
4. **Автоплан — черновик:** предлагаемые размещения на планировщике и списком, требования — по «Принять».
5. **Вес выпуска для качества OEE — из карточки продукции** (`ВесЕдиница`, правило `КгНаЕдиницу`); продукция без веса
   в качество не входит (ни выпуск, ни вход её требований), отчёт предупреждает.
6. **Отказ для MTBF/MTTR — только вид «Ремонт или авария»** (фактический).
7. **Растяжение меняет только время:** ручная длительность хранится в требовании, количество не меняется, расчёт по
   весу её не перезаписывает.
8. **Порядок:** плановые даты ТО + OEE → MTBF/MTTR → автоплан → растяжение; **не останавливаться между сборками** —
   каждая сборка коммитится со своей версией и секцией «Что нового», владелец проверяет конечный релиз.
9. **Добавлено владельцем — инвентаризация станков** (сборка 5 волны): документ инвентаризации выбирает станок вместо
   склада (вид операции «Инвентаризация станков»); списание и оприходование умеют работать по станку; оприходование по
   станку называется «Оприходование материалов» и открывается из «Производство → Станки» списком, сразу
   отфильтрованным по своему виду операции.

## Сборка A (2.0.16.36): плановые даты обслуживания и OEE

### Факты

- `ОбслуживаниеСтанка`: `Плановое` (Булево), `Начало`, `Окончание`; одна запись «Загрузки станков» с `План =
  Плановое`. Перевод в факт — тот же документ с `Плановое = Ложь` и фактическим временем: плановые даты теряются.
  Модуля формы нет, модуль объекта — заполнение, проверка, проведение.
- `ЗагрузкаСтанков.КатегорииВремени` (сборка 4) — фонд, работа, обслуживание, «нет заказа» по станку до момента
  расчёта; строка фонда на станок; работа — без объединения фактических обслуживаний.
- `ЗагрузкаСтанков.ЗавершенныеТребования` — требования, завершённые в периоде: `Кг` (израсходованные материалы),
  `Часы` (работа без ограничения сменами), `НормаЧасов` = Кг / выработка + смена заказа, `Выпущено`, `Продукция`.
- `КгНаЕдиницу(Номенклатура)` — кг на единицу, 0 — веса нет.

### Плановые даты обслуживания

- Новые реквизиты `ОбслуживаниеСтанка`: `ПланНачало`, `ПланОкончание` (`Date`, `DateTime`, как `Начало`). Синонимы на 4
  языках: «План начала», «План окончания».
- Правило (модуль объекта, `ПередЗаписью`, не при `ОбменДанными.Загрузка`): пока `Плановое = Истина` — `ПланНачало =
  Начало`, `ПланОкончание = Окончание` (перенос на планировщике и правка в форме двигают план). Переход в факт
  (`Плановое = Ложь`) — плановые даты **остаются** как были. Документ, переведённый в факт до этой сборки, плановых
  дат не получает: если в базе он ещё плановый, а `ПланНачало` пуст (не перезаписан после обновления), читающий
  запрос берёт `Начало`/`Окончание` (см. ниже). Переход в факт этого документа без перезаписи невозможен — запись
  проходит `ПередЗаписью`: если `ПланНачало` пуст, а в базе документ плановый, даты берутся из базы
  (`ОбщегоНазначения.ЗначенияРеквизитовОбъекта(Ссылка, "Плановое, Начало, Окончание")`) до замены. Поэтому
  **обработчик обновления не нужен**: старые плановые документы получат даты при первой записи, а до неё читаются по
  `Начало`/`Окончание`.
- `ПриКопировании` — плановые даты очищаются (копия плановая — получит их при записи).
- Форма документа: поля `ПланНачало`, `ПланОкончание` в левой колонке шапки после `Окончание`, только просмотр
  (`readOnly`), подпись «План: с … по …» не нужна — синонимы. Видны всегда (у планового совпадают с началом/окончанием).
  Модуля формы не появляется.

### Плановые остановки в `КатегорииВремени`

- Новая колонка таблицы категорий `ПлановыеОстановки` (часы, только в строке фонда станка).
- Источник — новый запрос `ПлановыеОстановкиПериода(Станки, Начало, Окончание)`: проведённые непомеченные
  `ОбслуживаниеСтанка` станков, интервал = `ПланНачало`–`ПланОкончание`, если заполнены; иначе плановый документ —
  `Начало`–`Окончание`; иначе фактический вида «Плановое ТО» без плановых дат — `Начало`–`Окончание` (ТО, введённое
  сразу фактом, всё равно плановое по виду). Фактический ремонт, переналадка, «Прочее» без плановых дат — не плановые.
- Часы = объединение плановых интервалов ∩ факт-окно `[Начало, Мин(Окончание, Момент))` ∩ рабочие интервалы,
  **минус** пересечение с фактической работой станка (ТО запланировали, но станок работал — остановки не было,
  иначе доступность больше 100 %). Один запрос на период, интервалы — общей процедурой слияния.
- Прочие колонки и отчёты сборки 4 не меняются (контрольный пример сборки 4 — регресс).

### Отчёт «Эффективность станков» (`ЭффективностьСтанков`, СКД, по образцу `ВыработкаСтанков`)

`Отчеты.ЭффективностьСтанков.ДанныеОтчета(Период, Момент)` → `Эффективность` (таблица), `Предупреждение`:
- по строке на станок из `КатегорииВремени(СтанкиОтчетов, Начало, Окончание, Момент)` (по режиму): `Фонд`,
  `ПлановыеОстановки`, `Работа` (сумма по станку);
- по строке на требование из `ЗавершенныеТребования`: `ЧасыТребований` (= Часы), `НормаЧасов`, `КгВход` (= Кг),
  `КгВыпуск` = `Выпущено` × `КгНаЕдиницу(Продукция)`, `КгВходКачества` = `Кг`, если у продукции есть вес, иначе 0
  (ответ 5); продукция без веса — в предупреждение.
- Ресурсы СКД (итоги группировок — формулы от сумм, а не средние процентов):
  - `Доступность` = Работа / (Фонд − ПлановыеОстановки) × 100;
  - `Производительность` = НормаЧасов / ЧасыТребований × 100 (то же, что «% нормы» выработки: факт кг/ч к норме,
    норма включает смену заказа); требование без нормы (у станка нет выработки) не входит ни часами, ни нормой (ревью
    P2-10);
  - `Качество` = КгВыпуск / КгВходКачества × 100; требование, у которого вес посчитан не по всем материалам
    (`ЗавершенныеТребования.ЕстьМатериалыБезВеса`), в качество не входит (ревью P2-9);
  - `OEE` = Доступность × Производительность × Качество / 10000; множитель, который посчитать нельзя (знаменатель 0 —
    нет завершённых требований, нет выработки станка, нет веса продукции), принимается 100 % и называется в
    предупреждении — иначе один незаполненный вес обнуляет OEE станка.
  - Процент больше 100 не обрезается (перевыполнение нормы видно).
- Поля группировок: станок, продукция, требование. Структура по умолчанию — станок; детализация — пользователем.
- Период — `ЗагрузкаСтанков.ГраницыПериодаОтчета`; факт — до момента (правило сборки 4).
- Меню: «Производство → Отчёты» после «Выработки станков»; ФО `ИспользоватьУчетСтанков`; `ОператорПроизводства` —
  `Use`, `View`; `Configuration.mdo` — список отчётов; форма — `ОбщаяФорма.ФормаОтчёта`; синонимы на 4 языках
  («Эффективность станков (OEE)», «Efficacité des machines (TRS)», «Machine effectiveness (OEE)», «Eficiencia de
  máquinas (OEE)»).

### Тесты A (`ТестыДокументов`, сценарий `ЭффективностьСтанков`)

1. Пример сборки 4 (смена 08–16, требование 08–16, ремонт 10–12) плюс плановое ТО 16:00–17:00 следующего дня,
   переведённое в факт 16:30–17:30: `ПланНачало`/`ПланОкончание` сохранились; `ПлановыеОстановки` дня примера 0
   (ТО вне смены дня — проверка обрезки сменой), отдельный день со сменой — плановые часы в фонде.
2. Плановое ТО внутри смены, станок в это время работал → плановые остановки 0 (вычет работы).
3. Отчёт компоновкой: доступность = 6 / (8 − 0) = 75 %; производительность = норма / 6; качество = выпуск кг / вход кг
   при заданном весе продукции; без веса продукции — качество 100 % и предупреждение.
4. Регресс: `КатегорииВремени` контрольного примера сборки 4 без изменений.
5. **Последний шаг (настоящий отказ):** перевод планового ТО в факт на время другого фактического обслуживания станка
   — отказ проведения, плановые даты в базе не изменились.

## Сборка B (2.0.16.37): MTBF и MTTR

- Отчёт «Простои станков» (`ПростоиСтанков.ДанныеОтчета`): новые колонки набора `Отказов` (1 у строки фактического
  обслуживания вида «Ремонт или авария», ответ 6), `ЧасыОтказов` (полная длительность ремонта в периоде — `Часы`, не
  только рабочее время: ремонт идёт и ночью) и в строке фонда — `ЧасыРаботы` (Работа из `КатегорииВремени` по режиму,
  до момента расчёта).
- Фактический ремонт с плановыми датами (был запланирован заранее) — плановая остановка OEE, а не отказ (ревью P2-8).
- Ресурсы: `MTBF` = Сумма(ЧасыРаботы) / Сумма(Отказов) (ч наработки на отказ), `MTTR` = Сумма(ЧасыОтказов) /
  Сумма(Отказов); отказов нет — пусто (0). Плановые ремонты (флажок «Включать план») в отказы не входят.
- Синонимы полей на 4 языках: «Отказов», «Наработка на отказ (MTBF), ч», «Среднее время ремонта (MTTR), ч».
- Тест (`ОтчетыСтанков` дополнить или `ЭффективностьСтанков`): два ремонта по 2 ч и работа 6 ч → MTBF 3, MTTR 2;
  переналадка и «Прочее» в отказы не входят.
- «Что нового» 2.0.16.37 — MTBF и MTTR в отчёте простоев.

## Сборка C (2.0.16.38): допустимые станки и автоплан

### Допустимые станки продукции

- Новая ТЧ `Станки` справочника `Номенклатура` (колонка `Станок`, `ПроизводственноеОборудование`, отбор «не
  выведен»). Новая ТЧ — новая таблица базы, реструктуризация основной таблицы номенклатуры не нужна. Синоним «Станки».
- Форма элемента номенклатуры: страница «Станки» (таблица с одной колонкой) — видимость по ФО
  `ИспользоватьУчетСтанков` (`functionalOptions` элемента) и только для продукции (видимость как у прочих
  производственных реквизитов карточки — уточняется по форме при реализации). Подсказка: «Пустой список — любой станок».
- Загрузка номенклатуры из базы Drissotex (`MERGE-DRISSOTEX.md`) ТЧ не знает — список пустой, что значит «любой».

### Автоплан (`ЗагрузкаСтанков`)

- `ПредложениеАвтоплана(Момент, Склад) Экспорт` → ТаблицаЗначений: `Заказ`, `КодСтроки`, `НомерЗаказа`, `Клиент`,
  `ДатаОтгрузки`, `Номенклатура`, `Характеристика`, `Количество` (остаток строки), `Вес`, `Станок`, `Начало`,
  `Окончание`, `Часы`, `Просрочен`, `ТекстОшибки`. Без записи в базу.
  1. Строки — `СтрокиГотовых(Неопределено, Склад)` (те же «Готовые к запуску»: стадии, материалы, остаток строки),
     порядок — дата отгрузки (пустая — в конце), заказ, строка.
  2. Станки строки — ТЧ `Станки` продукции ∩ действующие (не выведен, не помечен); пустая ТЧ — все действующие.
  3. Контекст окна (`КонтекстОкна`: рабочие интервалы и занятость на горизонт) — по одному на станок, читается один
     раз; каждое предложенное размещение добавляется в занятость контекста с **регистратором-маркером черновика**
     (строка «Автоплан», не `Неопределено`: `ОкончаниеПомехи` пропускает записи, равные `Исключить`), и занятость
     **пересортировывается по началу** (`ОкончаниеПомехи` прерывает обход по началу) — ревью P1-1, P1-2. Реквизиты
     станков читаются один раз (P3-12).
  4. Для строки и каждого её станка: часы — тем же правилом, что при размещении (`ДлительностьМатериалов` по
     материалам строки, заполненным как в требовании; ревью P2-7, тест на равенство окончаний); окно — `ОкноВКонтексте` от
     `Момент`; выбирается станок с **наименьшим окончанием** (ответ 2), равенство — порядок станков (наименование).
     Строка ставится целиком (без разбиения). Нет станка (в том числе ТЧ не пуста, но все её станки выведены —
     ошибка, а не «любой», P3-11), веса, выработки или окна — строка с `ТекстОшибки`.
  5. `Просрочен` — дата отгрузки раньше окончания.
- «Принять» передаёт **текущий** момент; черновик, посчитанный раньше текущего момента больше чем на шаг
  планирования, не принимается — пересчитывается и показывается заново (ревью P2-6).
- `ПринятьАвтоплан(Строки, Момент, Склад) Экспорт` → Массив текстов ошибок: по каждой строке без ошибки по порядку —
  `РазместитьСтроку(Заказ, КодСтроки, Количество, Станок, Начало, Момент, Склад)` (своя транзакция и блокировки,
  перепроверка остатка и окна под блокировкой — как ручное размещение). Отказ одной строки не отменяет остальных: время
  могли занять, остаток — изменить; текст ошибки «<заказ> / <продукция>: <причина>». Уже запланированное не
  трогается (ответ 3).
- Права: размещать может тот, кто размещает вручную (`МожноРазмещатьНаСтанки`).

### Закладка «Станки» (форма АРМ)

- Кнопки «Автоплан» (рассчитать черновик) и «Принять автоплан» на панели закладки, «Принять» доступна при непустом
  черновике.

  — красным (как в «Готовых»).
- Черновик на планировщике — элементы светло-зелёного цвета с текстом «Автоплан: <заказ> / <продукция>»,
  `ЗапретитьРедактирование`, значение — пусто; перенос и двойной щелчок пустые значения пропускают (P3-13).
- Страница «Станки» — в `ФормаЭлемента` номенклатуры; `ФормаЭлементаECommerce` — карточка интернет-магазина, без
  производственных реквизитов, не меняется (P3-14).

## Сборка D (2.0.16.39): растяжение на планировщике

### Ручная длительность требования

- Новый реквизит `ТребованиеНакладная.ДлительностьВручную` (Число 10,2, ч; 0 — по весу). Синоним «Длительность
  вручную, ч».
- `ТребованияНакладные.ЗаполнитьРасчетныеПоля`: `Длительность = ДлительностьВручную`, если > 0, иначе по весу (как
  сейчас); ошибка веса/выработки (`ТекстыВесаИСтатуса`) при ручной длительности не мешает проведению — вес всё равно
  считается для отчётов.
- `ЗагрузкаСтанков.ДлительностьМатериалов` в `ПеренестиЗагрузку` заменяется длительностью требования
  (`ДлительностьТребования(Объект)`: ручная или по материалам) — перенос растянутой загрузки сохраняет её длину.
- `ПриКопировании` — ручная длительность очищается; перенос на **другой станок** её сбрасывает (выработка и
  переналадка другие, ревью P3-15).
- Форма требования: поле «Длительность вручную, ч» рядом с «Длительностью» (редактируемое при «Запланировано»);
  очистка — возврат к расчёту по весу.

### Планировщик

- План требования и план обслуживания — `РежимРазрешенияРедактирования` = полное редактирование (вместо
  `ЗапретитьРастягивание`); факт — `ЗапретитьРедактирование` как было.
- `ПриОкончанииРедактирования` передаёт и `Конец` элемента. Сервер (`ИзменитьЗагрузку(Регистратор, Станок, Начало,
  Окончание, Момент)`) различает: длина элемента (Окончание − Начало) не изменилась — перенос (как сейчас); изменилась
  — растяжение: начало до шага и на смену, окончание — вверх до шага; требование — `ДлительностьВручную` = рабочие
  часы между новым началом и окончанием по режиму станка (`ЧасыВРабочееВремя`), перепроведение «Разместить» под той же
  блокировкой и сверкой с фактом, что перенос; обслуживание — новые `Начало`/`Окончание`. Растяжение до нуля рабочих
  часов — ошибка без записи.

### Тесты D (`ТестыДокументов`, сценарий `РастяжениеСтанков`)

1. Растянуть запланированное требование на 1 ч: `ДлительностьВручную` = прежняя + 1, `ПланОкончание` по режиму,
   количество прежнее; перенос после растяжения сохраняет длительность.
2. Растяжение через нерабочее время: часы — только рабочие; конец, растянутый в нерабочее время, после
   перепроведения стоит в конце смены (P3-16).
3. Обслуживание плановое — окончание сдвинуто.
4. Очистка ручной длительности — длительность снова по весу.
5. **Последний шаг:** растяжение на время другого плана станка — отказ проведения, длительность в базе прежняя.

только время, количество прежнее. Ручная длительность видна в требовании и сбрасывается очисткой поля.»

## Сборка E (2.0.16.40): инвентаризация, списание и оприходование по станку

### Факты

- Инвентаризация — `Документ.ПересчётТоваров` (подсистема «Склад → Инвентаризация»): шапка `Организация`,
  `МестоХранения`, `ТоварнаяГруппа`, `Статус`; ТЧ `ТЧТовары` (учётное `Количество`, `КоличествоФакт`, серия). Движений
  нет. Форма: «Заполнить товары»/«Заполнить остатки» — `ТоварыВНаличии.Остатки` по месту хранения на границу документа
  (`ПолучитьОстатки`, модуль формы); «Создать оприходование/списание» — оба документа на основании пересчёта
  (`СоздатьОприходованиеСписаниеТоваровНаСервере`), заполнение — `ОбработкаЗаполнения` документов (излишки и
  недостачи).
- `СписаниеТоваров` (`МестоХранения`, `Основание` — пересчёт или поступление; движения `ТоварыВНаличии` расходом с
  партиями, `Убытки`) и `ОприходованиеТоваров` (`МестоХранения`, `Основание`; `ТоварыВНаличии` приходом с ценой) —
  вида операции нет ни у одного из трёх документов.
- Склад станка — `ПроизводственноеОборудование.СкладСтанка` (место хранения). Остаток склада станка — в
  `ТоварыВНаличии`; закреплённое за требованиями — `МатериалыНаСтанках`; инвариант «остаток склада станка ≥
  закреплено» проверяет модуль набора `ТоварыВНаличии` при каждой записи (сборка 2) — списание закреплённого уже
  отказывает.
- Образец команды «список с отбором по виду операции» — общая команда `ЗаказыНаПроизводство`
  (`ОткрытьФорму(ФормаСписка, Новый Структура("Отбор", ...), , КлючУникальности)`), список ставит свой заголовок по
  отбору; подменю — вложенная подсистема (образец `Производство/Переработка`).
- Права: `Кладовщик` — полные на три документа; `ОператорПроизводства` — списание и оприходование с проведением,
  пересчёт — только чтение.

### Решение

- Новое перечисление `ВидыСкладскихОпераций`: `Склад` («По складу»), `Станок` («По станку»), 4 языка. Новые реквизиты
  у `ПересчётТоваров`, `СписаниеТоваров`, `ОприходованиеТоваров`: `ВидОперации` (пустое = по складу — старые документы
  без обработчика обновления), `Станок` (`ПроизводственноеОборудование`). Оба реквизита — в ФО
  `ИспользоватьУчетСтанков`.
- Модуль объекта каждого из трёх (`ПередЗаписью`, кроме `ОбменДанными.Загрузка`; общая процедура
  `ЗагрузкаСтанков.ЗаполнитьСкладСтанкаДокумента(Объект, Отказ)`): вид «По станку» — `Станок` обязателен, у станка
  должен быть склад станка (иначе отказ с текстом), `МестоХранения = Станок.СкладСтанка` (поле склада скрыто); вид
  «По складу» — `Станок` очищается. Проведение не меняется: движения по месту хранения = складу станка.
- **Учётное количество инвентаризации станка — весь остаток склада станка** (как у склада; ревью P1-4: закреплённое
  за запущенным требованием лежит на том же станке и физически неотличимо — учётное «без закреплённого» дало бы
  фантомный излишек и проведённое оприходование). Заполнение остатков и «по заданиям» — без изменений, по месту
  хранения = складу станка.
- Списание недостачи по станку берёт свободный остаток; недостача больше свободного (пропало закреплённое) — отказ
  существующим инвариантом (`ТоварыВНаличии`), текст называет требование: сначала завершить или отменить его.
- «Создать оприходование/списание» из пересчёта «По станку» (ревью P2-5): пустой документ не создаётся, отказ
  проведения показывается пользователю, а не превращается молча в непроведённый документ. Вне вида «По станку» —
  поведение прежнее (TECHDEBT).
- Везде проверяется `ВидОперации = Станок`: у старых документов вид пустой (P3-20). Оприходование по станку увеличивает свободный остаток станка (следующее требование возьмёт его первым —
  решение 6).
- Документы на основании пересчёта копируют `ВидОперации` и `Станок`.
- Формы документов: поле «Вид операции» (переключатель, видно при ФО) в шапке перед складом, «Станок» на месте
  склада при виде «По станку»; заголовок формы — «Инвентаризация станка», «Оприходование материалов», «Списание
  материалов» для вида «По станку». Формы списков: колонка «Станок» (основная таблица динсписка — `listcheck`); при
  отборе по виду «По станку» — свой заголовок (как список заказов на производство), пагинатор учитывает отбор.
- Меню: вложенная подсистема `Производство/Станки` («Станки», 4 языка) с тремя общими командами — «Инвентаризация
  станков» (`ПересчётТоваров`), «Оприходование материалов» (`ОприходованиеТоваров`), «Списание материалов»
  (`СписаниеТоваров`): список с фиксированным отбором `ВидОперации = Станок` и своим ключом уникальности; новый
  документ из такого списка получает вид из отбора. Команды — в ФО `ИспользоватьУчетСтанков`; видимость по правам
  документа (команда открывает форму — нет права, нет и команды в меню). `menucheck`.
- Права на документы не меняются. У общих команд своё право `View` (ревью P1-3): `Кладовщик` — все три,
  `ОператорПроизводства` — «Оприходование материалов» и «Списание материалов» (пересчёт у него только на чтение);
  `Администратор`, `Руководитель` — автоматически (`setForNewObjects`).

### Тесты E (`ТестыДокументов`, сценарий `ИнвентаризацияСтанков`)

1. Станок со складом станка; требование завершено с недорасходом (свободный остаток X) и второе запущено (закреплено
   Y того же материала).
2. Пересчёт «По станку»: `МестоХранения` = склад станка; учётное = X + Y.
3. Факт X + Y − 1: списание на основании — «По станку», станок, 1 шт со склада станка; после проведения свободный
   остаток X − 1, закреплённое Y цело.
4. Оприходование материалов по станку 2 шт — свободный остаток X + 1.
5. Вид «По станку» без станка — отказ записи; станок без склада — отказ.
6. Регресс: пересчёт и списание «По складу» — как раньше (пустой вид операции у старых документов).
7. **Последний шаг:** списание по станку больше свободного остатка — отказ инварианта, закреплённое не тронуто.

## Риски волны

- Плановые даты без обработчика обновления: старые плановые документы читаются по `Начало`/`Окончание` до первой
  записи — правило в одном запросе; переведённые в факт до 2.0.16.36 плановых дат не имеют (TECHDEBT).
- OEE множители «нельзя посчитать» = 100 % — завышение при незаполненных весах; предупреждение обязательно.
- Автоплан не резервирует материалы между строками (как ручное размещение — «кто первым запустит», решение 3 сборки
  2): две строки на одни и те же материалы могут обе попасть в план.
- Автоплан — жадный по отгрузке, не оптимальный по сумме просрочек.
- Растяжение планировщика на macOS — проверить вручную (как перетаскивание в сборке 3).
- Форма АРМ растёт: узлы только добавляются.
