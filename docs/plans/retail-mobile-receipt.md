# Мобильная приёмка через приходный ордер — `retail-mobile-receipt` (заготовка, сборка после 2.0.17.15)

Дата: 2026-11-11. Вынесено из волны 5 (`docs/plans/retail-tools.md`, п. 9) после 8 кругов `ai-review-plan`.
Статус: **заготовка** — перед реализацией свой `ai-review-plan`.

## Нерешённое ревью (круг 8) — решить в этом плане

- Удаление черновика при обнулении факта: у СкладскиеОрдера нет права `Delete` на `ПриходныйОрдер` — пометка
  удаления с исключением из поиска или узкая привилегированная операция удаления с повторной проверкой.
- Признак мобильного ордера: обычный непроведённый ордер, заполненный по поступлению на всё количество, не должен
  приниматься за факт приёмки — устойчивый признак (реквизит) и единственное поступление-источник как инвариант.

## Черновик из плана волны 5 (круги 1–7)

### 9. Мобильная приёмка

- Реквизит `ПоступлениеТоваровУслуг.ОтветственныйЗаПриемку` (uuid `9497e83d-277d-4a39-9a62-bc390e1574b3`,
  `СправочникСсылка.Пользователи`): назначает менеджер в форме поступления (группа «Склад»), виден при ордерном
  складе поступления.
- Мобильный кладовщик — пользователь с ролями MobileClient **и** СкладскиеОрдера (права на ордера даёт только
  СкладскиеОрдера; MobileClient прав на ордера не получает): пункт меню «Приёмка» — список поступлений на ордерные
  склады с `ОтветственныйЗаПриемку` = текущий пользователь и незавершённой приёмкой (неоформленный остаток по
  механизму ордеров Ф4.4 больше нуля).
- **Модель доступа**: неоформленный остаток (`ТоварыКОформлению`, `НеоформленныеСтроки` — привилегированная) ролям
  не открывается. Список и ожидание — узкие серверные функции обработки в привилегированном режиме, которые сами
  проверяют: у пользователя право `Добавление` на `ПриходныйОрдер` (роль СкладскиеОрдера), поступление назначено
  ему (`ОтветственныйЗаПриемку` = текущий пользователь), склад поступления ордерный; возвращают только поступления и
  строки, прошедшие проверки (номенклатура, характеристика, серия, упаковка, количества — без сумм и цен). Запись и
  проведение ордера — под правами пользователя (права на ордер даёт СкладскиеОрдера). Тест — непустой список под
  MobileClient + СкладскиеОрдера, пустой/отказ под одной MobileClient.
- **Приёмка ведётся в черновике `ПриходныйОрдер` на сервере**, а не в памяти формы. Черновик приёмки —
  непроведённый, не помеченный на удаление ордер, в строках которого `ДокументИсточник` = это поступление, и
  `Ответственный` = текущий пользователь. Создаётся **атомарно при первом положительном изменении факта** (до первого
  скана черновика нет — повторный вход показывает пустой факт); факт обнулён по всем строкам — черновик удаляется
  (непосредственное удаление непроведённого ордера, проверки `ПередУдалениемОрдера` действуют). После потери формы
  или сеанса повторный вход находит тот же черновик с уже принятыми количествами; два черновика — исключение
  (создание — под блокировкой поступления). Ожидание («Ожидается») — неоформленные строки поступления
  (`ЗаполнитьПоДокументуИсточнику` во временный объект, проведённые ордера уже вычтены) с `КлючСтрокиДокумента`,
  номенклатурой, характеристикой, **серией**, упаковкой; черновик хранит только принятое (строки > 0 с ключом
  строки ожидания и серией). Каждое изменение факта записывается в черновик (обычная запись, без проведения) под
  исключительной блокировкой поступления.
- **Сопоставление скана**: строка ожидания — по номенклатуре, характеристике и серии (контракт ордера по
  поступлению — серия строки ордера совпадает с серией строки источника, `ОрдераСклада` `Module.bsl:1826-1848`).
  Несколько строк поступления с одинаковыми номенклатурой, характеристикой и серией — последовательное
  распределение по порядку ключей источника: скан идёт в первую строку, где принято меньше ожидаемого; один скан —
  ровно +1 базовая единица общего факта. Скан штрихкода — к строкам без серии; скан IMEI — к строке с этой серией;
  IMEI, которого нет в ожидании, — отказ («IMEI нет в поступлении»): первичное назначение IMEI при приёмке этой
  волной не делается. Повторный IMEI не добавляется (как в документах 2.0.17.11); ручной ввод количества строки.
  Сверх ожидания по всем подходящим строкам — отказ до записи.
- **«Провести»** — проведение черновика. Повтор после потерянного ответа безопасен без отдельного протокола:
  проведённый ордер уменьшает неоформленный остаток, повторный вход черновика не находит (он проведён) и показывает
  остаток к приёмке; повторное проведение того же ордера движения не удваивает. Принято 3 из 10 — ордер на 3,
  остаток к приёмке 7, поступление остаётся в списке, следующая приёмка — новый черновик.
- Неордерный склад: мобильная приёмка не применяется (поступление и есть приход) — поле ответственного скрыто.
- Права: MobileClient прав на `ПриходныйОрдер` **не получает**; обработка приёмки — право «Использование» в роли
  СкладскиеОрдера. Серверные операции обработки — без привилегированного режима: список и запись ордера идут под
  правами пользователя; перед записью черновика и проведением проверяются `ПравоДоступа("Добавление",
  ПриходныйОрдер)` и актуальное назначение (`ОтветственныйЗаПриемку` поступления = текущий пользователь, под
  блокировкой поступления); иначе — отказ. Мобильный список поступлений и форма приёмки — формы этой обработки; формы
  `ПриходныйОрдер` не меняются.
