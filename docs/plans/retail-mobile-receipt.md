# Мобильная приёмка через приходный ордер — `retail-mobile-receipt` (сборка 2.0.17.16)

Дата: 2026-11-11. Вынесено из волны 5 (`docs/plans/retail-tools.md`, п. 9) после 8 кругов `ai-review-plan` плана
волны. Мастер-план — `docs/plans/retail-chain.md`, волна 5 («мобильная приёмка через `ПриходныйОрдер` +
`ПоступлениеТоваровУслуг.ОтветственныйЗаПриемку` (uuid клиента)»). Существенная правка (новые реквизиты, права,
проведение ордеров): `ai-review-plan` → реализация → `ai-review` → `ai-database` + `ai-security` →
`ai-final-check --db`.

## Поиск готового

- Ордерные склады и приёмка по поступлению — `ОрдераСклада` (`ПередЗаписьюОрдера`, `ПровестиОрдер`,
  `ПередУдалениемОрдера`), `Документы.ПриходныйОрдер.ЗаполнитьПоДокументуИсточнику` (неоформленный остаток
  поступления, проведённые ордера вычтены), контракт строки ордера — `ДокументИсточник`, `КлючСтрокиДокумента`,
  серия строки ордера = серия строки источника (`ОрдераСклада` `Module.bsl:1826-1848`); сверх поступления — отказ
  проведения.
- Мобильные формы и выбор формы по виду клиента — `РеализацияТоваровУслуг`, `ЗаданиеНаПересчет.ИмяФормыКлиента`;
  мобильное меню — `Обработка.MobileMenu.Форма.MenuPrincipal`.
- Поиск товара по штрихкоду и IMEI — `ОбщегоНазначенияВызовСервера.ПолучитьНоменклатуруПоШтрихкоду` (права на
  серии проверяются), правило повторного IMEI — 2.0.17.11.

## Решения

### 1. Назначение кладовщика

- Реквизит `ПоступлениеТоваровУслуг.ОтветственныйЗаПриемку` (uuid клиента `9497e83d-277d-4a39-9a62-bc390e1574b3`,
  `СправочникСсылка.Пользователи`) — назначает менеджер в форме поступления, поле видно только при ордерном складе
  поступления. Новый реквизит — реструктуризация таблицы документа (столбец с пустым значением, данных не меняет).
- Назначение не требует перепроведения: `ОтветственныйЗаПриемку` **исключается** из сравнения реквизитов
  `ОрдераСклада.ДокументИзменен` (`Module.bsl:1611-1624`, сейчас исключены `Комментарий` и `Ответственный`) — иначе
  обычная запись проведённого поступления на ордерном складе со сменой ответственного будет запрещена.
- **Переназначение при незавершённой приёмке запрещено**: в `ПередЗаписью` поступления при смене
  `ОтветственныйЗаПриемку` — под исключительной блокировкой поступления — поиск мобильных черновиков по нему
  (любого автора); есть — отказ «Есть незавершённая приёмка <ордер> (<кладовщик>): проведите или отмените её, затем
  переназначьте». Передача черновика другому кладовщику этой сборкой не делается.

### 2. Признак мобильной приёмки и черновик

- Два новых реквизита шапки `ПриходныйОрдер`: `МобильнаяПриемка` (Булево) и `ПоступлениеПриемки`
  (`ДокументСсылка.ПоступлениеТоваровУслуг`). Только их ставит обработка приёмки; на формах ордера не выводятся
  (только просмотр в форме, в группе «Дополнительно»), очищаются в `ПриКопировании`.
- **Инвариант** (проверка в `ПередЗаписью` ордера, вне загрузки): при `МобильнаяПриемка` — `ПоступлениеПриемки`
  заполнено, и у каждой строки `ДокументИсточник` = `ПоступлениеПриемки`; иначе отказ записи. Обычный ордер
  (`МобильнаяПриемка` = Ложь) за черновик приёмки **не принимается** никогда.
- **Черновик приёмки** — ордер с `МобильнаяПриемка`, `ПоступлениеПриемки` = поступление, `Ответственный` = текущий
  пользователь, не проведён, не помечен на удаление. Ищется только по этим полям шапки (а не по строкам), поэтому
  существует и пока строк нет.
- Создаётся при первом положительном изменении факта (до первого скана черновика нет — повторный вход показывает
  пустой факт). Обнуление факта по всем строкам — **пометка удаления** черновика (права СкладскиеОрдера: `Update`
  есть, `Delete` нет; помеченный черновик из поиска выпадает). Следующий скан создаёт новый черновик.
- **След первого скана — регистр сведений `ИспользованныеСсылкиПриемки`** (измерение `Ссылка` — уникальный
  идентификатор выделенной ссылки, ресурсы `Поступление`, `Пользователь`, `Дата`). **Единый протокол первого
  положительного изменения** — для скана, ручного ввода количества и ручного выбора строки: запрос несёт выделенную
  ссылку; в одной транзакции создаётся черновик и пишется запись; повтор любого первого изменения сначала проверяет
  регистр — запись есть, нового черновика нет
  (возвращается текущее состояние приёмки), независимо от того, существует ли ещё ордер (помечен, удалён после
  вывода из мобильной приёмки). Регистр закрыт для ролей (пишет и читает только обработка в привилегированном режиме
  после проверок п. 3), записи не удаляются; рост — одна запись на приёмку. Физическое удаление ордера этим не
  ограничивается.
- **Уникальность черновика — инвариант объекта ордера**, а не только обработки: в `ПередЗаписью` ордера с
  `МобильнаяПриемка` при любом переходе в состояние черновика (новый, запись непроведённого, отмена проведения,
  снятие пометки удаления) — под исключительной блокировкой поступления (`Документ.ПоступлениеТоваровУслуг`, ключ —
  ссылка) проверяется, что другого черновика того же ответственного по тому же поступлению нет (есть — отказ
  «По поступлению уже есть незавершённая приёмка: проведите или отмените её») **и что `Ответственный` ордера совпадает
  с текущим `ОтветственныйЗаПриемку` поступления**; не совпадает (поступление переназначено после проведения
  ордера) — отказ «Поступление назначено другому кладовщику: верните назначение или снимите признак мобильной
  приёмки у ордера». Выход — явная команда «Вывести из мобильной приёмки» в обычной форме ордера (пользователь с правом
  на ордер): у непроведённого — снимает признак обычной записью; у проведённого — **атомарно** снимает признак и
  отменяет проведение одной записью в режиме `ОтменаПроведения` (все стандартные проверки отмены проведения ордера —
  остатки, зависимые документы — действуют; простая запись проведённого ордера и так запрещена
  `ОрдераСклада.ПроверитьЗащиту`). После неё ордер — обычный. Обработка берёт ту же блокировку
  перед поиском и созданием.

### 3. Модель доступа

- MobileClient прав на `ПриходныйОрдер` **не получает**. Мобильный кладовщик — пользователь с ролями MobileClient и
  СкладскиеОрдера; новая обработка `МобильнаяПриемка` — права «Использование» и «Просмотр» в роли СкладскиеОрдера (у роли
  `setForNewObjects` = Ложь, права выдаются явно).
- Неоформленный остаток (`ТоварыКОформлению`, `НеоформленныеСтроки` — привилегированные) ролям не открывается.
  **Список и ожидание** — функции модуля менеджера обработки. Порядок закреплён (как в
  `ОбщегоНазначенияВызовСервера` `Module.bsl:237-239, 693-701`): **сначала, до привилегированного режима**,
  `ПравоДоступа("Добавление", Метаданные.Документы.ПриходныйОрдер)` реальными правами пользователя (нет права —
  пустой список / отказ); текущий пользователь — `ПараметрыСеанса.Пользователь` на сервере, параметром не
  передаётся; **затем** привилегированно читаются назначение и остатки, и в выборку попадают только поступления с
  `ОтветственныйЗаПриемку` = текущий пользователь на ордерном складе. Возвращают только номенклатуру, характеристику,
  серию, упаковку и количества (без сумм и цен).
- **Запись черновика и проведение** — под правами пользователя (без привилегированного режима; проведение ордера
  внутри само привилегированное, как сейчас). Перед каждой записью — те же проверки (право, назначение, ордерный
  склад) под блокировкой поступления.

### 4. Ожидание и сопоставление скана

- **Дата черновика**: создаётся с текущей датой сеанса; ордер должен быть строго позже поступления
  (`ОрдераСклада.ОшибкиДокументаОрдера`, `Module.bsl:1818-1821`) — при создании и при каждом согласовании проверяется
  момент; поступление перенесено на дату не раньше черновика — конфликт «Дата поступления позже приёмки» с явным
  действием «Перенести дату приёмки» (дата черновика = текущая дата сеанса, если она позже поступления; иначе отказ с
  указанием даты поступления).
- **IMEI вне объёма**: товары с учётом по серийным номерам (IMEI) на ордерные склады не допускаются
  (`СерийныйУчет.ПроверитьСкладыДокумента`, решение волны 4) — в мобильную приёмку они не попадают; поддержка IMEI на
  ордерных складах — отдельная задача (TECHDEBT). **Обычные серии** (партии, сроки) — D в диапазоне 0…R, как у товара
  без серии; скан штрихкода серии (`ПолучитьНоменклатуруПоШтрихкоду` возвращает серию) — к строке этой серии, скан
  штрихкода товара без серии при нескольких строках разных серий — выбор серии из списка ожидания.
  Номенклатура с серийным учётом, оказавшаяся в ожидании (исторические данные), — строка «Не принимается мобильно»
  без скана.
- **Три величины по строке источника** (ключ `КлючСтрокиДокумента`): **R** — доступно к оформлению (неоформленный
  остаток из регистра через `ЗаполнитьПоДокументуИсточнику` во временный незаписываемый объект; непроведённый
  черновик в нём не учтён), **D** — принято в черновик, **R − D** — осталось сканировать. Скан разрешён при
  D + 1 ≤ R, ручной ввод — D в диапазоне 0…R. Строка формы: номенклатура, характеристика, **серия**, упаковка, R, D,
  R − D.
- **Дерево сопоставления скана** (единое): (1) поиск — `ОбщегоНазначенияВызовСервера.НайденныйТоварПоШтрихкоду`
  (2.0.17.13, со статусом): «НеНайден» — отказ; «Неоднозначен» (штрихкод у нескольких товаров, характеристик, серий
  или упаковок) — **автоматического приращения нет**: сообщение «Штрихкод неоднозначен — выберите строку» и выбор
  строки ожидания вручную (+1 к выбранной строке тем же протоколом версии); «Найден» — номенклатура, характеристика
  записи штрихкода (может быть пустой) и серия; (2) кандидаты — строки ожидания этой номенклатуры, у которых R − D > 0,
  отобранные по характеристике штрихкода (если задана) и по серии (если штрихкод серии); скан — неделимая единица,
  поэтому кандидаты — только строки с **R − D ≥ 1** (остаток меньше единицы — дробный — принимается ручным вводом);
  (3) кандидаты группируются
  по **позиции** — номенклатура, характеристика, серия; одна позиция — скан идёт в неё, несколько позиций (разные
  характеристики или серии при товарном штрихкоде) — форма запрашивает выбор позиции из списка, без выбора скан не
  записывается; (4) внутри выбранной позиции — по порядку ключей источника в первую строку с R − D ≥ 1; один скан —
  ровно +1 базовая единица; (5) кандидатов нет — отказ («Нет в поступлении» или «Принято всё»). Обычная серия при
  товарном штрихкоде участвует как позиция (единственная серия — сразу в неё).
- **Защита от устаревшей формы**: форма держит ссылку и `ВерсияДанных` черновика. Абсолютные изменения (ручной ввод
  количества, обнуление, «Привести к поступлению», перенос даты) — в одной транзакции под блокировкой поступления
  сравнивают переданную версию с актуальной; не совпадает — отказ «Приёмка изменена в другом окне», форма
  перечитывает. **Скан тоже несёт версию**: +1 применяется к D только при совпадении переданной версии с актуальной
  (в той же транзакции под блокировкой), ответ возвращает новую версию. Повтор доставки того же скана после
  потерянного ответа приходит со старой версией — приращения нет, возвращается текущее состояние («Скан уже учтён или
  приёмка изменена — проверьте количество»); следующий физический скан форма отправляет с версией из полученного
  ответа. **Первый скан — с заранее выделенной ссылкой**: открывая приёмку без активного черновика, форма получает на
  сервере новую ссылку ордера (`Документы.ПриходныйОрдер.ПолучитьСсылку(Новый УникальныйИдентификатор)`); первый скан
  создаёт черновик с этой ссылкой (`УстановитьСсылкуНового`). Повтор первого скана находит ордер по ссылке в любом
  состоянии (черновик, проведён, помечен на удаление) — новый не создаётся, возвращается текущее состояние. Новая
  приёмка получает новую ссылку так: **каждый ответ сервера, в котором активного черновика нет** (после обнуления,
  проведения, при открытии), несёт свежую выделенную ссылку; форма заменяет свою ссылку только по полученному ответу.
  Поэтому «скан → обнуление → новый скан» в той же форме создаёт новый черновик с новой ссылкой, а повтор старого
  запроса (со старой ссылкой и версией) нового черновика не создаёт. Потерян ответ на обнуление — повтор обнуления со
  старой версией отказан с текущим состоянием (черновик помечен) и свежей ссылкой.
- Черновик хранит только принятое: строки с количеством > 0, ключом строки источника, серией.
- **Согласование с изменившимся поступлением** (менеджер изменил или перепровёл поступление между входами): при
  каждом открытии и перед каждой записью строки черновика сопоставляются с актуальными строками источника по ключу
  **и по позиции** (номенклатура, характеристика, серия — как `ОрдераСклада.СтрокаОрдераНеСовпадает`). Ключа больше
  нет, позиция по ключу другая (заменён товар, характеристика или серия) или D > R — **конфликт**: показывается отдельным списком («В поступлении изменилось: принято N,
  доступно M» или «товар в строке поступления заменён»), принятое молча не меняется; действие «Привести к
  поступлению» по явному нажатию уменьшает D до R, а исчезнувшую строку и строку с заменённой позицией обнуляет (новую
  позицию принимают заново); пока конфликты не сняты, «Провести» недоступно (проведение и так отказало бы). Шапка
  поступления (организация, склад, поставщик, ордерность склада — те же поля, что сверяет
  `ОрдераСклада.ОшибкиДокументаОрдера`, и **основание** — заказ поставщику, который заполнение переносит в ордер и
  исполняет при проведении) изменилась — приёмка недоступна с сообщением, черновик остаётся
  для решения в обычной форме ордера.

### 5. Проведение и повтор

- «Провести» — команда получает **ссылку конкретного черновика**, которую форма показала. Первым шагом (под
  блокировкой поступления) перечитывается состояние этого ордера: уже проведён (повтор после потерянного ответа) —
  возвращается результат завершённой операции без согласования с R и без повторной записи; не проведён — команда
  несёт и **ожидаемую `ВерсияДанных`**: не совпадает (ордер с тех пор менялся — в т. ч. проведён и снова отменён
  пользователем) — отказ «Приёмка изменена, проверьте и проведите снова», форма перечитывает; совпадает — согласование
  (конфликты блокируют) и проведение обычным механизмом ордера (сверх поступления — отказ). Так повтор старой команды
  не восстанавливает отменённое пользователем проведение. Повтор после
  потерянного ответа безопасен: проведённый ордер черновиком уже не считается (поиск только непроведённых), его
  количество вычтено из ожидания; повторное проведение того же ордера движения не удваивает. Принято 3 из 10 —
  ордер на 3, к приёмке 7, поступление остаётся в списке; следующая приёмка — новый черновик.
- Отмена проведения ордера (кладовщик может, право СкладскиеОрдера) возвращает количество в доступное; такой ордер
  снова становится черновиком своего автора — если у автора нет другого черновика по поступлению (инвариант п. 2),
  иначе отмена проведения отказывается.

### 6. Интерфейс

- Обработка `МобильнаяПриемка`: форма списка «Приёмка» (мобильная): назначенные текущему пользователю поступления
  с положительным остатком к приёмке **или с его собственным черновиком** (даже при нулевом остатке — например,
  поступление оформлено другим ордером), колонки: номер, дата, поставщик, склад, осталось принять, признак «Есть
  конфликты» и форма приёмки (ожидание с принятым, поле скана, ввод
  количества, «Провести», «Отмена»). Кнопка «Приёмка» в мобильном меню.
- Форма поступления: поле «Ответственный за приёмку» в группе склада (видимость — ордерный склад).

## Тесты (`ТестыДокументов`)

- `МобильнаяПриемкаСписок`: поступление на ордерный склад с ответственным — в списке у ответственного; у другого
  пользователя, без права на ордер, на неордерном складе и после полной приёмки — нет.
- `МобильнаяПриемкаЧастично`: ожидалось 10, принято 3 — черновик с 3 и ключом строки; «потеря формы» (новый вызов
  функций) — тот же черновик; проведение — к приёмке 7; повторное проведение не меняет остаток; новая приёмка — новый
  черновик; обнуление факта — черновик помечен на удаление, повторный вход — пусто.
- `МобильнаяПриемкаСерии`: две обычные серии одного товара — скан штрихкода серии к своей строке, несколько единиц
  одной серии принимаются (0…R); серия вне ожидания — отказ; две одинаковые строки поступления по 5 — сканы заполняют
  первую, затем вторую, 11-й — отказ.
- `МобильнаяПриемкаИнвариант`: обычный непроведённый ордер на полное количество черновиком не считается; ордер с
  признаком и строкой другого поступления — отказ записи; копия ордера без признака; отмена проведения ордера при
  существующем черновике того же автора — отказ; снятие пометки удаления при существующем черновике — отказ.
- `МобильнаяПриемкаСканы`: ожидалось 10 — сканы 1…10 с повторным чтением состояния после каждой записи проходят,
  11-й — отказ.
- `МобильнаяПриемкаИзменениеПоступления`: принято 5, менеджер уменьшил строку поступления до 3 — конфликт «принято 5,
  доступно 3», D не меняется до «Привести к поступлению», после — 3; удалённая строка — конфликт, после приведения 0.
- `МобильнаяПриемкаЗаменаТовара`: в строке поступления заменены товар, характеристика, серия при том же ключе —
  конфликт «заменён», факт не меняется до приведения, после приведения — 0 по строке.
- `МобильнаяПриемкаСписокСЧерновиком`: черновик есть, поступление полностью оформлено другим ордером — поступление в
  списке с конфликтом.
- `МобильнаяПриемкаБезПрава`: прямой вызов функций списка и ожидания под пользователем без права «Добавление»
  ордера, которому поступление назначено, — пусто / отказ.
- `НазначениеКладовщика`: смена `ОтветственныйЗаПриемку` обычной записью проведённого поступления на ордерном складе
  проходит, движения не меняются; при существующем черновике с ненулевым фактом — отказ с указанием ордера.
- `МобильнаяПриемкаДата`: поступление перенесено на дату позже черновика — конфликт даты, «Перенести дату приёмки»
  снимает его.
- `МобильнаяПриемкаХарактеристики`: общий штрихкод товара с двумя характеристиками в поступлении — скан требует выбора
  позиции, после выбора — в выбранную; проведённый ордер — движения выбранной характеристики. Товарный штрихкод при
  одной обычной серии — сразу в неё, при двух — выбор.
- `МобильнаяПриемкаВерсия`: две «формы» на одном черновике — ручной ввод и скан из устаревшей версии не меняют D и
  возвращают актуальное состояние; следующий скан с актуальной версией — +1.
- `МобильнаяПриемкаПервыйСкан`: первый скан записан, ответ «потерян»; затем черновик проведён (или обнулён и помечен)
  из другого окна — повтор первого скана с той же выделенной ссылкой новый черновик не создаёт.
- `МобильнаяПриемкаОтменаИПовтор`: проведение → «потеря ответа» → пользователь отменил проведение → повтор старой
  команды с прежней версией — отказ, новых движений нет.
- `МобильнаяПриемкаДробныйОстаток`: первая строка с остатком 0,5, вторая с целым — скан идёт во вторую; 0,5 — ручным
  вводом.
- `МобильнаяПриемкаОрганизация`: организация поступления сменилась при существующем черновике — приёмка недоступна с
  объяснением.
- `МобильнаяПриемкаПовторСкана`: скан записан, ответ «потерян» — повтор со старой версией не увеличивает принятое,
  следующий скан с новой версией — +1.
- `МобильнаяПриемкаПереназначение`: ордер кладовщика А проведён → поступление назначено Б → отмена проведения ордера
  А — отказ; при существующем черновике Б — тот же отказ; «Вывести из мобильной приёмки» для проведённого ордера А —
  признак снят и проведение отменено одной записью, черновик Б не затронут.
- `МобильнаяПриемкаНеоднозначныйШтрихкод`: исторический дубль штрихкода у двух товаров (и у двух серий) — скан без
  приращения, выбор строки вручную даёт +1.
- `МобильнаяПриемкаОбнулениеИСкан`: скан → обнуление → новый скан в той же форме — новый черновик с новой ссылкой;
  повтор обнуления после «потерянного» ответа — без изменений, со свежей ссылкой.
- `МобильнаяПриемкаУдаление`: первый скан → обнуление → «Вывести из мобильной приёмки» → физическое удаление ордера
  → повтор первого запроса со старой ссылкой — нового черновика нет (след в регистре).
- `МобильнаяПриемкаОснование`: заказ поставщику в поступлении сменился А → Б при черновике — конфликт шапки,
  приёмка недоступна до решения в обычной форме ордера; движения заказов не тронуты.
- `МобильнаяПриемкаПервыйРучнойВвод`: первый ручной ввод 0,5 → «потеря ответа» → обнуление → вывод и физическое
  удаление → повтор исходного запроса — нового черновика нет.
- `МобильнаяПриемкаПовторПроведения`: черновик проведён (частично и полностью), повторный вызов «Провести» с той же
  ссылкой — результат завершённой операции, ордер не перезаписан, остаток к приёмке прежний.
- `МобильнаяПриемкаПрава`: у MobileClient нет записи и проведения ордера, у СкладскиеОрдера есть; запись приёмки
  чужого назначения — отказ. Живая проверка под пользователем только с MobileClient (отказ) и с MobileClient +
  СкладскиеОрдера (проходит) — на копии базы; мобильный клиент на телефоне — регресс человека.

## Порядок и проверки

tiny1C `checklist` по `.mdo`/`Form.form` → реквизиты и обработка → модули → тесты → lint, refcheck, listcheck,
colfont, menucheck → `ib-sync` → смок (мобильные формы обработки в смоке) → ТестыДокументов → «Что нового» →

## Риски

- Реструктуризация двух таблиц документов (новые столбцы, пустые значения) — время обновления большой базы.
- Блокировка поступления при каждом скане — параллельная приёмка одного поступления двумя кладовщиками идёт по
  очереди (короткие транзакции).
- Изоляция по ответственному обеспечена функциями обработки, а не правами роли: прямой доступ кладовщика к ордерам
  (роль СкладскиеОрдера) остаётся прежним.
