# Поступления в АРМ закупок, С2: «Создать поступление» в «Потребности» и учёт прямых поступлений

Клиент — Drissotex. Продолжение `docs/plans/arm-purchasing-receipts.md` (С1 — 2.0.16.98). Решения владельца
(2026-10-26): из «Потребности» — **сразу поступление**, без заказа поставщику; поступление **проводится сразу**;
перед этим — **починить учёт потребностей** (TECHDEBT «Учёт прямых поступлений под заказ клиента», три дефекта).

## Термины

- **Прямая закупка** — поступление, приходный ордер или возврат поставщику под заказ клиента на производство, у
  которого **нет заказа поставщику** (`ЗаказПоставщикуДокумента` пуст: основание — заказ клиента; у возврата —
  основание его поступления). Признак зависит только от основания самого документа и меняется только его же
  перепроведением (ревью плана, раунд 1, P1-1: признак по движениям заказа поставщику менялся бы без перепроведения
  поступления).
- **Закупка по заказу** — с заказом поставщику-основанием, записал он движения по заказу клиента или нет (заказ
  поставщику, проведённый до формирования потребности, — тоже по заказу; раскладка по-прежнему по остаткам).

## Дефекты (из TECHDEBT) и причина

1. Прямое поступление раскладывается по изделиям пределом «Потребность − Пришло» без «ИзОстатка»: приход ложится
   на изделие, уже обеспеченное со склада.
2. Обеспечение «Макс(Заказано, Пришло)» (закладка «Потребность», `РазложитьПоПродукции`, стадии заказа
   `ПроизводственныеЗаказы.ДобавитьПоказателиПотребностей`) не видит прямое поступление при открытом заказе
   поставщику: 10 нужно, 6 заказано, 4 принято напрямую — дефицит 4. `ДефицитЗаказа` («Потребность − Заказано −
   ИзОстатка», заполнение заказа поставщику по потребности) прямой приход не видит вовсе.
3. Пополнение до минимума: дефицит складывается по складам, а поступление пошло бы на склад по умолчанию.

Корень 1–2: регистр не отличает прямой приход от прихода по заказу.

## Р1. Модель: новый ресурс «ПришлоБезЗаказа»

Регистр `ПотребностиПроизводства` получает ресурс **`ПришлоБезЗаказа`** (тип `ОпределяемыйТип.Количество`, как
у остальных; ru «Пришло без заказа», fr «Reçu sans commande», en «Received without order», es «Recibido sin
pedido») — часть «Пришло», принятая прямой закупкой. Прямая закупка пишет `Пришло` и `ПришлоБезЗаказа` одной
величиной по одной раскладке (возврат — оба со знаком минус); закупка по заказу и заказ поставщику пишут как сейчас,
`ПришлоБезЗаказа = 0`. «Заказано» остаётся только заказанным у поставщиков (ревью плана, раунд 1: синтетическое
«Заказано» ломалось при перепроведении заказа поставщику и при возврате с чужого изделия).

**Обеспечено** строки (продукция, материал, характеристика) = `Макс(Заказано, Пришло − ПришлоБезЗаказа) +
ПришлоБезЗаказа`; **дефицит** = `Потребность − ИзОстатка − Обеспечено`, положительная часть. Без прямых закупок —
ровно прежняя формула.

Реструктуризация: добавление ресурса регистра накопления (данные не теряются, новый ресурс у старых записей — 0;
итоги пересчитываются при обновлении конфигурации). Права ролей — на регистр целиком, не меняются.

### Р1.1. Одна функция признака

`ПотребностиПроизводства` (модуль менеджера): служебная `ПрямаяЗакупка(ДокОбъект)` — не заказ поставщику и
`ЗаказПоставщикуДокумента(ДокОбъект)` пуст.

### Р1.2. Раскладка прямого поступления (дефект 1)

`ПределыДокумента`, прямое поступление/ордер: новая служебная `ПределыПрямойЗакупки(Заказ, Ссылка)` — по остаткам
заказа без движений документа предел продукции = дефицит строки (формула выше), не меньше нуля, только продукция с
потребностью, в порядке строк продукции заказа. Излишек — прежнее правило `РаспределитьПоПорядку`. Поступление по
заказу поставщику — без изменений (`ПределыПоОснованию` или `ПределыПоОстаткам(…, "Пришло")`).
Пример: изделия A и B по 5 материала, A получило 5 «ИзОстатка», прямое поступление 5 → всё на B.

### Р1.3. Возврат — по происхождению прихода (ревью плана, раунд 1, P1-2)

Возврат списывается **сначала со своего кармана, затем с другого** («перелив», ревью плана, раунд 4, P1):
пределы возврата (`ПределыВозвратаПоЗаказу(Заказ, Ссылка, Прямой)`) — две части в одной таблице с признаком кармана:
сначала свой карман (у прямого возврата — остаток `ПришлоБезЗаказа`, у возврата по заказу — остаток `Пришло −
ПришлоБезЗаказа`) по ключам в обратном порядке продукции, затем другой карман так же; без движений самого возврата, не
меньше нуля. Раскладка — новая служебная `РаспределитьВозврат`: по порядку пределов без излишка, остаток сверх всех
пределов — на последнюю строку материала (как сейчас: отказ проверки). Движение части из прямого кармана пишет
`Пришло` и `ПришлоБезЗаказа` со знаком минус, из кармана по заказам — только `Пришло`.
Следствия:
- сценарий P1-2 раунда 1 (прямой возврат не трогает изделие, обеспеченное по заказу) сохраняется: пока прямого
  прихода хватает, перелива нет;
- ни один карман не уходит в минус от возврата, пока общее «Пришло» ключа не меньше нуля; заказ со старыми движениями
  (`ПришлоБезЗаказа = 0`, например, если обработчик его не пересчитал) возвращается как раньше — переливом из кармана
  по заказам, без отказа (ревью плана, раунд 4, P1).
`ПроверитьПришло` проверяет оба кармана: по ключам, где новые движения уменьшают `ПришлоБезЗаказа` или
`Пришло − ПришлоБезЗаказа` против прежних, остаток без прежних плюс новые не меньше нуля (ловит отмену проведения
и перепроведение поступлений, по приходу которых уже вернули); тексты отказа — прежний шаблон.

### Р1.4. Формулы потребителей

Одна функция-образец в модуле менеджера регистра — экспортная `ТекстОбеспечено(Псевдоним)` (выражение запроса
«Обеспечено» по полям `Заказано, Пришло, ПришлоБезЗаказа` с префиксом псевдонима таблицы) и `Обеспечено(Строка)` для
кода; потребители переходят на них:
- `АРМЗакупки`: `ТекстЗапросаПотребностиПроизводства` (новое поле), `ТекстЗапросаИсточников` (дефицит),
  `ТекстЗапросаДефицитаПродукции`;
- `ПроизводственныеЗаказы`: запрос показателей разделяет чистое «Пришло», `ПришлоБезЗаказа` и «ИзОстатка» (сейчас
  «ИзОстатка» сложено в «Пришло»); `ДобавитьПоказателиПотребностей`: обеспечено = `ИзОстатка + Обеспечено` по чистым
  закупочным ресурсам, показатель «пришло» — по-прежнему `Пришло + ИзОстатка` (ревью плана, раунд 6, P1: иначе
  складское обеспечение перекрывалось «Заказано» внутри `Макс`);
- `ПотребностиПроизводства.ДефицитЗаказа`: `Потребность − ИзОстатка − Обеспечено` (было «− Заказано»: прямой и
  сверхзаказанный приход теперь уменьшают дефицит заказа поставщику, как на закладке «Потребность»);
- `ОстатокКПоступлению`: переключатель «по заказанному» (`Итог("Заказано") <> 0`) прежний и снова точный; ветка по
  заказанному — `Заказано − (Пришло − ПришлоБезЗаказа)`, иначе — прежняя;
- `АРМПроизводство`: запрос `МатериалыЗаказа` и дерево — колонка `ПришлоБезЗаказа`, `РазложитьОстаткиПоЛистьям` её
  раскладывает, `РассчитатьДефицитСтрокДерева` — дефицит по формуле, «к поступлению» как `ОстатокКПоступлению`.
Отчёт «Потребности производства» и карточка товара показывают «Пришло» целиком — не меняются.

### Р1.5. Старые данные — обработчик обновления

`ОбновлениеПрограммыОбработчики.ЗаполнитьПришлоБезЗаказа` (версия сборки, монопольно). **Раскладка старых движений по
изделиям не пересчитывается** — меняется только новый ресурс `ПришлоБезЗаказа` существующих записей; ключи и «Пришло»
остаются как есть (ревью плана, раунд 6, P0: повторное формирование по текущей потребности теряло движения заказов с
отменённой потребностью и материалов, которых в потребности уже нет; раунд 2, P0: простое «= Пришло» у возвратов
давало минус кармана):
1. затронутые заказы — заказы клиентов, у которых есть записи `Пришло <> 0` прямой закупки (регистратор —
   поступление или приходный ордер с основанием не заказ поставщику, или возврат, чьё поступление-основание имеет
   основание не заказ поставщику);
2. по каждому заказу в своей транзакции под исключительной блокировкой `ПотребностиПроизводства` по заказу, два прохода
   по записям закупок заказа (поступления, приходные ордера, возвраты) **по ключу записи** (продукция, материал,
   характеристика):
   - проход 1, приходы: прямое поступление/ордер — `ПришлоБезЗаказа = Пришло` записи; поступление/ордер по заказу —
     `ПришлоБезЗаказа = 0`; по ключу копятся **полные** ёмкости двух карманов — все приходы, в том числе более поздние
     по моменту времени (ревью плана, раунд 7, P1: старый возврат раскладывался по итоговым остаткам заказа без
     временной границы, поэтому обход по времени давал ложный минус кармана);
   - проход 2, возвраты (записи с `Пришло < 0`) по моменту времени: количество записи списывается на том же ключе
     сначала с остатка своего кармана (прямой возврат — с прямого, по заказу — с кармана по заказам), остаток — с
     другого (перелив Р1.3); `ПришлоБезЗаказа` записи = минус часть, списанная с прямого кармана;
   набор пишется `ОбменДанными.Загрузка = Истина`, только если `ПришлоБезЗаказа` записей изменился; без перепроведения
   и без прочих регистров;
3. итоги «Пришло» не меняются; итоговый инвариант — при общем «Пришло» ключа не меньше нуля оба кармана не меньше нуля
   (по построению: возвраты списываются с полных ёмкостей) — проверяется перед фиксацией; ключ с отрицательным
   карманом (только при отрицательном общем «Пришло» — уже испорченные данные) — предупреждение в журнал, обработчик
   не прерывается;
4. стадия заказа пересчитывается `ПроизводственныеЗаказы.ЗаписатьСтадиюЗаказа` (раунд 1, P2) — у затронутых заказов
   и у всех заказов со взятым со склада («ИзОстатка» больше не перекрывается «Заказано», ревью данных, P2).
Идемпотентен: повтор вычисляет те же значения и ничего не пишет; каждый заказ — своя транзакция. Распределение
старых прямых поступлений по изделиям (дефект 1) остаётся историческим — исправляется перепроведением документа.

## Р2. Пополнение склада — не в этой сборке

Прямое поступление пополнения до минимума (дефект 3 — склад дефицита) из сборки **исключено** (ревью плана, раунды
3, 5, 7: защита дефицита пополнения требует блокировки остатков товара на всех складах, а она встречно конфликтует с
порядком блокировок поступления и возврата поставщику; ожидание дефицита по складским долям требует отдельной модели
намеренного излишка). Строка пополнения и часть сводной строки, которая пришлась бы на пополнение, «Создать
поступление» не принимает: сообщение «пополнение склада принимается через «Заказать» или новым поступлением на
закладке «Поступления»». Дефект 3 и решение по пополнению — в TECHDEBT/ROADMAP §14 (вернуться с решением владельца:
склад пополнения и допустимость гонки «излишек при параллельном поступлении»). «Заказать» для пополнения — без
изменений.

## Р3. Кнопка «Создать поступление» на закладке «Потребность»

### Сервер — `Обработки.АРМЗакупки.ПринятьПотребность(Строки)` (экспорт)

Вход — как у `ЗаказатьПотребность` (Источник, Номенклатура, Характеристика, Поставщик, Количество = «к заказу»,
ДефицитНаЭкране), та же проверка структуры. Раскладка строки по свежим источникам — своя `РаспределитьСтрокуПоступления`
по образцу `РаспределитьСтрокуПотребности`: строка пополнения (`Источник` — пустой заказ) — отказ Р2; сводная строка
(`Источник` не задан) — свежий дефицит всех источников меньше показанного — отказ «потребность изменилась», затем
количество раскладывается **только по заказам клиентов** по дате отгрузки, не больше дефицита каждого; строка заказа
клиента — свежий дефицит меньше показанного — отказ, количество не больше дефицита. Часть сверх дефицитов заказов
клиентов не принимается — сообщение «сверх дефицита заказов клиентов не принято: N» (намеренный излишек под заказ
клиента производство не допускает и у «Заказать»: пакет урезает до дефицита). Товар с черновиком заказа поставщику —
**не отказ** (черновик заказа ничего не обеспечивает); черновик **поступления/приходного ордера** с основанием — этот
заказ клиента и этими товарами — отказ «есть черновик … : проведите или удалите его» (повтор после отказа проведения
принял бы второй раз). Решающая проверка — под блокировкой в пакете.

Доли группируются по (поставщик, заказ клиента), склад — по умолчанию нового документа (как у заказов поставщику
«Заказать» и их поступлений). На долю — пакет `Обработки.АРМПроизводство.ЗаписатьСтрокиПрямогоПоступления(СтрокиДанных,
Проверка)`. Итог по доле: Поставщик, Источник, Успех, Текст, Документ (как у `ЗаказатьПотребность`).

### Пакет — `Обработки.АРМПроизводство.ЗаписатьСтрокиПрямогоПоступления(СтрокиДанных, Проверка)` (экспорт)

По образцу `ЗаписатьСтрокиЗаказа` + ветки ордера `ЗаписатьСтрокиПоступления`:
- строки: `Вид = ВидПоступление()`, новые, одного поставщика и заказа клиента (заполнен), `КонтекстЗаказПоставщику`,
  `ЗаказПоставщику` пуст, новый признак данных строки **`ПрямоеПоступление = Истина`** (в `НовыеДанныеСтрокиДокумента`,
  по умолчанию Ложь; `ТекстЗапретаОснованияСтрокиПоступления` пропускает строку закупочного контекста без заказа
  поставщику только с ним; ручной ввод строк формы признак не ставит — поведение формы прежнее);
- на ордерном складе — приходный ордер с основанием — заказ клиента (`ОрдерВместоДокумента`);
- номер накладной пуст, дата — сегодня;
- транзакция: **только** блокировка проведения документа (у ордера — `ОрдераСклада.ЗаполнитьБлокировкуОрдера`): оба
  набора включают `ПотребностиПроизводства` по заказу клиента исключительно — два вызова по одному заказу идут по
  очереди; новых элементов и нового порядка блокировок нет. Затем `Обработки.АРМЗакупки.
  ТекстЗапретаПрямогоПоступления(СтрокиДанных, Проверка)`:
  - черновик поступления/ордера под заказ клиента с этими товарами — отказ (ревью плана, раунд 2, P2);
  - количество строки урезается до свежего дефицита заказа по товару (`ДефицитИсточника`), дефицит ≤ 0 — отказ (как у
    заказа поставщику «Заказать»);
  - документ пересобирается по урезанным строкам (подмножество прежних товаров — набор блокировки его покрывает);
- запись с проведением; отказ проверки — пустая транзакция фиксируется;
- отказ проведения — откат, затем черновик **в новой транзакции под тем же набором блокировки** с той же повторной
  проверкой (черновик есть или дефицита нет — черновик не пишется, итог с текстом отказа; меньше — строки урезаются);
  только потом черновик пишется (решение владельца 9).

### Форма `Обработка.АРМЗакупки.Форма`

- Кнопка «Создать поступление» в панели таблицы `Потребность` рядом с «Заказать» (команда
  `СоздатьПоступлениеПоПотребности`, ru/fr/en/es; видимость — как у «Заказать»: право добавления поступлений).
- Берутся отмеченные строки с «к заказу» > 0 — тот же сбор, что у «Заказать» (не отмечено ничего — сообщение);
  без поставщика — отказ строки, как у «Заказать».
- После создания: сообщения по долям, переход на закладку «Поступления», перечитывание, курсор на первый созданный
  документ (как С1), «Потребность» перечитывается при следующем открытии.

## Тесты (`ТестыДокументов`, `docs/TESTS.xlsx`, `docs/TESTING.md`)

Новый сценарий `ПрямыеПоступленияПотребности` (опция «Производство»):
1. Дефект 1: два изделия по 5 материала, изделию A 5 «ИзОстатка» → прямое поступление 5 ложится на B, дефицит 0.
2. Дефект 2: нужно 10, заказ поставщику 6, прямое поступление 4 → дефицит источника 0, `ДефицитЗаказа` пуст,
   стадия «обеспечено»; возврат прямого поступления 4 → дефицит 4, «Заказано» 6. Вариант раунда 6: нужно 10, со склада
   2, заказано 6, прямо 2 → дефицит 0 и стадия «обеспечено».
3. Возврат по происхождению (P1-2): A и B по 5; по B заказано 2 и принято по заказу 5; прямое 5 на A; возврат
   прямых 5 снимает с A (`ПришлоБезЗаказа` A → 0), B не трогается; возврат прямых сверх — отказ.
4. Стабильный признак (P1-1): заказ поставщику на 10 проведён до потребности, поступление по нему 10 →
   `ПришлоБезЗаказа` 0; перепроведение заказа поставщику → обеспечено 10, не 20; возврат 10 → дефицит 10.
5. `ОстатокКПоступлению`: без заказов поставщику, нужно 10, прямое 4 → 6; с заказом 6 и прямым 4 → 6.
6. `ПринятьПотребность` по строке заказа клиента → проведённое поступление с основанием — заказ клиента, без номера
   накладной; повтор — отказ.
7. Пополнение (Р2): строка пополнения — отказ с подсказкой, документов нет; сводная строка с заказом клиента и
   пополнением — поступление только на дефицит заказа клиента, сообщение о непринятом сверх.
8. Черновик заказа поставщику по товару «Создать поступление» не мешает.
9. Гонка заказа клиента: строки на дефицит 10 → прямое поступление 4 другим путём → пакет → поступление на 6.
10. Обработчик Р1.5: прямое поступление 5 на A, поступление по заказу 5 на B, прямой возврат 5 записан по-старому с B
    (движения теста без `ПришлоБезЗаказа`) → обработчик: ключи и «Пришло» не меняются, у возврата `ПришлоБезЗаказа` 0
    (перелив с кармана по заказам B), оба кармана по A и B не меньше нуля, стадия пересчитана; повтор ничего не
    пишет. Вариант раунда 7: два прямых поступления (5 на A, 5 на B) и возврат первого, записанный с B, с моментом
    раньше второго поступления — у B `ПришлоБезЗаказа` итог 0, карманы не меньше нуля. Заказ с отменённым проведением
    и сохранившимися закупками — обработан без ошибки.
11. Перелив (раунд 4): заказ со старыми движениями (`ПришлоБезЗаказа` обнулён тестом) — прямой возврат проходит,
    списывается с кармана по заказам; прямой возврат сверх прямого прихода при новых движениях — перелив, без отказа.
12. Черновики: поступление-черновик под источник есть → пакет отказывает «есть черновик», нового документа нет.

`ТестыДокументов` выполняет сценарий в одной внешней транзакции (ревью плана, раунд 4, P2): отказ проведения с
откатом и запись черновика в новой транзакции, а также откат заказа в обработчике в нём не проверить. Они проверяются
**отдельным прогоном на одноразовой копии базы** без внешней транзакции — внешняя обработка (как прогоны
`epf-runner`) через `1cv8c /Execute`: отказ проведения пакета (поставщик с запретом проведения, например договор
другой организации) → черновик; второй вызов по тому же источнику — отказ «есть черновик»; результат читается из
нового сеанса. Сценарий заносится в реестр `docs/TESTS.xlsx` строкой «машина, отдельный прогон».
Прежние сценарии (`ПотребностьЗакупок`, E7/E9, ордерные склады, `ПоступленияЗакупок`) — без изменений и зелёные.

## Ревью плана

- Раунд 1 (reject, 3 × P1 + P2): синтетическое «Заказано» и признак по движениям заказа поставщику — заменены
  ресурсом `ПришлоБезЗаказа` и признаком по основанию; возврат по происхождению прихода; перепроверка пополнения по
  обоим дефицитам; обработчик пересчитывает стадии.
- Раунд 2 (reject, P0 + P2): обработчик заполнял ресурс по старой раскладке возвратов — теперь формирует движения
  закупок затронутых заказов заново по порядку; черновики перепроверяются под блокировкой, черновик после отказа
  проведения пишется с перепроверкой.
- Раунд 3 (reject, P0 + P1): порядок пересчёта с зависимостями «возврат после своего прихода», инварианты и откат
  заказа при нарушении; блокировка пополнения по товару на всех складах.
- Раунд 8 (**approve_with_changes**, 2 × P2): строки одного товара в пакете расходуют общий дефицит; в дереве
  «Материалы» части «Пришло» раскладываются по листьям по отдельности, «Пришло» листа — их сумма.
- Раунд 7 (reject, 3 × P1): пополнение исключено из сборки (Р2) — блокировки остатков по всем складам и ожидания
  складских долей уходят вместе с ним, пакет берёт только блокировку проведения; обработчик размечает возвраты по
  полным ёмкостям приходов ключа.
- Раунд 6 (reject, P0 + P1): обработчик не формирует движения заново — только размечает `ПришлоБезЗаказа`
  существующих записей (возвраты — перелив на том же ключе), без отказов и откатов; стадии считают «ИзОстатка»
  отдельно от закупочных ресурсов.
- Раунд 5 (reject, 2 × P1): блокировки пополнения встроены в общий порядок захвата; непересчитанный заказ —
  исключение обработчика после остальных, версия не повышается.
- Раунд 4 (reject, P1 + P2): возврат с переливом между карманами — заказ со старыми движениями работает без отказов,
  откат в обработчике остаётся только на ошибку программы; проверки отката и черновика — отдельным прогоном вне
  транзакции сценария.

## Ревью кода и данных

- ai-review (reject, P1 + 2 × P2): неактивные записи в обработчике — пропускаются; дефицит дерева «Материалы» — по
  ключу регистра до раскладки; сообщения формы не в панели сведений — существующее поведение формы, TECHDEBT.
- ai-review --verify (approve_with_changes): отрицательная невязка раскладки по листьям — раскладка разностями
  накопленных долей.
- ai-database (approve_with_changes, P2): стадии пересчитываются и у заказов с «ИзОстатка».

## Риски

- Реструктуризация регистра при обновлении: время пропорционально числу записей регистра (у клиента — тысячи).
- Поступление на основании заказа клиента при открытых заказах поставщику (ветка «по заказанному»
  `ОстатокКПоступлению`) — прямая закупка: обеспечение растёт сверх заказанного поставщикам, заказ поставщику
  остаётся открытым — как сейчас (поведение ввода на основании не меняется).
- `ДефицитЗаказа` теперь вычитает и приход по заказу сверх заказанного (`Макс`) — как закладка «Потребность».
- Обработчик пишет наборы с `ОбменДанными.Загрузка` и меняет только `ПришлоБезЗаказа` существующих записей; прочие
  ресурсы, ключи и регистры документов не трогаются. Нарушения карманов на старых данных — в журнал, не отказ
  обновления.
