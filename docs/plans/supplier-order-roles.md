# Сборка 2.0.18.5: роли заказа поставщику, рабочее место производства без него, запуск веб-клиента

Приёмка: `.ai/reports/supplier-order-roles-acceptance.md`. Уровень - существенная правка (права ролей,
обработчик обновления): план → `ai-review-plan` → реализация → `ai-review` → гейт базы.

## Постановка владельца (2026-11-22)

1. Пользователю без доступа к заказу поставщику («чистый производственник») рабочее место производства
   не должно мешать добавлять строки; закладку «Заказы поставщику» таким пользователям не показывать.
2. Отдельные роли «ЧтениеЗаказаПоставщику» и «ИзменениеЗаказаПоставщику».
3. Дать рабочим ролям право запуска нужных видов клиента; тестом закрепить.
4. Решения по вопросам исполнителя: у роли оператора производства чтение заказа поставщику убрать;
   действующим операторам при обновлении выдать роль чтения автоматически (ответ «делай» на рекомендацию).

Исходная жалоба владельца («у пользователя с ролью оператора производства кнопка «Добавить» на закладке
«Товары» недоступна, сборка 2.0.18.4») на базе гейта под пользователем с единственной ролью
ОператорПроизводства НЕ воспроизведена: строка добавляется (`scripts/uitest.sh`, сценарий «единица»,
тонкий клиент). План её причину не объясняет; это прямо говорится владельцу, у него запрошена база.

## Поиск готового

  обновление не останавливается).
- В модуле менеджера рабочего места уже есть образец запроса, который присоединяет заказ поставщику только
  при праве чтения: `ПодзапросПоступлений` (`ManagerModule.bsl`:3918) и `СтрокиЗаказовПоставщикуДляВыбора`

## Этапы

### Э1. Роли

- `Role.ЧтениеЗаказаПоставщику` (новые uuid, синонимы ru/fr/en/es): `Document.ЗаказПоставщику` - Read, View,
  InputByString; команды печати документа (правило 2 `rolecheck.py`) и `CommonForm.ПечатьДокументов`
  (правило 3); команды навигации документа (правило 5); `AccumulationRegister.ЗаказыПоставщикам` - Read.
  Объекта `Configuration` в роли нет: это дополнение к основной роли.
- `Role.ИзменениеЗаказаПоставщику`: всё из роли чтения плюс полный набор прав на документ и регистр
  `ЗаказыПоставщикам` - тот же, что сейчас у МенеджерПоЗакупкам на эти объекты (копия его записей по
  `Document.ЗаказПоставщику*` и `AccumulationRegister.ЗаказыПоставщикам`), и команда
  `EMailОтправитьПоставщику`. Роль самодостаточна: чтение в ней есть, вторую роль выдавать не нужно.
- ОператорПроизводства: запись `Document.ЗаказПоставщику` удаляется. `AccumulationRegister.ЗаказыПоставщикам`
  (Read) и `ПотребностиПроизводства` остаются: по ним считаются потребности и обеспечение, документ они не
  открывают.
- Остальные роли (Казначей, Кладовщик, МенеджерПоЗакупкам, PDV, MobileClient, ЛичныйКабинет) не меняются.
- Обе роли добавляются в `Configuration.mdo` и в список ролей переноса старой редакции
  (`ЗагрузкаПереносаСтаройРедакции`), если он перечисляет роли-дополнения.

### Э2. Обработчик обновления

`ОбновлениеПрограммыОбработчики.ВыдатьЧтениеЗаказаПоставщикуОператорам`, версия 2.0.18.5, оперативный режим.
Обходит `ПользователиИнформационнойБазы.ПолучитьПользователей()` и для каждого пользователя с ролью
ОператорПроизводства делает два независимых шага, у каждого своё условие: (а) нет роли ЧтениеЗаказаПоставщику -
роль добавляется, пользователь ИБ записывается; (б) строка ролей в карточке справочника «Пользователи» (по
идентификатору пользователя ИБ) не равна `СформироватьСписокРолей` - реквизит «Роли» карточки обновляется. Запись
карточки имеет побочное действие: `ПриЗаписи` объекта (`Catalogs/Пользователи/ObjectModule.bsl`) у карточки с
заполненным контрагентом очищает логин и пароль личного кабинета контрагента и не смотрит на режим загрузки.
Поэтому карточки с заполненным контрагентом обработчик НЕ записывает (строка ролей у них - только текст для
списка, права определяет пользователь ИБ; строка обновится при следующем сохранении карточки администратором),
остальные записывает в режиме загрузки. Модуль объекта справочника не меняется. Шаг (б) не зависит
от того, был ли на этом запуске шаг (а): после сбоя между двумя записями повтор доводит карточку. Сбой любой
записи НЕ подавляется: исключение уходит наружу, механизм обновления не поднимает версию базы и при следующем
запуске выполняет обработчик заново (образец с журналом и продолжением здесь не годится: это миграция прав, а не
необязательных настроек). Повторный запуск на доведённой базе ничего не меняет. На новой базе операторов нет -
обработчик пуст. Данные, кроме ролей пользователей, не трогаются; реструктуризации нет.

### Э3. Рабочее место производства

- Новое право формы `МожноЧитатьЗаказыПоставщику` = `ПравоДоступа("Чтение", Метаданные.Документы.ЗаказПоставщику)`
  в `ПраваРабочегоМеста`.
- Без него: страница `СтраницаЗаказыПоставщику` невидима; колонка заказа поставщику в таблице «Поступления»
  невидима; кнопка создания заказа поставщику и заполнение по потребностям в заказ поставщику невидимы;
  переход на скрытую закладку из сохранённых настроек окна не происходит (текущая страница - первая видимая).
- Запросы: соединение с `Документ.ЗаказПоставщику` в `ТекстЗапросаСтрокПоступлений` и
  `ТекстЗапросаСтрокПриходныхОрдеров` собирается только при праве чтения (без права поля заказа поставщику -
  пустые значения того же типа).
- `ЗаказыПоставщикуЗаказа` (:4652) в `СтрокиДокументов` даёт массив оснований для отбора `Д.Основание В (&Основания)`:
  без него поступления и приходные ордера, введённые на основании заказа поставщику, выпали бы из выборки, хотя сами
  они пользователю доступны. Поэтому для отбора массив ссылок читается в привилегированном режиме (режим включается
  только вокруг этого запроса и сразу снимается); ссылки служат параметром отбора и пользователю не показываются:
  колонка заказа поставщику скрыта, поля номера и даты заказа поставщику в строках пусты. Вызов :1492 (выбор заказа
  поставщику в строке) остаётся под проверкой права, как сейчас.
- Обращения к `Документ.ЗаказПоставщику` в модуле менеджера (полный перечень - поиском до правки, в таблицу
  однотипных объектов приёмки) защищаются в точке обращения к таблице заказа поставщику, а не на входе функции:
  многие из этих функций обслуживают и другие документы, и общий отказ на входе сломал бы их у оператора.
  - `СтрокаВБазеНеИзменилась` (:6506) подставляет в запрос таблицу фактического вида документа: защищать нечего,
    к заказу поставщику она приходит только от строки вида «заказ поставщику», а такая строка без права отклонена
    раньше (см. ниже).
  - `ЦенаСтрокиЗакупки` (:6710): цена прямого поступления по прайсу работает без права; ветка «цена из строки
    заказа поставщику» выполняется только при заполненном заказе поставщику в строке И праве чтения.
  - `ЗаблокироватьЗависимыеДокументы` (:9983): блокировки остатков переработки и прочего остаются; элемент
    блокировки по заказу поставщику добавляется только когда строка ссылается на заказ поставщику (управляемая
    блокировка права чтения не требует - это проверяется на базе тестом; если требует - блокировка заказа
    поставщику ставится только при праве чтения, а строка без права до неё не доходит).
  - `ТекстЗапретаСтрокиСПоступлениями`, `ПришлоПоСтрокеЗаказаПоставщику`, `ЕстьПоступленияПоЗаказуПоставщику`,
    `ТекстЗапретаЗаказаСПереносом`, `ЗаблокироватьЗаказПоставщику`, `ТекстЗапросаОстатковСтрокЗаказаПоставщику`,
    `ОткрытыеСтрокиЗаказовПоставщика`: вызываются только для строки или документа «заказ поставщику»; вызывающая
    точка (запись, удаление, смена статуса строки вида «заказ поставщику») отклоняет операцию без права чтения до
    вызова. Для каждой функции вызывающие точки сверяются поиском, результат - в приёмке.
- Строка поступления, введённая на основании заказа поставщику (`ТекстЗапретаСтрокиДокумента` :1097 →
  `ТекстЗапретаОснованияСтрокиПоступления` :5344 → `ТекстЗапретаСтрокиОснования` :5429): без права чтения заказа
  поставщику такая строка только для просмотра - изменение и удаление отклоняются текстом «строка введена по заказу
  поставщику, нет права на заказ поставщику», до любого чтения заказа. Новые строки поступлений пользователь без
  права вводит только без заказа поставщику (прямое поступление): выбор заказа поставщику в строке ему уже закрыт
  (:1454).
- Контроль «по материалу есть открытые строки заказа поставщику - прямое поступление запрещено»
  (`ТекстЗапретаОснованияСтрокиПоступления` → `ЕстьСтрокиОснований` → `СтрокиЗаказовПоставщикуДляВыбора`) сейчас без
  права чтения получил бы пустой список и молча разрешил бы поступление в обход заказа. После правки наличие
  открытых строк для этого контроля определяется отдельной функцией в привилегированном режиме (возвращает только
  Булево, данные заказа наружу не выходят). Есть открытые строки и нет права чтения - прямое поступление отклоняется
  текстом «по материалу есть открытый заказ поставщику: поступление по нему вводит пользователь с доступом к
  заказам поставщику». Нет открытых строк - прямое поступление проходит, как у пользователя с правом. Список для
  выбора (:1454) по-прежнему пуст без права. Это решение исполнителя в сторону сохранения контроля; владельцу
  называется в отчёте как развилка.
- Строка вида «заказ поставщику» без права чтения отклоняется на входе записи текстом `ТекстНетПраваВводаДокументов`.
- Список «Документы» заказа (`ОписаниеЧастейДокументовЗаказа` :3701, `ДобавитьЧастьДокументов` :3740,
  `ПодзапросПоступлений` :3914): сейчас ветви поступлений, приходных ордеров и возвратов по ним выпадают без чтения
  заказа поставщику. После правки цепочка «заказ клиента → заказ поставщику → поступление → ордер, возврат» строится
  по параметру - массиву ссылок заказов поставщику, прочитанному в привилегированном режиме (та же функция, что для
  `СтрокиДокументов`), а не подзапросом к таблице документа. Сами заказы поставщику в список без права чтения не
  попадают; поступления, ордера и возвраты, доступные пользователю, остаются.
- Однотипное: рабочее место закупок (`АРМЗакупки`) требует заказ поставщику по своей сути; у ролей, которым оно
  доступно (МенеджерПоЗакупкам, СкладскиеОрдера вместе с основной ролью), проверяется открытие формы под
  основной ролью без чтения заказа поставщику - находки идут в эту же сборку или в TECHDEBT с причиной.

### Э5. Тесты

- Сначала падающие: сценарий `tests/ui` под пользователем «Тест ОператорПроизводства» (после Э1 у него нет
  чтения заказа поставщику) - открыть рабочее место, ввести и ЗАПИСАТЬ строку на «Товарах» (проверка: строка
  после перечитывания на месте, статус не «не записано», окна ошибки нет), пройти строки заказов с выделением,

- Оговорка к сценарию оператора без чтения: обход Э2 на базе гейта выдаст роль чтения и тестовому оператору, поэтому
  `tests/ui/role-users.bsl` при каждом прогоне выставляет тестовым пользователям роли заново, точным набором.
- Тест документов на контроль открытых заказов: функция наличия открытых строк возвращает Истина при открытой строке
  заказа поставщику по материалу, запрет прямого поступления срабатывает в ветке «без права чтения».
- Под двумя пользователями с парами ролей ОператорПроизводства+ЧтениеЗаказаПоставщику и
  ОператорПроизводства+ИзменениеЗаказаПоставщику: закладка видна; у первой - только просмотр, у второй - ввод
  строки. `tests/ui/role-users.bsl` учится заводить пользователя с несколькими ролями.
- Тесты документов: сценарий прав новых ролей (`ПравоДоступа` с метаданными роли), сценарий обработчика
  обновления: обработчик разделён на обход и экспортную функцию обработки одного пользователя ИБ; тест вызывает
  только функцию одного пользователя на своём тестовом пользователе (получает роль чтения, повтор не меняет,
  карточка без контрагента получает строку ролей, карточка с контрагентом не записывается - логин контрагента цел),
  пользователь и карточка удаляются в конце теста и в обработке исключения. Обход всех пользователей в тесте не
  запускается: он менял бы настоящих пользователей базы, а откат транзакции теста роли ИБ не восстанавливает.
  Обход проверяется гейтом на обновлении базы гейта (у пользователя «Тест ОператорПроизводства» появляется роль), поступление на основании заказа поставщику
  остаётся в строках «Поступлений» заказа клиента при выключенном чтении заказа поставщику (ветка без права
  вызывается параметром функции), запросы поступлений и ордеров без соединения с заказом поставщику возвращают те же
  строки, что с соединением (сравнение двух вариантов текста под администратором).
- Пороги `scripts/smoke-floor.txt` поднимаются по факту.

## Риски

1. Оператор, которому заказ поставщику нужен, после обновления его теряет - закрыто обработчиком Э2; пользователь
   ИБ без карточки в справочнике тоже обходится (обход по пользователям ИБ, а не по карточкам). Сбой обработчика
   останавливает обновление и повторяется при следующем запуске - права не теряются молча.
2. Пропущенное обращение к заказу поставщику в рабочем месте - ошибка прав у оператора. Закрывается сценариями
   на клиенте под ролью (Э5) и поиском по обоим модулям; непроверенные ветки называются в отчёте.
3. Другие формы, доступные оператору и читающие заказ поставщику (поступление, приходный ордер, отчёт
   потребностей, дашборд): поиск по `src/cf` запросов с `Документ.ЗаказПоставщику` в объектах, на которые у
   оператора есть право; найденное - в таблицу однотипных объектов приёмки.
4. Веб-клиент у всех рабочих ролей расширяет поверхность входа: публикация базы в интернете теперь пускает их
   через браузер. Решение владельца («давай права на запуск нужных типов клиентов»).
5. Исходная жалоба не воспроизведена - сборка может её не устранить.

## Принято по итогам ревью плана (круг 5, approve_with_changes)

1. Колонка «Через» списка «Документы» (`ТекстЧастиДокументовЗаказа` :3768): у документов второго уровня она
   возвращает основание. Без права чтения заказа поставщику основание-заказ поставщику в колонке заменяется пустым
   значением - ссылка пользователю не показывается.
2. Ветки ограниченных прав исполняются и под настоящим пользователем: сценарий на клиенте под «Тест
   ОператорПроизводства» выбирает заказ клиента с подготовленной цепочкой «заказ поставщику → поступление» (данные
   базы гейта; если такого заказа нет - добавляется в `scripts/dirty-data.sh`/фикстуры) и проверяет, что закладка
   «Поступления» открывается без окна ошибки и строка поступления на месте; попытка прямого поступления по
   материалу с открытым заказом поставщику даёт текст запрета, а не ошибку.

## Дополнение 2026-11-23: служебные чтения, найденные прогонами под ролью

Прогоны под оператором без чтения заказа поставщику показали места, где запись документа читает объекты, на
которые у оператора прав нет. Правки - точечные, без изменения прав ролей:

1. `НалоговыеДокументыНаОснованиях.НаборБлокировки` (полный набор): `НалоговыеНакладныеПоОснованиям` и
   `ПроведенныеНалоговыеНакладные` читаются в привилегированном режиме. Набор блокировки оснований от прав
   пользователя не зависит; наружу уходят только ссылки для блокировки, пользователю они не показываются. Без этого
   оператор не мог дописать строку в проведённое поступление или отгрузку («Недостаточно прав для работы с таблицей
   Документ.НалоговаяНакладная» из `ПередЗаписью`; новый документ проходил - у него ветка блокировки пустая).
   Привилегия выключается сразу после двух чтений, остальной код функции - под правами пользователя.
2. `ПотребностиПроизводства.ЗаказКлиентаОснования`: реквизит «Основание» заказа поставщику читается в
   привилегированном режиме (отмена проведения поступления по заказу поставщику пользователем без права на заказ).
3. Отказы вместо ошибки прав для пользователя без чтения заказа поставщику: `ОрдераСклада.ЗаполнитьПоОрдерам`
   (поступление по ордеру, введённому по заказу), `ТекстЗапретаСтатусаДокумента` рабочего места производства,
   открытие рабочего места закупок (`Отказ` с сообщением о нужной роли).

Проверка: сценарии `tests/ui/role-scenarios.txt` - две записи строки поступления подряд под оператором (вторая
дописывается в проведённый документ), отказ открытия рабочего места закупок под оператором со складскими ордерами.
Не исполняется на базе: пункты 2 и 3, кроме рабочего места закупок (TECHDEBT).

4. Поступление по заказу поставщику без права на заказ: форма документа открывается только для просмотра, запись
   отказывает в `ПередЗаписью` (кроме привилегированного режима и обмена) - ревью кода, P1.
5. Новые роли получают просмотр раздела «Закупки» (в нём команда списка заказов) и чтение зависимостей печати заказа,
   сверенное с адаптерами фирменной печати: номенклатура, единицы, характеристики, ставки НДС, валюты, договоры,
   пользователи, контрагенты, организации, банковские счета, реквизиты контрагентов и их виды, присоединённые файлы
   (фото в запросе котировок), регистр заказов поставщикам. Перечень Э1 дополняется этим списком; основная роль
   этих прав может не иметь.
6. Ветки пунктов 2-4 под настоящим пользователем без права не исполнены: для них нужны данные (поступление и ордер
   по заказу поставщику у заказа в работе). Ревью плана требует сценариев в этой же сборке; они вынесены в TECHDEBT
   и названы владельцу как непроверенное.
