# План: рабочее место закупок (АРМ закупок)

## Задача

Рабочее место менеджера по закупкам по образцу АРМ производства: путь закупки слева направо —
«Потребность» → «Заказы поставщикам» → «К поступлению». Сейчас закупка живёт только внутри АРМ
производства (закладки «Заказы поставщику» и «Поступления» у заказа клиента) и в общих списках
документов; работать от поставщика и от заказа поставщику негде.

## Решения владельца (2026-10-07)

1. Вариант «путь закупки», по этапам: первым — «Заказы поставщикам» и «К поступлению», вторым —
   «Потребность».
2. Стадия заказа поставщику **вычисляется** из движений и реквизитов, нового регистра статусов нет.
3. Пользователь — **менеджер по закупкам** (роль `МенеджерПоЗакупкам`), суммы ему видны.
4. Предложения поставщиков и тендер — позже, не в этой волне. **Пересмотрено 2026-10-07 (после сдачи 2.0.16.28):**
   «Потребность» и тендеры входят в эту волну — по потребностям нужно анализировать закупку; план этих сборок
   дописывается и проходит ревью плана перед реализацией (см. «Сборки», п. 3–4).
5. Оплаты поставщикам — **только показываются**, ввода оплат в АРМ нет.
6. Серверная логика ввода заказа поставщику и поступления строкой — **одна** с АРМ производства;
   закладки АРМ производства остаются как есть.

## Факты из кода (2026-10-07)

- Ввод строкой — `Обработки.АРМПроизводство.ЗаписатьСтрокуДокумента` / `УдалитьСтрокиДокументов` /
  `ТекстЗапретаСтрокиДокумента` / `ИзменитьСтатусДокументовСтрок` / `СтрокиЗаказовПоставщикуДляВыбора`.
  Все требуют `ДанныеСтроки.Заказ` (`ЗаказПокупателя`): запрет без заказа (`ТекстЗапретаЗаказаСтроки`),
  основание нового документа, блокировка заказа (`ЗаблокированныйЗаказ`), строки заказа поставщику
  для выбора фильтруются `Основание = Заказ`.
- `ЗаказПоставщику`: `Контрагент`, `ДатаПоставки`, `ВидЗаказа` (Основной/Предварительный),
  `Основание` (`ЗаказПокупателя`, может быть пустым), ТЧ с `КодСтроки` и `Продукция`. Двигает
  `ЗаказыПоставщикам` (ЗаказПоставщику, Номенклатура, Характеристика, КодСтроки; Количество, Сумма)
  и `ПотребностиПроизводства` (только при основании-заказе клиента).
- `ПоступлениеТоваровУслуг` по строке заказа поставщику списывает остаток `ЗаказыПоставщикам`;
  `ВозвратПоставщику` его возвращает.
- Оплаты: `ВзаиморасчётыСПоставщиками.ОбъектРасчётов` — поступление (и платёжные документы для
  авансов); основание платёжки — поступление (`ТЧОснования`). **Заказа поставщику среди объектов
  расчётов нет**: оплата заказа = оплата поступлений по нему; аванс поставщику до поступления к
  заказу не привязан и показывается только сальдо поставщика. Проведённая `НалоговаяНакладнаяПокупка`
  **переносит на себя** долг и оплаты покрытых поступлений (`ДолгПоПоступлениям`,
  `ОплатыПоПоступлениям` в модуле менеджера регистра) — остатков по одним поступлениям мало.
- Поступление списывает остаток `ЗаказыПоставщикам` с заказа из **шапки** (`Основание`): одно
  поступление = один заказ поставщику (`ТекстЗапретаОснованияПоступления` это и проверяет).
- Остаток заказа уходит в ноль и без поставки: другой заказ поставщику может забрать строки
  предварительного заказа (`ТЧТовары.ЗаказПоставщику`).
- Общий путь создаёт поступление в основной валюте с курсом 1 (`НовыйДокументЗакупки`, ~4366) —
  **ошибка уже сейчас** в АРМ производства для заказа поставщику в валюте.
- Применение введённой цены зависит от `ПоказыватьСуммы()` — настройки «Видеть суммы (производство)».
- Сценарий `АРМЗакупки` пропускается при выключенной опции «Производство».
- Общие механизмы: пагинатор (`РаботаСДокументамиКлиентСервер.ОбновитьПагинатор`, счёт страниц по
  образцу `Обработки.АРМПроизводство.СтраницаЗаказов`), панель отборов (`docs/plans/arm-production-panel.md`),
  легенда индикатора в одну строку. Правила форм — `docs/FORMS-STYLE.md` (в т.ч. новое: полосу
  прокрутки таблиц не отключать, tiny1C forms-023).

## Раскладка формы

```
┌ Заказы поставщикам ┬ К поступлению ┬ (Потребность — этап 2)
│ Отборы: Поставщик · Товар · Стадия · Период поставки · Ответственный          [Статус ▾] [Создать]
│ № | Дата | Поставщик | Стадия | ●◐ | Дата поставки | Сумма | Валюта | Заказ клиента | Ответственный
│ ◀◀ ◀ 1/3 ▶ ▶▶  1-50 из 124                               поставка · оплата: ○ ◐ ●
├ Товары ┬ Поступления ┬ Оплаты ┬ Документы
│ строки выбранного заказа: товар, заказано, пришло, осталось, цена, сумма, продукция/заказ клиента
```

- **Заказы поставщикам** — динамический список с пагинатором и панелью отборов. Стадия и индикатор —
  поля запроса.
- **Товары** — строки выбранного заказа, ввод строкой (общий путь); у проведённого заказа правка
  перепроводит, как в АРМ производства.
- **Поступления** — строки поступлений по заказу, ввод строкой с выбором строки заказа (общий путь),
  номер и дата накладной поставщика.
- **Оплаты** — только чтение: платёжки по поступлениям заказа (дата, документ, сумма, валюта) и
  внизу строкой — сальдо расчётов с поставщиком по организации и договору заказа (аванс/долг).
- **Документы** — только чтение: вся цепочка (заказ, поступления, возвраты, платёжки) со статусом.
- **К поступлению** — таблица строк всех проведённых заказов с остатком `ЗаказыПоставщикам` > 0:
  поставщик, заказ, товар, осталось, дата поставки, просрочка. Отметить строки одного поставщика →
  «Поступление» → номер и дата накладной → **по поступлению на каждый заказ поставщику** среди
  отмеченных строк, с общими номером и датой накладной (одно поступление на несколько заказов
  модель учёта не поддерживает — см. факты). Каждое поступление пишется **пакетом**: все его строки
  проверяются, блокируются, перечитываются остатки и документ записывается один раз в одной
  транзакции; отказ любой строки — откат всего документа. Итог — по заказу: создано / отказ с причиной.

## Статус и индикатор (вычисляются)

Терминология (замечание владельца 2026-10-07, TECHDEBT «Стадия и Статус»): в этом АРМ то, что в плане ниже
называется стадией, в интерфейсе — **«Статус»** (колонка и отбор); действия над заказами — кнопка
**«Изменить статус ▾»**; колонка «Статус» нижних закладок — статус документа строки.

«Пришло» считается **по движениям поступлений и возвратов**: сумма расхода `ЗаказыПоставщикам` с
регистраторами `ПоступлениеТоваровУслуг` и `ВозвратПоставщику` (у возврата количество уже отрицательное —
не вычитать повторно), а не по нулевому остатку; списание остатка другим заказом поставщику —
«перенесено».

| Стадия | Условие |
|---|---|
| Отменён | `ПометкаУдаления` |
| Черновик | не проведён |
| Ожидает поставки | проведён, пришло = 0, остаток > 0, `ДатаПоставки` не прошла или пустая |
| Просрочен | проведён, остаток > 0, `ДатаПоставки` **заполнена** и < начала текущего дня |
| Частично поступил | пришло > 0, остаток > 0, не просрочен |
| Поступил | остаток ≤ 0, пришло > 0 (≤ — сверхпоставка: проведение остаток не контролирует) |
| Перенесён | остаток ≤ 0, пришло = 0 (строки забрал другой заказ поставщику; частично поступивший и затем перенесённый показывается «Поступил» — пояснение в легенде) |

Стадия — **только по поставке**; оплата в стадию не входит (решение 5: оплаты только показываются).
Стадия — новое перечисление `СтатусыЗаказовПоставщику` **только для отбора и представления**
(в регистры не пишется; новое перечисление — объект метаданных, проходит ревью как существенное).

Индикатор — два кружка: **поставка** (пришло/заказано по количеству) и **оплата** (доля оплаченного
долга поступлений заказа). Оплата считается с переездом расчётов: долг и оплата поступления, покрытого
налоговой накладной покупки, берутся с накладной в доле покрытия (`НалоговыеНакладныеПоОснованиям`,
`РаботаСДокументами.СуммаВДолеПокрытия`). Принадлежность оплат сохраняется: платёж, выписанный на
конкретное поступление и перенесённый накладной, остаётся оплатой этого поступления (по `ДокументПродажи`,
без повторного учёта переноса); по долям покрытых поступлений распределяются **только** платежи прямо на
общую накладную. Закладка «Оплаты» показывает и платёжки на накладные таких поступлений.
Граница «сегодня» для просрочки — параметр списка, обновляется при каждом обновлении списка, а не только
при открытии формы. Стадия — поле запроса списка: отбор по ней работает до пагинации, счётчик страниц считается теми же
условиями (образец `СтраницаЗаказов`). Только **индикатор оплаты** (по нему нет отбора и сортировки)
можно при тяжести считать запросом по ссылкам текущей страницы.

## Общий путь ввода (решение 6)

Рекомендация — **обобщить функции АРМ производства на месте**, не копировать:
- `ДанныеСтроки.Заказ` для видов `ВидЗаказПоставщику`/`ВидПоступление` становится необязательным, если
  задан контекст «заказ поставщику» (новое поле `КонтекстЗаказПоставщику`). **Связь с заказом клиента
  и производственный контекст разделяются**: проверки производства (проведённость заказа, блокировка,
  потребности) применяются, только если основание — заказ, который проводится
  (`Документы.ЗаказПокупателя.ЗаказПроводится(ВидОперации)`, то есть заказ на производство при включённой
  опции). Заказ поставщику под торговый заказ клиента работает в закупочном контексте, основание
  сохраняется.
- Без заказа клиента: блокируется сам заказ поставщику (по образцу `ЗаблокированныйЗаказ`), новое
  поступление заполняется от заказа поставщику (`ДокОбъект.Заполнить(ЗаказПоставщику)` уже есть),
  новый заказ поставщику — без основания, `Продукция` пустая.
- `СтрокиЗаказовПоставщикуДляВыбора` и `ИзменитьСтатусДокументовСтрок` получают тот же контекст.
- **Пакетная запись поступления** — новая функция общего пути `ЗаписатьСтрокиПоступления(Строки, Накладная)`:
  все строки одного заказа поставщику, одна транзакция, одна запись; на ней же «вторая строка в тот же
  документ» не нужна. В пакете черновик при отказе проведения **не пишется внутри транзакции**
  (`ЧерновикСразу = Ложь`): полный откат, а черновик — если нужен по решению владельца 9 — только после
  `ОтменитьТранзакцию`, отдельной записью; итог пакета говорит, что именно записано.
- **Блокировка остатков заказов поставщику (правка проведения трёх документов).** Сейчас проведение
  поступления блокирует `ТоварыВНаличии`, `ВзаиморасчётыСПоставщиками` и `ПотребностиПроизводстваЗакупки`,
  но **не** `ЗаказыПоставщикам`; перенос строк в `ЗаказПоставщику` читает остатки источника тоже без
  блокировки. Новая `УправляемыеБлокировки.ЗаказыПоставщикам(Блокировка, ЗаказыПоставщику)` — исключительная
  по измерению `ЗаказПоставщику` — добавляется в `ЗаполнитьБлокировкуПроведения`: поступления — по
  `Основание`, возврата поставщику — по заказу-родителю, заказа поставщику — по своей ссылке и всем
  `ТЧТовары.ЗаказПоставщику`. Порядок — тот же, что у остальных элементов. АРМ (проверки зависимых
  поступлений и переносов, «Статус», пакет) берёт тот же набор в том же порядке через общую процедуру по
  образцу `ЗаполнитьБлокировкуПередачи`. Без этого проверки «перед записью» не защищают от штатной формы,
  проводимой параллельно. Ревью — `ai-database` обязателен.
- **Валюта**: новое поступление от заказа поставщику сохраняет `ВВалюте` и `Валюту` заказа, а **курс —
  на дату поступления** штатной `РаботаСВалютами.ЗаполнитьВалютуПоОснованию` после установки даты;
  принудительный сброс валюты и курса в `НовыйДокументЗакупки` убирается. Введённая цена — в валюте
  документа. Исправляет и АРМ производства (пункт «Что нового»).
- **Цена из прайса в валютном документе**: `ЦенаСтрокиЗакупки` различает источник — цена из заказа-основания
  берётся в его валюте, цена из `ЦеныНоменклатурыПоставщиков` (основная валюта) переводится в валюту
  документа по его курсу до расчёта упаковки и НДС.
- **Защита перенесённых строк**: перед изменением и удалением строки, отменой проведения и пометкой
  удаления заказа поставщику общий путь проверяет зависимые заказы поставщику (движения переноса
  `ЗаказыПоставщикам` с регистратором `ЗаказПоставщику` и непомеченные документы со ссылкой на строки
  через `ТЧТовары.ЗаказПоставщику`) — под той же блокировкой, что проверка зависимых поступлений.
- **Дата документа строки**: ограничение «новая строка — только в документ за сегодня» остаётся в
  производственном контексте; в закупочном строку можно добавить в выбранный заказ поставщику любой даты
  (версия, права, зависимые поступления и перепроведение проверяются как прежде). **Исключение** — заказ,
  забравший строки другого заказа (`ТЧТовары.ЗаказПоставщику` заполнен): его перепроведение заново берёт
  остаток источника на свою дату и может увести источник в минус, поэтому в АРМ такой заказ только
  читается, правка — в форме документа.
- **Цены**: политика применения введённой цены разделяется по контексту — в закупочном контексте цена
  применяется по праву изменения заказа поставщику/поступления, производственный контекст по-прежнему
  зависит от `ПоказыватьСуммы()`.
- АРМ закупок вызывает эти функции через свой модуль менеджера (тонкие обёртки), своего пути записи
  нет. Сценарий `АРМЗакупки` гарантирует, что поведение АРМ производства не изменилось.

Альтернатива — вынести ввод закупок строкой в общий модуль и звать из обоих АРМ. Чище, но это
перенос ~1500 строк из модуля на 593 КБ; предлагаю записать в TECHDEBT и не делать в этой волне.

## Сборка 2.0.16.30 — «Потребность» (анализ закупки по потребностям)

### Решения владельца (2026-10-07, после сдачи 2.0.16.29)

7. Источники потребности — **заказы клиентов на производство** (регистр `ПотребностиПроизводства`) и **пополнение до
   минимального остатка**; торговые заказы клиентов регистр не ведёт — не показываются.
8. Группировка по умолчанию — **по товару сводно**; переключатель «по заказу клиента» / «по поставщику» остаётся.
9. Выгрузки в отчёт нет — экран АРМ (штатное «Вывести список» таблицы).
10. «Заказать» — отдельный заказ поставщику на каждый заказ клиента на производство (основание одно), пополнение —
    отдельным заказом без основания.

### Факты из кода

- `ПотребностиПроизводства` — остатки по (Заказ, Продукция, Материал, Характеристика): Потребность, Заказано, Пришло,
  ИзОстатка. Дефицит заказа — «Потребность − Заказано − ИзОстатка» > 0 (`ДефицитЗаказа`). Заказано растёт только у
  заказа поставщику **с основанием-заказом клиента** — заказ без основания дефицит производства не закрывает.
- Минимальный остаток: `РегистрСведений.МинимальныйОстатокПоСкладам` (склад, номенклатура; мин/макс), иначе реквизит
  `Номенклатура.МинимальноеКоличествоХранения`; регламентное оповещение берёт склады с `ОповещатьОМинимальномОстатке`.
- `ФормированиеЗаказовПоставщику` считает пополнение по остатку, заказам клиентов и заказам поставщикам — свой
  механизм в форме; переиспользуется идея, не код (код в модуле формы).

### Раскладка

Верхняя закладка **«Потребность»** — первой, слева от «Заказов поставщикам»:
- над таблицей — группировка (по товару / по заказу клиента / по поставщику), флажок «только с дефицитом» (вкл.);
  отборы панели — поставщик (основной поставщик товара), товар;
- таблица: товар, характеристика, источник (заказ клиента или «пополнение склада»), нужно, заказано, пришло,
  со склада, на складе (для пополнения), **дефицит**, поставщик (основной, можно сменить), последняя цена закупки
  (прайс поставщика), **к заказу** (по умолчанию дефицит, правится), флажок;
- нижние закладки по строке: «Источники» (заказы клиентов и пополнение, составившие строку), «Заказы поставщикам»
  (строки заказов поставщику по товару с остатком, в том числе черновики, и поступления), «Остатки» (по складам);
  «Предложения» — в 2.0.16.31;
- **«Заказать»** по отмеченным строкам: по каждому поставщику — заказ на каждый заказ клиента (основание —
  заказ клиента: иначе дефицит производства не закроется) и один заказ без основания на пополнение. Запись —
  **пакетом** (новая `ЗаписатьСтрокиЗаказа` общего пути по образцу `ЗаписатьСтрокиПоступления`): один заказ — одна
  транзакция и одно проведение; под блокировкой `ПотребностиПроизводства` по заказу клиента (и набором проведения
  заказа поставщику) **дефицит перечитывается**, количество строки урезается до него, нулевой дефицит — отказ строки
  («уже заказано, обновите»): второе нажатие и устаревший экран дубля не создают. Отказ проверки — пустая транзакция,
  отказ проведения — откат и черновик после; черновики заказов поставщику по источнику видны в строке («заказано
  черновиком») и в дефицит не входят как заказанное, но «Заказать» при их наличии требует подтверждения. Итог — по
  заказу: создан / отказ с причиной. Строка без поставщика отклоняется. Ревью — `ai-database` обязателен.

### Расчёт

- Производство: регистр `ПотребностиПроизводства` пишет только приход — остатки выполненных заказов не обнуляются,
  поэтому берутся только непомеченные проведённые заказы клиентов на стадии **до выпуска** — явный список:
  ФормируетсяПотребность, ЗаказПоставщику, ВосполнениеПотребности, ВПроизводстве (последняя запись
  `ИсторияЗаказовПокупателейПоСтатусам.СрезПоследних`, как в АРМ производства). Заказ без записи истории не
  показывается (пояснение в легенде; TECHDEBT — заполнение истории старых заказов).
- Дефицит строки производства — своя формула запроса, **не** `ДефицитЗаказа`: «Потребность − Макс(Заказано, Пришло) −
  ИзОстатка» по (Заказ, Продукция, Материал, Характеристика), положительные части складываются по продукции до свёртки
  по материалу — так же, как «обеспечено» в стадии заказа (`ПроизводственныеЗаказы`, Макс(Заказано, Пришло)):
  поступление прямо под заказ клиента дефицит закрывает. `ДефицитЗаказа` не меняется (его зовут `Производство` и
  заполнение заказа поставщику).
- Пополнение — одно правило с регламентным оповещением о минимальном остатке: по складам с
  `ОповещатьОМинимальномОстатке`, минимум склада — из `МинимальныйОстатокПоСкладам`, нулевой — реквизит номенклатуры;
  на складе — `ТоварыВНаличии` склада без партий, пришедших под заказы клиентов на стадии до выпуска (по `Партия`);
  дефицит склада = минимум − на складе, сумма по складам; минус заказано — остатки строк `ЗаказыПоставщикам`
  проведённых заказов **без заказа клиента** (каждая строка зажата нулём снизу; предварительные — не учитываются);
  итог > 0. Характеристики в минимуме нет — пополнение по товару без характеристики.
- Группировка по товару складывает источники; «к заказу» распределяется по источникам в порядке (заказы клиентов по
  дате отгрузки, затем пополнение); сверх суммы дефицитов — в заказ пополнения.
- Всё считается запросом на сервере (не копируя запрос `ФормированиеЗаказовПоставщику`: соединение с оборотами по
  регистратору размножает остаток); до 500 строк **после** группировки, с предупреждением. Количества — в единицах
  хранения, «к заказу» — в единицах, упаковка строки заказа — единица товара.

### Уточнения второго круга ревью

- Стадия — последняя **запись стадии** истории (`Индикатор <> ""`, признак `ЭтоЗаписьСтадии`), а не последняя запись
  вообще: у заказов до E8 последней бывает запись статуса продаж.
- Пакет пополнения перед перечитыванием берёт исключительную блокировку `ЗаказыПоставщикам` по `Номенклатура` строк
  пополнения — два закупщика не создадут дубль.
- Перечитывание урезает до дефицита только производственные строки; намеренный излишек «к заказу» идёт в заказ
  пополнения и не срезается.
- Нет ни одного склада с `ОповещатьОМинимальномОстатке` — на закладке подсказка «пополнение не настроено».
- Экран и перечитывание в пакете считают дефицит **одной** функцией запроса.

### Тесты

Новый сценарий `ПотребностьЗакупок` (опция «Производство» включается в транзакции сценария, `УстановитьОпции`):
