# Проект: список и карточка товара — UI/UX, динамическая иерархия, рефакторинг (2026-10-10)

Задача владельца 2026-10-10: в списке товаров — панель быстрых фильтров «как в обычных наших списках»; карточку
перегруппировать по важности без потери функционала; показать, что ещё можно отобразить; анализ кода списка и карточки
для рефакторинга с учётом нового функционала; переключаемая иерархия списка (папки / виды / свойства) с быстрым
выбором типа иерархии. Документ — проект, кода нет. Исследование — три субагента (список, карточка, модель данных),
находки сверены точечно.

## 1. Что есть сейчас (факты)

**Справочник.** `Номенклатура` иерархический с папками (2 уровня, папки сверху). Классификаторы: `ТипНоменклатуры`
(перечисление: Товар, Услуга, Продукция, Полуфабрикат, Сырьё, Комплект), `СпособПополнения` (опция «Производство»),
`ТоварнаяГруппа` (плоский справочник, на карточке скрыт), `Бренд`, `Качество`, `ОсновнойПоставщик`, `СтавкаНДС`.
Свойства — два механизма: **новый** `УправлениеСвойствами` (план видов характеристик `ДополнительныеРеквизиты`;
«реквизиты» в ТЧ `ДополнительныеРеквизиты`, «сведения» в регистре `ДополнительныеСведения`; один набор на объект
метаданных, без наборов по виду или папке) и **старый** из базы клиента — ТЧ `СвойстваНоменклатуры`
(`ВидыСвойствНоменклатуры` → `ЗначенияСвойствНоменклатуры`, на карточке скрыт, в коде не используется, в TECHDEBT —
к переносу и удалению).

**Список (`ФормаСписка`).** Простая таблица `HierarchicalList` на 17 колонок (правило «без горизонтальной прокрутки»
нарушено), без панели «Сведения», фильтров и пагинатора, хотя FORMS-STYLE называет список номенклатуры частью пилота
2026-08-27. Запрос динсписка соединяет остаток (склад пользователя), продажи за 12 мес, файлы, закупочную цену
основного поставщика и розничную цену — для всего справочника. Есть заготовка «сегментов» — дерево `ДЗСегменты`
(товарные группы и типы) и `Справочники.Номенклатура.УстановитьПараметрыСписка`, переключающая плоский/иерархический
вид, — но дерево **никто не заполняет и не показывает**: механизм мёртвый. Сканер штрихкодов работает.

**Карточка (`ФормаЭлемента`).** Form.form 9 089 строк, модуль 848. Слева картинка, справа наименование/артикул и 11
закладок: Реквизиты, Хранение, Дополнительно, Свойства (скрыта), Описание, Стикер (скрыта), Цена, Технологическая
карта, Станки, Комплект. Скрыты, но живы в коде: блок упаковок, температура хранения, производитель/импортёр, полное
наименование, товарная группа, код. Не на форме вовсе: штрихкоды, характеристики, серии (только команды навигации),
`Ответственный`, `ECommerce`, `ОтражатьвЛКП`. Живых данных (остатки, продажи, заказы, потребность, станки) карточка
не показывает.

**Образец панели фильтров** — `Документы.РеализацияТоваровУслуг.ФормаСписка` (FORMS-STYLE, правило 6): справа панель
«Сведения» (закладки Фильтры / Клиент / Детали, сворачивается в колонку значков, состояние в `savedData`), фильтры —
тумблеры перечислений с «Все» первым и поля справочников заголовком сверху, пагинатор ◀ ▶. Кода общего нет: тройка
`ПрименитьОтборы` / `УстановитьОтборПоПолю` / `ПрименитьСтраницу` **скопирована в 43 модуля** форм списков документов;
общие только `ПараметрыВыборкиСтраницы` и `ОбновитьПагинатор` (`РаботаСДокументамиКлиентСервер`, порядок «по дате»).
Образец переключаемой группировки динсписка — `Справочники.ПодключаемоеОборудование.ПодключениеИНастройкаОборудования`
(`Список.Группировка`, включаемая флажками).

## 2. Список товаров — новая раскладка

```
┌ Иерархия ─────────────┐┌ Список ───────────────────────────────────────────┐┌ Сведения ─────┐
│ [Папки ▾] ☆           ││ 🔍 поиск                                   ◀ 1/12 ▶ ││ ▣ Фильтры     │
│ ▸ Все товары   (1 240)││ Наименование      Артикул  Ед.  Остаток  Цена     ││ ▣ Товар       │
│ ▸ Ткани        (  410)││ ...                                               ││ ▣ Движение    │
│ ▸ Фурнитура    (  305)││                                                   ││               │
│ ▸ <не задано>  (   12)││                                                   ││ [свернуть]    │
└───────────────────────┘└───────────────────────────────────────────────────┘└───────────────┘
```

**Колонки таблицы (5–6, помещаются):** Наименование (с картинкой вида/пометкой папки), Артикул, Ед., Остаток
(по складу фильтра), Розничная цена; опционально Тип пиктограммой. Остальные колонки — в панель «Товар» и остаются
скрытыми колонками (доступны через «Ещё → Изменить форму»), **кроме «Продажи»**: её поле уходит из запроса списка
(самое дорогое соединение), колонка удаляется, продажи — только в панели «Движение» по текущей строке (ревью плана
Codex, P2).

**Панель «Сведения» — закладка «Фильтры»** (по правилу 6, значения в `savedData`):
- **Тип** — тумблер: Все · Товар · Услуга · Продукция · Полуфабрикат · Сырьё · Комплект (производственные — по опции
  «Производство», комплект — по опции комплектации).
- **Пополнение** — тумблер Все · Закупка · Производство · Оба (по опции «Производство»).
- **Наличие** — тумблер Все · В наличии · Нет в наличии · Ниже минимума.
- **Склад** остатка — поле (по умолчанию склад пользователя; сейчас зашит параметром).
- Товарная группа, Бренд, Основной поставщик, Качество — поля справочников.
- **Свойство = значение** — поле вида доп. реквизита и поле значения (тип значения — по виду).
- Флажок «Показывать помеченные на удаление».

**Закладка «Товар»** (по текущей строке, отложенное обновление 0,3 с как у реализаций): картинка, артикул, коды
поставщика/производителя, основной поставщик, бренд, качество, ставка НДС, закупочная и розничная цена, ячейки
хранения, папка, старый код. **Закладка «Движение»**: остатки по складам (свободно — без закреплённого на станках),
заказано поставщикам, потребность производства, продано за 12 мес.

**Пагинатора нет — осознанное отклонение от правила 6** (ревью плана Codex, P1): образец пагинатора сам выбирает
ссылки по условиям панели и не видит штатного поиска динсписка, а с иерархией папок постраничная выборка «Ссылка В
списке» несовместима. Список товаров работает на штатной порционной выборке динсписка — поиск, иерархия, отборы
дерева и панели работают вместе. Отклонение записывается в FORMS-STYLE (правило 6, исключение для справочников).

**Остаток в запросе — свёрнутый подзапрос** (ревью плана Codex, P1): сейчас `ТоварыВНаличии.Остатки` соединяется
только по номенклатуре, а у регистра есть характеристика, серия, партия и дата партии — товар с двумя партиями
даёт две строки списка. Остаток — вложенный запрос `СГРУППИРОВАТЬ ПО Номенклатура` по складу фильтра; то же для
цен поставщика (одна строка на товар). Продажи за 12 мес из запроса списка убираются в панель «Движение» (по текущей
строке). Замер открытия на базах Drissotex и 2MZL до и после.

## 3. Динамическая иерархия

**Выбор типа иерархии** — поле-список над деревом (`[Папки ▾]`) и звёздочка «закрепить» (избранные режимы — первыми в
списке, сохраняются в настройках формы):

| Режим | Узлы дерева | Отбор списка | Вид таблицы |
|---|---|---|---|
| Папки (стандарт) | дерева нет, навигация по папкам самой таблицы | — | иерархический список |
| Тип | значения `ТипНоменклатуры` с количеством | `ТипНоменклатуры` | плоский + пагинатор |
| Товарная группа | элементы `ТоварныеГруппы` + «<не задано>» | `ТоварнаяГруппа` | плоский |
| Бренд / Основной поставщик / Качество / Способ пополнения | значения поля + «<не задано>» | по полю | плоский |
| Свойство: <вид доп. реквизита> | значения свойства (для списков — элементы `ЗначенияДополнительныхРеквизитов`, для строк/чисел — различные значения) + «<не задано>» | по полю `ЗначениеСвойства` запроса | плоский |
| Два уровня (вариант 2) | например Тип → Бренд, Свойство «Материал» → «Цвет» | оба поля | плоский |

**Как устроено.**
- Дерево — реквизит формы `ДеревоЗначений` (оживляем идею `ДЗСегменты`: тот же реквизит, своё заполнение),
  строится на сервере одним запросом `СГРУППИРОВАТЬ ПО` выбранному полю с `КОЛИЧЕСТВО` при смене режима и по кнопке
  «Обновить»; узел «Все» сверху, «<не задано>» снизу.
- Выбор узла — программный отбор в **своей группе элементов отбора** `Список.Отбор` (группа «Иерархия»), фильтры
  панели — в группе «Панель» (ревью плана Codex, P2: образец реализаций ищет элемент по имени поля и перезаписывает
  первый найденный — дерево и панель по одному полю затирали бы друг друга). Обе группы «И», каждая перестраивается
  только своим кодом. Счётчики дерева учитывают фильтры панели **и ограничения контекста открытия** (`ТолькоЗакупаемые`,
  `ТолькоПродаваемые`, `ТолькоТовары`, `ОтборТипа` — те же параметры, что у запроса списка; ревью плана Codex, P2) и
  **пересчитываются при каждом изменении фильтра панели** (тем же серверным вызовом, что ставит отбор), смене режима и по «Обновить» (ревью плана Codex, P2).
- **Узел «<не задано>»** — явное условие: для ссылочного поля `ВидСравнения.НеЗаполнено` (пустая ссылка), для
  свойства — «нет строки свойства» (NULL соединения) или пустое значение (ревью плана Codex, P2: образец считает пустое
  значение командой снять отбор).
- **Свойства в динсписке** — два независимых пути (ревью плана Codex, P1):
  - **одна семантика значения свойства** для карточки, дерева и фильтра (ревью плана Codex, P1/P2): уникальность пары
    «товар, свойство» в ТЧ не гарантирована, карточка при обходе ТЧ показывает **последнюю строку** — значит, значение
    свойства товара = значение строки с наибольшим `НомерСтроки` по этому свойству (для «сведений» — запись регистра
    `ДополнительныеСведения`, пара «объект, свойство» в нём ключ). Это правило — один текст подзапроса в модуле
    менеджера номенклатуры, его используют и дерево, и фильтр. **Запись согласуется с чтением в этапе 0** (ревью плана
    Codex, P1: `УправлениеСвойствами.ПеренестиЗначенияИзФормыВОбъект` меняет `Строки[0]` и оставляет последнюю строку
    дубля прежней): одна экспортная процедура `УправлениеСвойствами.УстановитьЗначениеСвойстваВОбъекте(Объект, Свойство,
    Значение)` пишет значение в одну строку и удаляет остальные строки того же свойства. Через неё идут **все пути
    записи** (полный поиск 2026-10-10; ревью плана Codex, P1): `ПеренестиЗначенияИзФормыВОбъект` (карточка),
    `ЗаписатьЗначениеСвойства` (АРМ производства, `ЗаписатьСвойствоПродукции`) и групповое изменение реквизитов
    (`ГрупповоеИзменениеРеквизитов/ObjectModule.bsl:383`). Чтение по ссылке (`ЗначенияСвойствОбъекта`, через
    `СвойстваИЗначенияОбъекта` — АРМ производства) получает `УПОРЯДОЧИТЬ ПО НомерСтроки`, чтобы и для исторических
    дублей побеждала последняя строка (ревью плана Codex, P2). Правило одинаково для всех объектов со свойствами;
    массовая чистка старых дублей — в TECHDEBT;
  - *дерево*: `ЛЕВОЕ СОЕДИНЕНИЕ` с этим подзапросом по `&СвойствоИерархии` даёт поле `ЗначениеИерархии` (одна строка на
    товар); вне режима «по свойству» параметр пустой;
  - *панель*: условие запроса `Ссылка В (ВЫБРАТЬ … из того же подзапроса по &СвойствоОтбора ГДЕ значение = &ЗначениеОтбора)`,
    включаемое параметром `&ОтборПоСвойству` (как существующие `ВЫБОР КОГДА &…Установлены`) — работает в любом режиме
    иерархии и не зависит от свойства дерева.
  «Характеристики» справочника не описываем (решение владельца 2).
- Режим, узел и избранные режимы — в настройках формы (`savedData`), как состояние панели.
- **Логика — в модуле менеджера, форма только вызывает** (ревью плана Codex, P2: смок не читает данные динсписка):
  `Справочники.Номенклатура.ТекстЗапросаСписка()` (форма ставит его в `Список.ТекстЗапроса` при создании),
  `ПараметрыЗапросаСписка(Контекст, ОтборыПанели, Иерархия)` и `ДеревоИерархии(Режим, Свойство, ОтборыПанели, Контекст)`.
  Сценарий уровня 3 `СписокНоменклатуры` выполняет тот же текст запроса с теми же параметрами на своих товарах
  (две партии одного товара — одна строка; товар без свойства — узел «<не задано>»; дубль строки свойства —
  значение последней строки; ограничения контекста `ТолькоЗакупаемые` в счётчиках) и сверяет количество строк и
  счётчики дерева. **Программные отборы** (группы «Иерархия» и «Панель» в `Список.Отбор`) обычный запрос не применяет
  (ревью плана Codex, P2), поэтому сценарий строит схему компоновки с набором-запросом `ТекстЗапросаСписка()`, ставит
  в её настройки те же группы отбора функциями общего модуля `ОтборыСписков` (тип `ОтборКомпоновкиДанных` тот же, что у
  динсписка), компонует в таблицу значений и сверяет пересечение дерева и панели по одному полю, «<не задано>» и
  независимость групп (перестройка одной не трогает другую).
- **Ручная приёмка** (раздел в `docs/TESTING.md` «Проверка списка и карточки товара»): поиск при выбранном узле
  дерева и фильтре панели, смена режима с сохранением после переоткрытия, «<не задано>», ленивые закладки карточки
  (первое открытие, повторное, запись без посещения закладки), видимость при смене типа — снимки окна на macOS.
- Выбор из списка (`ФормаВыбора`, `ФормаПодбора`) получает тот же навигатор — второй этап, после обкатки на списке.

Почему не `Список.Группировка` (строки-группы в самой таблице): с ней не работают пагинатор и иерархия папок, на
больших справочниках она тяжелее, а дерево слева даёт быстрые переходы и счётчики. `Группировка` оставляю как
вариант «развернуть всё одним списком», если владелец захочет.

## 4. Карточка товара — перегруппировка по важности

Весь функционал остаётся; меняется место. Порядок — от того, что смотрят каждый раз, к служебному.

```
┌ Шапка (всегда видна) ─────────────────────────────────────────────────────────────┐
│ [картинка ◀▶]  Наименование ______________________   Артикул ______               │
│                Тип: (Товар|Услуга|Продукция|Полуфабрикат|Сырьё|Комплект)  Ед. ___   │
│                Папка ________   Остаток 125 шт · Свободно 110 · Цена 12,50 · Закуп. 8,10 │  ← живые, ссылки на отчёты
└───────────────────────────────────────────────────────────────────────────────────┘
 Основное | Цены | Склад | Производство | Комплект | Свойства | Описание и печать | Служебное
```

| Закладка | Состав | Откуда |
|---|---|---|
| **Основное** | Классификация: Тип (в шапке), Способ пополнения, Товарная группа (вернуть из скрытых), Бренд, Качество. Учёт: Единица, Вес и ед. веса, Ставка НДС, ТН ВЭД. Закупка: Основной поставщик, Код поставщика, Код производителя, Производитель, Импортёр (вернуть) | «Реквизиты» |
| **Цены** | Закупочная цена, виды цен с наценкой (как сейчас) + история цен по ссылке | «Цена» |
| **Склад** | Остатки по складам и свободно (новое), Мин/Макс по складам, ячейки хранения, упаковки (блок сейчас скрыт — см. вопрос 3), условия и температура хранения | «Хранение» + скрытые блоки |
| **Производство** (опция «Производство»; Сырьё, ПФ, ГП) | Для ПФ/ГП: техкарта с версиями и статистикой; станки — допустимые + выработка кг/ч по каждому станку (новое, из карточек станков). Для Сырья и ПФ (ревью плана Codex, P2): «Где используется» — продукция, в техкарты которой входит товар (новое, `СоставТехКарты`); «На станках сейчас» (новое, `МатериалыНаСтанках`); потребность производства | «Техкарта», «Станки» |
| **Комплект** | как сейчас | «Комплект» |
| **Свойства** | Доп. реквизиты и сведения (`УправлениеСвойствами`); старые свойства клиента — до переноса (вопрос 2) | «Дополнительно», «Свойства» |
| **Описание и печать** | Описание, «выводить на печать», данные стикера (сорт, декларация, регламент, срок и условия хранения, стикеры по контрагентам) | «Описание», «Стикер» |
| **Служебное** | Код, Старый код, Полное наименование, Автор, Дата создания, Ответственный, ECommerce, Отражать в ЛКП, штрихкоды списком (новое — сейчас только команда) | разное |

Видимость закладок — по типу и опциям (как сейчас): одна процедура `НастроитьВидимость(Форма)` без контекста на
значениях опций, кэшированных в реквизитах формы при создании (опции на клиенте недоступны, tiny1C bsl-009);
вызывается из `ПриСозданииНаСервере` (без мигания — сейчас только `ПриОткрытии`) и из всех обработчиков, которые
меняют видимость в открытой карточке: смена типа, «использовать упаковки», индивидуальный/общий набор (ревью плана
Codex, P2). Данные закладок «Цены», «Склад», «Производство» — **ленивой загрузкой** при первом
переходе на закладку (сейчас грузятся все при открытии, даже скрытые). **Исключение — минимумы по складам**: таблица
грузится при открытии, как сейчас, потому что сохранение карточки материализует вычисленные минимумы складов без
записи (их читают закупки и «Недостаточные запасы»; ревью плана Codex, P2); ленивыми становятся цены, производство и
блоки движения.

## 5. Что ещё можно показать (из нового функционала базы)

Шапка-«светофор»: остаток всего / свободно (без закреплённого на станках, 2.0.16.58), ниже минимума — красным.
Закладка «Движение» / блоки карточки:
- **Запасы:** остатки по складам, в переработке у переработчика (`ТоварыВПереработке`), на станках
  (`МатериалыНаСтанках`), заказано поставщикам и ожидаемая дата (`ЗаказыПоставщикам`), потребность производства
  (`ПотребностиПроизводства`) — «сколько нужно / заказано / пришло».
- **Закупки:** последняя закупка (дата, поставщик, цена), цены поставщиков (`ЦеныНоменклатурыПоставщиков`), открытые
  тендеры по товару.
- **Продажи:** продано и выручка/маржа за 12 мес (`Продажи`), последние клиенты; себестоимость.
- **Производство:** выработка станков по товару, ближайшие требования-накладные и загрузка станков по этой продукции,
  плановая себестоимость и доступный выпуск (уже есть на техкарте — вынести в шапку для ПФ/ГП).
- **Ссылки-кнопки на отчёты** с отбором по товару: «Движения товара», «История товара», продажи, «Материалы на
  станках».

## 6. Анализ кода — рекомендации по рефакторингу

**P1 — корректность**
0. **P0 (ревью плана Codex): «артикул → штрихкод» перезаписывает чужой штрихкод.** У `ШтрихкодыНоменклатуры`
   единственное измерение — `Штрихкод`, номенклатура — ресурс; `ПослеЗаписиНаСервере` пишет `Записать(Истина)`:
   если артикул товара совпал со штрихкодом другого товара, штрихкод молча переезжает. Исправление (ревью плана
   Codex, пять кругов): одна функция модуля регистра `ЗанятьШтрихкод(Штрихкод, Номенклатура, Серия = пустая)` — в
   транзакции с управляемой исключительной блокировкой `ШтрихкодыНоменклатуры` по ключу `Штрихкод` читает запись;
   **нет записи** — пишет новую (Штрихкод, Номенклатура и Серия, если передана); **запись своя** — ничего не трогает
   (иначе потерялись бы характеристика, упаковка и серия штрихкода); «своя» — та же номенклатура, а при переданной
   серии — та же номенклатура **и** та же серия (штрихкод другой серии того же товара — чужой; ревью плана Codex, P1);
   **запись чужая** — не пишет, возвращает текст «штрихкод занят …», вызывающий показывает его. Её зовут **все пути, создающие штрихкод** (полный поиск
   `ШтрихкодыНоменклатуры.СоздатьМенеджерЗаписи` 2026-10-10; ревью плана Codex, P0): карточка — артикул и параметр
   `Штрихкод` по сканеру (`ФормаЭлемента/Module.bsl:159, 166`); загрузка из Excel (`ЗагрузкаИзExcel/…/Module.bsl:86,
   151`) — отказы собираются в отчёт загрузки; серия (`СерииНоменклатуры/ObjectModule.bsl:27`) — сгенерированный
   EAN-13 при занятости генерируется заново. Удаление штрихкодов при удалении товара (`Номенклатура/ObjectModule.bsl:104`)
   не меняется. Синхронизацию в модуль объекта **не переносим** (иначе она пошла бы и по программным записям).
1. `ФормаЭлемента.ПриЗаписиНаСервере` и `ПослеЗаписиНаСервере` пишут `МинимальныйОстатокПоСкладам` и штрихкоды
   с `Объект.Ссылка` формы, а не `ТекущийОбъект.Ссылка` (Module.bsl:213, :161, :167): у нового товара — риск записей с
   пустой номенклатурой.
2. Запись минимумов — переносится в модуль объекта: форма в `ПередЗаписьюНаСервере` кладёт таблицу минимумов в
   `ТекущийОбъект.ДополнительныеСвойства`, объект в `ПриЗаписи` пишет строки, которые **отличаются от регистра или
   которых в регистре нет** (сравнение с регистром, а не с исходной таблицей формы: таблица содержит вычисленные
   значения для складов без записи, и сохранение карточки, как сейчас, их материализует; ревью плана Codex, P2) — каждую своим
   набором записей с отбором **по обоим измерениям** (`Номенклатура = Ссылка` и `МестоХранения = склад строки`),
   `Записать(Истина)` замещает ровно эту запись; строки других складов не затрагиваются (ревью плана Codex, P0: набор
   без полного отбора стёр бы неизменённые строки). Всё — в транзакции записи товара. Это и делает дефект проверяемым (ревью плана Codex, P2: сценарий `ТестыДокументов` пишет
   объект, обработчики формы он не вызывает): сценарий записывает **новый** товар с `ДополнительныеСвойства` и
   сверяет регистр. Штрихкоды остаются в форме (п. 0), сценарий проверяет `ЗанятьШтрихкод` всеми тремя ветками
   (свободен, свой с характеристикой — не тронут, чужой — отказ без записи). Документ установки цен и запись техкарты из формы — в модуль менеджера, одной транзакцией с
   товаром — отдельным шагом этапа 0.

**P2 — архитектура и производительность**
3. **Общий модуль отборов списков.** До 44-й копии вынести установку программного отбора в общий модуль (например

## 8. Риски

- Отрисовку форм смок не проверяет — нужна приёмка глазами на macOS (вертикальные группы, мигание, ширина панели).
- Запрос списка с остатками, ценами и свойством на больших справочниках — замер до/после на базах клиентов.
- Карточка — самая используемая форма: переносить элементы скриптом опасно (Form.form 9 тыс. строк) — правка по
  проверенным позициям, дифф по всей форме (tiny1C workflow-009).
- Права: новые блоки карточки читают регистры (`МатериалыНаСтанках`, `ПотребностиПроизводства`, `ЗаказыПоставщикам`)
  — у ролей кладовщика, кассира (PDV), продавца прав может не быть; блок без права скрывать, а не падать.

## 9. Решения владельца (2026-10-10)

1. **Иерархия — один уровень + избранные режимы.** Второй уровень (вариант 2 таблицы раздела 3) — не делаем сейчас.
2. **Свойства — только новые доп. реквизиты** (`УправлениеСвойствами`, соединение с ТЧ и регистром сведений). Старые
   свойства клиента (`СвойстваНоменклатуры`) — перенос и удаление отдельной задачей; «Характеристики» справочника не
   описываем.
3. **Скрытые блоки карточки — вернуть на свои закладки** (упаковки — «Склад», температура — «Склад», производитель и
   импортёр — «Основное», полное наименование и код — «Служебное», товарная группа — «Основное», стикер — «Описание и
   печать»), под опциями, где они есть.
4. **Порядок — этапы 0→5 подряд**, сборки без остановок (как волны станков).
