## 2. Повторный запуск

### 2.0. Только демо- и тестовая база

До любых изменений (до констант, до первой транзакции) `СоздатьДемоНабор` проверяет, что в базе нет рабочих документов,
и повторяет ту же проверку под блокировкой набора в первой транзакции (§2.3).

**Рабочий документ — любой документ любого вида конфигурации** (обход `Метаданные.Документы`; проведён он или нет —
не важно; непроводимые и `КорректировкаРегистров` с движениями — тоже), **кроме**:

1. `Комментарий` начинается с маркера автоматических данных: «Démo 2mzl» (демо-набор, старый и новый — ключи начинаются
   так же), «Образец автотеста» (образцы `fixtures.sh`, `ТестовыеДанные.ПометкаОбразца`), «Тест уровня 3» (сценарии
   `ТестыДокументов`, на случай прогона без отката);
2. документ создан механизмом: `ВыпускПродукции` с `СозданАвтоматически = Истина` (автовыпуск при отгрузке и передаче) или
   с заполненным `Требование` (выпуск по требованию) — их основание проверяется само;
3. `ТехнологическаяКарта` демо-номенклатуры — `Номенклатура.Артикул ПОДОБНО "DEMO-2MZL%"` или (старый набор)
   `Номенклатура.Единица.Наименование ПОДОБНО "pce (Démo)%"`: базовые карты и карты, которые пишет проведение заказа,
   комментария набора не имеют;
4. вид **без реквизита `Комментарий`** (сейчас `ЗаданиеНаПересчет`, `КассоваяСмена`, `УстановкаЦенНоменклатурыВручную`,
   `СертификатНаОплату`, `ЗаявкаНаПоискТовара`): любой экземпляр — рабочий, кроме `ЗаявкаНаПоискТовара`, которую создаёт
   набор (кейс Z): у неё ключ набора пишется в `Артикул` (§2.2), исключение — `Артикул ПОДОБНО "Démo 2mzl%"`; заявки
   **старого** набора (ключа нет) распознаются точно, а не всем видом: `Контрагент.Наименование ПОДОБНО "Démo 2mzl - %"`
   **и** `Описание` — одна из пяти строк старого генератора («Suspension laiton 40 cm», «Tabouret de bar rotin»,
   «Lampe suspendue», «Miroir vénitien 2 m», «Tapis berbère 3x4»). Посторонняя заявка (другой контрагент или другой
   текст) остаётся рабочей и даёт отказ.

**Явное назначение тестовой базы.** На `build/ib` лежат образцы `fixtures.sh` по **всем** видам документов, в том числе
без `Комментарий` — их не отличить от рабочих. Поэтому запуск из `fixtures.sh --demo` (параметр запуска СмокТест
`ТестовыеДанные;<отчёт>;Демо…`) передаёт `Параметры.ТестоваяБаза = Истина`: это явное заявление разработчика о назначении
базы, и в этом режиме п. 4 не применяется (виды без `Комментарий` не проверяются; все виды с `Комментарий` — проверяются
как обычно). Кнопка этот параметр не передаёт никогда.

Запрос строится **динамически по метаданным**: один пакет, по `ВЫБРАТЬ ПЕРВЫЕ 1 "<вид>" КАК Вид, Д.Ссылка, Д.Номер, Д.Дата
ИЗ Документ.<вид> КАК Д ГДЕ <исключения вида>` на каждый вид из `Метаданные.Документы`; условие исключений собирается по
наличию реквизитов (`Комментарий`, `СозданАвтоматически`, `Требование`, `Номенклатура`) у вида; неограниченные строки —
`ВЫРАЗИТЬ(Д.Комментарий КАК СТРОКА(100))`. Первый непустой результат → отказ без единой записи: `ОТКАЗ;Демо-набор;База
содержит рабочие документы (<вид> № <номер> от <дата>) — демо-набор заполняется только в демо- или тестовой базе`
(4 языка). Итог: `Ошибок = 1`, `fixtures.sh` печатает строку и завершается кодом 1.

Следствие: в базе, где кнопка работает, все документы — свои (демо, образцы, тесты). Поэтому ниже **нет** защиты от
чужих техкарт, чужих движений и чужих взаиморасчётов — она избыточна.

### 2.1. Ключи справочников

Поиск — одним запросом на вид справочника; неограниченные строки — через `ВЫРАЗИТЬ(… КАК СТРОКА(N))`. Суффикс — часть
ключа. Найден → переиспользуется без перезаписи (кроме дописывания артикула, ниже); не найден → создаётся.

| Вид | Ключ |
|---|---|
| `УпаковкиЕдиницыИзмерения` | `Наименование` («pce (Démo)», «kg (Démo)») + суффикс |
| `МестаХранения` | `Наименование` с префиксом «Démo 2mzl - » |
| `Кассы`, `БанковскиеСчета` | `Владелец` (организация контекста) + `Наименование` с префиксом |
| `Контрагенты` | `Наименование` с префиксом |
| `ДоговорыСКонтрагентами` (основные договоры участников) | `Контрагент` + `ВидДоговора` + `Описание` («Démo 2mzl: …» + суффикс) |
| `Номенклатура` | `Артикул` «DEMO-2MZL-<код>» + суффикс; запасной для старого набора — `Наименование` + `Единица` = «pce (Démo)»; найденной по запасному ключу позиции артикул дописывается |
| Базовая техкарта | позиция создана → `ЗаписатьТехкарту` (CORE — на дату прогона, Sac tissé блока M — на начало Д1); переиспользована → не пишется (§2.5) |
| `ПроизводственноеОборудование` | `Наименование` с префиксом |
| Регистр `ПроизводственныйКалендарь` | записи на текущий год есть → не пишется (§4.2) |

Найден только помеченный на удаление элемент → кейсы, которым он нужен, получают `ПРОПУСК;<кейс>;<элемент> помечен на
удаление — снимите пометку или удалите окончательно и повторите`.

### 2.2. Ключ документа

Каждый документ, который создаёт набор, получает в `Комментарий` **`Démo 2mzl #<блок>-<кейс>-<n>` + суффикс**
(`Démo 2mzl #CORE-P1-3`, `Démo 2mzl #M-M-7`); `<n>` закреплён в коде шага и между версиями генератора не
перенумеровывается. Договоры кейса C — ключ в `Описание` («Démo 2mzl #CORE-C-1: Contrat cadre 2027»), лиды кейса L —
`Комментарий` записи регистра, заявки кейса Z (у `ЗаявкаНаПоискТовара` нет `Комментарий`) — в `Артикул`. Автовыпуски и выпуски по требованию создаёт механизм — они не документы набора.

**Ключ ставится последним**: `Заполнить` и обработчики заполнения переписывают `Комментарий`. Единая процедура
`ЗаписатьДокументКейса(Док, Ключ, Режим)` присваивает `Док.Комментарий = Ключ` после всех `Заполнить`, переносов и
расчётов строк — непосредственно перед `Записать`/`Провести` (через `ТестыДокументов.Записать/Провести`). Требования
записывает `ТребованияНакладные.ВыполнитьДействие` — ключ ставится после `Заполнить(ДанныеЗаполнения)` и до первого
действия (`Комментарий` оно не трогает). `Заполнить`, которые копируют или чистят комментарий (по `ObjectModule.bsl`):
заказ из КП — копирует (P1); реализация из заказа — копирует (P1, P2, P9, S3, S5); выпуск — очищает (P3, P9, S4, S5,
P10); заказ без основания — очищает.

Найти документы кейса — один запрос по типам документов кейса и его ключам. **Ничего, кроме ключа, не сравнивается.**
Перед фиксацией кейса — проверка «ровно один документ на ключ», иначе откат кейса и `ОШИБКА;<кейс>;ключ <…>: найдено N`.

### 2.3. Поколение набора, правило кейса, транзакции

**Поколение.** Признак новой схемы — `Démo 2mzl #RUN-v2` + суффикс в `Комментарий` контрагента «Démo 2mzl - Café Atlas»
+ суффикс. Пишется **первой транзакцией** прогона вместе со справочниками CORE, до кейсов.

| Café Atlas | `#RUN-v2` | Что это | Что делается |
|---|---|---|---|
| нет | — | чистая демо-база | первая транзакция: справочники и признак; дальше кейсы |
| есть | есть | новая схема, в том числе прерванный прогон | справочники по §2.1, кейсы по правилу ниже |
| есть | нет | **старый набор** | `ПЕРЕИСПОЛЬЗОВАН;CORE;старый набор`, кейсы CORE не создаются, признак **не пишется**; справочники — по §2.1; блок M создаётся |

**Правило кейса** (кейс атомарен):

| Найдено ключей кейса | Что делается | Строка итога |
|---|---|---|
| все | ничего; ссылки — в `Кейсы` | `ПЕРЕИСПОЛЬЗОВАН;<кейс>` |
| ни одного | предусловия (§2.4) → кейс целиком в своей транзакции, датами «сейчас» с шагом 2 с (блок M — §4.3) | `СОЗДАН;<кейс>` или `ПРОПУСК;<кейс>;<причина>` |
| часть (или документ кейса помечен на удаление) | ничего не создаётся и не трогается | `НЕПОЛНЫЙ;<кейс>;нет документов <n…> — удалите оставшиеся документы кейса, чтобы он создался заново` |

**Транзакции и блокировки.** Блокировка набора (исключительная управляемая, элемент
`Константа.ИспользоватьАвтовыпускПриОтгрузке`) **сериализует только запуски генератора**; под ней — повторный поиск ключей
кейса, предусловия, создание и проведение. Блокировки регистров берут сами документы при проведении, в своём существующем
порядке — генератор заранее ничего не блокирует. Предусловие по остаткам — проверка «на момент»: пользователь демо-базы,
проводящий документы по демо-номенклатуре во время прогона, может её опередить — **принятый риск**.

Два режима вызова (`ТранзакцияАктивна()` на входе):

| Режим | Транзакции | Ошибка кейса |
|---|---|---|
| Кнопка и `fixtures.sh` (`СоздатьДемоНабор`, внешней транзакции нет) | первая транзакция (проверка §2.0, справочники, `#RUN-v2`) и **каждый кейс — отдельная транзакция верхнего уровня** | откатывается только этот кейс: `ОШИБКА;<кейс>;…`; предыдущие кейсы зафиксированы, следующие выполняются; зависимые (L от S1/S3) — `ПРОПУСК;…;нет кейса <код>` |
| Сценарий уровня 3 (`ЗаполнитьДемоНабор` внутри транзакции прогона) | свои транзакции не открываются — всё в транзакции сценария | **исключение пробрасывается**, выполнение прекращается; транзакция прогона только откатывается (как `ТестыДокументов.ВыполнитьСценарий` и `ЗаписатьТехкарту`: после ошибки вложенной записи транзакция годна только для отката) — сценарий падает |

Гарантия «предыдущие кейсы сохранены, следующий выполняется» проверяется ручным прогоном `fixtures.sh --demo` на
одноразовой копии базы с управляемым сбоем в одном кейсе (временная правка не коммитится) — уровень 2, §7.

### 2.6. Программный интерфейс (совместимый)

- `ЗаполнитьДемоНабор(Начало, Суффикс)` — сигнатура и результат прежние, своей внешней транзакции нет, проверки §2.0 нет;
  внутри — схема §2.3. Для сценария `ДемоНабор` все кейсы идут веткой «ни одного → создать».
- Новая `ЗаполнитьДемоДанные(Параметры) Экспорт` — блоки `CORE`, `M` по `Параметры.Блоки`; возвращает `Кейсы` и итог.
- `СоздатьДемоНабор(Параметры = Неопределено)` — проверка §2.0, **без раннего отказа по маркеру**; константы — до
  транзакций кейсов; итог — прежние поля + `Переиспользовано`, `Неполных`, `Пропущено`, строки `ОТКАЗ;`,
  `ПЕРЕИСПОЛЬЗОВАН;`, `НЕПОЛНЫЙ;`, `ПРОПУСК;`. `Было` = 1, если ничего не создано и отказа нет.
- `fixtures.sh` показывает новые виды строк; `ОТКАЗ;` — код выхода 1.

## 3. Кнопка в «Компания и учёт»

Форма `DataProcessors/НастройкиПрограммы/Forms/КомпанияИУчёт`, образец кнопки — соседняя `СоздатьСвойстваНоменклатуры`;
оформление — `docs/FORMS-STYLE.md`, `<visible>true</visible>` явно.

1. **Право** — `ПравоДоступа("Администрирование", Метаданные)`, как `НачальноеЗаполнениеВызовСервера.ПроверитьПравоНачальногоЗаполнения`
   (не `ЭтоАдминистраторНастроек` — тот пускает и Руководителя). Видимость кнопки в `ПриСозданииНаСервере`, повторная
   проверка на сервере перед запуском задания и в самой фоновой процедуре.
2. **Проверка базы** — до открытия подтверждения серверная функция выполняет запрос §2.0; есть рабочие документы →
   предупреждение с видом, номером и датой документа, подтверждение не открывается. Задание проверяет ещё раз.
3. **Подтверждение и выбор** — форма `ПараметрыДемоДанных` обработки `НастройкиПрограммы` (`Ждать ОткрытьФормуАсинх`):
   текст на 4 языках — демо-данные пишутся в регистры этой базы и сами не удаляются; флажки опций, которые нужны блокам и
   в базе выключены — «Производство», «Автовыпуск при отгрузке», «Учёт станков» (по умолчанию сняты; без флажка
   зависимые блоки — `ПРОПУСК`), флажок блока «Станки» (§4.1). Отмена — ничего не делается.
4. **Фон** — образец `ПерепроведениеДокументов`: `ФоновыеЗадания.Выполнить("ПроцедурыРегламентныхЗаданий.ЗаполнитьДемоДанные",
   Параметры, "ДемоДанные", Наименование)` (метод задания — общий серверный неглобальный модуль). Параметры: структура
   выбора и адрес временного хранилища формы; процедура кладёт итог `СоздатьДемоНабор` по адресу. Второе активное задание
   с ключом «ДемоДанные» платформа не запускает — исключение перехватывается, «заполнение уже выполняется». Клиент —
   `ПодключитьОбработчикОжидания` (1 с); ошибка — `ИнформацияОбОшибке` задания. `ДлительныеОперации` не используется и не
   правится (сломанный вызов — в `docs/TECHDEBT.md`).
5. **Итог** — оповещение «Демо-данные: создано N, переиспользовано M, неполных K, пропущено L» и сообщения построчно на
   4 языках (`ССЫЛКА;` → навигационная ссылка). После включения опций — `ОбновитьИнтерфейс()`; в задании константы
   пишутся до транзакций с `ОбновитьПовторноИспользуемыеЗначения()`.

## 4. Блок `M` «Учёт станков»

### 4.1. Опция `ИспользоватьУчетСтанков`

Блок M выполняется, если опция уже включена или отмечен флажок «Включить учёт станков»; без него —
`ПРОПУСК;M;учёт станков выключен`. `fixtures.sh --demo` на `build/ib` — параметр `;Демо;Станки`. Текст у флажка:
появятся группа «Станки» и поле «Оборудование» в выпуске; открытые требования («Запущено», «Запланировано») запретят
выключить учёт станков и производство (`ЗагрузкаСтанков.ТекстЗапретаВыключенияУчета`), пока их не завершить или не
отменить. Нужна и `ИспользоватьПроизводство` — тоже флажком. `СписыватьМатериалыНаСтанокПриРазмещении` блок не меняет —
ожидания считаются от её значения.

### 4.2. Справочники блока

- Единица «kg (Démo)» (тип «Вес»); склады станков «Démo 2mzl - Stock Extrudeuse», «Démo 2mzl - Stock Métier».
- Станки (по образцу `НовыйСтанокСценария`): «Démo 2mzl - Extrudeuse E1» (120 кг/ч, 15 мин на смену заказа, 80 за час,
  Пн–Пт 08–20, с календарём, склад станка); «Démo 2mzl - Métier à tisser M1» (60 кг/ч, `РаботаетБезКалендаря`,
  Пн–Сб 06–22, 50 за час); «Démo 2mzl - Presse P1» (Пн–Пт 08–20, без работы — простой «нет заказа» и «Свободен»).
- Номенклатура (артикулы «DEMO-2MZL-M-…»): «Granulés PP», «Fil polyester» (kg), «Sac tissé» (pce с весом); табличная
  часть `Станки` у Sac tissé = E1, M1.
- Техкарта Sac tissé (Granulés 0,5 + Fil 0,2) — **на начало Д1**: заказ датирован Д1, а заполнение его материалов читает
  карту на дату заказа; окно дат (§4.3) считается до записи карты.
- Свои поставщик «Démo 2mzl - Plastiques Sud» и клиент «Démo 2mzl - Sacs Export» с договорами.
- Календарь: записей на текущий год нет и задана `СтранаКалендаря` → праздники страны (`ПраздничныеДни(КодСтраны, Год)`);
  иначе не трогаем.

### 4.3. Один атомарный кейс, окно дат, предусловие

Блок M — **один кейс** «M» (ключи `#M-M-<n>`): документы связаны движениями и временем на станках. Правило §2.3.
Прошлые даты допустимы: база демо (§2.0).

**Предусловие «у блока нет своей истории»**: перед созданием кейса — по номенклатуре блока (Granulés, Fil, Sac tissé),
складам станков и станкам блока нет движений в `ТоварыВНаличии`, `МатериалыНаСтанках`, `ЗагрузкаСтанков` (один пакетный
запрос, `ПЕРВЫЕ 1`). Есть → `ПРОПУСК;M;по номенклатуре или станкам блока уже есть движения без ключей блока — удалите их`.
Так кейс с ключами либо есть целиком, либо создаётся на номенклатуре без движений — партии и загрузки в прошлом не
пересекаются ни с чем.

**Окно дат.** Граница = `НачалоДемоНабора()` (сейчас − 15 мин). По режиму E1 и календарю берутся **три последних
рабочих интервала, целиком завершённых до границы** (`ОкончаниеИнтервала ≤ Граница`), с поиском назад не дальше 14 дней:
Д1 < Д2 < Д3. Сегодняшний интервал не завершён → Д3 = предыдущий рабочий день. Интервалы могут попасть в прошлый месяц —
тогда строка `ИНФО;M;часть факта — в прошлом месяце: в отчётах выберите период шире «Этого месяца»`. Даты запрета
редактирования (`ДатыЗапретаРедактирования`, `АвтозакрытиеПериода`) позже начала Д1 → `ПРОПУСК;M;даты запрета`.
Трёх завершённых интервалов за 14 дней нет → `ПРОПУСК;M`.

Время каждого события задаётся **от границ интервала** [Нi, Кi] (у E1 — 12 ч), и до записи проверяется вся
последовательность. Проверки разделены: **производственные события станков** (запуск и завершение требований 3, 4, 10,
обслуживание 5 и 9; документы 6–8 — по станку внутри интервала Д2) — внутри своего рабочего интервала и не позже границы;
**документы 1–2** (поступление и заказ) — датируются за час до Н1 **без** проверки интервала, только «раньше первого
запуска» и «не раньше даты запрета»; плановые (11 — размещение, 12, 13) — документ датируется моментом прогона, плановое
время — в будущем через `ПланНачало`; M1 работает Пн–Сб 06–22 без
календаря, поэтому интервалы E1 входят в его рабочее время. Не помещается → `ПРОПУСК;M`.

### 4.4. Документы блока

Требование — по образцу `ТестыДокументов.НовоеТребованиеСценария`:
