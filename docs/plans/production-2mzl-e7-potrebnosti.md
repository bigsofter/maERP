# Бриф: потребности производства (E7)

## Задача

Проведённый заказ клиента на производство (E6) формирует потребность в материалах, а закупочный контур её
закрывает: заказ поставщику — «заказано», поступление товаров и услуг — «пришло», возврат поставщику сторнирует
«пришло». Новый регистр накопления остатков `ПотребностиПроизводства` — первая опора стадий E8 и автовыпуска E9.
Основание — `docs/plans/production-2mzl.md`, этап E7 и обязательства разделов E5 и E6.

Что появляется:

- **регистр накопления** `ПотребностиПроизводства` (остатки): измерения `Заказ` (`ДокументСсылка.ЗаказПокупателя`),
  `Продукция`, `Материал` (`СправочникСсылка.Номенклатура`), `Характеристика`; ресурсы `Потребность`, `Заказано`,
  `Пришло`, `ИзОстатка` (`DefinedType.Количество`, базовые единицы). `ИзОстатка` в E7 только объявляется — пишет его
  автовыпуск E9. Новый объект, новые uuid (у drissotex аналога нет). Права чтения — ролям с доступом к разделу
  «Производство» и к закупкам; запись — только движениями документов (привилегированное проведение);
- **заказ клиента на производство** пишет `Потребность` из базового `Количество` материалов (обязательство E5), по
  продукции строки (`КодСтрокиПродукции` → номенклатура строки товаров). Только при
  `Документы.ЗаказПокупателя.ЗаказПроводится(ВидОперации)` (обязательство E6). Первые движения заказа:
  `registerRecords` в `.mdo`, `ОбработкаПроведения` из страховки становится формированием движений — регистрация
  карт остаётся в `ПередЗаписью`, блокировки регистра — **после** блокировки карт продукции (обязательство E6);
- **заказ поставщику** пишет `Заказано`, если его основание — проведённый заказ клиента на производство. Продукция
  строки материала — новая скрытая колонка `Продукция` в `ТЧТовары` заказа поставщику (включается через «Ещё»); при
  пустой колонке количество распределяется по остатку потребности заказа клиента в порядке строк продукции. Материал,
  которого нет в потребности, движения не даёт;
- **кнопка «Заполнить по потребности»** над табличной частью заказа поставщику: дефицит `Потребность − Заказано` из
  регистра (не из текущей техкарты), с колонкой `Продукция`. Ввод заказа поставщику **на основании заказа клиента на
  производство** заполняет строки так же; без сформированной потребности (заказ не проведён) — отказ с внятным
  сообщением (требование 3.6). Ввод на основании **продажи** — как сейчас (состав товаров);
- **поступление товаров и услуг** пишет `Пришло`: тип основания расширяется `ДокументСсылка.ЗаказПокупателя`
  (ввод на основании заказа клиента на производство — по остатку `Заказано − Пришло`, иначе по потребности), а
  при основании «заказ поставщику» заказ клиента берётся из основания заказа поставщику. Продукция — тем же
  распределением, что у заказа поставщику. Колонка «Заказ клиента» в списке поступлений (запрос списка восстановлен
  в 2.0.15.1 — после правки прогнать `listcheck.py`);
- **возврат поставщику** сторнирует `Пришло` по заказу клиента поступления-основания;
- **блокировка** регистра — процедура в общем модуле `УправляемыеБлокировки` по образцу `ТоварыВНаличии`;
- **отчёт** `ПотребностиПроизводства` (СКД): группировки заказ → продукция → материал, четыре ресурса, дефицит
  (`Потребность − Заказано`), «к заказу» и флаг «только дефицит»; в разделе «Производство»;
- **сценарий уровня 3** `ПотребностиПроизводства` и строки в `docs/TESTING.md`, `docs/TESTS.xlsx`.

## Почему сейчас

E8 считает стадии «Заказ поставщику» и «Восполнение потребности» по этому регистру, E9 списывает партии под заказ и
пишет `ИзОстатка`. Без регистра заказ на производство и закупка не связаны ничем, кроме ссылки основания.

## Границы (чего НЕ делать)

- **Стадии** (E8) и **автовыпуск / `ИзОстатка`** (E9) — не делать; ресурс `ИзОстатка` только объявить.
- **Исторические заказы** клиентов, заказы поставщику и поступления **не перепроводить**, обработчика обновления
  нет: регистр наполняется новыми проведениями.
- **Продажи** не пишут потребность; ввод заказа поставщику на основании продажи и заполнение поступления по
  заказу поставщику для обычной закупки — без изменений поведения.
- **Регистрация карт в `ПередЗаписью` заказа** (E6) — не трогать; ECommerce-форму не менять.
- **«Техкарта» строки не использовать** для решений — только `ТЧМатериалы` (обязательство E6).
- Попутно найденное — в `docs/TECHDEBT.md`, не в этот коммит.

## Уроки последних сборок — обязательны

- **Проверка заполнения у проводимого документа** в форме — только при проведении (справка 8.5, E6): у заказа
  поставщику и поступления уже `posting = Allow`, новые обязательные реквизиты проверять с учётом этого.
- **Отказ записи внутри транзакции сценария** портит её: проверки отказов — через экспортные процедуры без
  записи, настоящий отказ — последним шагом (E5, E6).
- **Вложенная транзакция**: `ОтменитьТранзакцию` внутри вложенной отменяет внешнюю — не бросать ожидаемые отказы
  из-под `НачатьТранзакцию` (E6, находка N1).
- **Порядок блокировок** один для всех путей: карты продукции → регистры заказа (E6).
- **Привилегированный режим** не заменяет проверку права; `ПравоДоступа` без пользователя в привилегированном режиме
  не проверяет права (E6, находка безопасности).
- **Элементы Form.form копировать с работающего образца целиком**; реквизиты формы и элементы — разные
  пространства id (forms-001); **кнопка внутри таблицы динамического списка на закладке роняет клиент 8.5**
  (forms-009) — колонка «Заказ клиента» и команды списка поступлений ставить с этим уроком; видимость по опции — на
  сервере (bsl-009); запрос динамического списка — сверка `listcheck.py` (урок затёртого запроса поступлений).
- **Новый регистр верхнего уровня** — инкрементальное обновление `build/ib` падает, нужно **полное** (E4).
- **Смок форму не рисует** — в отчёте явный список «что посмотреть глазами».
- **Проверка на базе — сам**: копия `build/ib` (`cp build/ib/1Cv8.1CD build/ib-check/`), `scripts/smoke.sh` и
  `scripts/doctests.sh` на копии; шаг 1б смока ложно срабатывает — шаг 2 запускать отдельно.
- **Оркестрация**: обязательные гейты — Codex; при его лимите — субагенты Claude, не OpenCode (`.ai/README.md`,
  «Цепочка бэкендов»). Зависший прогон снимать по PID своего процесса.

## Вопросы владельцу

1. **Размер этапа.** E7 крупный (регистр, четыре документа, отчёт). Сдать одной сборкой или двумя: E7а — регистр,
   потребность заказа, заказано и «Заполнить по потребности»; E7б — пришло (поступление, основание, колонка списка),
   возврат и отчёт? Предлагается — двумя, каждая со своей версией и проверкой на базе.
2. **Сверх потребности.** Заказано или пришло больше потребности (перезаказ, поставка с запасом) — писать фактическое
   количество (дефицит уходит в минус, излишек виден в отчёте) или ограничивать потребностью? Предлагается — фактическое.
3. **Закупка под непроведённый или не производственный заказ.** Заказ поставщику / поступление, основание которого —
   продажа или непроведённый заказ на производство, движений потребности не пишет (регистр не уходит в «заказано без
   потребности»). Так и оставить? Предлагается — да.
4. **Порядок распределения без колонки «Продукция».** По остатку потребности в порядке строк продукции заказа клиента
   (как в плане волны) — или пропорционально потребности? Предлагается — в порядке строк.
