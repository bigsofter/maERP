# Сборка 2.0.17.4: потребность торговой точки — документ, статусы, регистр, перемещение (`retail-store-needs`)

Волна 2 мастер-плана `docs/plans/retail-chain.md`. Волна делится на две сборки:

- **2.1 (эта, 2.0.17.4)** — документ «Потребность торговой точки», статусы и история статусов, регистр
  потребностей, связь с перемещением (отгружено/получено), склад снабжения у места хранения, роль точки.
- **2.2 (2.0.17.5, свой план)** — рабочее место «Потребности точек» для склада снабжения (очередь, построчное
  принятие, «Создать перемещение» по нескольким), рекомендации при формировании («Заполнить по анализу»), строка
  «Пополнение точек» в АРМ закупок, оповещения и получатели по складу, история системных сообщений.

Объекты, переносимые из базы клиента FlyCDI, создаются с его uuid (CLAUDE.md, «Именование»; uuid — выгрузка клиента
`build/flycdi/cf`, приложение А мастер-плана).

### Регистр накопления `ПотребностиТорговыхТочек` (остатков, по образцу `ПотребностиПроизводства`)

- Измерения: `Точка`, `СкладСнабжения` (`МестаХранения`), `Потребность` (документ), `КодСтроки` (строки
  потребности), `Отгрузка` (`ДокументСсылка.ПеремещениеТоваров` — списание; у движений потребности пусто),
  `КодСтрокиОтгрузки` (`КодСтроки` строки списания; у движений потребности 0), `Номенклатура`, `Характеристика`,
  `Серия`. Ресурсы (единицы хранения): `Запрошено`, `Принято`, `Отгружено`, `Получено` (не
  `Потребность` — имя занято измерением).
- Движения потребности (приход): статус «Отправлена» — `Запрошено = Количество`; «Принята» — ещё `Принято =
  КоличествоПринято`; «Закрыта» — `Принято = Мин(КоличествоПринято, отгружено по строке)` (остаток к отгрузке
  снимается); «Черновик» и «Отклонена» — движений нет. Проведение пишет набор всегда (пустой стирает прежние).
- Движения перемещения (приход): списание (`ПеремещениеСписание`) — `Отгружено` с `Отгрузка` = само списание и
  `КодСтрокиОтгрузки` = код его строки, оприходование (`ПеремещениеОприходование`) — `Получено` с `Отгрузка` = его
  основание и `КодСтрокиОтгрузки` = код соответствующей строки основания (у оприходования, введённого на
  основании, `КодСтроки` строк совпадает с основанием — ТЧ копируется целиком); строка оприходования с
  потребностью проводится, только если основание — проведённое списание (иначе отказ): «в пути» общего склада
  StockEnCoursDeRoute не различает перемещения, а регистр потребностей — различает.
- «К отгрузке» = Принято − Отгружено; «в пути» = Отгружено − Получено.
- **Баланс строки** — `Отгружено ≤ Принято` по строке потребности (Потребность + КодСтроки) и `Получено ≤
  Отгружено` по строке потребности, отгрузке, строке отгрузки **и серии** (Потребность + КодСтроки + Отгрузка +
  КодСтрокиОтгрузки + Серия): одно списание и одну его строку не получают дважды, строку и серию, которых в
  списании нет, не получают; перепроведение списания с другой серией уже полученного товара даёт `Получено` по
  прежней серии больше `Отгружено` — нарушение.
- **Оприходование соответствует строкам списания с потребностью**: для каждой строки основания-списания **с
  потребностью** строка оприходования с тем же `КодСтроки` (если есть) несёт ту же потребность и
  `КодСтрокиПотребности`, тот же товар, характеристику и серию (связь не снимается, строка не подменяется), а
  строка оприходования без потребности не может иметь `КодСтроки` такой строки основания; количество по строке
  с потребностью — баланс регистра по `КодСтрокиОтгрузки`. Строки основания **без** потребности — обычный «в пути»
  перемещений, как сейчас (регистр потребностей их не учитывает). **Каждая** строка оприходования такого списания
  (основание со строками потребности) — строка основания по `КодСтроки` с тем же товаром, характеристикой, серией и
  той же связью с потребностью (или её отсутствием): новая строка с другим кодом — нарушение (иначе связь снимается
  заменой строки: товар пришёл на точку, а потребность показывает его в пути). Иначе отказ с перечнем строк.
- **Проведённое перемещение с движениями потребностей не меняет основание и связи**: если у перемещения в базе
  есть движения регистра потребностей, перепроведение со сменой `Основание`, `ХозяйственнаяОперация`, складов или
  `Потребность`/`КодСтрокиПотребности`/товара/серии строк с движениями — отказ («отмените проведение»); количество
  меняется (баланс). Отмена проведения — разрешена, она снимает и товарные движения, и исполнение потребности
  вместе.
- **Удаление**: `ПередУдалением` перемещения и потребности — отказ, если у документа есть движения регистра
  потребностей или на него ссылаются движения других документов (`Отгрузка` = это списание, `Потребность` = эта
  потребность): удаление без отмены проведения обходило бы баланс (tiny1C bsl-024 — `Удалить()` не вызывает
  проведение и отмену). Загрузка обменом — как везде, без проверки.
  Проверяется после записи движений **любым** документом, меняющим строки: проведение и отмена проведения
  перемещения (в том числе уменьшение количества, удаление строки или связи, смена потребности) и проведение
  потребности (закрытие, правка принятого) — общая процедура регистра `ПроверитьБалансСтрок(Ключи, Отказ)` по
  ключам старых и новых движений документа, с перечнем нарушенных строк. Отмена проведения перемещения: в
  `ОбработкаУдаленияПроведения` набор регистра очищается и записывается явно, затем проверка (отмена списания при
  проведённом оприходовании — отказ).
- **Блокировки**: перед чтением и записью — исключительная управляемая блокировка регистра по `Потребность` всех
  затронутых потребностей (старые и новые движения), общей функцией `УправляемыеБлокировки` — и в перемещении, и в
  проведении потребности (закрытие читает отгруженное под той же блокировкой, что и отгрузка).

### `ПеремещениеТоваров`

- Шапка: `Перевозчик` (`Контрагенты`, uuid клиента 8d8baf3f-…).
- ТЧ `ТЧТовары`: `Потребность` (`ДокументСсылка.ПотребностьТорговойТочки`, uuid клиента колонки `Заказ` ef830f36-…;
  имя у нас — `Потребность`, данные по uuid сохраняются) и `КодСтрокиПотребности` (новая). Для баз других клиентов —
  новые колонки ТЧ: реструктуризация таблицы перемещений при обновлении (оценить на большой базе — регресс).
- Оприходование, введённое на основании списания (`ОбработкаЗаполнения`), копирует ТЧ целиком — колонки
  потребности переходят сами.
- **Коды строк — только там, где на них опирается приёмка потребностей**: требование действует для перемещений,
  у которых строки (или строки основания) ссылаются на потребность. Списание по потребности (новый ввод на
  основании) получает уникальные коды при заполнении; `ПередЗаписью` списания **со строками потребности**
  дозаполняет нулевые коды (`РаботаСДокументамиКлиентСервер.ПолучитьСледующийКодСтроки`) и отказывает при повторе
  кода у строки с потребностью или совпадении её кода с другой строкой; оприходование такого списания — коды
  основания (сверка построчная, см. выше). Перемещения без потребностей — без изменений: исторические документы с
  повторяющимися кодами (разбиение по сериям `СерииИРазмещение.ОбъединитьТоварыССериями` сохраняет код исходной
  строки) записываются как сейчас. Коды строк потребности — уникальны (`ПередЗаписью` потребности).
- Проведение: регистр `ПотребностиТорговыхТочек` в составе движений; строки с потребностью — `Отгружено`/`Получено`.
  Баланс — см. регистр. **Маршрут**: строка с потребностью проводится, только если склады перемещения совпадают с
  потребностью — у списания `МестоХранения` = склад снабжения потребности и `МестоХраненияОприходование` = точка, у
  оприходования `МестоХраненияОприходование` = точка; **товар**: номенклатура и характеристика строки перемещения =
  строке потребности (по `КодСтрокиПотребности`), серия — та же, если в потребности задана; строки потребности с
  таким кодом нет — нарушение. Иначе отказ с перечнем строк (форма позволяет сменить склад и товар после ввода на
  основании).
- **Проведённое перемещение со связью с потребностью записывается только проведением**: обычная запись (без
  проведения) проведённого документа, у которого строки сейчас или в базе (свежие данные) ссылаются на потребность,
  — отказ в `ПередЗаписью`: иначе связь меняется без пересчёта движений.
- **Закрытая потребность заморожена по отгрузке**: проведение или отмена проведения перемещения, меняющие
  `Отгружено` по строкам потребности в статусе «Закрыта» или «Отклонена», — отказ («потребность закрыта»); `Получено`
  по закрытой меняется (оприходование того, что было в пути).
- Ввод на основании потребности: списание, склад списания — склад снабжения, оприходования — точка, строки —
  остаток к отгрузке (Принято − Отгружено) по каждой строке потребности; только для статуса «Принята». Тип
  реквизита `Основание` перемещения дополняется `ДокументСсылка.ПотребностьТорговойТочки` (составной тип —
  расширение, данные не теряются), ветка `ОбработкаЗаполнения` для потребности — до прочих (присваивание
  `Основание = ДанныеЗаполнения` в начале процедуры с новым типом корректно).

### Регистр сведений `ИсторияСтатусовПотребностей`

- Периодический (секунда), измерение `Потребность`; ресурсы `Статус`, `Пользователь`. Запись — в привилегированном
  режиме (как история статусов `ЗаказПокупателя`, `ObjectModule.bsl:238–246`): у роли точки на историю только
  чтение; проведение потребности и перемещения пишут регистр потребностей тоже в привилегированном режиме, как прочие
  проведения. Период новой записи — не
  раньше последней записи по потребности плюс секунда (как `РаботаСДокументами.ПериодЗаписиСтатусаЗаказа`: два
  перехода в одну секунду не падают на дубле ключа). Пишется в `ПриЗаписи`
  документа при смене статуса (прежний статус — `ДополнительныеСвойства` из `ПередЗаписью`). Показ — в форме
  документа (список «кто и когда»).

### Права

- Новая роль `ПотребностиТорговыхТочек` (точка): документ — чтение, добавление, изменение, проведение (в статусах
  «Черновик» и «Отправлена»); регистр и история — чтение.
- Склад снабжения: роль `Кладовщик` получает права на документ (чтение, изменение, проведение, **отмена
  проведения** — для возврата в черновик и отклонения), регистр, историю (у роли `setForNewObjects = false`, права
  нового документа задаются явно).
- **Получение точкой**: общих прав на проведение перемещений роль точки не получает (у `PDV` на перемещение нет
  проведения — так и остаётся). Точка получает товар командой «Получить» формы потребности: серверная процедура
  `Документы.ПотребностьТорговойТочки.ПолучитьОтгрузку(Потребность, Списание)` в привилегированном режиме проводит
  оприходование на основании проведённого списания этой потребности — **существующий черновик** оприходования,
  который форма перемещения уже записывает после проведения списания (`ФормаДокумента.ПослеЗаписиНаСервере`), а если
  его нет — новый на основании. Дата оприходования — момент получения (`ТекущаяДатаСеанса()`), а не дата
  черновика, созданного при отгрузке. Строки **строятся заново из проведённого списания**, а не берутся из
  черновика (его строки точка могла изменить — `PDV` может править перемещения): строки списания с потребностью —
  неполученный остаток по регистру (`КодСтрокиОтгрузки`, нулевые не добавляются), строки без потребности — как в
  списании (смешанное списание получает и их, как сейчас); черновик используется только как документ (ссылка и
  номер), шапка — из списания (склады, организация), дата — момент получения. Вся операция — в транзакции под
  **исключительной блокировкой документа-списания** (`Документ.ПеремещениеТоваров`, Ссылка = списание), взятой
  первой: проверка «проведённого оприходования ещё нет», построение строк и проведение. Ту же блокировку основания
  берёт проведение **любого** оприходования с основанием-списанием — в `ПередЗаписью` перемещения в режиме
  проведения (до того, как платформа очистит прежние движения и заблокирует итоги регистров, tiny1C bsl-029), — два
  получения одного списания выполняются по очереди. Порядок блокировок одинаков: команда сначала
  блокирует найденный черновик оприходования (если есть), затем списание — как обычная запись черновика (неявная
  блокировка записываемого объекта, затем основание в проведении). Повторное получение строк **без** потребности
  обычным оприходованием (не командой) — существующая модель «в пути» (см. «Вне сборки»), сборкой не меняется:
  команда не получает списание повторно, ручное оприходование склада — как сейчас. После блокировки черновик
  **перечитывается** и используется, только если он по-прежнему оприходование (`ПеремещениеОприходование`) с
  основанием — этим списанием, не проведён и не помечен на удаление; иначе команда создаёт новое оприходование
  (найденный документ не трогает). Списание, у которого уже есть
  проведённое оприходование, командой не получается повторно — для частичных и повторных получений склад
  оформляет оприходование сам. — только своей точки (настройка
  `ТочкаПотребностей`) или доверенным, строки — неполученный остаток строк списания по регистру (`КодСтрокиОтгрузки`),
  склад оприходования — точка потребности. Произвольного оприходования точка не создаёт.
- Статус и движения не расходятся: смена статуса на «Отправлена», «Принята», «Отклонена», «Закрыта» — только
  проведением; **возврат в «Черновик»** — командой «Вернуть в черновик» отменой проведения (`Записать(ОтменаПроведения)`
  со статусом «Черновик»: движения снимаются, дальше черновик пишется обычной записью); документ, проведённый в
  базе (свежие данные), обычной записью не записывается — отказ (иначе возврат обычной записью оставил бы
  движения). Роль точки получает право отмены проведения потребности — сервер разрешает отмену только с новым
  статусом «Черновик» (из «Отправлена», своей точки или доверенным) и «Отклонена» (доверенным); отмена проведения — только в статусах «Черновик» и «Отклонена»
  (у них нет движений), иначе отказ «смените статус»; пометка удаления проведённого — через отмену проведения.
- **Доверенные** (пишут потребности любых точек и переходы склада): роль `Кладовщик`, `Администратор` и
  пользователи, которым `НастройкиПользователей.ЭтоАдминистраторНастроек()` разрешает менять настройки доступа
  (сейчас — ещё роль `Руководитель`): кто может назначить себе точку, тому граница по точке ничего не даёт.
- **Свои документы точки**: пользователь, не входящий в доверенных, записывает потребность, только если её
  точка — его **точка потребностей**: новая предопределённая настройка `ТочкаПотребностей` (`МестаХранения`) в группе
  «Настройки доступа» плана видов `ВидыНастроекПользователей` — её меняет только администратор
  (`НастройкиПользователей.ИзменяютсяПраваДоступа`), в отличие от бытовой настройки «Склад», которую пользователь
  меняет себе сам. И у записанного документа (свежие данные) точка была тоже его; иначе отказ. Настройка не
  задана — пользователь без роли склада потребности не записывает. `ОбработкаЗаполнения` ставит точкой эту
  настройку. Ограничение записи, не чтения: RLS в конфигурации не
  используется, чужие потребности точка видит в списке.
- Переходы статусов проверяются **на сервере** (`ПередЗаписью`), не только доступностью команд: «Черновик →
  Отправлена» и правка строк в «Черновике» — точка своего документа (см. выше) или склад; «Отправлена → Принята/Отклонена», «Принята →
  Закрыта», правка `КоличествоПринято` — только **доверенные** (см. выше; роли пользователя ИБ, как
  `КонтрольЦенПродажи.ДопускПродажиНижеМинимальной`, и `ЭтоАдминистраторНастроек`); назад в «Черновик» — из «Отправлена»
  автором или складом. Принятая потребность меняется только складом (закрытие); строки принятой — не правятся.
- `Rights.rights` всех ролей, у которых есть права на `Document.ПеремещениеТоваров`, — без изменений; новые объекты
  в ролях — по образцу `ПотребностиПроизводства`/`ЗаказПоставщику`.

### Подсистема

- «Склад» (или «Закупки» — по месту `ПеремещениеТоваров` в `CommandInterface`): список потребностей; создание —
  видимое (точка создаёт документ сама). `menucheck.py`.

## 2. Тесты (`ТестыДокументов`, сценарий `ПотребностьТорговойТочки`)

Каждый сценарий выполняется в своей транзакции с откатом: **настоящий** отказ — только последним шагом сценария,
поэтому каждый запрет, подключённый к записи, получает отдельный короткий сценарий с настоящим отказом:
`ПотребностьТорговойТочки` (основной путь, отказ — отмена списания при проведённом оприходовании),
`ПотребностьОтгрузкаСверхПринятого` (проведение списания сверх принятого), `ПотребностьМаршрут` (списание на
другой склад оприходования), `ПотребностьЗаписьПроведенной` (обычная запись проведённой потребности),
`ПотребностьУдаление` (`Удалить()` проведённого списания), `ПотребностьПолучитьДважды` («Получить» по списанию с
проведённым оприходованием), `ПотребностьПодменаСтроки` (оприходование со строкой другого кода),
`ПотребностьСменаСвязей` (перепроведение оприходования со снятой связью), `ПотребностьПовторКода` (списание с
повтором кода строки потребности), `ПотребностьОтгрузкаЗакрытой` (списание по закрытой потребности). Основной путь
получает товар командой «Получить» (`ПолучитьОтгрузку`), а не прямым проведением оприходования. Функции нарушений
проверяются в основном сценарии дополнительно.

1. Точка и склад снабжения, закупка на склад снабжения; потребность А из двух строк (10 и 5): «Черновик» — движений
   нет; «Отправлена» — `Запрошено` 10/5; «Принята» с принятием 8 и 0 (вторая отклонена) — `Принято` 8/0; история —
   две записи; переход «Черновик → Принята» — текст ошибки (функция `ТекстОшибкиПерехода`).
2. Списание по А на основании — строка 8 (остаток к отгрузке), количество 6 → `Отгружено` 6, состояние «Частично
   отгружена»; перепроведение того же списания с 4 — `Отгружено` 4 (ключи прежних движений собраны), обратно 6;
   маршрут со сменённым складом и строка с другим товаром — нарушения (функция `НарушенияМаршрута`); второе
   списание 3 сверх принятого — нарушение (функция `НарушенияБаланса`).
3. Оприходование по А на основании списания — `Получено` 6 (по отгрузке-списанию); второе оприходование того же
   списания на 6 — нарушение (функция, `Получено` по отгрузке > `Отгружено`).
4. Потребность Б: принято 5, отгружено 3, «Закрыта» — `Принято` 3, к отгрузке 0; изменение отгрузки по Б —
   нарушение заморозки (функция).
5. Последний шаг — настоящий отказ: отмена проведения списания по А (потребность не закрыта) при проведённом
   оприходовании — `Получено` 6 > `Отгружено` 0 по отгрузке; путь `ОбработкаУдаленияПроведения` с явной записью
   набора и проверкой баланса (вызов контроля после записи движений).
6. Права (своя точка — настройка «Точка потребностей», роль склада) — живая проверка на копии базы
   (`live-role-check`), прогон — под администратором.

Человек: точка создаёт и отправляет потребность; склад принимает часть, отгружает перемещением, точка оприходует;
состояние в списке меняется.

## 3. Порядок и проверки

1. Метаданные (uuid клиента), формы, модули; «Что нового» 2.0.17.4 на 4 языках; версия.
2. `lint.sh`, `refcheck.py`, `listcheck.py`, `colfont.py`, `menucheck.py`; `ib-sync`; смок; тесты.
3. `ai-review` (обязателен) → `ai-database` (новый регистр, новые колонки перемещения) → `ai-security` (роль,
   переходы статусов) → `ai-final-check --db` → отчёт.

## 4. Вне сборки

- «В пути» товарного учёта (`ТоварыВНаличии`, склад StockEnCoursDeRoute) — общий пул всех перемещений: оприходование
  без основания (ручное) расходует его независимо от списаний. Это существующая модель перемещений; учёт исполнения
  потребности такие оприходования не засчитывает (точка видит товар «в пути» до оприходования по списанию).
  Обязательное основание у всех оприходований меняет поведение для всех клиентов — TECHDEBT (ревью плана, круг 6),
  решение владельца.

## 5. Риски

- Новые колонки `ПеремещениеТоваров.ТЧТовары` — реструктуризация таблицы перемещений у всех клиентов при
  обновлении (одна колонка ссылки и одна числовая, без пересчёта данных).
- Состояние исполнения не хранится — вычисляется запросом к регистру; список с отбором по состоянию — по
  подзапросу остатков (на больших объёмах — индекс по измерению `Потребность`).

## Статус ревью плана

- Круг 1 — reject: ресурс `Запрошено` (имя `Потребность` занято измерением); баланс строки после любой записи
  движений, в том числе отмены проведения перемещения; общая блокировка по потребности и в закрытии; маршрут
  перемещения = склады потребности; не «Черновик» — только проведением, отмена проведения — только без движений;
  период истории — +секунда; настоящий отказ в тесте — последним.
- Круг 2 — reject: строка перемещения соответствует строке потребности по товару (номенклатура, характеристика,
  серия); отгрузка по закрытой/отклонённой потребности заморожена; история и движения — в привилегированном режиме;
  тест — перепроведение и отмена настоящими записями, отказ отмены — последним.
- Круг 3 — reject (P0): точка пишет только свои потребности (склад пользователя, и у записанного документа);
  проведённое перемещение со связью — только проведением; сценарий теста упорядочен (перепроведение до закрытия,
  отказ отмены — последним).
- Круг 4 — reject (P0): граница «свои потребности» — настройка доступа `ТочкаПотребностей` (меняет только
  администратор), а не бытовой «Склад»; измерение `Отгрузка` — получено не больше отгруженного по каждому списанию,
  оприходование только на основании списания; тест — отказ отмены проведения по незакрытой потребности (баланс).
- Круг 5 — reject: баланс получения — по серии; оприходование списания с потребностями соответствует ему построчно
  (связь не снимается, товар и серия не подменяются).
- Круг 6 — reject: измерение `КодСтрокиОтгрузки` — получение построчно по строке списания; оприходование без
  основания и связи — существующий общий «в пути», вне сборки (TECHDEBT, решение владельца).
- Круг 7 — reject (P0): доверенные — и те, кто меняет настройки доступа (`ЭтоАдминистраторНастроек`, роль
  `Руководитель`); смена статуса — только проведением, проведённый документ обычной записью не пишется; получение
  точкой — командой «Получить» (привилегированное оприходование по списанию своей потребности), без общих прав на
  проведение перемещений.
- Круг 8 — reject (P0): удаление документов с движениями или ссылками регистра — отказ; соответствие оприходования —
  только строкам списания с потребностью; переходы склада — тот же круг доверенных.
- Круг 9 — reject: серия — в ключе баланса получения (подмена серии перепроведением списания — нарушение); «Получить»
  проводит черновик оприходования, который уже создаёт форма списания.
- Круг 10 — reject: «Получить» ставит дату получения; строки без потребности в черновике сохраняются, строки с
  потребностью — по неполученному остатку.
- Круг 11 — reject (P0): «Получить» строит строки оприходования из проведённого списания, черновику не доверяет.
- Круг 12 — reject (P0): блокировка списания — на всё получение и в проведении любого оприходования с этим
  основанием; тип `Основание` перемещения дополняется потребностью; настоящие отказы — отдельными сценариями.
- Круг 13 — reject: порядок блокировок команды = порядку обычной записи (черновик, затем списание); повторное
  получение строк без потребности ручным оприходованием — существующая модель, вне сборки (P1 отклонено с причиной);
  возврат в черновик — отменой проведения, роль точки получает отмену проведения с серверной проверкой.
- Круг 14 — reject (P0): черновик после блокировки перечитывается и проверяется (операция, основание, не проведён,
  не помечен), иначе новый документ; блокировка основания — в `ПередЗаписью` (до очистки движений).
- Круг 15 — reject: оприходование списания со строками потребности — каждая его строка соответствует строке
  основания по коду (замена строки не снимает связь).
- Круг 16 — reject: коды строк перемещения и потребности — обязательные и уникальные (дозаполнение и отказ на
  повторах), на них опирается построчная приёмка.
- Круг 17 — reject: уникальность кодов — только у перемещений со строками потребности; исторические перемещения
  без потребностей не затрагиваются.
- Круг 18 — reject: перемещение с движениями потребностей не меняет основание, операцию, склады и связи строк при
  перепроведении (только отмена проведения); `Кладовщик` — право отмены проведения потребности.
- Круг 19 — approve_with_changes (P2: настоящие отказы по каждому запрету, «Получить» в основном пути) — внесено в
  раздел «Тесты».

## Отклонения реализации

- Формы документа — автоматические (список и документ) с командами «Отправить», «Принять», «Отклонить», «Закрыть
  потребность», «Вернуть в черновик», «Получить отгрузку» и «История статусов» (список истории с отбором).
  Состояние исполнения (частично отгружена / отгружена / получена) показывает рабочее место склада сборки 2.2
  (`СостояниеИсполнения`), в автоформах его нет.
- У принятой и закрытой потребности заморожены точка, склад снабжения и строки (код, товар, характеристика, серия,
  запрошенное количество) — меняются только принятые количества и статус (ревью кода, круг 1).
- «Получить отгрузку» берёт первое проведённое списание без проведённого оприходования; частичное повторное
  получение оформляет склад.
