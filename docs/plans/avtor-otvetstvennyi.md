# «Автор» → «Ответственный» (сборка 2.0.15.28)

Решение владельца 2026-09-14: «Ответственный и автор дублируют друг друга. Надо оставить только один и весь код
переделать на одно оставшееся реквизит» — оставить **Ответственный**.

## Что есть сейчас (проверено 2026-09-14)

- Общий реквизит `АвторОбщий` (синоним «Автор», тип `DefinedType.Пользователь`, uuid `5d11664e-…`), автоиспользование
  по умолчанию «Использовать» (в `.mdo` не записано — значение EDT по умолчанию), явно выключен у `Номенклатура`
  и `Контрагенты`. Проба на копии `build/ib` 2.0.15.27 (временный сценарий, в репозиторий не попал): реквизит есть у
  **172 объектов** (85 явно, 87 по автоиспользованию; из них 3 — журналы и последовательность); у **47** есть свой
  реквизит `Ответственный` типа «Пользователь», у **2** (`МестаХранения`, `ТоварныеГруппы`) `Ответственный` —
  «Физическое лицо», у **120** `Ответственного` нет. В тестовой базе 888 записей, **заполненный автор — 0**.
- У drissotex общего реквизита нет (`docs/drissotex-analysis/common-service-hr-acc.md`): данные клиента его не несут.
- Код ставит автора в трёх местах, больше нигде (в том числе по истории git):
  - `Catalogs/ПроектыКонфигураций/Forms/ФормаЭлемента/Module.bsl` и `Catalogs/ШаблоныКонфигураций/Forms/ФормаЭлемента/Module.bsl`:
    `ПриСозданииНаСервере` — автор = текущий пользователь, если пуст. У этих справочников `Ответственного` нет.
  - `DataProcessors/ЛичныйКабинетПартнера/Forms/ФормаНоменклатура/Module.bsl`: заказ из ЛКП — автор = текущий
    пользователь, `Ответственный` = ответственный контрагента.
- Показывается: поле «Автор» на формах документов `ЗаказПокупателя`, `КоммерческоеПредложение`, `ЗаявкаНаПоискТовара`,
  на формах элементов `ПроектыКонфигураций` и `ШаблоныКонфигураций`; скрытая колонка и поле запроса в списке
  `ЗаказПокупателя`; поле набора данных в списке `РеализацияТоваровУслуг`. Право `View` в роли `ЛичныйКабинет`.

Вывод: в известных базах значений нет, но базы клиентов maERP, где создавались проекты и шаблоны конфигураций или
заказы из ЛКП, могут их содержать. Удаление общего реквизита одним релизом стёрло бы их при реструктуризации раньше,
чем отработает обработчик обновления.

## Решение: два шага

### Шаг 1 — сборка 2.0.15.28 (эта работа)

1. **Переименование без потери данных.** `АвторОбщий` → `УдалитьАвторОбщий`, синоним «(не используется) Автор» на
   четырёх языках, uuid и состав не меняются. Ссылки в `Configuration.mdo` и `Roles/ЛичныйКабинет/Rights.rights`
   переименовываются, право `View` роли `ЛичныйКабинет` остаётся на переименованном объекте до шага 2.
2. **`Ответственный` у `ПроектыКонфигураций` и `ШаблоныКонфигураций`.** Новый реквизит `Ответственный`
   (`DefinedType.Пользователь`, новые uuid — это объекты maERP, у drissotex их нет). Реструктуризация двух маленьких
   справочников подсистемы «МультиКонфигурация».
3. **Код на «Ответственный».**
   - Формы элементов проектов и шаблонов: при создании `Ответственный` = текущий пользователь, если пуст; поле
     «Автор» заменяется полем «Ответственный» с тем же местом на форме.
   - ЛКП: строка про автора удаляется; `Ответственный` заказа по-прежнему ответственный контрагента.
4. **Формы и списки.** Поле «Автор» убирается с форм `ЗаказПокупателя`, `КоммерческоеПредложение`,
   `ЗаявкаНаПоискТовара`; колонка и поле запроса — из списка `ЗаказПокупателя`; поле набора — из списка
   `РеализацияТоваровУслуг`. `scripts/listcheck.py` и `scripts/queryfields.py` — без новых расхождений.
5. **Обработчик обновления 2.0.15.28** `ОбновлениеПрограммыОбработчики.ПеренестиАвтораВОтветственного`
   (монопольно, как остальные):
   - по составу `УдалитьАвторОбщий` (явно или по автоиспользованию) берутся объекты, у которых есть реквизит
     `Ответственный` с типом, содержащим `СправочникСсылка.Пользователи`: 47 объектов + два справочника из п. 2;
   - запросом по каждой таблице выбираются ссылки, где автор заполнен, а `Ответственный` пуст; объект получает
     `Ответственный` = автор и пишется с `ОбменДанными.Загрузка = Истина` (как `ЗаполнитьВидОперацииЗаказовПокупателей`:
     без `ПередЗаписью`, пересчёта итогов, истории статусов; проведённый документ остаётся проведённым, движения не
     трогаются);
   - где `Ответственный` уже заполнен, он не меняется, автор не переносится (такие расхождения пишутся в журнал
     количеством по объекту);
   - объекты с `Ответственным` другого типа (`МестаХранения`, `ТоварныеГруппы` — «Физическое лицо») и без
     `Ответственного` (120 объектов) не трогаются: значения автора остаются в `УдалитьАвторОбщий` до шага 2, число
     таких заполненных записей пишется в журнал;
   - идемпотентен: повтор выбирает только записи с пустым `Ответственным`; каждый объект пишется отдельно, падение на
     середине оставляет обработанные записи обработанными;
   - в журнал пишутся не только количества, но и сами пары «объект — автор» там, где автор не перенесён (заполненный
     другой `Ответственный`, другой тип или его нет): решение шага 2 принимается по этим записям.
6. **Запись в режиме загрузки не трогает чужие документы** (находка ревью плана, P1). Подписка
   `ПослеОтменыПроведенияДокументаОплаты` (событие «ПриЗаписи» у ПКО, РКО, поступления и списания безналичных) не
   проверяет `ОбменДанными.Загрузка` и у непроведённой оплаты перепроводит связанные проведённые налоговые накладные.
   Добавляю ранний выход по `Источник.ОбменДанными.Загрузка`, как у соседних подписок `ПользователиПередЗаписью` и
   `ПослеЗаписиСнятиеРазрешенияНаРедактирование` (запись в режиме загрузки — это перенос данных, а не хозяйственное
   действие; тот же режим использует групповое изменение реквизитов). Остальные подписки на запись переносу не мешают:
   нумерация по организации срабатывает только при записи из формы, установка номера — только для нового объекта.
   Проверено: у всех 46 объектов переноса с модулем объекта имеющиеся `ПередЗаписью` и `ПриЗаписи` начинаются с выхода по
   `ОбменДанными.Загрузка` (у `ЗаданиеНаПересчет`, `ПроектыКонфигураций`, `ШаблоныКонфигураций` модуля объекта нет).
7. **Тесты.** Новый сценарий `ТестыДокументов.АвторВОтветственного` в транзакции с откатом: заказ клиента с автором
   и пустым ответственным получает ответственного, запись с заполненным ответственным не меняется, проведённый
   документ остаётся проведённым без изменения движений, непроведённая оплата со связанной проведённой налоговой
   накладной получает ответственного, а у накладной не меняются версия данных, реквизиты и движения, справочник
   проектов конфигураций получает ответственного,
   повторный запуск ничего не меняет; `УдалитьАвторОбщий` не читает ни одна строка кода, кроме обработчика и теста
   (проверка поиском). Смок, 25+1 сценариев на копии обновлённой базы. Реестр `docs/TESTS.xlsx`.
8. **Проверка перехода.** На копии базы 2.0.15.27 заранее заполняю автора (заказ клиента с пустым ответственным,
   непроведённая оплата с накладной, проект конфигураций, справочник без `Ответственного`), затем загружаю туда
   конфигурацию 2.0.15.28 целиком (`scripts/edt-export.sh` → `scripts/xml-load.sh` → `UpdateDBCfg`), вхожу — обработчик
   выполняется. Сверяю: авторы переименованного реквизита сохранились, перенос прошёл, накладная не перепроведена,
   у справочника без `Ответственного` автор остался в `УдалитьАвторОбщий`, записи в журнале.
   Перед публикацией CF тот же переход повторяется через поставляемый CFU (шаги `docs/RELEASING.md`): загрузка XML
   его не заменяет (замечание ревью плана).
9. **Документы.** «Что нового» 2.0.15.28 на четырёх языках; `docs/TECHDEBT.md` и `docs/ROADMAP.md` — пункт шага 2.

### Шаг 2 — отдельный релиз, когда все базы клиентов пройдут 2.0.15.28

Удалить общий реквизит `УдалитьАвторОбщий`, обработчик переноса и сценарий. До удаления — решение владельца по
записям из журналов обновления клиентов: авторы у объектов без совместимого `Ответственного` и авторы, отличные от
уже заполненного `Ответственного`. Релиз удаления поддерживает обновление только с версий не ниже 2.0.15.28; для
старых копий баз — промежуточная поставка 2.0.15.28 и порядок обновления в `docs/RELEASING.md`.

## Что не делаю

- Не добавляю `Ответственный` 120 объектам без него (справочники вроде `Валюты`, `Банки`, `СтавкиНДС`): у них автор
  нигде не заполнялся и не показывался.
- Не выключаю `УдалитьАвторОбщий` в составе на шаге 1: смена «Использовать» на «Не использовать» — та же потеря данных.
- Не трогаю `Ответственный` типа «Физическое лицо».

## Риски и проверки

- EDT: переименование общего реквизита правится текстом в трёх файлах (`.mdo` реквизита, `Configuration.mdo`,
  `Rights.rights`); после Refresh — проверка EDT у владельца. Ссылок по имени в запросах и СКД после п. 3–4 не
  остаётся (`grep -r АвторОбщий`).
- Обновление базы: переименование общего реквизита данные не перестраивает; реструктуризация — только два
  справочника из п. 2.
- Гейты: план → ревью плана (gpt-6-astra) → реализация → `lint`/`refcheck`/`listcheck`/`queryfields` → ревью кода →
  ревью данных → смок и сценарии на копии обновлённой базы.
