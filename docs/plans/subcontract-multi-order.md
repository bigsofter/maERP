# Переработка по нескольким заказам: заказ в строке передачи и поступления

Задача владельца 2026-11-01…02 (переписка в сессии). Несколько заказов разных клиентов уходят подрядчику **одним
документом передачи** и возвращаются **одним поступлением из переработки**, а отгружаются каждому клиенту своей
реализацией. Существенное изменение по CLAUDE.md: реструктуризация двух документов, проведение и блокировки,
обработчик обновления, автовыпуск, стадии заказов → план → `ai-review-plan` → код.
Вариант «пакетов» (одна передача на заказ, объединённые отправкой) прошёл первый круг ревью
(`.ai/reviews/subcontract-packages/`) и отклонён владельцем.

## Решения владельца

1. **Заказ — в строке** табличных частей передачи и поступления (2026-11-01, подтверждено 2026-11-02; вариант
   «пакетов» — одна передача на заказ, объединённые отправкой, — отклонён).
2. **Общий документ создаётся только в режиме нескольких заказов** (2026-11-02): в верхнем списке рабочего места
   выделено больше одного заказа → на закладках «Передача в переработку» и «Поступления из переработки» появляется
   колонка «Заказ», новые строки идут в **новый общий документ**, заказ строки выбирается из выделенных. **В уже
   существующий (проведённый) документ строки других заказов не дописываются.** Один заказ — всё как сейчас.
3. Заполнение общей передачи — **по потребностям или вручную**; способы заполнения — все три сразу: по этапам
   переработчика, по выпущенным ПФ, пустая.
4. «Общая отгрузка» — это передача подрядчику, не реализация (2026-11-02). Реализация остаётся по одному заказу.
5. В списках выбора передачи — **подрядчик**.
6. Верхняя закладка **«Документы»** (третья, после «Заказы» и «Продукция») с выбором вида: «Переработка»,
   «Выпуски», «Требования-накладные». Режимы «Документы / Строки», у переработки ещё **«У подрядчиков»** — сразу.
   Сумма услуг — по праву видеть суммы.
7. **Выпуски без заказа** вводятся строкой в виде «Выпуски» закладки «Документы».
8. **Требования-накладные** в рабочем месте производства — просмотр и статус; ввод остаётся в рабочем месте станков.
   Вид виден только при выключенной константе `ИспользоватьАвтовыпускПриОтгрузке` и праве чтения документа.

## Ревью плана

складской дефект раунда 17 — в TECHDEBT. **Решение владельца 2026-11-02:** начинать сборку 1 без approve ревью плана;

## Модель данных

### Реквизиты

- `Документ.ПередачаВПереработку.ТЧТовары.Заказ`, `…ТЧГотоваяПродукция.Заказ` — `ДокументСсылка.ЗаказПокупателя`.
- `Документ.ПоступлениеИзПереработки.ТЧТовары.Заказ`, `…ТЧГотоваяПродукция.Заказ` — то же.
- `Документ.ПередачаВПереработку.НесколькоЗаказов` — Булево, **признак общего документа** (ревью плана, раунд 5, P1:
  без явного признака документ сеанса после первой строки A становился одно-заказным, и строка B отклонялась).
  Ставится рабочим местом при создании документа в режиме нескольких заказов и флажком «Несколько заказов» в форме
  документа. Поступлению признак не нужен: его основание — передача.
- Реструктуризация — добавление колонок, данные заполняет обработчик обновления (ниже).

### Шапка

- **Передача, общая** (`НесколькоЗаказов = Истина`): `Основание` всегда пусто, `Заказ` обязателен в каждой строке
  обеих ТЧ — отказ с номером строки и ТЧ **в `ПередЗаписью`** (кроме `ОбменДанными.Загрузка`), проверка заполнения
  повторяет его для ранней диагностики (ревью плана, раунд 8, P1: программное проведение не вызывает
  `ПроверитьЗаполнение`, пустой заказ строки дал бы беззаказную партию у подрядчика; тест — прямые `Записать()` и
  `Записать(Проведение)` с пустым заказом отдельно в каждой ТЧ), строки любых заказов — в любом порядке ввода, в том числе один заказ. Флажок
  снимается, только если у всех строк один заказ (`Основание` := он); ставится — `Основание` очищается, заказы строк
  сохраняются. У проведённого документа смена флажка — только с перепроведением (шаг 2 ниже).
- **Передача, обычная** (`НесколькоЗаказов = Ложь`): все строки — заказа `Основание` (или без заказа). Строка другого
  заказа — отказ «документ одного заказа: отметьте «Несколько заказов»». Инвариант поддерживает `ПередЗаписью` (не
  форма и не рабочее место), по шагам:
  1. **смена заказа одно-заказного документа** (ревью плана, раунд 3, P2): в базе документ одно-заказный с заказом Z
     (или без заказа), в объекте `Основание` = Y ≠ Z, и все строки объекта — с Z или пустые → строки переносятся на Y
     (пустой Y — документ без заказа), ожидаемая продукция пересчитывается; действующая проверка
     `ПроверитьСменуОснованияИПереработчика` (поступления, списание по передаче) сохраняет запрет;
  2. **проведённый документ** (передача и поступление): смена заказа хотя бы одной строки (эффективного — с учётом
     шапки) допускается только в режиме записи «Проведение»; обычная запись проведённого документа со сменой заказа
     строк — отказ «заказ проведённого документа меняется только с перепроведением» (ревью плана, раунд 4, P1: иначе
     строки разойдутся с приходом у подрядчика). Сравнение — распределение `КодСтроки → эффективный заказ` в базе и в
     объекте;
  3. строки с пустым `Заказ` получают `Основание`; строка с заказом, отличным от `Основание`, — отказ (см. выше);
  4. ветки не смешиваются (ревью плана, раунд 6, P2): у общего документа `Основание` **всегда пусто** — при нуле, одной
     или нескольких группах; `ПередЗаписью` очищает его, поле в форме недоступно; единственный заказ строк ставится
     в `Основание` **только при снятии флажка**. Шаги 1–3 — только для обычного документа. затем `Основание` = единственный заказ строк или пусто.
  Документ без строк сохраняет `Основание` (новый документ рабочего места до первой строки). Передача без заказа
  вовсе (основание пусто, заказ строк пуст) — как сейчас.
- **Поступление — проверка заказов строк на сервере** — общая процедура `ТекстЗапретаЗаказовСтрок()`, вызов из
  **`ПередЗаписью`** (транзакционный, выполняется и при программной записи без `ПроверитьЗаполнение`; пропуск при
  `ОбменДанными.Загрузка` — обработчик обновления), `ОбработкаПроверкиЗаполнения` зовёт её же для ранней
  диагностики (ревью плана, раунды 5–6, P1). Тест — прямые `Записать()` и `Записать(Проведение)` без
  `ПроверитьЗаполнение`. Правила:
  - основание — **общая** передача: заказ каждой строки продукции входит в заказы ожидаемой продукции этой передачи;
  - основание — **обычная** передача: допустимый заказ — эффективный заказ передачи (`Основание` передачи; у
    передачи без заказа — пустой), независимо от наличия ожидаемой продукции (ревью плана, раунд 7, P1: передача
    без ожидаемой продукции и поступление с ручной продукцией допустимы сейчас);
  - заказ каждой строки сырья — в заказы строк продукции этого поступления (у поступления без продукции — в
    допустимые заказы основания);
  - основание-заказ — все строки этого заказа; без основания — заказ строк пуст.
  Тест: обновление, прямая запись и перепроведение поступления по беззаказной передаче с пустой ожидаемой ТЧ. Выбор заказа в форме ограничен тем же набором. Исторические документы
  согласованы обработчиком (строки = заказ передачи), исключение не нужно. Проверка — и при прямой записи объекта.
- **Поступление:** `Основание` остаётся **передачей** (одна передача на поступление): «ожидаемое по передаче»,
  остаток к приёму, сырьё по передаче и половина рабочего места держатся на нём. Заказы строк поступления — из строк
  ожидаемой продукции этой передачи. Поступление по заказу (`Основание` = заказ, старый режим) — заказ строк =
  основание. **Ограничение волны:** общее поступление собирается из **одной** передачи — общей (многозаказной) или
  одно-заказной; поступление из нескольких передач разных заказов — нет (отдельное решение владельцу, если
  понадобится: тогда в строки поступления нужен реквизит `Передача`).

### Единое правило «заказ строки»

Одна функция на сервере и одно выражение в запросах:
- `ПроизводственныеЗаказы.ЗаказСтрокиПереработки(Строка, ДокОбъект)` — `Строка.Заказ`, если заполнен; иначе заказ
  шапки (`Основание` передачи; у поступления — заказ основания-передачи или основание-заказ).
- В запросах: `ВЫБОР КОГДА Т.Заказ = ЗНАЧЕНИЕ(Документ.ЗаказПокупателя.ПустаяСсылка) ТОГДА <заказ шапки> ИНАЧЕ
  Т.Заказ КОНЕЦ`. **Запасной путь обязателен** (ревью карты, п. 7): прежние обработчики обновления (2.0.15.48,
  2.0.16.41, 2.0.16.99) на базах, догоняющих версии, выполняются на новом коде **до** заполнения заказа строк.

## Проведение и расчёты (сборка 1)

Номера пунктов — строки карты влияния (отчёт разбора 2026-11-02, сохраняется в `.ai/reports/subcontract-multi-order-map.md`).

### Передача

- **Приход у переработчика по заказам** (карта п. 25, 29). Списание со склада передачей — с `ПоСтрокам = Истина` (так
  уже списывает расходный ордер, `ОрдераСклада`): код строки попадает в движения `ТоварыВНаличии` и
  `ДополнительныеРасходы`. `ТоварыВПереработке.ОтразитьПередачу` сворачивает **складские расходы** по
  `КодСтроки, Номенклатура, Характеристика, Серия, Партия, ДатаПартии`, а **издержки** (`ДополнительныеРасходы`, у
  регистра нет `ДатаПартии`) — по `КодСтроки, Номенклатура, Характеристика, Серия, Партия` (ревью плана, раунд 3,
  P1); издержки ключа прибавляются к складскому расходу с тем же ключом без даты партии ровно один раз: обычно у партии
  одна дата партии; если у ключа их несколько, издержки идут к расходу с самой ранней датой (сейчас `НайтиСтроки` по
  ключу без даты прибавил бы их к каждому — двойной учёт; новое правило его исключает, тест «одна партия, две даты»). Код строки переводится в заказ строки `ТЧТовары`, приход пишется с `ЗаказПокупателя` строки.
  **Уникальность кода строки** (ревью плана, раунд 7, P1): сейчас код назначает форма, `ПередЗаписью` его не
  нормализует, а `СписатьНоменклатуру` с `ПоСтрокам` сворачивает одинаковые позиции с одинаковым кодом.
  `ПередЗаписью` передачи (и поступления — его ТЧ тоже несут заказ) до всех проверок присваивает нулевым и
  повторяющимся кодам обеих ТЧ новые значения `максимум + 1` — правило `ОрдераСклада.ЗаполнитьКодыСтрок`
  (выносится в `РаботаСДокументамиКлиентСервер`, ордера переходят на общую процедуру); корректные коды не меняются.
  Сравнение «прежний → новый заказ строки» (шаг 2 шапки): если у сохранённой версии коды неоднозначны (нули или
  повторы) — сравнение по номеру строки. Тест: программное проведение общей передачи с нулевыми и повторяющимися
  кодами двух строк одного материала A=5/B=5 — движения отдельно по A и B. Тест:
  передача двух заказов с одной складской партией и дополнительными расходами. **Обязательная часть сборки** (ревью плана, раунд 2, P1):
  `ТоварыВНаличии.РазложитьКомплектыНаСоставляющие` сейчас не переносит `КодСтроки` в строки составляющих — перенос
  кода исходной строки добавляется, дальнейшие свёртки проверяются на сохранение кода (тест: комплекты двух заказов с
  общей составляющей, количество и стоимость каждого заказа отдельно). Читатели `ТоварыВНаличии.КодСтроки`
  проверяются при реализации; поведение одно-заказной передачи не меняется (сверка движений до/после на тестовой
  базе).
- **Блокировки** (п. 3): `УправляемыеБлокировки.ПотребностиПроизводства` — по каждому заказу строк, заказы
  упорядочены по `XMLСтрока(Ссылка)`; порядок общий с рабочим местом (`Производство.ЗаполнитьБлокировкуПередачи`).
  `ПроизводственныеЗаказы.ЗаблокироватьИсторию` — проверить упорядочение заказов, иначе упорядочить.
- **Требования-накладные** (п. 2): `ТекстЗапретаВыпускаБезТребования` — по каждому заказу на его строках
  `ТЧГотоваяПродукция` (сейчас при пустом основании проверка молча не выполнялась бы).
- **Автовыпуск ПФ** (п. 31–35) — **только в одно-заказной передаче**. Многозаказная передача автовыпуск не делает:
  ПФ выпускается заранее (ручным выпуском или способ заполнения «по выпущенным ПФ»). Явная проверка проведения:
  строка ПФ, который автовыпуск выпустил бы, в многозаказной передаче при нехватке на складе — отказ «в передаче
  нескольких заказов автовыпуск не выполняется — выпустите ПФ заказа N». Прежний автовыпуск передачи, ставшей
  многозаказной, распроводится и помечается на удаление штатно (`РаспровестиЛишниеАвтовыпуски`). Решение — на
  подтверждение владельца в отчёте сборки (поддержка — N автовыпусков на передачу, высокий риск).
- **Ожидаемая продукция** (п. 7, 11, 12): `ЗаполнитьОжидаемуюПродукцию` делит `ТЧТовары` по заказу строки, на каждую
  группу — `ОжидаемаяПродукцияПередачи(Заказ, Группа)`, результат — со своим `Заказ`. Функции менеджера
  (`ОжидаемаяПродукцияПередачи`, `ДопустимаяПродукцияМатериала`, `КоличествоПродукцииПоНорме`) не меняются —
  вызывающие подают заказ строки.
- **Протокол блокировки передачи** (ревью плана, раунд 9, P0: проверка «нет поступлений» в `ПередЗаписью` шла до
  блокировок проведения — поступление, проведённое в промежутке, списывало приход заказа A, который передача затем
  заменяла на C). Управляемая блокировка `Документ.ПередачаВПереработку` по `Ссылка`:
  - **передача** — исключительная, **первой** в транзакции записи (в начале `ПередЗаписью`, до чтения
    зависимостей), если меняется распределение заказов строк, подрядчик, основание или документ проводится/
    распроводится; под ней перечитываются зависимости (`ЕстьПоступленияПоПередаче`, `ЕстьСписаниеПоПередаче`) и
    выполняются проверки смены заказа; держится до конца транзакции;
  - **поступление** — разделяемая на свою передачу-основание (прежнюю и новую при смене основания), **первой** в
    `ПередЗаписью`, до чтения допустимых заказов основания; держится до конца транзакции;
  - порядок: блокировка передачи — до регистровых блокировок проведения (`ЗаполнитьБлокировкуПередачи`,
    `ЗаполнитьБлокировкуПроведения` поступления, потребности) и в объекте документа, и в рабочем месте (там, где
    оно блокирует передачу перед правкой строк и проводит поступление, — тот же первый шаг; общий порядок фиксируется
    комментарием в `Производство.ЗаполнитьБлокировкуПередачи`).
  Тест двух сеансов (фоновое задание + основной сеанс, как в существующих тестах блокировок, или последовательная
  имитация с удержанием транзакции): перепроведение передачи со сменой A → C и проведение поступления A — второй
  ждёт и получает отказ, остатки по заказам согласованы.
- **Контроль израсходованных партий** (ревью плана, раунд 10, два P0: поступление списывает партии всего подрядчика
  в пределах допустимых заказов, не только своей передачи-основания, поэтому блокировка документа-основания гонку не
  закрывает; и при неизменных заказах уменьшение количества или удаление строки после поступления увело бы остаток в
  минус). Защита — на уровне регистра, общая для любого источника списания:
  - блокировка `ТоварыВПереработке` передачи (`УправляемыеБлокировки.ТоварыВПереработке` в
    `Производство.ЗаполнитьБлокировкуПередачи`) — по **объединению прежних и новых пар `Контрагент, Номенклатура`**:
    прежние — из **фактических движений** `ТоварыВПереработке` документа (запрос по `Регистратор` до их замены),
    новые — из позиций документа **с раскрытием комплектов** на составляющие тем же способом, что складская
    блокировка (ревью плана, раунд 13, P0: приход у подрядчика пишется по составляющим, а блокировка шла по
    комплекту и не конфликтовала с поступлением по составляющей); тот же набор — в объекте и в рабочем месте до
    чтения остатков; тест двух сеансов: уменьшение передачи комплекта и списание его составляющей поступлением с
    основанием-заказом; (сейчас — только новые позиции нового подрядчика; ревью плана, раунд 11, P0: смена подрядчика
    P → Q иначе не блокирует и не контролирует P); поступления любого вида блокируют тот же регистр по подрядчику и позициям — проведения
    сериализуются регистровой блокировкой;
  - **`ЕстьСписаниеПоПередаче`** ищет расходы по `ПередачаВПереработку = Ссылка` **у всех фактических контрагентов
    движений** документа (а не по контрагенту сохранённой шапки; ревью плана, раунд 14, P0: шапку проведённой
    передачи можно было переписать на другого подрядчика без перепроведения); смена подрядчика проведённой
    передачи — только с перепроведением (как смена заказа строк, шаг 2 шапки); тест — смена P → Q обычной записью
    (отказ) и историческая передача с уже рассогласованными шапкой и движениями (отмена проведения при расходе у P —
    отказ);
  - **единое правило «передача с расходом»** (раунд 11, P0 и P1): под этой блокировкой повторяется
    `ЕстьСписаниеПоПередаче`; если по партиям передачи есть расход другими документами, запрещены **смена
    подрядчика, сдвиг периода прихода** (иначе приход уходит за дату расхода, а срез остатков этого не видит; дата
    сравнивается с **фактическим периодом приходных движений** документа, а не с сохранённой шапкой — ревью плана,
    раунд 15, P0: дату проведённой передачи можно было переписать без перепроведения; сдвиг периода прихода при
    наличии расхода — отказ, в том числе при перепроведении после обновления без изменения шапки), **отмена
    проведения и удаление** — отказ «по передаче уже принята продукция: …»;
  - **после `Движения.Записать()`** в проведении передачи — запрос остатков `ТоварыВПереработке` с отбором
    `Контрагент В (прежний, новый), ПередачаВПереработку = Ссылка`, **количество** в разрезе `Контрагент,
    Номенклатура, Характеристика, Серия, ПередачаВПереработку, ЗаказПокупателя` — **без `Партия` и `ДатаПартии`**
    (ревью плана, раунд 12, P1: пошаговое восстановление последовательности перепроводит передачу отдельно от
    поступления; при смене складской партии по FIFO приход уходит на другую партию раньше, чем расход поступления, и
    контроль по партии остановил бы пересчёт. Уменьшение количества, удаление строки и смена заказа этим разрезом
    ловятся; перенос расхода на новую партию делает перепроведение поступления дальше по последовательности): любой
    отрицательный остаток — отказ «по партии … уже списано больше, чем остаётся после изменения» с позицией и
    заказом; транзакция откатывается целиком (контроль остатков после записи — тот же приём, что в
    `ТоварыВНаличии`);
  - **отмена проведения** (`ОбработкаУдаленияПроведения`) и **удаление** (`ПередУдалением` — сейчас при отсутствии
    автовыпуска сразу возвращает управление; ревью плана, раунд 11, P0) под той же блокировкой прежних пар:
    `ЕстьСписаниеПоПередаче` — отказ независимо от автовыпуска (рабочее место уже так делает в
    `ВыполнитьСнятиеПередачи`; объект документа — нет);
  - **момент** (ревью плана, раунд 16, P1): у передачи включено автоудаление движений — платформа очищает прежние
    движения **до** `ОбработкаПроведения`. Поэтому полный набор регистровых блокировок (прежние пары из фактических
    движений + новые с раскрытием комплектов) и решающие проверки «передачи с расходом» (подрядчики движений,
    период прихода, `ЕстьСписаниеПоПередаче`) выполняются **в `ПередЗаписью`** в режимах проведения и отмены
    проведения, до автоудаления; снимок прежних ключей, контрагентов и периодов прихода — в
    `ДополнительныеСвойства` объекта; контроль остатков после `Движения.Записать()` использует снимок (контрагенты
    прежние и новые), а не ищет уже удалённые приходы. Блокировки держатся до конца транзакции. Тест двух сеансов:
    перенос даты передачи и конкурентное поступление с основанием-заказом между датами.
  Тесты: уменьшение A после частичного и полного поступления, удаление строки, смена заказа A → C, смена подрядчика
  P → Q, перенос даты за поступление, отмена проведения, программное `Удалить()` — отказ, документ и движения не
  изменились; двухсеансовые: перепроведение передачи и поступление с основанием-заказом, другой
  передачей и без основания, смена подрядчика P → Q и списание у P через основание-заказ — согласованные остатки.
  Уровень 3: полностью израсходованная передача, новая более ранняя складская партия, восстановление
  последовательности до конца — количество и стоимость у подрядчика и в продукции сходятся.
- Проверки (п. 6, 9): `ПроверитьПродукциюСтрок` — по заказу строки, заказ — в ключе записанной строки;
  `ПроверитьСменуОснованияИПереработчика` — сравнение набора `КодСтроки → Заказ` в базе и в объекте (смена заказа
  строки при поступлениях или списании по передаче — отказ).
- Заполнение на основании заказа и выпуска (п. 1, 8) — заказ в строки.

### Поступление

- **Ремонт старых расходов** (п. 26, обработчик ниже): `ЗаказПокупателя` расходов `ТоварыВПереработке`
  выравнивается по приходу той же партии и передачи (старые передачи одно-заказные — однозначно; суммы не меняются).
  После ремонта отбор по измерению `ЗаказПокупателя` остатка сбалансирован.
- **Списание у переработчика по группам** (п. 26, 27): `СписатьИзПереработки` сворачивает сырьё по
  `(Заказ строки, Номенклатура, Характеристика, Серия)`. Группы двух видов:
  - **группа заказа X** — допустимы **только** партии с `ЗаказПокупателя В (X, пустой)`: отбор применяется и в
    контроле недостачи, и в `СписатьПартии` (сейчас она отбирает партии только по номенклатуре, характеристике и
    серии — добавляется отбор по допустимым заказам группы; ревью плана, раунд 2, P1, сценарий A=6/B=4 при остатках
    A=5/B=5 — отказ по A, а не списание партии B);
  - **группа без заказа** (заказ строки и заказ шапки пусты — поступление без основания, допустимо сейчас) —
    **прежнее поведение**: отбора по заказу нет, любые партии подрядчика по FIFO (ревью плана, раунд 2, P1).
  **Отбор по измерению — для всех поступлений с заказом** (ревью плана, раунд 6, P1): после ремонта старых расходов
  (обработчик) прежний отбор «через передачи заказа» изоляцию больше не держит — общая передача содержит приходы
  нескольких заказов, и обычное поступление A через неё взяло бы партию B. Поэтому и одно-заказное, и частичное
  поступление по общей передаче, и поступление по обычной передаче берут **только** партии `ЗаказПокупателя В (X,
  пустой)`. Группа без заказа — прежнее поведение. Прежний отбор «через передачи заказа» и `ЗаказСписания` удаляются.
  Группы разбираются по очереди на общей изменяемой таблице партий (беззаказная партия не достаётся двум группам):
  сначала группы заказов в порядке первой строки заказа в документе, затем группа без заказа. Внутри группы —
  сортировка по допустимому подмножеству: партии своего заказа, затем передачи-основания, затем FIFO. Контроль
  недостачи — по группе с учётом уже распределённого, сообщение называет заказ группы. **Контроль после записи и в поступлении** (ревью плана, раунд 17, P0 — дефект и текущего кода): контроль недостачи
  читает остатки на момент документа, поэтому поступление задним числом списывает уже израсходованное позже. После
  `Движения.Записать()` проведения поступления — тот же контроль, что у передачи: текущие остатки `ТоварыВПереработке`
  по затронутым ключам (прежние из снимка `ПередЗаписью` и новые: `Контрагент, Номенклатура, Характеристика, Серия,
  ПередачаВПереработку, ЗаказПокупателя`, без `Партия`/`ДатаПартии` — совместимо с восстановлением
  последовательности) не отрицательны; иначе отказ и откат. Под удерживаемой регистровой блокировкой. Тест:
  полностью списанная передача → новое поступление более ранней датой → отказ.
  Тесты: обычное поступление A с расходом 6 при исчерпанной своей передаче и общей передаче A=5/B=5 — отказ;
  частичное поступление только A по общей передаче A=5/B=5 с сырьём 6 — отказ.
- **Себестоимость по группам** (п. 29, заключение 4) — одна группа даёт прежний результат (вся продукция — одна
  группа): `СписатьИзПереработки` возвращает суммы списанного по заказам
  групп (в памяти, тот же код при пересчёте последовательности); `РаспределитьСебестоимостьНаПродукцию` делит сумму
  группы по весам техкарт только на продукцию **её** заказа. Проверка «сырьё без продукции» — по группам (п. 15) и **обязательно в `ОбработкаПроведения`** до формирования
  расходов (ревью плана, раунд 8, P0: сейчас `ПроверитьСписаниеБезПрихода` зовётся только из проверки заполнения, и
  программное `Записать(Проведение)` без продукции списывает сырьё, стоимость которого не на что распределить —
  она исчезает из учёта; это и текущий дефект, закрывается в этой сборке); каждая списывающая группа должна иметь
  продукцию своего заказа с **положительным количеством** (ревью плана, раунд 16, P0: строка с нулевым количеством
  проходила бы проверку, а последняя строка распределения получала остаток стоимости без товара); строки с нулевым
  количеством исключаются из распределения себестоимости и из выбора последней строки; получателей нет — отказ до
  формирования расходов; **ненулевые услуги на строке с неположительным количеством** — отказ проведения (ревью
  плана, раунд 17, P1: услуги без получателя), сопоставление услуг с получателями — по `КодСтроки`; тест — прямое проведение с нулевой продукцией A и корректной B: отказ, откат документа; проверка заполнения сохраняет раннюю диагностику. Тест: прямое `Записать(Проведение)`
  без продукции — отказ, остатки и суммы не изменились.
  Одна позиция в двух заказах одного поступления — одна партия продукции (партия = документ) со средней стоимостью:
  принимается, отмечается в TECHDEBT.
- **Ожидаемая продукция и сырьё** (п. 13, 17–21) — по группам заказа для всех поступлений (одна группа — частный
  случай). **Прежний расчёт** сырья (остатки передачи по всем заказам) сохраняется только для вызова из старого
  обработчика 2.0.15.48 (`ЗаполнитьУслугиИПризнакПоступленийИзПереработки` → `СырьеСовпадаетСРасчетом`): явный
  параметр `ПрежнийРасчет = Истина` (ревью плана, раунд 5–6, P2): на догоняющей базе он выполняется до ремонта
  расходов и должен получить прежний признак `СырьеИзмененоВручную`. Остальные вызовы — новый расчёт: `ОжидаемаяПродукция(Передача)` — строки ожидаемой продукции
  передачи с заказом; `ВычестьПоступившуюПродукцию` — `Заказ` в ключе; `ОграничитьОстаткомЗаказа` — по каждому
  заказу на его строках; `СырьеПоПродукции`/`ЗаполнитьСырье` — по группам (продукция заказа X → расход по техкартам
  → остатки передачи с заказом X и беззаказные → сырьё с `Заказ = X`; беззаказные — последовательно по группам);
  дочистка ограничена партиями передачи и заказа (комментарий `ManagerModule:437-442`). `СырьеСовпадаетСРасчетом` —
  по группам с запасным путём заказа (его зовёт обработчик 2.0.15.48).
- `ПроверитьПорядокВыпуска` (п. 16), `ВыпускПоступленияИзменен` (п. 38) — по заказам строк.
- **Услуги при удалении строки** (ревью плана, раунд 14, P2): `ПересчитатьПоступлениеПослеУдаления` /
  `ДобавитьСтоимостьУслуг` в общем поступлении переносят услуги удалённой строки **только на строки её заказа**;
  удалена последняя строка заказа с услугами — услуги этой строки не переносятся на другие заказы, документ
  получает сообщение «услуги заказа N (сумма) сняты — задайте сумму услуг заново» и итог услуг уменьшается. Тест:
  удаление строки A — услуги и себестоимость B не изменились.

- Акт передачи и акт приёмки (п. 10): заказ и клиент — в шапке, если заказ один; иначе «Заказы: №1 (Клиент 1), №2

   - передача: проведённая с активными приходами `ТоварыВПереработке` — заказ этих приходов (сегодня он один на
     документ; больше одного — документ в отчёт расхождений, строки не трогаются); без приходов (черновик,
     непроведённая) — `Основание`;
   - поступление: основание-передача — заказ строк этой передачи по тому же правилу; основание-заказ — он;
     без основания — пусто (группа без заказа, прежнее поведение);
   - **расхождение** заказа движений с `Основание` передачи (шапку переписали без перепроведения; заказ движений
     может быть и пустым): **строки и шапка** получают заказ движений — то, что фактически лежит у подрядчика и что
     сейчас использует `ЗаказСписания` (ревью плана, раунд 3, P1: иначе пустой заказ движений не отличить от «ещё
     не заполнено», и запасной путь подставил бы шапку). После этого правило «пустой заказ строки = заказ шапки»
     верно для всех документов без отдельного признака. Документ — в журнал регистрации и в отчёт обработчика
     («Переработка: шапка выровнена по движениям», оба заказа); его поступления получают тот же заказ строк;
     **в той же транзакции**, что и запись документа, пересчитываются стадии прежнего и нового заказов (шаг 3):
     транзакция на документ — сбой обработчика не оставляет исправленный документ без пересчёта (ревью плана,
     раунд 4, P2);
   - записываются **только** документы, у которых **целевое состояние отличается от сохранённого** — шапка или заказ
     любой строки, включая переход к пустой ссылке (ревью плана, раунды 2 P2 и 4 P1): сравнение по значениям, без
     условия «целевой заказ заполнен»; документ без заказа, у которого и шапка, и строки пусты, не записывается;
     повторный запуск ничего не пишет;
   - запись в режиме загрузки, без перепроведения.
2. Ремонт расходов `ТоварыВПереработке` (см. «Поступление»). Заказ каждого расхода := **единственный заказ всех
   активных приходов его `ПередачаВПереработку`**, а не приход той же партии (ревью плана, раунд 13, P0: после
   перепроведения передачи по FIFO приход мог уйти на другую складскую партию, а последовательность ещё не
   восстановлена — точного совпадения партии нет). Приходов у передачи нет (передача распроведена, расход
   остался) — заказ из `Основание` передачи; приходов нескольких заказов (исторически невозможно) или нет и
   передачи — расход не меняется. Все неточные случаи (без прихода, неоднозначные, без передачи) — в отчёт
   обработчика и журнал регистрации списком «Переработка: расход без однозначного прихода». Наборы регистраторов-
   поступлений, где заказ хотя бы одного расхода меняется, записываются с `ОбменДанными.Загрузка`; итоги регистра
   пересчитываются платформой. Тест: заменённая по FIFO партия, асимметричный заказ расхода, незавершённое
   восстановление последовательности — после обработчика повторное списание поступлением A отклоняется.
2а. Диагностика дат: проведённые передачи, у которых `Дата` шапки ≠ периода их приходных движений
   `ТоварыВПереработке` и есть расход другими документами, — в отчёт обработчика и журнал регистрации («Переработка:
   дата шапки расходится с движениями»); документы не меняются (перепроведение такой передачи отклонит контроль
   выше, владелец согласует дату). Тест: дата, изменённая без перепроведения до обновления, — после обновления
   перепроведение передачи отклоняется, восстановление последовательности не ломает остатки.
3. Стадии: у обычных документов расчёт с запасным путём даёт тот же результат — не пересчитываются (тест «стадия
   до/после»). У документов с выровненной шапкой (шаг 1) стадии прежнего и нового заказов пересчитываются штатно
   (`ПроизводственныеЗаказы.ЗаписатьСтадиюЗаказа`) в транзакции записи этого документа (ревью плана, раунды 3–4,
   P2), после записи всех его поступлений в той же транзакции; повторный запуск расхождений не находит и ничего не
   пересчитывает. Тест: сбой (исключение) после записи шапки внутри транзакции — откат, повторный запуск исправляет
   и пересчитывает.

## Рабочее место (сборка 1 — только чтение и одно-заказная правка; сборка 2 — режим нескольких заказов)

### Сборка 1

Многозаказный документ уже может появиться (форма документа). Закладки заказа показывают **строки этого заказа**
многозаказных документов: запросы рабочего места по шапке (`СтрокиПередач`, `ТекстЗапросаСтрокПередач`,
`СтрокиПоступленийИзПереработки`, `ТекстЗапросаСтрокПоступленийИзПереработки`, `ТекстЗапросаДокументовЗаказа`,
`ПодзапросОснований`, `РеализацииЗаказа`, `ТекстЗапросаСтрокОтгрузок`, `ДокументыВыпускаИОтгрузкиДляВыбора`,
`ПередачиЗаказаДляВыбора`, `СтрокаПередачиСвойств`, полный перечень — карта) — на заказ строки. Правка строки
многозаказного документа на закладке одного заказа — разрешена для строк этого заказа (норма и допустимая продукция —
по заказу строки, `ПрименитьДанныеСтрокиПередачи`); новая строка одного заказа в многозаказный документ не идёт
(сегодняшний документ для новой строки — только одно-заказный этого заказа, `ДокументыСтрокиДляВыбора`).
«Статус» многозаказного документа с закладки одного заказа — вопрос «документ содержит строки заказов A, B, C —
применить?», заказ документа сверяется по набору заказов строк, а не по `Основание`.

### Сборка 2: режим нескольких заказов

- **Включение:** выделено больше одного заказа в «Заказах» или в «Продукции» (`ОтмеченныеЗаказы().Количество() > 1`;
  выделение уже есть, им пользуется «Статус»). Реквизит формы `ТекущиеЗаказы` (список); `ТекущийЗаказ` — заказ
  текущей строки, как сейчас.
- Закладки **«Передача в переработку»** и **«Поступления из переработки»** грузят строки документов всех выделенных
  заказов (`СтрокиПереработок(Заказы)`, `СтрокиПоступленийПереработки(Заказы)` — массив), колонка «Заказ» видна,
  заголовок закладки — «… (3 заказа)». Остальные нижние закладки — по текущему заказу, как сейчас.
- **Новая строка** в режиме нескольких заказов: колонка «Заказ» обязательна, выбор — из `ТекущиеЗаказы`
  (по умолчанию — заказ предыдущей строки). Документ новой строки — **новый общий документ** этого сеанса ввода:
  первая строка создаёт передачу с `НесколькоЗаказов = Истина` и пустым `Основание`, следующие строки того же подрядчика и склада (соседняя
  строка, `ДокументЗаСегодня`, тот же правило `СоседняяСтрокаПодходит`) дописываются в него. В одно-заказный
  документ и в общий документ другого набора заказов строки не идут.
- **«Заполнить по потребностям»** (командная панель закладки «Передача», видна в режиме нескольких заказов): диалог —
  подрядчик, склад, способ заполнения, предпросмотр с флажками (Заказ · Клиент · Этап (ПФ/ГП) · Материал ·
  Характеристика · Количество — редактируется), «Заполнить» → строки в новый общий документ.
  - **По этапам переработчика** — `СырьеЭтаповПереработчикаКПередаче(Заказы)`: по каждому заказу — ключи сырья ПФ
    переработчика (`ПотребностиПроизводства.ДеревоГраницЗаказа`) с потребностью минус переданное по заказу
    (`ПереданоСырьеПереработчику`) и минус строки непроведённых передач заказа; Продукция = ПФ. Заказ без этапов —
    сообщение «у заказа N нет этапов переработчика».
  - **По выпущенным ПФ** — `ВыпущенныеПФКПередаче(Заказы)`: свои ПФ, лежащие в дереве заказа под узлом
    «Переработчик»; выпущено по заказу − передано по заказу ≥ 0; Продукция — узел-переработчик.
  - **Пустая** — новая общая передача без строк (подрядчик и склад из диалога); строки — вручную.
  - Подрядчик по умолчанию — `ОсновнойПоставщик` этапов, если у всех один и он субподрядчик.
  - **Повторный расчёт под блокировкой:** перед записью количества пересчитываются той же функцией; рассчитанное
    меньше предпросмотра — отказ без записи и обновлённый предпросмотр («данные изменились, проверьте количества»);
    количество, увеличенное пользователем вручную (`ИзмененоВручную`), — его решение, не сверяется.
  - Проверки строк — общие с записью строки рабочего места; отказ по строке — отказ всего заполнения, ничего не
    записано. Документ проводится, как новый документ рабочего места.
- **Общее поступление:** в режиме нескольких заказов колонка «Передача» строки поступления предлагает передачи всех
  выделенных заказов (`ПередачиЗаказовДляВыбора(Заказы)`, с подрядчиком); строки одной передачи идут в одно
  поступление (ограничение модели); «Заказ» строки — из строки ожидаемой продукции передачи. «+ услуга переработки»
  — на документ, как сейчас.
- **Подрядчик в списках выбора:** `ДокументыСтрокиДляВыбора` (передача), `ДокументыПоступленияИзПереработкиДляВыбора`,
  `ПередачиЗаказаДляВыбора` — «№ от дд.ММ · Подрядчик · заказы»; `ОбработкаПолученияДанныхВыбора` менеджера
  `ПередачаВПереработку` — «Передача №15 от 02.11.2026 · Подрядчик» в быстром выборе поля «Основание» поступления.
  `ОбработкаПолученияПредставления` документа не меняется (отчёты и журналы).

  документы» (образец — АРМ Закупки, `СтраницаСписокПоступлений`).

- **Переработка / Документы** (сборка 3): передачи и поступления — Документ · Дата · Подрядчик · Склад · Заказы ·

- **Переработка / У подрядчиков**: остатки `ТоварыВПереработке` (подрядчик · заказ · клиент · материал · количество ·

- **Выпуски** (сборка 4): ручные выпуски и автовыпуски, с заказом и без; в «Строках» новая строка без заказа —

### Отклонения сборки 1 от плана

- Сравнение с прежним расчётом (`ПрежнийРасчет`) не понадобилось: передача одного заказа и без заказа считает сырьё
  поступления прежним путём целиком (`СырьеПоПродукцииГруппы` без отбора по заказу), по группам — только общая.
- В рабочем месте строки общих документов в сборке 1 **только просматриваются** (и «Статус» по ним запрещён):
  правка строки своего заказа в общем документе на закладке одного заказа перенесена в сборку 2 вместе с режимом
  нескольких заказов — иначе проверки строк пришлось бы писать дважды.
- Ревью плана закрыто решением владельца после 17 кругов без approve; обязательные `ai-review` и `ai-database` по коду
  сборки — в силе.
- Тире «—» в подписях групп печатных форм заменено на «-» (правило BSL LS о символах в модуле).

### Отклонения сборки 2 от плана

- Строки общих документов правятся только в режиме нескольких заказов; на закладке одного заказа они только
  просматриваются (как в сборке 1), «Статус» общего документа из рабочего места не меняется — в форме документа.
  Вопрос «документ содержит строки заказов A, B, C — применить?» не делался: правка общего документа с закладки одного
  заказа задела бы строки чужих заказов без их проверок.
- Строки документов одного заказа в режиме нескольких заказов только просматриваются: запись строки этого режима идёт
  только в общий документ.
- «Пустая» в «Заполнить по потребностям» документ не создаёт: диалог закрывается, на закладке появляется новая строка
  общего документа с подрядчиком и складом диалога — пустой проведённой передачи не бывает.
- Пересчёт перед записью - под исключительной блокировкой выделенных заказов (два заполнения по одним заказам идут по
  очереди; ревью кода сборки 2).

## Тесты

`ТестыДокументов`, новый сценарий `ПереработкаНесколькихЗаказов` (опция «Производство») + расширение сценариев
переработки, автовыпуска S4 и обработчика 2.0.15.48:
- одно-заказная передача и поступление: движения `ТоварыВНаличии`, `ТоварыВПереработке`, себестоимость, стадии —
  **совпадают** с эталоном до изменения (регресс `ПоСтрокам`);
- общая передача двух заказов с общим материалом: приход у переработчика по двум заказам с суммами по строкам;
  `Основание` пусто, в том числе после первой строки; снятие флажка при одном заказе строк → `Основание` = заказ;
- поступление по общей передаче: списание по группам, беззаказная партия не списана дважды, недостача называет заказ;
  себестоимость продукции заказа A — только из сырья A;
- стадии обоих заказов пересчитаны после проведения и отмены; `ПереданоСырьеПереработчику` по каждому заказу;
- автовыпуск: одно-заказная передача — как раньше; многозаказная при нехватке ПФ — отказ с текстом;
- обработчик: заказ строк заполнен по движениям; передача с шапкой, изменённой без перепроведения, — строки по
  движениям, документ в отчёте расхождений, поступление по ней проводится; ремонт расходов; повтор — ни одной записи
  (включая документы без основания); стадия до/после совпадает;
- поступление без основания (историческое, списавшее партию заказа A) — перепроведение и пересчёт последовательности
  проходят, как раньше;
- передача с пустым заказом прихода и шапкой A, поступление по ней списало и чужую партию B — после обработчика шапка
  пуста, перепроведение поступления проходит; стадии A пересчитаны;
- смена заказа одно-заказной передачи A → B в черновике — строки на B; проведённой без перепроведения — отказ, с
  перепроведением — приход у подрядчика по B; при поступлениях — запрет; многозаказный документ с заполненным
  основанием — отказ;
- обработчик: передача с приходом без заказа и шапкой A — шапка очищена (запись при переходе к пустой ссылке),
  повтор — без записей;
- изоляция групп: остатки A=5/B=5, сырьё в поступлении A=6/B=4 — отказ по A;
- комплекты двух заказов с общей составляющей — приход у переработчика по заказам раздельно;
- печать акта: одно-заказный — прежний, многозаказный — заказы в шапке и группы строк;

## Риски

- **Вне волны, в TECHDEBT** (ревью плана, раунд 17, P0): `ТоварыВНаличии.СписатьНоменклатуру` соединяет остаток
  `ДополнительныеРасходы` (без даты партии) с каждой `ДатаПартии` одной партии и списывает издержки по копии на каждую
  дату — удвоение при двух датах у одной партии. Дефект общий для всех расходных документов, не создаётся этой
  волной; правило «издержки — к самой ранней дате» в `ОтразитьПередачу` его не усиливает. Чем ловится: тест «одна
  партия, две даты» на складском расходе; вернуться — отдельной задачей складского модуля.

- **`ПоСтрокам` в передаче** меняет детализацию движений склада у всех передач — регрессия одно-заказного случая
  ловится сверкой движений с эталоном; запасной вариант — пропорциональное деление партий.
- **Ремонт старых расходов** пишет движения регистра в режиме загрузки — `ai-database` обязателен; перед обработчиком
  на клиентской базе — резервная копия (DEPLOY).
- **Порядок блокировок** нескольких заказов — упорядочение по ссылке в проведении и в рабочем месте.
- **Автовыпуск** в многозаказной передаче запрещён — на подтверждение владельцу.
- **Поступление из нескольких передач** не поддерживается — на подтверждение владельцу.
