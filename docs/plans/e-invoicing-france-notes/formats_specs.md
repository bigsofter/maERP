## 1. Factur-X: версия, профили, требуемый профиль, контейнер PDF/A-3

### Takeaway
Актуальная версия — Factur-X 1.09.2 (= ZUGFeRD 2.5.2) от 4 августа 2026 на синтаксисе CII D22B; для французской реформы «socle minimal» (XP Z12-012) составляют профили **EN 16931** и **EXTENDED-CTC-FR**, плюс временно **BASIC WL** (только в Factur-X, до 31/12/2027); **MINIMUM в B2B-обмене после 01/09/2026 не допускается** (остаётся только для Chorus Pro/B2G). Контейнер — PDF/A-3 (ISO 19005-3, любой уровень a/b/u) с одним вложением `factur-x.xml`, AFRelationship на уровне документа, XMP-расширение `urn:factur-x:pdfa:CrossIndustryDocument:invoice:1p0#`.

(Точную строку в нормативном тексте XP Z12-012 не нашёл — см. Gaps.)
- Профиль объявляется дважды — в BT-24 XML и в XMP `fx:ConformanceLevel`; они должны совпадать, иначе валидаторы отклоняют файл — [ma-facture-electronique.org/profils](https://ma-facture-electronique.org/formats-normes/factur-x/profils/), [Factur-X 1.07.2 §6.3](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf).

**Какой профиль требует реформа**
- XP Z12-014: «норма XP Z12-012 описывает использование EN16931 в контексте реформы через 2 основных профиля (EN16931 и EXTENDED-CTC-FR) и один временный профиль, реализованный в смешанном формате Factur-X (BASIC WL)»; профили реализованы в 3 форматах: UBL 2.1, UN/CEFACT CII D22B, Factur-X (PDF/A-3 ISO 19005-3 + вложение CII D22B) — [XP Z12-014 Annexe A §1.1](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf).
- Схематроны «socle», которые предлагает FNFE-MPE: UBL — `EN16931-FR`, `EXT-CTC-FR`; CII — `D22B-EN 16931FR`, `D22B-EXT-CTC-FR`; Factur-X — профили `Basic WL FR`, `EN16931 FR`, `EXT-CTC-FR`; «форматы вне нормы (EDIFACT, расширенные профили выше нормы) — только по двусторонним соглашениям» — [FNFE-MPE Fiche Flash «Utilisation documentation» 2026](https://fnfe-mpe.org/wp-content/uploads/2026/04/Fiche_Flash-Utilisation_documentation.new_.pdf).
- MINIMUM в socle не входит (принимается для B2G на Chorus Pro); BASIC WL — переходный, только в Factur-X, «терпим для депозита PDF до 31 декабря 2027»; платформы обязаны поддерживать EN 16931 и EXTENDED-CTC-FR как основные профили; MINIMUM «выпадает из B2B-потоков после 1 сентября 2026» — [ma-facture-electronique.org/profils](https://ma-facture-electronique.org/formats-normes/factur-x/profils/) (коммерческий сайт; противоречит одиночному блогу donneespersonnelles.fr, утверждавшему, что MINIMUM достаточен — см. результаты поиска, этот блог считаю ненадёжным).
- EXTENDED-CTC-FR добавляет блоки `EXT-FR-FE-BG-01…05` и данные `EXT-FR-FE-XX`, ослабляет часть кардинальностей EN 16931 (affacturage, сложные схемы); дополнительные стороны: FACTURANT, AGENT DE VENDEUR, ADRESSÉ À, AGENT D'ACHETEUR, PAYEUR, BÉNÉFICIAIRE (несколько — только в EXTENDED-CTC-FR); эти стороны «входят в Socle Minimal, который плательщики и PA ДОЛЖНЫ уметь обрабатывать» — [XP Z12-014 Annexe A §1.1–1.2](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf), [ma-facture-electronique.org/Z12-012](https://ma-facture-electronique.org/formats-normes/afnor-z12-012/).

**Контейнер PDF/A-3 (из спецификации Factur-X 1.07.2, §2.2, §6)**
- Factur-X = файл PDF/A-3 (ISO 19005-3 на базе ISO 32000-1); опционально допускается PDF/A-4 (ISO 19005-4). Исходный документ должен быть PDF/A-3-совместим и без вложения; **уровень конформности (3a, 3b, 3u) не важен** — [Factur-X 1.07.2 §2.2, §6](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf).
- Ограничения PDF/A (§6.1): все метаданные в XMP; XMP extension schema обязательна; **все шрифты встроены** (допускаются подмножества); запрещены внешние медиа/бинарники вне механизма A-3; запрещены JavaScript/Flash; только форматы изображений CCITT G3/G4, JBIG2, JPEG, JPEG2000; **документ не должен быть зашифрован, требовать аутентификации или DRM** — там же.
- Вложение (§6.2): MIME-тип всегда `text/xml`; словарь потока должен содержать `Params` с `ModDate`; файл обязан присутствовать в дереве `Names`; имя файла **всегда `factur-x.xml`**, единственное исключение — референсные профили вроде XRECHNUNG (`xrechnung.xml`); на один PDF — только один файл данных счёта; дополнительные сопроводительные файлы можно вкладывать — там же.
- Связь (§6.2.1–6.2.2): массив `AF` на **уровне документа** (не страницы); `AFRelationship` принимает `Data`, `Source`, `Alternative`, `Supplement`; правило выбора: если визуальная часть содержит больше данных, чем XML (MINIMUM, BASIC WL) → `Data`; если PDF сгенерирован из XML → `Source`; если XML и PDF содержат одинаковые данные как два альтернативных представления → `Alternative` — там же. Библиотека Akretion пишет `/Data` по умолчанию (спецификация Factur-X требует Data, а не Alternative, по их changelog v0.4) и позволяет задать `afrelationship` — [github.com/akretion/factur-x](https://github.com/akretion/factur-x).
- XMP (§6.3.1): схема «Factur-X PDFA Extension Schema», URI `urn:factur-x:pdfa:CrossIndustryDocument:invoice:1p0#` (обязателен завершающий `#`), префикс `fx`; поля: `fx:DocumentType` = `INVOICE`; `fx:DocumentFileName` = `factur-x.xml` (должно совпадать с ключом `F` файлового словаря); `fx:Version` = `1.0` (версия XML-схемы данных, не связана с версией спецификации); `fx:ConformanceLevel` ∈ {`MINIMUM`, `BASIC WL`, `BASIC`, `EN 16931`, `EXTENDED`, `XRECHNUNG`} — [Factur-X 1.07.2 §6.3](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf). Пример из спецификации:
  ```xml
  <rdf:Description rdf:about="" xmlns:fx="urn:factur-x:pdfa:CrossIndustryDocument:invoice:1p0#">
    <fx:DocumentType>INVOICE</fx:DocumentType>
    <fx:DocumentFileName>factur-x.xml</fx:DocumentFileName>
    <fx:Version>1.0</fx:Version>
    <fx:ConformanceLevel>EXTENDED</fx:ConformanceLevel>
  </rdf:Description>
  ```
- Свойства `fx:*` не принадлежат предопределённым схемам PDF/A, поэтому без описания в `pdfaExtension` veraPDF даёт ошибку по ISO 19005-3 п. 6.6.2.3.1 — [loslab.com](https://blog.loslab.com/el/delphi-pdf-library/pdflibpas-pdfa3-xmp-extension-schema-facturx.html). Для обратной совместимости поддерживается XMP ZUGFeRD 2.0 (префикс `zf`, `zugferd-invoice.xml`) — [Factur-X 1.07.2 §6.3.2](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf).
- Akretion: при генерации копируются `/OutputIntents` и `/ID` исходного PDF; выход проверен veraPDF — [github.com/akretion/factur-x](https://github.com/akretion/factur-x).

**Типы документов и кредит-ноты в Factur-X (§7.1.6–7.1.7)**
- Допустимые BT-3 (`ram:TypeCode`): 380 счёт, 381 кредит-нота (avoir), 384 корректировочный счёт, 389 самовыставленный счёт (не допускается Chorus Pro), 261 самовыставленный avoir (не допускается Chorus Pro), 386 счёт на аванс (acompte), 751 «информация для бухучёта» (Германия; не допускается Chorus Pro). Во Франции принято кодировать avoir, отменяющий счёт, типом 381 с **положительными** суммами и ссылкой BT-25 на исходный счёт; «отрицательный счёт» (380/384/389/386 с отрицательным итогом) используется, когда это результат расчёта (зачёт авансов, возврат тары); отрицательные кредит-ноты (381/261 с отрицательным TTC) семантической нормой запрещены — [Factur-X 1.07.2 §7.1.6](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf).
- BT-2 кодируется в `udt:DateTimeString @format="102"` (YYYYMMDD) внутри `ram:IssueDateTime` — [Factur-X 1.07.2 §7.1.7](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf).

### Inferences
- Для maERP целевая пара профилей на выдачу: **EN 16931** (базовый) и, для кейсов с третьими сторонами/affacturage/мультипродавцов, **EXTENDED-CTC-FR**; BASIC WL имеет смысл только как переходный приёмный формат до конца 2027. MINIMUM реализовывать не стоит.
- Поскольку Factur-X = CII D22B, а UBL — отдельный синтаксис, экономнее держать одну внутреннюю семантическую модель (BT/BG) и два сериализатора (CII, UBL); Factur-X — это CII-сериализатор + упаковка PDF/A-3.
- Обновления валидационных артефактов идут два раза в год (май/ноябрь) — надо планировать регулярный перенос XSD/Schematron.

### Gaps
- Официальную спецификацию 1.09.2 скачать не удалось (выдаётся по e-mail); разделы о PDF/A-3 и XMP цитируются по немецкой копии 1.07.2 — по вторичным источникам в 1.08–1.09.2 эти разделы не менялись, но это не проверено.
- Точная нормативная строка BT-24 для EXTENDED-CTC-FR в XP Z12-012 (Annexe A, Excel) не получена; есть только пример Akretion.
- Полный список полей профиля EXTENDED-CTC-FR (EXT-FR-FE-BG-01…05) недоступен: текст AFNOR в открытом веб-доступе не воспроизводится (AFNOR запрещает автоматизированную обработку), нужна бесплатная загрузка с boutique.afnor.org.

## 2. Семантическая модель EN 16931: термины, правила, кодовые списки, артефакты валидации

### Takeaway
Модель EN 16931-1 (BT-1…BT-16x, BG-1…BG-3x) остаётся базой; в марте 2026 одобрена EN 16931-1:2026 с идентификатором `urn:cen.eu:en16931:2026`, но все французские профили и валидаторы на октябрь 2026 по-прежнему используют `urn:cen.eu:en16931:2017`. Валидация — два слоя: XSD синтаксиса (UBL 2.1 / CII D16B или D22B) и Schematron бизнес-правил BR-*, BR-CO-*, BR-S/Z/E/AE/K/G/O/IC-*, BR-CL-* из репозитория ConnectingEurope (v1.3.16, апрель 2026), поверх которых — национальные BR-FR.

### Cited Findings
- EN 16931-1:2026 одобрена CEN в марте 2026; идентификатор `urn:cen.eu:en16931:2026`; `urn:cen.eu:en16931:2017` применяется только к экземплярам предыдущей версии; CIUS может добавлять национальные правила, но не противоречить модели — [econnect.eu](https://econnect.eu/en/docs/knowledge/document-formats/formats/en-16931-cius-pint).
- Паттерн идентификаторов: CIUS → `urn:cen.eu:en16931:2017#compliant#<urn CIUS>`, расширение → `#conformant#`; пример Peppol BIS 3: `urn:cen.eu:en16931:2017#compliant#urn:fdc:peppol.eu:2017:poacc:billing:3.0` (правило PEPPOL-EN16931-R004) — [docs.peppol.eu](https://docs.peppol.eu/poacc/billing/3.0/rules/ubl-peppol/PEPPOL-EN16931-R004/); Factur-X использует те же `#compliant#` (BASIC) и `#conformant#` (EXTENDED) — [Factur-X 1.07.2, табл. BT-24](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf).

- Сейчас (октябрь 2026) в BT-24 для Франции надо писать `urn:cen.eu:en16931:2017` (а для EXTENDED-CTC-FR — `#conformant#`-вариант); переход на `urn:cen.eu:en16931:2026` потребует отдельного релиза, когда его примут XP Z12-012 и Factur-X.

## 3. Французская специфика: модель данных DGFiP, cadre de facturation, идентификаторы, cas d'usage

- Acompte / окончательный счёт (кейсы 20–21): счёт на аванс — BT-3 = 386 (avoir на аванс — 503), cadre B1/S1/M1, НДС по каждой строке (при нескольких ставках — пропорциональные строки); окончательный счёт — BT-3 = 380, cadre B4/S4/M4, ссылка на счета аванса в BG-3 (BT-25 номер, BT-26 дата, EXT-FR-FE-02 тип — только EXTENDED-CTC-FR); вариант 1 — строки «reprise d'acompte» с количеством −1 — там же.
- «Уже оплачен» (кейс 2): BT-113 (Paid amount) = BT-112 (Total с НДС), BT-115 = 0, BT-9 = дата платежа; если услуга и НДС по оплате (BT-8 отсутствует или = 72 CII / 432 UBL) — VENDEUR ДОЛЖЕН передать статус «Encaissée» в период e-reporting платежей; плательщик-третье лицо — в блоке PAYEUR (EXT-FR-FE-BG-02) — там же.
- Multi-vendeurs (кейс 39): cadre B8/S8/M8, подстроки типа `GROUP` с VENDEUR и номером унитарного счёта в BT-128 с квалификатором BT-128-1 = `AFL`; автофактурация для multi-vendeurs запрещена — там же.

### Inferences
- Объём «французской надстройки» над EN 16931 для ERP умеренный: ~8 новых реквизитов карточки (SIREN, электронный адрес 0225, cadre de facturation, опция «TVA sur les débits», код VATEX, признак assujetti unique, коды нот), но много **правил**, завязанных на тип операции (biens/services/mixte) и на НДС по оплате.
- Для 1С естественно хранить категорию операции (LB/PS/LBPS) как реквизит документа и вычислять BT-23 из неё + ситуации (аванс, окончательный, уже оплачен), а не вводить код вручную.

### Gaps
- Способ переноса BT-23 в CII (какой элемент) и официальное место в UBL: eConnect кладёт в `AdditionalDocumentReference/DocumentDescription=CADRE_DE_FACTURATION`, DGFiP говорит «BT-23» (в UBL BT-23 = `cbc:ProfileID`, в CII = `ram:BusinessProcessSpecifiedDocumentContextParameter/ram:ID`). Нужно проверить по Annexe A XP Z12-012.
- Полный нормативный список кодов cadre с расшифровкой (включая 9 «bi-directional» и 3 — встречается `S3` в кейсе 11) не найден в первичном источнике.
- Перечень VATEX-кодов FR (franchise en base, régimes de la marge и т.д.) не извлечён.

## 4. Cycle de vie (flux 6): формат сообщения, обязательные статусы, коды

### Takeaway
Статусы передаются сообщением UN/CEFACT **CDAR (Cross Domain Acknowledgement and Response) D22B** с профилем `urn:cpro.gouv.fr:1p0:CDV:invoice`; код статуса — `ProcessConditionCode` (MDT-9), коды 200–214 и 220–228; обязательных к передаче в PPF четыре — **Déposée (200), Rejetée (213), Refusée (210), Encaissée (212)**, причём Encaissée обязателен только когда НДС exigible по оплате (услуги без опции débits, и любые acomptes); для 210 и 213 обязательны код и текст мотива.

### Cited Findings
- XP Z12-012 описывает «как сообщение статуса CDAR (Cross Domain Acknowledgement and Response) должно использоваться конечными пользователями, их PA и PA между собой»; flux 6 между PA и PPF — только обязательные статусы; PPF (CdD) принимает flux 1, flux 10 и flux 6 «для обязательных статусов (Déposée, Rejetée, Refusée, Encaissée)» — [XP Z12-014 Annexe A §1.1](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf).
- Семейства статусов: фаза передачи (создаются PA) — Déposée / Rejetée à l'émission, Émise, Reçue / Rejetée en réception, Mise à disposition — строго в этом порядке; фаза обработки (ставят конечные пользователи) — Refusée, En litige, Suspendue, Complétée, Approuvée, Approuvée Partiellement, Paiement Transmis, Encaissée — независимо; планируется статус «Annulée» для счёта, заменённого rectificative; «Encaissée» обязателен для администрации только если НДС exigible à l'encaissement (услуги без опции débits; **также все счета-acomptes, товары или услуги, даже при опции débits**); при НДС по дебетам Encaissée можно слать, но он уйдёт только покупателю — [XP Z12-014 Annexe A §2.1](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf).
- С v1.1 Z12-014: статус «Déposée» больше не передаётся в PA-R (но всегда в PPF) — [XP Z12-014 Annexe A, история версий](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf).
- Коды (CDAR `ApplicationResponse/DocumentResponse/Response/ResponseCode`, 1..1; у Vertex с префиксом `VRBL:FR:`): 200 Submitted/Déposée (*), 201 Issued by platform/Émise (*), 202 Received by platform/Reçue (*), 203 Made available/Mise à disposition (*), 204 In hand/Prise en charge, 205 Approved/Approuvée, 206 Partially approved, 207 In dispute/En litige, 208 Suspended/Suspendue, 209 Completed/Complétée, 210 Refused/Refusée, 211 Payment sent/Paiement transmis, 212 Payment received/Encaissée, 213 Rejected/Rejetée (*), 214 Reviewed, 220 Cancelled/Annulée, 221 Routing error (*), 224 Direct payment request, 225 Factored, 226 Factored confidential, 227 Change of accounts payable, 228 Non-factored; (*) — генерируются только PA, принимаются как входящие — [developer.vertexinc.com](https://developer.vertexinc.com/einvoicing/docs/france-cii-cdar-d22b-response-code). GOBL даёт те же 200–213 (213 = «Semantically rejected»; 211/212 только для платежей) — [docs.gobl.org fr-ctc-flow6-v1](https://docs.gobl.org/addons/fr-ctc-flow6-v1); Sovos: коды реформы 200–213, мотив (код + текст) обязателен для 210 и 213 — [docs.sovos.com](https://docs.sovos.com/indirect-tax/indirect-tax-products/einvoicing/compliance-network-implementation-guide/france/create-a-document/lifecycle-status-body). Quadient говорит о «14 статусах» и что XP Z12-012 в действующей редакции опубликована AFNOR в июне 2026 — [quadient.com](https://www.quadient.com/fr/blog/cycle-vie-facture-electronique-statuts) (расхождение по числу статусов — см. Gaps).
- Структура CDAR (Sovos): D22B, профиль AFNOR XP Z12-012; три блока: `ExchangedDocumentContext` (профиль `urn:cpro.gouv.fr:1p0:CDV:invoice`), `ExchangedDocument` (ID сообщения, дата-время, отправитель/получатель), `AcknowledgementDocument` (ссылка на счёт: номер, дата, SIREN продавца; `ProcessConditionCode` = код статуса; `ProcessCondition` = текст; опциональные код и текст мотива); при передаче через SBDH CDAR вкладывается Base64 в `<enc:EmbeddedDocument fileName="status.xml" mimeCode="application/xml">` — [docs.sovos.com](https://docs.sovos.com/indirect-tax/indirect-tax-products/einvoicing/compliance-network-implementation-guide/france/create-a-document/lifecycle-status-body).
- Маппинг MDT (GOBL): статус → `ProcessConditionCode` (MDT-9); мотив → `ReasonCode`; тип данных → `CharacteristicTypeCode` (MDT-207): для статусов `CBB, DIV, DVA, MAJ, MAP, MAPTTC, MNA, MNATTC, ESC, RAB, REM`, для платежей `MEN` (encaissé), `MPA` (avis), `RAP` (partiel); действие → `RequestedActionCode` (MDT-121): `NOA, PIN, NIN, CNF, CNP, CNA, OTH`; роли → `RoleCode` (MDT-158): `SE`, `BY`; код статуса = ID документа CDV (`ram:ID`, BR-FR-CDV-03, MDT-4); мотив обязателен при `rejected`, `querying`, `error` (BR-FR-CDV-15) — [docs.gobl.org fr-ctc-flow6-v1](https://docs.gobl.org/addons/fr-ctc-flow6-v1).
- Коды мотивов (≈50): `NON_TRANSMISE` (единственный для 200), `DOUBLON`, `SIRET_ERR`, `JUSTIF_ABS`, `ROUTAGE_ERR`, `COORD_BANC_ERR`, `TX_TVA_ERR`, `MONTANTTOTAL_ERR`, `CALCUL_ERR`, `DEST_INC`/`DEST_ERR`, `CMD_ERR`, `ADR_ERR`, `NON_CONFORME`, `TRANSAC_INC`, `EMMET_INC`, `CONTRAT_TERM`, `DOUBLE_FACT`, `REF_CT_ABSENT`, `REF_ERR`, `PU_ERR`, `REM_ERR`, `QTE_ERR`, `ART_ERR`, `MODPAI_ERR`, `QUALITE_ERR`, `LIVR_INCOMP`, `CODE_ROUTAGE_ERR`, `AUTRE`, `REJ_SEMAN`, `REJ_UNI`, `REJ_COH`, `REJ_ADR`, `REJ_CONT_B2G`, `REJ_REF_PJ`, `REJ_ASS_PJ`, `IRR_*` (файловые нерегулярности); допустимые по статусам: 210 → `TX_TVA_ERR, MONTANTTOTAL_ERR, CALCUL_ERR, NON_CONFORME, DOUBLON, DEST_ERR, TRANSAC_INC, EMMET_INC, CONTRAT_TERM, DOUBLE_FACT, CMD_ERR, ADR_ERR, REF_CT_ABSENT` (+ описание); 213 → `MONTANTTOTAL_ERR, CALCUL_ERR, DOUBLON, DEST_INC, ADR_ERR, REJ_*`; 208 → `JUSTIF_ABS, COORD_BANC_ERR, CMD_ERR, SIRET_ERR, CODE_ROUTAGE_ERR, REF_CT_ABSENT, REF_ERR` — [docs.gobl.org fr-ctc-flow6-v1](https://docs.gobl.org/addons/fr-ctc-flow6-v1).
- Содержание «Encaissée»: ДОЛЖЕН указывать сумму(ы) encaissées по каждой применимой ставке НДС: на каждую ставку — вхождение MDG-43 с MDT-207 = `MEN`, MDT-215 = сумма TTC, MDT-224 = ставка; пример для счёта 1 160 € TTC (600 HT @20 % + 400 HT @10 %): MDG-43 №1 — MEN / 720 / 20 — [XP Z12-014 Annexe A §2.1](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf).
- Обязанности PA-E при ошибке регламентных контролей — отклонить (статус «Rejetée» с мотивом); VENDEUR ДОЛЖЕН сторнировать учёт счёта с «Rejetée»; при «NON_TRANSMISE» PA-E передаёт flux 1 и «Déposée» с этим мотивом в PPF и может потом переслать счёт, когда получатель выберет PA — [XP Z12-014 Annexe A §2.2–2.3](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf).
- Сроки (вторичный источник): PA-E передаёт данные счёта в concentrateur в течение 24 ч после депозита; окно ответа покупателя задаётся его PA, обычно 15–30 дней, затем implicit acceptance; Rejetée/Refusée необратимы, корректируются только avoir/новым счётом — [ma-facture-electronique.org/cycle-de-vie](https://ma-facture-electronique.org/facture-electronique-definition/cycle-de-vie/).
- Между предприятием и его PA формат и частота обмена статусами по e-reporting и «формат возвратов cycle de vie» не регламентированы (контракт/лучшие практики); регламентированы только отношения PA ↔ PPF — [FNFE-MPE Fiche Flash e-reporting](https://fnfe-mpe.org/wp-content/uploads/2026/04/Fiche-Flash-Fonctionnement-e-reportingnew.pdf).

### Inferences
- ERP должна (а) принимать входящие статусы 200–203, 213, 221 по своим исходящим счетам и 203/204…210 по входящим; (б) уметь выставлять исходящие: как покупатель — 204, 205, 206, 207, 208, 210 (с мотивом), 211; как продавец — 209, 212 Encaissée (с разбивкой по ставкам), 214, 220, 225–228 при affacturage. Минимум для сдачи: 210 с мотивом и 212 с суммами по ставкам.
- Поскольку между SC и PA формат не регламентирован, в 1С можно хранить статусы в своей модели и преобразовывать в CDAR/JSON API конкретной PA (XP Z12-013) на уровне коннектора.

### Gaps
- Полный XSD CDAR D22B и путь элементов `ram:*` для MDT-9/MDT-207/MDT-215 не извлечён (Sovos/GOBL дают логические имена; XSD — на unece.org и в пакете spécifications externes).
- Расхождение по числу статусов: Vertex — 22 кода (200–214, 220–228), GOBL/Sovos — 200–213, Quadient — «14 статусов». Вероятно, 214/220+ добавлены в XP Z12-012 v1.3 (июнь 2026?) — требует сверки с нормой.

## 5. E-reporting (flux 10 и данные платежей)

### Takeaway
E-reporting — проприетарный XML AIFE (XSD из пакета spécifications externes, v3.1/3.2): **10.1** — данные международных B2B-счетов (по счёту, со строками для продаж), **10.2** — платежи по ним (по платежу, формат CDAR), **10.3** — B2C-транзакции, агрегированные по дню × валюта × категория (TLB1/TPS1/TNT1/TMA1) × SIREN, **10.4** — платежи B2C по услугам (по дню, CDAR). Исторические «flux 8/9» в V1.x — это семантика e-reporting международных счетов и B2C; сейчас FNFE называет «socle flux 8 / 9» входные счета в UBL/CII/Factur-X, из которых SC строит 10.1/10.3. Периодичность — по режиму НДС (декада / месяц / 2 месяца).

### Cited Findings
- Нормативная база — ст. 290 и 290 A CGI; обязательства: международные B2B продажи и покупки (кроме импорта по DEB), продажи B2C, encaissements по услугам для не выбравших опцию débits; **все авансы (acomptes) декларируются по оплате независимо от режима** — [FNFE-MPE Fiche Flash e-reporting](https://fnfe-mpe.org/wp-content/uploads/2026/04/Fiche-Flash-Fonctionnement-e-reportingnew.pdf).
- Формат файла: «format propriétaire AIFE XML»; B2B international покупки/продажи — выгрузка проведённых данных на уровне счёта с теми же обязательными данными, что и у domestic-счёта (строки обязательны для продаж, не обязательны для покупок); B2C — агрегированные выручки по дню и SIREN, число операций не обязательно; сумма самоначисленного НДС (autoliquidée) ожидается в e-reporting покупок — там же.
- Периодичность (там же):
  | Режим НДС | Транзакции | Срок | Платежи |
  |---|---|---|---|
  | Réel normal mensuel | декады 1–10, 11–20, 21–конец | 10 дней после конца декады | ежемесячно, до 10-го |
  | Réel normal trimestriel | квартал | 10-го следующего месяца | ежеквартально, 10-го |
  | Régime simplifié | месяц | между 25 и 30 следующего месяца | ежемесячно, 25–30 |
  | Franchise en base | 2 месяца | между 25 и 30 следующего месяца | каждые 2 месяца |
  Sovos приводит те же периоды, но «quarterly normal real» описывает как ежемесячную декларацию до 10-го и даёт «TA deadlines» (день после срока, 8:00 CET) — [docs.sovos.com](https://docs.sovos.com/indirect-tax/indirect-tax-products/einvoicing/compliance-network-implementation-guide/france/send-e-reports) (расхождение по квартальному режиму).
- Структура XML (Sovos, pass-through): `ReportDocument` (заголовок: `Id` ≤ 35 символов по AFNOR v1.3, `TypeCode` `IN`/`RE`, `Sender` — платформа, роль `WK`, `Issuer` — SIREN `schemeId="0002"`, `RoleCode` `SE`/`BY`); `TransactionsReport` (10.1, 10.3) и/или `PaymentsReport` (10.2, 10.4) — хотя бы один; 10.1/10.2 — элементы `Invoice` (с вложенными `Payment` для 10.2); 10.3/10.4 — элементы `Transactions` (с `Payment` для 10.4) — [docs.sovos.com](https://docs.sovos.com/indirect-tax/indirect-tax-products/einvoicing/compliance-network-implementation-guide/france/send-e-reports).
- Поля B2C-агрегата (10.3): `Transactions/Date` (TT-77, AAAAMMJJ); `TransactionsCurrency` (TT-78, ISO 4217; все суммы в ней, кроме `TaxTotal`); `CategoryCode` (TT-81): `TLB1` товары с НДС, `TPS1` услуги с НДС, `TNT1` не облагается французским НДС, `TMA1` режим маржи; `TaxExclusiveAmount` (TT-82); `TaxTotal` (TT-83, всегда EUR); `TransactionsCount` (TT-85, опц.); `TaxDueDateTypeCode` (TT-80, опц., опция débits); по ставкам `TaxSubtotal`: `TaxPercent` (TT-86), `TaxableAmount` (TT-87), `TaxTotal` (TT-88, EUR); TT-58/TT-59 (освобождения) для B2C не включать; отчёт — по SIREN (9 цифр), не по SIRET; опциональный `TaxRegistrationId` = `FR` + 2 контрольные + SIREN (13 символов); смешанные операции — по главной; независимые товары и услуги — отдельные `Transactions`; 10.4 только для `TPS1` — там же.
- XSD: папка `[3-XSD...]/[1-E-reporting]` пакета spécifications externes; правила — Annexe 7 (Règles de gestion); схема flux 10 — v3.1 — [docs.sovos.com](https://docs.sovos.com/indirect-tax/indirect-tax-products/einvoicing/compliance-network-implementation-guide/france/send-e-reports); B2Brouter валидирует файл против «официального XSD v3.2» — [docs.b2brouter.net](https://docs.b2brouter.net/en/developers/use-cases-by-country/submit-flux10-ereporting-file/).
- Состав аннексов V1.1 (исторически): Annexe 4 — e-reporting flux 8, Annexe 5 — flux 9, Annexe 6 — flux 10; в текущих версиях на Annexe 6 ссылаются как на «формат e-reporting данных транзакций и платежей» — [impots.gouv.fr](https://www.impots.gouv.fr/node/14441), [XP Z12-014 Annexe A §1.2](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf). FNFE: источники для 10.1 — «facture électronique au format du socle Flux 8 (international) en UBL, CII ou FacturX», для 10.3 — «format du socle 9 (B2C)» или файл кассового ПО — [FNFE-MPE Fiche Flash e-reporting](https://fnfe-mpe.org/wp-content/uploads/2026/04/Fiche-Flash-Fonctionnement-e-reportingnew.pdf).
- Роли: предприятие (через SC) передаёт данные PA «au fil de l'eau» или по согласованной частоте; PA обязана принять 10.1/10.3, передать агрегат за период в CdD по SIREN и по налоговому календарю эмитента, предоставить возвраты cycle de vie DGFiP; контроль унитарных файлов и подготовка агрегаций — опция (может делать SC); платёж B2C — статус «Encaissée» CDAR → 10.4; при acompte декларируется только оплата acompte по услугам; статусы e-reporting: «recevable/irrecevable», «Déposé/Rejeté» — [FNFE-MPE Fiche Flash e-reporting](https://fnfe-mpe.org/wp-content/uploads/2026/04/Fiche-Flash-Fonctionnement-e-reportingnew.pdf).
- Кейс 30 Z12-014: продажа, ушедшая в e-reporting B2C (10.3) и затем оформленная B2B-счётом, кодируется cadre S7/B7/M7 с сохранением продажи в e-reporting — [XP Z12-014 Annexe A §3.2.29](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf).
- Loi de finances 2026 (n° 2026-103 от 19/02/2026, ст. 123) расширяет периметр e-reporting транзакций и усиливает санкции — [KPMG](https://kpmg.com/av/fr/avocats/eclairages/2026/03/facturation-electronique-amenagement-des-obligations-et-renforcement-des-sanctions.html).

### Inferences
- Для ERP минимально нужно: (1) выгрузка 10.1 как «счёт в формате socle» (тот же генератор, что для e-invoicing) для международных продаж/покупок; (2) агрегатор 10.3 — журнал розничных продаж по дню × валюта × категория × ставка; (3) журнал платежей по услугам (10.2/10.4) с привязкой к счетам/дням — фактически те же данные, что «Encaissée» по ставкам.
- Формат между ERP и PA не регламентирован, поэтому конкретный XML 10.x может собирать PA/SC; но данные (по ставкам, по дням, по SIREN) ERP обязана отдавать корректно.

### Gaps
- XSD 10.1 (полный список полей счёта в e-reporting) и 10.2 не извлечён — только по описанию FNFE («те же данные, что domestic-счёт»).
- Точные изменения периметра e-reporting по ст. 123 LF 2026 не раскрыты в доступных источниках.

## 6. Приём входящих счетов: извлечение, разбор, сверка

### Takeaway
Входящий счёт приходит от PA-R в одном из трёх форматов socle; ERP должна извлечь XML из PDF/A-3 (вложение `factur-x.xml` из `AF`/`Names`, с учётом `/Kids` и регистронезависимого имени), распознать профиль по BT-24/XMP, разобрать CII D22B/UBL 2.1 в модель BT и сверять поставщика по SIREN (0002), номер BT-1, дату BT-2, итоги BG-22 и разбивку НДС BG-23; после приёма — выставлять статусы обработки.

### Cited Findings
- Извлечение из PDF: Akretion перечисляет вложения через pypdf, включая `/Kids`; `get_facturx_xml_from_pdf()` ищет имя регистронезависимо; поддерживаются нестандартные имена (XRechnung) и список паттернов; `get_level()` возвращает профиль по URN (ошибка, если URN без «:»); `xml_check_xsd()` — XSD, включая UBL 2.1; `xml_check_schematron()` — через Saxon-сервер — [github.com/akretion/factur-x](https://github.com/akretion/factur-x).
- Исторические имена вложения: `ZUGFeRD-invoice.xml`/`zugferd-invoice.xml` (ZUGFeRD 1.x/2.0), `factur-x.xml` (Factur-X 1.0+), `xrechnung.xml` (XRECHNUNG) — [Factur-X 1.07.2 §6.2, §6.3.2](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf), [github.com/akretion/factur-x](https://github.com/akretion/factur-x).
- Обязанность принимающей стороны и её PA — «уметь обрабатывать форматы и профили socle minimum, в т.ч. EXTENDED-CTC-FR»; покупатель ставит статусы «Refusée», «Prise en charge», «En litige», «Approuvée», «Approuvée Partiellement», «Suspendue» через PA-R; при «Suspendue» продавец может ответить «Complétée» с недостающими элементами — [XP Z12-014 Annexe A §2.1](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf).
- Данные, которые администрация получает по каждому счёту (а значит, должны совпадать у обеих сторон): SIREN поставщика/клиента, страны, BT-23, BT-1, BT-2, BT-116/117/119 по ставкам, BT-109/110, BT-5 — [impots.gouv.fr таблица](https://www.impots.gouv.fr/facturation-electronique-donnees-de-facture-et-correspondance-des-flux-de-donnees).
- Электронные адреса приёма (0225) публикуются в Annuaire; зная SIREN клиента, можно найти все его адреса — [XP Z12-014 Annexe A §1.4](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf). API Annuaire (flux 11/12) и Flow Service (flux 2 отправка/получение, flux 6, flux 10) описаны в XP Z12-013; обязательные для провайдера API: OAuth2, обязательные маршруты Flow Service, domestic B2B-потоки, `GET /healthcheck`; рекомендуемые: webhooks, международные и B2C потоки; `trackingId` для каждого потока; payload — XML или JSON по маршруту; Swagger-контракты (JSON) приложены к норме — [ma-facture-electronique.org/Z12-013](https://ma-facture-electronique.org/formats-normes/afnor-z12-013/).
- Архивирование: «не рекомендуется изменять гибридный счёт для архивирования; по национальным правилам это может быть запрещено, например во Франции с 2024» — [Factur-X 1.07.2 §4](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf).

### Inferences
- Парсер входящих должен быть толерантен к трём синтаксисам (CII D16B/D22B, UBL 2.1 Invoice + CreditNote) и к профилям от BASIC WL до EXTENDED-CTC-FR (неизвестные EXT-FR блоки — сохранять как есть/игнорировать, а не падать).
- Сверка с заказом/поставкой: BT-13 (заказ), BT-16 (накладная), BT-25/26 (исправляемый счёт), BT-113/115 для «уже оплачено», BT-8 для определения момента exigibilité и необходимости слать Encaissée (это — обязанность продавца, но покупателю важно для вычета).

### Gaps
- Нет первичного источника о том, какие именно проверки PA-R обязана делать при приёме (список «contrôles réglementaires» — в Annexe 7 spécifications externes и XP Z12-012, не извлечён).

## 7. Инструменты валидации и известные подводные камни

### Takeaway
Бесплатные валидаторы: Mustangproject (Java, Apache-2.0; поглотил ZUV — проверка PDF/A-3 через veraPDF + XML), KoSIT Validator (референсный в Германии, официальный Schematron), veraPDF (только PDF/A), Schematron/XSLT из ConnectingEurope и FR-схематроны FNFE-MPE (UBL/CII/Factur-X `EN16931-FR`, `EXT-CTC-FR`, `Basic WL FR`). Главные ловушки — порядок округления (строки vs итог), несовпадение BT-24 и `fx:ConformanceLevel`, разбивка НДС по ставкам/категориям, обязательные причины для 0 %/освобождений, авансы и отрицательные значения, а также полугодовая смена версий правил.

### Cited Findings
- Mustangproject — open source (Apache-2.0), генерация и валидация Factur-X/ZUGFeRD; в него влит проект ZUV, проверяющий PDF/A-3 (на базе veraPDF) и XML ZUGFeRD 1/2.x — [interoperable-europe.ec.europa.eu](https://interoperable-europe.ec.europa.eu/collection/eprocurement/solution/mustangproject/news/open-source), [github.com/ZUGFeRD/ZUV](https://github.com/ZUGFeRD/ZUV).
- KoSIT validator — референсный валидатор Германии, запускает официальный Schematron и возвращает точные упавшие правила — [dev.to/facturata](https://dev.to/facturata/your-factur-x-passes-xsd-and-still-gets-rejected-here-is-why-341g).
- Файл может быть валидным PDF/A-3 (veraPDF) и при этом нести XML, не проходящий бизнес-правила: в тесте 4 счёта прошли PDF/A-3 и были отклонены валидатором правил; Mustang отклоняет файл с неверной меткой/URN профиля («invalid conformance value», «unsupported profile type») — [loslab.com](https://blog.loslab.com/en-gb/delphi-pdf-library/pdflibpas-einvoice-verapdf-mustang-validation.html).
- Схематроны FNFE-MPE покрывают только профили нормы XP Z12-012 — [FNFE-MPE Fiche Flash documentation](https://fnfe-mpe.org/wp-content/uploads/2026/04/Fiche_Flash-Utilisation_documentation.new_.pdf); каждое сообщение проходит двойную валидацию — XML-структура, затем французские бизнес-правила — [ma-facture-electronique.org/Z12-012](https://ma-facture-electronique.org/formats-normes/afnor-z12-012/).
- Округление: пример 3 строки по 19,99 при 20 % — округление по строкам даёт нетто 59,97 и НДС 12,00; сумма-потом-налог даёт 59,97 × 0,20 = 11,994 → 11,99; полцента расхождения достаточно, чтобы упасть на BR-CO-17; мультиставочные счета часто ломают BR-S-08; 0 %/exempt без кода причины — отказ; совет: тестировать credit notes, corrections, авансы + финальный счёт с зачётом, мультиставку, reverse charge, self-billing, освобождения; закреплять версию правил и во время перехода валидировать против текущей и предыдущей — [dev.to/facturata](https://dev.to/facturata/your-factur-x-passes-xsd-and-still-gets-rejected-here-is-why-341g).
- В EXTENDED допускались неточности округления (ZUGFeRD 2.3.2), не во всех предыдущих версиях; 1.09.2 исправляет правила разбивки НДС, округления и кардинальность НДС на строке в EXTENDED — [vatupdate](https://www.vatupdate.com/2026/08/11/germany-and-france-update-zugferd-2-5-for-2026-e-invoicing-compliance/), [dev.ferd-net.de](https://dev.ferd-net.de/publikationen-produkte/publikationen/detailseite/zugferd-232-english).
- Правила округления сумм описаны в XP Z12-012 — [ma-facture-electronique.org/Z12-012](https://ma-facture-electronique.org/formats-normes/afnor-z12-012/).
- Авансы/acomptes: НДС по каждой строке аванса, при нескольких ставках — пропорциональные строки; окончательный счёт — строки «reprise d'acompte» с количеством −1 (вариант 1) или иной вариант; негативные кредит-ноты запрещены, негативные счета допустимы только как результат расчёта — [XP Z12-014 Annexe A кейсы 20–21](https://fnfe-mpe.org/wp-content/uploads/2025/11/XP_Z12-014_CAS_USAGE_Annexe_A_V1.2.pdf), [Factur-X 1.07.2 §7.1.6](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf).
- Валидационные артефакты: UBL/CII v1.3.16 с исправлениями по allowance/charge (#491), monetary summation (#492), BT-123 (#493), BR-CO-25/26/27 — [GitHub release v1.3.16](https://github.com/ConnectingEurope/eInvoicing-EN16931/releases/tag/validation-1.3.16); Peppol Authority NL сделал артефакты мая 2026 (v1.3.16) обязательными с 17/08/2026 — [vatupdate](https://www.vatupdate.com/2026/05/31/may-2026-npa-validation-artefacts-for-si-ubl-2-nlcius-and-peppol-bis-3-mandatory-from-17-august-2026/) (вторичный).
- Библиотеки с реализованными правилами: Akretion factur-x (Python; XSD/Schematron 1.0.5…1.0.9, UBL 2.1) — [github](https://github.com/akretion/factur-x); GOBL fr-ctc (Go; BR-FR-xx, коды cadre, CDAR) — [docs.gobl.org](https://docs.gobl.org/addons/fr-ctc-flow2-v1.md); Mustang (Java); Securibox.FacturX (.NET) — [nuget](https://packages.nuget.org/packages/Securibox.FacturX).

### Inferences
- В 1С стоит заложить политику округления «сначала строки до 2 знаков, затем суммы по ставкам = сумма строк, НДС по ставке = round(база × ставка/100, 2)» и прогонять каждый сгенерированный XML через внешний Schematron (Saxon/XSLT) в тестовом контуре; смок-тест «сформировать все печатные формы» надо дополнить «сгенерировать и провалидировать все e-invoices».
- Песочницы PA (sandbox) — в источниках не найдены как общедоступные; для приёмочных тестов потребуется договор с конкретной PA.

### Gaps
- Онлайн-валидатор FNFE-MPE как отдельный сервис в источниках не обнаружен; есть только схематроны для скачивания.
- Официальных открытых sandbox-ов PPF/PA с публичной документацией не найдено.

## 8. Подпись и целостность: нужна ли ЭП

### Takeaway
Электронная подпись **не требуется**: ст. 289 V CGI требует гарантировать authenticité, intégrité, lisibilité, а 289 VII даёт выбор — 1° piste d'audit fiable, 2° signature électronique (qualifiée) / cachet, 3° EDI-сообщение; обмен через PA под ст. 289 bis этих требований не отменяет, но в LF 2026 были поправки о замене ссылки на PAF ссылкой на 289 bis для электронных счетов — их судьба в итоговом тексте по открытым источникам не подтверждена. ERP ничего подписывать не обязана; Factur-X сам по себе — PDF без подписи.

### Cited Findings
- Ст. 289 V CGI: authenticité de l'origine, intégrité du contenu, lisibilité — от эмиссии до конца срока хранения; VII: 1° любая техническая форма (электронная или бумажная) при наличии документированных и постоянных контролей, устанавливающих piste d'audit fiable; 3° структурированное сообщение по норме, согласованной сторонами (EDI); версия в силе с 31/12/2023 — [legifrance.gouv.fr art. 289](https://www.legifrance.gouv.fr/codes/article_lc/LEGIARTI000048827413) (прямой fetch вернул 403; по сниппетам поиска и BOFiP).
- BOFiP (BOI-TVA-DECLA-30-20-30-10): три способа — «contrôles établissant une piste d'audit fiable», «signature électronique avancée fondée sur un certificat qualifié», «EDI»; метод «peut être différente entre l'émetteur et le récepteur»; получатель подписанного счёта хранит подпись и сертификат в сроки L. 102 B LPF — [bofip.impots.gouv.fr](https://bofip.impots.gouv.fr/bofip/8862-PGP.html/identifiant=BOI-TVA-DECLA-30-20-30-10-20180207). Вторичный комментарий добавляет cachet électronique qualifié как вариант (четыре процедуры) — результаты поиска, блоги.
- Factur-X §4: для authenticité/intégrité/lisibilité — либо квалифицированная подпись/печать на PDF-конверте, либо документированные контроли (PAF); EDI-режим к гибридному счёту применим только к компоненту `factur-x.xml` при AFRelationship `Alternative` или `Source` — [Factur-X 1.07.2 §4](https://easyfirma.net/wp-content/uploads/2024/12/1.-FACTUR-X-1.07.2-DE.pdf).
- LF 2026: поправки к ст. 28 PLF 2026 предлагали в 1° VII ст. 289 заменить упоминание piste d'audit fiable ссылкой на ст. 289 bis (мотив — избыточность для электронных счетов); одна поправка Сената внесена, другая отозвана, поправка АН не поддержана; подтверждения принятия в итоговом тексте нет — [senat.fr Amdt I-1576](https://www.senat.fr/enseance/2025-2026/138/Amdt_I-1576.html), [senat.fr Amdt I-1940](https://www.senat.fr/enseance/2025-2026/138/Amdt_I-1940.html), [assemblee-nationale.fr CF1429](https://www.assemblee-nationale.fr/dyn/17/amendements/1906A/CION_FIN/CF1429.pdf).
- Ст. 123 LF 2026 (loi n° 2026-103 от 19/02/2026) изменила ст. 289 bis, 289 E, 290, 290 A, 290 B; décret n° 2026-677 от 27/07/2026 изменил ст. 242 nonies B и сл. annexe II, arrêté от 27/07/2026 — ст. 41 septies A и сл. annexe IV; вступление в силу 29/07/2026; декрет уточняет правила для PA, их иммatriculation и обязанности аудита — [lemondedudroit.fr](https://www.lemondedudroit.fr/fiscal/309-fiscalite-des-entreprises/105345-generalisation-de-la-facturation-electronique.html), [lexisveille.fr](https://lexisveille.fr/node/81454).
- Срок хранения электронных счетов — 6 лет (BOFiP) — [bofip.impots.gouv.fr BOI-CF-COM-10-10-30](https://bofip.impots.gouv.fr/bofip/645-PGP.html/identifiant=BOI-CF-COM-10-10-30-20250903).

### Inferences
- Для maERP достаточно piste d'audit fiable (связь заказ → поставка → счёт → платёж в учёте) и неизменяемого хранения принятых/отправленных файлов «как есть»; модуль ЭП не нужен. Если клиент захочет cachet/подпись — это функция PA/внешнего сервиса, не ERP.

### Gaps
- Актуальный консолидированный текст ст. 289 VII после LF 2026 и décret 2026-677 не получен (Légifrance 403); не подтверждено, сохранилось ли упоминание PAF в 1° VII.
- Суммы санкций по ст. 123 LF 2026 в открытых источниках не найдены.
