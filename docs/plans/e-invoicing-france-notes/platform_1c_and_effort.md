## Вопрос 1. Умеет ли платформа нативно делать PDF/A-3 с вложенным XML (требование Factur-X)?

### Takeaway
Да, на уровне «PDF/A-3 + вложение с MIME-типом и типом связи (AFRelationship)» платформа это умеет штатно с линейки 8.3.15–8.3.16, а объект `ДокументPDF` (8.3.21+) закрывает чтение/запись/подпись; maERP работает в режиме совместимости 8.5.1, то есть всё это доступно. Не подтверждено главное для валидного Factur-X — запись пользовательских XMP-метаданных (схема `fx:` с `ConformanceLevel`, `DocumentFileName`, `DocumentType`, `Version`): в списках изменений платформы такой возможности нет, это надо проверять экспериментом на сборке.

### Inferences
- Технически цепочка «печатная форма → `ТабличныйДокумент.Записать(…, ТипФайлаТабличногоДокумента.PDF_A_3)` с коллекцией вложений, где `ВложениеPDF.ТипСодержимого = "text/xml"`, `ТипСвязи` = значение `ТипСвязиВложенияPDF`, соответствующее `/Alternative`», реализуема без внешних компонент (вывод из записей 8.3.15/8.3.16 и 8.3.23). Нужно проверить, есть ли в `ТипСвязиВложенияPDF` именно `Alternative` (у Factur-X профиль EN 16931 требует `/Alternative`; у MINIMUM/BASIC WL — `/Data`), и допускает ли платформа имя вложения `factur-x.xml`.
- Критическая развилка — XMP: ни одна запись в списках изменений 8.3.14–8.3.27 не упоминает запись произвольных XMP-метаданных в PDF (единственное упоминание XMP — про GIF-картинки). Без `fx:`-схемы файл будет валидным PDF/A-3 с вложением, но валидаторы Factur-X (Mustang, factur-x) его отвергнут. Вероятные пути: (а) эксперимент — записать PDF_A_3 с вложением из 1С и прогнать через `Mustang-CLI --action validate` и `facturx-xmlcheck`/pdfgen; (б) если XMP не пишется — постобработка внешним инструментом или сборка Factur-X на стороне PA (см. вопрос 2). Оценивать трудозатраты надо с резервом на этот эксперимент (1–3 дня) и на план Б.
- Поскольку maERP ещё не использует PDF-объекты платформы, «нативный» путь не имеет локального опыта; первые шаги — это прототип, а не доработка.

### Gaps
- Нет официального подтверждения (ни в списках изменений, ни в найденных публикациях), что `ЗаписьPDF`/`ДокументPDF` умеют писать пользовательские XMP-метаданные; нужен эксперимент или синтаксис-помощник 8.5.1.
- Состав значений перечисления `ТипСвязиВложенияPDF` не найден в открытых источниках (поиск по ITS/Infostart не дал страниц); проверяется в синтаксис-помощнике.
- Умеет ли `ДокументPDF` объединять документы/страницы — в списках изменений не найдено; Infostart-публикации 1844363 и 1731973 были недоступны для чтения (429).
- Точная версия появления PDF/A-2/A-3 (8.3.15 или 8.3.16) определена по заголовкам кумулятивного файла; файлов 8.3.14/8.3.15 я не скачивал.

## Вопрос 2. Если нативного Factur-X не хватает — какие обходные пути и что делают PA?

### Takeaway
Есть три рабочих пути: сторонние CLI (Java Mustang `--action combine`, Python `facturx-pdfgen`) через `ЗапуститьПриложение`; делегирование сборки Factur-X самой платформе-агрегатору (Pennylane прямо обещает конвертацию в Factur-X для «не API-ready» решений, Odoo как PA отправляет только UBL); или полностью структурированная эмиссия UBL/CII без гибридного PDF (для B2B в рамках реформы это допустимо, так как PA обязаны принимать все три формата). Для небольшого ERP наиболее дешёвый минимум — генерировать UBL или CII XML + обычный PDF и отдавать PA.

### Cited Findings
- Mustangproject (Java, Apache-2.0) — библиотека и CLI для создания, чтения и валидации Factur-X/ZUGFeRD; CLI `--action combine` объединяет готовый PDF/A и XML; `--action validate` проверяет; релиз в Maven Central от 6 августа 2026 — [MVN Repository](https://mvnrepository.com/artifact/com.github.ZUGFeRD.mustangproject/library); [Linuxhotel wiki, пример combine](https://wiki.lab.linuxhotel.de/doku.php/intern:xrechnung); [список Gambas с командой `java -jar Mustang-CLI-2.10.0.jar --action combine` и предварительным Ghostscript `-dPDFA=3`](https://lists.gambas-basic.org/archive/user/2024-07/0000096.html).
- Python `factur-x` 7.7 (релиз 14 октября 2026, BSD, автор Alexis de Lattre): генерирует Factur-X/Order-X из обычного PDF + XML, извлекает XML, валидирует по XSD и Schematron; CLI `facturx-pdfgen`, `facturx-pdfextractxml`, `facturx-xmlcheck`; на pypdf; полное соответствие PDF/A-3 — только если входной PDF уже PDF/A — [PyPI factur-x](https://pypi.org/project/factur-x/).
- Akretion ведёт `pyfrctc` — «Python lib for eInvoicing and eReporting in France», создана 16 апреля 2026, используется community-модулями Odoo, помечена как alpha — [github akretion/pyfrctc](https://github.com/akretion/pyfrctc).
- Pennylane (PA, immatriculation сентябрь 2024, окончательная — декабрь 2025) для издателей ПО: «0 € … API REST AFNOR», «конвертация форматов, включая Factur-X для решений, которые не API-ready», конвертация в «Factur-X, EDI, PDF signé, UBL, CII»; подключение 2–4 недели; grey label (не white label); только французские клиенты, международное — через Peppol — [Pennylane, Solutions Compatibles](https://www.pennylane.com/fr/facture-electronique-scpa).
- Odoo — сама PA; «принимает Factur-X, UBL и CII, отправляет исключительно в UBL» — [Odoo docs 19.0, France](https://www.odoo.com/documentation/19.0/applications/finance/fiscal_localizations/france.html).
- Dolibarr в своём модуле не рекомендует Factur-X для отправки: «ограниченная поддержка у точек доступа, большие файлы, труднее отлаживать»; CII поддержан с v18, Factur-X только с v24+, UBL не реализован — [Dolibarr wiki, Module EInvoicing/PDPConnectFR](https://wiki.dolibarr.org/index.php/Module_PDPConnectFR).
- Все PA обязаны обрабатывать три формата: Factur-X (профили до EXTENDED), UBL, CII — [Indy](https://www.indy.fr/guide/facturation/electronique/format-facture-x-ubl-cii/); для эмиссии через PA допустимы профили, согласованные с EN 16931 (BASIC, EN 16931, EXTENDED при соблюдении требований) — [Agicap](https://agicap.com/fr/article/factur-x-definition-utilite/). Это вторичные (коммерческие) источники.
- 1С: внешняя компонента или GitHub-проект на BSL для Factur-X/ZUGFeRD по поиску не обнаружены; найденные библиотеки — .NET (`ZUGFeRD-csharp`), TypeScript (`@stackforge-eu/factur-x`) — [результаты поиска](https://www-1.nuget.org/packages/ZUGFeRD-csharp/7.0.1), [jsr.io](https://jsr.io/@stackforge-eu/factur-x/1.4.0/README.md).
- maERP уже вызывает `ЗапуститьПриложение` в 2 местах (grep по `src/cf/src`), то есть вызов внешнего CLI не будет новым типом зависимости, но потребует установки Java/Python у клиента.

### Inferences
- Для PME-ERP с файловыми базами внешние CLI (Java, Python) — это дополнительная установка на каждом рабочем месте или сервере; это удорожает поставку и поддержку. Делегирование сборки Factur-X платформе PA снимает проблему XMP/PDF/A полностью, ценой зависимости от конкретной PA и её API.
- Самый дешёвый минимум для эмиссии: XML UBL 2.1 (как Odoo) или CII через `ЗаписьXML` (в maERP 33 использования) + PDF печатной формы, передаваемые PA; гибрид Factur-X становится «nice to have» на стороне ERP.

### Gaps
- Нет публичной документации API Iopole/SuperPDP/EsaLink, чтобы подтвердить, что именно они принимают «PDF + XML раздельно» и собирают Factur-X сами; найдены только маркетинговые страницы (Pennylane, Tiime).

## Вопрос 3. XML/JSON/HTTP/OAuth2/вебхуки в 1С и следствия для развёртывания

### Takeaway
Генерация и разбор XML/JSON, Base64, HTTP-клиент — штатные; OAuth2 в платформе встроен только для почты (IMAP/SMTP), для REST его реализуют вручную через `HTTPЗапрос`; приём вебхуков требует HTTP-сервиса, опубликованного на веб-сервере (Apache/IIS), что для файловых баз малых клиентов означает дополнительный компонент инфраструктуры — альтернатива polling регламентным заданием.

### Cited Findings
- Платформа поддерживает OAuth2 для почты: «реализована поддержка протокола OAuth2 в случае использования протокола SMTP. Для аутентификации используется свойство `ИнтернетПочтовыйПрофиль.ТокенДоступа`. … протокол OAuth2 использовался только для протокола IMAP» — [1cv8upd 8.3.27.1559](https://dl03.1c.ru/content/Platform/8_3_27_1559/1cv8upd_8_3_27_1559.htm). Упоминаний OAuth2 для `HTTPСоединение` в списках изменений нет.
- Практика OAuth2 client_credentials в 1С — вручную: `Новый HTTPСоединение`, тело `grant_type=client_credentials`, заголовок `Content-Type: application/x-www-form-urlencoded`, `ВызватьHTTPМетод("POST", Запрос)` — [форум Infostart](https://forum.infostart.ru/forum15/topic237318/); статьи [Infostart 889724](https://infostart.ru/public/889724/), [Infostart 1817924](https://infostart.ru/public/1817924/) (авторизация собственного HTTP-сервиса по токену).
- HTTP-сервисы в файловой базе публикуются через «Администрирование → Публикация на веб-сервере», требуется установленный веб-сервер (например, Apache) — [Infostart 1885817](https://infostart.ru/1c/articles/1885817/); адрес вида `домен/ИмяБазы/hs/ИмяСервиса/…`, обработчики POST/GET — [Habr 488374](https://habr.com/en/articles/488374).
- При добавлении нового HTTP-сервиса файл публикации перезаписывается и ранее настроенные объекты могут пропасть — [форум Infostart](https://forum.infostart.ru/forum9/topic269139/message2717201/); сервисы из расширений не попадают в публикацию без флага — [форум Infostart](https://forum.infostart.ru/forum9/topic230966/).
- По норме AFNOR XP Z12-013 вебхуки уведомлений — только рекомендация, обязательны аутентификация и REST «API Flux» (отправить, найти, получить поток); часть PA требуют OAuth 2.0, другие — логин/пароль — [ma-facture-electronique.org, API PA](https://ma-facture-electronique.org/formats-normes/api-plateforme-agreee/) (сайт с партнёрскими ссылками, см. оговорку в вопросе 7).
- Odoo-модуль `l10n_fr_pdp` содержит `controllers/webhooks.py` и `data/ir_cron.xml` — то есть использует и вебхуки, и периодические задания — [дерево odoo/addons/l10n_fr_pdp, 19.0](https://github.com/odoo/odoo/tree/19.0/addons/l10n_fr_pdp).
- maERP (grep по `src/cf/src`): `Новый ЗаписьXML` — 33, `ФабрикаXDTO` — 6, `Новый ЧтениеJSON` — 6, `Base64Строка` — 5; обращений к `HTTPСоединение`/`HTTPЗапрос` — 0; каталогов `HTTPServices`/`WebServices` в конфигурации нет; `МенеджерКриптографии`/`ЭлектроннаяПодпись` — 0; регламентных заданий — 7.

### Inferences
- Исходящий HTTP-клиент с OAuth2 для maERP — новый слой (нет ни одного `HTTPСоединение`), но типовой по сложности: 1–2 общих модуля.
- Для файловых баз у малых клиентов разумная архитектура — polling статусов регламентным заданием (в файловой базе регламентные задания выполняются в сеансе пользователя или отдельной сессии), а не вебхуки; если PA требует вебхуки для какого-то потока — потребуется публикация на веб-сервере, чего в maERP сейчас нет.
- Электронная подпись для реформы не обязательна (норма допускает «PDF signé» как один из вариантов, но Odoo/Dolibarr её не используют для B2B-потока); отсутствие криптографии в maERP не блокер.

### Gaps
- Не найдена официальная страница ITS по публикации HTTP-сервисов с текстом (в выдаче только оглавления).
- Поведение регламентных заданий в файловой базе под 8.5.1 (автономный запуск) в этом ресёрче не проверялось.

## Вопрос 5. Паттерн 1С-ЭДО / БЭД (подсистема «Обмен с контрагентами») как образец архитектуры

- Трудозатраты Odoo на `l10n_fr_pdp` (без учёта `account_edi_ubl_cii` и `account_peppol`, сделанных ранее) по коммитам/авторам/объёму кода можно грубо оценить как 2–4 разработчика на протяжении ~6 месяцев (декабрь 2025 — июнь 2026 до стабильного состояния и бэкпорта); при этом у Odoo уже были генератор/парсер UBL/CII (с 2022) и Peppol-инфраструктура (с 2023). Для команды, у которой ни того, ни другого нет, объём работ складывается: генератор+валидация EN 16931 (аналог `account_edi_ubl_cii`, у Odoo ~0,9 МБ Python, но с множеством стран) + французский поток.
- Dolibarr: ~1 800 коммитов за 4 месяца двумя основными авторами при ещё не сделанном e-reporting указывает на интенсивный, не завершённый проект порядка 8–12 человеко-месяцев к октябрю 2026 (оценка по активности, не по данным авторов).
- Цифры PA (2–4 недели, 4–8 недель) относятся только к транспортному слою и тестам с одной PA, при условии, что XML и маппинг уже готовы; их нельзя принимать за весь проект.

### Gaps
- Нет ни одного первичного источника с человеко-месяцами от вендора ERP (Odoo, Sage, Cegid, EBP, Axonaut); французская пресса о пилоте описывает отрасль, а не трудозатраты.
- Немецкие и польские бенчмарки относятся к внедрению у клиента, а не к разработке у вендора.

## Вопрос 7. Что требует онбординг ISV у PA, пилот DGFiP, нормы AFNOR

### Takeaway
Для «Solution Compatible» (бывший OD) формальной сертификации DGFiP нет — конформность проверяет PA в своей sandbox (тестовая среда, тесты эмиссии/приёма, затем продакшен); регуляторная база — спецификации DGFiP v3.2 (30.04.2026) плюс нормы AFNOR XP Z12-012 (форматы и статусы), XP Z12-013 (API, бесплатно на сайте AFNOR), XP Z12-014 (кейсы использования, ~44 в версии февраля 2026); пилот шёл с 26 февраля по конец августа 2026, старт 1 сентября дал 2,5 млн потоков за неделю и четырёхкратный рост отказов — отказы почти всегда из-за новых обязательных реквизитов.

### Cited Findings
- Официальная страница DGFiP: версии внешних спецификаций — 3.2 (30/04/2026), 3.1 (31/10/2025), 3.0 (18/12/2024), 2.4 (19/06/2024, есть англ.), …, 1.0 (30/09/2021); приложения: семантика потоков 1 и 2, CDV (статусы), справочник, e-reporting (потоки 8, 9, 10), правила управления; нормы AFNOR XP Z12-012 (форматы/профили счетов и статусов), XP Z12-013 (API между ИС предприятий и PA), XP Z12-014 (кейсы B2B) — загружаются бесплатно с сайта AFNOR; Chorus Pro — отдельные спецификации — [impots.gouv.fr, spécifications externes](https://www.impots.gouv.fr/specifications-externes-b2b).
- По KPMG: версия 3.0 больше не описывает форматы, сообщения жизненного цикла и кейсы — они переданы комиссии AFNOR (создана в январе 2025, под надзором Peppol-authority); тесты интероперабельности для окончательной регистрации PA начались только в конце 2025, обновления форматов шли весь 2025 год — [KPMG Avocats](https://kpmg.com/av/fr/avocats/eclairages/2024/12/facturation-electronique-nouvelles-precisions-sur-le-deploiement-de-la-reforme.html).
- Количество кейсов использования: 44 в версии февраля 2026 — [blog Tiime](https://blog.tiime.fr/cas-d-usage-facturation-electronique); «около тридцати» — [comparepdp](https://comparepdp.com/articles/cas-usage-facturation-electronique). Расхождение не разрешено.
- XP Z12-013: обязательны аутентификация и REST «API Flux» (отправить/найти/получить поток) для регламентированных внутренних счетов; рекомендации — вебхуки, тонкие права, потоки B2C/международные, «API Métier»; всего около 30 кодов статусов, четыре обязательны к передаче администрации: «déposée», «rejetée», «refusée», «encaissée»; версии: май 2025, 1.1 — сентябрь 2025, пересмотр 26.02.2026; применение нормы добровольно; 149 зарегистрированных операторов на 22.09.2026; >200 000 адресов в центральном справочнике на начало 2026 — [ma-facture-electronique.org, API PA](https://ma-facture-electronique.org/formats-normes/api-plateforme-agreee/). Оговорка: сайт с партнёрскими ссылками (Pennylane, Indy). По другой странице того же сайта, 84 % PA в опросе DGFiP от 5.05.2026 подтвердили реализацию XP Z12-013 — [ma-facture-electronique.org, AFNOR Z12-013](https://ma-facture-electronique.org/formats-normes/afnor-z12-013/). Магазин AFNOR показывает действующую версию XP Z12-013 от июня 2026 (44 стр.), предыдущая отменена — [AFNOR boutique](https://www.boutique.afnor.org/fr-fr/norme/xp-z12013/api-pour-interfacer-les-systemes-dinformations-des-entreprises-avec-les-pla/fa301170/601639).
- Переименование: с июля 2025 DGFiP называет бывшего «opérateur de dématérialisation» (OD) «solution compatible» (SC) — [expert-comptable-tpe.fr](https://www.expert-comptable-tpe.fr/articles/facturation-electronique/); «Solution Compatible» — издатель не становится PA, а подключает ПО к существующей — [codeur.com](https://www.codeur.com/blog/plateforme-agreee-editeur-de-logiciels/).
- Iopole для издателей: «полный API и выделенная sandbox для тестов и POC», сопровождение для ускорения «сертификации Solution Compatible»; модели white label (издатель сам становится PA) и Solution Compatible — [munci.org](https://www.munci.org/comment-les-editeurs-de-logiciels-sadaptent-a-la-reforme-de-la-facturation-electronique/), [francenum.gouv.fr, Iopole](https://www.francenum.gouv.fr/activateurs/iopole). Публичной документации API Iopole поиском не найдено.
- Pennylane: онбординг издателя — интеграция API → тесты в выделенной среде → продакшен, маркетинг-кит; участие в пилоте DGFiP с февраля 2026; член рабочих групп AFNOR — [Pennylane SCPA](https://www.pennylane.com/fr/facture-electronique-scpa).
- Odoo (как PA) при настройке требует аутентификацию легального представителя по e-mail с проверкой личности и электронной подписью аттестации о назначении платформы, подтверждение SIREN, настройку журнала входящих, опции e-reporting/PPF и периодичности e-reporting; модуль форсирует 2FA — [Odoo docs 19.0](https://www.odoo.com/documentation/19.0/applications/finance/fiscal_localizations/france.html); [коммит «Force 2FA when pdp installed»](https://github.com/odoo/odoo/commits/18.0/addons/l10n_fr_pdp).
- Пилот: запущен 26 февраля 2026 — [LégiFiscal](https://www.legifiscal.fr/actualites-fiscales/4444-facturation-electronique-phase-pilote-demarre.html); длился до конца августа 2026, в реальных условиях с настоящими счетами и платежами — [comparateur-efacturation.fr](https://comparateur-efacturation.fr/blog/pilote-facturation-electronique-lance-fevrier-2026).
- Старт 1 сентября 2026 (по данным, приписываемым бюллетеню AIFE/DGFiP для PA от 3 сентября 2026): 1–7 сентября PPF получил >2,5 млн потоков, пик ≈700 тыс. 3 сентября; менее половины крупных компаний выпустили первый электронный счёт; ежедневная доля отказов выросла в 4 раза за неделю; отказы почти всегда связаны с реквизитами, добавленными реформой; на запуске 118 PA зарегистрированы/в проверке, 101 подключена к концентратору PPF — [comparatif-facture-electronique.fr, bilan de démarrage](https://www.comparatif-facture-electronique.fr/bilan-demarrage-facturation-electronique-premiers-chiffres/) (вторичный источник; сам бюллетень не найден).
- Число PA в разных источниках: 134 на 26.05.2026 ([ma-facture-electronique.org](https://ma-facture-electronique.org/reforme-2026/dgfip-role/)), 149 на 22.09.2026, 156/166 на сентябрь 2026 — цифры расходятся; официальный список — на impots.gouv.fr — [impots.gouv.fr, plateformes agréées](https://www.impots.gouv.fr/facturation-electronique-et-plateformes-agreees).
- Провизорная vs окончательная регистрация PA: окончательная даётся после успешных тестов интероперабельности в реальных условиях — упоминается в выдаче по Odoo ([digitiz.fr](https://digitiz.fr/odoo-facturation-electronique/)) и в совете Tiime проверять статус «définitive» — [blog Tiime](https://blog.tiime.fr/api-facturation-electronique-gestion).

### Inferences
- Для maERP как «Solution Compatible» критический путь онбординга — не регулятор, а sandbox конкретной PA: 2–4 недели интеграции + 4–8 недель тестов (по заявлениям PA), то есть ~2–3 календарных месяца транспортного слоя после готовности XML.
- Поскольку XP Z12-013 не обязателен и 16 % PA его не реализуют, выбор PA, реализующей норму, снижает риск привязки к одному API.

### Gaps
- Нет текста XP Z12-013/014 (скачивание требует регистрации на AFNOR) — список обязательных эндпоинтов и 44 кейсов не проверен по первоисточнику.
- Официальный бюллетень AIFE/DGFiP от 3 сентября 2026 не найден в открытом доступе.

## Вопрос 8. Минимальный жизнеспособный объём для PME-ERP к сентябрю 2026 (приём) и сентябрю 2027 (эмиссия PME)

### Takeaway
Приём (уже обязателен с 1 сентября 2026): получать от PA входящие документы в трёх форматах (Factur-X, UBL, CII), разбирать и создавать документ поступления с сопоставлением поставщика/товаров, отправлять статусы приёма/отказа. Эмиссия (для PME с 1 сентября 2027): генерировать EN 16931-совместимый XML (UBL или CII) с французскими обязательными реквизитами (SIREN, VATEX при 0 %, категория операции товары/услуги/смешанная, аванс/финальный счёт, кредит-ноты), отдавать PA вместе с PDF, вести жизненный цикл по ~30 кодам (минимум 4 обязательных), и e-reporting (потоки 8/9/10) — последнее Dolibarr отложил на 2027.

### Cited Findings
- Календарь: с 1 сентября 2026 все компании обязаны принимать внутренние B2B электронные счета через PA; GE и ETI одновременно обязаны выпускать и передавать e-reporting (B2C, международный B2B); с 1 сентября 2027 те же обязанности у PME и микропредприятий; операции, освобождённые по ст. 261–261E, исключены — [Odoo docs 19.0](https://www.odoo.com/documentation/19.0/applications/finance/fiscal_localizations/france.html); подтверждение дат — [expert-comptable-tpe.fr](https://www.expert-comptable-tpe.fr/articles/facturation-electronique/).
- Odoo: модули `l10n_fr_pdp` (эмиссия/приём), `l10n_fr_pdp_pos` («PDP Flux 10 e-reporting for POS»), `l10n_fr_facturx_chorus_pro` (B2G); приём трёх форматов, эмиссия только UBL — [Odoo docs 19.0](https://www.odoo.com/documentation/19.0/applications/finance/fiscal_localizations/france.html). Тестовые эталоны Odoo для французского потока: аванс/финальный счёт, кредит-нота на аванс, скидка за раннюю оплату, профили goods/services/mixed, B2G, округление — [tests/test_files](https://github.com/odoo/odoo/tree/19.0/addons/l10n_fr_pdp/tests/test_files).
- Dolibarr MVP: отправка клиентских счетов (вручную/авто) с кодами 200/213/210; импорт счетов поставщиков с созданием неизвестных контрагентов/товаров; sandbox; VATEX для 0 % НДС; POS-счета исключены из отправки по умолчанию; e-reporting — «ещё сделать», начало 2027 — [Dolibarr wiki](https://wiki.dolibarr.org/index.php/Module_PDPConnectFR); EN 16931 требует код освобождения BT-121, операции вне поля НДС (категория O) не смешиваются с облагаемыми в одном счёте, SIREN (BT-32) сохраняется — [README einvoicing](https://github.com/Dolibarr/dolibarr-community-modules/blob/main/einvoicing/README.md).
- Роль PPF сведена к двум функциям: центральный справочник получателей и концентратор данных от PA — [blog Tiime, interopérabilité](https://blog.tiime.fr/interoperabilite-plateformes-agreees); ошибки адресации по справочнику (SIREN/адрес) — типичные причины HTTP 400 — [Dolibarr wiki](https://wiki.dolibarr.org/index.php/Module_PDPConnectFR).
- Опрос соответствия ПО: «раскрыт ли e-reporting, а не только e-invoicing?», «подключено ли хотя бы к одной PA?» — [Agicap](https://agicap.com/fr/article/meilleur-logiciel-facturation/).
- Профили: для эмиссии через PA — профили, согласованные с EN 16931 (BASIC, EN 16931, EXTENDED при соблюдении требований) — [Agicap, Factur-X](https://agicap.com/fr/article/factur-x-definition-utilite/).

### Inferences
- Разбивка MVP для оценки (по структуре модулей Odoo и Dolibarr): (1) маппинг данных maERP → EN 16931 и генератор UBL 2.1 (или CII) + валидация по Schematron; (2) транспорт к одной PA: OAuth2/токены, отправка потока, polling статусов, регистрация адреса в справочнике; (3) регистр жизненного цикла и UI (список электронных счетов, «текущие дела», причины отказов); (4) приём: разбор трёх форматов (для Factur-X — извлечение XML через `ЧтениеPDF.НачатьПолучениеВложений()`), сопоставление контрагентов/номенклатуры, создание документа; (5) e-reporting потоков 8/9/10 (B2C, международный, платежи) — можно отложить до 2027, как Dolibarr; (6) тесты: эталонные XML, sandbox PA, кейсы AFNOR. Factur-X-гибрид на выходе — опционально, если PA конвертирует.
- Для приёма с 1 сентября 2026 (срок уже наступил) у клиентов maERP, если они не ETI/GE, дефицит пока закрывается тем, что PME не обязаны эмитировать до 2027, а входящие от GE/ETI уже могут приходить — приёмный поток нужен первым.

### Gaps
- Какие именно из 44 кейсов AFNOR должен покрыть издатель для «Solution Compatible» (есть ли обязательный минимум) — не найдено.
- Текущие требования к e-reporting по платежам (поток 10) для PME в 2027 — не проверялись по первоисточнику.
