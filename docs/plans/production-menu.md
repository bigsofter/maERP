# План: раздел «Производство» — перестройка меню и отчёт себестоимости

Слаг: `production-menu`. Сборка: `2.0.15.36`. Один коммит, одна передача на тест.

Редакция 2 (2026-09-17) — по находкам состязательного разбора плана. Обязательный гейт
`ai-review-plan` (Codex) **не прошёл**: подписка в лимите до 19 сентября (`usage limit`,
`.ai/state/production-menu/plan-review-*.jsonl`). По правилу `.ai/README.md` гейт выполнен субагентом
Claude `architecture-critic`; в отчёте владельцу это сказано прямо.

## Контекст

Разбор раздела «Производство» (2026-09-17) нашёл: видимость команд раздела не задана явно, поэтому
фактическое меню не совпадает с записанным порядком — четыре пункта (три отбора номенклатуры и
«Готовая продукция» в «Важном») приходят по умолчанию; давальческая схема не обособлена; норматив
(техкарта) лежит среди операций; панель «Создать» не настроена и даёт создавать документы мимо
цепочки; регистр `ТоварыВПереработке` выведен в «См. также» — единственный регистр накопления в
интерфейсе всей конфигурации, да ещё и одноимённый отчёт уже стоит в панели отчётов; отчётов
производства по выпуску и себестоимости нет вообще.

## Решения владельца (2026-09-17)

1. Характеристики и серии номенклатуры в раздел «Производство» **не добавляем**.
2. Нужен отчёт себестоимости продукции.
3. Остальные пункты разбора приняты.

Два пункта разбора в эту сборку **не входят**, владельцу сказано отдельно:

- **«Переработчики»** — у `Catalog.Контрагенты` есть `Покупатель`, `Поставщик`, `Перевозчик`;
  признака `Переработчик` нет, отбирать не по чему. Новый реквизит — реструктуризация справочника,
  который переносится из базы drissotex. В `docs/ROADMAP.md`.
- **«Настройки производства» в меню раздела** — команда `DataProcessor.НастройкиПрограммы.Command.Производство`
  существует, но прав на саму обработку нет **ни у одной роли** (`grep "НастройкиПрограммы" src/cf/src/Roles/`
  пуст). Права выдаются на обработку целиком, а не на отдельную команду: чтобы оператор производства
  увидел пункт, он получит доступ ко всем страницам настроек программы. Это расширение прав, а не
  правка меню — не делаю. Настройки остаются в разделе «Настройка».

## Что меняется

### A. Структура подсистем

| Было | Стало |
|---|---|
| `Производство` — 2 отчёта, АРМ, общая команда | + `Document.ВыпускПродукции`, + `Report.СебестоимостьПродукции` |
| `Производство.ПроизводственныеОперации` — выпуск, техкарта, передача, поступление, регистр | → `Производство.Переработка`: только `ПередачаВПереработку`, `ПоступлениеИзПереработки` |
| `Производство.Справочники` — номенклатура, оборудование | → `Производство.Нормативы`: + `Document.ТехнологическаяКарта` |

`AccumulationRegister.ТоварыВПереработке` из состава подсистем убирается (остаётся одноимённый
отчёт). Регистров накопления в интерфейсе конфигурации не остаётся — как и во всех прочих разделах.

**Переименование подсистемы — шесть мест, не четыре.** EDT хранит подсистему как
`Subsystems/<Имя>/<Имя>.mdo`, поэтому меняются **каталог и имя файла** тоже, иначе EDT при Refresh
заведёт дубль:

| Файл | Что правим |
|---|---|
| `Subsystems/Производство/Subsystems/ПроизводственныеОперации/` | каталог → `Переработка/`, файл → `Переработка.mdo`, `<name>` (`:3`) |
| `Subsystems/Производство/Subsystems/Справочники/` | каталог → `Нормативы/`, файл → `Нормативы.mdo`, `<name>` (`:3`) |
| `Subsystems/Производство/Производство.mdo` | `:29`, `:30` — `<subsystems>` |
| `Subsystems/Производство/CommandInterface.cmi` | `:16`, `:17` — `subsystemsOrder` |
| `Roles/Кладовщик/Rights.rights` | `:4876`, `:4883` |
| `Roles/ОператорПроизводства/Rights.rights` | `:1595`, `:1895` |

uuid подсистем сохраняются. Данных подсистемы не держат, обработчик обновления не нужен. Каталоги
переносим `git mv` и после коммита сверяем `git show --stat`: имена с «ё»/«й» на macOS дают
NFC/NFD-дубликат (tiny1C `workflow-007`); здесь кириллица без «ё», но проверка обязательна.

В `Configuration.mdo` дочерних подсистем нет (только `Subsystem.Производство`), в
`MainSectionCommandInterface.cmi`, модулях, картинках и `scripts/` ссылок нет — проверено грепом.

### C. Отчёт «Себестоимость продукции»

**Откуда берутся данные.** Себестоимость выпуска не хранится в документе:
`ВыпускПродукции.ТЧГотоваяПродукция` суммы не имеет. Её считает
`AccumulationRegisters/ТоварыВНаличии/ManagerModule.bsl`: `СформироватьОприходованиеПоВыпускуПродукции`
(`:307-310` — материалы + `ДополнительныеРасходы` + `СтоимостьУслугВыпуска`) и
`СформироватьОприходованиеПоПоступлениюИзПереработки` (`:340-343` — сумма из `ТоварыВПереработке` +
`СтоимостьУслуг` переработчика), обе через `РаспределитьСебестоимостьНаПродукцию` (`:361+`).
Результат ложится в приход регистра `ТоварыВНаличии`: ресурс `Сумма`, партия = сам документ.

Единственный корректный источник — **приход `ТоварыВНаличии` по регистраторам `ВыпускПродукции` и
`ПоступлениеИзПереработки`**. Считать себестоимость в отчёте заново нельзя: это второй источник
истины, который разойдётся с учётом.

**Ресурс `Сумма` регистра — с НДС.** `ManagerModule.bsl:12-15` переименовывает колонку `СуммаСНДС`
в `Сумма`; `:339` — «услуга капитализируется, её НДС попадает в НДС партии»; `:359` —
`СебестоимостьНДС — НДС в составе себестоимости`. Поэтому отчёт обязан вычитать
`СуммаНДСПриход`, как это уже делает
`Reports/ВедомостьПоТоварамНаСкладах/.../Template.dcs:513`. Без вычитания отчёт молча показал бы
себестоимость с НДС и разошёлся с «Ведомостью по товарам на складах» ровно на НДС.

**Объект.** `Report.СебестоимостьПродукции` по образцу `Report.ПотребностиПроизводства`: `.mdo`
(`useStandardCommands`, `defaultForm = CommonForm.ФормаОтчёта`, один макет) и
`Templates/ОсновнаяСхемаКомпоновкиДанных/Template.dcs`. Ни формы, ни модуля. Новые uuid для
`mdclass:Report`, обоих `producedTypes` и макета. **Плюс строка
`<reports>Report.СебестоимостьПродукции</reports>` в `Configuration/Configuration.mdo`** — без неё
объекта в конфигурации нет. Синонимы — на четырёх языках.

**Запрос:**

```
ВЫБРАТЬ
	ТоварыВНаличииОбороты.Регистратор КАК Документ,
	ТоварыВНаличииОбороты.Период КАК Период,
	ТоварыВНаличииОбороты.Номенклатура КАК Продукция,
	ТоварыВНаличииОбороты.Характеристика КАК Характеристика,
	ТоварыВНаличииОбороты.МестоХранения КАК МестоХранения,
	СУММА(ТоварыВНаличииОбороты.КоличествоПриход) КАК Количество,
	СУММА(ТоварыВНаличииОбороты.СуммаПриход - ТоварыВНаличииОбороты.СуммаНДСПриход) КАК Себестоимость,
	СУММА(ТоварыВНаличииОбороты.СуммаНДСПриход) КАК НДС
ИЗ
	РегистрНакопления.ТоварыВНаличии.Обороты(&НачалоПериода, &КонецПериода, Регистратор, ) КАК ТоварыВНаличииОбороты
ГДЕ
	(ТоварыВНаличииОбороты.Регистратор ССЫЛКА Документ.ВыпускПродукции
		ИЛИ ТоварыВНаличииОбороты.Регистратор ССЫЛКА Документ.ПоступлениеИзПереработки)
	И (ТоварыВНаличииОбороты.КоличествоПриход <> 0
		ИЛИ ТоварыВНаличииОбороты.СуммаПриход <> 0)

СГРУППИРОВАТЬ ПО
	ТоварыВНаличииОбороты.Регистратор,
	ТоварыВНаличииОбороты.Период,
	ТоварыВНаличииОбороты.Номенклатура,
	ТоварыВНаличииОбороты.Характеристика,
	ТоварыВНаличииОбороты.МестоХранения
```

- `Период` считается как `НАЧАЛОПЕРИОДА(Регистратор.Дата, ДЕНЬ)` — по образцу `Reports/ДвиженияТовара`.
  Разыменование составного `Регистратор` даёт соединение со всеми таблицами документов, но выбор поля
  `Период` у оборотов с периодичностью `Регистратор` в конфигурации не встречается ни разу, а
  выдумывать конструкцию без образца правило проекта запрещает (tiny1C `workflow-005`);
- `СГРУППИРОВАТЬ ПО` сворачивает серии и партии — иначе детальных строк столько, сколько серий
  (`ТоварыВНаличии.mdo:247, 273, 299`);
- условие по **сумме или количеству**: `РаспределитьСебестоимостьНаПродукцию` (`:373-388`) отдаёт
  последней строке `Себестоимость - Начислено` независимо от веса, а при `ОбщийВес = 0` — всю
  себестоимость; фильтр только по количеству выбросил бы такой приход и разошёлся бы с регистром;
- поля «способ выпуска» текстом не вводим: текст запроса одноязычный, а тип документа виден в
  представлении регистратора.

**Ресурсы** (`totalField`):

| Ресурс | Выражение |
|---|---|
| Количество | `Сумма(Количество)` |
| Себестоимость | `Сумма(Себестоимость)` |
| НДС | `Сумма(НДС)` |
| СебестоимостьЕдиницы | `Выбор Когда Сумма(Количество) = 0 Тогда 0 Иначе Сумма(Себестоимость) / Сумма(Количество) Конец` |

Защита от нуля — по образцу `Reports/ВедомостьПоТоварамНаСкладах`. Ограничить `СебестоимостьЕдиницы`
группировками не удалось: `totalField` с перечнем группировок в конфигурации не встречается ни разу,
конструкцию без образца не вводим. В общем итоге показатель — средневзвешенный по разной
номенклатуре; смотреть его надо на уровне продукции, это записано в `docs/ROADMAP.md`.

**Параметры** — по образцу `Reports/ДвиженияТовара/.../Template.dcs:221-283`: пользователь заполняет
`Период` типа `StandardPeriod`, а `НачалоПериода`/`КонецПериода` — производные
(`useRestriction=true`, `availableAsField=false`, выражения `&Период.ДатаНачала` и
`&Период.ДатаОкончания`). Два голых `xs:dateTime`-параметра отрезали бы последний день: конец
периода вводится датой без времени.

**Вариант настроек** один, `Основной`: группировки `Продукция` → `Характеристика` → `Документ`,
выбранные поля — четыре ресурса; выключенные пользовательские отборы по `Продукция` и
`МестоХранения`; `AppearanceTemplate` — `Арктика`.

**Права**: `Use` и `View` ролям `ОператорПроизводства` и `Кладовщик` — обе видят раздел
«Производство», и у обеих уже есть права на соседний `Report.ПотребностиПроизводства` и `Read` на
регистр `ТоварыВНаличии` с суммами, так что отчёт не открывает им ничего нового. `Руководитель` и
`Администратор` получают права на новые объекты сами (`setForNewObjects=true`).
`МенеджеруПоЗакупкам` не даю: у него нет `View` на раздел, отчёт нашёлся бы только через
«Все функции».

**Чего отчёт не делает** (в `docs/ROADMAP.md`, владельцу сказать прямо):

- нет расшифровки «из чего сложилась себестоимость» — расхода материалов по тому же документу;
- автовыпуск при отгрузке ставит выпуск на секунду раньше реализации
  (`CommonModules/Производство/Module.bsl:767-771`, `Возврат Реализация.Дата - 1`). Реализация ровно
  в 00:00:00 (импорт, ECommerce, перенос drissotex) уводит выпуск на предыдущие сутки, а 1-го числа —
  в предыдущий месяц: месячный отчёт разойдётся с отгрузкой. Механизм не меняем, ограничение
  записываем.

## Проверка

- `scripts/lint.sh`, `scripts/refcheck.py` — после правок модулей и имён метаданных;
- **смок новый отчёт не проверит**: `DataProcessors/СмокТест/ManagerModule.bsl:370-387` берёт у
  объекта `.Формы`, а у отчёта своей формы нет. Текст запроса в `.dcs` не читает ни один гейт
  (`queryfields.py` — только `.bsl`, `listcheck.py` — динсписки, `refcheck.py` — строковые имена);
- поэтому запрос покрывается **сценарием уровня 3** в `DataProcessors/ТестыДокументов`: тридцать
  первый сценарий компонует отчёт через СКД и сверяет себестоимость и себестоимость единицы с
  движениями регистра. Образец — `СтрокиОтчетаПотребностей` (`ManagerModule.bsl:2733`), который так
  же компонует «Потребности производства». Данные сценария — со ставкой НДС 20%: общий помощник
  `ДобавитьСтрокуТоваров` кладёт в строку `СуммаНДС = 0` и строку не пересчитывает, поэтому сценарий
  собирает поступление сам и зовёт `РаботаСДокументамиКлиентСервер.РассчитатьСтроку` до проведения —
  иначе в регистр ушёл бы нулевой НДС и проверка вычитания оказалась бы пустой;
- `scripts/smoke.sh` на обновлённой из EDT `build/ib` — формы раздела и печатные формы;
- руками на клиенте: раздел «Производство» под `ОператорПроизводства` и `Кладовщик` — состав
  пунктов, отсутствие дублей, панель «Создать», открытие отчёта;
- поднять `<version>` до `2.0.15.36` (`Configuration.mdo:32`), завести секцию `## 2.0.15.36` на
  ru/fr/en/es в `CommonTemplates/ОписаниеИзменений/Template.txt`, добавить строку сценария в
  `docs/TESTS.xlsx` по регламенту `docs/TESTING.md`.

## Риски

1. **Права ролей.** Переименование подсистем ломает по две строки в `Rights.rights` двух ролей;
   пропустить одну — группа исчезнет из раздела. Ловится глазами на клиенте под обеими ролями.
2. **НДС в себестоимости** — см. раздел C. Если вычитание `СуммаНДСПриход` потеряется при правке,
   отчёт разойдётся с «Ведомостью по товарам на складах» ровно на НДС и будет выглядеть
   правдоподобно. Сценарий уровня 3 сверяет суммы с регистром именно поэтому.
3. **Скрытая `Create`** не запрещает создание — документ по-прежнему создаётся из списка. Это
   интерфейсная подсказка, а не контроль; выдавать её за запрет владельцу нельзя.
4. **EDT не перечитывает файлы, изменённые снаружи** (tiny1C `workflow-001`) — владельцу явно
   сказать про Refresh и проверку конфигурации.
