# Полуфабрикаты: сырьё переработчика в закупку, способ «Закупка», ручной выпуск ПФ

Задача владельца 2026-10-27 (клиент Drissotex, заказ «COTTE JACQUARD BRACELET fini»). Продолжение волны многоуровневых
техкарт (`docs/plans/production-subcontracting.md`, S1–S9). Существенное изменение по CLAUDE.md: реструктуризация
документа, потребности, проведение выпуска, обработчик обновления — план → `ai-review-plan` → код.

## Что видит владелец

- Изделие «fini» сделано из ПФ «COTTE JACQUARD BRACELET» со способом «Переработчик»; ПФ — из хлопка (своя карта).
  На закладке «Материалы» рабочего места производства — только ПФ (потребность 15, дефицит 15), хлопка нет: закупать
  нечего, а переработчику мы передаём наш хлопок.
- Колонка способа изготовления на «Материалах» есть, но последняя и уходит за край окна; глубже первого уровня
  она пустая (способ читается из карты продукции строки заказа, у узлов ПФ его нет).
- Материалу в техкарте ставится «Наше производство» по умолчанию — владелец просил «Закупка».
- На закладке «Выпуск» нельзя выбрать ПФ: выбор (`АРМПроизводство.ПродукцияЗаказаДляВыбора`) — только продукция
  заказа. Ручной выпуск одноуровневый (TECHDEBT 2.0.15.43, вопрос владельцу был открыт).

## Решения владельца 2026-10-27

1. **ПФ у переработчика из нашего сырья: сырьё — в потребность и закупку.** Сам ПФ не закупается — его покрывает
   поступление из переработки.
2. **Новое значение способа «Закупка»**, подставляется по номенклатуре при вводе материала: по правилу `Производство.ПроизводитсяПоТехкарте`
   (см. редакцию 3, P2): производимая — «Наше производство», иначе «Закупка».
   Существующие карты поправит обработчик обновления.
3. **Ручной выпуск ПФ из рабочего места** — делать.
4. Способ изготовления — колонкой на «Материалах» рядом с материалом, на всех уровнях.

## Главное: у узла дерева две роли

Сейчас одно правило «лист / узел» отвечает и за **потребность** (что закупать: листья), и за **списание** (что
списывает автовыпуск: тоже листья). Для ПФ переработчика они расходятся:

| Роль | ПФ «Переработчик» | Его сырьё |
|---|---|---|
| Потребность (закупка, дефицит, «Материалы», АРМ закупок) | не потребность | потребность |
| Списание автовыпуском изделия (отгрузка) | списывается (пришёл от переработчика) | не списывается изделием |
| Передача в переработку | ожидаемая продукция (родитель переданных строк, S5-A) | передаётся |

Поэтому разворачивание ПФ переработчика **не делает его обычным узлом**. Вводится понятие **«граница списания»**:
узел со способом «Переработчик» — граница. Правила:

- **Лист потребности** — строка без потомков (как сейчас). После изменения хлопок — лист, ПФ переработчика — узел.
- **Строка списания** — граница списания или лист, у которого нет предка-границы. Потомки границы не списываются
  изделием.

Хранение карт (`СоставТехКарты`, один уровень) **не меняется** — P0 волны S1–S3 (сверка карты при проведении заказа,
E6) не задевается.

## Изменения

### 1. Перечисление и умолчание способа (сборка 2.0.16.102)

- `Enums.СпособыИзготовления` + значение **`Закупка`** (ru/fr/en/es: «Закупка» / «Achat» / «Purchase» / «Compra»).
  Реструктуризации нет.
- Общая функция умолчания `ТехнологическиеКарты.СпособИзготовленияПоУмолчанию(Номенклатура)` (экспорт): закупаемая →
  `Закупка`, иначе `НашеПроизводство`. Правило «закупаемая» — то же, что `Производство.ПроизводитсяПоТехкарте`
  наоборот (один источник): реквизиты номенклатуры одним запросом для массива (вариант функции для таблицы строк).
- Подстановка: `ТехнологическаяКарта.ПередЗаписью` (пустой способ — по номенклатуре вместо `НашеПроизводство`);
  форма документа карты и закладка «Производство» карточки номенклатуры — при смене материала строки
  (`ПриИзменении`), только если способ пуст или равен прежнему умолчанию для прежнего материала (пользовательский
  выбор не перетирается).
- Правило остановки (`ТехнологическиеКарты.ОтобратьРазворачиваемые`): `Закупка` — **явный лист** (не полагаться на
  `ПроизводитсяПоТехкарте`): закупаемый ПФ с картой не разворачивается.
- **Обработчик обновления** 2.0.16.102: строки `ТЧМатериалы` документов `ТехнологическаяКарта` и записи
  `СоставТехКарты` со способом `НашеПроизводство` (или пустым) у закупаемой номенклатуры → `Закупка`. Семантика не
  меняется (закупаемая и так лист), поэтому обработчик безопасен для любых данных. Запись регистра — наборами по
  регистратору, документы — `ОбменДанными.Загрузка = Истина` (без перепроведения и без пересоздания версии карты).
  Повтор — ничего не пишет. Существующий `ЗаполнитьСпособыИзготовленияТехкарт` (2.0.15.39) переводится на новую
  функцию умолчания (для пустых способов).
- **Сверка карты при проведении заказа (E6):** способ входит в `СвойстваИзготовленияОтличаются`. Обработчик правит и
  документ карты, и регистр одинаково, а заказ берёт способ из карты (`ПеренестиСвойстваИзготовленияКарты`) —
  расхождения нет. Проверить сценарием `ПроверитьСверкуСвойствИзготовления` + новым шагом «после обработчика
  проведение заказа не пишет новую версию карты».

### 2. Способ в материалах заказа (2.0.16.102)

- `ЗаказПокупателя.ТЧМатериалы` + реквизит **`СпособИзготовления`** (`ПеречислениеСсылка.СпособыИзготовления`).
  **Реструктуризация табличной части заказа** — у клиента данные сохраняются, новое поле пустое.
- Заполняется там же, где дерево: `Документы.ЗаказПокупателя.ДобавитьМатериалыСтроки` из узла `РазвернутыйСостав`
  (у узла уже есть `СпособИзготовления`). Первый уровень — как сейчас из карты продукции.
- Пустой способ у старых строк читается как «не граница» — это ровно прежнее поведение (раньше ПФ переработчика был
  листом и без способа). Перезаполнение дерева (проведение/перезаполнение заказа) проставит способ. Обработчик для
  заказов **не нужен** — проверить на копии базы 2MZL, что старые заказы считаются как раньше.
- АРМ производства, «Материалы»: способ берётся из строки заказа (все уровни); для пустого — прежний путь
  `ЗаполнитьСпособыИзготовления` (первый уровень из карты). Колонка переносится сразу за «Продукцию».

### 3. ПФ переработчика разворачивается (2.0.16.102)

- `ОтобратьРазворачиваемые`: убрать «Переработчик → лист» (строка ~1233); узел разворачивается, в результате
  `РазвернутыйСостав` у узла новый признак **`ГраницаСписания`** = способ «Переработчик».
- **Потребность** (`ПотребностиПроизводства.ПотребностьЗаказаКлиента`, `Производство.ДобавитьПотребностьИзМатериалов`,
  стадии, дефицит): листья — как сейчас. ПФ переработчика уходит из потребности (он узел), сырьё приходит. Проверить
  все потребители по карте влияния (ниже).
- **Списание автовыпуском при отгрузке** (`Производство.НормыПоМатериаламЗаказа`): вместо «пропускать строки с
  потомками» — «строки списания» по правилу границы (способ строки заказа = `Переработчик` → строка списывается,
  её поддерево — нет).
- **Канал передачи** (`ДобавитьНормыРазвернутогоСостава`, автовыпуск ПФ при передаче, S4-B): ПФ, который сам
  передаётся переработчику, разворачивается до своих листьев как сейчас; если внутри встречается граница — по тому же
  правилу. Сценарий S4-B не должен поменяться (там ПФ «наше производство»).
- **Передача в переработку** (S5-A `ОжидаемаяПродукцияПередачи`, `ДопустимаяПродукцияМатериала`): переданный хлопок
  теперь лежит под ПФ в дереве → ожидаемая продукция = ПФ по доле. Это то, что S5-A и задумывал; проверить сценарием.
- **Рабочее место закупок, «Потребность»** читает регистр — хлопок появится сам после перепроведения заказа.

### 4. Ручной выпуск ПФ (отдельная сборка 2.0.16.103, после проверки 1–3 владельцем)

- Выбор на «Выпуске»: к продукции заказа добавляются **узлы-ПФ дерева со способом не «Переработчик»** (наше
  производство / оба / пустой у производимого ПФ) с остатком «к выпуску» = количество узла − выпущено этого ПФ по
  заказу (`ВыпускПродукции` с основанием-заказом, вид — ручной).
- Материалы выпуска ПФ — листья поддерева узла в заказе (пропорционально количеству), а не одноуровневая карта.
- **Списание изделия после ручного выпуска ПФ**: автовыпуск изделия списывает выпущенный по заказу ПФ как строку
  списания (на выпущенное количество), а его поддерево — только на невыпущенный остаток. Без этого хлопок спишется
  дважды. Детальный план этой сборки — отдельным разделом после сдачи 2.0.16.102 (нужен разбор `ВыполнениеЗаказаПоПродукции`,
  «Выпущено» по ПФ, `ИзОстатка`).

## Редакция 2 — ответ на разбор плана (Codex, 2026-10-27, reject, 5 × P1)

**R1 (P1, свободный хлопок со склада).** Передача сырья переработчику по заказу закрывает потребность в нём:
`ПередачаВПереработку` с основанием-заказом пишет в `ПотребностиПроизводства` ресурс **`ИзОстатка`** по ключам
потребности переданного материала этого заказа (`Заказ, Продукция, Материал, Характеристика`) — в объёме переданного, но
не больше непокрытого `Потребность − Пришло − ИзОстатка` (собственные прежние движения передачи не считаются: читаются
без регистратора, как у оформления ордеров). Распределение по ключам — в порядке строк дерева заказа. `ПередачаВПереработку`
добавляется в регистраторы `ПотребностиПроизводства` (`registerRecords`; реструктуризации нет). Блокировка
`ПотребностиПроизводства` по заказу у передачи уже есть (`ObjectModule:107`), порядок блокировок не меняется.
Перепроведение замещает набор, отмена проведения его удаляет (автоудаление). Закупка под заказ (`Пришло`) отдельно
не вычитается из переданного: она уже уменьшила непокрытое. Сценарий полного цикла со свободным хлопком: дефицит 0,
«Потребность» АРМ закупок пуста.

**R2 (P1, старые заказы).** Обычное перепроведение дерево не переразворачивает — обещание снято. Переход
существующего заказа — **явной командой** формы заказа «Заполнить материалы по техкарте» (она есть, перезаполняет
дерево целиком через `ЗаполнитьМатериалыПоТехкартам`). Перед перезаполнением команда предупреждает, если по ПФ
переработчика заказа уже есть «Заказано»/«Пришло» (закупали ПФ) или передачи — эти количества останутся на ключе ПФ.
Без перезаполнения заказ считается как раньше (ПФ — лист, способа в строке нет). Тест: заказ со старым деревом после
обновления — проведение без перезаполнения не меняет потребность; после команды — хлопок в потребности.

**R3 (P1, приоритет правил остановки).** Порядок в `ОтобратьРазворачиваемые`:
1. способ строки карты **`Закупка`** — лист;
2. способ **`Переработчик`** — разворачивается по карте ПФ **независимо от способа пополнения номенклатуры**; нет
   действующей карты — лист с сообщением в `Ошибки` («у ПФ переработчика нет карты: сырьё не планируется»);
3. иначе — как сейчас `ПроизводитсяПоТехкарте`.
Тесты сочетаний: «Переработчик» × способ пополнения «Оба»/«Закупка»/«Производство», «Закупка» с картой.

**R4 (P1, вложенные уровни при передаче).** Продукция строки передачи и норма считаются от **ближайшего предка-границы**
(узла «Переработчик») переданного материала, а если границы над ним нет — от прямого родителя (как сейчас).
`ДопустимаяПродукцияМатериала` и `КоличествоПродукцииПоНорме` переходят на общую функцию `ПредокПередачи(дерево,
строка)`. Маршрут «переработчику передаётся собственный ПФ B» — как сейчас: B выбирается материалом передачи
(узлы дерева есть в подборе), ПФ B производится вручную (сборка .103) или автовыпуском при передаче (S4-B, свободный
остаток по S9 не перевыпускается). Сквозной тест: изделие → A («Переработчик») → B («Наше производство») → хлопок:
передача хлопка → ожидаемая продукция A; передача B → ожидаемая A, автовыпуск B при передаче.

**R5 (P1, одно правило списания).** Единая функция **`СтрокиСписания(дерево, узел)`** в модуле `Производство`: обход
поддерева узла; граница «Переработчик» списывается и её поддерево исключается; лист вне границ списывается. Её
используют автовыпуск при отгрузке (`НормыПоМатериаламЗаказа`, узел — строка продукции), автовыпуск ПФ при передаче
(`ДобавитьНормыРазвернутогоСостава` — то же правило на дереве `РазвернутыйСостав`) и ручной выпуск ПФ (.103). Тест с
вложенным полученным ПФ: выпуск A списывает B, хлопок не трогает.

**Вопрос владельца 2026-10-27: выпущенный ПФ — в передачу.** Уже работает: подбор материала на закладке
«Передача в переработку» предлагает все узлы дерева (`МатериалыЗаказаДляПодбора` → `СобратьМатериалыВетви`), продукция —
родитель (с R4 — ближайшая граница). Автовыпуск при передаче берёт свободный остаток ПФ (S9) и не выпускает его повторно.
В сборке .103 — сценарий «ручной выпуск ПФ → передача ПФ → автовыпуск не повторяется».

## Редакция 3 — ответ на второй разбор (reject, 3 × P1 + P2)

**R1 уточнён (P1, двойной зачёт закупленного).** Передача зачитывает в `ИзОстатка` **только часть, списанную со
свободных партий**, — тем же распределением, что автовыпуск: `Производство.РаспределитьМатериалы` (партии под этот
заказ — первыми, затем свободный остаток). Партии под заказ уже учтены в «Пришло» и в `ИзОстатка` не идут. Если
передача списывает партии не через `РаспределитьМатериалы` (проверить `ПередачаВПереработку.ТаблицаСырья`), её списание
переводится на это распределение — одно правило «партия заказа → свободный остаток» для отгрузки, передачи и выпуска
(решение волны S9). Сценарий: хлопок 10 закуплен под заказ + 5 свободных, передано 15 → `ИзОстатка` 5, дефицит 0.

**R6 (P1, передача своего ПФ со склада).** Если передаётся **узел** дерева (ПФ с поддеревом), его свободная часть
закрывает потребность листьев поддерева: на ключи листьев (по `СтрокиСписания` относительно узла, R5) пишется
`ИзОстатка` = норма листа × количество ПФ, взятое со свободного остатка (часть ПФ, выпущенная автовыпуском при передаче,
закрывает листья уже через `ПеренестиИзОстаткаНаПотребности` автовыпуска — не дважды: свободная часть = переданное −
выпущенное этим автовыпуском − партии ПФ под заказ). Тот же перенос — у автовыпуска изделия при отгрузке, когда ПФ
взят со свободного склада. Общая процедура `ПокрытьПотребностиПоддерева(заказ, узел, количество)` в `Производство`.
Сценарий: ПФ B со свободного склада передан → хлопок под B в потребности закрыт.

**R4 дополнен (P1, путь ожидаемой продукции).** На `ПредокПередачи` переводятся **все три** пути передачи:
`ДопустимаяПродукцияМатериала`, `КоличествоПродукцииПоНорме` и `ОжидаемаяПродукцияПередачи` →
`ПродукцияПоДеревуЗаказа` → `ПотребностьРодителей` (группировка — по ближайшему предку-границе, а не по прямому родителю).

**P2 (правило закупаемости).** Формулировка раздела 1 заменена: способ по умолчанию — `НашеПроизводство`, если
`Производство.ПроизводитсяПоТехкарте(реквизиты номенклатуры)`, иначе `Закупка`. Один источник; «тип вне
Продукция/Полуфабрикат» отдельно не проверяется (способ пополнения «Производство» у материала — значит производится).

## Редакция 4 — сужение объёма (решение владельца 2026-10-27 после третьего разбора)

Третий разбор (reject, 3 × P1) показал, что вложенные и смешанные сочетания давальческой схемы — отдельная задача.
Владелец выбрал: **сборка 2.0.16.102 закрывает его случай — один уровень сырья под ПФ переработчика.** Редакции 2–3
(R1–R6) **заменяются** этим разделом там, где расходятся.

## Редакция 5 — ответ на четвёртый разбор (reject, 2 × P1)

(ПФ переработчика) со свободного остатка, `РаспределитьМатериалы` пишет `ИзОстатка` на ключ ПФ — а потребность теперь на
листьях-сырье. Правило: свободная часть списанной границы **переносится на ключи её листьев** заказа по норме (количество
листа на единицу ПФ из дерева заказа × свободное количество ПФ), не больше непокрытого листа; на ключ самой границы
`ИзОстатка` не пишется. Механизм тот же, что `Производство.ПеренестиИзОстаткаНаПотребности` у автовыпуска ПФ при передаче
(перенос с ключа ПФ на ключи листьев) — расширяется на границы канала отгрузки. Списание партий ПФ под заказ (если ПФ
закупали под заказ) — «Пришло» на ключе ПФ, переноса нет. Сценарий: ПФ переработчика лежит свободно на складе, отгрузка
изделия → дефицит хлопка 0, «Потребность» АРМ закупок пуста.

**R8 (P1, явная «Закупка» и автовыпуск передачи).** `Производство.ПродукцияПередачи` (и канал отгрузки
`ПродукцияЗаказа`) решают «производить автоматически» не только по `ПроизводитсяПоТехкарте(номенклатура)`, но и по
**способу строки заказа**: строка материалов заказа со способом `Закупка` или `Переработчик` автоматически не
производится (закупается / приходит от переработчика). Для строк без способа (старые заказы) — прежнее правило.
Сценарий: закупаемый ПФ с собственной картой и способом «Закупка» передан переработчику без остатка → автовыпуска нет,
отказ по недостаче (или минус по правилу проекта — как у прочих материалов).

приоритета заказа, а поступление из переработки не распознаётся как «под заказ» — любой зачёт движениями задваивается.

Правило: для листа-сырья, у которого **родитель в дереве заказа — граница «Переработчик»**, обеспечение =
**Макс(Обеспечено(закупка), Передано по заказу)**, где «Передано по заказу» — приход `ТоварыВПереработке` с
`ЗаказПокупателя` = заказ по этому материалу (оборот прихода, без возвратов — по регистру переработки). Максимум, а не

## Редакция 7 — ответ на шестой разбор (reject: максимум, распределение по ключам, все потребители)

**Максимум — осознанно (P1).** Сумма закупки и передачи занижает дефицит, когда купленное под заказ и есть переданное
(потребность 30, куплено под заказ 15, эти же 15 переданы: сумма 30 → дефицит 0, а сырья не хватает на 15 — АРМ не
предложит закупку, производство встанет). Максимум в обратном случае **временно завышает** дефицит: куплено под заказ 15
и ещё лежит, а FIFO передал 15 свободных (максимум 15 → дефицит 15, хотя покрыто 30). Завышение снимается, как только
оставшееся сырьё передано (передано станет 30), и в худшем случае приводит к лишнему предложению закупки, которое видит
и снимает менеджер. Ошибка «не докупили» хуже ошибки «предложили лишнее» — выбираем максимум. Записывается в TECHDEBT с
этим примером; точное решение — с приоритетом партий заказа при передаче (FIFO → «партия заказа, затем свободный»), это
изменение списания передачи, вне объёма.

**Распределение переданного по ключам (P1).** `ТоварыВПереработке` хранит переданное по заказу и материалу (+
характеристика), без продукции. Функция `ПотребностиПроизводства.ПереданоПоКлючам(Заказ)` распределяет переданное
материала+характеристики по ключам-листьям под границами «Переработчик» этого заказа **в порядке строк дерева**, каждому
ключу — не больше его `Потребность`; остаток сверх суммы потребностей — последнему ключу (дефицит отрицательным не
становится). Один источник для всех потребителей.

**Все потребители (P2).** `ПереданоПоКлючам` используют: `Обеспечено`/`ДефицитЗаказа`, `ТекстОбеспечено` (запросы
«Потребность» АРМ закупок и «Материалы» АРМ производства — через временную таблицу переданного по ключам, подставляемую
в запрос), `ПроизводственныеЗаказы.ДобавитьПоказателиПотребностей` + `СтадияПоПоказателям` (стадия «обеспечено» —
передано тоже), `ОстатокКПоступлению` (вычитает переданное), `АРМПроизводство.РассчитатьДефицитОстатков`. Перечень
сверяется полным поиском `Обеспечено(`/`ТекстОбеспечено(`/`ИзОстатка` перед кодом; сценарий проверяет стадию, дефицит,
«к поступлению» и строку АРМ закупок на одном заказе.

## Редакция 8 — ответ на седьмой разбор (reject: зачёт между изделиями, остаток к поступлению)

**Максимум — по материалу заказа, а не по ключу (P1).** Для материала+характеристики M, у которого есть ключи-листья под
границами «Переработчик» этого заказа: `ОбеспеченоM = Макс(Σ Обеспечено(закупка) по всем ключам M под границами,
Σ передано M по заказу)`. Затем `ОбеспеченоM` раскладывается по этим ключам в порядке строк дерева, каждому — не больше
его `Потребность − ИзОстатка`; дефицит ключа = `Потребность − ИзОстатка − разложенное`. Закупка, привязанная к
продукции A, и передача без продукции сравниваются на одном уровне — материал заказа, поэтому одна и та же единица
сырья не засчитывается двум изделиям. Ключи M вне границ (обычный материал собственного производства) считаются как
сейчас, по своему `Обеспечено`, и в сумму не входят. Функция одна — `ПотребностиПроизводства.ОбеспечениеСырьяПереработчика(Заказ)`
(возвращает разложенное обеспечение по ключам), ей пользуются все потребители редакции 7.

**`ОстатокКПоступлению` не меняется (P1).** Это обязательство поставщика (`Заказано − ПришлоПоЗаказам`), из него
заполняются поступление и приходный ордер по заказу на производство; передача переработчику его не уменьшает. Из
перечня потребителей редакции 7 убран.

## Редакция 10 — ответ на девятый разбор (reject: общий ключ, пустая продукция строки, тест умолчания)

**Общий ключ под границей и вне (P1).** Ключ потребности — `(Заказ, конечная Продукция, Материал, Характеристика)`, и

их долей под границами, Σ передано M)`.

вхождений несколько разных (граница и не граница, или две границы) — строка в покрытие **не** засчитывается (осторожная

материала, иначе прежний (выбор пользователя сохраняется). Уровень 3 проверяет все ветки; клиентский `ПриИзменении`

  излишек передачи для одного ПФ другой ПФ не закрывает, закупка обычной части изделия на ключ ПФ не попадает.
- Закупки под заказ (`ЗаказыПоставщикам`/поступления с распределением по продукции заказа,
  `РаспределитьПоПродукции`): ключ ПФ — обычная «продукция» заказа, распределение уже идёт по ключам регистра. Проверить,
  что распределение закупки берёт продукцию из ключей регистра, а не из строк товаров заказа (иначе ключ ПФ не
  получит закупку) — **обязательная проверка перед кодом**, при расхождении — добавить ключ ПФ в источник распределения.
- `ОстатокКПоступлению`, ветка без заказанного: вычитается только **добавка передачи** `Макс(0, Передано ключа −
  Обеспечено(закупка ключа))` — не полное обеспечение, приход не вычитается дважды.
- Перенос `ИзОстатка` автовыпуска (`ПеренестиИзОстаткаНаПотребности`) и `ДефицитЗаказа`: ключи с продукцией-ПФ
  обрабатываются как любые ключи; автовыпуск изделия эти ключи не трогает (граница списывается целиком, её листья нет).
- Максимум (а не сумма) — по-прежнему осознанно, с примером в TECHDEBT (редакция 7), теперь в пределах одного ключа.

Функция одна: `ПотребностиПроизводства.ПереданоПоКлючамПереработчика(Заказ, ИсключитьРегистратор = Неопределено)`.
Сценарий: два ПФ переработчика с одним сырьём и обычное то же сырьё у изделия — передача для ПФ1 не закрывает ПФ2 и
обычную часть; закупка обычной части не закрывает ПФ.

## Редакция 12 — ответ на одиннадцатый разбор (reject: 2 × P1, 2 × P2)

**ПФ переработчика — ещё и продукция заказа (P1).** Если номенклатура границы встречается в строках товаров этого же
заказа (ПФ продают отдельно), ключ `(Заказ, ПФ, сырьё)` совпал бы с ключом собственной продукции ПФ. Для такого заказа
граница **не разворачивается** (прежнее поведение: ПФ — лист со своей потребностью) — правило проверяется при заполнении
дерева заказа (`ЗаполнитьМатериалыПоТехкартам`, известны строки товаров). Тест: заказ с изделием и тем же ПФ отдельной
строкой — ПФ лист, ключ один.

**Пересчёт стадий при отмене передачи (P1).** Источник «передано» читается тем же пакетом `ДанныеРасчёта`
(`ТекстЗапросаРасчёта`) с тем же контрактом контекста: строки передач отбираются условием «проведён ИЛИ это документ
контекста и `ДокументПроведён`», а документ контекста при `ДокументПроведён = Ложь` исключается — как уже сделано для
прочих источников стадии. `ПередачаВПереработку` уже участвует в `ЗапомнитьЗаказыДокумента`/`ОбновитьСтадииПриЗаписи`
(проверить; если нет — добавить в перечень типов `ПроизводственныеЗаказы`). `ПереданоПоКлючамПереработчика` принимает
тот же контекст `(Документ, ДокументПроведён)` вместо одного `ИсключитьРегистратор`. Тест: провести и отменить передачу —
стадия и дефицит возвращаются.

**Ключ сопоставления листьев в АРМ (P2).** `АРМПроизводство.МатериалыЗаказа`, `СобратьЛистьяДерева`,
`РазложитьОстаткиПоЛистьям`: у листа под границей поле «Продукция» для сопоставления с остатками регистра — номенклатура
границы (тот же ключ, что в регистре), а колонка «Продукция» на экране — по-прежнему продукция строки заказа (для
пользователя). Тест: строка хлопка под ПФ показывает дефицит своего ключа.

**Номера сборок (P2).** 2.0.16.102 занят (падение карточки товара). Этот план — **2.0.16.103**; ручной выпуск ПФ —
**2.0.16.104**.

## Редакция 13 — проверка целостности дерева при проведении (ответ на двенадцатый разбор)

**Коллизия ключа после частичного заполнения (P1).** Правило редакции 12 проверяется не только при заполнении, но и
**при проведении заказа** (`ЗаказПокупателя.ПроверитьПроведениеЗаказа`) по всему сохранённому дереву: если в
`ТЧМатериалы` есть узел-граница «Переработчик» с потомками, а его номенклатура (+характеристика) есть в строках товаров
этого заказа, — **отказ проведения** с текстом «ПФ «%1» есть и в продукции заказа, и в составе другой продукции у
переработчика: заполните материалы по техкарте заново» (4 языка), поле — строка товаров с этим ПФ. Перезаполнение
(полное или по строке) снова применит правило редакции 12. Отказ, а не молчаливое сворачивание: дерево правил
пользователь, и решать ему. Тест: заказ с развёрнутой границей + добавлена строка товаров с тем же ПФ → проведение
отказано; после «Заполнить материалы по техкарте» — проводится, ПФ лист.

## Редакция 14 — ответ на тринадцатый разбор (reject: 2 × P1)

**Коллизия — по номенклатуре ПФ без характеристики (P1).** Измерение `Продукция` регистра хранит только номенклатуру.
Правила редакций 12–13 (не разворачивать при заполнении, отказ проведения) сравнивают **номенклатуру** границы с
номенклатурой строк товаров заказа, характеристика ПФ не учитывается. Текст и тест — те же, с ПФ другой характеристики
в строке товаров (тоже коллизия).

**Перенос `ИзОстатка` автовыпуска не трогает ключи ПФ переработчика (P1).** `Производство.ПеренестиИзОстаткаНаПотребности`
выбирает дефициты по материалу и характеристике. Ключи, у которых `Продукция` — граница «Переработчик» этого заказа
(множество номенклатур границ из дерева заказа), **исключаются** из выбора переноса: их обеспечивают только закупка под
ключ и передача переработчику (редакция 11). Автовыпуск собственного ПФ при передаче закрывает сырьё только обычных
ключей. Тест: заказ с собственным ПФ B (автовыпуск при передаче, хлопок) и ПФ переработчика A (хлопок) — автовыпуск B не
уменьшает дефицит хлопка ключа A.

## Редакция 15 — ответ на четырнадцатый разбор (reject: 2 × P1)

**Коллизия — по всему заказу, не только по строкам товаров (P1).** Граница «Переработчик» с номенклатурой П
разворачивается (и проводится, редакция 13), только если П **нигде больше в заказе** не встречается в другой роли: ни в
строках товаров, ни узлом или листом дерева материалов со способом, отличным от «Переработчик». Иначе — при заполнении
граница остаётся листом, при проведении сохранённого дерева с такой развёрнутой границей — отказ с тем же текстом
(редакция 13). Так у ключа `(Заказ, П, сырьё)` один смысл — «сырьё П для переработчика», а строка передачи с продукцией
П однозначно относится к нему. Две границы с одной П в разных ветвях — допустимы (одна роль; ключ общий, потребности
складываются). Тест: П своим производством в одной ветви и у переработчика в другой — граница не разворачивается; при
ручной сборке такого дерева — отказ проведения.

**`ПотребностьНеИзменилась` (P1).** Запрос сохранённого дерева в `ЗаказПокупателя/ObjectModule` (~645–680) получает
`СпособИзготовления` строк — общий контракт `ПотребностьЗаказаКлиента` требует способ родителя. Полный перечень
вызовов `ПотребностьЗаказаКлиента` и всех запросов `ТЧМатериалы`, передающих строки в него, сверяется поиском перед
кодом; каждый получает поле способа.

## Редакция 16 — общий итог по материалу среди ключей ПФ переработчика (ответ на пятнадцатый разбор)

**Двойной зачёт между ключами разных ПФ (P1).** Передача списывает партии по дате и может отдать ПФ2 сырьё, купленное под
ключ ПФ1; максимум внутри каждого ключа засчитал бы одно сырьё дважды. Максимум переносится **на материал**, но только
среди ключей-границ (после редакции 11 у них своя «Продукция» = ПФ, с обычными ключами изделия они не смешиваются —
это снимает возражение девятого разбора):

1. Для материала+характеристики M и множества ключей-границ K_M этого заказа:
   `ИтогM = Макс(Σ Обеспечено(закупка) по K_M, Σ Передано по K_M)`.
2. Разложение `ИтогM` по ключам K_M: сначала каждому ключу — его собственное «Передано» (явная продукция строки передачи),
   не больше его `Потребность − ИзОстатка`; затем остаток `ИтогM − разложенное` — по ключам в порядке строк дерева, не
   больше их оставшейся потребности.
3. Дефицит ключа = `Потребность − ИзОстатка − разложенное ключу`.

Сумма покрытия ключей M никогда не превышает `ИтогM` — одно физическое количество засчитывается один раз; распределение
между ключами может отличаться от «истинного» (какой ПФ получил какую партию), но итоговый дефицит материала верен. Это
и есть единая функция `ОбеспечениеСырьяПереработчика(Заказ, Контекст)` (редакции 8 и 11 — уточнены этим разделом);
`ОстатокКПоступлению` без заказанного вычитает добавку `разложенное ключу − Обеспечено(закупка ключа)`, если она
положительна. Тест: ПФ1 и ПФ2 переработчика с хлопком 15+15, закуплено 15 под ПФ1, передано 15 для ПФ2 → итог 15,
дефицит хлопка 15 (а не 0).

## Решение владельца после 16 кругов разбора (2026-10-27)

`ai-review-plan` после редакции 16 — **reject** (2 × P1): двойной зачёт физического сырья между обычным ключом и ключом
переработчика при общем списании передачи по FIFO; формула добавки в `ОстатокКПоступлению` после перераспределения.
Корень — передача списывает партии без привязки к потребности; пока это так, любое расчётное покрытие ошибается в
сочетаниях «одно сырьё нужно нескольким ветвям заказа». **Владелец выбрал: реализовать редакцию 16 с принятым риском**
(его случай — сырьё только под один ПФ переработчика — считается верно). Сочетания с общим сырьём нескольких ветвей —
TECHDEBT с примерами; точное решение — списание передачи «партии под заказ, затем свободные» (отдельная задача).
Обязательный гейт плана **не пройден** — это записывается в отчёт сборки и отчёт владельцу.
