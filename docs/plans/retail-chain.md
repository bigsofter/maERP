# Розничная сеть в типовой maERP и внедрение у FlyCDI (редакция 2.0.17)

Дата: 2026-11-09. Основание: анализ базы клиента — `docs/drissotex-analysis/flycdi-2026-11-09.md` (отчёты по
областям — `docs/drissotex-analysis/flycdi/`), решения владельца от 2026-11-09. Часы — FlyCDI, инициатива «Внедрение
maERP». Имя клиента в объектах `src/cf` не используется: все доработки — типовые возможности розничной сети.

## Решения владельца (2026-11-09)

1. Порядок: сначала релиз текущего `develop` (2.0.16.150) на GitHub, затем в новой редакции (2.0.17.*) — доработки
   типовой, затем обновление базы клиента.
2. «Внутренний заказ» клиента → **«Потребность торговой точки»** на существующем механизме потребностей:
   формирование, обработка центральным складом, контроль отгрузок, дат обработки и статусов; заполнение не только
   вручную, но и **по анализу** (ликвидность, скорость продаж, минимум) с рекомендациями магазину при формировании.
3. **Вид цены — у склада/точки.** Пустой = прежнее поведение (один вид для всех магазинов). Контроль цены «не ниже
   себестоимости» / «не ниже вида цен» — **отдельная настройка склада/магазина**.
4. **Обмен между базами — типовой**: план обмена, регистрация объектов, контроль, статусы, блокировки, включение обмена
   с конфигурацией поставщика. На переходный период — **расширение**: база контрагента может быть ещё на старой
   редакции. Это осознанное исключение из правила «разработка без расширений» (`CLAUDE.md`).
5. Отрасль **«Телефоны и аксессуары» с IMEI** — включаем сразу.
6. **Загрузка из Excel — универсальная** для любого документа: сопоставление колонок, сохранённые настройки загрузки
   (пресеты с быстрым выбором).
7. Остальное — на усмотрение разработчика (по отчёту анализа, раздел 2).

## Принцип переноса данных клиента

Корневой uuid и uuid 558 из 562 общих объектов у клиента совпадают с maERP — база обновляется нашим CF напрямую.
Всё, что берём из базы клиента, создаётся **с uuid клиента**: тогда его данные заходят без конвертации.
Имена при этом могут отличаться (сопоставление при загрузке конфигурации — по uuid). Таблица uuid — приложение А.

## Волны

Каждая волна — сборка 2.0.17.Y с секцией «Что нового» на четырёх языках. Существенные (все, кроме мелочей волны 5)
идут по схеме `CLAUDE.md`: свой план `docs/plans/retail-*.md` → `ai-review-plan` → реализация → `ai-test` →
`ai-review` → `ai-database`/`ai-security` по теме → `ai-final-check` → отчёт `.ai/reports/<slug>.md`.

### Волна 1. Склад как торговая точка: цена, контроль цены, касса — `retail-store-price`

- `МестаХранения.ВидЦеныПродажи` (uuid клиента `ВидЦены`). Правило выбора вида цены продажи:
  - **касса и розничные продажи со склада-точки** — вид цены склада → «Розничная». Договор не учитывается: касса сама
    создаёт покупателю договор с видом «Розничная» (`VentesEnDetail/.../Module.bsl:1067`), это не согласованная цена;
  - **прочие документы продаж** — нынешний порядок выбора каждого документа сохраняется как есть (например,
    `ЗаказПокупателя` и `КоммерческоеПредложение` берут `Контрагент.ТипЦены` независимо от договора,
    `ЗаказПокупателя/.../Module.bsl:440`, `КоммерческоеПредложение/.../Module.bsl:293`); вид цены склада заменяет
    только конечный откат на «Розничная».
  Пустой у склада — прежнее поведение во всех документах. Одна функция
  `ЦенообразованиеСервер.ВидЦеныПродажиПоУмолчанию(Склад)` для конечного отката вместо захардкоженной «Розничная»: касса (`VentesEnDetail`),
  подбор, печать этикеток, `ЗаказПокупателя`, `КоммерческоеПредложение`, `ИзбраннаяНоменклатураРМК`, `Номенклатура` и
  ещё ~15 мест — полный перечень с путями в плане волны (grep `ВидыЦен.Розничная`).
- `МестаХранения.КонтрольМинимальнойЦены` — перечисление `НеКонтролировать` (умолчание) / `НеНижеВидаЦен` /
  `НеНижеСебестоимости`, плюс `ВидЦеныМинимальный` (пусто → предопределённый `МинимальнаяЦенаПродажи`).
  Себестоимость — максимальная себестоимость единицы по партиям остатка склада (`ТоварыВНаличии`, по образцу
  клиента), по полному ключу партии (Характеристика, Партия, ДатаПартии, Серия, УУ), с отбором по складу и паре
  номенклатура + характеристика строк документа.
  Нет партий в остатке (продажа в минус) — строку не проверяем: политика отрицательных остатков. Партия ордерного
  склада, принятая приходным ордером, но ещё не оценённая (стоимость оформляется позже, `ТоварыВНаличии/ManagerModule`),
  — не «себестоимость 0»: порог берётся по последней цене закупки позиции (`ЦеныНоменклатурыПоставщиков`), нет и её —
  строка пропускается с предупреждением кассиру. Схема — в плане волны.
  Проверка одной общей функцией: в кассе — **до оплаты и фискализации** (иначе отказ после пробитого чека), в форме
  реализации — при проведении. На сервере — **всегда** при проведении документа со склада с контролем (в т. ч.
  проведение из списка), кроме явных исключений: `ОбменДанными.Загрузка`; служебные перепроведения, которые сами
  ставят флаг `ДополнительныеСвойства.БезКонтроляМинимальнойЦены` (групповое перепроведение, закрытие периода,
  пересчёт партий). Исключений по дате документа нет: служебные перепроведения старых продаж идут с флагом, а
  интерактивное перепроведение старой продажи ниже минимума требует роли-допуска, как и новая. Отсутствие флага =
  проверка. Нарушение — отказ с перечнем строк; обход — роль `ПродажаНижеМинимальнойЦены` (допуск).
- Мелочи кассы: `Контрагенты.НеОтображатьВИнтерфейсеКассира` (uuid клиента), комментарий к продаже с кассы, оплата
  долга в кассе — только неоплаченные (`ТолькоНеоплаченные`).
- Справочник **`Города`** (uuid клиента `НаселенныеПункты`) и `Контрагенты.Город` (uuid клиента) — необязательный.

### Волна 2. Потребности торговых точек — `retail-store-needs`

Модель (окончательно — по ревью плана волны):
- `МестаХранения.СкладСнабжения` — **Булево** с uuid клиента (у клиента это признак «склад снабжения», заполнен у
  всех складов; смена типа обнулит значения). Склад снабжения точки — новый реквизит
  `МестаХранения.СкладСнабженияТочки` (ссылка); обработчик обновления заполняет его единственным складом с
  признаком, при нескольких — оставляет пустым и сообщает.
- Документ **`ПотребностьТорговойТочки`** (uuid клиента `ВнутреннийЗаказ`). Все реквизиты клиента — с его uuid и типом
  не уже клиентского: «точка» = `МестоХранения` (9d80b383…), `Организация`, `Ответственный`, `Статус`,
  `Комментарий`; ТЧ `ТЧТовары` с `КодСтроки`, `Номенклатура`, `Характеристика`, `Упаковка`, `Серия`,
  `КоличествоУпаковок`, `Количество`. Нумерация как у клиента (строка 9, периодичность Год). Новые реквизиты (склад
  снабжения, желаемая дата) — с новыми uuid. 4 пилотных документа клиента не проведены (`Posting=Deny`) — приходят
  черновиками «Отправлена», без движений; склад обрабатывает их заново.
- Статусы — перечисление `СтатусыПотребностейТорговыхТочек` (uuid клиента `СтатусыВнутреннихЗаказов`). Значения
  клиента переименовываются с сохранением uuid (удалять нельзя — битые ссылки): Новый → Отправлена, Подтвержден →
  Принята, ВРаботе → ЧастичноОтгружена, Отклонен → Отклонена, Завершен → Закрыта; новые значения (Черновик,
  Отгружена, Получена) — с новыми uuid. Таблица uuid значений — в плане волны. Даты обработки — регистр сведений
  истории статусов (кто, когда).
- Регистр накопления **`ПотребностиТорговыхТочек`** по образцу `ПотребностиПроизводства`: точка, склад снабжения,
  потребность (документ), **КодСтроки**, номенклатура, характеристика, серия; ресурсы Потребность / Принято /
  Отгружено / Получено. Ключ строки (`КодСтроки` документа) нужен для построчного принятия, отклонения и исполнения;
  строка перемещения ссылается на потребность и её `КодСтроки`. Новый
  регистр, а не новое измерение `ПотребностиПроизводства`: там измерение `Заказ` типа `ЗаказПокупателя` и нет
  склада, смена типа — реструктуризация регистра с 21 модулем-читателем. «Задействовать механизм» = тот же паттерн
  ресурсов (потребность → принято/покрыто → пришло), те же функции дефицита и заполнения по образцу
  `ПотребностиПроизводства.ДефицитЗаказа`, общие блокировки, та же витрина в АРМ закупок.
- **Связь с закупками — агрегатная** (у `ЗаказПоставщику` и `ЗаказыПоставщикам` нет склада): дефицит склада
  снабжения = принятые неотгруженные потребности точек − **свободный** остаток складов с признаком `СкладСнабжения`
  (без зеркального прихода на `ПодчиненныйСклад` — `ТоварыВНаличии/ManagerModule.bsl:24-41` дублирует приход, такой
  склад в пул не входит; без **количества**, закреплённого за производством по позициям номенклатура +
  характеристика: пришло под заказ и ещё не израсходовано. **Готового источника нет**: ресурсы
  `ПотребностиПроизводства` такого количества не дают (`Пришло` включает возвраты поставщику, `ИзОстатка` — расход
  свободных партий, `ManagerModule.bsl:1020-1038, 1368-1385`), а `Производство.ПартииПодЗаказ` возвращает документы
  партий целиком. Связи остатка со строкой прихода в модели нет (`КодСтроки` в
  `ТоварыВНаличии` — реквизит движения, партия = документ поступления целиком). **Решение волны 2:** резерв
  производства в пул не вычитается; в АРМ закупок строка «Пополнение точек» показывает предупреждение, если у
  складов снабжения есть открытые потребности производства по той же позиции. Строковый резерв — пункт TECHDEBT) −
  **свободная**
  часть открытых заказов поставщикам по номенклатуре. Свободная = остаток `ЗаказыПоставщикам` − часть, уже
  закреплённая за потребностями производства: по ресурсам `ПотребностиПроизводства` только **заказанная** часть,
  ещё не пришедшая по заказу, — max(0, Заказано − (Пришло − ПришлоБезЗаказа)) по номенклатуре **и характеристике**
  (весь расчёт дефицита — в разрезе номенклатура + характеристика, как в `ЗаказыПоставщикам` и потребностях) (поступление без
  заказа поставщику заказанную партию не освобождает; та же логика, что в `ОстатокКПоступлению`, но без его ветки
  «непокрытая потребность», когда Заказано = 0). Закупка под заказ на производство розницу не покрывает. Это показывается в АРМ закупок отдельной строкой «Пополнение точек» и
  заполняет заказ поставщику; заказ поставщику потребность точки **не закрывает** (её закрывает перемещение), поэтому
  повторное заполнение не задваивает: открытые заказы уже вычтены. Допущение — склады снабжения считаются общим
  пулом; склад в заказе поставщику — отдельная задача, если владельцу понадобится.
- `ПеремещениеТоваров.ТЧТовары.Потребность` (uuid клиента `Заказ`, тип `ДокументСсылка.ПотребностьТорговойТочки` —
  тот же uuid документа, данные сохраняются). Перемещение в maERP двухшаговое (списание на «в пути», затем
  оприходование): колонка переносится в документ оприходования; списание пишет «Отгружено», оприходование —
  «Получено», одношаговое — оба сразу. `ПеремещениеТоваров.Перевозчик` (uuid клиента). Для баз других клиентов
  это новая колонка ТЧ перемещения — реструктуризация таблицы, оценить время на большой базе.
- **Рабочее место «Потребности точек»** для центрального склада: очередь по точкам и датам, просрочка обработки и
  отгрузки, принять/отклонить строку, «Создать перемещение» по выбранным, контроль отгружено/получено.
- **Рекомендации при формировании** («Заполнить по анализу» и колонки в форме): средние продажи точки за N дней
  (`Продажи` по `МестоХранения`), остаток точки, в пути (отгружено − получено), минимум/максимум
  (`МинимальныйОстатокПоСкладам`), класс ABC/XYZ (`ABCАнализ`), наличие на складе снабжения, рекомендуемое
  количество = max(минимум, продажи/день × дней запаса) − остаток − в пути − **открытые потребности этой точки**
  (отправленные и принятые, ещё не отгруженные, кроме текущего документа), с округлением до упаковки; меньше нуля — 0. Дней запаса и
  период анализа — настройки точки. Основа запроса — отчёт `ТоварыДляЗаказа`; ошибки клиента (средняя цена вместо
  средней продажи, оповещение без отбора по документу) не переносим.
- Оповещения: создание потребности → склад снабжения, перемещение → автор потребности; получатели по складу —
  `МестаХранения.ТЧПолучателиОповещения` (uuid клиента), они же для минимального остатка. История системных
  оповещений: формы списка и записи, команда «Системные сообщения».
- Права: новая роль `ПотребностиТорговыхТочек` (точка — создать/отправить свои), центральный склад — обработка;
  живая проверка ролей на копии базы.

### Волна 3. Универсальная загрузка из Excel — `excel-import-universal`

- Обработка загрузки в **любую табличную часть любого документа**: приёмник выбирается по метаданным, колонки
  файла сопоставляются с реквизитами ТЧ автоматически по заголовкам и вручную, поиск номенклатуры по
  штрихкоду/артикулу/коду поставщика/наименованию, предпросмотр с ошибками строк.
- **Настройки загрузки (пресеты)** — справочник `НастройкиЗагрузкиИзФайла` (приёмник = документ+ТЧ, сопоставление,
  строка заголовка, правила поиска; общий или личный), быстрый выбор последних пресетов приёмника.
- Вход: общая команда «Загрузить из Excel» для всех документов (по записанному документу, с обновлением формы) и
  тот же движок из форм шести документов, где кнопка уже есть (заполнение незаписанного объекта). Старая обработка
  `ЗагрузкаИзExcel` уходит под новый движок, режим «создавать товары» и «установка цен» сохраняются.
- Запись в документ — обычной записью объекта (не `ОбменДанными.Загрузка`), с проверкой права на изменение;
  проведённый документ после загрузки перепроводится с вопросом пользователю или загрузка в него запрещается
  (выбрать в плане волны). Пересчёт зависимых колонок (суммы, НДС, `КодСтроки`, `ТЧСерии`) — теми же процедурами,
  что форма. Перечень запрещённых ТЧ и колонок (служебные, `КодСтроки`, движения) — в плане волны.
- Это этап У3 из `docs/UNF-ADOPTION.md` — закрыть его там.

### Волна 4. Отрасль «Телефоны и аксессуары» с IMEI — `industry-phones`

- Значение `Отрасли.ТелефоныИАксессуары`, код хаба, `ПрименитьОтрасль` по образцу «Ткани»: включает серии и заводит
  доп. реквизиты номенклатуры `Модель`, `Совместимость` (для аксессуаров), `ГарантияМесяцев`. Состояние товара
  (новый / б/у / восстановленный) — существующий `Номенклатура.Качество` → `КачествоТоваров` (тот же uuid, данные
  клиента сохраняются), нового свойства не нужно. Цвет и память — характеристики или доп. реквизиты: решить в плане
  волны (характеристики дают остатки по цвету/памяти, но у клиента их нет и ФО выключена).
- Константа `ИспользоватьСерииНоменклатуры` сейчас к функциональной опции не привязана и поведение не меняет —
  в плане волны выяснить, что реально включает серии в документах, и привязать.
- IMEI = серия через существующий механизм `ТЧСерии` (`СерииИРазмещение.ОбъединитьТоварыССериями`), строки не
  дробятся до количества 1. Флаг номенклатуры «учёт по серийным номерам» (новая колонка справочника). Ввод/скан
  IMEI в поступлении, кассе, реализации, возврате, перемещении; поиск товара в кассе по IMEI; срок гарантии в чеке и
  накладной. `ТоварыВНаличии` уже имеет измерение Серия — реструктуризации остатков нет.
- **Требования к гарантиям IMEI** (детальная схема — в плане волны 4 с отдельным `ai-review-plan`; мастер-план её не
  фиксирует):
  1. Уникальность IMEI в базе при параллельном создании серий (регистр с измерением IMEI под блокировкой по значению;
     запрос по наименованию серии не гарантирует).
  2. Один физический экземпляр: IMEI не продаётся дважды и не приходуется дважды; соблюдается для расхода,
     повторной приёмки, отмены/изменения прихода по проданному IMEI и перемещения с правильного склада. Это узкое
     исключение из политики отрицательных остатков — только для номенклатуры с серийным учётом (**согласовано
     владельцем 2026-11-09**: для товаров с сериями уход в минус запрещён).
  3. Ограничения, которые схема обязана учесть (найдены ревью мастер-плана, круг 3): перемещение через склад «в
     пути» (`ТоварыВНаличии/ManagerModule.bsl:65-78`) не меняет сетевой итог — контроль нужен по складу списания;
     дублирование прихода на `ПодчиненныйСклад` (`ManagerModule.bsl:24-41`) — не считать дважды; промежуточная
     очистка набора при перепроведении (`AutoDelete`, bsl-029, `RecordSetModule.bsl:35-53`) — не отказывать на ней;
     блокировки поступления берутся по складу — взаимное исключение по IMEI нужно сетевое; `ЗаполнитьСерииПоОстаткам`
     добивает недостающее количество пустой серией.
  4. Переход существующих остатков: флаг включается у номенклатуры/группы с даты; несерийный остаток, набранный до
     флага, продаётся без IMEI **только в пределах этого остатка** (минус без серии для флагованной позиции
     запрещён); привязка IMEI к уже лежащему товару — пересчётом со сканированием (пересортица «без серии» →
     серия). У клиента серий нет — флаг ставит владелец по группам, когда магазины готовы сканировать.
  5. Касса: IMEI проверяется при сканировании, реализация проводится **до оплаты и фискализации**; отказ проведения —
     чек не пробивается. Нужен протокол незавершённой продажи (сейчас отмена оплаты просто возвращается, ошибка
     записи платежа только журналируется; платежи — отдельные документы, создаются последовательно,
     `VentesEnDetail/.../Module.bsl:716-733, 792-821`): проведённая реализация до полной оплаты имеет статус «ожидает
     оплаты». Полная оплата = все виды оплаты кассы по существующему расчёту оплат реализации: денежные документы,
     сертификат на оплату (`СертификатНаОплату`, гасит долг в `ВзаиморасчётыСПокупателями`) и отсроченная часть,
     оформленная штатной продажей в кредит (`ФормаСложнойОплаты.КомандаКредит`); новый вид оплаты кассы
     автоматически входит в этот расчёт, отдельного перечня в протоколе нет; сбой или отмена любой части оплаты **не откатывает** реализацию и уже записанные платежи
     автоматически — продажа остаётся «ожидает оплаты» с фактически записанными платежами; ошибка записи платежа
     больше не глушится, а показывается кассиру. Состав согласованной оплаты (виды и суммы, включая сумму в
     кредит) сохраняется в реализации до записи платежей — по нему восстанавливается смешанная оплата после сбоя;
     сейчас строка Credit нигде не сохраняется, кроме смены хозяйственной операции. Завершение — «доплатить» или «отменить продажу» (возврат уже
     принятых платежей документами возврата, сертификата — отменой его привязки, затем отмена проведения
     реализации). При открытии кассы и закрытии
     смены — список незавершённых продаж, закрытие смены с ними запрещено.
     Протокол хранит и **состояние выдачи чека**: этапы «реализация проведена → оплата записана → чек
     фискализирован (номер чека/смены)» записываются в реализации по мере выполнения, восстановление при сбое
     доводит продажу с того этапа, на котором она остановилась (в т. ч. повторная фискализация без повторной
     оплаты). То же — для контроля минимальной цены (волна 1).
  6. Ордерный склад: реализация с ордерного склада партии не списывает до расходного ордера, а блокировка проверки
     не оставляет резерва после транзакции. План волны 4 решает одно из двух: склад-точка с кассой для позиций с
     серийным учётом — только неордерный (проверка в настройке склада), либо IMEI закрепляется за реализацией
     отдельным резервом до расходного ордера.
- Возврат только по чеку, где этот товар/IMEI продавался (настройка, включена отраслью).

### Волна 5. Отчёты, инструменты, мелочи — `retail-tools`

Анализ инвентаризаций (uuid клиента), отгрузки с изменёнными ценами (uuid клиента, цена на дату продажи), экранный
прайс-чекер (uuid клиента), макеты этикеток «60×40 с QR» и «только наименование», «Товары в наличии» — только свой

мобильная приёмка через `ПриходныйОрдер` + `ПоступлениеТоваровУслуг.ОтветственныйЗаПриемку` (uuid клиента), пункт
«Задание на пересчёт» в мобильном меню, роли-допуски на правку проведённых реализаций и поступлений — **с uuid
клиентских ролей** `РеализацииИзменениеПроведенных` и `РедактированиеПоступлениеТоваровУслуг`, чтобы назначения
пользователям сохранились. Для `АнализИнвентаризаций` — три значения `ПоказателиДвиженияТоваров` (`Оприходовано`,
`ПеремещениеСписание`, `ПеремещениеОприходование`) с uuid клиента.

### Волна 6. Типовой обмен между базами maERP — `exchange-maerp`

- План обмена `ОбменМеждуБазами` (узел = база контрагента; контрагент, организация, склад приёма, что выгружать:
  реализации как поступления, установки цен; статус обмена). Регистрация изменений подписками с фильтрами узла,
  номера сообщений, квитирование.
- Свой формат сообщения (XML, ключи сопоставления вместо локальных ссылок: ICE/NIF организации и контрагента,
  артикул/штрихкод номенклатуры, uuid документа источника), регистр соответствий объектов.
- Транспорт: HTTP-сервис публикации maERP (основной) и файловый каталог (запасной). Учётные данные — в отдельном
  регистре с привилегированным доступом, не в карточке контрагента. COM не используем.
- Мастер «Настройка обмена с базой поставщика/покупателя», монитор обмена (статусы, ошибки — `ИсторияОбменаДанными`,
  `ОшибкиОбменаДанными`), блокировки повторного запуска, регламентное задание. Приём: `ОбменДанными.Загрузка`,
  поступление создаётся непроведённым и попадает в мобильную приёмку. Это конвертация «реализация → поступление»,
  а не перенос того же объекта: поступление записывается **обычной записью**, без `ОбменДанными.Загрузка`.
  `ПередЗаписью` поступления (`ObjectModule.bsl:340-357`) суммы строк не рассчитывает — только итоги из готовых
  `СуммаСНДС`/`СуммаНДС`, поэтому приёмник сам считает строку (Сумма, СуммаНДС, СуммаСНДС, `КодСтроки`) теми же
  процедурами, что форма документа, и только потом пишет. Регистрация обратно на тот же узел отсекается фильтром
  подписки (документ, созданный из обмена, помечен узлом-источником), а не режимом загрузки. HTTP-сервис = публикация и технический пользователь в базе-приёмнике — обязательный `ai-security`; пароли —
  только в регистре с доступом из привилегированного модуля.
- Продажа «по себестоимости внутри группы» — опция договора, работает с обменом.
- Мёртвые заготовки (`ВнешнееСоединение`, `ПараметрыОбменаДанными`, `РегистрацияИзмененийДляОбменаДанными`) —
  задействовать или выпилить; закрывает пункт TECHDEBT про `V83.comconnector`.

### Волна 7. Переходное расширение и обновление базы клиента — `retail-client-update`

- Расширение `src/ext/ОбменСоСтаройРедакцией`: из обновлённой maERP — выгрузка реализаций и цен в базы контрагентов,
  оставшиеся на старой редакции 1C:Commerce (COM, Windows; формат старой базы), реквизиты подключения с uuid клиента
  переносятся в регистр учётных данных волны 6. Сборка расширения — первое использование `src/ext`, дописать
  скрипты (`SRC_EXT`).
- Сервер клиента — Windows (подтвердил владелец 2026-11-09), COM-подключение к старым базам партнёров доступно; версию платформы зафиксировать до начала волны.
- **Выгрузка до обновления — внешней обработкой на старой конфигурации клиента** (обработок maERP там ещё нет), в
  файл во временном каталоге: значения реквизитов приложения Б и реквизитов обмена контрагента (данные реквизитов,
  которых нет в maERP, удаляются при реструктуризации — реквизит расширения с тем же uuid их не вернёт), назначения
  ролей пользователей, число ссылок на значения перечислений, которых нет в maERP (приложение В). Файл с паролями
  чужих баз удаляется после переноса.
- **Загрузка после обновления**: ПКО/РКО — пакетами с `ОбменДанными.Загрузка = Истина`, без
  перепроведения; реквизиты обмена — в узлы плана обмена волны 6 и учётные данные; роли — типовые вместо
  `PDVПросмотрРеализаций` и `РуководительПродаж`, проверка, что ни один пользователь не остался без ролей.
- Прогон на копии `build/ib-flycdi`: выгрузка → **отключить и удалить расширение `МароккоCOM`** → загрузка CF →
  реструктуризация → обработчики обновления → загрузка значений (вкл. записи `Убытки`) → дата запрета на дату
  обновления → смок → сверка остатков, взаиморасчётов, кассы и `Убытки` до/после → живая проверка ролей кассира и мобильного пользователя → `.dt`.
- Каждый объект с uuid клиента сверяется по свойствам: тип и длина кода/номера, иерархия, владельцы, типы
  реквизитов — не уже, чем у клиента, иначе данные обрежутся при конвертации.

## Приложение Б. Реквизиты с разными uuid — перенос обработкой при обновлении

`ПриходныйКассовыйОрдер.МестоХранения`, `РасходныйКассовыйОрдер.МестоХранения`,
`Кассы.МестоХранения`; `Контрагенты.СуммаКредита`, `СрокОплаты`, `КонтрольКредита`, `СпособРасчётаОтсрочки` (если

`УстановкаЦенНоменклатуры.Категория` (проверить заполненность); измерения `Убытки.МестоХранения`,
`ХозяйственнаяОперация` — **не перепроведением**: у клиента ПКО по прочим расчётам и расчётам с физлицами пишет
отрицательный убыток, в maERP такой ветки нет, и перепроведение молча изменит историю. Записи `Убытки`
выгружаются до обновления и восстанавливаются наборами по регистратору с `ОбменДанными.Загрузка = Истина`; сверка
итогов `Убытки` по складу и операции до/после — отдельный пункт сверки.
**Защита перенесённой истории** — не датой запрета редактирования (у неё есть обходы: настройка пользователя и
разовое разрешение, `РаботаСДокументами.МожноРедактироватьДокумент`) и не запретом всех ранних документов (касса
штатно записывает и перепроводит старый `СертификатНаОплату` при оплате им новой продажи,
`VentesEnDetail/.../Module.bsl:716-724`). Защищаются **только документы, чьи движения восстановлены переносом**
(ПКО, РКО, регистраторы `Убытки`): обработка переноса записывает их в регистр сведений `ПеренесенныеДокументы`
(документ, дата переноса). Для документа из этого регистра проведение, отмена проведения, запись с изменением
движений и удаление запрещены всем без исключений, включая полные права и групповое перепроведение; снимается
только удалением записи администратором. Проверка — в общих подписках `ПередЗаписью` **и `ПередУдалением`**
документов (непосредственное удаление и программное `Удалить()` проходят мимо `ПередЗаписью` и модуля набора,
правило tiny1C bsl-024); при `ОбменДанными.Загрузка` не действует — нужна для загрузки истории. Служебные
механизмы, которые перепроводят ранние документы внутри другой транзакции
(`ПодпискиНаСобытия.ПослеПроведенияДокументаОплаты` → `НалоговыеДокументыНаОснованиях.ПерепровестиПокрывающиеДокументы`
и подобные — перечень в плане волны 7), защищённые документы **пропускают** без ошибки. Остальные ранние документы
(сертификаты, договоры, реализации) живут по обычным правилам. Пригодится каждому переходу на maERP со старой учётной системы. `ПрочиеРасходы` — документов 0, переноса не нужно.

Роли клиента с uuid: `РеализацииИзменениеПроведенных`, `РедактированиеПоступлениеТоваровУслуг` — выписать в плане
волны 5.

(запрет продажи в минус противоречит политике отрицательных остатков), `ФормаПоискаДокумента` кассы, Devis из заказа,
`Организации.СтавкаНДС`, роль-флажок `PDVПросмотрРеализаций`, правки ролей клиента, роль `РуководительПродаж`
(собирается из типовых ролей). Осознанные потери данных при обновлении: документ `ОтгрузкаТовара` (1, не проведён),
регистры `НДСПродажи`, `ОтгрузкиТоваров`, `ТоварыНедостача` (пуст), корзина `ТоварыДляЗаказа` (пилот),
`ЗаказПокупателя.МестоХранения` (6 заказов), планы обмена с сайтом.
