## Состав сборки 1

1. **Детальный раздел плана и ревью до кода.**
   - В `docs/plans/machines.md` — раздел «Сборка 1 — детально»: точные имена, типы и uuid новых объектов, роли и
     права, тексты на четырёх языках, тесты.
   - Затем `.ai/bin/ai-review-plan machines-s1` (Codex). Если он в лимите — субагент `architecture-critic`, и
     владельцу прямо сказать, что гейт не пройден.
   - В тот же прогон повторить ревью общего плана: первый Codex-гейт по `machines.md` не пройден.
2. **Настройки производства** (`DataProcessors/НастройкиПрограммы/Forms/Производство`, по образцу
   `ИспользоватьПереработку`):
   - константа и функциональная опция **«Учёт станков»** (`ИспользоватьУчетСтанков`); доступна только при включённом
     «Производстве»;
   - константа-флажок **«Списывать материалы на станок при размещении»**; доступна только при включённом учёте
     станков; в сборке 1 только хранится, используется со сборки 2;
   - запрет выключения опции при остатке материалов на станках — в сборке 2, здесь пометить точку расширения.
3. **Станок — справочник `ПроизводственноеОборудование`.** Расширять без смены uuid: это данные Drissotex.
   - **Реквизиты:**
     - вид станка — строка или перечисление, решить в детальном плане;
     - **выработка, кг/ч** — одно число;
     - **время на смену заказа, мин**;
     - склад станка (`МестаХранения`);
     - стоимость часа работы;
     - оператор по умолчанию;
     - **«Выведен»** — булево.
   - **ТЧ «Режим работы»:** день недели, начало и окончание смены (время — по mdo-003). Смена через полночь
     допускается.
   - **Праздники** — по регистру `ПроизводственныйКалендарь`. Сначала проверить, что он хранит и кто его ведёт; если
     он не годится, решение записать в план.
   - **Функция «фонд времени станка за период»** — в новом общем модуле `ЗагрузкаСтанков`, с тестом.
   - Форма элемента и форма списка (колонки «Выработка» и «Выведен»; выведенные скрыты отбором по умолчанию).
4. **Обслуживание и простои:**
   - документ **«Обслуживание станка»**: станок, вид (перечисление: плановое ТО, ремонт или авария, переналадка,
     прочее), план или факт, начало, окончание, причина, исполнитель, затраты, комментарий;
   - проведение пишет регистр сведений **«Загрузка станков»** (подчинён регистратору): станок, начало — измерения;
     окончание, часы, вид записи (работа или обслуживание), план или факт — ресурсы. Требование-накладная (сборка 2)
     будет писать туда же;
   - запись идёт под исключительной блокировкой станка с проверкой пересечения интервалов;
   - отчёт СКД **«Простои станков»**: часы и число случаев по станкам, видам и причинам за период; фонд времени и %
     простоя.
5. **Меню и права:**
   - «Производство → Нормативы»: «Станки»;
   - документы производства: «Обслуживание станков»;
   - «Производство → Отчёты»: «Простои станков»;
   - всё под опцией;
   - роль руководителя производства выбрать по матрице ролей (`МенеджерПроизводства` нет); `ОператорПроизводства` —
     ввод обслуживания;
   - проверка — `scripts/menucheck.py`.
6. **Проба поля «Планировщик» (главный риск волны):**
   - отдельная форма обработки — например, `Обработки.ЗагрузкаСтанков.Форма.ПробаПланировщика`, без связи с АРМ;
   - станки — измерение, записи «Загрузки станков» — элементы, шкала — часы и дни;
   - перетаскивание элемента пишет перенос;
   - открыть на клиенте macOS по копии базы, снять окно (только окно 1С, по id) и записать вывод в план: планировщик
     годится или берём табличный документ;
   - если XML поля не собирается по модели EDT (`PlannerExtInfo`) — проверить по jar `~/.p2` и записать правило в
     tiny1C.
