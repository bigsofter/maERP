# План: перенос старых свойств номенклатуры в дополнительные реквизиты и удаление старой ТЧ (2026-10-10)

Задача владельца 2026-10-10 (хвост плана `docs/plans/nomenclature-ui.md`, раздел 9, решение 2; TECHDEBT «Два механизма
свойств номенклатуры»). Уровень — **существенная**: обработчик обновления, данные клиентов, удаление табличной части.
Часы — TinyCIO.

## 1. Что есть (факты, полный поиск 2026-10-10)

- `Справочник.Номенклатура`, ТЧ `СвойстваНоменклатуры` (`СвойствоНоменклатуры` → `Справочник.ВидыСвойствНоменклатуры`,
  `ЗначениеСвойства` → `Справочник.ЗначенияСвойствНоменклатуры`). На карточке закладка скрыта (2.0.16.62 — тоже).
- `ВидыСвойствНоменклатуры`: наименование (50), реквизит `ТипЗначенияСвойства` (`Перечисление.ТипыЗначенийСвойствНоменклатуры`:
  Строка, Число, Дата). `ЗначенияСвойствНоменклатуры`: владелец — вид свойства, код 8, реквизит `ЗначениеСвойства`
  (Строка/Дата/Число).
- Код (`.bsl`) их не использует: совпадения по имени — чужие (`Производство.СвойстваНоменклатуры` — функция,
  `СоздатьСвойстваНоменклатуры` — команда отрасли «Ткани»). Ссылки в метаданных: формы номенклатуры (колонки/поля ТЧ в
  `ФормаЭлемента`, поля списков), роли `PDV`, `ЛичныйКабинет`, `MobileClient`, общий реквизит `УдалитьАвторОбщий`, `Configuration.mdo`.
- Новый механизм: ПВХ `ДополнительныеРеквизиты` (тип значения — `ЗначенияДополнительныхРеквизитов`, `Контрагенты`,
  `Номенклатура`, Строка(200), Дата, Булево, Число(15,3)), значения-элементы — `Справочник.ЗначенияДополнительныхРеквизитов`
  (владелец — свойство), запись значения — `УправлениеСвойствами.УстановитьЗначениеСвойстваВОбъекте` (одна строка на свойство).
- Заполненность ТЧ у клиентов **не известна**: базы клиентов отсюда не читаются без щелчка владельца (окно «Предупреждение
  безопасности» внешней обработки). Поэтому обработчик переносит всё, что есть, и пишет отчёт.

## 2. Главное ограничение — порядок обновления и границы задачи

Обработчики обновления выполняются **после** реструктуризации базы, и не при загрузке CFU, а при первом входе
администратора в «Предприятие» (`ОбновлениеПрограммыВызовСервера.ОбработатьНачалоРаботы`). Если в той же сборке удалить
ТЧ из метаданных, её данные исчезнут при реструктуризации раньше, чем обработчик их прочтёт. Поэтому:

- **Эта задача — только сборка A (2.0.16.66): перенос.** Ничего не удаляется: ТЧ, справочники и перечисление остаются.
- **Удаление (сборка B) — отдельная задача со своим планом и ревью плана**, после подтверждения владельца. Её условия,
  которые эта задача только записывает (TECHDEBT, ROADMAP), а не реализует:
  - доказательство переноса на базе — версия базы в `ВерсииПодсистем` ≥ 2.0.16.66: обработчик A при любой ошибке
    вызывает исключение (п. 3.4), и версия не поднимается, пока перенос не завершён без ошибок; приложение не может
    помешать реструктуризации до входа, поэтому проверка — по каждой базе клиента до выдачи ей B;
  - поставка B: источники CFU — только CF версии ≥ 2.0.16.66 (явный список аргументов `dist-build.sh`), проверка — по
    базе поставки (`DIST_IB`), а не по рабочему дереву (ревью плана Codex, P0); как именно — решает план B;
  - B удаляет только ТЧ `СвойстваНоменклатуры`; справочники `ВидыСвойствНоменклатуры`/`ЗначенияСвойствНоменклатуры` —
    словарь значений, в том числе не использованных ни одним товаром, — остаются до отдельного решения владельца
    (ревью плана Codex, P0: значения без ссылок из товаров иначе пропали бы).

## 3. Сборка A — перенос

Обработчик `ОбновлениеПрограммыОбработчики.ПеренестиСтарыеСвойстваНоменклатуры` (версия 2.0.16.66, монопольно,
идемпотентный). Переносится **весь** старый механизм, а не только используемое (ревью плана Codex, P0: справочники
удаляются целиком):

1. **Свойство на каждый вид** `ВидыСвойствНоменклатуры` — все, в том числе помеченные на удаление (ревью плана Codex,
   P1: пометка не означает отсутствия ссылок; пометка в отчёт): `УправлениеСвойствами.ДобавитьСвойство` с `Имя` =
   `"СтароеСвойство_"` + уникальный идентификатор вида без дефисов — повторный запуск находит то же свойство по имени,
   наименование — наименование вида. **Тип значения — фактические типы значений вида**, а не ссылка на элементы (ревью
   плана Codex, P0: данные старого значения — его реквизит `ЗначениеСвойства` составного типа Строка(10)/Число(10)/Дата,
   представление строится из него же) и не только объявленный `ТипЗначенияСвойства` (ревью плана Codex, P1: тип вида
   меняется в форме без конвертации значений): объединение объявленного типа и типов `ЗначениеСвойства` всех значений
   вида; при смеси — составной тип (подмножество типа ПВХ, tiny1C bsl-007). Значение переносится как есть, без
   приведения. Квалификаторы ПВХ (Строка(200), Число(15,3), Дата) шире старых: обрезки нет. Вид без типа и без значений —
   Строка (в отчёт).
2. **Значения.** Новых элементов не создаётся: строка товара получает `ЗначениеСвойства` старого значения как есть.
   Словарь значений остаётся в старом справочнике (раздел 2) — ничего не теряется. **Явный ноль, пустая строка и пустая
   дата** в новом механизме неотличимы от «не задано» (форма карточки и `УстановитьЗначениеСвойстваВОбъекте` удаляют строку
   незаполненного свойства — так устроен механизм, ревью плана Codex, P1): такие строки не переносятся, а перечисляются в
   отчёте (товар, вид, значение); источник — старая ТЧ — остаётся до сборки B, и её план решает их судьбу.
3. **Строки товаров.** На каждый вид у товара — значение **последней строки** этого вида (семантика нового механизма);
   если у товара уже есть значение этого нового свойства — не перезаписывается (в отчёт «уже задано»); пустое значение
   строки — пропуск (в отчёт). Запись — `УстановитьЗначениеСвойстваВОбъекте`, объект с `ОбменДанными.Загрузка = Истина`,
   каждый товар своей транзакцией с управляемой блокировкой товара. ТЧ в сборке A **не очищается**.
4. **Отчёт и ошибки.** Счётчики (видов, значений, товаров, строк, пустых, «уже задано») — в журнал регистрации. Ошибка
   записи товара не останавливает перебор, но **в конце обработчик вызывает исключение** со списком товаров (ревью плана
   Codex, P0: возврат без исключения поднимает версию, и повторного запуска не будет). Обновление базы тогда не завершится,
   администратор видит причину; повторный запуск дописывает только недописанное (шаги 1–3 идемпотентны).
5. Порядок новых свойств в форме — после существующих.

## 3а. Поставка A

Версия 2.0.16.66 в `Configuration.mdo`, секция «Что нового» на ru/fr/en/es (ревью плана Codex, P2).

## 4. Проверка

- Сценарий `ТестыДокументов` `ПереносСтарыхСвойств` (в откатываемой транзакции): виды типов Строка и Число,
  неиспользуемый вид, помеченный вид, товар с дублем строк одного вида и строкой другого, второй товар с уже заданным
  новым свойством; обработчик вызывается дважды. Сверка: свойство на каждый вид (и неиспользуемый, и помеченный) с типом
  вида, у товара — значение последней строки дубля нужного типа, у второго — прежнее значение, повторный вызов ничего не
  добавил, ТЧ и справочники не тронуты; регистрация обработчика — строка с версией 2.0.16.66 и именем процедуры в
  `ОбновлениеПрограммы` (таблица обработчиков). Исключение при ошибке записи — функцией сборки текста ошибки (настоящий
  отказ записи внутри транзакции сценария испортил бы её).
- Отказ одного товара (ревью плана Codex, P2): обработка товаров вынесена в функцию, принимающую список товаров;
  сценарий последним шагом передаёт ей несуществующую ссылку (отказ до начала транзакции товара — внешняя транзакция
  сценария не портится) между двумя настоящими товарами и сверяет: оба настоящих перенесены, ошибка собрана, итоговое
  исключение обработчика поднято (ловится в сценарии).
- Сохранение версии при исключении — по коду `ОбновлениеПрограммы` (версия пишется после успешного выполнения всех
  обработчиков; подтверждено ревью плана) и на копии базы: `build/ib-kp` с подложенными строками старой ТЧ обновляется до A
  штатно; журнал регистрации и реквизиты сверяются; повтор обработчика ничего не добавляет.

## 5. Риски

- Неизвестный объём у клиентов — обработчик монопольный, но по товару своей транзакцией; при десятках тысяч строк —
  минуты. Замер на копии базы клиента при приёмке.
- Наименование вида длиннее 150 символов не бывает (50) — обрезки нет.
- Совпадение имени `СтароеСвойство_*` с существующим свойством невозможно (префикс новый, `git grep` пусто).
- Удаление (сборка B) без всех обновлённых баз — потеря данных: решение только владельца, в TECHDEBT.

## 6. Ревью плана

Codex `ai-review-plan old-item-properties`, четыре круга 2026-10-10: 1–3 — reject (P0: соответствие значений по
представлению, подавление ошибок записи, обход сборки A при поставке B, неполный перенос справочников; потеря типа значения;
P1: помеченные виды, ноль значения, тип вида против фактического типа значений), 4 — **approve_with_changes**. Две P2
последнего круга:
- база без записи версии и без номенклатуры считается пустой и получает только начальное заполнение — перенос видов не
  выполнится. **Отклонено:** в такой базе нет товаров, а значит и строк старой ТЧ; виды и значения остаются в старых
  справочниках, которые сборка B не удаляет (раздел 2);
- отказ до начала транзакции товара не проверяет откат неуспешной записи и фиксацию соседних товаров. **Принято как
  ограничение:** внутри откатываемой транзакции сценария этого не проверить; проверка — на копии базы при приёмке (TESTING).
