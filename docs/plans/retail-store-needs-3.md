# Сборка 2.0.17.6: оповещения по потребностям точек (`retail-store-needs-3`)

Волна 2 мастер-плана `docs/plans/retail-chain.md`, сборка 2.3 (2.1 — `retail-store-needs.md`, 2.2 —
`retail-store-needs-2.md`).

## 1. Спрос точек в АРМ закупок — не в этой сборке

Ревью плана (круг 1) показало, что спрос точек нельзя корректно встроить в строку «Пополнение» АРМ закупок без
переделки самого расчёта пополнения: он считает сумму положительных дефицитов складов, а не общий пул складов
снабжения; работает по номенклатуре без характеристик, тогда как строка потребности исполняется только той же
характеристикой; резерв производства вычитает партии-документы целиком; свободные заказы поставщикам делились бы
между минимумами складов и спросом точек. Отдельная строка «Пополнение точек» по мастер-плану требует своего пула по
«товар + характеристика» и правила разделения открытых заказов поставщикам между видами спроса — это решение
владельца и отдельная сборка. Запись в TECHDEBT; до неё закупщик видит спрос точек в списке потребностей (отбор
«Принята», колонки принято / отгружено, 2.0.17.5).

## 1а. Оповещения

- `МестаХранения.ТЧПолучателиОповещения` (uuid клиента 96d01978-…, колонка `Получатель` 1bddac44-…, `Пользователи`)
  — получатели оповещений склада; в форме склада — таблица «Получатели оповещений».
- События (регистр `СистемныеОповещения.Сформировать`, навигационная ссылка на документ):
  - потребность отправлена → получатели склада снабжения;
  - принята, отклонена, закрыта → ответственный (автор) потребности;
  - отгрузка по потребности (списание) → ответственный потребности («отгружено по потребности N»): по **каждой
    потребности** в новых движениях списания, у которой в прежних движениях этого документа отгрузки не было
    (добавленная в проведённое списание потребность тоже оповещается). Однократность — по ключу события: ID записи
    регистра — детерминированный UUID из MD5 строки «отгрузка|списание|потребность»; запись с таким ID у получателя
    уже есть — не повторяется (перепроведение и отмена с повторным проведением не дублируют).
- Вызов — после записи (`ПриЗаписи` потребности по смене статуса; `ОбработкаПроведения` списания), в той же
  транзакции: отказ записи — оповещения нет. Новая процедура регистра `СформироватьОднократно(Сотрудник, Ключ,
  Описание, Ссылка)`.
- **Защита регистра оповещений**: сейчас роли `PDV`, `МенеджерПоЗакупкам`, `ОператорПроизводства`, `MobileClient`,
  `ЛичныйКабинет` читают и меняют `СистемныеОповещения` без ограничения по получателю (стандартные команды списка
  открыты). Новые адресные сообщения о потребностях этого не должны наследовать: RLS чтения и изменения
  `ГДЕ Сотрудник = &Пользователь` у всех ролей с правом на регистр. Код модуля регистра (запись, показ непоказанных,
  отметка) работает привилегированно; единственный чтец вне модуля — `ПроцедурыРегламентныхЗаданий.
  СформироватьОповещенияБезПовторов` (читает непоказанные сообщения нескольких пользователей, вызывается и из
  проведения под пользователем) — его запрос переводится в привилегированный режим, иначе RLS сломал бы рассылку
  запретов отгрузок и минимальных остатков.
- Ответственный потребности необязателен: пустой — оповещение автору не пишется; `ПередЗаписью` заполняет пустого
  ответственного текущим пользователем (новый документ и черновик).
- История системных сообщений (форма и команда в разделе) — не в этой сборке (TECHDEBT); после RLS стандартный
  список регистра показывает пользователю только его сообщения.

## Тесты

1. `ПотребностиОповещения`: получатель склада снабжения получает оповещение при отправке; автор — при принятии и
   при списании; перепроведение списания второго оповещения не даёт.

## Порядок и проверки

ТЧ склада и форма, оповещения; «Что нового» 2.0.17.6; lint, refcheck, listcheck, colfont;
`ib-sync`; смок; тесты; `ai-review` → `ai-security` → `ai-final-check --db` → отчёт.

## Риски

- Оповещения пишутся в транзакции записи документа: сбой записи оповещения отменяет запись документа (запись
  регистра сведений — без внешних вызовов).

## Статус ревью плана

- Круг 1 — reject (4 P1 по встраиванию спроса точек в пополнение АРМ закупок): интеграция с АРМ закупок вынесена из
  сборки (раздел 1, TECHDEBT, решение владельца); сборка — оповещения.
- Круг 2 — reject (P0): RLS регистра оповещений по получателю у всех ролей; оповещение об отгрузке — по каждой
  потребности, однократно по ключу события.
- Круг 3 — reject: запрос рассылки без повторов — привилегированно (RLS); пустой ответственный — без оповещения,
  дозаполнение текущим пользователем.
