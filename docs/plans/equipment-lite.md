# Торговое оборудование: облегчённая БПО и устойчивые рабочие места

Задача владельца 2026-10-18. Торговое оборудование и удобство работы с ним — приоритет (снимает развилку Р2: оборудование
нужно). Взять современный подход БПО из УНФ, но без перегрузки базы: фискальные регистраторы не нужны. Админ настраивает
оборудование быстро, в идеале клиент сам — лёгким мастером. Отдельно две жалобы клиентов: форма настроек оборудования не
загружается (драйверы 32/64 бит), и рабочее место периодически «отваливается» — система создаёт новое с пустым списком
оборудования.

Ответы владельца 2026-10-18:
- принтеры: принтеры чеков (ESC/POS), принтеры этикеток, обычные Windows-принтеры;
- устройства: сканеры штрихкода, весы, дисплей покупателя, денежный ящик; позже — RFID;
- запуск на кассах: тонкий клиент на ПК и автономная локальная база на кассовой машине.

## Факты (исследование 2026-10-18)

**Сейчас в maERP** — перенесённая старая БПО, 11 модулей `МенеджерОборудования*` (~16 тыс. строк) и два модуля
универсального драйвера (~6,3 тыс.), на карантине с 2026-08-24 (ROADMAP блок 4).
- Реально работают: сканер (`ОперацииСПодключаемымОборудованиемКлиент.ПодключитьОборудование`, событие `ScanData`
  примерно в 20 формах, РМК `VentesEnDetail`), чек — табличным документом на Windows-принтер из
  `НастройкиПользователей.ПринтерЧеков` (`ПечатныеФормыКлиент.ВыполнитьКомандуПечатиНаПринтер`), этикетки —
  `ПечатныеФормыКлиент.ВывестиСтикерыНаПринтер` (WMI). Драйвер оборудования печать не использует.
- Весы, дисплей, принтер чеков как устройство — типы закомментированы (`МенеджерОборудованияВызовСервераПереопределяемый`
  строки 11–70), доступны только сканер, ККТ и эквайринг. Фискальная очередь без внешних точек входа.
- `ОбновитьПоставляемыеДрайвера` регистрирует 110 драйверов: 57 ссылаются на отсутствующие макеты, 35 — только ProgID COM.
- Макеты драйверов в CF — ~66 МБ, из них ~55 МБ — российские эквайринговые терминалы (MPos2can 22 МБ, IboxPro 13 МБ,
  SKAM 4,8 МБ, Сбербанк, ИНПАС, ARCUS, ГАЗПРОМБАНК, TRPOS, Ярус). CF 2.0.16.70 весит 82 МБ.
- Разрядность не учитывается нигде. Форма настроек по умолчанию — универсальная `ФормаНастройкиУниверсальныйДрайвер`
  (`МенеджерОборудованияКлиент:104-111`), она строит параметры динамически из описания драйвера и имеет страницу
  «драйвер не установлен». Ломается не выбор формы, а создание объекта драйвера: для COM ProgID (`Новый(ProgID)`,
  `МенеджерОборудованияКлиент:1683-1733`) 32-битная компонента в 64-битном клиенте 1С (и наоборот) не создаётся,
  ошибка гасится общим `Попытка` без причины, и форма остаётся без параметров — это и есть «форма настроек не
  подгружается» (гипотеза по коду; на кассе клиента подтвердить разрядностью клиента и драйвера).
- **Рабочее место** — `Справочник.РабочиеМеста.Код = ВРег(СистемнаяИнформация.ИдентификаторКлиента)`, поиск только по коду
  (`МенеджерОборудованияВызовСервера:175-196`), при промахе `ОбновитьРабочееМестоКлиента`
  (`МенеджерОборудованияКлиент:428-461`) молча создаёт новое и ставит его в сеанс. Оборудование остаётся на старом.
  Имя компьютера хранится, но в поиске не участвует; уникальность кода не проверяется.

**БПО в УНФ 3.0.14** (`build/unf_14_123/`):
- Ядро (`МенеджерОборудования*`, `ПодключаемоеОборудованиеДрайверКлиент`, `ВнешниеКомпонентыБПО*`, `ОбщегоНазначенияБПО*`)
  плюс модули по типам: `ОборудованиеУстройстваВвода*`, `ОборудованиеВесовоеОборудование*`, `ОборудованиеДисплеиПокупателя*`,
  `ОборудованиеПринтерыЭтикеток*`, `ОборудованиеЧекопечатающиеУстройства*` (13 тыс. строк, из них для принтера чеков
  нужно ~300: печать текста и денежный ящик). Подсистемы-типы ядро проверяет через `ОбщегоНазначенияБПО.Используется*()`,
  поэтому ненужные вырезаются целиком.
- Драйверы: `ДрайверыОборудования.СпособПодключения` — ИзМакета (Native zip в общем макете), ЛокальноПоИдентификатору
  (COM), ИзИнформационнойБазы (загружен из файла или с ИТС). Native-драйверы 1С (`Драйвер1СУстройстваВводаNative`,
  `Драйвер1СПринтерЧеков`, `Драйвер1СЭлектронныеВесы`, `Драйвер1СДисплейПокупателя`) несут Win32/Win64/Linux/Mac
  в одном zip — разрядность решает платформа по MANIFEST. Размер в выгрузке: 14 / 30 / 12 / 23 МБ.
- Одна общая форма настроек `ПодключаемоеОборудование.ФормаНастройки`: драйвер отдаёт XML `<Settings>` через
  `ПолучитьОписание`/`ПараметрыОборудования`, форма строит реквизиты `P_*` динамически; кнопки «Тест устройства»,
  «Автонастройка», «Установить драйвер». При неподключённом драйвере — отдельная страница «Компонента не установлена».
- Рабочие места: табличные части `ИдентификаторыКлиентов` и `MACАдреса`, поиск по приоритетам (код → доп. идентификаторы →
  MAC+имя компьютера → имя компьютера → MAC), диалог «обновить идентификатор у текущего / создать новое / продолжить»
  (в тексте прямо названа смена характеристик RDP-сервера), привязка нового идентификатора к найденному месту.
- Мастера подключения в БПО нет; копирования оборудования между рабочими местами нет.

## Причины жалоб

1. **Новое рабочее место.** Любая смена `ИдентификаторКлиента` даёт промах поиска и молчаливое создание. Когда платформа
   меняет идентификатор, из репозитория не проверить (профиль Windows, переустановка или смена разрядности платформы,
   чистка профиля — гипотезы); УНФ эту ситуацию обходит, значит она реальная. Обход не зависит от причины: искать не
   только по идентификатору и не создавать молча.
2. **Форма настроек.** Драйверы через COM ProgID требуют совпадения разрядности компоненты и клиента 1С; диагностики нет,
   форма открывается пустой. Native-драйверы из макета с обеими разрядностями проблему снимают; для COM, если оставить,
   нужен понятный текст «драйвер 32-битный, клиент 64-битный — поставьте …».

## Решение

Не переносить БПО УНФ целиком (с фискальным контуром — десятки тысяч строк), а собрать «БПО-лайт» из её ядра и модулей
нужных типов, заменив нынешнюю подсистему. Сначала — отдельная небольшая сборка по рабочим местам: она снимает самую
болезненную жалобу на текущем коде и переносится в новую подсистему без изменений.

### Фаза 1 — устойчивое рабочее место (на текущей подсистеме)

- Идентификаторы клиента — новый регистр сведений `ИдентификаторыРабочихМест` (измерение `ИдентификаторКлиента`,
  ресурс `РабочееМесто`), а не табличная часть: ключ регистра даёт уникальность идентификатора между всеми рабочими
  местами, запись — под управляемой блокировкой по идентификатору (две кассы одновременно не привяжут один id к разным
  местам). Обработчик обновления переносит `Код` существующих мест в регистр (идемпотентно, повтор безопасен) только
  для однозначных кодов: если один `Код` у нескольких неудалённых мест (дубли у клиентов), он в регистр не пишется.
  Поиск: запись регистра — решение (миграция однозначного кода, выбор пользователя, объединение), она главнее `Код` и
  определяет место без диалога, если место не помечено на удаление и не объединено (объединённое — переход на
  «объединено в»; помеченное — запись пропускается, дальше как при её отсутствии; сами записи при пометке не
  удаляются — это история, снятие пометки их возвращает). Запись, указывающая на помеченное место, при привязке
  считается свободной: идентификатор перепривязывается к выбранному месту (запись перезаписывается). Проверка
  «место не помечено и не объединено» в протоколе блокировок касается места-приёмника; источник переноса
  идентификатора или оборудования может быть помечен — именно так с него уводят идентификаторы и устройства. Нет записи — `Код`: одно неудалённое и не объединённое место — оно (и идентификатор
  пишется в регистр), несколько — форма выбора среди совпавших (сейчас берётся первое из массива). Выбор пользователя
  и объединение пишут идентификатор в регистр, поэтому конфликт старых одинаковых кодов больше не всплывает.
  Ошибочный выбор исправляет администратор: в форме рабочего места список его идентификаторов с командой «Перенести
  на другое рабочее место» (по протоколу блокировок ниже); автоматическая привязка занятый идентификатор не
  перезаписывает. MAC в этой фазе не используем.
- Имя компьютера только подсказывает, но не привязывает: на RDP-сервере у всех сеансов одно `ИмяКомпьютера()`, и
  совпадение имени не доказывает, что это то же рабочее место. При неизвестном идентификаторе — форма выбора:
  сначала места с тем же именем компьютера (с числом и списком устройств), затем остальные; «Это рабочее место»
  (привязать идентификатор), «Создать новое». Молча новое не создаётся никогда.
- На старте сеанса — только тихий поиск: если идентификатор известен, параметр сеанса ставится сразу; диалога на
  старте нет, чтобы не навязывать выбор сеансам без оборудования (бухгалтер, менеджер). Форма выбора открывается
  асинхронно (через `ОписаниеОповещения`) только из мест, где пользователь явно работает с оборудованием: РМК, мастер
  и формы оборудования и рабочих мест. Признак — новый необязательный параметр
  `ОперацииСПодключаемымОборудованиемКлиент.ПодключитьОборудование(…, РазрешитьВыборРабочегоМеста = Ложь)`: РМК
  передаёт Истина, остальные вызовы не меняются. Обычные формы, которые подключают сканер в `ПриОткрытии`
  (налоговая накладная, список номенклатуры и другие — у них свой `ScanData`), модального выбора не открывают: запрос
  встаёт в ту же очередь отложенных подключений, а пользователь получает одно немодальное оповещение «Сканер не
  подключён: рабочее место не определено» с переходом к выбору (и команда «Выбрать рабочее место» в разделе
  «Настройка» — из любой формы). После выбора очередь подключает драйверный сканер во всех ещё открытых формах, и
  `ScanData` приходит без переоткрытия форм. Синхронные потребители
  (`НачатьПодключениеОборудования` и прочие, `МенеджерОборудованияКлиент:356-666`, `ПредложитьВыбратьСмену`) больше
  ничего не создают: читают параметр сеанса. Если место не определено (выбор ещё открыт или пользователь его закрыл),
  `ОперацииСПодключаемымОборудованиемКлиент.ПодключитьОборудование` — через него подключают сканер РМК и около 20 форм —
  запоминает запрос формы и открывает выбор с оповещением о закрытии; после выбора подключение выполняется для всех
  отложенных запросов ещё открытых форм, без переоткрытия формы. Закрыли без выбора — сообщение «оборудование не
  подключено: выберите рабочее место» и команда «Выбрать рабочее место» в РМК. Ветку автосоздания
  `ОбновитьРабочееМестоКлиента` удалить. Стартовая переустановка драйверов (`ПереустановитьПомеченныеДрайверы`,
  `МенеджерОборудованияКлиент:1587-1630`, сейчас сама ищет место и берёт первое) переносится в продолжение после
  определения рабочего места и берёт его из параметра сеанса. Установка переводится на асинхронный вызов с оповещением
  (`УстановитьВнешнююКомпонентуАсинх`): очередь отложенных подключений разбирается только после её завершения, а
  признаки «требуется установка/переустановка» сбрасываются только при успехе (сейчас — сразу и независимо от
  результата, `МенеджерОборудованияКлиент:1600-1624`).
- Смена рабочего места в открытом сеансе (форма выбора, мастер, `УстановитьРабочееМесто`): менеджер оборудования
  отключает все устройства прежнего места во всех открытых формах сеанса и ставит их запросы в очередь отложенных
  подключений. Для этого менеджер ведёт реестр запросов форм (идентификатор формы, типы оборудования, обработчик) —
  отдельно от реестра подключений, где форма появляется только при найденном устройстве: запрос формы, для которой
  на прежнем месте устройств не было, тоже сохраняется и может подключиться на новом; после смены параметра сеанса
  очередь подключает оборудование нового места — РМК и формы со сканером переоткрывать не нужно.
- Форма рабочего места: список его оборудования и команда «Перенести оборудование с другого рабочего места».
- Дубли, уже накопленные в базах клиентов: обработчик обновления ничего не сливает сам (данные клиента); в списке рабочих
  мест — команда «Объединить с…» (перенос оборудования и идентификаторов, пометка удаления дубля, ссылка «объединено в»
  у дубля). Целостность: объединение и перенос — одна транзакция на сервере с исключительными управляемыми
  блокировками обоих рабочих мест, их записей регистра идентификаторов и переносимого оборудования; блокировки
  берутся в порядке uuid рабочих мест (встречные объединения A→B и B→A не взаимоблокируются: второе ждёт и после
  первого видит, что источник уже объединён, — отказ с текстом). Объединять в место, которое само объединено, нельзя.
- Протокол блокировок, общий для всех операций с рабочими местами (привязка идентификатора, перенос оборудования,
  объединение): в одной транзакции сначала исключительные блокировки затронутых рабочих мест (по одному — привязка;
  по два — перенос и объединение) в порядке uuid, затем записи регистра идентификаторов этих мест и привязываемый
  идентификатор; под блокировкой проверяется, что ни одно место не объединено и не помечено на удаление. Так
  привязка нового идентификатора к источнику, который в этот момент объединяется, либо успевает до объединения
  (и переносится им), либо после — и получает отказ. Обычная запись оборудования входит в протокол:
  `ПодключаемоеОборудование.ПередЗаписью` блокирует рабочее место объекта, а если реквизит `РабочееМесто` изменён
  (перенос из формы элемента), — и прежнее место из базы, оба в порядке uuid; отказ, если любое из них объединено или
  помечено на удаление.
- Одно физическое устройство на двух местах-дублях: при объединении форма показывает оборудование обоих мест,
  совпадающие записи (тип, драйвер, порт или идентификатор устройства) подсвечены; администратор отмечает, какие
  оставить, лишние помечаются на удаление в той же транзакции. По умолчанию из пары совпадающих остаётся запись
  места-приёмника.
- Действующие сеансы: рабочее место и подключённые устройства кэшируются в клиентском сеансе, и чужой сеанс
  переподключить с сервера нельзя. Поэтому объединение и перенос — операции администратора «при закрытой 1С на этих
  кассах»: команда предупреждает об этом явно; изменение подхватывается при следующем запуске клиента на кассе.
  Это осознанное ограничение (как и в БПО), не дефект.
- Автономная база на кассе: рабочие места и оборудование в ней свои, механизм тот же.
- Размер M. Существенное (новый регистр, обработчик обновления, поведение старта сеанса) → детальный план фазы,
  ревью плана и кода, `ai-database` обязательны.

### Фаза 2 — ядро «БПО-лайт» вместо старой подсистемы

- Перенести из УНФ: справочники `ДрайверыОборудования`, `ПодключаемоеОборудование` (формы списка, элемента, настройки,
  выбора рабочего места), перечисления `ТипыПодключаемогоОборудования` (урезанное: СканерШтрихкода, СчитывательДанных
  при необходимости, ПринтерЧеков, ПринтерЭтикеток, ЭлектронныеВесы, ДисплейПокупателя; RFID — позже),
  `СпособПодключенияДрайвера`; ядро `МенеджерОборудования*`, `ПодключаемоеОборудованиеДрайверКлиент` (без фискальных
  и прочих веток), `ВнешниеКомпонентыБПО*`, необходимое из `ОбщегоНазначенияБПО*` — на наших `ОбщегоНазначения`.
- Справочники сохраняют свои uuid (данные клиентов). Ничего, что хранит данные клиентов, в этой волне не удаляется:
  обработчик обновления работает уже после реструктуризации (`ManagedApplicationModule.bsl:41`), а CFU собирается из
  всех прежних CF (`scripts/dist-build.sh`), так что проверка версии в обработчике удаление данных не остановит.
  - Старые реквизиты, которые надо перенести, переименовываются в `Удалить…` и остаются в метаданных; перечисления
    `ОбработчикиДрайверовПодключаемогоОборудования` и `ТипыПодключаемогоОборудования` остаются со всеми значениями
    (у второго ненужные значения — ККТ, ФискальныйРегистратор, ЭквайринговыйТерминал и др. — скрываются из выбора
    отбором в формах и мастере, а не удаляются: они записаны в реквизитах `ПодключаемоеОборудование` и
    `ДрайверыОборудования`).
  - Обработчик обновления переносит значения в новые реквизиты идемпотентно, с отчётом в журнал по элементам, которые
    не удалось сопоставить (такое оборудование остаётся, но помечается «требует настройки»).
  - Удаление `Удалить…`-объектов и лишних значений перечислений — отдельное решение позже, со своим планом: после
    подтверждения, что базы всех клиентов прошли релиз с переносом, и со сборкой CFU только из этих версий.
- Удалить код и макеты: фискальные ветки модулей, маркировку, офлайн-оборудование, эквайринг, ссылки на отсутствующие
  объекты (`ШаблоныМагнитныхКарт`, `РедакторЭтикетокФормаРедактированияМакета`) и ~55 МБ макетов эквайринга.
  Объекты с данными фискального контура (`ОчередьЧековККТ`, `ФискальныеОперации`, `НумерацияЧековККТ`, кассовые смены
  ККТ) — по тому же правилу, что выше: сначала сверить читателей и наличие данных у клиентов, удаление — отдельным
  решением.
- Разрядность: Native из макета или из ИБ — по манифесту. COM (`ЛокальноПоИдентификатору`) оставить для сторонних
  драйверов, но при ошибке создания объекта писать причину с разрядностью клиента (`СистемнаяИнформация.ТипПлатформы`)
  и подсказкой.
- Контракты, которые должны остаться: `ОперацииСПодключаемымОборудованиемКлиент.ПодключитьОборудование` и события
  `ScanData`/`ScanDataBase64` (около 20 форм), сеансовый параметр `РабочееМестоКлиента`, печать чека табличным документом
  на `НастройкиПользователей.ПринтерЧеков`, `ВывестиСтикерыНаПринтер`, константы `ВыводитьЧекНаЭкрнПередПечатью`,
  `ПечататьЦенуНаЭтикетке`.
- Размер L. Реструктуризация, обработчики обновления, права ролей (Казначей, ЛичныйКабинет, PDV и др.) — все гейты.

### Фаза 3 — устройства

- Сканер — `ОборудованиеУстройстваВвода*` (драйвер 1С Native; клавиатурный режим сканера работает и без драйвера).
- Принтер чеков ESC/POS — свой модуль из ~300 строк печати текста `ОборудованиеЧекопечатающиеУстройства*` и открытия
  денежного ящика; РМК печатает чек на принтер чеков, если он подключён к рабочему месту, иначе — как сейчас, табличным
  документом на Windows-принтер. Чек на ленте — текстовый макет из фирменной формы «Ticket» (branded-print).
- Принтер этикеток — `ОборудованиеПринтерыЭтикеток*` для сторонних Native-драйверов; путь через Windows-принтер
  (`ВывестиСтикерыНаПринтер`) остаётся основным.
- Весы — `ОборудованиеВесовоеОборудование*`: кнопка «Взвесить» в РМК для весового товара. Весы с печатью этикеток — позже.
- Дисплей покупателя — `ОборудованиеДисплеиПокупателя*`: позиция и итог из РМК.
- Денежный ящик — через принтер чеков (команда ESC/POS), отдельного драйвера нет.
- Размер L, по устройству — отдельная сборка.

### Фаза 4 — мастер «Подключить оборудование» (своего в БПО нет)

Для клиента, один экран на шаг:
1. «Это рабочее место» — определено по фазе 1, видно имя компьютера; можно выбрать существующее.
2. Что подключаем — плитки типов (Сканер, Принтер чеков, Принтер этикеток, Весы, Дисплей).
3. Драйвер — рекомендованный по умолчанию; установка компоненты из макета без вопросов.
4. Параметры — встроенная `ФормаНастройки` (порт, скорость, модель), «Автонастройка» где драйвер умеет. Элемент
   `ПодключаемоеОборудование` записывается перед этим шагом, сразу после выбора драйвера (как кнопка «Параметры
   подключения» формы элемента в УНФ): `ПередЗаписью` нового элемента обнуляет `Параметры`
   (`ObjectModule.bsl:7-15`), поэтому параметры пишутся только в уже записанный элемент.
5. Проверка — «Тест устройства» (печать тестовой строки, открыть ящик, считать штрихкод, взвесить).
6. Готово — «Скопировать на другие рабочие места». Отмена мастера после шага 3 удаляет записанный им черновик
   оборудования. Признак — реквизит `ЧерновикМастера` (Булево), он переживает аварийное закрытие: черновики не
   подключаются и видны в списке оборудования; мастер при старте на этом рабочем месте предлагает продолжить или
   удалить найденные черновики.

Плюс «Скопировать настройки оборудования» с рабочего места на рабочее место (новая касса той же модели). Права —
отдельная роль «Настройка оборудования» для клиентского админа. Размер M.

### Фаза 5 — RFID

## Вес поставки

Макеты драйверов 1С Native: 14 + 30 + 12 + 23 МБ в выгрузке. Минус ~55 МБ эквайринга. Чтобы CF не росла,
два варианта — решает владелец:
- **(а) в CF** только сканер (14 МБ, уже есть как `Драйвер1СУстройстваВводаNative`), остальные драйверы — загрузкой в ИБ
  из файла или из хаба tinycio по кнопке мастера (`СпособПодключения = ИзИнформационнойБазы`). CF легче нынешней.
- **(б) всё в CF** — CF около нынешнего размера, но мастер работает без интернета.

## Открытые вопросы владельцу

1. Вариант поставки драйверов: (а) или (б).
2. Автономная база на кассе: как она обменивается с центральной (РИБ, свой обмен, без обмена)? Где ведётся справочник
   рабочих мест и оборудования — только в кассовой базе или ещё и в центральной.
3. Модели оборудования у клиентов (принтеры чеков, этикеток, весы, дисплей) — для проверки драйверами 1С и для
   рекомендуемых драйверов в мастере.
4. Лицензия: драйверы 1С из БПО распространяются с конфигурациями на платформе 1С — уточнить условия для тиражной
   конфигурации (до фазы 2).
5. Кто включает мастер клиенту — отдельная роль или право администратора.

## Проверка

- Фаза 1, автоматически (уровень 3, серверная часть): определение рабочего места вынесено в серверную функцию
  «идентификатор + имя компьютера → найдено / кандидаты для выбора»; сценарии `ТестыДокументов`: известный
  идентификатор, новый идентификатор при одном месте с тем же именем (кандидат, не привязка), при нескольких,
  неоднозначный `Код`; привязка идентификатора, уже занятого другим местом, — отказ; объединение переносит
  оборудование и идентификаторы, повторное и встречное объединение — отказ.
- Фаза 1, руками (уровень 4 у нас нет: смок ограничен `ПриСозданииНаСервере`, старт приложения в автотестах
  пропускается): чек-лист в `docs/TESTING.md` и строки в `TESTS.xlsx` — новый профиль 1С на кассе → форма выбора, а не
  новое место; РМК открыт до выбора → после выбора сканер подключён без переоткрытия; две формы со сканером ждут выбора
  → обе подключены; выбор закрыт → сообщение и команда в РМК; RDP с двумя сеансами одного сервера.
- Фаза 1, данные: обработчик переноса `Код` в регистр — повторный запуск ничего не меняет; два места с одинаковым
  `Код` (дубли, которые уже есть у клиентов) — второй идентификатор не перезаписывает первый, конфликт в журнал.
- Фаза 2, миграция: фикстура базы со старой структурой (оборудование с параметрами для сканера 1С, универсального
  драйвера, COM-драйвера, фискального устройства) → обновление CFU до релиза N → проверка: каждое старое оборудование
  либо сопоставлено с новым драйвером с сохранёнными параметрами, либо помечено «требует настройки»; повторный запуск
  обработчика идемпотентен; обновление со сборки до N сразу на сборку после N (накопительный CFU) переносит те же
  данные — `Удалить…`-объекты в этой волне не удаляются.
- Фазы 2–4: смок форм оборудования (сейчас пропускаются); ранее настроенный сканер после обновления сканирует без
  перенастройки (ручная приёмка на копии базы клиента); ручная приёмка на живом оборудовании владельца — сканер,
  принтер чеков, весы, дисплей; 32- и 64-битный клиент 1С на одной кассе.
