# Волна 1 редакции 2.0.17: склад как торговая точка — вид цены, контроль минимальной цены (`retail-store-price`)

Дата: 2026-11-09. Мастер-план — `docs/plans/retail-chain.md`, раздел «Волна 1» (требования оттуда — вход этого
плана). Часы — FlyCDI, «Внедрение maERP». Имя клиента в `src/cf` не появляется. Сборка — 2.0.17.1.

## Разбиение волны на сборки (решение после 25 кругов ревью, 2026-11-09)

Круги 8-25 `ai-review-plan` показали: касса сейчас неверно ведёт суммы (скидка чека не доходит до реализации,
повторное вычитание скидки, единицы количества отложенного чека, возврат без скидки), и контроль цены на кассе
без исправления сумм не замыкается — любая схема проверки кассы упирается в эти ошибки. Поэтому:

- **1.1 (этот план, 2.0.17.1)** — вид цены склада во всех местах, включая пути добавления товара в кассу;
  контроль минимальной цены при проведении документов **вне кассы**; города, флажок «не показывать кассиру»,
  комментарий с кассы. Реализация, записываемая кассой (`ДополнительныеСвойства.ЭтоИнтерфейсПродавца`),
  в 1.1 контролем **явно не проверяется** — иначе отказ пришёл бы после оплаты; в форме склада при включённом
  контроле — пояснение «на кассе контроль включится в следующей сборке».
- **1.2** — суммы кассы: скидка чека, отложенные чеки, возвраты (свой план и ревью; разбор ошибок — раздел
  «Сборки 1.2 и 1.3» ниже и TECHDEBT).
- **1.3** — контроль цены на кассе (предварительная проверка до оплаты, порог в строке кассы, проверка при
  проведении реализации из кассы) поверх исправленных сумм 1.2.

## Что делаем

1. Вид цены продажи у склада: `МестаХранения.ВидЦеныПродажи`. Пустой — прежнее поведение везде.
2. Контроль минимальной цены — настройка склада: не контролировать / не ниже вида цен / не ниже себестоимости.
   Серверная проверка при проведении реализации вне кассы (касса — сборка 1.3). Обход — роль-допуск.
3. Мелочи розницы: справочник `Города` и `Контрагенты.Город`, флажок контрагента «не показывать кассиру»,
   комментарий к продаже с кассы.

Перенесено в волну 5 (`retail-tools`), чтобы волна 1 осталась про цену: «оплата долга в кассе — только
неоплаченные» (`ТолькоНеоплаченные`) — механизм оплаты долга в кассе в разведке не разобран.

## 1. Вид цены продажи у склада

**Метаданные.** `МестаХранения.ВидЦеныПродажи` — `CatalogRef.ВидыЦен`, **uuid клиента
`af5c86da-24d1-4335-bd32-10944aaa2c2c`** (у клиента — `ВидЦены`, заполнен у всех складов; данные заходят без
конвертации). Синоним ru/fr/en/es «Вид цены продажи / Type de prix de vente / Sales price type / Tipo de precio de
venta». Подсказка: «Пусто — цены как сейчас: вид цены покупателя или «Розничная»».

**Ограничение вида цены склада.** Касса считает строки с `ЦенаВключаетНДС = Истина` в основной валюте, а подбор
кассы — динамический список, где построчный пересчёт валюты, НДС и динамического расчёта невозможен. Поэтому
`ВидЦеныПродажи` склада — только вид цен **в основной валюте (или с пустой валютой), с `ЦенаВключаетНДС = Истина`
и без `ДинамическийРасчет`**, как предопределённая «Розничная». Ограничение держится с двух сторон:
- `МестаХранения.ПередЗаписью` (ObjectModule) — отказ с объяснением при любой записи, в том числе программной
  (`ОбработкаПроверкиЗаполнения` при программном `Записать()` не вызывается); в форме склада — `ПараметрыВыбора`
  по этим реквизитам вида цен;
- `ВидыЦен.ПередЗаписью` (ObjectModule) — если вид указан у какого-либо склада как `ВидЦеныПродажи` (запрос по
  `МестаХранения`), смена валюты на неосновную, снятие `ЦенаВключаетНДС` или включение `ДинамическийРасчет` —
  отказ с перечнем складов. Обе проверки пропускаются при `ОбменДанными.Загрузка`.
- **Проверка при чтении** — главная гарантия: значения могут прийти минуя `ПередЗаписью` (загрузка данных,
  обновление конфигурации по uuid, старые данные клиента). `Справочники.МестаХранения.ВидЦеныПродажи(Склад)`
  возвращает вид, только если он удовлетворяет ограничению; иначе — пустую ссылку (касса и формы работают по
  прежнему правилу) и пишет предупреждение в журнал регистрации (событие «Цены.ВидЦеныСклада»). Нарушающий
  `ВидЦеныМинимальный` контролируемого склада — наоборот, **отказ** проведения и предварительной проверки с текстом
  «настройка контроля минимальной цены склада некорректна» (контроль не отключается молча).

**Пустой вид цены склада — касса не меняется ни в одном пути.** Сейчас пути кассы выбирают цену по-разному:
штрихкод — «Розничная», подбор и избранное — `РозничныйКлиент.ТипЦены`, иначе «Розничная». При пустом
`ВидЦеныПродажи` склада каждый путь остаётся ровно таким, код не трогается (ветвление по заполненности вида
склада).

**Заданный вид цены склада — одна функция и одно правило для строки и для сеток.**
`Справочники.МестаХранения.ЦеныПродажиСклада(Склад, Номенклатура, Дата) Экспорт` (вызывается только при
заполненном виде склада) → таблица `Номенклатура, Характеристика, Цена` за единицу хранения: цена вида склада, нет
её — «Розничная», но только если «Розничная» сама удовлетворяет ограничению выше (проверка при чтении, как для
вида склада); иначе отката нет и цена 0 — касса не даст продать товар без цены (существующая проверка
`Payer`/`Valider`), в журнал — предупреждение. Срез `ЦеныНоменклатуры` не уникален по номенклатуре + характеристике (измерение
`ТоварнаяГруппа`), поэтому правило выбора — как в действующей `ИзбраннаяНоменклатураРМК.ИзбранноеПользователя`
(ManagerModule:126-161): последний период по паре номенклатура + характеристика, при нескольких записях этого
периода — максимум цены; цена до свёртки делится на коэффициент `Упаковка` записи (нет упаковки — 1). Для
динамического списка подбора (`FormProduitsOnStock`) — тот же отбор вложенными запросами без временных таблиц.
Текст — функция `ТекстЗапросаЦенПродажиСклада(ДляДинамическогоСписка)` модуля менеджера; его используют запрос
штрихкода (`StructureProductByBarCode`), подбор и `ИзбранноеПользователя`. Цена строки = цена, которую кассир видел
в сетке/получил по штрихкоду. **Единица цены строки кассы.** У строки кассы есть `Упаковка`, `Количество` — в упаковках (сканер ставит
`Количество = 1` упаковки), `CreateFacture` переносит его в `КоличествоУпаковок` реализации, `РассчитатьСтроку`
умножает на коэффициент. Значит `Цена` строки кассы — цена **упаковки строки**: цена единицы хранения из
`ЦеныПродажиСклада` умножается на коэффициент `Упаковка` строки (пустая — 1). Сетки показывают цену единицы
хранения. Тест: сканирование штрихкода упаковки с коэффициентом 6 — цена строки = 6 × цена единицы, сумма
реализации = сумма строки кассы. Путей добавления товара в кассе четыре, все получают цену из этой функции при
заполненном виде склада: ввод штрихкода (`AfterInputBarcode` → `StructureProductByBarCode`), (сейчас `StructureProductByBarCode` читает `Упаковка` штрихкода в первую временную таблицу, но не переносит её
в выборку и в возвращаемую структуру — упаковка теряется; после правки структура несёт `Упаковка`, строка кассы
получает её, цена = цена единицы × коэффициент), **аппаратный сканер**
(`ОбработкаОповещения`, событие `ScanData` → `РаботаСДокументамиКлиентСервер.ДобавитьНоменклатуруПоШтрихкоду`;
упаковку штрихкода этот путь сейчас теряет дважды: `ОбщегоНазначенияВызовСервера.ПолучитьНоменклатуруПоШтрихкоду`
(Module.bsl:674) её не возвращает, а `ПолучитьДанныеНоменклатуры` (Module.bsl:236, 268-269) ставит строке основную
единицу. Это нынешнее поведение сканера, в 1.1 оно не меняется (штрихкод упаковки сканером добавляет основную
единицу — запись в TECHDEBT, исправление — сборка 1.2 вместе с суммами кассы); цена ставится за **ту упаковку,
что оказалась в строке** (основную единицу), так что цена и количество строки согласованы — после
добавления или увеличения строки цена новой строки ставится серверным вызовом `ЦеныПродажиСклада`, затем
пересчёт строки тем же путём, что при правке строки сейчас (`РассчитатьСтроку(Стр, Истина, "Цена")` и
`CalculateSumTotal`, `Form/Module.bsl:745-752`) — суммы пересчитываются от новой цены), подбор
(`FormProduitsOnStock`) и избранное. Подбор сейчас теряет характеристику: `VTSelection`/`Choisir` возвращают
структуру без `Характеристика`, `AfterChoiceProduit` ищет строку только по `Номенклатура`. Исправляю контракт:
результат выбора несёт `Характеристика` (а `Серия` — только если сетка её показывает), **ключ объединения строки кассы** во всех путях — номенклатура + характеристика + серия + **упаковка** (количество
строки — в её упаковках, складывать количество разных упаковок нельзя): подбор (`AfterChoiceProduit`), избранное
(`ПослеВыбораИзбранного` — сейчас ищет только номенклатуру и характеристику), ввод штрихкода и аппаратный сканер
(`ДобавитьНоменклатуруПоШтрихкоду` — проверяю его ключ, при расхождении добавляю упаковку в отбор строк). `CreateFacture` пишет в `NewStr.ВидЦены` вид склада (цену не пересчитывает). Тест:
цена в сетке = цена строки для вида с упаковкой, для товара без цены вида (откат на «Розничную») и для двух записей
одного периода с разными товарными группами. `ПолучитьЦенуНоменклатуры` в кассе не используется: у неё другой
откат и динамический расчёт.

**Функция.** `Справочники.МестаХранения.ВидЦеныПродажи(Склад) Экспорт` (ManagerModule, сервер): реквизит склада или
пустая ссылка. Для клиента — обёртка в `ОбщегоНазначенияВызовСервера.ВидЦеныПродажиСклада(Склад)`.
Повторное использование — не нужно (одно чтение ссылки, вызов по смене склада).

## 2. Контроль минимальной цены

**Метаданные.**
- Перечисление `РежимыКонтроляМинимальнойЦены`: `НеКонтролировать` (первое = умолчание платформы),
  `НеНижеВидаЦен`, `НеНижеСебестоимости`; синонимы на 4 языках.
- `МестаХранения.КонтрольМинимальнойЦены` (`EnumRef.РежимыКонтроляМинимальнойЦены`), новый uuid.
- `МестаХранения.ВидЦеныМинимальный` (`CatalogRef.ВидыЦен`), новый uuid; доступен при `НеНижеВидаЦен`;
  пусто → предопределённый `ВидыЦен.МинимальнаяЦенаПродажи`.
- Роль `ПродажаНижеМинимальнойЦены` — допуск без прав на объекты (образец — `Roles/СкладскиеОрдера`,
  комментарий в mdo). В `Rights.rights` ролей не добавляется ничего.
- Обработчик обновления не нужен: у существующих складов реквизит — **пустая ссылка** перечисления (первое
  значение не подставляется в уже записанные элементы), и весь код трактует пустое значение как `НеКонтролировать`
  (одна функция `Справочники.МестаХранения.РежимКонтроляМинимальнойЦены(Склад)`, возвращает `НеКонтролировать` для
  пустого; прямых сравнений реквизита в коде нет). Новый склад получает `НеКонтролировать` в `ОбработкаЗаполнения`.

**Общий модуль `КонтрольМинимальнойЦены`** (сервер, не глобальный, без вызова сервера; для клиента — экспорт в
`ОбщегоНазначенияВызовСервера`). Экспортные функции:
- `Нарушения(ДокументОбъект, Режим) Экспорт` → таблица нарушений (`НомерСтроки, Номенклатура, Характеристика, Цена,
  Порог, Основание`) и список предупреждений. Вход — объект `РеализацияТоваровУслуг` (записанный при проведении или
  незаписанный, собранный кассой для предварительной проверки): склад, дата, курс и строки `ТЧТовары` (`КодСтроки`,
  `Ордер`, `КлючСтрокиОрдера`, суммы) берутся из него — ключи ордерной проверки в контракте есть. `Режим` —
  «Проведение» / «Предварительная». Пустая таблица, если режим склада `НеКонтролировать` (или пустой).
- `ПроверитьДокумент(ДокументОбъект, Отказ) Экспорт` — вызов из `ОбработкаПроведения` реализации.
- `ДопускПродажиНижеМинимальной() Экспорт` — `Истина`, если у текущего пользователя ИБ есть роль-допуск или
  `Администратор`. Проверяю через `ПользователиИнформационнойБазы.ТекущийПользователь().Роли.Содержит(...)`, а
  не `РольДоступна`: проверка идёт внутри проведения, где включён привилегированный режим
  (`РеализацияТоваровУслуг/ObjectModule.bsl:73`), и поведение `РольДоступна` там надо подтвердить на базе — на
  копии базы проверяю оба способа и оставляю тот, что верно различает кассира с ролью и без (тест п. 5).
  Пользователь ИБ без ролей (пустой список пользователей) — допуск есть.

**Цена строки.** Цена единицы хранения после всех скидок по суммам, которые формирует
`РаботаСДокументамиКлиентСервер.РассчитатьСтроку` (Module.bsl:30-108: `Сумма`, `СуммаСкидки`, `СуммаНДС`, `СуммаСНДС`):
с НДС — `СуммаСНДС / Количество`, без НДС — `(СуммаСНДС − СуммаНДС) / Количество` (отдельного реквизита суммы без
НДС у строки нет, `СуммаБезНДС` — реквизит шапки) (`Количество` строки — в
единицах хранения, `КоличествоУпаковок` не используется), в валюте регламентированного учёта по курсу документа
(`РаботаСВалютамиКлиентСервер.СуммаРегл`). Сравнение с порогом того же базиса НДС: вид цен с
`ЦенаВключаетНДС` сравнивается с ценой строки с НДС, без — с ценой строки без НДС; себестоимость —
всегда без НДС. Сравнение — **суммой строки**, а не ценой единицы: нарушение, если сумма строки (с НДС или без, по
базису порога) меньше `Окр(Порог × Количество, 2) − 0,01`; допуск — одна копейка на строку независимо от количества.

**Порог «не ниже вида цен».** Строго цена минимального вида, без откатов: срез `ЦеныНоменклатуры` по виду,
номенклатуре и характеристике на дату документа (нет цены по характеристике — по пустой характеристике), с тем же
устранением неоднозначности по `ТоварнаяГруппа`, что в §1 (последний период пары, при нескольких записях периода —
максимум цены единицы хранения; общий текст запроса `ТекстЗапросаЦенВида` модуля менеджера `МестаХранения`;
`ПоследнийПрайс` не используется — он не убирает дубли товарных групп); `ПолучитьЦенуНоменклатуры` не используется — при отсутствии цены она откатывается на «Розничную» и
меняет `ВидЦены` строки. Цена приводится к единице хранения (коэффициент `Упаковка` среза), из валюты вида — в
регламентированную по курсу на дату (`РаботаСВалютами`), базис НДС — по `ЦенаВключаетНДС` вида (сравнение с ценой строки с НДС или без НДС). `ВидЦеныМинимальный` с `ДинамическийРасчет` не допускается:
отказ в `МестаХранения.ПередЗаписью`, отбор выбора в форме, та же охрана в `ВидыЦен.ПередЗаписью`.
Нет цены вида — строка не проверяется, предупреждение.

**Порог «не ниже себестоимости».** Максимальная себестоимость единицы среди партий остатка склада по номенклатуре +
характеристике (как у клиента — `ПолучитьМаксимальнуюЦенуПоОстаткам`), остатки `ТоварыВНаличии` на
`Новый Граница(МоментВремени документа, ВидГраницы.Исключая)` с отбором по складу; группировка по полному ключу
партии (`Серия, Партия, ДатаПартии, УУ`), себестоимость единицы партии = (`Сумма − СуммаНДС` остатка
`ТоварыВНаличии` + **дополнительные расходы партии** — остаток `ДополнительныеРасходы` по ключу склад, номенклатура,
характеристика, серия, партия, сумма по `СтатьяДДС`, без НДС) / `Количество` при `Количество > 0` — как в действующей
`ТоварыВНаличии.ПолучитьСреднююЦенуПоОстаткам` (ManagerModule:1807-1860, читает оба регистра) и в
`СебестоимостьПродаж.СформироватьПоРеализации` (переносит расходы обоих регистров). У `ДополнительныеРасходы` нет
`ДатаПартии` и `УУ`: если в остатке несколько ключей `ТоварыВНаличии` с одной партией, расходы партии делятся между
ними пропорционально количеству (сверено по коду: оприходование пишет в ресурс `Сумма` сумму с НДС —
  `ManagerModule:12-14`, НДС отдельно в `СуммаНДС` — `ДобавитьПриход`, 1277-1289; тест п. 3 подтверждает на базе).
- Граница «исключая момент документа» делает проверку одинаковой при первом проведении и при перепроведении:
  собственные движения документа не попадают ни в каком случае. Касса (документ «сейчас») и предварительная
  проверка (на `ТекущаяДатаСеанса`) видят один и тот же остаток.
- Максимум, а не FIFO-партия списания: предварительная проверка в кассе идёт до проведения и списания не знает.
  Гарантии «прошло предварительную — пройдёт проведение» **нет**: между `Payer` и `CreateFacture` нет общей
  транзакции, остаток может измениться (параллельная продажа, приход дорогой партии). Окно — время оплаты. Если
  проведение откажет после оплаты, касса идёт штатной веткой отказа проведения (`AfterPaymentAtServer` → 
  `ОшибкаПроведенияДокумента`: денежные документы не создаются, чек не печатается) — как сейчас при любом отказе
  проведения продажи (например, ошибке списания). Отдельно в отчёте волны: проверяю, проводится ли операция
  эквайринга до `AfterPayment` (`ФормаСложнойОплаты`); если да — это существующий риск всех отказов проведения
  кассы, фиксирую в TECHDEBT, а не чиню в этой волне.
- **Ордерный склад** (`МестаХранения.ОрдерныйСклад(Склад, Дата)`): партии списывает расходный ордер, реализация
  только оформляет его (`ТоварыВНаличии/ManagerModule.bsl:48-52`). Связь строки реализации с ордером берётся из двух мест, потому что в точке проверки движения документа ещё не
  записаны (`СформироватьДвиженияОформления` только заполняет набор в памяти, `Движения.Записать()` — позже):
  (а) **набор в памяти** `ДокументОбъект.Движения.ТоварыКОформлению`, сформированный `ОрдераСклада.
  СформироватьДвиженияОформления` (ObjectModule:96) до проверки, — пары схемы «ордер первым» этой версии документа
  (ордер и код строки ордера по `КодСтроки` реализации); (б) **из базы** `РегистрыНакопления.ТоварыКОформлению.
  ПарыОформления([Ссылка])` — только пары, где регистратор — расходный ордер, а реализация — `ДокументИсточник`
  (схема «документ первый», поздний ордер; собственные записи реализации из базы — прежняя версия, их не беру).
  В предварительной проверке кассы (новый незаписанный документ, неордерный по умолчанию) пар нет. Строка может быть оформлена ордерами частично: количество, покрытое парами (сумма `Количество` пар
  строки), берёт себестоимость из партий ордеров, **непокрытый остаток строки** (`Количество` строки − покрытое,
  если > 0) — из остатка склада; порог строки — максимум по обоим источникам. Источник по парам — партии расходных
  движений `ТоварыВНаличии` ордера пары (`Регистратор = Ордер`, `КодСтроки = КодСтрокиОрдера`), максимум их
  себестоимости единицы с дополнительными расходами — по тому же правилу, что применяет к этим парам
  `СебестоимостьПродаж.СформироватьПоРеализации` / `ПересчитатьПоПарам` (их расчёт выношу в общую функцию, если он
  не вызывается отдельно, а не дублирую). Строка без пар целиком (документ первый, ордер ещё не пробит; новый документ кассы) — по остатку склада. Поздний ордер реализацию не перепроводит (себестоимость пересчитывает
  `СебестоимостьПродаж.ПересчитатьПоПарам` в своём регистре, ManagerModule:40-56), поэтому повторной проверки и
  отказа задним числом нет.
- Нет партий в остатке (продажа в минус) — строка не проверяется: политика отрицательных остатков.
- Неоценённая партия — по **действующей функции** `ТоварыВНаличии.НеподтвержденныеПартии()` (ManagerModule:1659-1718)
  целиком, **с замыканием** `ЗамыканиеПартий` (выпуск, пересортица, акт разбора, поступление из переработки):
  ордерное происхождение с остатком `ТоварыКОформлению` или с движениями после границы последовательности и все
  производные от них партии. Сокращённого варианта не делаю. Функция читает ордерные партии **всей истории** движений и строит
  замыкание без ограничения датой (граница применяется после обхода) — она не дешёвая. Поэтому вызывается не
  больше одного раза на проверку документа и только при одновременно: режим склада `НеНижеСебестоимости`; в базе
  включены ордерные склады (`МестаХранения.ОрдерныеСкладыВключены()`, ManagerModule:89 — иначе неоценённых партий
  нет по определению); среди партий-кандидатов строк есть партии ордерного или производного происхождения (тип
  документа партии — приходный ордер, выпуск, пересортица, акт разбора, поступление из переработки). Обычная
  розница с закупкой поступлениями на неордерный склад функцию не вызывает. Время вызова замеряю на копии базы с
  ордерными складами (тест п. 3, в отчёте); порог — 0,5 с на документ; выше — оптимизация функции до передачи
  сборки, без отказа от замыкания. Себестоимость неоценённой партии в порог **не берётся** (была бы 0 или неполной): партия не
  участвует в максимуме. Вместо неё — **мягкий** контроль по последней цене закупки единицы хранения
  (`ЦеныНоменклатурыПоставщиков.ПоследнийПрайс` без поставщика, ресурс `ЦенаЕдиницыХранения` — с НДС, в
  регламентированной валюте, `ManagerModule.bsl:16`). Это цена **другой** закупки позиции, ставка НДС в ней не
  сохранена — ни точной оценкой, ни гарантированной границей она не является. Оценка
  `ЦенаЕдиницыХранения / (1 + СтавкаНДС номенклатуры / 100)` сравнивается с ценой строки без НДС и при нарушении
  даёт **предупреждение** «себестоимость партии ещё не оформлена, по последней закупке цена ниже себестоимости»,
  но не отказ; нет последней закупки — предупреждение «себестоимость не определена». Отказ даёт только порог по
  оценённым партиям. Отход от мастер-плана (там — порог по последней закупке) осознанный: блокировать продажу по
  чужой цене нельзя, а молча пропускать — тоже; выбран явный сигнал. Если не участвует ни одна партия — строка не проверяется.
- Услуги (`ТЧУслуги`) и номенклатура с типом «Услуга» не проверяются. Комплекты: строка комплекта проверяется
  только по виду цен; при `НеНижеСебестоимости` — пропуск с предупреждением (себестоимость комплекта из партий
  компонентов в эту волну не считаю, `TECHDEBT`).

**Где проверяется.**
- `РеализацияТоваровУслуг.ОбработкаПроведения` — после `Блокировка.Заблокировать()`, ордерных проверок и
  **автовыпуска** (`Производство.ОбеспечитьАвтовыпуск` проводит выпуск секундой раньше продажи — его партии должны
  попасть в остаток), до `ТоварыВНаличии.СформироватьДвижения` (`ObjectModule.bsl:88-103`): `КонтрольМинимальнойЦены.ПроверитьДокумент(ЭтотОбъект, Отказ)` и **сразу** `Если Отказ Тогда Возврат;` —
  следующая строка `Отказ = Не РегистрыНакопления.ТоварыВНаличии.СформироватьДвижения(ЭтотОбъект)` (ObjectModule:103)
  перезаписала бы результат контроля. В ветке налоговой реализации на основаниях — так же до `ПровестиДокумент`. Пропуск только если:
  `ОбменДанными.Загрузка`; `ДополнительныеСвойства.БезКонтроляМинимальнойЦены = Истина`; есть допуск. Отсутствие
  флага = проверка. Даты исключений нет. Нарушение — `Отказ = Истина` и перечень строк «Строка N: <товар> — цена X
  ниже порога Y (<основание>)»; при `ЭтоИнтерфейсПродавца` тот же текст в `ДополнительныеСвойства.ТекстОшибки`
  (касса показывает его через ветку `ОшибкаПроведенияДокумента`).
- **Налоговая реализация на основаниях** (`ObjectModule.bsl:73-77`: `НалоговыеДокументыНаОснованиях.ПровестиДокумент` и
  `Возврат` до общей ветки) тоже может назначить цену ниже порога — налоговая выручка считается из её сумм.
  Проверка вызывается и в этой ветке (место — ниже, в абзаце о блокировке), с теми же исключениями. **Режим контроля — по складу основания строки, а не шапки**: шапку
  `ЗаполнитьПоОснованиям` берёт из первого основания, а основания могут быть с разных складов
  (`ПроверитьОснования` совпадения складов не требует, Module.bsl:240-262, 1303-1369). Для каждой строки берутся её
  основания (`Основания`), у каждого — режим и минимальный вид его склада (`МестоХранения` основания); строка
  проверяется по каждому контролируемому основанию, порог строки — максимум порогов; ранний выход «склад шапки не
  контролируется» в этой ветке не применяется. **Блокировка**: себестоимость оснований меняет
  `СебестоимостьПродаж.ПересчитатьПоПарам` наборами регистра без записи объектов оснований, под своей
  блокировкой `СебестоимостьПродаж` по `ДокументПродажи` (ManagerModule.bsl:128-143); в налоговой ветке проверка вызывается **внутри**
  `НалоговыеДокументыНаОснованиях.ПровестиДокумент` после её блокировок товаров оснований (Module.bsl:390-411) и до
  формирования движений; **последней** к этим блокировкам добавляется разделяемая блокировка `СебестоимостьПродаж`
  по `ДокументПродажи` = основания строк (тем же способом, что ManagerModule:128-143). Порядок «товары →
  `СебестоимостьПродаж`» совпадает с ордерным путём `ПередЗаписьюОрдера` (`ОрдераСклада:49-69`) — встречного
  захвата нет. Отказ контроля — выход из `ПровестиДокумент` до движений. Порог «не ниже вида цен» — как у обычной реализации, с отказом. Себестоимость к
  строке налогового документа точно не привязать: товар отгрузили основания, а `СебестоимостьПродаж`
  (`НоваяЗаписьСписания`) не хранит код строки реализации, тогда как `ЗаполнитьПоОснованиям` переносит строки
  оснований раздельно — отбор по основанию + номенклатуре + характеристике смешал бы разные строки. Сами основания
  прошли контроль себестоимости при своём проведении. Поэтому при `НеНижеСебестоимости` порог строки — **максимум** себестоимости
  единицы по связанным основаниям (`Основания`), по номенклатуре + характеристике строки: записи
  `СебестоимостьПродаж` основания с количеством (списанные партии) дают себестоимость единицы каждой партии
  (сумма без НДС / количество записи, без усреднения между партиями); записи без количества (дополнительные расходы) `НоваяЗаписьСписания`
  (ManagerModule.bsl:1912-1935) пишет с теми же `Партия`, `Серия`, `НоменклатураПартии`, `СкладОтгрузки`, без
  `ДатаПартии` — они присоединяются **к своей партии** (ключ: основание, номенклатура, характеристика, серия,
  партия) и прибавляются к её сумме; физическая себестоимость считается **по полному ключу** записи с количеством
  (включая `ДатаПартии`, как в обычной ветке): сумма без НДС / количество этого ключа, без усреднения ключей одной
  партии; допрасходы партии (у них нет `ДатаПартии`) делятся на единицу пропорционально количеству ключей этой
  партии (то же правило, что для `ДополнительныеРасходы` в обычной ветке) и прибавляются к себестоимости единицы
  каждого ключа. Только допрасходы с **пустой** партией (собственные допрасходы
  ордерного склада, `ДобавитьСвоиДопрасходыОрдерногоСклада`) распределяются на единицу равномерно по всем партиям
  товара этого основания. Порог = максимум себестоимости единицы по партиям и основаниям; цена ниже — **отказ**,
  обход — допуск. Максимум может завысить порог строки, если у товара в основаниях несколько строк с разной
  себестоимостью, — это осознанная строгость (ложный отказ снимается допуском), но не обход контроля. 
- **Служебные перепроведения** контроль не проходят по двум признакам. (1) Существующий

## 2а. Склад продажи кассы (нужен вид цены уже в 1.1)

Новая переменная формы кассы `СкладПродажи`: при продолжении отложенного чека — `МестоХранения` этого документа
(`ЗаполнитьПоДокументуНаСЕрвере` / ветка существующего `CurFacture` в `CreateFacture` сохраняет склад документа),
иначе — `РозничныйСклад`; сбрасывается в `NewFacture`. Вид цены и цены новых строк (§1) берутся по `СкладПродажи`,
то есть по складу фактического списания и в отложенном чеке. В той же сборке исправляется количество
восстановленного чека: `ЗаполнитьПоДокументуНаСЕрвере` (1072-1078) пишет в `Количество` кассы (упаковки)
`Количество` реализации (единицы хранения), а `CreateFacture` снова трактует его как `КоличествоУпаковок` — после
загрузки `Количество` кассы = `КоличествоУпаковок` строки документа (одна строка; тест: отложенный чек с упаковкой
коэффициента 6 → открыть → сумма и количество единиц реализации не меняются). Восстановление скидки — сборка 1.2. Тест: отложенный чек склада А открыт кассиром
склада Б — новые строки по виду цены склада А.

**Редактор строки кассы в 1.1.** Нынешний редактор (`ФормаРедактированияСтроки:69-77, 307`) берёт минимальную цену
`МинимальнаяЦенаПродажи` из регистра за единицу хранения и сравнивает её с ценой строки, которая после §1 может
быть ценой упаковки (ручной ввод штрихкода упаковки). Поэтому уже в 1.1 `Modifier` передаёт редактору `Упаковка`
строки, а прежняя минимальная цена приводится к упаковке строки с учётом **упаковки записи регистра**: редактор читает
сейчас сырой ресурс `Цена` среза `ЦеныНоменклатуры`, а запись хранит и свою `Упаковка` — цена единицы хранения =
`Цена / коэффициент упаковки записи` (нет упаковки — 1), затем × коэффициент упаковки строки (то же правило, что в
`ЦеныПродажиСклада` §1). Прежний запрет снижения цены работает в тех же единицах, что цена строки. Порог склада в редакторе — сборка 1.3. Тест: минимальная
цена задана за единицу и за упаковку 6 — для строки в единицах и в упаковках 6 порог редактора верен в обоих
случаях (без двойного умножения).

## Сборки 1.2 и 1.3 (касса) — черновик, войдёт в их планы

Ниже — наработки кругов ревью этого плана по кассе; они не реализуются в 1.1 и пройдут ревью в планах 1.2/1.3.

- **Касса — до оплаты.** `CreateFacture` (`Form/Module.bsl:842-890`) делится на две части: серверная функция формы
  `ОбъектРеализацииКассы(Черновик)` — выбирает объект **так же, как сейчас** (продолжение отложенного чека —
  существующий документ `CurFacture` со своим складом, `ЗаполнитьПоДокументуНаСЕрвере`; иначе — новый с
  `РозничныйСклад`), заполняет шапку и строки (цикл 867-876: `ЗаполнитьЗначенияСвойств`, `СтавкаНДС`,
  `ПроцентСкидки`, `РассчитатьСтроку(..., "Цена")`, итоги) и возвращает объект **без записи**; `CreateFacture` вызывает
  её и записывает. Новая `НарушенияМинимальнойЦеныНаСервере()` вызывает ту же функцию и передаёт объект в
  `КонтрольМинимальнойЦены.Нарушения(Объект, "Предварительная")`. Склад, дата, суммы строк — ровно те, что будут
  проведены; суммы формы (`CalculateSumTotal` меняет `СуммаСНДС` и скидку без пересчёта `СуммаНДС`) не участвуют.
  (Склад продажи — §2а, в 1.1.) Прежний текст: новая переменная формы `СкладПродажи`: при продолжении отложенного чека — склад этого
  документа (`ЗаполнитьПоДокументуНаСЕрвере`), иначе — `РозничныйСклад`; сбрасывается в `NewFacture`. Цены новых
  строк, вид цены строки и контроль берутся по `СкладПродажи`, то есть по складу фактического списания и в
  отложенном чеке.
  **Скидка чека кассы — проверка по сумме к оплате; исправление переноса скидки — отдельная волна.** Найденные
  ошибки (`Form/Module.bsl`): `CalculateSumTotal` (752-779) применяет скидку вычитанием из текущей `СуммаСНДС`
  строки — повторные вызовы уменьшают повторно; `CreateFacture` (867-876) пересчитывает строку реализации от цены,
  восстанавливая процент из `СкидкаНаЦену` (= 0), — скидка в реализацию, по-видимому, не попадает; восстановление
  отложенного чека (`ЗаполнитьПоДокументуНаСЕрвере`, 1072-1078) путает единицы количества и не восстанавливает
  процент; возврат с кассы считается от цены без скидки. Исправление затрагивает расчёт итогов, отложенные чеки,
  возвраты и распределение скидок между частичными возвратами — это деньги и отдельный механизм. Разбор кругов
  ревью этого плана (круги 8-24) показал, что внутри волны про цены его не закрыть: **выношу в отдельную волну
  «Касса: скидка чека, возвраты и отложенные чеки»** со своим планом и ревью, запись в TECHDEBT с этим разбором,
  отдельный пункт владельцу.
  Чтобы контроль не обходился скидкой уже в этой волне, **предварительная проверка кассы сравнивает порог с тем,
  что платит покупатель**: цена строки для проверки = `СуммаСНДС` строки кассы (после скидки, именно из неё
  складывается `СуммаКОплате`, которую `Payer` передаёт в оплату) / количество в единицах хранения (`Количество`
  кассы × коэффициент `Упаковка`); без НДС — по ставке номенклатуры строки (`РассчитатьСуммуНДС`). Ошибка
  повторного вычитания может только уменьшить эту сумму — проверка строже, но не обходится. Объект
  `ОбъектРеализацииКассы` (шапка и строки, как сейчас в `CreateFacture`, без изменения расчёта) нужен проверке для
  склада, даты, ордерных ключей и состава строк; суммы строк в предварительном режиме подменяются суммами кассы
  (по номеру строки — порядок строк кассы и реализации совпадает, `CreateFacture` идёт циклом по
  `Object.TabularSection`). Серверная проверка при проведении реализации из кассы видит суммы реализации (пока —
  без скидки, то есть не ниже оплаченных) и для кассы не является основным барьером; основной барьер кассы —
  предварительная проверка до оплаты. В шапке реализации из кассы явно ставится `ЦенаВключаетНДС = Истина` (сейчас
  не ставится: `СоздатьДокумент()` без `Заполнить()`, а строки посчитаны с НДС) — безопасная однострочная правка,
  не меняющая сумм.
Вызывается только для **новой
  продажи** (`ЭтоПродажа`): в `Payer` (105-118) **до открытия** `ФормаСложнойОплаты` и в `Valider` (399-420) до
  `CreateFacture`. Возврат (`ЭтоВозврат`, `СоздатьВозвратНаСервере`) и погашение долга по существующей реализации
  (`ЭтоКредит`, `AfterPaymentAtServer:702-710` — новая реализация не создаётся) не проверяются: они не продают
  товар заново; серверная проверка при проведении тоже не затрагивает их — она стоит только в реализации, а
  перепроведение старой реализации при погашении долга кассой не выполняется (проверю в коде оплаты; если
  выполняется — оно идёт с флагом `БезКонтроляМинимальнойЦены`, т. к. цены строк не меняются). Нарушения и нет допуска —
  предупреждение со списком строк, оплата не открывается. Черновик (отложенный чек, `СохранитьНакладную`) не
  проверяется — он не проводится.
- **Строка кассы** (`ФормаРедактированияСтроки:69-77`): редактируется цена **упаковки строки** (контракт §1).
  `Modifier` передаёт редактору ещё `Характеристика`, `Серия` и `Упаковка` строки (сейчас — только товар,
  количество и цену). При режиме склада, отличном от `НеКонтролировать`, поле «минимальная цена» — порог в базисе
  редактора: порог единицы хранения × коэффициент `Упаковка` строки, с НДС (порог без НДС умножается на `1 +
  Ставка/100` ставки номенклатуры); это подсказка до скидки. Запрет ввода ниже (307) — по этому порогу, при допуске
  снимается. **В режиме возврата** (`ЭтоВозврат`) порог склада не применяется: редактор работает как сейчас
  (`Мин(МинимальнаяЦена, Параметры.Цена)` — не ниже исходной цены строки), иначе частичный возврат мог бы
  блокироваться новым минимумом; признак возврата `Modifier` передаёт параметром. Окончательная проверка — до оплаты и при проведении по суммам реализации. При `НеКонтролировать` — как
  сейчас, по `МинимальнаяЦенаПродажи`.

## Риски

- Нагрузка: запрос остатков по партиям на каждой продаже склада с контролем — один запрос на документ по

  `НеНижеСебестоимости` на ордерном складе `ЗаполнитьБлокировкуПроведения` добавляет **разделяемые** блокировки
  `ТоварыВНаличии` и `ДополнительныеРасходы` (порог читает оба; запись допрасходов, например
  `ПоступлениеДополнительныхРасходов`, блокирует только свой регистр) по складу и номенклатуре строк — в том же месте порядка захвата (после складов, до
  `ТоварыКОформлению`, правило плана warehouse-orders), отдельной второй блокировки после основной нет. Режим
  склада читается до формирования блокировки. Строки, оформляющие ордер, читают движения проведённого ордера —
  их блокировка не нужна.
