# Тесты интерфейса через тест-клиент и прогон под ролями

Решение владельца от 2026-11-21 по разбору качества: поведение формы на клиенте исполняется до сдачи, и не
только под администратором. Заказчик времени — 2MZL (прочие задачи).

## Зачем

За 02.10–21.11 около 30 из 55 ушедших дефектов — ошибка при действии в форме, вёрстка, регресс формы; ещё
девять — права ролей. Смок открывает форму через `ПолучитьФорму` без отрисовки и под администратором, тесты
документов — серверные. 89 тыс. строк модулей форм, 899 команд и 844 обработчика `ПриИзменении` не исполняет
ни один тест.

## Проба (2026-11-21, 8.5.1.1423, macOS, копия `build/ib-kp`)

Проверено исполнением, а не по документации:

- `1cv8c /TESTCLIENT -TPort 1538` и `1cv8c /TESTMANAGER /Execute <epf>` соединяются:
  `Новый ТестируемоеПриложение("localhost", 1538)`, `УстановитьСоединение()`.
- Главное окно — `НайтиОбъект(Тип("ТестируемоеОкноКлиентскогоПриложения"))`; форма открывается
  `ВыполнитьКоманду("e1cib/app/Обработка.АРМЗакупки")`.
- Форму искать по `ИмяФормы` перебором `НайтиОбъекты(Тип("ТестируемаяФорма"))` с повтором: первый
  `НайтиОбъект` возвращает форму, открытую при запуске (дашборд).
- Рабочее место закупок отдаёт 192 кнопки, 12 таблиц, 111 полей; `Кнопка.Нажать()` исполняется.
- Имена свойств и методов тестируемых объектов сверять по модели типов EDT (память `platform-type-model`):
  `ЗаголовокФормы` и `ПолучитьТекстыПользовательскихСообщений` у этих объектов не существуют, у формы —
  `ТекстЗаголовка`. Переменная `Окно` в модуле формы занята свойством формы.

Не проверено: запуск тест-клиента под пользователем роли (диалог лицензии разработчика при первом входе —
память `live-role-check`), как тест-менеджер видит окно ошибки времени выполнения, устойчивость долгого прогона.

## Решение

Тесты интерфейса — **внешняя обработка, собираемая из исходников репозитория**, а не объект конфигурации:

- исходники — `tests/ui/` (модуль-ядро и файлы сценариев `.bsl`), сборка в `.epf` скриптом по образцу
  `scripts/print-preview/build_epf.py`; бинарник в git не попадает;
- код тест-менеджера выполняется в сеансе администратора, тест-клиент запускается под проверяемым
  пользователем. Роли пользователя не нужны права ни на обработку тестов, ни на внешние обработки — значит,
  в поставку не уходит ни новая роль, ни тестовый код, версия конфигурации не меняется;
- пользователи ролей заводятся в базе гейта `build/ib-gate` один раз серверной обработкой под
  администратором; пароли — в `build/`, в git и отчёты не попадают.

### Этап 1. Обход форм («нажать безопасное»)

Для каждой формы из списка (рабочие места производства, закупок, станков; касса; карточка товара; списки
документов с закладкой «Товары»): открыть на клиенте, переключить каждую страницу, активизировать первую
строку каждой таблицы, нажать команды сортировки и обновления и команды из явного белого списка формы.
Провал — окно ошибки, исключение тест-клиента, форма закрылась, клиент упал. Команды, меняющие данные,
на этом этапе не нажимаются.

Прогон — под администратором и под типовыми ролями (оператор производства, кладовщик, менеджер по
продажам, менеджер по закупкам, казначей, руководитель). Для роли дополнительно: команды раздела, видимые
в меню, открываются без «Недостаточно прав».

### Этап 2. Сценарии

Сценарий — файл `.bsl` с шагами над ядром: открыть, ввести строку, выбрать значение, нажать команду,
проверить значение поля и число строк таблицы. Первые сценарии — по дефектам из разбора: ввод строки и
сортировка в рабочих местах, панель «Клиент» без контрагента, выделение двух заказов, кнопка «Удалить»
кассы, окно печати под ролью. Дальше — правило «ошибка сначала становится тестом»: на замечание по форме
сначала пишется падающий сценарий.

### Встройка в гейт

`scripts/uitest.sh [база]` → шаг `scripts/gate.sh` после тестов документов; ключи `ФормОбойдено`,
`КомандНажато`, `СценариевИнтерфейса` — в `scripts/smoke-floor.txt`. Пропуск формы или роли — провал.

## Критерии приёмки

| № | Критерий | Чем доказывается |
|---|---|---|
| 1 | `scripts/uitest.sh` на базе гейта открывает каждую форму списка на клиенте и нажимает команды сортировки каждой её таблицы; отчёт называет форму, таблицу, команду | отчёт прогона |
| 2 | Намеренно сломанная команда сортировки (несоответствие типов, как в 2.0.17.32) роняет прогон с именем формы и команды | прогон на испорченной копии модуля |
| 3 | Тот же обход идёт под шестью ролями; команда, на которую у роли нет права, даёт провал с именем роли | отчёт прогона, контроль на роли без права |
| 4 | Гейт базы включает обход; порог не даёт пройти при меньшем числе форм или ролей | `scripts/gate.sh`, `smoke-floor.txt` |
| 5 | Пять сценариев этапа 2 проходят на текущей сборке | отчёт прогона |
| 6 | Прогон не требует действий владельца и не мешает EDT | запуск с закрытой и открытой IDE |

## Риски

- Диалог лицензии при первом входе нового пользователя: если тест-клиент на нём висит, нужен разовый
  Enter на каждого пользователя базы гейта — с разрешения владельца, один раз.
- Окна клиента открываются на экране владельца на время прогона (как у смока сейчас).
- Время гейта вырастет; обход под ролями идёт последовательно, оценка — после этапа 1.

## Состояние на 2026-11-21 (вечер)

Сделано и входит в гейт базы: обход 13 форм с закладками, появляющимися под выбранной строкой; восемь сценариев
«единица после выбора товара» (все таблицы ввода рабочих мест закупок и производства, кроме верхних «Документов»
производства); окно ошибки платформы считается ошибкой; снимок окна тест-клиента. Критерии 1 и 4 закрыты; критерий 2
закрыт фактически: на базе без правки обход красный на закладке «Оплаты» закупок (составной ключ динамического списка)
и на строке заказа в списке поступлений (не та выборка в панели сведений) - обе ошибки найдены тестами, а не
владельцем.

Не сделано:
- критерий 3 (роли): вход пользователя роли каждый раз встаёт на диалоге лицензии разработчика. Окна 1С не видны
  системе доступности macOS, фокус чужому приложению система не отдаёт - программно OK не нажать. Нужен способ
  отключить предупреждение или щелчок человека на прогон;
- критерий 5: из пяти сценариев по дефектам разбора есть один (ввод строки и единица). Остались: панель «Клиент»
  без контрагента, выделение двух заказов, кнопка «Удалить» кассы, окно печати;
- сценарий «повторная активизация той же строки не перечитывает нижние таблицы»: тест-клиентом повторная
  активизация не вызывается, счётчик серверных вызовов требует технологического журнала (общий файл настроек
  пользователя занят другим проектом);
- верхние «Документы» рабочего места производства: строка вводится только в режиме «выпуск без заказа».
