## Задача владельца (2026-10-29…30)

> Клиент жалуется: оформили приходный ордер на материал, а выпуск этот материал не списывает. Разрыв между ордером
> и поступлением может быть долгим, двигать товар нужно сразу после прихода, даже по ордеру.

> Нужны обе схемы: ордер первый (кладовщик принял — менеджер оформил поступление) и документ первый (пришла
> электронная накладная — поступление, кладовщик принимает ордером на основании поступления). Так же с расходом.

> Себестоимость — не оценкой: оценка даёт ложное восприятие цифр. Пусть до оформления будет 0 — это подталкивает
> оформлять поступления быстрее.

> Отдельный регистр себестоимости: в «Продажах» только выручка, себестоимость по партиям и допрасходам — в своём
> регистре.

> Баз с ордерной схемой нет. Запускающийся клиент — первые документы перепроведём вручную. На совместимость с
> ордерными данными время не тратить.

### Почему не работает сейчас (проверено по коду)

Приходный ордер пишет только `ТоварыНаСкладах` (физика) и `ТоварыКОформлению`; в `ТоварыВНаличии` у него движений
нет (`ОрдераСклада.ПровестиОрдер`:67, `СформироватьФизическиеДвижения`:1337). Выпуск списывает материал по партиям
`ТоварыВНаличии` (`ВыпускПродукции/ObjectModule.bsl`:37 → `ТоварыВНаличии.СписатьНоменклатуру`:766; автовыпуск —
`Производство.ОстаткиМатериалов`:3060) и при нехватке партий отказывает. Партию создаёт только поступление.

Зеркальная дыра на расходе: между расходным ордером и реализацией партии физически ушедшего товара доступны выпуску,
перемещению, требованию; потом не проводится сама реализация.

## Новое главное архитектурное решение

**На любом складе `ТоварыВНаличии` — физика с партиями и стоимостью. Документ, который физически двигает товар,
двигает и партии.** На ордерном складе это ордер, на неордерном — сам документ, как сейчас.

| Слой | Регистр | Кто пишет на ордерном складе |
|---|---|---|
| физика + партии + стоимость | `ТоварыВНаличии`, `ДополнительныеРасходы` | приходный ордер (приход, партия = ордер), расходный ордер (расход по FIFO); прочие складские документы — как сейчас |
| связь «первый документ ждёт второго» | `ТоварыКОформлению` (переделанный, ниже) | первый документ пары — приход, второй — расход |
| выручка | `Продажи` | реализация, возврат от покупателя |
| себестоимость продаж | `СебестоимостьПродаж` (новый) | реализация (из своего списания или из списания расходных ордеров), возврат от покупателя |
| взаиморасчёты, заказы | как сейчас | поступление, реализация; заказы и потребности — ордер |

**Партия на ордерном складе — всегда `ПриходныйОрдер`**, в обеих схемах: дата партии = дата физического прихода,
FIFO идёт по полке, а не по дате, когда менеджер дошёл до счёта.

**Носитель и источник стоимости.**

- Приход: носитель партии — приходный ордер, источник стоимости — поступление. Сумма партии ордера = сумма
  оформленных пар (ниже) по строкам поступлений; неоформленная часть — 0.
- Расход: носитель списания — расходный ордер (FIFO, стоимость известна сразу), потребитель стоимости — реализация.
  Себестоимость реализации = доля списания строк ордера по оформленным парам.

**Ближний пересчёт вместо каскада.** Изменение источника сразу пересчитывает только носителя, без цепочки:

| Событие | Что пересчитывается сразу | Что дальше |
|---|---|---|
| проведение, перепроведение, отмена поступления на ордерном складе | суммы партий его приходных ордеров (`ТоварыВНаличии`, `ДополнительныеРасходы` ордера) | граница `Основная` → момент самого раннего из этих ордеров; потребители партии — восстановлением последовательности |
| проведение, перепроведение, отмена расходного ордера | `СебестоимостьПродаж` его реализаций | ничего: от себестоимости продаж ничего не рассчитывается (возвраты — правило ниже) |
| проведение реализации | своя `СебестоимостьПродаж` из списания ордеров | — |

Пересчёт носителя — **перезапись стоимостных наборов** документа-носителя под блокировкой, а не его перепроведение:
перепроведение потянуло бы автовыпуск, защиту оформленного ордера, `ПотребностиПроизводства`, взаиморасчёты с их
блокировками после `ТоварыКОформлению` — нарушение единого порядка захвата. Количества носителя не меняются, только
суммы. Направление ближнего пересчёта выбрано так, чтобы пересчитываемый документ не мог упасть по остаткам:
приходный ордер ничего не списывает, реализация на ордерном складе тоже.

## Регистры

### `ТоварыВНаличии` и `ДополнительныеРасходы`

- Тип измерения `Партия` — `DefinedType.ПриходныйДокументПартии`: добавить `DocumentRef.ПриходныйОрдер`. Тип
  общий для `ТоварыВНаличии`, `ДополнительныеРасходы`, `ТоварыВПереработке`, `Продажи` и реквизитов партии
  реализации, выпуска, передачи в переработку — каждое место сверить (раздел «Партия — не поступление»).
- Новый реквизит **`КодСтроки`** (Число, 10.0) у обоих регистров: строка документа, давшая запись. Заполняет
  `СписатьНоменклатуру` и приход ордера; остальные документы могут оставлять 0. Нужен, чтобы доля стоимости строки
  расходного ордера и строки приходного ордера находилась без ТЧ-снимков. Реквизит, не измерение — итоги не растут.
- Записи приходного ордера: по строке (с `КодСтроки`) — количество, `Сумма`, `СуммаНДС` = сумма его пар оформления.
  Записи `ДополнительныеРасходы` ордера — допрасходы поступлений по тем же парам, по статьям.
- `РассчитатьСуммуСписанияДополнительныхРасходов` делит допрасход по **сумме** партии; при сумме партии 0 и
  ненулевом допрасходе формула вырождается (`СуммаСписания = СуммаПартии = 0` → весь допрасход уходит первому
  списанию). Для партии-ордера с нулевой суммой — делить по количеству. Проверить тестом. **Редакция 6:** то же
  правило — в первичном распределении `ДополнительныеРасходы.РаспределитьПоПозициям` (база — сумма товаров; при
  нулевом итоге — количество, остаток округления — последней строке) и в разложении расходов поступления по парам;
  тест — документ допрасходов на ордер с двумя нулевыми позициями, с НДС.

### `ТоварыКОформлению` — двусторонний

Сейчас: приход пишет только ордер, расход — поступление или реализация; измерение `Ордер`. Новая модель — **первый
документ пары пишет приход, второй — расход**, кто бы ни был первым.

| Измерение | Тип | Смысл |
|---|---|---|
| МестоХранения | как сейчас | |
| **Источник** (вместо `Ордер`) | `ПриходныйОрдер`, `РасходныйОрдер`, `ПоступлениеТоваровУслуг`, `РеализацияТоваровУслуг` | первый документ пары |
| **КлючСтрокиИсточника** (вместо `КлючСтрокиОрдера`) | Число | `КодСтроки` строки источника |
| Номенклатура, Характеристика, Серия | как сейчас | коммерческая номенклатура строки (комплект — комплектом) |
| ~~Составляющая~~ | — | **удаляется**: реализация больше не списывает партии, составляющие ей не нужны |

Ресурс `Количество`. Реквизит **`КодСтрокиРегистратора`** (Число): строка второго документа — по нему
восстанавливается пара. Баз с данными нет (В7) — меняем структуру без переноса.

**Пара оформления** = запись расхода `ТоварыКОформлению`: (Источник, КлючСтрокиИсточника) ↔ (Регистратор,
КодСтрокиРегистратора), количество q. Одна функция `ТоварыКОформлению.ПарыОформления(Документы)` возвращает пары в
обе стороны для набора документов — ею пользуются и ордера (стоимость партии), и реализация (себестоимость), и
отчёты.

Целостность — как сейчас: после записи остаток по каждому затронутому ключу ≥ 0, иначе отказ; исключительная
блокировка по источникам до чтения их реквизитов; защита оформленной строки источника (меняется только количество, не
ниже оформленного; удалить нельзя) — **обобщается на четыре типа источника**. У финансового источника (поступления,
реализации) правка цены оформленной строки разрешена — это и есть ближний пересчёт.

### `СебестоимостьПродаж` (новый, обороты)

Регистраторы: `РеализацияТоваровУслуг`, `ВозвратОтПокупателя` (сторно), `КорректировкаРегистров`.

| Измерение | Смысл |
|---|---|
| ХозяйственнаяОперация, Организация, Сотрудник, Контрагент, ДокументПродажи, Номенклатура, Характеристика, Ответственный, МестоХранения, УУ | **те же, что у `Продажи`** — отчёты маржи объединяют два регистра `ОБЪЕДИНИТЬ ВСЕ` + группировка, без соединения |
| Серия | для возврата |
| НоменклатураПартии | что списано физически: составляющая комплекта, иначе = Номенклатура |
| Партия | `ПриходныйДокументПартии` |
| СтатьяДДС | пусто — стоимость партии; заполнено — допрасход этой статьи |

Ресурсы: `Количество` (только в строках партии, в строках допрасходов 0), `Сумма`, `СуммаНДС`.

Пишет реализация: на неордерном складе — из своих движений списания (`ТоварыВНаличии` + `ДополнительныеРасходы`
расход), на ордерном — из пар оформления: для пары (строка ордера k, q) — записи `ТоварыВНаличии`/`ДополнительныеРасходы`
ордера с `КодСтроки = k`, умноженные на q / Q_k; остаток округления — последней паре строки по моменту реализации.
**Редакция 4:** получатель остатка зависит от всех пар строки ордера — добавление, изменение или удаление пары
пересчитывает `СебестоимостьПродаж` **всех реализаций затронутых строк ордера** под одной блокировкой (не только
своей); **Редакция 7:** целевая сумма оформленной части = округлённая стоимость строки ордера × Σq / Q_k (отдельно
`Сумма` и `СуммаНДС`); последней паре — разность целевой суммы и суммы остальных округлённых долей, неоформленная
часть в себестоимость не попадает. Тесты: оформление 4 из 10, отмена второй частичной реализации. **Редакция 11:** изменение стоимостных записей прежней реализации
сдвигает границу строго раньше самого раннего её проведённого возврата (возврат — потребитель этой стоимости);
сценарий «три частичных оформления, возврат между вторым и третьим», после восстановления — стоимость возврата и
последующих списаний возвращённого товара.
Тесты: обратный порядок создания реализаций, смена даты реализации, отмена одной из пар.
Услуги — как сейчас, по закупочной цене (`Продажи`:148–326, ветка услуг), партия пустая.

**Возврат от покупателя** восстанавливает партии из `СебестоимостьПродаж` основания (сейчас — из `ТоварыВНаличии`
реализации, `СформироватьОприходованиеПоРеализации`:178, и сторнирует `Продажи` основания, `УменьшитьПрибыльПоВозврату`:36).
Один источник для обоих складов. `ВычестьПрежниеВозвраты` — по `СебестоимостьПродаж` прежних возвратов.
**Редакция 7:** записи `СебестоимостьПродаж` хранят происхождение списания — документ физической отгрузки (сама
реализация или расходный ордер) и ключ его строки (реквизиты `ДокументОтгрузки`, `КлючСтрокиОтгрузки`); возврат
берёт только списания с моментом отгрузки не позже возврата и вычитает прежние возвраты по тем же ключам. Тест: две
отгрузки, возврат между ними, восстановление после второй — возврат не меняется.
Возврат по реализации ордерного склада — только оформленного (отгруженного) количества на дату возврата.
**Редакция 6:** проверка не только при проведении возврата — отмена, уменьшение, перенос даты и смена привязки
расходного ордера проверяют все затронутые реализации и их проведённые возвраты под общей блокировкой: если после
изменения возвращено больше, чем отгружено на момент любого возврата, — отказ (защита «документ первый», фаза 4).
Тест «реализация → ордер → возврат → отмена ордера»: атомарный отказ, остатки не изменились.

### `Продажи` после переноса

**Редакция 5:** писатели ресурсов `Себестоимость`/`ДополнительныеРасходы`/`ВаловаяПрибыль` — не только реализация и
возврат: `КорректировкаДолга` (`Продажи.УменьшитьПрибыльПоКорректировке` читает и пишет `ВаловаяПрибыль`). В фазе 2
корректировка пишет только выручку и НДС; историческая маржа корректировок — перенос с явной сверкой (сейчас
`ВаловаяПрибыль` там считается иначе, чем общей формулой) — расхождение в отчёт владельцу. Полный список писателей —
поиском по `Продажи` в модулях при старте фазы 2; тест: проведение корректировки после удаления колонок.

Остаются: Количество, Выручка, НДС; измерения без `Партия`. Выручка больше не распределяется по партиям
пропорционально себестоимости (`РаспределитьВыручкуПоСебестоимости`:328) — строка продажи без партии.
`ВаловаяПрибыль` не хранится: отчёты считают Выручка − НДС(если так сейчас) − Себестоимость − ДопРасходы по
формуле из `Продажи/ManagerModule.bsl` (55–58, 146, 309–316 — сверить одну формулу, она встречается в трёх местах).

Удаление ресурсов `Себестоимость`, `ДополнительныеРасходы`, `ВаловаяПрибыль` и измерения `Партия` — **только в
следующей публикации CF после фазы 2**: реструктуризация выполняется раньше обработчиков обновления, перенос
истории должен отработать на всех базах, пока старые колонки ещё есть. До удаления новые движения их не заполняют.
**Редакция 3:** CFU релиза с удалением собирается только с версий не ниже публикации фазы 2 (иначе база, прыгнувшая
через неё, теряет историю при реструктуризации до обработчика) — строкой в `docs/RELEASING.md` в ту же сборку.

**Источник переноса истории (Редакция 3).** В `Продажи` нет `Серия`, `НоменклатураПартии` (у комплекта — сам комплект),
`СтатьяДДС` и НДС себестоимости: перенос по товарам — из движений расхода самой реализации (`ТоварыВНаличии` +
`ДополнительныеРасходы`) и возврата (приход), по услугам и записям `КорректировкаРегистров` — из `Продажи`. Тогда
возврат по старой реализации, читая новый регистр, восстанавливает те же партии, что сейчас.

### `ТоварыНаСкладах`

После фаз 3–4 на любом складе равен свёртке `ТоварыВНаличии` без партий. Фаза 5 удаляет регистр, зеркало
(`RecordSetModule` `ТоварыВНаличии`, `ЗаписатьЗеркало`, `ПерестроитьНаборНеЗеркала`, `ИсключитьЗаписиОрдерногоСклада`,
подписка `ПрежниеПозицииСкладаПередЗаписью`), ступень порядка блокировок; минимальный остаток возвращается в
`ПриЗаписи` набора `ТоварыВНаличии`.

## Документы

### Приходный ордер

- Основания: как сейчас + **`ПоступлениеТоваровУслуг`** (документ первый). Строка из поступления хранит
  `Документ` + `КлючСтрокиДокумента` (новые реквизиты ТЧ); строка без них — ордер первый.
- Проведение:
  - `ТоварыВНаличии` приход по строкам, `Партия` = ордер, `ДатаПартии` = дата ордера, `КодСтроки`, сумма по парам;
    `ДополнительныеРасходы` по парам;
  - `ТоварыКОформлению`: строки без документа — приход (источник = ордер); строки с документом — расход по
    источнику-поступлению;
  - `ЗаказыПоставщикам`, `ПотребностиПроизводства` — как сейчас; у строки из поступления заказ и строка заказа
    берутся из поступления (`Основание` шапки поступления, `КодСтрокиЗаказа` его строки — сверить, как поступление
    хранит строку заказа);
  - `ТоварыНаСкладах` — до фазы 5 пишет зеркало (у ордера появляются движения `ТоварыВНаличии`), прямая запись
    `СформироватьФизическиеДвижения` удаляется.
- В последовательности `Основная`.

### Поступление на ордерном складе

- Строки с ордером (ордер первый) и без ордера (документ первый) — **в одном документе допустимы обе**. Правило
  «строка ордерного склада без ордера — отказ» (решение 3 прошлой волны) **снимается**.
- **Редакция 5:** ближний пересчёт сравнивает рассчитанные стоимостные наборы ордера с записанными под блокировкой:
  совпали — не пишет и границу не двигает (иначе восстановление последовательности, перепроводя поступление,
  возвращало бы границу назад бесконечно); изменились — пишет и сдвигает. Тест: цепочка T1–T3 + документ T4 после
  поступления, полное восстановление и повторный прогон без изменений — граница стоит.
- Проведение: `ТоварыВНаличии` и `ДополнительныеРасходы` **не пишет** на строках ордерного склада; взаиморасчёты —
  как сейчас; `ТоварыКОформлению`: строки с ордером — расход, без ордера — приход (источник = поступление);
  `ЗаказыПоставщикам`/`ПотребностиПроизводства` на ордерном складе не двигает (их двигает ордер, как сейчас).
- После записи движений — **ближний пересчёт**: ордера всех пар документа (прежних и новых) перезаписывают
  стоимостные наборы; граница `Основная` → самый ранний момент этих ордеров
  (`Последовательности.Основная.УстановитьГраницу`, только назад — сравнить с `ПолучитьГраницу()`).
- Отмена проведения — тот же пересчёт (пары ушли — суммы партий уменьшились).

### Расходный ордер

- Основания: как сейчас + **`РеализацияТоваровУслуг`** (документ первый). Строка хранит `Документ` +
  `КлючСтрокиДокумента`.
- Проведение: автовыпуск — как сейчас (владелец — ордер в обеих схемах); `ТоварыВНаличии` и
  `ДополнительныеРасходы` расход через `СписатьНоменклатуру` (FIFO, комплекты — составляющими по снимку
  `ТЧФизическийСостав`, `КодСтроки` в записях); `ТоварыКОформлению`: строки без документа — приход, с документом —
  расход по источнику-реализации.
- **Нехватка партий — отказ**, как у реализации сейчас (`СписатьНоменклатуру` без `РазрешитьНедостачи`). Это новое
  поведение ордера (сейчас он физику не проверяет): при приходе ордерами партия есть всегда, когда товар на полке.
  Правило владельца 2026-10-09 о минусах новых запретов не добавляет — это существующий контроль партий списания.
  **Развилка Р1** (ниже).
- После записи — ближний пересчёт `СебестоимостьПродаж` реализаций всех пар (прежних и новых).
- В последовательности `Основная`.
- `ТЧФизическийСостав`: снимок по-прежнему нужен — восстановление последовательности перепроводит ордер, и состав
  комплекта не должен браться из текущего справочника. Правило заморозки строки-комплекта с оформлениями остаётся.

### Реализация на ордерном складе

- Строки с ордером (ордер первый) и без ордера (документ первый) — обе допустимы.
- Проведение: `ТоварыВНаличии` не пишет; `Продажи` — выручка; `СебестоимостьПродаж` — по парам; взаиморасчёты как
  сейчас; `ТоварыКОформлению`: с ордером — расход, без ордера — приход (источник = реализация). Автовыпуск не
  вызывает (как сейчас на ордерном складе).
- Строка без пары — себестоимости нет, в отчётах маржи — признак «себестоимость не определена».

### Прочие складские документы

Перемещение, списание, оприходование, пересортица, возвраты поставщику и от покупателя, переработка, требование,
выпуск на ордерном складе — без ордеров, как сейчас: сами пишут `ТоварыВНаличии` (они и есть физические документы).
Пункт TECHDEBT «возвраты и переработка на ордерном складе — без ордеров» остаётся.

### `ПоступлениеДополнительныхРасходов`

`ТЧТовары.ДокументПартии` типизирован прямо `DocumentRef.ПоступлениеТоваровУслуг` (`.mdo`:770). Тип расширить
`ПриходныйОрдер`; если выбрано поступление ордерного склада — `ДополнительныеРасходы.РаспределитьНаСебестоимость`
раскладывает строку на партии-ордера по его парам пропорционально сумме пар (сейчас ищет записи
`ТоварыВНаличии` с `Регистратор В (партии)` — у поступления ордерного склада их нет). **Редакция 5:** изменение пар
поступления (проведение, перепроведение, отмена поступления или ордера) находит документы
`ПоступлениеДополнительныхРасходов` по этому поступлению и сдвигает границу не позже самого раннего из них —
распределение перепроведётся восстановлением. При неполной приёмке допрасход делится по оформленным парам на дату
документа допрасходов; **Редакция 6:** неоформленная часть не исчезает и не ложится на несуществующую партию — она
хранится как нераспределённый остаток документа допрасходов (признак в его записях) и распределяется записями с
периодом поздней приёмки (момент приходного ордера, давшего пару), не раньше появления партии. Механизм — детальный
план фазы 3; тест: 100 допрасхода, приёмки 6 (до) и 4 (после) — до T4 на партии только 60, после T4 — все 100. Тест:
две приёмки, допрасход между ними, граница уже за документом допрасходов. Заполнение по поступлению
(`ObjectModule.bsl`:12) — так же. Семантика даты (допрасход действует с даты документа) — без изменений.

`ПерепроведениеДокументов` предопределённое, **расписания в `.mdo` нет** — работает, только если расписание задано в
базе. При стоимости 0 до оформления восстановление последовательности обязательно.

Перемещение (если есть) **пересобирается с теми же партиями, сериями и количествами** (берутся из его же записей расхода `ТоварыВНаличии` на складе-источнике) — `СписатьНоменклатуру` с явной партией + `ОприходоватьСписанное`: меняются только суммы. Инвариант «перемещение неизменно» (склад, дата, строки, партии) сохраняется. Нехватка явной партии — отказ, задание останавливается (Ф1.3) |

### Ф1.3 Задание и граница

Протокол `ПроцедурыРегламентныхЗаданий.ПерепроведениеДокументов`:

1. Выход сразу: обновление не завершено; граница не раньше момента последнего проведённого документа
   последовательности.
2. Интервал — от границы `Г0` до момента последнего проведённого документа (задание) или до конца периода
   обработки (кнопка «Выполнить» обработки всегда начинает от границы — начало периода в форме не раньше границы).
   **Редакция 8:** заранее составленный список не перепроводится — он только показан в форме и задаёт конец
   интервала. Каждый шаг под блокировкой (п. 4) **сам выбирает следующий документ**: первый проведённый документ
   последовательности с моментом после текущей позиции (запрос по `Последовательность.Основная` с
   `Регистратор.Проведен`); отменённый, удалённый или перенесённый после составления списка документ так не
   перепроводится и не теряется. Тест: отмена проведения документа после построения списка формы, до его шага —
   документ остаётся непроведённым.
3. **Остановка на первой ошибке** (сейчас идёт дальше и каждый следующий запуск перепроводит весь хвост): ошибка —
   в `НепроведенныеДокументы` (текст — `ДополнительныеСвойства.ТекстОшибки` или краткое представление исключения).
   **Редакция 7 — замороженные основания.** Реализация или поступление, покрытые налоговым документом на основаниях
   с возвратами или корректировками, не перепроводятся никем (`НалоговыеДокументыНаОснованиях
   .ПричинаЗапретаИзмененияОснования`:1100 — возвраты уже прочитали их партии); иначе пересчёт встал бы на них
   навсегда. Запрет не снимается: перед перепроведением документ проверяется новой экспортной функцией того же
   модуля (`ОснованиеЗаморожено`, тот же признак `ЕстьЗависимыеРасчеты` покрывающего документа) — заморожен:
   не перепроводится, в `НепроведенныеДокументы` — пояснение «стоимость заморожена налоговым документом с
   возвратами», шаг двигает границу через него. **Редакция 8:** отметка постоянная — новый реквизит регистра
   `НепроведенныеДокументы.СтоимостьЗаморожена` (Булево; регистр служебный, измерение одно — `Документ`,
   реструктуризация малая); `ОчиститьОшибки` в начале прогона снимает только обычные ошибки, отметку снимает лишь
   успешное перепроведение этого документа. Позиция обхода (граница) и подтверждённая актуальность разделены: см. Ф1.4.
   **Редакция 13 — возврат в пересчёт:** до раннего выхода (п. 1) задание перепроверяет каждую отметку
   `СтоимостьЗаморожена` той же функцией `ОснованиеЗаморожено`; причина снята (последний зависимый возврат отменён)
   — граница строго раньше документа (дата − 1 с, только назад, под исключительной блокировкой таблицы
   последовательности), отметка остаётся до успешного перепроведения. Документ не проведён или удалён — отметка
   снимается, граница строго раньше его даты (отмена проведения платформа и так отражает сдвигом назад — это
   страховка). Тест цепочки отмен: возврат → покрывающий налоговый документ → основание. Тест: отмена последнего зависимого возврата
   после полного обхода → следующий прогон перепроводит основание и снимает отметку. Его стоимость и стоимость обеих сторон переклассификации не догоняют
   пересчёт — TECHDEBT, решение в фазе 2 вместе с переводом `ПереклассифицироватьПродажи` на `СебестоимостьПродаж`.
   Тест: сценарий «поступление → реализация → налоговая реализация на основаниях → возврат по ней → пересчёт» —
   пересчёт проходит через реализацию, не перепроводя её, движения возврата те же.
4. **Шаг = одна транзакция: перепроведение `d` → блокировка таблицы последовательности → перепроверка → граница на
   `d`** (Редакция 9; итоговой сверки нет — сбой между шагами ничего не теряет). Позиция = граница = момент последнего
   обработанного документа; следующий — первый проведённый документ последовательности с моментом **строго после**
   позиции (п. 2). Шаг:
   1. выбрать `d` (без блокировки);
   2. `НачатьТранзакцию`; загрузить объект `d` и проверить `Проведен`, `ПометкаУдаления` и момент: не проведён,
      помечен или момент уже не после позиции — откат шага и выбор заново (п. 4 считает и эти повторы); иначе
      перепровести `d` — со своими обычными блокировками (склад, потребности…), как любое проведение. **Редакция 11:**
      явной блокировки документа нет (она давала встречный порядок с внешними транзакциями АРМ, которые блокируют
      остатки до записи существующего документа, — `АРМПроизводство.ЗаписатьСтрокуПоступленияИзПереработки`:10063).
      Отмену проведения между загрузкой и записью ловит оптимистическая проверка версии платформы: запись объекта,
      изменённого другим сеансом после чтения, отклоняется — проверено 2026-10-30 на копии (два объекта одной ссылки,
      запись второго, затем первого — «incompatibilidad de la versión», и с `ОбменДанными.Загрузка` тоже). Такая
      ошибка шага (версия `d` в базе ≠ прочитанной) — не ошибка документа: откат и выбор заново;
   3. управляемая **разделяемая** блокировка всей таблицы `Последовательность.Основная` (пространства «границ» у
      платформы нет — проверено 2026-10-30 на копии: `Последовательность.Основная.Границы` — «Nombre incorrecto del
      espacio de bloqueos», `Последовательность.Основная` — принято). Параллельное проведение документа
      последовательности пишет свою запись под неявной исключительной блокировкой: оно либо зафиксировано до этого
      места, либо ждёт конца шага;
   4. под блокировкой: граница **раньше позиции** (её сдвинули назад) — откат шага, остановка прогона. Граница на
      позиции или на `d` — норма (**Редакция 12:** при `Move` платформа сама переносит границу вперёд на проводимый
      документ, если между ней и ним нет других проведённых документов последовательности, — это и есть `d`;
      «Не перемещать» не ставим: оно выключило бы и автоматический сдвиг назад при проведении задним числом, на
      котором держится протокол; сдвиг назад при записи влияющих регистров документом вне проведения —
      `КорректировкаРегистров` — делаем сами, Ф1.1). Первый проведённый документ после позиции уже не `d`
      (появился или исчез документ раньше `d`) — откат шага и выбор заново (не больше трёх раз, затем остановка);
      иначе `УстановитьГраницу(d)` (если платформа ещё не поставила), `ЗафиксироватьТранзакцию`.

   **Порядок блокировок** (Редакция 9, ответ на встречный порядок с АРМ производства): блокировка последовательности
   берётся **последней**, как и у обычного проведения (складские — в `ОбработкаПроведения`, запись последовательности —
   платформой в конце записи). Внешние транзакции рабочих мест (`АРМПроизводство`: `ЗаблокированноеПрямоеПоступление`
   :5401, `ПровестиПоступлениеИзПереработки`/`ЗаблокироватьОстаткиПоступления` ~10100) тоже берут складские
   блокировки раньше записи документа — порядок совпадает. Остаточный цикл возможен, только если внешняя транзакция
   уже записала один документ последовательности и затем блокирует склад, занятый шагом; платформа снимет одну из
   транзакций ошибкой взаимоблокировки — шаг откатывается, прогон останавливается и повторится по расписанию;
   откат пользовательской транзакции в этом случае — известный риск, в TECHDEBT. Проверка — двухсеансовый прогон на
   копии (две внешние обработки с файлом-барьером: А держит складскую блокировку и пишет документ, Б — шаг пересчёта):
   нет взаимоблокировки, граница верна.

   Почему этого достаточно: документ, изменённый параллельно и зафиксированный до п. 3, виден перепроверке п. 4 (если
   он раньше `d`) или конфликтует с `d` по складским блокировкам и тогда `d` перепроведён уже на его данных; документ,
   ждущий шага, после фиксации видит границу на `d` и при моменте раньше неё сдвигает её назад сам (`Move`).
   Перепроверку и `УстановитьГраницу` с параллельным сдвигом назад упорядочивает п. 3. Список, переданный обработкой
   не от границы, границу не двигает вовсе.
5. `КорректировкаРегистров` (Ф1.1) сдвигает границу назад под **исключительной** блокировкой той же таблицы.
6. Одновременный запуск (**Редакция 14**): уникальность ключа регламентного задания и программного фонового считается
   по-разному (у первого — по объекту метаданных задания, у второго — по методу), поэтому оба пути сводятся к одному
   рабочему методу: регламентный метод `ПроцедурыРегламентныхЗаданий.ПерепроведениеДокументов` — диспетчер,
   запускающий `ФоновыеЗадания.Выполнить("ПроцедурыРегламентныхЗаданий.ПересчитатьПоследовательность", , Ключ)`, и
   обработка запускает тот же метод с тем же ключом; второй запуск получает исключение платформы «задание с таким
   ключом уже выполняется» — диспетчер молча выходит, обработка сообщает «пересчёт уже выполняется». Проверка на
   8.5.1 — одновременный запуск из обработки и диспетчером в обоих порядках (прогон на копии).

Расписание (Р2): в `.mdo` его нет (свойство транзитное) — ставит идемпотентная процедура
`ОбновлениеПрограммыОбработчики.НастроитьЗаданиеПерепроведения`, зарегистрированная **дважды**: обработчиком
обновления 2.0.16.120 и обработчиком начального заполнения (`НачальноеЗаполнение = Истина`, как у функциональных
опций 2.0.16.5) — иначе новая база осталась бы без расписания (`ОбновлениеПрограммы.ВыполняемыеОбработчики`:357).
Если предопределённое задание выключено — включить, каждые 30 минут; включённое администратором — не трогать. Тест
`ПоследовательностьСостав` проверяет и задание: включено, расписание задано.

Сдвиг границы платформой проверяется тестом (Ф1.6): проведение документа последовательности задним числом
(`MoveBoundaryOnPosting = Move`) сдвигает её назад. `УстановитьГраницу` назад вручную нужен только
`КорректировкаРегистров` (Ф1.1) и в фазе 3.

### Ф1.4 Показатель «Себестоимость актуальна по»

`РаботаСДокументами.АктуальностьСебестоимости()` → `Граница` (Дата), `Актуальна` (граница не раньше последнего
документа последовательности **и нет отметок `СтоимостьЗаморожена`** — Редакция 8), `Заморожено` (число таких
документов и самая ранняя дата), `Текст` (ru/fr/en/es: «Себестоимость актуальна на ДД.ММ.ГГГГ ЧЧ:ММ» /
«Себестоимость пересчитана по ДД.ММ.ГГГГ ЧЧ:ММ, более поздние документы ждут пересчёта»; при заморозке —
постоянное «N документов с замороженной стоимостью (с ДД.ММ.ГГГГ) — список в «Непроведённых документах»», и после
полного обхода тоже). Тест замороженного основания: после полного прогона `Актуальна = Ложь`, текст называет
заморозку. Вывод:
- отчёты `СтоимостьСклада`, `ВедомостьПоТоварамНаСкладах`, `ВедомостьПоПродажам`, `ФинансовыйРезультат`,
  `СебестоимостьПродукции` — строка над результатом: `ПриКомпоновкеРезультата` в модуле объекта (у трёх его нет —
  создать) компонует сам с данными расшифровки (расшифровка сохраняется), строка — только если не актуальна;
- `ДашбордПродаж` — надпись и кнопка «Пересчитать», открывающая обработку «Перепроведение документов»; кнопка видна
  при праве `Использование` обработки. В отчётах кнопки нет (формы отчётов типовые): текст называет путь «Сервис →
  Перепроведение документов».
Права не меняются: задание и обработка работают с правами запустившего; не хватает прав на документ — остановка на
нём с текстом ошибки. **Редакция 10:** права показателя отделены от прав пересчёта — `АктуальностьСебестоимости`
читает `Последовательность.Основная` и `НепроведенныеДокументы` в привилегированном режиме и возвращает только
дату, число и признак (без ссылок на документы); у ролей отчётов (`МенеджерПоПродажам` — `ВедомостьПоПродажам`,
`ОператорПроизводства` — `СебестоимостьПродукции`) прав на эти объекты нет и не появляется. Тест: показатель и
формирование отчёта под этими ролями (как `ПраваРолей` в сценариях).

### Ф1.5 Первая установка на базы клиентов (обработчик 2.0.16.120, монопольно)

Замер 2026-10-30 на копиях (только чтение): **2MZL** — граница 06.01.2026 (начало истории), после неё 456 документов
последовательности и 227 из 228 автовыпусков; задание выключено. **Drissotex** (копия на 2.0.16.119, клиент
запускается) — граница 25.10.2026, 9 документов новых видов; задание выключено. Записей последовательности у
документов новых видов **нет** — платформа заполняет их при проведении.

1. Записи последовательности по проведённым документам четырёх видов (набор `Последовательности.Основная` с отбором
   по регистратору, идемпотентно); граница до и после — та же (восстанавливается, если запись её сдвинула).
2. **Редакция 6:** граница → **строго раньше самого раннего проведённого документа четырёх добавленных видов**
   (Редакция 9: `Новый МоментВремени(Дата − 1 с)` — обход берёт документы строго после границы, сам документ должен
   попасть в пересчёт; только назад). **Редакция 14 — переход семантики:** старая процедура ставила границу на
   первый документ с ошибкой и включала дату границы в выборку; новый обход идёт строго после границы. Поэтому
   обработчик однократно ставит границу = минимум из (прежняя граница − 1 с) и (самый ранний добавленный документ − 1 с)
   — документ, на котором старое восстановление встало, перепроведётся; пустая граница (`'0001-01-01'`) остаётся
   пустой. **Редакция 15 — идемпотентность:** старая процедура всегда ставила границу на момент документа (со
   ссылкой), обработчик ставит момент без ссылки — повторный запуск после сбоя видит границу без ссылки и секунду не
   вычитает (отдельный признак не нужен; между сбоем и повтором задание не работает — `ОбновлениеНеЗавершено`).
   Тест: двойной вызов обработчика даёт ту же границу. Тест: прежняя граница на ошибочной реализации раньше всех добавленных документов — после обновления
   реализация перепроводится. Старая граница подтверждала только прежний состав; оставь её — показатель «актуальна» врал бы по
   историческим выпускам и переработке, а выборка от границы их бы не взяла. Замер: на 2MZL граница уже 06.01 (раньше
   первого автовыпуска) — ничего не меняется, первый прогон перепроведёт историю с 06.01 в любом случае; на Drissotex
   — 25.10 → 07.10. Время и ошибки первого прогона — замер на копиях с новой конфигурацией, в отчёт владельцу.
   Альтернатива для владельца (рекомендация промпта «оставить» пересмотрена по этому разбору): граница «на сейчас»
   без пересчёта истории — тогда показатель обязан говорить «актуальна с ДД.ММ», а не «по», и это отдельная доработка.
3. Расписание задания (Ф1.3).

### Ф1.6 Тесты (`ТестыДокументов`, реестр `TESTS.xlsx`)

- `ПоследовательностьСостав` — Ф1.1.
- `ВыпускВПоследовательности` — материал: поступление 10 по 10 (T1), выпуск 10 (T2), реализация продукции (T3);
  поступление 10 по 20 задним числом (T0 < T1) → граница ≤ T0 (сдвинула платформа) → пересчёт списком этих документов
  → себестоимость выпуска и реализации — по 20 (FIFO); второй пересчёт — движения те же (сравнение наборов).
- `АвтовыпускВПоследовательности` — реализация с автовыпуском: снимок ТЧ автовыпуска, `ПотребностиПроизводства`,
  стадии заказа → пересчёт [автовыпуск, реализация] → снимок тот же, стоимость пересчитана; без отказа правки.
- `ТребованиеВПоследовательности` — завершённое требование с перемещением: пересчёт → выпусков не прибавилось,
  `ЗагрузкаСтанков`/`МатериалыНаСтанках` те же, партии перемещения те же.
- `ОбновлениеГраницы` — обработчик: граница позже исторического выпуска → после обновления строго раньше него, и
  пересчёт перепроводит этот выпуск, даже если он единственный в хвосте;
  граница раньше → не тронута; записи последовательности у выпуска есть; повторный запуск ничего не меняет.
- `ЗаданиеПересчёта` (Редакция 12) — сама процедура задания без конкуренции: единственный документ после границы
  перепроведён, транзакция шага зафиксирована, граница на нём; повторный запуск — выход сразу, ничего не меняет.
- `ГраницаПересчёта` — список не от границы границу не двигает; документ, распроведённый после выбора и до шага,
  не проводится и границу не задерживает (Редакция 10); двухсеансовый вариант (отмена именно между выбором `d` и
  загрузкой) — в прогоне на копии вместе с проверкой порядка блокировок (Ф1.3 п. 4). Остановка на ошибке — ручная
  проверка (ошибка записи внутри транзакции сценария портит его транзакцию).
- `ПереработкаВПоследовательности` — передача и поступление из переработки с услугой: пересчёт → долг перед
  переработчиком тот же, стоимость продукции пересчитана.

| `КорректировкаДолга` | не пишет (как сейчас) | не пишет |

Прибыль хранится только у исторических записей `Продажи`; новые записи её не заполняют. Формула одна —
`Прибыль = Выручка − Себестоимость − ДопРасходы`, где `Себестоимость` = Σ `СебестоимостьПродаж.Сумма` при `ДополнительныйРасход` = Ложь,
`ДопРасходы` = Σ при Истина. В модулях — одна функция `РегистрыНакопления.СебестоимостьПродаж
.ТекстПродажССебестоимостью()`: текст запроса во временную таблицу `ВТПродажиССебестоимостью` (все измерения
`Продажи` кроме `Партия` + `Партия` из `СебестоимостьПродаж`, ресурсы Количество, Выручка, НДС, Себестоимость,
ДопРасходы, Прибыль) с параметрами `&НачалоПериода`, `&КонецПериода` и условием отбора; ей пользуются `ТаблицаПоказателейПродаж`,
план рентабельности, `Убытки`, `Дашборд`, `ABCАнализПродаж.ObjectModule`, форма реализации, тесты. Схемы СКД — тот же
текст в наборе данных (функцию СКД не вызывает): формула в каждой ветке объединения одна и та же, проверка —

### Ф2.3 Возврат от покупателя

Алгоритм `СформироватьОприходованиеПоРеализации` не меняется, меняется источник:

1. **Блокировка** (Редакция 17): существующий упорядоченный механизм `НалоговыеДокументыНаОснованиях
   .ЗаблокироватьОснования(…, ПолныйНабор = Истина)` — обычные основания раньше налоговых документов. При проведении
   возврата он уже вызывается из `ПроверитьДокументПоОснованию` для любой реализации (`ЭтоВидДокументаНаОснованиях`
   проверяет тип ссылки). Добавляется: при отмене проведения и при записи проведённого возврата со сменой основания —
   тот же вызов по массиву {прежнее основание из базы, новое}, одним вызовом (порядок задаёт механизм, а не вызывающий).
   Сериализует возвраты одного основания между собой и с перепроведением основания и налогового документа.
   Двухсеансовая проверка на копии: возврат по налоговому документу T одновременно с пересчётом его основания S —
   нет взаимоблокировки, партии возврата согласованы.
2. **Источник** — записи `СебестоимостьПродаж` основания: обычная реализация — `Регистратор = Основание`; налоговый
   документ — его белые записи (`Регистратор = Основание`, УУ = Ложь), только записи с `Списание` = Истина. Строки партий
   (`ДополнительныйРасход` = Ложь) → таблица партий
   (`МестоХранения` = `СкладОтгрузки`, `Номенклатура` = `НоменклатураПартии`, характеристика, серия, партия,
   `ДатаПартии`, количество, сумма, НДС); строки допрасходов (`ДополнительныйРасход` = Истина) → таблица допрасходов
   (тот же ключ + статья, пустая — как есть). **Редакция 18 — несколько оснований:** записи разных отгрузок с
   одинаковым физическим ключом сворачиваются, как сейчас (`СформироватьОприходованиеПоРеализации`:242), —
   распределение возврата по партиям и допрасходам и вычитание прежних возвратов идут по свёрнутому ключу, движения
   склада те же, что сейчас. Происхождение сохраняется отдельной **раскладкой результата**: каждая восстановленная часть
   (партия или допрасход) делится по записям-источникам своего свёрнутого ключа в порядке момента `ДокументОтгрузки`,
   затем `НомерСтроки`: количество — в пределах невозвращённого остатка записи (её количество минус возвращённое по тем
   же `ДокументОтгрузки` + `КлючСтрокиОтгрузки` прежними возвратами), сумма и НДС — пропорционально, последней части —
   остаток; Σ раскладки = части точно. Записи `СебестоимостьПродаж` возврата пишутся по раскладке — с `ДокументОтгрузки`
   и `КлючСтрокиОтгрузки` записи-источника. **Допрасходы** (количества у них нет; Редакция 22 заменяет варианты
   Редакций 19 и 21): сумма допрасхода **знаковая** (уценка пишет отрицательную, `ДополнительныеРасходы/ManagerModule`:116).
   Движение возврата по свёрнутому ключу (физический ключ + статья) уже равно `R × Сумма / СуммаПартии`, где R — Σ
   невозвращённых остатков источников ключа со знаком (`РассчитатьСуммуСписанияДополнительныхРасходов`). Раскладка той же
   пропорцией: точная доля источника i = `Rᵢ × A / R`, где Rᵢ — невозвращённый остаток источника со знаком (его сумма
   минус возвращённое по нему прежними возвратами), A — движение возврата. Копейки (Редакции 23–24): каждая точная доля
   усекается к нулю до копейки; разница D = A − Σ усечённых — знаковая и равна сумме знаковых дробных частей. D > 0 —
   по копейке добавляется D источникам с **положительной** долей в порядке убывания дробной части; D < 0 — по копейке
   вычитается |D| источникам с **отрицательной** долей в порядке убывания модуля дробной части; при равенстве — порядок
   момента `ДокументОтгрузки`, затем `НомерСтроки`. Таких источников хватает всегда (D по модулю не больше суммы дробных
   частей своего знака, каждая < копейки), часть каждого источника становится округлением его точной доли от нуля, а
   так как 0 ≤ A/R ≤ 1 и Rᵢ в копейках, |часть| ≤ |Rᵢ| и знак = знаку Rᵢ. НДС — тем же правилом отдельно по
   невозвращённому НДС. Источники с уже возвращённым количеством участвуют (их Rᵢ ≠ 0, пока допрасход
   не сторнирован); при последнем возврате ключа A = R и каждая часть = Rᵢ — сторно полное, знак сохраняется; R = 0 →
   A = 0, записи нет. Раскладка не зависит от раскладки количества; Σ = A точно. Часть партии с нулевой суммой раскладывается по количеству так же; допрасход при нулевой стоимости
   партии — по количеству её раскладки. Тесты: первый и второй частичные возвраты по двум основаниям с допрасходом
   пустой статьи и с нулевой стоимостью партии; Редакция 21 — два последовательных возврата, допрасходы источников 100 и 0:
   после каждого возврата раскладка = движениям склада, после второго допрасход сторнирован полностью; Редакция 22 —
   «уценка → продажа → два частичных возврата» (отрицательный допрасход), то же — исторический случай в фикстуре
   обновления и повторный перенос. Порядок —
   `НомерСтроки` записей (= порядок записей списания). Отбор «отгрузка не позже возврата» — по `ДокументОтгрузки`
   (в фазе 2 всегда выполнен, механизм — для фазы 3).
3. **Прежние возвраты вычитаются для любого основания** (Редакция 7): записи `СебестоимостьПродаж` проведённых
   возвратов того же основания **с моментом строго раньше текущего** (Редакция 17: более поздний возврат при
   восстановлении последовательности ещё не пересчитан и не должен влиять на ранний), с обратным знаком, по ключам партии
   и допрасхода (`ВычестьПрежниеВозвраты` переписывается на новый регистр). **Редакция 27 — внутри документа:** уменьшение
   количества, суммы и НДС использованной партии и остатка допрасхода после каждой строки возврата (сейчас только
   `НаОснованиях`, `СформироватьОприходованиеПоРеализации`:263, 285) распространяется на все основания: две строки
   одного физического ключа не восстанавливают одну партию дважды; раскладка происхождения учитывает части, уже
   распределённые этим же возвратом, наравне с прежними возвратами. Записи с `Списание` = Ложь (услуги, поправки, ручные) не участвуют.
   Хвост пересчитывается последовательностью: возврат в составе `Основная`, его проведение, перепроведение со сменой
   даты и отмена проведения сдвигают границу назад (платформа, `Move`), более поздние возвраты того же основания
   перепроводятся в своих шагах. Контроль «возвращено не больше проданного» — отдельно, по количествам всех возвратов
   (`ПроверкаСоответствияВозвратовРеализации`, как сейчас). Тест: два возврата, поступление задним числом дешевле,
   пересчёт — у второго возврата партии и суммы те же, что при проведении с нуля в том же порядке; промежуточное
   списание возвращённого товара пересчитано. Сейчас это делается только по налоговому документу;
   по обычной реализации второй частичный возврат больше не восстанавливает уже восстановленную партию — исправление,
   в отчёт владельцу.
4. **Запись**: приход `ТоварыВНаличии`/`ДополнительныеРасходы` — как сейчас; на каждую восстановленную часть —
   запись `СебестоимостьПродаж` с измерениями и реквизитами записи-источника, знаком минус, периодом и операцией
   возврата. Приход партией самого возврата (нехватка, комплект) в `СебестоимостьПродаж` не пишется — так же, как сейчас
   его себестоимость не сторнируется в `Продажи`.

5. **Компенсация поправок** (Редакция 24). Поправки переноса — разница между себестоимостью `Продажи` и физической
   стоимостью — физическим возвратом не гасятся. Возврат, после которого возвращённое количество ключа (номенклатура,
   характеристика) основания равно проданному (**завершающий** — считается по возвратам с моментом строго раньше и
   текущему), пишет нефизическую запись `Поправка` = Истина, `Списание` = Ложь, отдельно стоимость и допрасходы: минус Σ
   записей `Поправка` этого ключа у основания и у его возвратов строго раньше. Тогда после полного возврата себестоимость
   основания с возвратами = 0 при любой смеси старых и новых возвратов. Запись — функция проведения: перепроведение
   даёт то же, отмена завершающего возврата снимает компенсацию вместе с его движениями, восстановление
   последовательности пересчитывает её в своём шаге (возврат в составе `Основная`). Услуги и ручные записи
   (`Поправка` = Ложь) компенсацией не затрагиваются — их себестоимость возврат не сторнирует и сейчас.

**Эквивалентность** (тест `ВозвратИзСебестоимостиПродаж`): эталон — реализация с двумя партиями, допрасходом и
серией + первый возврат части: записи прихода `ТоварыВНаличии`/`ДополнительныеРасходы` возврата, проведённого на
сборке 2.0.16.120, зафиксированы в тесте числами (партии, суммы, НДС, склад допрасхода); на 2.0.16.121 — те же.
Для старой реализации (до переноса) то же доказывает перенос: источник возврата — перенесённые записи, построенные из
тех же записей списания (Ф2.6), сверка «партии и суммы источника = расход `ТоварыВНаличии` + `ДополнительныеРасходы`
основания» входит в сверку обработчика.

### Ф2.4 Замороженные основания (TECHDEBT фазы 1)

Заморозка сделана потому, что возвраты по налоговому документу прочитали партии основания, а перепроведение основания
их меняло. После фазы 2 возврат читает партии из `СебестоимостьПродаж` налогового документа, а тот строится из
`СебестоимостьПродаж` оснований. Цепочка «основание → налоговый документ → возврат» — вся в последовательности
`Основная` (реализация и возврат в составе), и пересчёт проходит её по порядку моментов: основание перепроводится,
покрывающий документ перепроводится в той же транзакции (`ПерепровестиПокрывающиеДокументы`, строки и реквизиты не
менялись — `ТекстЗапретаПриЗависимыхРасчетах` пропускает), возврат перепроводится своим шагом и читает свежие партии.
Решение:
- **продажная сторона** — запрет снимается **только в режиме пересчёта** (`РаботаСДокументами.ПересчетСтоимости`):
  ветка «есть зависимые расчёты» `ПричинаЗапретаИзмененияОснования` пропускается для реализации в этом режиме;
  `ОснованиеЗаморожено` для реализаций возвращает Ложь; прежние отметки `СтоимостьЗаморожена` снимаются механизмом фазы 1
  (перепроверка отметок → граница раньше документа → успешное перепроведение снимает отметку). Ручное перепроведение
  основания пользователем по-прежнему запрещено: пользователь не перепроводит возвраты следом.
- Остановка пересчёта между основанием и возвратом (ошибка документа между ними) оставляет приход возврата по прежним
  партиям до следующего прогона — тот же класс временной несогласованности, что у любой цепочки документов в пересчёте;
  показатель «актуальна» в это время ложь.
- **закупочная сторона** (поступление, покрытое налоговым документом с возвратами поставщику) — **остаётся заморожена**:
  фаза 2 её не касается, партия поступления — сам документ, перевод — вместе с фазой 3 (партия = ордер). Запись в
  TECHDEBT переписывается на закупочную сторону.
- Тест: «поступление → реализация → налоговая реализация на основаниях → возврат по ней → поступление задним числом
  дешевле → пересчёт» — основание перепроведено, себестоимость налогового документа и возврата пересчитана, отметки
  нет, остатки партий сходятся.

### Ф2.5 Последовательность

`СебестоимостьПродаж` в `registerRecords` `Основная` **не входит**: от него не рассчитывается стоимость других
документов (кроме возврата, который сам в составе и читает основание, а не остатки). Пересчёт переписывает регистр
естественно — перепроведением реализации и возврата. Тест «повторный пересчёт итогов не меняет» (`ВыпускВПоследовательности`)
дополняется сравнением наборов `СебестоимостьПродаж` реализации и возврата. Попутно (TECHDEBT фазы 1)
`НалоговаяНакладная` выводится из состава `Основная` (движений стоимости не пишет с 2026-09-28) — тест
`ПоследовательностьСостав` правится.

### Ф2.6 Перенос истории (обработчик 2.0.16.121, монопольно)

`ОбновлениеПрограммыОбработчики.ПеренестиСебестоимостьПродаж`, регистрация — в новой группе
`ДобавитьОбработчикиСебестоимостиПродаж(Обработчики, РежимМонопольно)` из `ДобавитьОбработчикиРазделов`. Один проход
(замер Ф2.0). Алгоритм по регистраторам `Продажи` (кроме налоговых документов на основаниях — вторым проходом):

1. **Цель** — записи `Продажи` регистратора, сгруппированные по **Периоду, Активности** и всем измерениям (Редакция 26:
   у `КорректировкаРегистров` период и активность записей редактируются вручную — `СоздатьМассивПолейРегистра`):
   `Себестоимость`, `ДополнительныеРасходы`. Записи `СебестоимостьПродаж` наследуют период и активность своей цели;
   ручные записи `КорректировкаРегистров` переносятся построчно (своя запись на каждую строку, без свёртки).
2. **Детализация** — записи того же регистратора: реализация — расход `ТоварыВНаличии` и `ДополнительныеРасходы`;
   возврат — приход тех же регистров с партией не самого возврата; ключ сопоставления — (номенклатура записи `Продажи` =
   комплект записи списания или её номенклатура, характеристика, партия).
3. **Детализация переносится как есть, разница — поправкой** (Редакция 17). Записи партий и допрасходов — ровно
   фактические движения: количество, `Сумма`, `СуммаНДС`, серия, партия, склад, дата партии записи списания, статья
   допрасхода как есть, в том числе пустая (возврат — записи прихода, со знаком минус). У возврата
   `Продажи.Себестоимость` считалась пропорционально количеству по записи `Продажи`, свёрнутой без серии
   (`УменьшитьПрибыльПоВозврату`), а склад восстановил стоимость конкретной серии: суммы могут разойтись. Разница ключа
   (Σ `Продажи` − Σ детализации), отдельно себестоимость и допрасходы, пишется **записью поправки**: `Поправка` = Истина,
   `Списание` = Ложь, количество 0, измерения записи `Продажи`, `НоменклатураПартии` = номенклатура, серия пуста;
   у разницы допрасходов — `ДополнительныйРасход` = Истина, статья последней записи допрасходов ключа (без них — пустая).
   Записи поправки входят в маржу (историческая маржа сохраняется), но **исключены из источника партий возврата и из
   вычитания прежних возвратов** (Ф2.3) — возврат после обновления восстанавливает фактически списанное. Нет
   детализации вовсе (услуги, `КорректировкаРегистров`, ключ без записей списания): одна запись партии записи `Продажи`
   (`НоменклатураПартии` = номенклатура, серия пуста, `Списание` = Ложь — у услуг это и есть их себестоимость, но не партия) и, если
   допрасходы не 0, одна запись с `ДополнительныйРасход` = Истина и пустой статьёй (Редакция 18: признак, а не статья,
   отличает её от партии). Допрасходы в `Продажи` всегда строились из записей `ДополнительныеРасходы` того же документа —
   без детализации они бывают только у `КорректировкаРегистров` (возврат её не читает); у клиентов таких записей 0 (Ф2.0).
4. **Порядок проходов** (Редакция 19): (а) обычные реализации; (б) налоговые документы на основаниях — той же функцией,
   что при проведении (Ф2.2), из уже перенесённых записей оснований; (в) возвраты — **в порядке моментов**: детализация —
   фактические движения прихода возврата (п. 3), а `ДокументОтгрузки`/`КлючСтрокиОтгрузки` восстанавливаются той же
   раскладкой, что при проведении (Ф2.3 п. 2), по уже перенесённым записям основания и уже перенесённым прежним
   возвратам; **Редакция 20:** склад прихода возврата (`Стр.МестоХранения` — склад возврата) не равен складу
   списания и в ключ сопоставления не входит: приход товара сопоставляется с записями основания по номенклатуре,
   характеристике, серии, партии и дате партии; несколько складов-источников — раскладка по их невозвращённым остаткам в
   порядке момента `ДокументОтгрузки`, затем `НомерСтроки`; `СкладОтгрузки` записи возврата — склад найденного
   источника, допрасход — по своему складу (его возврат приходует на склад записи основания, как сейчас). Фактические
   движения склада возврата не меняются; (г) `КорректировкаРегистров` и прочие. **Предварительная проверка** (Редакция 25, до записи чего-либо): по каждому основанию и
   физическому источнику (номенклатура, характеристика, серия, партия, дата партии) Σ количеств прихода исторических
   возвратов ≤ отгруженному. Превышение возможно в старых данных: обычная реализация не вычитала прежние возвраты (Ф2.0),
   и повторный возврат мог восстановить ту же партию дважды. Такая цепочка не переносится молча: журнал (`Ошибка`) с
   перечнем оснований, возвратов и источников и **исключение** — версия не поднимается, обновление повторится после
   исправления истории владельцем (отмена или перепроведение лишнего возврата на прежней версии с проверкой
   последующих складских движений; инструкция — в `docs/RELEASING.md`, «Перенос себестоимости продаж»). По замеру Ф2.0 у
   клиентов возвратов нет — проверка проходит. Тест «исторический возврат → обновление →
   второй возврат»; Редакция 20 — «продажа двух партий со склада А → исторический возврат первой на склад Б → перенос →
   второй возврат»: второй восстанавливает P2, первый остаётся физическим возвратом (`Списание` = Истина, `СкладОтгрузки` = А).
5. **Идемпотентность**: набор `СебестоимостьПродаж` регистратора пишется замещением (`ОбменДанными.Загрузка`, отбор по
   регистратору) — повторный запуск даёт те же записи. Регистраторы, у которых записи уже есть и сходятся, не трогаются.
6. **Сверка — по регистраторам**, а внутри — по периоду, активности и измерениям `Продажи` (Редакция 26; активные
   обороты по месяцам и ключам равны), после записи: Σ `Продажи.Себестоимость` = Σ `Сумма` при `ДополнительныйРасход` = Ложь
   и Σ `Продажи.ДополнительныеРасходы` = Σ `Сумма` при Истина, с точностью до копейки. По построению равенство точное:
   расхождение — ошибка обработчика → журнал (`Ошибка`) с перечнем и **исключение**: версия не поднимается, обновление
   повторится (как обработчик 2.0.16.76). Отдельно, без остановки — журнал `Предупреждение` и строка в отчёте владельцу:
   число записей без детализации (п. 3), число записей `Продажи`, где хранимая `ВаловаяПрибыль` ≠ формуле (отчёты маржи
   после переноса покажут формулу), сумма такой разницы.
7. **`Продажи` не переписываются**: старые записи сохраняют `Партия` и ресурсы себестоимости до их удаления (ниже);
   отчёты их больше не читают.

и итоги — на копиях `*-f2` с новой конфигурацией, плюс копия `build/ib-kp` после полного `ТестыДокументов`. Маржа

### Ф2.9 Права

`Rights.rights` (чтение `Продажи` сейчас, полей-запретов на `Себестоимость` нет ни у кого, кроме `ЛичныйКабинет`):
`Казначей`, `БухгалтерПоЗарплате`, `Логист`, `МенеджерПоПродажам`, `Оператор`, `Кладовщик`,
`МенеджерПоЗакупкам`, `MobileClient`, `PDV` — **чтение** `СебестоимостьПродаж`; `Администратор`, `Руководитель` —
`setForNewObjects`. **`ЛичныйКабинет` — без чтения** (партнёр видит продажи, себестоимость ему скрыта — поле
`Себестоимость` у роли уже без просмотра). Запись не выдаётся никому: реализация и возврат проводятся в
привилегированном режиме (`ОбработкаПроведения`:1), обработчик — монопольно. **Проверка до сдачи**: прогон на копии под
`Кладовщик` и `PDV` — проведение, перепроведение (у реализации `AutoDelete`: платформа удаляет прежние наборы до
`ОбработкаПроведения`) и отмена проведения реализации и возврата. Если платформа требует права изменения на удаление
наборов — роли, проводящие эти документы, получают «Изменение» (без интерактивных прав), как у `Продажи`, и это
пишется в отчёт. **Редакция 19:** форма реализации доступна `ЛичныйКабинет` и при открытии считает финансовый результат
(`РаботаСДокументамиВызовСервера.ЗаполнитьФинРезультат`, без привилегий) — перед запросом проверяется
`ПравоДоступа("Чтение", Метаданные.РегистрыНакопления.СебестоимостьПродаж)`; права нет — запрос не выполняется,
поля себестоимости, прибыли и наценки скрыты; привилегированным чтением запрет не обходится. Так же — прочие места,
доступные ролям без чтения (полный поиск читателей регистра при реализации). Тест: проверка права в функции
(эмуляция — параметр роли) + ручная проверка открытия реализации пользователем `ЛичныйКабинет` на копии. Отчёты маржи
под ролью без чтения регистра (`ЛичныйКабинет`) не открываются — как сейчас без чтения
`Продажи`; тест `ПраваРолей` расширяется (чтение у перечисленных ролей, нет у `ЛичныйКабинет`, изменения нет ни у кого
кроме полноправных).

### Ф2.10 Блокировки

Единый порядок (раздел «Блокировки»): `Справочник.МестаХранения` → `ТоварыВНаличии` → `ДополнительныеРасходы` →
`ТоварыНаСкладах` → `ТоварыКОформлению` → `СебестоимостьПродаж`. В фазе 2 регистр пишется только набором своего
регистратора (неявная блокировка записи), а читается возвратом (записи основания и прежних возвратов) — согласованность
чтения даёт блокировка ссылки основания, взятая **до** складских блокировок возврата (Ф2.3 п. 1; тот же порядок
«основания первыми», что у налоговых документов, план С2). Явная блокировка самого регистра появляется в фазе 3 (ближний
пересчёт от расходного ордера, последней).

### Ф2.11 Тесты (`ТестыДокументов`, реестр `TESTS.xlsx`)

- `СебестоимостьПродажРеализации` — реализация с двумя партиями, серией и допрасходом: Σ регистра = расход
  `ТоварыВНаличии` + `ДополнительныеРасходы`, построчно; комплект — `НоменклатураПартии` составляющих, `Номенклатура` =
  комплект; услуга — закупочная цена, партия пустая; `Продажи` — одна запись на товар, ресурсы себестоимости 0.
- `ВозвратИзСебестоимостиПродаж` — эталон Ф2.3 (числа зафиксированы); второй частичный возврат берёт оставшиеся партии;
  комплект — приход комплекта партией возврата, `Продажи` и `СебестоимостьПродаж` не сторнируются (как сейчас).
- `СебестоимостьНалоговогоНаОснованиях` — черная и белая стороны, допрасходы оснований, возврат по налоговому документу:
  партии и допрасходы = прежнему поведению; Ф2.4 — пересчёт через основание с возвратом. Редакция 18: два основания с
  одинаковыми партией, серией, складом и статьёй, два частичных возврата — движения склада = эталону 2.0.16.120,
  раскладка `СебестоимостьПродаж` по `ДокументОтгрузки` не превышает отгруженного по каждому основанию и в сумме равна
  движениям.
- `ВыручкаВозвратаПослеОбновления` (Редакция 23) — старая продажа двух партий разной стоимости (выручка разнесена по
  себестоимости), частичный возврат до обновления (сторно по партии) — в фикстуре; завершающий возврат после обновления
  и его повторное проведение, затем пересчёт последовательности: итоговые количество, выручка, НДС, себестоимость
  основания с возвратами — 0; то же — двумя новыми возвратами в `ТестыДокументов`.
- `РаскладкаКопеек` (Редакции 23–24) — четыре малые положительные суммы, смешанные знаки, зеркальный случай с
  отрицательным A, отдельно сумма и НДС: Σ раскладки = движению, ни одна часть не меняет знак и не превышает по модулю
  остаток своего источника.
- `ВозвратДвумяСтроками` (Редакция 27) — обычная реализация двумя партиями разной стоимости, полный возврат двумя
  строками одного товара, перепроведение и восстановление последовательности: каждая партия восстановлена ровно один
  раз, себестоимость основания с возвратом = 0.
- `ПереносРучнойКорректировки` (Редакция 26) — в фикстуре: `КорректировкаРегистров` с записями `Продажи` одинаковых
  измерений в разных месяцах и неактивной записью → после обновления и повторного переноса месячная маржа та же,
  неактивная запись не входит в обороты.
- `ИзлишекИсторическихВозвратов` (Редакция 25) — отдельная копия-фикстура: продажа трёх единиц из двух партий, два
  старых повторных возврата первой партии → обновление останавливается, в журнале перечень; версия не поднята. Основная
  фикстура (без излишка): тот же сценарий с одним старым возвратом и новым завершающим — остатки источников и итоговая
  себестоимость основания с возвратами = 0. Функция предварительной проверки — ещё и сценарием `ТестыДокументов`.
- `КомпенсацияПоправок` (Редакция 24) — в фикстуре: продажа двух серий разной стоимости, старый частичный возврат
  (поправка ≠ 0), обновление, завершающий новый возврат → себестоимость основания с возвратами 0; перепроведение
  завершающего — то же; отмена — компенсация снята; восстановление последовательности — то же.
- `ВозвратУслуги` (Редакция 19) — реализация товара и услуги, перенос, возврат: склад приходует только товар (как
  сейчас), услуга источником партий не становится.
- `ДопрасходБезСтатьи` (Редакция 18) — документ допрасходов с пустой статьёй строки → реализация → перенос истории
  (сверка сходится) → возврат восстанавливает допрасход в `ДополнительныеРасходы`, а не в стоимость партии.
- `ПереносСебестоимостиПродаж` — исторические записи строятся прямой записью наборов `Продажи` (как до фазы 2) на
  реализации, возврате, налоговом документе, услуге, `КорректировкаРегистров`; обработчик → сверка по регистраторам
  равна, маржа функции Ф2.2 = Σ хранимой `ВаловаяПрибыль`; второй вызов — те же записи. Редакция 17: реализация двух
  серий разной стоимости, исторический возврат одной из них (`Продажи` — пропорция, склад — стоимость серии) →
  перенос даёт поправку = разнице; следующий возврат после обновления восстанавливает оставшуюся серию по её стоимости.
- `МаржаОтчетов` — `ВедомостьПоПродажам` (СКД) и функция Ф2.2 на одном периоде дают одну прибыль.
- `ВыпускВПоследовательности` — + сравнение наборов `СебестоимостьПродаж`; `ПоследовательностьСостав` — без
  `НалоговаяНакладная`; `ПраваРолей` — Ф2.9.
- Правка существующих проверок `ТестыДокументов`, читающих `Продажи.Себестоимость` (7 мест), — на функцию Ф2.2.
- Ручная проверка владельца (`docs/TESTING.md`): маржа `ВедомостьПоПродажам` до и после обновления на копии базы,
  возврат по старой реализации, отчёты под ролью без себестоимости.

### Ф2.13 Уточнения при реализации (2026-10-30)

- **Активность — у набора, не у записи**: платформа отказывает в записи набора регистра накопления с разной активностью
  записей («La actividad de registros no coincide»). Неактивная запись `КорректировкаРегистров` бывает только целым
  набором — перенос сохраняет активность цели; тест и фикстура держат неактивный набор отдельным документом.
- **Пустая статья допрасхода** при интерактивном вводе невозможна (проверка заполнения шапки
  `ПоступлениеДополнительныхРасходов`), но встречается в загруженных данных — фикстура проводит такой документ без
  проверки заполнения.
- **Услуга с закупочной ценой** машинным тестом не проверена (цена карточки пишется датой «сейчас», документы
  сценариев раньше) — в TECHDEBT; услуга без цены себестоимости не даёт, перенос услуги — запись без детализации.
- **Блокировка оснований возврата** — `НалоговыеДокументыНаОснованиях.ЗаблокироватьОснованияВозврата` (проведение и
  отмена, прежнее и новое основание одним вызовом).

### Ф3.2 Пары оформления

`РегистрыНакопления.ТоварыКОформлению.ПарыОформления(Документы)` — одна функция для ордеров, реализации, ближнего
пересчёта и тестов. Пара — запись **расхода** регистра: (`Источник`, `КлючСтрокиИсточника`) ↔ (`Регистратор`,
`КодСтрокиРегистратора`), количество q; отбор — `Источник В (Документы) ИЛИ Регистратор В (Документы)`, `Регистратор
<> Источник`, активные. Результат: Источник, КлючСтрокиИсточника, Регистратор, КодСтрокиРегистратора, Количество,
МоментРегистратора (момент времени документа-регистратора), упорядочен по МоментРегистратора, КодСтрокиРегистратора.

- **Запись пар.** Оформляющий документ пишет расход **по строке** (сейчас — свёрнуто по ключу ордера):
  `КодСтрокиРегистратора` = `КодСтроки` строки документа. Приход ордера — по строке ордера,
  `КодСтрокиРегистратора` = 0.
- **Старые записи** (`КодСтрокиРегистратора` = 0 у расхода): строка регистратора восстанавливается по его ТЧ
  (`Ордер` = Источник, `КлючСтрокиОрдера` = ключ); несколько таких строк — пара на каждую с её количеством (сумма
  равна записи — так её и писала свёртка); строки нет — пара с кодом 0 (стоимости не даёт, Ф3.3). Так и восстановление
  последовательности, и ручное перепроведение не зависят от того, перепроведён ли уже оформляющий документ.
- `РасходОформления`, `ДобавитьСоставляющиеОформления`, `ДоступныйОстатокСоставляющих`, `РаспределитьПоСтрокам`,
  `ЗаменитьКомплектыПоОрдерам` удаляются вместе с `Составляющая`: реализация больше не списывает партии, составляющие
  комплекта списывает расходный ордер по снимку `ТЧФизическийСостав`. Остаток к оформлению — по коммерческой строке.

### Ф3.3 Приходный ордер

Проведение (`ОрдераСклада.ПровестиОрдер`):

1. `ТоварыВНаличии` приход по строке (строка = физическая строка: у приходного ордера комплект приходуется комплектом,
   как поступлением): `Партия` = ордер, `ДатаПартии` = дата ордера, `КодСтроки` = код строки, серия строки,
   количество строки, **`Сумма`/`СуммаНДС` = стоимость строки** (ниже).
2. `ДополнительныеРасходы` приход по строке и статье — допрасходы её пар (ниже).
3. `ТоварыКОформлению` приход (как сейчас, без составляющих); `ЗаказыПоставщикам`, `ПотребностиПроизводства` — как
   сейчас.
4. `ТоварыНаСкладах` пишет **зеркало** набора `ТоварыВНаличии`; `СформироватьФизическиеДвижения` удаляется. Ордер
   становится регистратором, «движения которого ведёт `ТоварыВНаличии`» — его набор физики защищён
   `ПерестроитьНаборНеЗеркала`, инвариант `РасхожденияСТоварамиВНаличии` его сверяет.

**Стоимость строки k** = Σ по парам (k ↔ строка r поступления) стоимости строки r поступления: строки r берутся из
`СерииИРазмещение.ОбъединитьТоварыССериями(поступление)` с отбором `КодСтроки = r` (та же таблица и тот же пересчёт в
основную валюту, по которым поступление сейчас пишет свою партию: `Сумма` = сумма с НДС, `СуммаНДС`). Строка
поступления по ордеру всегда целиком оформляет одну строку ордера (q = количество строки r, контроль
`ТоварыКОформлению`), поэтому доля не нужна и округления нет. Неоформленная часть строки — 0 (В2): запись одна на
строку, её средняя цена до полного оформления занижена — это и есть «стоимость не подтверждена» (Ф3.10).

**Допрасходы пар.** Допрасходы поступления (`ТЧДополнительныеРасходы`) распределяются по его строкам той же функцией,
что сейчас пишет их на его партии (`ДополнительныеРасходы.РаспределитьПоПозициям`, база — сумма строки, нулевая база —
количество, Ф3.9), но **в таблицу**, а не в движения: новая функция `РаспределениеПоСтрокам(ДокОбъект, Товары,
Допрасходы)` → (КодСтроки, Номенклатура, Характеристика, Серия, СтатьяДДС, Сумма, СуммаНДС); `РаспределитьПоПозициям`
пишет движения через неё (одна формула). Приходный ордер берёт строки r своих пар.

**Функция одна**: `ОрдераСклада.СтоимостныеЗаписиПриходныхОрдеров(Ордера)` → записи `ТоварыВНаличии` и
`ДополнительныеРасходы` каждого ордера в виде таблиц, ровно как их пишет проведение. Ею пользуются проведение ордера,
ближний пересчёт поступления (Ф3.7) и тест-инвариант «записанное = рассчитанное».

### Ф3.4 Поступление на ордерном складе

- Строки — только по ордеру (Ф3 — схема «ордер первый»; проверка `ОрдераСклада.ПроверитьОформление` не меняется).
- `ТоварыВНаличии`/`ДополнительныеРасходы`: записи на складе, ордерном на дату записи, **не пишутся** (тот же критерий,
  что `ТоварыНаСкладах.ИсключитьЗаписиОрдерногоСклада`); подчинённый неордерный склад — как сейчас (поступление его
  приходует партией-поступлением). Взаиморасчёты, `Убытки`, цены поставщиков, `ЦеныНоменклатуры` — как сейчас;
  `ЗаказыПоставщикам`/`ПотребностиПроизводства` на ордерном складе не двигаются (как сейчас — их двигает ордер).
- `ТоварыКОформлению` — расход по строке (Ф3.2).
- После `Движения.Записать()` и контроля `ТоварыКОформлению` — **ближний пересчёт приходных ордеров** (Ф3.7) по
  ордерам прежних и новых пар (`ДополнительныеСвойства.ОрдераДокумента`, уже берётся сейчас). Отмена проведения —
  тот же пересчёт после записи пустого набора `ТоварыКОформлению` (`ОтменитьОформлениеОрдеров`).
- Покрывающий налоговый документ на основаниях — как сейчас (`ПерепровестиПокрывающиеДокументы`): белый контур
  количеств поступления не меняется.

### Ф3.5 Расходный ордер

1. Автовыпуск — как сейчас (до своего расхода, на секунду раньше).
2. `ТоварыВНаличии`/`ДополнительныеРасходы` расход: `СписатьНоменклатуру` по физическим строкам
   (`ТоварыКОформлению.ФизическиеСтрокиОрдера` — комплект составляющими по снимку `ТЧФизическийСостав`); новый параметр
   **`ПоСтрокам`**: строки списания группируются и с кодом строки, `КодСтроки` попадает в записи `ТоварыВНаличии` и
   `ДополнительныеРасходы` (у прочих документов `ПоСтрокам = Ложь` — группировка и записи как сейчас, код 0);
   `Комплект` записи — комплект строки. **Нехватка партий — отказ** (Р1, существующий контроль партий; та же нехватка
   сейчас отказывает реализацией — запрет переезжает с реализации на ордер, новых запретов нет, правило владельца
   2026-10-09 о минусах не задето). Пункт TECHDEBT «расходный ордер не проверяет физический остаток» закрывается
   этим (остаток партий = остаток физики после фазы 3).
3. `ТоварыКОформлению` приход — по коммерческим строкам (без составляющих).
4. `ТоварыНаСкладах` — зеркало; `СформироватьФизическиеДвижения` удаляется.
5. После записи — **ближний пересчёт себестоимости реализаций** (Ф3.7) по строкам ордера (прежние и новые пары).
6. `ТЧФизическийСостав` — как сейчас (оформленные строки замороженного состава); в режиме пересчёта стоимости снимок не
   пересчитывается вовсе (Ф3.7).

### Ф3.6 Реализация на ордерном складе

- Строки — только по ордеру (как сейчас). `ТоварыВНаличии` **не пишет**; `Продажи` — выручка (как после фазы 2);
  взаиморасчёты — как сейчас; `ТоварыКОформлению` — расход по строке; автовыпуск не вызывает (как сейчас).
- **`СебестоимостьПродаж` по парам — распределение матрицей (Редакция 30).** Строка k расходного ордера O списана
  записями `ТоварыВНаличии` с `КодСтроки = k` (партии; у комплекта — по каждой составляющей c свои записи) в порядке
  списания; пары строки — реализации с количествами q_i в порядке (МоментРегистратора, КодСтрокиРегистратора). Для
  каждой физической позиции строки (сама номенклатура или составляющая c):
  1. **Количества столбцов**: оформленное количество позиции T_c = Окр(Σ записей c × Σq / Q_k) (разрядность
     количества) делится между парами пропорционально q_i наибольшими остатками (обобщённая
     `СебестоимостьПродаж.РаспределитьПропорционально(Базы, Итог, Разрядность)`, ничья — порядок пар). У некомплекта
     Σ записей = Q_k, и столбец пары равен q_i точно.
  2. **Матрица «записи × пары»** заполняется последовательно: пары по порядку забирают количество из записей по порядку
     списания (как FIFO), пока столбец пары не заполнен; сумма каждой строки матрицы ≤ количества записи, сумма каждого
     столбца = столбцу пары **точно**. Каждая клетка — кусок записи: партия, серия, дата партии, склад, количество.
  3. **Стоимость куска**: по каждой записи e её оформленная часть (Σ кусков) получает `Сумма`/`СуммаНДС` = e ×
     оформлено / количество e (вся запись — ровно e), и делится между кусками пропорционально их количествам
     наибольшими остатками. Допрасходы записи (`ДополнительныеРасходы` ордера той же строки, партии и серии, по статье)
     делятся между кусками той же партии так же.
  Итог: количество каждой реализации по каждой партии — целые куски физических записей; полный возврат всех реализаций
  строки восстанавливает ровно списанные партии; знак и предел каждой доли соблюдены. Записи `СебестоимостьПродаж`:
  измерения реализации, `Номенклатура` = номенклатура строки реализации (комплект), `НоменклатураПартии`, серия,
  партия, дата партии, склад записи — из куска; `ДокументОтгрузки` = O, `КлючСтрокиОтгрузки` = k; `Списание` = Истина.
  Неоформленная часть в себестоимость не попадает. **Семантика частичного оформления** (Редакция 31): по партиям — FIFO
  (раньше оформленная реализация получает раньше списанные партии), внутри записи — пропорционально; это заменяет
  «долю q/Q_k» Редакций 4 и 7 для количеств и стоимости партий (целевая сумма оформленной части Редакции 7 остаётся —
  по каждой записи). Пример теста: строка 10 списана партиями 6 по 10 и 4 по 20; реализация 4 — себестоимость 40,
  затем реализация 6 — 2 × 10 + 4 × 20 = 100; полный возврат первой восстанавливает 4 первой партии. Тесты: три партии × три реализации с полными возвратами — лишних
  партий возврата нет, количества и себестоимость сторнированы полностью; комплект двумя реализациями; знак и предел.
- Доля зависит от всех пар строки — поэтому себестоимость пишет **одна процедура по строкам ордеров**
  `СебестоимостьПродаж.ПересчитатьПоПарам(СтрокиОрдеров)` (Ф3.7) для всех реализаций этих строк, а не проведение
  реализации только для себя. Проведение реализации: `Движения.Записать()` пишет набор `СебестоимостьПродаж` без записей
  по парам (услуги, свои допрасходы — ниже), затем `ПересчитатьПоПарам` по строкам её прежних и новых пар дописывает
  записи по парам ей и пересчитывает соседей. Отмена проведения — то же после записи пустого набора `ТоварыКОформлению`.
- **Строка без пары** (возможна только в фазе 4) — записей нет; в отчётах маржи — признак «себестоимость не определена»
  (фаза 4, Ф3.18).
- **Свои допрасходы реализации** (`ТЧДополнительныеРасходы`; у клиентов не используются — `ДополнительныеРасходы` 0
  записей на обеих базах): на неордерном складе — как сейчас (приход и расход на списанные партии). На ордерном складе
  партий у реализации нет — допрасход пишется **только в `СебестоимостьПродаж`**: `ДополнительныйРасход` = Истина,
  статья, `Списание` = **Ложь** (физическим списанием склада не является; возврат его не восстанавливает — отличие от
  неордерного склада, в TECHDEBT), партия пустая, распределение по строкам товаров по сумме строки (нулевая база — по
  количеству, остаток — последней строке). Не зависит от пар — пересчёт по парам его не трогает.

### Ф3.6а Раздельный учёт на ордерном складе (Редакция 29)

- Признак `УУ` товарных движений ордеров — **Ложь**: у ордеров нет реквизита `УУ` (`НалоговыйУчет.ЗначениеУУ` → Ложь),
  как у выпуска, перемещения, требования. На ордерном складе партия — ордер, и «чёрная» партия поступления на нём больше
  не возникает: товарный признак `УУ` там не ведётся (белый товарный учёт — отдельный проект
  `docs/plans/belyi-tovarnyi-uchet.md`, где `ТоварыВНаличии` остаётся управленческим).
- **Налоговый документ на основаниях с основанием ордерного склада — отказ проведения** (основание — поступление или
  реализация на складе, ордерном на дату основания): его товарная переклассификация (`НалоговыеДокументыНаОснованиях.
  ПереклассифицироватьТовары`, `ЗаблокироватьТоварыОснований`) читает `ТоварыВНаличии` регистратора-основания, а у
  основания ордерного склада этих движений больше нет, переклассифицировать нечего и некуда. Проверка — в
  `НалоговыеДокументыНаОснованиях` рядом с прочими проверками оснований (Ф2-контур С2), текст ru/fr/en/es «основание на
  ордерном складе: налоговый документ на основаниях — после белого товарного учёта». **Замер**: Drissotex — раздельный
  учёт выключен, документов на основаниях 0; 2MZL — раздельный учёт есть, ордерных складов нет (опция выключена) —
  отказ никого не задевает. Тест — отказ проведения. Выручка и себестоимость продаж основания ордерного склада без
  налогового документа — как у прочих реализаций.
- Следствие для Ф3.7: у реализаций ордерного склада нет покрывающих налоговых документов — ближний пересчёт соседней
  реализации инвалидирует только её возвраты.

### Ф3.7 Ближний пересчёт

Две процедуры, обе — после `Движения.Записать()` документа, под его блокировками (Ф3.8), в привилегированном режиме:

| Процедура | Кто вызывает | Что пишет | Граница (только назад, `РаботаСДокументами.СдвинутьГраницуПоследовательностиНазад`) |
|---|---|---|---|
| `ОрдераСклада.ПересчитатьСтоимостьПриходныхОрдеров(Ордера, ДокОбъект)` | поступление (проведение, отмена) | наборы `ТоварыВНаличии` и `ДополнительныеРасходы` ордеров (запись набора с отбором по регистратору; зеркало физики пишет модуль набора — количества не меняются) | при изменении набора — на **момент самого раннего изменённого ордера** (обход берёт документы строго после: сам ордер не перепроводится, его потребители — да); плюс — строго раньше (`МоментДоДаты`) самого раннего проведённого `ПоступлениеДополнительныхРасходов` по этому поступлению (Ф3.9) |
| `СебестоимостьПродаж.ПересчитатьПоПарам(СтрокиОрдеров, ДокОбъект)` | расходный ордер, реализация (проведение, отмена) | в наборах `СебестоимостьПродаж` реализаций с парами на этих строках — **только записи с ключом (`ДокументОтгрузки`, `КлючСтрокиОтгрузки`) из переданных строк** (Редакция 31); набор читается целиком под блокировкой, прочие записи — других строк и других ордеров, услуги, свои допрасходы — сохраняются как есть | при изменении набора реализации, **отличной от проводимого документа**, — строго раньше самого раннего её проведённого возврата (Редакция 11), если он есть; у самой проводимой реализации сдвиг делает платформа (`Move`) |

- **Запись только при изменении** (Редакция 5): рассчитанный набор сравнивается с записанным (выгрузка, сортировка по
  ключевым полям, сравнение ресурсов и реквизитов); совпал — не пишется, граница не двигается. Поэтому повторное
  восстановление последовательности не возвращает границу назад.
- **Режим пересчёта стоимости** (обход последовательности, Ф1.2). Ордера — `AutoDelete`: платформа очищает все их
  наборы до проведения, поэтому в этом режиме ордер пишет **все** наборы (они — функция документа), но не выполняет
  проверок и побочных действий, зависящих от состояния базы: `ПроверитьЗащиту`, `ОбновитьФизическийСостав` (снимок как
  записан), `ЗапомнитьЗаказыДокумента`, `ПроверитьПришло`, `ОбновитьСтадииПослеПроведения`, контроль
  `ТоварыКОформлению` (набор тот же); автовыпуск в фоне и так не трогается. Нехватка партий у расходного ордера —
  ошибка шага, остановка (как у прочих документов). Поступление и реализация в обходе ведут себя как сейчас (12 прежних
  документов) — их ближний пересчёт обычно ничего не меняет: стоимость ордера — функция поступлений, а не порядка
  обхода; себестоимость реализации пересчитана перепроведением расходного ордера раньше неё.
- **Свой сдвиг границы в шаге обхода.** Если ближний пересчёт **в шаге** всё же изменил наборы документа раньше позиции
  (старые пары Drissotex, Ф3.2; поступление задним числом относительно своих ордеров невозможно — ордер не позже
  документа), он ставит признак в дополнительные свойства проводимого объекта, и шаг обхода (`ПроцедурыРегламентныхЗаданий.
  ШагПересчетаВТранзакции`) при «граница раньше позиции» **фиксирует шаг и продолжает с новой границы**, а не
  останавливается. Защита от зацикливания: тот же документ второй раз подряд сдвинул границу своим пересчётом — остановка
  с ошибкой в «Непроведённых документах». Повтор конечен: второй расчёт ордера по тем же поступлениям даёт тот же набор.
- **Удаление документа** (Редакция 31; `Удалить()` не вызывает отмену проведения, tiny1C bsl-024). Проведённые
  поступление и реализация с записями `ТоварыКОформлению` — **отказ** прямого удаления в `ПередУдалением` («сначала
  отмените проведение»; отмена выполняет ближний пересчёт), удаление после отмены — как сейчас. Проведённый
  неоформленный ордер (оформленный и сейчас не удаляется) — в `ПередУдаленииОрдера` граница строго раньше его даты
  (`МоментДоДаты`, только назад, как `КорректировкаРегистров` Ф1.1): его партии списаны потребителями. Тесты: прямое
  `Удалить()` проведённого поступления по ордеру — отказ; «отмена → удаление» — стоимость ордера и доли соседних
  реализаций пересчитаны; удаление проведённого ордера — граница раньше него.
- **Чужой документ.** Набор чужого регистратора пишется `РегистрыНакопления.X.СоздатьНаборЗаписей()` с отбором по
  регистратору, `Записать(Истина)`; дополнительные свойства проведения документа-владельца не нужны (`ТоварыВНаличии`:
  `ПередЗаписью`/`ПриЗаписи` набора — зеркало и инвариант склада станка работают по самому набору). Тест — записанное
  пересчётом = записанному перепроведением владельца (Ф3.17). Правило в tiny1C по итогам.

### Ф3.8 Блокировки

Единый порядок: `МестаХранения` → `ТоварыВНаличии` (+ `ТоварыНаСкладах`, `ДополнительныеРасходы` — одним элементом
`УправляемыеБлокировки.ТоварыВНаличии`) → взаиморасчёты, потребности, заказы (как сейчас) → `ТоварыКОформлению` →
`СебестоимостьПродаж` → `Последовательность.Основная` (сдвиг границы — исключительно, последним, как в Ф1.3).

| Документ | Что добавляется |
|---|---|
| Поступление | ближний пересчёт замещает **целые** наборы ордеров — поэтому позиции `ТоварыВНаличии` (с зеркалом `ТоварыНаСкладах` и `ДополнительныеРасходы` в том же элементе, P2-9 критика) = номенклатура строк поступления **и всех строк всех ордеров** прежних и новых пар, на складах поступления (прежнем и новом) и **складах этих ордеров**; ключи читаются до блокировки (ордера — из строк документа и записей `ТоварыКОформлению` регистратора, их строки — из ТЧ ордеров) и берутся одним объектом вместе с остальными, до взаиморасчётов и `ТоварыКОформлению`. **Снимок после блокировки** (Редакция 30): под всеми блокировками ордера пар, их склады и номенклатура строк перечитываются; новое значение вне захваченных ключей — отказ «ордер изменён, пока документ проводился, проведите ещё раз» (`ПроверитьСнимокПослеБлокировки`), без расширения блокировок после `ТоварыКОформлению`. Ордер, изменённый до нашей блокировки `ТоварыКОформлению`, дальше меняться не может — его проведение берёт ту же блокировку |
| Расходный ордер | как сейчас (номенклатура строк и составляющих прежней и новой версии, склад); после блокировки `ТоварыКОформлению` по себе — читаются реализации его пар (пары не меняются, пока держится блокировка), затем **вторым объектом** — исключительная блокировка `СебестоимостьПродаж` по `ДокументПродажи` в этих реализациях |
| Реализация на ордерном складе | **весь набор блокировок — в `ПередЗаписью`** (Редакция 33): у реализации `AutoDelete`, платформа удаляет прежние наборы (в том числе `СебестоимостьПродаж` и `ТоварыКОформлению`) до `ОбработкаПроведения` — неявные блокировки этих наборов иначе встали бы раньше явных и дали встречный путь с ближним пересчётом расходного ордера. Если реализация касается ордеров (ордера в строках или в прежних записях `ТоварыКОформлению`), в `ПередЗаписью` при проведении и отмене проведения берётся полный набор в общем порядке (склады, взаиморасчёты, потребности автовыпуска, `ТоварыКОформлению` по прежним и новым ордерам, затем вторым объектом `СебестоимостьПродаж` по `ДокументПродажи` — своя и соседние реализации, читаемые под блокировкой ордеров); контекст (ордера, соседи, контекст автовыпуска) — в `ДополнительныеСвойства`, `ОбработкаПроведения` пользуется им (повторный захват в той же транзакции не конфликтует). Складские ключи этого набора (Редакция 34) — **по прежней и новой версиям**: `ТоварыВНаличии` (с зеркалом и допрасходами) по номенклатуре строк и составляющих обеих версий на прежнем и новом складах, если хотя бы одна версия пишет или удаляет партии (неордерный склад на её дату) — переход реализации с ордерного склада на обычный и обратно перепроведением блокирует и удаляемые `AutoDelete` движения, и новое списание; обе версии на ордерном складе — `ТоварыВНаличии` не берётся. Реализация без ордеров в обеих версиях — как сейчас. На ордерном складе `ТоварыВНаличии` реализация не пишет; после блокировки `ТоварыКОформлению` по своим ордерам — реализации пар на тех же строках, вторым объектом — `СебестоимостьПродаж` по `ДокументПродажи` (своя и соседи). Снимок состава ордеров (`СнимокСоставаОрдеров`, `ПроверитьСнимокПослеБлокировки`, позиции составляющих) больше не нужен — удаляется |
| Возврат от покупателя | перед чтением источника (Ф3.11) — **разделяемая** блокировка `СебестоимостьПродаж` по `ДокументПродажи` = основание: последней из своих, после складских (порядок соблюдён); ближний пересчёт, переписывающий себестоимость основания, и чтение возврата сериализуются |

Читаемые наборы ордеров (`ТоварыВНаличии` ордера в `ПересчитатьПоПарам`) согласованы: ордер пишет их под своей
блокировкой `ТоварыКОформлению` по себе, читающий её держит. Пространство `РегистрНакопления.СебестоимостьПродаж` с
полем `ДокументПродажи` платформа принимает — проверено 2026-10-30 на копии (как и `…СебестоимостьПродаж.НаборЗаписей`
с полем `Регистратор`); выбран `ДокументПродажи`: им помечены и записи реализации, и записи её возвратов.

**Двухсеансовые проверки на копии** (две внешние обработки с файлом-барьером, как Ф1.3): (а) поступление по ордеру O и
расходный ордер, списывающий партию O, одновременно; (б) расходный ордер и возврат по реализации его пары; (в) две
реализации по одной строке расходного ордера; (г) два поступления по разным товарам одного многострочного приходного
ордера (Редакция 30); (е) переход реализации между ордерным и обычным складом перепроведением одновременно с обычной реализацией того же
товара (Редакция 34); (д) одновременное **перепроведение** существующих O и S с барьером перед автоочисткой S — и
когда S перепроводит восстановление последовательности: нет взаимоблокировки, записи себестоимости целы (Редакция 33). Нет взаимоблокировки, итоговые наборы = последовательному проведению.

### Ф3.9 Допрасходы

- **Нулевая база.** `РассчитатьСуммуСписанияДополнительныхРасходов` получает количества: сумма партии 0 — доля по
  количеству (списываемое / остаток партии); `РаспределитьПоПозициям` (через `РаспределениеПоСтрокам`): база — сумма,
  нулевая сумма — количество, оба нуля — всё последней строке; остаток округления — последней строке (сейчас при нулевой
  сумме — деление на ноль). НДС — той же пропорцией.
- **`ПоступлениеДополнительныхРасходов` по поступлению ордерного склада**: строка с `ДокументПартии` = поступление,
  проведённое на ордерном складе, раскладывается на партии-ордера его пар — база — стоимость пар (Ф3.3), нулевая —
  количество; записи с `Партия` = ордер, `КодСтроки` = строка ордера, **период — дата документа допрасходов** (как
  сейчас). `ДокументПартии` = приходный ордер — напрямую на его строки этой номенклатуры. **Порядок (Редакция 35):**
  ордер партии (прямой или через пары поступления) раньше документа допрасходов по моменту — иначе отказ проведения
  («допрасход раньше приёмки ордером»); правка даты **любого** приходного ордера (оформленного или нет — Редакция 36) на момент не раньше самого
  раннего проведённого документа допрасходов на его партии (прямо или через поступления его пар) — отказ в
  `ПроверитьЗащиту`, **до** раннего выхода «оформлений нет», под блокировками ордера; так же — отмена проведения и
  удаление ордера с проведёнными прямыми допрасходами (их партии не стало бы). Тест: неоформленный ордер → прямой
  допрасход → перенос ордера позже допрасхода — атомарный отказ, дата и движения те же.
  **База распределения (Редакция 37):** проведённый документ допрасходов на партию ордера защищает ордер так же, как
  оформление: строки ордера с номенклатурой и характеристикой его строк допрасходов не удаляются и не меняют
  номенклатуру, характеристику, серию; количество — не до нуля (`ПроверитьЗащиту`, до раннего выхода). Проведение
  документа допрасходов: строка без подходящей базы (нет строк партии этой номенклатуры и характеристики) — **отказ**, а
  не молчаливый пропуск (сейчас `РаспределитьПоПозициям` при пустой базе ничего не пишет); после распределения Σ движений
  = сумме строки, иначе отказ. Тест: «неоформленный ордер → прямой допрасход → замена последней подходящей строки» —
  атомарный отказ, движения те же. Тогда движения документа допрасходов от даты ордера не зависят, и перенос ордера раньше ничего в них не
  меняет (сам ордер, проведённый задним числом, двигает границу платформой). Тест: перенос даты ордера позже документа
  допрасходов — отказ; раньше — допрасход тот же, пересчёт с расходом между датами — допрасход списан полностью, повтор
  ничего не меняет. Поступление без пар (не проведено) — **отказ** проведения документа допрасходов с текстом (сейчас
  допрасход в этом случае молча не распределяется — в обходе последовательности это станет ошибкой шага с текстом).
- **Неоформленный остаток (Редакция 6)**: в схеме «ордер первый» его нет — строка поступления по ордеру целиком
  оформляет строку ордера, и все пары поступления существуют на момент его проведения (ордер не позже документа). Механизм
  «нераспределённый остаток с периодом поздней приёмки» нужен схеме «документ первый» — **фаза 4**, вместе с ней.
- **Сдвиг границы на документы допрасходов** (Редакция 5) — при изменении пар поступления (Ф3.7); их перепроведение
  пересчётом раскладывает допрасход по новым парам.

### Ф3.10 Защиты нулевой стоимости (защита 1 и минимальная пометка)

**Неподтверждённые партии** — `РегистрыНакопления.ТоварыВНаличии.НеподтвержденныеПартии()` (вычисление по цепочке,
без новых реквизитов): множество U партий, чья записанная стоимость не окончательна.

1. U₀ — партии-приходные ордера с неоформленным остатком (`ТоварыКОформлению.Остатки`, `Источник ССЫЛКА
   ПриходныйОрдер`, остаток > 0).
2. **Ордерное происхождение** O* — партии-приходные ордера и все партии, созданные из них: партия, созданная документом D
   (выпуск, пересортица, акт разбора — партия = D; поступление из переработки — через передачу, списавшую партию в
   `ТоварыВПереработке`), входит в O*, если записи расхода D списали партию из O*. Перемещение, требование, возврат от
   покупателя партию не меняют.
3. **Непересчитанные движения** (Редакция 29): партия из O* входит в U, если у неё есть любое движение `ТоварыВНаличии`
   или `ДополнительныеРасходы` (приход, расход, перемещение, возврат, списание) документа последовательности **с моментом
   после границы**: после оформления ближний пересчёт ставит границу на ордер, и пока обход не прошёл расходы партии,
   остаток суммы = новая сумма прихода минус старые суммы расходов — он не достоверен, хотя ордер уже оформлен.
4. Замыкание по происхождению: партия, созданная документом D из партии U, — тоже в U (стоимость D унаследовала
   неподтверждённую).

Замыкание — до отсутствия новых партий с множеством посещённых ссылок, **без лимита глубины** (Редакция 29): каждая
итерация добавляет только новые партии, множество конечно. На базе без ордерных складов O* пусто — запрос один и
дешёвый. Тест — цепочка выпусков длиной больше десяти.

**Защита 1:** `ТоварыВНаличии.ПолучитьСреднююЦенуПоОстаткам` (её вызывают `ОбщегоНазначенияВызовСервера.
ДанныеЦенДляСписка`, `ДинамическаяЦена`, форма оприходования «по себестоимости»), `ПравилаЦенообразования.
СформироватьБазовыеЦены` (основа «Себестоимость», `ВТОстатки`) — остатки и допрасходы с `Партия В (U)` не участвуют;
других нет — база как при пустом остатке (цена 0 / правило пропускает, как сейчас). `ПолучитьСреднююЦенуПоПоступлениям`
(вызовов нет) — + приход приходных ордеров не из U.
**Минимальная пометка:** `РаботаСДокументами.АктуальностьСебестоимости` получает `Неподтверждено` — число партий U
**независимо от остатка** (Редакция 34: партия, проданная целиком до оформления, остаётся в U, пока у ордера есть
неоформленный остаток, — её себестоимость продаж тоже не подтверждена); `Актуальна` = граница не раньше последнего
документа, нет заморозок **и** `Неподтверждено` = 0 — поэтому строка актуальности в отчётах стоимости и маржи и
карточка дашборда выводятся и при полностью пройденной последовательности: «N партий со стоимостью, не подтверждённой
поступлением». Тест: полная продажа до оформления поступления — после пересчёта строка есть; после оформления и
пересчёта — нет. Колонки в отчётах стоимости, пометка в форме выпуска, «себестоимость не определена» в
марже — фаза 4 (защиты 2–3 полностью).

### Ф3.11 Возврат от покупателя

- **Порядок моментов** (Редакция 32). Сейчас «ордер не позже документа» сравнивает даты (`ОшибкиШапкиОрдера`,
  `ПроверитьЗащиту`) — при одной секунде момент ордера может оказаться позже оформляющего документа. Правило
  становится **строгим по моменту времени**: момент ордера раньше момента оформляющего документа (при оформлении —
  `Шапка.МоментВремени` против `ДокОбъект.МоментВремени()`; при правке даты оформленного ордера — новый момент раньше
  самого раннего момента оформляющих документов, `ОформленияОрдера` отдаёт и момент). Тогда для любой реализации
  ордерного склада S и её возврата V: O < S, и при V > S отгрузка всегда раньше возврата.
- Источник — записи `СебестоимостьПродаж` основания (как фаза 2); `МоментОтгрузки` — момент `ДокументОтгрузки`
  (реализация **или расходный ордер**). **Отбор «отгрузка раньше возврата»** включается: источники с моментом отгрузки
  позже возврата не участвуют. Если отбор отсёк источники, без которых количества строки хватило бы, — **отказ**
  проведения возврата («товар отгружен ордером позже возврата»), а не приход новой партией по продажной цене; нехватка
  по прочим причинам (комплект, превышение — как фаза 2) — как сейчас. Тест: S, V, O в одну секунду с разными ссылками —
  оформление при O позже S отклоняется; правка даты O на момент позже S отклоняется; повторное проведение V и
  восстановление последовательности — источники те же.
- Защита «возвращено ≤ отгружено» при правке ордера: в фазе 3 ордер с оформлениями нельзя распровести, удалить,
  уменьшить ниже оформленного, сдвинуть позже оформляющего документа (защита оформленного ордера) — отгруженное по
  реализации ниже возвращённого опуститься не может. Полная защита при отмене ордера (реализация первая) — **фаза 4**.
- Приход возврата на ордерный склад — без ордеров, как сейчас (TECHDEBT «возвраты … без ордеров»): партия
  восстанавливается партией-ордером.

### Ф3.12 Закупочная сторона заморозки (Ф2.4)

**Остаётся, с причиной.** Заморозка закупочной стороны — поступление, покрытое налоговым документом с возвратами
поставщику: возвраты поставщику по налоговому документу прочитали партии поступления. На **неордерном** складе партия по-
прежнему поступление — фаза 3 это не меняет. На **ордерном** складе партия — ордер, и пересчёт поступления меняет только
стоимость партий его ордеров ближним пересчётом; но возврат поставщику на ордерном складе — без ордеров (FIFO по
остаткам), его зависимость от партий через налоговый документ не разобрана. Снятие — вместе с возвратами поставщику по
ордерам (TECHDEBT «возвраты … без ордеров»), запись TECHDEBT переписывается: «закупочная сторона: остаётся — партия
неордерного склада = поступление; ордерный склад — с переводом возвратов на ордера».

### Ф3.16 Права

Ролям ничего не добавляется: ордера, поступление и реализация проводятся привилегированно (`postInPrivilegedMode`),
ближний пересчёт пишет чужие наборы (`ТоварыВНаличии` ордера, `СебестоимостьПродаж` реализаций) в привилегированном

отдаёт только ссылки партий вызывающим серверным механизмам цен (их результат — цена, как сейчас). `ai-security` —
обязателен (новый привилегированный путь записи).

### Ф3.17 Тесты (`ТестыДокументов`, реестр `TESTS.xlsx`)

Сценарий **`ОрдерныйСкладПартии`** (и соседние по смыслу, по одному действию-отказу на сценарий):
- приходный ордер 10 → выпуск списывает материал (жалоба клиента): партия = ордер, сумма 0;
- поступление 10 по цене p позже выпуска → набор ордера = 10p (= `СтоимостныеЗаписиПриходныхОрдеров`), граница = момент
  ордера; пересчёт → себестоимость выпуска и продукции по p; **повторный пересчёт — граница стоит, наборы те же**
  (Редакция 5);
- частичное: поступление 8 → сумма 8p, партия в U, база цен её не видит; поступление ещё 2 → вне U после пересчёта;
- **цепочка неподтверждённости**: выпуск из партии U → продукция в U; после поступления до пересчёта — **и ордер, и
  продукция** в U (их расходы после границы); после пересчёта — вне U; цепочка из 11 выпусков — последняя продукция в U;
- инвариант `ТоварыНаСкладах` = свёртка `ТоварыВНаличии` по регистраторам-ордерам (`РасхожденияСТоварамиВНаличии`).
Сценарий **`ОрдерныйСкладРасходПартий`**: расходный ордер без партий → отказ (Р1); расходный ордер 10 → реализации 4 и 6 по
одной строке: Σ долей = списанию строки, остаток — последней по моменту; **обратный порядок создания** (поздняя проведена
первой); **смена даты** реализации — получатель остатка меняется, обе пересчитаны; **отмена одной пары** — доли
оставшейся; оформление 4 из 10 при партиях 6 по 10 и 4 по 20 — себестоимость 40 (FIFO по партиям, Ф3.6), затем 6 — 100;
комплект — составляющие по снимку; реализация по двум ордерам и по двум строкам одного ордера — перепроведение одного
ордера меняет только записи его строк (Редакция 31).
Сценарий **`ОрдерныйСкладПересчетРасхода`**: поступление задним числом дешевле → граница → пересчёт перепроводит
расходный ордер (FIFO по новой цене) → `СебестоимостьПродаж` реализаций обновлена ближним пересчётом в шаге.
Сценарий **`ОрдерныйСкладВозвратМеждуОформлениями`** (Редакция 11): три частичных оформления строки, возврат по второй
реализации между вторым и третьим оформлением → третье меняет остаток второй → граница строго раньше возврата; пересчёт —
стоимость возврата и последующего списания возвращённого товара.
Сценарий **`ОрдерныйСкладДопрасходы`**: допрасходы поступления по парам на партии-ордера; `ПоступлениеДополнительныхРасходов`
по поступлению ордерного склада; допрасход партии с нулевой суммой списывается по количеству; документ допрасходов на
две нулевые позиции с НДС — по количеству, Σ = документу; поступление без пар — отказ.
Сценарий **`ОрдерныйСкладБазаЦен`**: неподтверждённая партия не меняет `ПолучитьСреднююЦенуПоОстаткам`,
`СформироватьБазовыеЦены`, `ДинамическаяЦена`; после оформления и пересчёта — входит.
Сценарий **`ОрдерныйСкладСвойСдвиг`**: старая пара с `КодСтрокиРегистратора` = 0 (прямая запись набора) → шаг обхода,
сам сдвинувший границу, фиксируется и обход продолжается; повтор — граница стоит.
Плюс: `ПоследовательностьСостав` (ордера в составе), `ОбновлениеГраницыПоследовательности` (обработчик 2.0.16.122: записи
ордеров, граница, повтор идемпотентен); правка существующих `ОрдерныйСклад*` (поступление ордерного склада больше не

### Ф4.0 Факты (сверка с кодом 2026-10-31, дерево фазы 3)

- Отказ «строка ордерного склада без ордера» — `ОрдераСклада.ОшибкаСтрокиОформления` (из `ПроверитьОформление`,
  вызовы — проверка заполнения и проведение поступления и реализации); строгий момент «ордер раньше документа» —
  `ОшибкаШапкиОрдера`; защита оформленного ордера — `ПроверитьЗащиту`, `ПроверитьОформленнуюСтроку`,
  `МинимальныйМоментОформлений`.
- `ТоварыКОформлению`: приход пишет только ордер (`СформироватьДвиженияОрдера`), расход — только строки документа с
  ордером (`РасходОформления`). `ПарыОформления` типа источника не фильтрует; «источник — ордер» зашито в
  `ОрдераСклада.ПарыОрдера`, `ПарыПоступлений`, `ЭтоСсылкаОрдера`, `ТоварыВНаличии.ОрдераПарПоступления`,
  `ТоварыКОформлению.НоваяТаблицаЗаписей` (тип колонки), `НеоформленныеСтроки`, `ОрдераДокумента`,
  `ДокументыСоСтрокамиОрдера`, `ФизическиеСтрокиОрдера`.
- Основания: приходный ордер — заказ поставщику, заказ покупателя, реализация; расходный — заказ покупателя,
  поступление. Заполнение по документу (`ПриходныйОрдер.ЗаполнитьПоДокументуТоваров`) связи строки не хранит;
  реквизитов `Документ`/`КлючСтрокиДокумента` в ТЧ ордеров нет.
- Себестоимость: на ордерном складе реализация пишет только свои допрасходы; строка без пары записей не даёт, признака
  «не определена» нет. Отчёты стоимости и маржи выводят строку актуальности через
  `РаботаСДокументами.ВывестиОтчетСАктуальностьюСебестоимости` (6 отчётов) и дашборд.
- Допрасходы: база ордерного склада — только оформленные пары (`ОрдераСклада.БазаПартийОрдеровПоступлений`); строка
  поступления без пары — отказ «нет партий».
- Возврат: `ТоварыВНаличии.СформироватьОприходованиеПоРеализации` — отказ, если товар отгружен ордером позже возврата;
  сверх партий реализации — оприходование по цене возврата.
- Очереди: списки ордеров — страница «К оформлению» (`ПрименитьСтраницу`, остаток `ТоварыКОформлению` по ордеру).
  Отчёт `ОстаткиНаСкладах` различает приход и расход к оформлению по типу источника — у источника-документа даст 0.
- `СистемныеОповещения` (регистр сведений + обработчик ожидания клиента) — есть.
- Тесты, проверяющие отказ без ордера, — внутри `СценарийОрдерныйСклад` (`ПроверитьПриходПоОрдеру`,
  `ПроверитьРасходПоОрдеру`, `ПроверитьДатуНачалаОрдерности`): поведение меняется.

### Ф4.1 Метаданные

- `ПриходныйОрдер.ТЧТовары`, `РасходныйОрдер.ТЧТовары`: реквизиты **`Документ`** (тип: приходный —
  `ДокументСсылка.ПоступлениеТоваровУслуг`, расходный — `ДокументСсылка.РеализацияТоваровУслуг`) и
  **`КлючСтрокиДокумента`** (`ОпределяемыйТип.КодСтроки`). Новые реквизиты — реструктуризация без переноса (пустые).
- Основания: приходный ордер + `ПоступлениеТоваровУслуг`; расходный + `РеализацияТоваровУслуг`.
- `ТоварыКОформлению.НоваяТаблицаЗаписей` — тип колонки `Источник` из метаданных измерения.
- Версия 2.0.16.123. Обработчика обновления нет (данных схемы «документ первый» нет).

### Ф4.2 Пара и источник в обе стороны

Пара = запись расхода `ТоварыКОформлению`: (Источник, КлючСтрокиИсточника) ↔ (Регистратор, КодСтрокиРегистратора).
**Ордер — сторона пары независимо от направления:** ордер первый — ордер источник, документ регистратор; документ
первый — документ источник, ордер регистратор. Новая функция `ОрдераСклада.СтороныПар(Пары)` даёт для каждой пары
(Ордер, КодСтрокиОрдера, Документ, КодСтрокиДокумента, Количество, МоментДокумента, МоментОрдера); все «ордерные»
места (`ПарыОрдера`, `ПарыПоступлений`, `ОрдераПарПоступления`, `СтрокиРасходногоОрдера`, `КускиПар`,
`РеализацииПарОрдеров`, `ОрдераДокумента`, `ДокументыСоСтрокамиОрдера`) переходят на неё. Пары документа и ордера
собираются `ПарыОформления(Документы)` — функция уже ищет документ и как источник, и как регистратор.

### Ф4.3 Поступление и реализация — строки без ордера

- Отказ «строка без ордера на ордерном складе» снимается; в одном документе допустимы обе схемы.
- Строка без ордера на ордерном складе — **приход** `ТоварыКОформлению`: Источник = документ, ключ = `КодСтроки`
  (образец `СформироватьДвиженияОрдера`). Строка с ордером — расход, как сейчас. Партий и физики документ не пишет
  (как в фазе 3); `ЗаказыПоставщикам`/`ПотребностиПроизводства` на ордерном складе — по-прежнему ордер.
- Защита оформленной строки источника-документа — та же, что у ордера, **обобщается на документ**: строку, по которой
  есть оформление, нельзя удалить и сменить номенклатуру, характеристику, серию, склад; количество — не ниже
  оформленного; отмена проведения и удаление при оформлениях — отказ «сначала отмените ордер»; дата — не позже
  самого раннего ордера, оформившего строку (строгий момент — зеркально Ф4.4). Цену и сумму менять можно — это и
  есть ближний пересчёт.
- Формы: отбор ордерности склада в поступлении и реализации снимается (ордерный склад выбирается и без ордеров).
- **Редакция 44 — серии.** Строка-источник — одна серия, как строка с ордером сейчас (`ОшибкаСтрокиОформления`
  запрещает несколько серий при заполненном ордере): несколько серий в `ТЧСерии` у строки без ордера на ордерном
  складе — отказ «разбейте строку по сериям». Тест: строка с двумя сериями — отказ; две строки A=6 и B=4 — частичные
  приёмки по каждой.
- Список «Ожидают приёмки» / «Ожидают отгрузки» — Ф4.10.

### Ф4.4 Ордер на основании документа

- Заполнение по поступлению (реализации): строки — неоформленный остаток `ТоварыКОформлению` по источнику-документу
  (по ключам строк), с `Документ` и `КлючСтрокиДокумента`; склад, контрагент, организация, заказ (для заказов
  поставщику — из основания поступления) — из документа. Ручное добавление строк к такому ордеру — без документа
  (ордер первый).
- Проведение ордера: строка без `Документ` — приход `ТоварыКОформлению` (как сейчас); строка с `Документ` — расход по
  источнику-документу (`Регистратор` = ордер, `КодСтрокиРегистратора` = код строки ордера); партии и физика — как в
  фазе 3 (приходный — приход партии-ордера, расходный — списание ФИФО).
- Проверки строки с документом: склад, номенклатура, характеристика, серия — как у строки документа; документ
  проведён; **документ строго раньше ордера** (момент; для нового ордера — по дате, как в фазе 3); остаток источника
  после записи ≥ 0 (существующий `ПроверитьОстатки` по ключам источника).
- Защита ордера (`ПроверитьЗащиту`) не меняется для строк-источников; строки-регистраторы защищены остатком
  источника.

### Ф4.5 Стоимость партии приходного ордера и ближний пересчёт

- `СтоимостныеЗаписиПриходногоОрдера`: пары ордера в обе стороны (Ф4.2) — стоимость строки = стоимость строк
  поступлений её пар (функция `СтоимостьСтрокПоступлений` не меняется: на вход — пары «строка ордера ↔ строка
  поступления»).
- Ближний пересчёт при проведении, перепроведении, отмене поступления — ордера **всех** его пар (обе стороны).
- Проведение и отмена приходного ордера, оформившего поступление-источник, пересчитывают только сам ордер (его записи
  пишет проведение).
- **Редакция 39 — доля строки поступления.** В ордере первом строка поступления оформляет одну строку ордера целиком;
  в документе первом строку поступления делят несколько пар (приёмки 6 + 4). Стоимость пары = сумма, НДС и свои
  допрасходы строки поступления × q / Q (Q — количество строки поступления). Округление: целевая сумма оформленной
  части строки = round(сумма строки × Σq / Q) отдельно по сумме, НДС и каждой статье допрасходов; **Редакция 40:** она
  делится между парами строки методом наибольших остатков (`РаспределитьПропорционально`, порядок пар — момент ордера,
  код строки) — знак каждой доли совпадает со знаком строки; неоформленная часть — не распределена. Тест: четыре малые
  приёмки, отмена одной, знак каждой доли. Изменение состава пар строки поступления (новый ордер, отмена, количество) пересчитывает **все**
  ордера пар этой строки (меняется получатель остатка округления). Тест: 6 + 4 при цене 3,33; дробное количество;
  отмена первой приёмки; смена цены поступления.
- **Редакция 39 — свои пары ордера до записи.** Ордер, оформляющий документ-источник, сам создаёт пару, а стоимость
  считает до записи движений (`ПровестиОрдер`: стоимость → `ТоварыКОформлению` → запись), при перепроведении прежние
  пары удаляет AutoDelete. Поэтому пары ордера-регистратора берутся **из данных объекта** (строки с `Документ`:
  документ, ключ, количество, код строки ордера), пары ордера-источника — из базы (их пишут другие документы); общий
  расчёт получает обе таблицы. Другие ордера той же строки поступления (получатель остатка округления) пересчитываются
  после записи движений ордера. Тест: стоимость сразу после первого проведения, перепроведения и изменения количества
  без перепроведения поступления.
- **Редакция 40 — блокировки соседей.** Пересчёт соседних ордеров строки поступления перезаписывает их наборы целиком.
  Ордер в `ПередЗаписью`, до AutoDelete и до своих блокировок, собирает соседей прежних и новых пар (ордера тех же
  строк поступлений), все их строки и склады; ключи складов и позиций соседей блокируются **вместе с ключами ордера**
  одним объектом блокировки (порядок `МестаХранения` → `ТоварыВНаличии` → `ДополнительныеРасходы`), затем
  `ТоварыКОформлению` по источникам; после блокировки снимок соседей перечитывается — вырос — отказ «повторите
  проведение» без позднего добора блокировок (образец `ПроверитьСнимокОрдеровПоступления`). Тест — двухсеансовый: две
  приёмки по разным поступлениям с общим многострочным ордером-соседом.

### Ф4.6 Себестоимость реализации по ордеру-регистратору

- `СебестоимостьПродаж.КускиПар` / `ЗаписатьСебестоимостьПоПарам`: строка ордера определяется стороной пары (Ф4.2);
  записи реализации — периодом реализации (как в фазе 3), `ДокументОтгрузки` = ордер, `КлючСтрокиОтгрузки` = код
  строки ордера.
- Ближний пересчёт: проведение и отмена расходного ордера с документом — реализации его пар; перепроведение реализации
  — свои пары (как в фазе 3).
- **Редакция 39 — получатель, потерявший пару.** `ПересчитатьПоПарам` строит список реализаций по оставшимся записям
  `ТоварыКОформлению`: реализация, у которой отменили последнюю пару, в него не попадает и сохраняет себестоимость.
  Ордер в `ПередЗаписью` (до AutoDelete) снимает реализации и ключи отгрузки прежних пар (обе стороны); пересчёт
  получает объединение прежних и новых получателей и обрабатывает каждого, в том числе с пустым набором кусков:
  записи с отгрузкой по затронутым ключам удаляются, прочие сохраняются. Тест: отмена последнего ордера реализации без
  возвратов; перенос строки ордера на другую реализацию-источник.
- **Строка реализации без пары** (ещё не отгружена) — себестоимости нет. `АктуальностьСебестоимости` получает счётчик
  `Неотгружено` (строки реализаций ордерного склада с остатком источника > 0): «Актуальна» = Ложь, текст «Реализаций с
  неотгруженными строками: N — себестоимость по ним не определена». Колонка в отчётах маржи — TECHDEBT (Р4.3).

### Ф4.7 Возврат от покупателя

- Возврат по реализации ордерного склада — **не больше отгруженного ордерами на момент возврата** по строке; сверх —
  отказ (вместо оприходования по цене возврата). Неордерный склад — как сейчас.
- Отмена и уменьшение оформления (отмена расходного ордера-регистратора, удаление его строки, уменьшение количества,
  перенос даты ордера позже возврата) при проведённых возвратах по реализации пары — проверка «отгружено на момент
  каждого возврата ≥ возвращено» по затронутым реализациям после записи; нарушение — отказ. Блокировка возвратов —
  `СебестоимостьПродаж` по реализациям пар (уже последней в порядке). Тест «реализация → ордер → возврат → отмена
  ордера».
- **Редакция 42:** та же общая проверка «возвращено нарастающим итогом на момент каждого возврата ≤ отгружено на этот
  момент» — и при **проведении, перепроведении, переносе даты и смене основания возврата** (прежнее и новое основание,
  под блокировкой `СебестоимостьПродаж` по обоим до записи). Тест: две отгрузки, второй возврат задним числом между
  ними — атомарный отказ.

### Ф4.8 Допрасходы поступления «документ первый»

- Свои допрасходы поступления (`ТЧДополнительныеРасходы`) — через пары, как в фазе 3: ордер, оформивший строку
  позже, получает свою долю своим проведением; период записи — момент ордера. Неоформленная часть ждёт ордера.
- Документ `ПоступлениеДополнительныхРасходов` по поступлению ордерного склада: база — пары поступления **на любую
  дату** (не только до даты документа); запись по каждой паре — периодом **позже из двух**: дата документа допрасходов
  или дата ордера пары. Неоформленная часть строк — не распределяется: документ проводится, сообщение «распределено
  X из Y; остаток распределится после приёмки». Строгая база фазы 3 «без базы — отказ» остаётся только для
  ордера первого (партия указана ордером) и для строки с номенклатурой, которой нет в поступлении.
- Проведение и отмена приходного ордера-регистратора по поступлению с документами допрасходов сдвигает границу
  `Основная` строго раньше самого раннего из этих документов (D): пересчёт перепроведёт их с новой базой.
  **Редакция 39:** сдвиг — **только при изменении базы** D: ордер в `ПередЗаписью` (до AutoDelete) снимает свои пары с
  поступлениями, по которым есть документы допрасходов (поступление, ключ строки, количество, момент ордера), после
  записи сравнивает с новыми; совпали — граница не трогается (фоновое перепроведение ордера при обходе не возвращает
  её назад). Тест: D < O < последующее списание — полный обход завершается, повторный не меняет ни границу, ни наборы.
- **Редакция 44 — изменение поступления.** База распределения D зависит и от полного количества и сумм строки
  поступления (доля q / Q), не только от пар. Перепроведение поступления сравнивает прежнюю (снимок в `ПередЗаписью`) и
  новую базу связанных документов допрасходов — **нормализованную базу, которую читает распределение**
  (`ДополнительныеРасходы.БазаДокументаДопрасходов`: код строки, номенклатура, характеристика, серия, количество,
  сумма, НДС, пары; Редакция 45) — одной функцией до и после записи; изменилась —
  граница строго раньше самого раннего затронутого D **независимо** от того, изменились ли наборы ордеров. Тест: D < P
  < O, нулевая цена, количество 10 → 20; смена характеристики неоформленной строки — распределение 100 → 50, повторный
  пересчёт не меняет.
- **Редакция 41 — защита базы до приёмки.** Проведённый документ допрасходов по поступлению ордерного склада защищает
  строки поступления **независимо от оформлений**: удаление строки, смена её номенклатуры, характеристики или
  уменьшение количества, после которых у строки документа допрасходов не остаётся подходящих строк поступления, —
  отказ «сначала отмените документ допрасходов»; отмена поступления — отказ (фаза 3, `ПроверитьОтменуПоступленияСДопрасходами`).
  Сериализация: документ допрасходов блокирует `ТоварыКОформлению` **по поступлению как источнику** (а не только по
  ордерам его пар), поступление при проведении и отмене берёт ту же блокировку (Ф4.11). Тест: поступление без ордеров,
  допрасход на него, удаление строки — атомарный отказ. **Редакция 42:** прямое удаление проведённого поступления
  (`ПередУдалением`) — та же проверка под той же блокировкой; тест `Удалить()` поступления без ордеров с проведённым
  документом допрасходов — отказ, оба документа и движения целы.
- **Редакция 39 — защита даты ордера.** `ПроверитьДопрасходыОрдера` (фаза 3) требует, чтобы ордер был раньше любого
  связанного документа допрасходов. Защита делится: **прямой** допрасход на партию ордера (партия указана ордером) —
  как в фазе 3, без изменений (круги 8–10); допрасход **через поступление** — поздняя приёмка разрешена, вместо запрета
  — сдвиг границы перед D при изменении даты, количества или привязки ордера (правило выше). Тест: перепроведение и
  перенос даты ордера в обе стороны относительно D. Тест: допрасход 100
  на поступление 10 штук, приёмки 6 и 4 — после первой на партии 60, после второй и пересчёта — 100.

- **Выпуск**: после проведения выпуска, списавшего неподтверждённую партию, — предупреждение пользователю «стоимость

  обработчика; 0 как «выключить» не используется (выключение — Р4.5). Тест: пустая константа → 3, заданная 7 → 7.
  **Редакция 43:** проверка ожидания — в диспетчере `ПерепроведениеДокументов` после проверки завершения обновления и

  дедупликация. Тест: актуальная последовательность, поступление без ордеров старше порога, повторный запуск в тот же

### Ф4.11 Блокировки

Порядок не меняется. Документ-источник при проведении и отмене блокирует `ТоварыКОформлению` по себе как источнику
(как ордер). **Редакция 43:** реализация, у которой в прежней или новой версии есть строки-источники ордерного склада
(строки без ордера), берёт полный захват в `ПередЗаписью` до AutoDelete **независимо от наличия пар**: ранний выход
`ЗаблокироватьРеализациюПоОрдерам` при пустом списке строк с ордерами снимается для этого случая — блокируется свой
источник `ТоварыКОформлению`, затем `СебестоимостьПродаж` своей реализации; поступление-источник — так же (свой
источник `ТоварыКОформлению`). Двухсеансовый тест: перепроведение реализации без пар одновременно с первым ордером
на её основании. Ордер со строками-документами — по источникам-документам; расходный ордер — `СебестоимостьПродаж` по
реализациям-источникам последним; состав пар читается до блокировки и перепроверяется после (образец фазы 3).

фазы 3; тест — цепочка «до поступления → после поступления → после восстановления».

## Блокировки

документа-источника**, до `ТоварыКОформлению`: поступление — `ТоварыВНаличии`/`ДополнительныеРасходы` по партиям

Состав ордеров и реализаций пар читается до блокировки и перепроверяется после неё (образец
`ПроверитьСнимокПослеБлокировки`).

| **5. Удаление `ТоварыНаСкладах`** | читатели (~60 мест, список — исследование 2026-10-30, перепроверить) → `ТоварыВНаличии`, удаление регистра и зеркала, минимальный остаток; удаление старых ресурсов `Продажи` — в первой публикации CF после фазы 2 | одна модель хранения |

Порядок жёсткий: 3 опирается на 1 (без последовательности нулевая стоимость в выпуске не догоняется) и на 2
(себестоимость реализации ордерного склада пишется только в новый регистр).

## Тесты (`ТестыДокументов`, реестр `TESTS.xlsx`)

Фаза 1:
- `ПоследовательностьСостав` — состав `Основная` = регистраторы двух регистров (сверка по метаданным);
- `ВыпускВПоследовательности` — поступление материала задним числом раньше выпуска → граница сдвинулась →
  восстановление → себестоимость продукции и реализации продукции пересчитаны; повторное восстановление итогов не меняет;
- автовыпуск и стадия заказа после восстановления — те же, что до (TECHDEBT ~1742).

Фаза 2:
- `СебестоимостьПродаж` — реализация на неордерном складе: сумма регистра = списание `ТоварыВНаличии` +
  `ДополнительныеРасходы`; комплект — `НоменклатураПартии` составляющих; услуга — по закупочной цене;
- возврат: восстановленные партии и сторно себестоимости = прежнему поведению (сравнение с эталонной реализацией);
- перенос истории: `Продажи.Себестоимость` до = `СебестоимостьПродаж` после, по регистраторам; маржа в
  `ВедомостьПоПродажам` до и после — равна.

Фаза 3 (сценарий `ОрдерныйСкладПартии`):
- приходный ордер 10 → выпуск списывает материал (жалоба клиента) с нулевой стоимостью;
- поступление 10 по цене p позже выпуска → сумма партии ордера = 10p, граница = момент ордера, после восстановления
  себестоимость выпуска и продукции учитывает p;
- частичное: поступление 8 → сумма 8p, неподтверждённая партия видна;
- расходный ордер без партий → отказ (Р1); расходный ордер → реализация: `СебестоимостьПродаж` = списание ордера;
  две реализации по одной строке ордера — сумма долей = списанию, остаток округления — последней;
- перепроведение расходного ордера после смены стоимости партии → `СебестоимостьПродаж` реализаций обновилась;
- допрасходы поступления и `ПоступлениеДополнительныхРасходов` по поступлению ордерного склада → на партии-ордера;
- допрасход при нулевой сумме партии делится по количеству;
- инвариант до фазы 5: `ТоварыНаСкладах` = свёртка `ТоварыВНаличии` (`РасхожденияСТоварамиВНаличии` — ордера теперь
  тоже зеркалятся).

Фаза 4 (сценарий `ОрдерныйСкладДокументПервый`):
- поступление первым → товара на складе нет → приходный ордер на основании → партия = ордер со стоимостью сразу;
- реализация первой → расходный ордер на основании → себестоимость реализации появилась;
- смешанный документ (строки с ордером и без); правка цены оформленного поступления → ближний пересчёт;
- уменьшение оформленной строки источника ниже оформленного → отказ; удаление → отказ;
- база цен: неподтверждённая партия в среднюю не идёт;
- возврат от покупателя больше отгруженного по реализации ордерного склада → отказ.

Фаза 5: смок отчётов физики; сверка остатков отчётов до/после на тестовой базе.

Граница машинных тестов: очереди и оповещения в формах — ручная проверка владельца (`docs/TESTING.md`).

## Права

- `СебестоимостьПродаж`: чтение — роли, читающие себестоимость `Продажи` сейчас (сверить по `Rights.rights` 11 ролей);
  запись — не выдаётся (документы пишут при проведении; ближний пересчёт — привилегированно).
- `ТоварыКОформлению` — как сейчас; новые основания ордеров — роли `Кладовщик`, `ОператорПроизводства`.
- Ближний пересчёт — привилегированный режим: кладовщик проводит ордер и тем самым переписывает себестоимость
  реализации, к которой прав записи у него нет. `ai-security` обязателен.

## Риски

- **Данные клиентов.** Перенос `Продажи` → `СебестоимостьПродаж` и смена состава последовательности идут на всех
  базах. Первое восстановление последовательности после фазы 1 перепроведёт выпуски, требования, переработку от
  границы — на базе Drissotex сначала прогон на копии, время и расхождения себестоимости — в отчёт.
- **Ближний пересчёт пишет движения чужого документа.** Платформа это допускает (набор с отбором по регистратору),
  но это новый в проекте приём: правило в tiny1C по итогам, тест на параллельное проведение источника и носителя.
- **Реструктуризация `ТоварыВНаличии`** (реквизит `КодСтроки`, расширение типа партии) — самый большой регистр
  базы; замер времени обновления на копии Drissotex.
- **`Продажи` без партии** меняет детализацию выручки: отчёты, где выручка группировалась по партии, теряют эту
  разбивку (найти при переносе отчётов).
