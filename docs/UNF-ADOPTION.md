# Перенятие механизмов УНФ 3.0 в maERP

Источник-образец — XML-выгрузка 1С:УНФ 3.0.14.123 в `build/unf_14_123/`
(в git не попадает, лежит только локально). Решения владельца от 2026-08-25.

## Общие принципы (обязательны для каждого этапа)

- **Берём идею и архитектуру, а не код.** УНФ/БСП — образец; функционал
  переписывается под maERP: свои имена (русские, без префиксов), свои роли,
  наши 4 языка синонимов. Код УНФ не копируется дословно — он тянет за собой
  десятки служебных модулей БСП, которых у нас нет и не будет.
- **Не нести лишнее.** Из каждого механизма берётся только то, что нужно
  maERP сейчас. Разделение данных, РИБ, модель сервиса, многопоточность,
  интернет-поддержка — выбрасываются сразу. Спорное — в `docs/TECHDEBT.md`,
  а не в код «на всякий случай».
- **Минимизировать объём базы.** Справочники и регистры — без запасных
  измерений и реквизитов. Всё, что можно хранить в конфигурации (макеты,
  описания изменений), храним в конфигурации, а не в данных. История —
  только с автоочисткой. Новые регистры без явной причины не заводить.
- **Каждый механизм — отдельная подсистема** верхнего уровня со своим
  составом объектов и общими модулями. Никакого размазывания по «Сервису».
- uuid объектов УНФ **не** переносим (правило про uuid действует только для
  объектов drissotex — там заходят данные клиента; здесь объекты свои).
- Новые формы автоматически попадают под смок-тест; обязательные параметры
  форм — сразу в `ПропускаемыеФормы` с причиной. После правок —
  `scripts/lint.sh`, перед сдачей этапа — `scripts/smoke.sh`.

Этапы выполняются по очереди, каждый — отдельной волной со своим промптом
в `docs/unf-adoption/`. Порядок утверждён владельцем.

## Этап У1. Механизм версий и обновлений + описание изменений

**Подсистема `ОбновлениеПрограммы`.** Образец: БСП «ОбновлениеИнформационнойБазы»
(`CommonModules/ОбновлениеИнформационнойБазы*`, регистр `ВерсииПодсистем`),
регистрация обработчиков — как в `ОбновлениеИнформационнойБазыУНФ.ПриДобавленииОбработчиковОбновления`.

Что делаем:

- Регистр сведений `ВерсииПодсистем` (измерение ИмяПодсистемы — строка,
  ресурс Версия — строка). Сейчас подсистема одна — «maERP»; регистр вместо
  константы, чтобы при появлении модулей не менять механизм.
- Общий модуль с таблицей обработчиков: Версия, Процедура (строкой),
  РежимВыполнения (Монопольно/Оперативно), ветка начального заполнения для
  пустой базы. При входе первого сеанса: сравнить версию базы с версией
  конфигурации, выполнить обработчики по возрастанию версий, записать
  новую версию, протокол — в журнал регистрации. Монопольные обработчики
  требуют монопольного режима: не удалось захватить — вход администратора
  с внятным сообщением, обычным пользователям — отказ до обновления.
- **Отложенные обработчики не делаем** (лишнее сейчас). Архитектура
  регистрации не должна мешать добавить их позже.
- **Поглотить механизм волны 11.1**: шаги `ОбновлениеДанныхВызовСервера`
  переносятся в обработчики с версиями, константа
  `НомерВыполненногоЗаполненияДанных` удаляется; миграционный обработчик
  конвертирует выполненный номер шага в стартовую запись `ВерсииПодсистем`,
  чтобы существующие базы не выполнили старые шаги повторно.
- **Описание изменений (единый источник)**: общий макет
  `ОписаниеИзменений` — текст с секциями по версиям (формат зафиксировать:
  заголовок секции = номер версии, далее список изменений). Хранится в
  конфигурации → объём базы не растёт.
  Потребители:
  1. окно «Что нового» — форма, показывается пользователю при первом входе
     после обновления (отметка «показано до версии N» — в хранилище общих
     настроек, без нового регистра);
  2. экспорт секции в JSON для хаба tinycio — публикация на сайт
     (`/products/maerp`) и рассылка оповещений. Экспорт и отправка
     (HMAC-вебхук в Product Hub) — шаг скрипта релиза (`scripts/`),
     а не код конфигурации; в чек-лист `docs/RELEASING.md` добавляется шаг
     «заполнить секцию описания изменений» и «опубликовать через хаб»
     (сама интеграция с хабом — этап 12 по MERGE-DRISSOTEX, здесь — формат
     JSON и заготовка скрипта).

## Этап У2. Подсистема печатных форм

**Подсистема `ПечатныеФормы`.** Образец: БСП «УправлениеПечатью»
(`CommonModules/УправлениеПечатью*`, регистр `ПользовательскиеМакетыПечати`,
его формы `МакетыПечатныхФорм` и `РедактированиеМакета`, общая форма
`ПечатьДокументов`, конвенция `ДобавитьКомандыПечати`/`Печать` в модулях
менеджеров).

Что делаем:

- Регистр `ПользовательскиеМакетыПечати`: Объект (строка вида
  «Документ.ИмяДокумента»), ИмяМакета, ресурсы Макет (хранилище значения)
  и Использование. Плюс версия конфигурации на момент правки — чтобы после
  обновления предупреждать «ваш макет правился при версии N, поставляемый
  с тех пор изменился» (без регистра контрольных сумм УНФ — избыточен).
- Резолвер: функция вида `МакетПечатнойФормы(ПутьКМакету)` — включённый
  пользовательский макет из регистра, иначе макет конфигурации. Все места
  печати получают макет только через неё.
- Формы: список всех макетов печати с признаком «изменён пользователем»,
  редактирование макета во встроенном редакторе табличного документа,
  возврат к поставляемому одним действием.
- Общее окно печати (по образцу `ПечатьДокументов`): несколько печатных
  форм, число экземпляров, сохранение в файл; отправка почтой — только
  если малой кровью, иначе TECHDEBT.
- Конвенция: в модуле менеджера печатаемого объекта —
  `ДобавитьКомандыПечати` и `Печать(МассивОбъектов, ...)`; подменю
  «Печать» в формах собирается из этого списка.
- **Перенос всех существующих печатных форм maERP** в подсистему: 114
  макетов при объектах + общие макеты; хелперы `ВыводПечатныхФорм(Клиент)`
  вливаются в модули подсистемы (со сведением дублей), старые прямые
  вызовы печати из форм переводятся на новый контур. Перенос — механический
  и поимённо фиксируется в отчёте волны.
- **Логотипы из карточки организации**: реквизиты уже есть
  (`Организации`: Логотип, ПечатьОрганизации(+Диаметр), ФонПечатныхФорм,
  БланкШапка/БланкПодвал, `ВыводПечатныхФорм.УстановитьЛоготип`).
  В подсистеме — единая точка: при формировании любой печатной формы
  логотип/факсимиле/фон подтягиваются автоматически, если в макете есть
  соответствующие области; ручные вставки по местам — убрать.

## Этап У3. Универсальная загрузка из Excel/CSV/буфера

Образец: БСП `DataProcessors/ЗагрузкаДанныхИзФайла` + УНФ
`ЗагрузкаДанныхИзВнешнегоИсточника` (запоминание маппинга колонок).
Обработка: источник xlsx/csv/вставка из буфера → таблица предпросмотра →
сопоставление колонок с реквизитами приёмника (справочник или табличная
часть документа) → поиск существующих по ключевым полям → создание/
обновление. Маппинг запоминается по приёмнику (хранилище настроек, не
новый регистр, если хватает). Без внешних источников данных и веб-загрузки.

## Этап У4. Даты запрета редактирования — переработка

У maERP уже есть: регистр `ДатыЗапретаРедактирования` (Организация,
ВидЗапрета из ПВХ `ВидыЗапретаРедактирования`: Общая/ПоГруппеПользователей/
ПоПользователю/ПоРоли, ЗначениеЗапрета, ДатаЗапрета), автосдвиг регзаданием
из константы `АвтозакрытиеПериода`, оповещения через
`ОповещатьЗаКолДнейДоЗапретаОтгрузок`, логика ЗапретОтгрузок в
`РаботаСДокументами*`. Образец: БСП «ДатыЗапретаИзменения» (относительные
даты).

Что делаем: сохранить нашу модель видов запрета (она богаче БСП), но:

- **Относительные даты вместо регзадания**: в записи запрета — способ
  «фиксированная дата» или «относительная» (конец прошлого дня/недели/
  месяца/квартала/года, минус N дней задним числом). Действующая дата
  вычисляется при проверке — автоматический сдвиг заложен в модель, а не
  в регламентное задание.
- **Избавиться от констант**: `АвтозакрытиеПериода` и
  `ОповещатьЗаКолДнейДоЗапретаОтгрузок` удалить; их значения переезжают в
  настройки самого механизма (запись регистра/настройка вида запрета).
  Обработчик обновления (механизм У1!) конвертирует значения констант в
  новые настройки.
- Проверка запрета — одна серверная функция, все документы ходят через
  неё; логика запрета отгрузок сохраняется как вид запрета со своими
  настройками, а не отдельная ветка кода.

## Этап У5. Групповое изменение реквизитов

У нас урезанный предок `ГрупповоеИзменениеРеквизитов` (принимает
МассивОбъектов). Образец: БСП `DataProcessors/ГрупповоеИзменениеРеквизитов`.
Довести до полноценного: изменение реквизитов и табличных частей у
выделенных объектов, отбор состава, предпросмотр, отчёт об ошибках по
объектам, без режима разработчика и доп. свойств (пока их нет). Вызов — из
списков через существующие команды.

## Этап У6. Варианты отчётов и панель отчётов с поиском

Образец: БСП «ВариантыОтчетов» (`Catalogs/ВариантыОтчетов`, панель
отчётов). Берём урезанно: панель отчётов раздела (единая форма со списком
отчётов по подсистемам и строкой поиска по названиям/описаниям),
сохранение пользовательских вариантов штатными средствами платформы.
Снимки, рассылки, оценки важности, поставляемые варианты со сверкой — не
берём. Каталог отчётов строится по метаданным подсистем — без нового
справочника, если возможно; иначе минимальный справочник с автозаполнением.

## Этап У7. Показатели бизнеса на нашем Дашборде

Образец: УНФ `Catalogs/ПоказателиБизнеса`, `КарточкиАнализаБизнеса`,
`CommonModules/ПоказателиБизнеса(Формулы)`, `DataProcessors/ПульсБизнеса`.
Идея: показатель = источник данных + формула; карточка = период, сравнение
с прошлым периодом, пороги «хорошо/плохо». Реализация — **внутри нашей
обработки `Дашборд`** отдельными формами (рядом с БазовыйДашборд/
ДашбордПродаж/ПроизводственныйДашборд/СтоковыйДашборд), в том же визуальном
стиле. Декларативная часть — минимальный справочник показателей; без
отдельной подсистемы мониторинга УНФ.

## Этап У8. Контакт-центр через хаб tinycio

Образец: УНФ `DataProcessors/КонтактЦентр`, `InformationRegisters/КонтактЦентрВходящее`,
`CommonModules/Мессенджеры`, `HTTPServices/Chatbot`. Архитектурный паттерн:
«внешний канал → входящее обращение → объект учёта».

Наша схема: каналы (почта, мессенджеры, формы сайта) терминируются в хабе
tinycio (Product Hub, `~/Dev/tinycio`), maERP получает обращения от хаба
(HMAC-вебхук, как в этапе 12 MERGE-DRISSOTEX) в регистр/документ входящих
обращений; АРМ «Контакт-центр» — единое окно обработки: привязка к
контрагенту, создание документов на основании, ответ через хаб. Никаких
прямых интеграций с мессенджерами из конфигурации — только хаб.
Детальная постановка — после этапа 12 (интеграция с хабом), выполняется
последним.
