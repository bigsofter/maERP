# Стандарт оформления форм maERP (интерфейс 8.5)

Решение владельца от 2026-08-27: формы приводятся к виду 1С:УНФ 3.0 —
воздух вместо рамок, адаптивные колонки, структура на страницах. Переделываются
**раскладка и группировки**: состав полей, их порядок и логика форм не меняются.

Платформенных препятствий нет: `compatibilityMode` = 8.5.1,
`interfaceCompatibilityMode` = `Version8_5EnableTaxi` — новый интерфейс основной.

Образец для сверки — выгрузка УНФ в `build/unf_14_123` (в git не попадает).
Показательная форма: `Documents/РасходнаяНакладная/Forms/ФормаДокумента`.

## В чём была разница

В форме расходной накладной УНФ из 73 групп у 57 представление `None` и у 62 снят
заголовок: группы работают невидимой сеткой, а структуру задают страницы и подвал.
В maERP на момент начала работ было 274 группы с `WeakSeparation` и 95 с
`AlwaysHorizontal` — отсюда «поля в коробочках» и неперестраивающаяся раскладка.

## Правила

1. **Рамок нет.** У группы-контейнера `representation` = `None`. Единственное
   исключение — подвал формы (итоги, автор, дата): одна группа с `WeakSeparation`
   внизу, она отделяет служебное от рабочего. Всплывающие группы (`behavior` =
   `PopUp`) рамку сохраняют — это отдельное окошко, а не блок формы.
2. **Заголовков у групп-контейнеров нет.** `showTitle` = `false` там, где заголовок
   не несёт смысла. Заголовки остаются у страниц (`Pages` → `Page`) и у
   сворачиваемых блоков — там текст заголовка и есть кнопка сворачивания.
3. **Горизонталь — адаптивная.** `AlwaysHorizontal` не используется, с одним
   исключением: короткая пара полей фиксированной ширины (номер + дата), которая
   обязана стоять в одну строку, — так делает УНФ (`ГруппаНомерДата`:
   AlwaysHorizontal, у полей width 12–16, autoMaxWidth и horizontalStretch = false;
   иначе HorizontalIfPossible переносит пару в столбик). Компактность даёт
   `verticalSpacing = Half` на колонках шапки. Остальное:
   - `AutoScreenTypeSensitive` — колонки шапки и подвала: на широком экране в ряд,
     на узком в столбик;
   - `HorizontalIfPossible` — короткие строки полей (наименование, код, артикул);
   - `Vertical` — сами колонки внутри контейнера.
4. **Шапка** — контейнер `AutoScreenTypeSensitive` без рамки и без заголовка,
   внутри две колонки `Vertical`. Если шапка сворачиваемая, `behavior` =
   `Collapsible` и заполняется `collapsedRepresentationTitle` на все четыре языка.
5. **Табличные части** — страницами (`Pages`), у страницы заголовок показывается.
   Одна табличная часть — без страниц, таблица прямо в форме.
6. **Списки** — таблица во всю форму, без рамки вокруг, с начальной высотой
   `heightInTableRows` ~20–22 — так форма открывается на высоту экрана, а не
   карточкой под две строки. Колонки — только влезающие без горизонтальной
   прокрутки; остальное — в панель сведений. У формы списка — панель
   «Сведения» справа (образец — список реализаций): страницы Фильтры /
   Клиент / Детали (реквизиты + состав), кнопкой панель сворачивается в
   столбик значков-кнопок (representation = Picture, свои SVG-шаблоны
   ПанельФильтры/ПанельКлиент/ПанельДетали/ПанельСвернуть/ПанельРазвернуть),
   значок раскрывает панель сразу на своей странице; состояние — реквизит
   с `savedData` + `autoSaveDataInSettings` = Use. **Фильтры по
   перечислениям — тумблером** в панели фильтров, с позицией «Все» первой;
   фильтры по справочникам — полями ввода с подписью сверху. Отдельных
   фильтров над самим списком не делать — все отборы живут в панели.
   Под списком — пагинация: кнопки ◀ ▶ и надпись «страница / всего»,
   сервер режет страницы отбором по ссылкам (`ВЫБРАТЬ ПЕРВЫЕ N·страница
   … УПОРЯДОЧИТЬ ПО Дата УБЫВ` + отбор «Ссылка В списке»), счётчик
   строится теми же условиями, что и отборы панели.
   ВАЖНО: у таблицы списка внутри закладок не задавать «группу
   пользовательских настроек» — клиент 8.5 падает (урок forms-008).
7. `showLeftMargin` и `united` оставляем по умолчанию: УНФ их не трогает, а
   массовое переключение ломает выравнивание подписей.

## Как править

Свойства групп лежат в `Form.form`, в блоке
`<extInfo xsi:type="form:UsualGroupExtInfo">` **после** дочерних элементов группы.
Порядок тегов внутри `extInfo` менять не нужно: новые вставляются на место,
принятое в остальных группах (`group`, `behavior`, `representation`,
`showLeftMargin`, `united`, `showTitle`, `throughAlign`, `currentRowUse`).

Правки точечные — по имени группы, а не переписыванием файла: иначе в дифф
попадает перегенерация всей формы и полезное изменение в ней теряется.

## Порядок работ

Волнами, каждая — отдельным коммитом:

1. **Пилот** (сделан 2026-08-27): форма документа реализации, карточка товара,
   список номенклатуры. На нём владелец смотрит направление и правит эти правила.
2. Документы по подсистемам: продажи, закупки, склад, деньги, производство, зарплата.
   Правки механические, их вносит `scripts/forms-style.py`: без ключа показывает, что
   изменится, с ключом `--применить` записывает. Мобильные формы скрипт пропускает —
   стандарт про интерфейс на компьютере. **Волна «Продажи» — сделана 2026-08-31**:
   8 форм, 11 свойств групп (возврат, отгрузка, заказ покупателя и его форма ECommerce,
   кассовая смена, установка цен, правило ценообразования, установка цен вручную).
3. Справочники.
4. Обработки и отчёты.

После каждой волны — `scripts/smoke.sh`. Прогон ловит только «форма открылась»:
раскладку смотрит владелец глазами, поэтому волна не считается принятой, пока он
не посмотрел хотя бы одну форму из неё.

## Что прогон здесь не проверяет

Смок открывает форму и молчит, если она выглядит криво: пустая группа, съехавшие
колонки, потерянный заголовок — для платформы это не ошибка. Единственная защита
от такого — глаз владельца и то, что правки идут по правилам выше, а не по вкусу
в каждой отдельной форме.
