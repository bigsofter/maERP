# План переноса функционала из drissotex в maERP

Дата анализа: 2026-08-22. Детальные отчёты по областям — в
`docs/drissotex-analysis/`.

## Контекст

`drissotex` — конфигурация клиента, унаследованная от исходной
«1C:Commerce» до преобразования в maERP (общий корневой uuid
`cc4f250d-…`, режим совместимости 8.3.23, языки ru/fr). В ней параллельно
дорабатывали функционал. Источники: `build/drissotex.zip` (XML-выгрузка
конфигуратора) и `build/drissotex.dt` (данные + та же конфигурация).

## Метод

Трёхстороннее сравнение: предок `build/xml` (выгрузка 18.08, сразу после
импорта) ↔ drissotex ↔ наша текущая (`build/xml-current`, снята 22.08 перед
заливкой .dt). Точного общего предка нет — часть диффов «предок →
drissotex» на самом деле наши добавления при конверсии; направление
оценивалось по смыслу (новые uuid, ссылки на объекты одной из сторон).

Шум отсеян: наши en/es в синонимах и `НСтр`, их французский в ru-синонимах,
имена параметров СКД в выгрузке (`Font`↔`Шрифт`), `Cmd+`↔`Ctrl+`,
`StandardAttributes`, перестановки блоков. После отсева: 90 BSL-модулей,
117 XML объектов, 156 форм, 79 макетов, 53 новых файла. Все СКД-макеты
бухгалтерских отчётов, обмены, оборудование — без содержательных
изменений.

## Итог одной строкой

Работающего нового функционала в drissotex немного: **выбор партии при
списании**, **НДС в себестоимости** (`СуммаНДС` в регистрах), **новые
печатные формы** (BL/Devis A4/A5, Facture, Заказ поставщику, чеки),
**премии из регистра `ПремииСотрудников`**, **обналичивание чеков** и
десяток багфиксов. Контур **переработки** — нерабочий каркас (проведение не
реализовано), его переносить «как есть» нельзя.

### Волна 3. Партии (M)

Ручной выбор партии при списании — законченная и полезная возможность.

1. `СерииИРазмещение.ОбъединитьТоварыССериями`: колонки `Партия`
   (`ПриходныйДокументПартии`) и `ЕстьПартия`.
2. `ТоварыВНаличии.СписатьНоменклатуру`: ВТ `ВТТовары`/`ВТТоварыБезПартии`,
   отбор партии по `Номенклатура, Характеристика, Серия, Партия` при
   `ЕстьПартия`, контроль «Недостаточно … по партии». Индексы пакета
   (`Результат[4..7]`) пересчитать под наш пакет; проверить, что
   `ТЗКонтрольОстатков` для строк с партией корректен (у них ВТ остатков
   строится по строкам **без** партии).
3. Форма выбора партии по остаткам (у них —
   `ПоступлениеТоваровУслуг.ВыборПартииПоОстаткам`; у нас разместить как
   форму регистра `ТоварыВНаличии` или общую), клиентский модуль
   `ПартииИРазмещениеКлиент`, реквизит
   `ВыпускПродукции.ТЧТовары.Партия`, колонка и `НачалоВыбора` в форме.
4. `ВыпускПродукции` → `ПриходныйДокументПартии` (выпуск становится
   партией-регистратором).

Переносить **хунками**: их `ТоварыВНаличии/ManagerModule.bsl` — старое
состояние, содержит удалённые нами на этапе 1 `СформироватьТаблицуКритическихОстатков`
и ветки `ЗаданиеНаПеревозку`, а также не содержит нашей ветки
`ВыпускПродукции` (ce16379). Зависит от 2.1.

Состояние на 2026-08-22: пункты 1–3 перенесены (`387bfa1`, `7fe8434`)

### Волна 5. Деньги и налоговый контур — пакетом или никак (решение № 2)

Половинчатый перенос сломает взаиморасчёты. Либо целиком, либо нет:

- `ДенежныеСредстваОрганизаций.СформироватьДвижения`: обналичивание чека
  (`ОбналичиваниеЧека` в ПБДС/СБДС), ручная корректировка только при
  непустой `ТЧСпособыОплаты`, `ДокументОснование` в `Движение(...)`,
  свёртка `"Накладная,Основание"`, ветки `ВозвратОтПокупателя`/`ЗаказПокупателя`
  в `ПолучитьОплаты`. Поправить: обращения по ссылке и `ПолучитьОсновную()`
  в цикле, возможные задвоения после левого соединения (M).
- ПКО, РКО, ПБДС, СБДС: вызовы `ВзаиморасчётыСПокупателямиНалоговый` и
  `ВзаиморасчётыСПоcтавщикамиНалоговый.СформироватьДвижения` + регистры в
  `RegisterRecords`; у нас эти ветки в модулях регистров — мёртвый код (S).
- `НалоговаяНакладная`, `ВозвратОтПокупателяНалоговый`,
  `НалоговаяНакладнаяПокупка`: движения в налоговых регистрах вместо обычных;
  платёжные документы не закрывают налоговые накладные в обычном регистре;
  `НалоговаяНакладнаяПокупка` — проведение по `ТоварыВНаличии` при
  `МестоХранения.Налоговый`, ввод на основании ПТУ с переносом входящего
  номера/даты (исправить `ПолучитьОсновнойДоговор(…, Истина)` → `Ложь` для
  поставщика; «первая запись из `В(&МассивДокументов)`») (L).
- `МестаХранения.Налоговый` + условия в диспетчере `ТоварыВНаличии`. У них
  при ложном флаге налоговые документы **молча** не проводятся — добавить
  сообщение (S).
- `НалоговаяНакладнаяПокупка` как основание РКО/СБДС (S).
- Отчёты `РасчетыСПокупателями`/`РасчетыСПоставщиками` — стандартный вывод
  без логотипа, отбор по контрагенту через СКД (решение № 7).
- Имя регистра `ВзаиморасчётыСПоcтавщикамиНалоговый` содержит латинскую «c»
  (у обеих сторон) — переименовать через рефакторинг EDT отдельным коммитом
  (уже в TECHDEBT).

### Волна 7. Производство и переработка (решение № 3 принято: берём полностью, проведение дописываем)

Что у них есть: документы `ПередачаВПереработку`, `ПоступлениеИзПереработки`,
регистр `ТоварыВПереработке`, справочник `ПроизводственноеОборудование`,
роль `ОператорПроизводства`, подсистема с подчинёнными, реквизиты
`ВыпускПродукции` (`Оборудование`, `Оператор`, `Основание`), ТЧ

выпуска, флаг `Контрагенты.Субподрядчик`.

Что с этим не так:
- проведение обоих документов переработки не реализовано — нет веток в
  `ТоварыВНаличии`/`Убытки`/`Хозрасчетный.СформироватьДвижения`, регистр
  `ТоварыВПереработке` никто не пишет, документы всегда получают `Отказ`;
- `ТоварыВПереработке/ManagerModule.bsl` (100 КБ) и `RecordSetModule` —

## Технические правила переноса

- Источник для копирования — XML drissotex; целевой формат — EDT
  (`.mdo`/`.form`/`.bsl`). Метаданные и формы переносить руками в EDT, код
  — хунками с переводом `НСтр` на четыре языка.
- Имена новых объектов на русском (`ImprimerBL` → переименовать), без
  префикса.
- Объекты, переносимые из drissotex, создаём с их uuid (в т. ч. реквизиты,
  ТЧ, значения перечислений) — данные клиента тогда заходят без конвертации.
  Исключение — наши переименования (`ПечатьТоварнаяНакладная`/`…Old`).
- После каждой волны: `scripts/lint.sh`, Refresh и проверка в EDT,
  обновление `build/ib`, перепроведение затронутых документов на данных
  drissotex.
- Каждая волна — отдельные коммиты по смыслу, импорт в EDT — отдельным
  коммитом.
