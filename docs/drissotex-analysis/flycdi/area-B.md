# Область B. Обмен между базами и справочники контрагентов (flycdi)

Пути: F = `build/flycdi/cf`, D = `build/drissotex`, R = `build/rayssouni`, M = `src/cf/src`.

## Схема обмена «база → база» (главное)

**Кто с кем.** Связь «точка-точка» через COM (`V83.comconnector` → в расширении `V85`). Отдельной сущности узла нет:
параметры подключения лежат прямо в карточке **контрагента-покупателя** F (`Catalogs/Контрагенты`: `ОбменДанными`,
`Файловая`, `Сервер`, `БазаДанных`, `Пользователь`, `Пароль` — строки, пароль открытым текстом). То есть база
flycdi (центр/оптовое звено) продаёт товар контрагенту, у которого своя база 1C:Commerce той же конфигурации
(магазин-партнёр/франчайзи или отдельная фирма группы — по коду не различить; в Stats у `Справочник.Организации` 1
элемент, своих филиалов внутри базы нет — значит, второе юрлицо/точка живёт в отдельной базе).

**Что выгружается** (`CommonModules/ПроцедурыОбменаДанными/Ext/Module.bsl`):
1. `РеализацияТоваровУслуг` → **`ПоступлениеТоваровУслуг` в базе покупателя** (`ВыгрузитьРеализацияТоваровУслуг`, :26–73),
   если у контрагента `ОбменДанными` и `ВыгрузкаПродажиВПокупку`. В приёмнике: Организация = своя организация по ICE
   нашего контрагента, Контрагент (поставщик) = наша организация по ICE, договор — основной, склад — по
   наименованию из строкового `Контрагенты.МестоХранения` (:39–41), дата/входящие номер и дата = наши.
   Цены строк: `Цена` = **последняя цена поставщика из `ЦеныНоменклатурыПоставщиков` F** (т. е. себестоимость
   закупки центра, не цена продажи!), `ЦенаМинимальная` и `ЦенаРозничная` — из видов цен F `МинимальнаяЦенаПродажи` и
   `Розничная` (:46–71). Шапочная `Сумма` при этом = сумма реализации — расходится со строками.
   Документ записывается **без проведения** (`РежимЗаписиДокумента.Запись`) — его принимают в базе-приёмнике.
2. `УстановкаЦенНоменклатуры` → такая же `УстановкаЦенНоменклатуры` **во все базы** контрагентов с
   `ОбменДанными И ВыгрузкаЦен` (`ПолучитьКлиентовДляВыгрузкиЦен`, :160–171; `ВыгрузитьУстановкуЦенНоменклатуры`, :75–103):
   вид цены и товарная группа — по наименованию, запись без проведения, ошибки глотаются пустым `Попытка`.

**Сопоставление объектов:**
- документ ↔ документ по **UUID ссылки** (`ПолучитьОбъект`, :105–139: ссылка в приёмнике = UUID источника).
  Повтор без флага «повторная выгрузка» не перезаписывает; кнопка всегда передаёт `Истина` → перезапись.
- номенклатура — по **`Артикул`**; не нашли — `СоздатьТовар` (:173–210): создаёт карточку (наименование, родитель по
  имени, бренд по имени с автосозданием, единица и ставка НДС — из констант приёмника, тип «Товар») и
  **штрихкод = артикул**.
- организация/контрагент — по **ICE** через `РегистрСведений.РеквизитыКонтрагентов` приёмника (:141–158).
- склад, вид цены, товарная группа, бренд — по наименованию.

**По какому событию.** Подписка `EventSubscriptions/ОбработкаПроведенияДокументаДляОбмена` (Posting, только
`РеализацияТоваровУслуг`) → `ПроцедурыРегламентныхЗаданий.ОбработкаСобытияОбработкаПроведения` (Module.bsl:168–171) —
**вызов закомментирован**, подписка пустая. Фактически работает только ручная общая команда
`CommonCommands/ВыгрузитьОбъект` («Выгрузить к клиенту» / «Exporter vers le client», важные команды формы
`РеализацияТоваровУслуг` и `УстановкаЦенНоменклатуры`; право — только у роли `PDV`). У `ВыгрузитьНаСервере` в модуле
команды нет директивы компиляции — не уверен, что компилируется на сервере как задумано (модуль
`ПроцедурыОбменаДанными` — серверный без вызова сервера).

**Приёмка в базе-приёмнике.** `ПоступлениеТоваровУслуг.ОтветственныйЗаПриемку` (СправочникСсылка.Пользователи) +
мобильные формы `ФормаСпискаМобильныйКлиент` (список **непроведённых** поступлений, где я — ответственный за приёмку;
запрос в Form.xml:243–246) и `ФормаДокументаМобильныйКлиент` (сканирование штрихкода камерой, добавление строки,
`КоличествоУпаковок = Количество`). Это пара к обмену: пришедшее «черновиком» поступление кладовщик точки проверяет
сканером и проводит. Обмен `ОтветственныйЗаПриемку` **не заполняет** — его ставят руками.

**Качество кода** (если переносить — переписывать): `ЗаполнитьЗначенияСвойств(НС, Стр)` копирует локальные ссылки
(характеристика, упаковка, ставка НДС) в COM-объект чужой базы; `НайтиПоНаименованию(Документ.ТоварнаяГруппа)` и
`(СтрТовар.Бренд)` получают ссылку, а не строку; `Справочники.Бренды.ПустаяСсылка()` — локальная; при ошибке одного
клиента в цикле цен — `Возврат` из всей выгрузки; соединение не закрывается; пароль базы в открытом виде в карточке
контрагента, видимой менеджерам; при пустом ICE организации (а в Stats `Организации.ICE` = 0 заполненных!) поставщик
в приёмнике остаётся пустым.

### Живое ли
- `РегистрСведений.ОшибкиОбменаДанными` = 0, `ИсторияОбменаДанными` = 0, `ПараметрыОбменаДанными` = 0.
- `Контрагенты.МестоХранения` (строка, имя склада в чужой базе — смысл только для обмена) заполнен у **единиц** контрагентов;
  `Контрагенты.ICE` — у 6. Булевы `ОбменДанными/ВыгрузкаЦен/ВыгрузкаПродажиВПокупку` и строки `Сервер/БазаДанных`
  Stats посчитать не смог (РЕКВОШ / булевы неточны).
- Расширение `МароккоCOM` (префикс `COM_`, `&Вместо("Подключиться")`, отличие от базы — одна строка `V83` → `V85`)
  сделано ровно для того, чтобы COM-обмен работал на 8.5 — косвенный признак, что обмен **используется** (или
  использовался перед переходом). Объём выгрузок по данным F не виден: следов в F он не оставляет, след — в базах
  приёмников, которых у нас нет.
- Итог: **скорее живое, ручной режим, ~6–8 связанных баз**. Подтвердить у владельца/клиента. Точные значения
  булевых флагов даст `build/flycdi/run/Fill.report.txt` (запрос `Fill` уже содержит `ОбменДанными`, `ВыгрузкаЦен`,
  `ВыгрузкаПродажиВПокупку`, `Файловая`, `МестоХранения`, `Город`, `ОтветственныйЗаПриемку`); когда я писал отчёт,
  его ещё не было.

### Есть ли в maERP
- **Нет.** В M нет планов обмена вообще (`ExchangePlans` отсутствует), нет реквизитов подключения у контрагента.
- Есть **мёртвая заготовка общего предка**: `CommonModules/ВнешнееСоединение` (идентична F/D/R, `V83.comconnector`,
  вызовов нет), `РегистрСведений.ПараметрыОбменаДанными` (Сервер, БазаДанных, Пользователь, Пароль, Файловая по
  Организация × `ПриложенияДляОбмена` {Бухгалтерия, ЗуП}; `ПолучитьДанныеПодключения` нигде не вызывается),
  `ОшибкиОбменаДанными.ДобавитьДанные`, обработка `РегистрацияИзмененийДляОбменаДанными` (работает по
  `Метаданные.ПланыОбмена`, которых нет), картинка `ВыполнитьОбменДанными`.
- **Конфликт имён:** в M у `Контрагенты` уже есть `Пользователь` (СправочникСсылка.Пользователи), `Логин`, `Пароль`
  (личный кабинет партнёра, другие uuid). В F `Пользователь` — строка (логин в чужую базу). Перенос «по uuid»
  невозможен, данные этих полей F в M не ложатся — при миграции клиента нужны новые имена/отдельный объект.

### Оценка
**«В типовую» как задача, но не этим кодом.** Связка «продажа в моей базе → черновик поступления в базе покупателя
+ рассылка прайса» полезна любому оптовику/сети с партнёрами на maERP (у flycdi — розница телефонов, сетевой
сценарий типичен для отрасли). Правильная форма: справочник/регистр «Связанные базы» (узел) вместо реквизитов
контрагента; хранение пароля в безопасном хранилище; транспорт — HTTP-сервис maERP или хаб, а не COM (COM только
Windows, см. TECHDEBT «ЗакрытиеСеансов работает только на Windows»); сопоставление по UUID/артикулу/ICE оставить,
плюс журнал ошибок (`ОшибкиОбменаДанными` уже есть). Для миграции flycdi — если клиент обмен реально использует,
минимально: перенести как **расширение клиента** с COM на 8.5 (S–M), типовой механизм — отдельный план (L).
Объём: типовой механизм **L**; клиентский перенос «как есть» **M** (код + 6 реквизитов + страница формы + команда +
мобильная приёмка).

## Карточка контрагента: страница «Обмен данными»
- **Что:** `Catalogs/Контрагенты/Forms/ФормаЭлемента/Ext/Form.xml:973–1060` — страница `ГруппаОбменДанными`:
  флажок обмена, «Файловая», сервер/файл, база, пользователь, пароль, «Продажа в покупку», склад приёмника,
  «Выгрузка цен». Module.bsl:105–152 — `ФайловаяПриИзменении`, `ОбменДаннымиПриИзменении`,
  `УстановитьВидимостьРеквизитов` (доступность полей и заголовок «Файл/Сервер»). `ПриСозданииНаСервере` отличается
  от M только вызовом `УстановитьВидимостьРеквизитов`.
- **Живое / в maERP / оценка** — вместе со схемой обмена выше; отдельно не переносится. S в составе пакета.

## Справочник НаселенныеПункты и Контрагенты.Город
- **Что:** простой справочник городов (`Catalogs/НаселенныеПункты`, код 9, наименование 150, без иерархии, формы
  списка/выбора/элемента, в подсистеме «Сервис»). `Контрагенты.Город` → ссылка на него; поле в `ФормаЭлемента`
  (Form.xml:149) и **обязательно** в `ФормаЭлементаРозница` — кассир не запишет нового клиента без города
  (`ПередЗаписью`, Module.bsl:59–63, вместе с обязательным сроком оплаты). Кроме карточек город нигде не
  используется (ни отчётов, ни отборов, ни печати).
- **Живое:** справочник городов заполнен; заполненность `Город` у контрагентов Stats не определил (ссылка).
- **В maERP:** нет. Есть `СтраныМира` и адреса через `РеквизитыКонтрагентов` (Адреса/АдресДоставки/… строками),
  отдельного города нет.
- **Оценка:** «в отрасль/в типовую — слабо»: справочник городов полезен рознице для аналитики клиентов по городам,
  но в F он ничем, кроме обязательности, не пользуется. В M разумнее — город как часть адреса или реквизит
  `Контрагенты.Город` + отбор/группировка в отчётах продаж. Для миграции данных клиента — перенести (с uuid), чтобы
  не потерять значения: **S**. Обязательность города в рознице — **расширение клиента**.

## Организации.СтавкаНДС
- **Что:** ставка НДС по умолчанию у организации; используется только в `НалоговаяНакладная` и
  `НалоговаяНакладнаяПокупка` (ФормаДокумента, Module.bsl:521 и :502) — при «заполнить по документам» перекрывает
  ставку во всех строках товаров и услуг ставкой организации.
- **Живое:** у единственной организации заполнена; но налоговых накладных в базе нет (`Организация` в них — 0);
  клиент работает «Sans TVA» (константа `СтавкаНДСПоУмолчанию`).
- **В maERP:** нет такого реквизита; есть константа `СтавкаНДСПоУмолчанию` и налоговый контур Марокко.
- **Оценка:** «не переносить» — механизм мёртв у клиента и грубый (затирает построчные ставки). Для одной
  организации хватает константы. —

## ПоступлениеТоваровУслуг.ОтветственныйЗаПриемку
- См. схему обмена: фильтр мобильного списка «мои поступления к приёмке» + мобильная форма приёмки сканером.
- **Живое:** поступления ведутся регулярно, почти все проведены; заполненность ссылки Stats не различает. Мобильные формы есть только в F
  (у D и M их нет).
- **В maERP:** нет реквизита и мобильных форм поступления. В M есть ордерные склады (`docs/plans/warehouse-orders.md`)
  — приёмку по ордеру с назначенным исполнителем правильнее строить там.
- **Оценка:** «в типовую» как идея (назначить ответственного за приёмку + приёмка на телефоне сканером), реализацию
  брать не из F. **S** реквизит + **M** мобильная приёмка. Пересекается с областью мобильного клиента.

## Обмен с сайтом (ОбменССайтом)
- **Что:** типовой обмен CommerceML (обработка `ОбменССайтом`, модуль `ПроцедурыОбменаССайтом`, планы
  `ОбменССайтомТоварами/Заказами`, справочник `НастройкиОбменаССайтом`, регламент `ЗаданиеОбменССайтом`). Есть и у D;
  отличие F от D — одна строка (`РассчитатьСтроку(..., False, ...)` вместо `Истина`, ObjectModule.bsl:4797).
- **Живое:** **нет** — константа `ОбменССайтом` = No, `НастройкиОбменаССайтом` = 0, в каждом плане 2 узла (это
  `ЭтотУзел` + один, вероятно, созданный автоматически/тестово; настроек под них нет).
- **В maERP:** выпилен сознательно (решение 2026-08-24, волна 11.3, `docs/MERGE-DRISSOTEX.md:404,423`).
- **Оценка:** «не переносить» — мёртв у клиента, в maERP удалён по решению владельца.

## ECommerce
- `Номенклатура.ECommerce`, `Контрагенты.ECommerce`, `ЗаказПокупателя.ECommerce`, формы `ФормаСпискаECommerce`
  (номенклатура), `ФормаДокументаECommerce` (заказ), роль `ECommerce` — **всё есть в M** (там же подсистема
  `ECommerce/ЛичныйКабинет`, ФО `ИспользоватьЛичныйКабинет`).
- Отличия F: `Номенклатура/ФормаСпискаECommerce` — дерево сегментов-флажков (товарные группы × типы номенклатуры) для
  отбора списка (`ДЗСегментыПометкаПриИзменении`, `УстановитьПараметрыСписка`, менеджер
  `ЗаполнитьДеревоСегментовДляФормы` — он есть и у D, т. е. общий код, у M списки номенклатуры переделаны планом
  `nomenclature-ui`); `ЗаказПокупателя/ФормаДокументаECommerce` — `ЦенаВключаетНДС = False` вместо `Истина` в
  расчёте строки и вид цены из договора вместо `Контрагент.ТипЦены` — старая версия общего кода; роль ECommerce в F
  беднее (17 объектов против 72 в M).
- **Живое:** заказов с ECommerce — 6 (2025-03…2026-04, **ни одного проведённого**). Фактически мёртво.
- **Оценка:** «не переносить» — в M есть и новее.
