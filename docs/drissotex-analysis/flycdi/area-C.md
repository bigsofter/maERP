# Область C — склад, снабжение магазинов, инвентаризация, мобильный клиент (flycdi → maERP)

Пути: F = `build/flycdi/cf`, D = `build/drissotex`, M = `src/cf/src`. Данные — `build/flycdi/run/Stats.report.txt`.

Главное:
- Единственная крупная доработка клиента в области — **снабжение магазинов со склада снабжения**: «Внутренний заказ», корзина
  «Товары для заказа», перемещение по заказам и оповещения. Механизм появился в ноябре 2026: несколько заказов,
  не проведены, корзина небольшая. Это пилот, а не устоявшийся процесс.
- В остальном F либо старше D/M (задания на пересчёт, загрузка из Excel, статусы пересчёта), либо добавляет мелочи:
  загрузку из Excel в 4 складских документа, себестоимость в перемещении, получателей оповещений по складу, вид цены склада.
- Всё, что переносится, в maERP должно читать физические остатки из `ТоварыНаСкладах`, а не из `ТоварыВНаличии`: с ордерными
  складами (`docs/plans/warehouse-orders.md`) количество по складу живёт там. Код F везде берёт `ТоварыВНаличии.Остатки`.

## 1. Внутренний заказ магазина складу снабжения (комплекс)

**Что делает.** Продавец магазина (роль PDV) кладёт товары в корзину и нажимает «Заказать». Создаётся документ
«Внутренний заказ» на склад продавца со статусом «Новый». Ответственные получают системное оповещение. Склад снабжения
создаёт «Перемещение» из заказа: на основании или командой «Заполнить по заказам», с множественным выбором. Автор заказа
получает оповещение «создано перемещение по заказу». В форме заказа по каждой строке видны остаток магазина, остаток на
складах снабжения и средние продажи магазина в месяц за последние 12 месяцев.

Состав (F):
- `Documents/ВнутреннийЗаказ` — шапка: Организация, МестоХранения, Ответственный, Статус, Комментарий. ТЧ `ТЧТовары`:
  номенклатура, характеристика, упаковка, серия, количество. Движений нет: `<RegisterRecords/>`, `пров=0`.
  - `ObjectModule.bsl:2-14` — при первой записи вызывает `РаботаСДокументами.ОповеститьОСозданииЗаказа`.
  - `Forms/ФормаДокумента/Module.bsl:5-14` — у PDV форма только для просмотра, если статус не «Новый».
  - `Forms/ФормаДокумента/Module.bsl:105-162` — `ЗаполнитьОстаткиНаСервере`: колонки «Остаток» и «ОстатокДепо».
    `ОстатокДепо` берётся по условию `МестоХранения.СкладСнабжения`, то есть сумма по всем складам с этим признаком.
  - `Forms/ФормаДокумента/Module.bsl:165-213` — `ЗаполнитьПродажиНаСервере`. Колонка «Продажи» считается как
    `СредняяПродажа/12`, где СредняяПродажа — это выручка/количество, то есть **средняя цена**, а не количество.
    По смыслу ожидались штуки в месяц. **Ошибка клиента.**
  - `ФормаСписка`/`ФормаВыбора` — у PDV отбор по складу пользователя.
- `Enums/СтатусыВнутреннихЗаказов`: Новый, Подтвержден, ВРаботе, Отклонен, Завершен. Код ставит только «Новый»,
  остальные статусы меняются вручную. Отбор по статусу «Подтвержден» в подборе закомментирован.
- `InformationRegisters/ТоварыДляЗаказа` — корзина. Непериодический, независимый; измерения Номенклатура и МестоХранения,
  ресурс Количество.
- `DataProcessors/СозданиеВнутреннегоЗаказа/Forms/Форма/Module.bsl:1-90` — каталог товаров, ввод количества, корзина,
  «Заказать». `ЗаказатьНаСервере` создаёт заказ (запись без проведения) и очищает корзину.
  Попутно: `Элементы.*.Обновить()` вызывается на сервере (стр. 82-83), так делать не принято.
- `Catalogs/Номенклатура/Forms/FormProduitsOnStock/Module.bsl:209-260` — та же кнопка «Заказать» в подборе «Товары на
  складе». Плюс остатки выбранного товара по всем складам при активизации строки (`ЗаполнитьОстаткиПоТовару`).
- `Catalogs/МестаХранения` — `СкладСнабжения` (признак) и `ВидЦены` (см. п. 6).
- `Documents/ПеремещениеТоваров`:
  - `ts.ТЧТовары/attr.Заказ` — ссылка на заказ в строке.
  - `ObjectModule.bsl:19-25` — заполнение на основании заказа: операция «ПеремещениеСписание», получатель = склад заказа.
  - `ObjectModule.bsl:49-62` — оповещение при первой записи.
  - `Forms/ФормаДокумента/Module.bsl:137-147, 275-293` — «Заполнить по заказам».
- `CommonModules/РаботаСДокументами/Module.bsl:715-751` — `ОповеститьОСозданииЗаказа`, `ОповеститьОСозданииПеремещения`.
  Получатели оповещения о заказе — пользователи с настройкой `ВидыНастроекПользователей.ОповещатьОСозданииВнутреннегоЗаказа`.
  **Ошибка в `ОповеститьОСозданииПеремещения` (стр. 734-751):** в запросе нет `ГДЕ Ссылка = &Перемещение`. Он выбирает
  заказы из **всех** перемещений базы, поэтому каждое новое перемещение повторно оповещает авторов всех когда-либо
  перемещённых заказов. Пока заказов 4, это незаметно; с ростом базы — лавина.

**Живое ли.** Да, но это пилот. `ВнутреннийЗаказ` — несколько документов за начало ноября 2026, ни одного проведённого.
`ТоварыДляЗаказа` — десятки записей. `МестаХранения.СкладСнабжения`/`ВидЦены` заполнены у всех складов, но для
ссылок и булевых счётчик неточен. `ПеремещениеТоваров.ТЧТовары.Заказ` показан у всех строк — для ссылки это тоже
неточно; по числу заказов реально заполнено единицы.

**Есть ли в maERP.** Нет. В M есть закупка у поставщика по минимальным остаткам: `DataProcessors/ФормированиеЗаказовПоставщику`,
отчёты `ТоварыДляЗаказа` (из `МинимальныйОстатокПоСкладам` + `Продажи`) и `НедостаточныеЗапасы`. Внутренней заявки
магазина складу и связи заявки с перемещением нет. Двухшаговое перемещение (списание → автосоздание оприходования,
`ПеремещениеТоваров/Forms/ФормаДокумента/Module.bsl:34-44`) в M уже есть, оно общее с D.

**Оценка.** «В типовую», но не копией. Розничной сети с центральным складом «заявка магазина → перемещение» нужна, и
пригодится любому многоскладовому клиенту. Переносить как процесс, а не код F:
- статусы с переходами;
- проведение по регистру «заказано к перемещению»: остаток по заявке = заказано − перемещено. Сейчас «Завершен» ставится
  руками, частичное выполнение не видно;
- средние продажи в штуках;
- остатки — из `ТоварыНаСкладах`;
- исправленное оповещение о перемещении;
- оповещения через существующие `СистемныеОповещения`;
- корзину можно оставить регистром, а можно заменить подбором — решать при проектировании.

**Объём.** L (документ + регистр + статусы + перемещение + права PDV/склада + тесты). Минимальный перенос «как у клиента» —
M, но выйдет с теми же дырами.

## 2. Системные оповещения: просмотр истории и команда

**Что делает.** У регистра `СистемныеОповещения` в F есть:
- формы `ФормаСписка`, `ФормаСпискаПросмотра`, `ФормаЗаписи`;
- команда `СистемныеСообщения` в панели навигации (`Commands/СистемныеСообщения/CommandModule.bsl:3-12`) — открывает
  оповещения текущего пользователя;
- в форме записи ссылка на объект кликабельна (`Forms/ФормаЗаписи/Module.bsl:3-24`); не администратору форма открывается
  только для просмотра, без полей «Сотрудник» и «Ссылка».

Всплывающие оповещения раз в 20 с — `Ext/ManagedApplicationModule.bsl:36,75-81`.

**Живое ли.** Да: регистр активно пополняется.

**Есть ли в maERP.** Частично. Регистр, `Сформировать`, вывод всплывающих раз в 30 с
(`Configuration/ManagedApplicationModule.bsl:51,143-149`) и источники (минимальный остаток, запрет отгрузок, контекстные
обсуждения) есть. **Форм и команды нет**: пропущенное всплывающее оповещение пользователь больше нигде не увидит.
`ВывестиСистемныеОповещения` в F отличается только третьим параметром `ПоказатьОповещениеПользователя` (пояснение = текст),
это не доработка.

**Оценка.** «В типовую»: без истории оповещения теряются. **Объём.** S (форма списка с отбором по пользователю, форма записи,
команда, права).

## 3. Минимальный остаток: получатели по складу и адресность

**Что делает.**
- `Catalogs/МестаХранения/ts.ТЧПолучателиОповещения` (Получатель) — список получателей оповещений о минимальном остатке для
  склада. Таблица видна при включённом `ОповещатьОМинимальномОстатке` (`Forms/ФормаЭлемента/Module.bsl:10-18`).
- `CommonModules/ПроцедурыРегламентныхЗаданий/Module.bsl:80-145` — новый параметр `Пользователь`. При продаже
  (`AccumulationRegisters/ТоварыВНаличии/Ext/RecordSetModule.bsl:2-10`, только регистратор РеализацияТоваровУслуг)
  оповещение получает только сам продавец, и только если он в списке получателей склада. Регламентное задание
  по-прежнему оповещает всех пользователей с настройкой `ОповещатьОМинимальномОстатке`.

**Живое ли.** Слабо. `ТЧПолучателиОповещения` — единичные строки; `МинимальныйОстатокПоСкладам` заполнен массово, то есть сами
минимумы живые.

**Есть ли в maERP.** Частично. M: `ПроцедурыРегламентныхЗаданий/Module.bsl:438` — `ПроверкаМинимальногоОстатка(МассивТоваров,
Склад)`, без адресата. Получатели — все пользователи с настройкой. Проверка на любой записи движений склада, а по плану
ордерных складов — в `ТоварыНаСкладах.ПриЗаписи`. Корректная обработка ухода в ноль уже сделана в M, в F её нет.

**Оценка.** «В типовую» — только идея «получатели по складу»: в сети из десятков складов оповещать всех о каждом магазине —
шум. Адресацию «только продавцу» не переносить: продавцу лучше видеть остаток в АРМ, чем получать оповещение.
**Объём.** S (ТЧ склада + отбор получателей в `ПроверкаМинимальногоОстатка`; пустая ТЧ — как сейчас).

## 4. Оповещение «товара нет в магазине»

**Что делает.** Если кассовый документ не провёлся из-за нехватки, `DataProcessors/VentesEnDetail/Forms/Form/Module.bsl:657-662`
вызывает `РаботаСДокументами.ОповеститьОбОтсутствииТовара` (`РаботаСДокументами/Module.bsl:752-768`). Оповещение
«товар X отсутствует на складе Y» получают пользователи с настройкой `ОповещатьОбОстутствииТовараВМагазине` (опечатка в
имени у клиента).

**Живое ли.** Не уверен: в Stats нет разбивки оповещений по тексту.

**Есть ли в maERP.** Нет. Кассовый интерфейс M устроен иначе; политика M — не запрещать проведение из-за минуса.

**Оценка.** «Расширение клиента» / «не переносить» в нынешнем виде. Держится на запрете продажи в минус, который в maERP
не применяется. Если владельцу нужен «упущенный спрос», делать отдельно: регистр отказов из кассы.
**Объём.** S (если понадобится).

## 5. Перемещение: заполнение по остаткам, из Excel, себестоимость, перевозчик

**Что делает** (`Documents/ПеремещениеТоваров/Forms/ФормаДокумента/Module.bsl`):
- «Заполнить товары» (стр. 122-130, 233-236) — все остатки склада-отправителя, с вопросом о перезаполнении.
- «Заполнить остатки» (стр. 132-135, 238-251) — проставить в строки текущий остаток.
- «Заполнить по заказам» — см. п. 1.
- «Заполнить из Excel» (стр. 115-120, 221-231) — через `Обработка.ЗагрузкаИзExcel`.
- `ПоказатьСебестоимость` (стр. 194-206) — себестоимость по строкам и итог в форме, через
  `ТоварыВНаличии.ПолучитьСебестоимостьПоДокументу`. В печатной форме (`ManagerModule.bsl`, `ПечатьПеремещениеТоваров`)
  выводятся цена и сумма по себестоимости и колонка «Серия».
- У PDV операция и склад-отправитель только для просмотра (стр. 9-12).
- Реквизиты `Перевозчик` (Контрагенты) и `СрокПеремещения` (дн.). В коде и печати не используются, только поле на форме.

**Живое ли.** Перемещения живые, ведутся ежедневно. `СрокПеремещения` заполнен в единичных документах — мёртвый.
`Перевозчик` — счётчик неточен (ссылка).

**Есть ли в maERP.** Частично:
- Команды «Заполнить товары/остатки», Excel, себестоимости в форме и печати нет.
- В M есть команда формы `Заполнить`, но **на форму она не выведена**, а `ЗаполнитьНаСервере`
  (`Documents/ПеремещениеТоваров/Forms/ФормаДокумента/Module.bsl:135-155`) — заглушка: запрос не выполняется, условие
  `МестоХранения = МестоХранения`. Мёртвый код в M (в TECHDEBT стоит записать или удалить).
- Себестоимость в форме в M есть у `СписаниеТоваров`, не у перемещения.

**Оценка.**
- «Заполнить остатками склада» и Excel — «в типовую» (инвентаризационный и магазинный сценарий), S.
- Себестоимость в форме и печати — «в типовую» (как в списании), S.
- `Перевозчик` — «в типовую» под вопросом: полезно для накладной на перемещение, но тогда выводить в печать; S.
- `СрокПеремещения` — «не переносить» (мёртвый).

## 6. Вид цены склада (магазина)

**Что делает.** `МестаХранения.ВидЦены` — у каждого магазина свой розничный вид цены. Его используют подбор «Товары на
складе» (`FormProduitsOnStock/Module.bsl:25-63`: цена склада, иначе розничная, ЦенаСНДС с НДС) и кассовый интерфейс
`VentesEnDetail/Module.bsl:17`.

**Живое ли.** Реквизит «заполнен у всех», но для ссылки это неточно. Насколько магазины реально различаются по цене —
**не уверен**, по Stats не определить.

**Есть ли в maERP.** Нет: цена в подборе — `ТипЦены` контрагента или розничная.

**Оценка.** «В отрасль Телефоны и аксессуары» / розничные сети: разные цены по точкам — типичная розничная потребность.
Переносить вместе с розничным контуром (касса), не отдельно. **Объём.** M (касса, подбор, реализации, печать ценников).

## 7. Подбор «Товары на складе» (FormProduitsOnStock)

**Что делает.** Помимо п. 1 («Заказать») и п. 6 (цена склада), выводит остатки выбранного товара по всем складам
(`ЗаполнитьОстаткиПоТовару`, стр. 211-224). Дерево групп в F упрощено (`СпрНоменклатура.Ссылка.Родитель` без иерархии)
и выглядит хуже, чем в D/M.

**Есть ли в maERP.** Форма есть (= версия D), без остатков по складам и без «Заказать».

**Оценка.** Остатки по всем складам — «в типовую», S. Источник — `ТоварыНаСкладах`. Дерево групп — «не переносить».

## 8. Загрузка из Excel в складские документы

**Что делает.** Команда «Заполнить из Excel» в `ОприходованиеТоваров`, `СписаниеТоваров`, `УстановкаЦенНоменклатуры`,
`ПеремещениеТоваров` (по формам `ЗаполнитьИзExcel`/`ЗаполнитьИзExcelНаСервере`/`ПослеЗакрытияФормыЗагрузки`). Строки
заменяют ТЧ, упаковка = единица товара; в оприходовании пересчитывается сумма. В `DataProcessors/ЗагрузкаИзExcel`
(F, `Forms/Форма/Module.bsl:250-267`) — режим `ЭтоУстановкаЦен` (параметр `Док`): прячет колонки количества, категории,
марки, мин. и продажной цены.

**Живое ли.** Документы живые: оприходования, списания, установки цен и перемещения ведутся регулярно. Сколько из них
загружено из Excel, по Stats не видно.

**Есть ли в maERP.** Частично. Обработка есть (361 строка, новее F: поиск по коду поставщика, артикулу и наименованию,
защита от ошибок чисел). Подключена в реализации, поступлении, налоговых накладных, заказе поставщику, предложении
поставщика. **В оприходовании, списании, установке цен и перемещении — нет.** Режима «установка цен» нет.
Остальные отличия обработки F от D/M — старый код (поиск только по артикулу, без `Попытка` при разборе чисел, `Прервать`
на пустой строке). Отброшено.

**Оценка.** «В типовую»: начальные остатки, пересчёты, массовая переоценка. **Объём.** S на документ, всего S–M.
Для установки цен проверить, что ТЧ называется `ТЧЦены`, и перезаполнять колонки из `ЗагрузитьДанныеДокумента`.

## 9. Инвентаризация: задания на пересчёт, пересчёт, отчёты

- **ЗаданиеНаПересчет** (живое).
  - M уже лучше. В мобильной форме M есть дата пересчёта строки, предупреждение «товар уже посчитан пользователем…»
    и запрет правки старых заданий. F — старая версия того же кода, с закомментированным `#Если МобильныйКлиент`.
    **Не переносить.**
  - Попутно в M: `Documents/ЗаданиеНаПересчет/ManagerModule.bsl:10-15`. В ветке `ФормаСписка` не стоит
    `СтандартнаяОбработка = Ложь`, а для немобильного клиента указана `"ФормаДокумента"`. Ветка, скорее всего, не
    срабатывает, и мобильная форма списка сама не выбирается. В `РеализацияТоваровУслуг/ManagerModule.bsl:704-720` это
    уже исправлено. **Вероятный дефект M** (не проверял в базе).
- **ПересчётТоваров** (живое).
  - Отличия F от M: свой `Enums/СтатусыПересчетаТоваров` (ВРаботе, Завершен) вместо `СтатусыДокументов` в M;
    `ЗаполнитьОстаткиНаСервере` с флагом «все товары склада».
  - M переписан на `Документы.ПересчётТоваров.ЗаполнитьУчетноеКоличество`. **Не переносить.**
  - Если данные клиента когда-нибудь заходят в maERP — нужна перекодировка `Статус` из `СтатусыПересчетаТоваров` в
    `СтатусыДокументов`.
- **Отчёт `АнализИнвентаризаций`** (`Reports/АнализИнвентаризаций/ObjectModule.bsl:1-60` + СКД). Для выбранного пересчёта
  показывает:
  - остаток на дату закрытия предыдущей инвентаризации склада (по связанным списанию и оприходованию);
  - движения между инвентаризациями по видам: поступило, продано, списано, оприходовано, отправлено и получено
    перемещением;
  - конечный остаток;
  - «по учёту / фактически / расхождение».

  Дата окончания инвентаризации = дата связанного списания или оприходования. Требует значений `ПоказателиДвиженияТоваров`:
  `Оприходовано`, `ПеремещениеСписание`, `ПеремещениеОприходование` — в M их нет, есть у D. Заголовки показателей
  зашиты по-французски.

  **Живое ли.** Не уверен (отчёт), но 47 пересчётов дают ему данные.

  **В maERP — нет.** Ближайший — `ДвиженияТовара`.

  **Оценка.** «В типовую»: разбор расхождения — ключевой вопрос после инвентаризации в рознице. **Объём.** M (СКД +
  3 значения перечисления + 4 языка + источник `ТоварыНаСкладах`/`ТоварыВНаличии`).
- **`AccumulationRegisters/ТоварыНедостача` + отчёт `НедостачиТоваров`.** Регистр пишется из
  `ТоварыВНаличии.ДобавитьНедостачу` (F, `ManagerModule.bsl:382-387, 461-469`) при `РазрешитьНедостачи`. В регистре
  **0 записей** — мёртвое. В M эта ветка помечена как мёртвая (`ТоварыВНаличии/ManagerModule.bsl:833`).
  **Не переносить.**

## 10. Списание и убытки

- **`СписаниеТоваров.Контрагент`** (Контрагенты, на форме «Client»). В F не используется ни в коде, ни в печати, ни в
  движениях — только поле на форме. Заполненность у всех документов неточна (ссылка). Похоже на «кому списали»: гарантийная
  замена, выдача клиенту. **Не уверен** в назначении. «Расширение клиента»; если владелец подтвердит смысл — S.
- **`ВидыУбытков.Отчисления`** — тот же uuid `296f760e…`, что у `Прочее` в M. Клиент просто переименовал значение.
  **Не переносить** (данные клиента заходят без конвертации).
- **`Убытки.СформироватьДвижения`.** У F добавлена ветка ПКО по прочим расчётам (возврат расхода — минус убыток), но нет
  `ПрочиеРасходыВозврат` и проверки Migration. M (`AccumulationRegisters/Убытки/ManagerModule.bsl:50-52`) уже учитывает
  `ПрочиеРасходыВозврат` и курсовые разницы. Ветку «ПКО уменьшает убыток» стоит **сверить с владельцем**: в M ПКО даёт
  только курсовую разницу. Скорее «не переносить» — у M для этого есть `ПрочиеРасходыВозврат`.

## 11. Мобильная приёмка поступлений

**Что делает.**
- `ПоступлениеТоваровУслуг.ОтветственныйЗаПриемку` (Пользователи) — менеджер назначает кладовщика.
- `ФормаСпискаМобильныйКлиент` показывает кладовщику его непроведённые поступления (`ОтветственныйЗаПриемку = &Ответственный`).
- `ФормаДокументаМобильныйКлиент` (`Module.bsl`): сканирование камерой (`Сканировать`, `ОбработкаРаспознанногоШтрихкода`),
  ввод количества, «Провести и закрыть».
- `ManagerModule.ОбработкаПолученияФормы` выбирает мобильные формы. В ветке списка — та же ошибка, что в п. 9:
  нет `СтандартнаяОбработка = Ложь`, а немобильному клиенту указана `"ФормаДокумента"`.
- В `DataProcessors/MobileMenu/Forms/MenuPrincipal/Module.bsl` пункты `FacturesAchat` и `ЗаданиеНаПересчет`.
- В `Roles/MobileClient` — чтение и изменение поступлений.
- `Roles/РедактированиеПоступлениеТоваровУслуг` — просто полные права на документ, нигде в коде не проверяется.

**Живое ли.** `ОтветственныйЗаПриемку` — заполнен у всех поступлений (неточно, ссылка); пользователей
мобильного клиента много — вероятно, живое, но точно не установить.

**Есть ли в maERP.** Нет. Мобильные формы в M есть у реализации, налоговой накладной и задания на пересчёт. MobileMenu M —
только «FacturesDeVente». Задача «кладовщик принимает без цен» в M решается ордерной схемой: `ПриходныйОрдер`.

**Оценка.** «В типовую», но перенести как **мобильную форму `ПриходныйОрдер`** (и, возможно, `РасходныйОрдер`), а не
поступления: кладовщику цены не нужны, а ордер уже есть. Пункт меню «Задание на пересчёт» в MobileMenu M —
тривиально, S. Роль `РедактированиеПоступлениеТоваровУслуг` — «не переносить».
**Объём.** M (мобильная форма ордера + назначение кладовщика + список «мои ордера» + права MobileClient + смок форм).
