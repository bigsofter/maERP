## Задача

Перенести расчёт премий на `ПремииСотрудников` и показатели продаж, довести
`Продажи.ПолучитьСуммуПоказателяПродажПоПараметру`, вывод премий/штрафов в
отчёте «Зарплата сотрудника», настройку праздников. Порядок:

6.1 → 6.2 → 6.3 → 6.4 → 6.5 (интерфейс, по решению) → 6.6 (проверка) →
6.7 (удаление плановых показателей, последним).

Каждый пункт — отдельный коммит; после каждого `scripts/lint.sh` и
XML-проверка правленых `.mdo`/`.form`.

## Правила

- Новые объекты/реквизиты — с uuid из drissotex; существующие не
  перенумеровывать; префикс не используется.
- Код хунками по смыслу; их модули — старое состояние без наших правок.
  Закомментированные блоки drissotex **удалять**, не переносить.
- `docs/rules-1c`: запросы не в цикле (§ 3.2 hr-acc: `РассчитатьПоказатель`
  делает запрос к `Продажи` на каждый показатель каждого сотрудника —
  при переносе собрать показатели сотрудника/подразделения и считать
  продажи **одним запросом** по периоду с группировкой по нужным разрезам,
  либо хотя бы кэшировать результат на (показатель, период, отбор)),
  без `ИЛИ` в параметрах виртуальных таблиц, `НСтр` ru/fr/en/es,
  директивы явно, экспортные методы документировать.
- `scripts/lint.sh`: база — **18 079** (`build/bsl-json-baseline.json`
  пересоздать из текущего `build/bsl-json.json` перед началом; сравнение
  по парам (файл, код)); `CommonModuleInvalidType` — ложное.
- Git: ветка `develop`, один коммит — один пункт, сообщения на русском.
  `build/`, `DT-INF` не трогать.
- **Не переносить**: жёсткие цвета в макетах зарплаты (у нас стилевые
  элементы), хардкод праздников Марокко, ресурсы `СебестоимостьНДС`/
  `ДополнительныеРасходыНДС` регистра `Продажи` (2.1 отложен),
  `ФизическоеЛицо` обязательное у `Пользователи`, роль `ОператорПроизводства`.

## Пункты

### 6.1. `Продажи.ПолучитьСуммуПоказателяПродажПоПараметру` — S

Файл: `AccumulationRegisters/Продажи/ManagerModule.bsl`.

- Отбор через `Отбор.Параметры`: `МестаХранения` (магазины, `ДокументПродажи.МестоХранения В ИЕРАРХИИ`
  — разыменование через соединение с документом, не `Ссылка.X` в запросе),
  `ФизическиеЛица` (сотрудники через `Ответственный.ФизическоеЛицо`),
  `ТипыНоменклатуры`; товарные группы — `Номенклатура В ИЕРАРХИИ (&ТоварныеГруппы)`
  с массивом `СправочникСсылка.Номенклатура`. Проверить, кто ещё вызывает
  функцию (по плану — только `Зарплата`), и не сломать сигнатуру.
- Показатель `ЧистаяПрибыль` = прибыль − затраты. `Убытки.ПолучитьЗатраты`
  не существует: реализовать как экспортную функцию регистра `Убытки`
  (сумма расходов за период по отбору организации/подразделения, на
  основе `СформироватьТаблицуПрибылейИУбытков` или прямого запроса к
  регистру) с документацией, **или** убрать ветку и зафиксировать в
  TECHDEBT — выбрать первое, если данные регистра `Убытки` у drissotex
  непустые (проверить на `build/ib` запросом, если база доступна, иначе
  реализовать и отметить как непроверенное).

### 6.2. Премии из `ПремииСотрудников` и отдельная статья движений — M

Файлы: `AccumulationRegisters/Зарплата/ManagerModule.bsl`,
`Documents/НачислениеЗарплаты/Forms/ФормаДокумента/{Form.form, Module.bsl}`.

- **Предопределённые виды премий** в `ПланыВидовХарактеристик.ПоказателиРасчётаПремий`
  (сейчас предопределённых нет; имена и uuid новые, синонимы ru/fr/en/es):
  - `ФиксированнаяПремия` — сумма из `ПремииСотрудников.Премия`;
  - `ПроцентОтПродажСотрудника` — `Премия` = процент; база — показатель
    продаж (`АнализПродажПоказатель`, по умолчанию `Выручка`) за месяц
    начисления с отбором `ФизическиеЛица = [сотрудник]`
    (`Ответственный.ФизическоеЛицо` документа продажи);
  - `ПроцентОтОбщегоОбъёма` — то же без отбора по сотруднику (все продажи
    организации за месяц);
  - `ПроцентОтПродажПодразделения` — отбор по `Подразделение` вида премии
    (магазин, `МестаХранения В ИЕРАРХИИ`) — вариант «от общего объёма
    точки»; перечисление `ВариантыАнализаПоказателей` (`ПоСотруднику`,
    `ПоПодразделению`, `ПоОрганизации`) уже есть — предопределённые виды
    при создании получают соответствующий `АнализПродажВариант` и
    `АнализПродажАнализировать = Истина` (заполнить в `ОбработкаПолученияДанныхВыбора`/
    обновлении данных — обработчик обновления или `ПриЗаписи` с
    проверкой предопределённого имени), пользовательские виды работают по
    своим реквизитам без привязки к именам.
- `РассчитатьПремию`: показатели сотрудника через
  `ПоказателиРасчётаПремий.ПолучитьПоказателиПоСОтруднику(Сотрудник, Период)`
  (срез `ПремииСотрудников`); выбор отбора — по `АнализПродажВариант`
  вида премии (предопределённое имя — только как значение по умолчанию);
  показатель продаж считается через `Продажи.ПолучитьСуммуПоказателяПродажПоПараметру`
  (п. 6.1) **одним запросом на документ**: собрать пары (сотрудник,
  вид премии) по всей ТЧ, сгруппировать одинаковые отборы, результат —
  в соответствие. Вид `ПоказателиПродаж.ЧистаяПрибыль` поддержать.
- `РассчитатьПоСотруднику.Итого` включает `Премия.Сумма`; движения
  `НачислениеЗарплаты` по регистру `Зарплата`: оклад — статья
  `НачислениеПоТабелю`, премия — статья `Премия` (предопределённые есть).
- Старую логику `ПлановыеПоказатели`/SMART из `РассчитатьПремию`/
  `РассчитатьПоказатель`/`РассчитатьВыполнениеПланаВЗачёт`/
  `ПолучитьПроцентПремииПоВыполненномуПлану` удалить (не комментировать);
  объекты удаляются в п. 6.7.
- Форма `НачислениеЗарплаты`: колонка `ТЧСотрудникиПремия` видима,
  `НС.Премия = …` при заполнении.
- Запросы из цикла — по правилу выше (один запрос на документ).
