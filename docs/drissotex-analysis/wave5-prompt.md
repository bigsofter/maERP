## Предусловия — решения владельца

Волна переносится **только пакетом**: половинчатый перенос сломает
взаиморасчёты (долг по налоговым накладным перестанет закрываться
оплатами). Перед началом убедись, что в чате или в
`docs/MERGE-DRISSOTEX.md` («Решения владельца») зафиксировано:

- **Решение № 2** — налоговый контур переносим. Если решение «не
  трогаем» — волну 5 пропустить целиком и взять промпт волны 6.
- **Решение № 7** — отчёты `РасчетыСПокупателями`/`РасчетыСПоставщиками`:
  по умолчанию (если владелец не сказал иначе) **логотип оставляем наш**,
  переносим только схему — отбор по контрагенту вместо параметра и
  группировку по контрагенту (п. 5.7).

Если решение № 2 не зафиксировано — остановись и спроси, ничего не меняя.

## Задача

Перенести учётную модель drissotex: оплаты и налоговые документы
проводятся по отдельным регистрам `ВзаиморасчётыСПокупателямиНалоговый` /
`ВзаиморасчётыСПоcтавщикамиНалоговый` (регистры и их модули у нас уже есть
и совпадают с drissotex — мёртвый код, который надо «подключить»), чек
обналичивается через ПБДС/СБДС, налоговая накладная покупки проводится
по складу с признаком `Налоговый`.

Порядок (каждый пункт — отдельный коммит, после каждого `scripts/lint.sh`
и XML-проверка правленых `.mdo`/`.form`):

5.1 → 5.2 → 5.3 → 5.4 → 5.5 → 5.6 → 5.7 → 5.8 (проверка на данных).

## Правила

- Новые реквизиты и значения — с **uuid из drissotex**
  (`МестаХранения.Налоговый` — из `build/drissotex/Catalogs/МестаХранения.xml`;
  типы в `Основание` РКО/СБДС — из их `.xml`). Существующие объекты не
  перенумеровывать (`ВозвратПоставщикуНалоговый`, `РеестрНалоговыхНакладных*`
  у них пересозданы — их uuid **не брать**). Префикс не используется.
- Имя регистра `ВзаиморасчётыСПоcтавщикамиНалоговый` содержит латинскую
  «c» в «Поcтавщиками» — это имя метаданных у обеих сторон. В коде
  **копировать** имя из `src/cf/src/AccumulationRegisters/`, не набирать.
  Переименование — отдельная задача владельца через рефакторинг EDT (уже
  в TECHDEBT), в этой волне не трогать.
- Код переносить хунками по смыслу; их модули — старое состояние без наших
  правок волн 1–4. В `ДенежныеСредстваОрганизаций` и `ТоварыВНаличии`
  перед переносом свериться с текущим `src/cf`.
- `docs/rules-1c`: без запросов и обращений по ссылке в цикле (см.
  cash-retail § 3.1–3.2: `СтрОплат.Организация.ОсновнойУчет`,
  `Кассы.ПолучитьОсновную`, `БанковскиеСчета.ПолучитьОсновной` — вынести до
  цикла / в запрос), без `ИЛИ` в параметрах виртуальных таблиц, блокировки
  по правилам `docs/rules-1c/locks-and-transactions.md`. Пользовательские строки — `НСтр`
  ru/fr/en/es. Директивы компиляции явно, экспортные методы документировать.
- Закомментированные блоки drissotex (`ПриКомпоновкеРезультата`, ветки в
  `СформироватьДвижения`) **удалять**, а не переносить комментарием.
- После правки модулей — `scripts/lint.sh`; база замечаний — **18 122**
  (`build/bsl-json-baseline.json` пересоздать из текущего `build/bsl-json.json`
  перед началом; сравнение — по парам (файл, код)). `CommonModuleInvalidType`
  — ложное, игнорировать. `YoLetterUsage` на именах регистров с «ё» —
  неизбежно, не плодить лишних обращений.
- Git: ветка `develop`, один коммит — один пункт, сообщения на русском в
  стиле `git log`. `build/` и `DT-INF` не трогать.
- **Не переносить**: откаты РМК (решение № 6), `ФизическоеЛицо`
  обязательное у `Пользователи`, права Оператора/Кладовщика (решение № 10),
  запреты толстого клиента Администратору, перевод ru-текстов макетов на
  французский, макет `Templates/Facture` у `НалоговаяНакладнаяПокупка`
  (французские заголовки), `СуммаНДС` в регистрах (2.1 отложен), роль
  `ОператорПроизводства` (волна 7), `SessionParameters.Контрагенты`.

## Пункты

### 5.1. `ДенежныеСредстваОрганизаций.СформироватьДвижения` — M

Файл: `AccumulationRegisters/ДенежныеСредстваОрганизаций/ManagerModule.bsl`
(у нас файл = предок, конфликтов нет).

- Операция `ОбналичиваниеЧека`: ПБДС списывает чек из кассы
  (`TypesDePayment.Cheque`), СБДС приходует чек на банковский счёт; снять
  правило «ПКО с типом оплаты Чек не даёт движений». Сверить с нашими
  `ДвиженияПоКассе`/`ОплатыЧеками`, где `ОбналичиваниеЧека` уже
  обрабатывается, — цепочка должна замкнуться, без задвоения.
- `НалоговаяНакладная`/`НалоговаяНакладнаяПокупка`: ручная корректировка
  только при непустой `ТЧСпособыОплаты`; тип движения по типу документа
  (продажа — Поступление, покупка — Списание).
- `Движение(...)` с параметром `ДокументОснование`; колонка `Накладная` и
  свёртка `"Накладная,Основание"`; ветки `ВозвратОтПокупателя`
  (основание — `ДокОбъект.Основание`) и `ЗаказПокупателя` (пустой массив)
  в `ПолучитьОплаты`; соединение по `ДокументПродажи = ДокументОснование`,
  сумма из `ДенежныеСредстваОрганизаций.Сумма`.
- Править при переносе (cash-retail § 3.1–3.4): `ОсновнойУчет` — в
  `ТЗОплат`; `ПолучитьОсновную()`/`ПолучитьОсновной()` — до цикла;
  `ДатаДвижения`/`ДокументДвижения = Неопределено` — явная проверка;
  `СУММА(…Сумма)` после левого соединения по трём полям — проверить на
  данных drissotex, что строки регистра не задваиваются (сравнить итог
  регистра до/после перепроведения по нескольким ПКО с несколькими
  основаниями).

### 5.2. Налоговые регистры в денежных документах — S

ПоступлениеБезналичныхДенежныхСредств,СписаниеБезналичныхДенежныхСредств}/

- В `ОбработкаПроведения` после `ВзаиморасчётыСПоставщиками` /

  документа (`.mdo`). Модули регистров уже содержат ветки для этих четырёх
  типов — убедиться, что условия прихода/расхода совпадают с drissotex.
- В отчёте отметить: после обновления нужно перепровести денежные
  документы за весь период данных.

### 5.3. `НалоговаяНакладнаяПокупка` как основание РКО/СБДС — S

### 5.4. `МестаХранения.Налоговый` и диспетчер `ТоварыВНаличии` — S

Файлы: `Catalogs/МестаХранения/{МестаХранения.mdo, Forms/ФормаЭлемента/Form.form}`,
`AccumulationRegisters/ТоварыВНаличии/ManagerModule.bsl`.

- Реквизит `Налоговый` (Булево, uuid drissotex, синонимы ru/fr/en/es,
  подсказка «Склад налогового учёта: по нему проводятся налоговые накладные
  покупки») + флажок на форме элемента (обработчики в `Form.form`).
- В диспетчере `ТоварыВНаличии` ветки `НалоговаяНакладнаяПокупка` (и, если
  есть у drissotex, `ВозвратПоставщикуНалоговый`) с условием
  `МестоХранения.Налоговый`. У drissotex при ложном флаге документ **молча**
  не проводится — добавить сообщение пользователю и отказ проведения
  (`Отказ = Истина`) с текстом «Склад … не помечен как налоговый».
  Реквизит склада брать из запроса/реквизитов объекта, не через ссылку в
  цикле.

### 5.5. `НалоговаяНакладная` и `ВозвратОтПокупателяНалоговый` → налоговый регистр — M

Файлы: `Documents/НалоговаяНакладная/{ObjectModule.bsl, НалоговаяНакладная.mdo}`,
`Documents/ВозвратОтПокупателяНалоговый/{ObjectModule.bsl, ….mdo}`,
`AccumulationRegisters/ВзаиморасчётыСПокупателями/ManagerModule.bsl`.

- Движения по `ВзаиморасчётыСПокупателямиНалоговый` вместо
  `ВзаиморасчётыСПокупателями`; регистр в `<registerRecords>`; ветки в
  `ВзаиморасчётыСПокупателями.СформироватьДвижения` удалить (не
  комментировать).
- `СформироватьПоПлатёжномуДокументу`: оплаты с основанием типа
  `НалоговаяНакладная` не закрывают долг в обычном регистре (они закрывают
  его в налоговом — п. 5.2).
- Наша функция `ОплатыИДолгПоДокументу` и `GetTableOfPayments` (волна 4)
  считают по `ВзаиморасчётыСПокупателями` — для налоговых документов печать
  BL/Facture должна брать налоговый регистр: добавить параметр/ветку по типу
  документа, не ломая печать по РТУ.
- Проверить потребителей `ВзаиморасчётыСПокупателями` у нас: списки РТУ и
  заказов, `Дашборд`, `СверкаВзаиморасчётов`, отчёты долгов — где ожидают
  долг по налоговым накладным, добавить объединение с налоговым регистром
  или отметить в отчёте как изменение поведения.

### 5.6. `НалоговаяНакладнаяПокупка`: проведение по складу и налоговому регистру — L

Файлы: `Documents/НалоговаяНакладнаяПокупка/{ObjectModule.bsl, ….mdo,
Forms/ФормаДокумента/{Form.form, Module.bsl}}`,

  `ВзаиморасчётыСПоcтавщикамиНалоговый`; движения по
  `ВзаиморасчётыСПоставщиками` убрать **вместе с** регистром из

  удаляется, `ВозвратПоставщикуНалоговый` — оставить как у нас (у drissotex
  удалена из-за пересозданного объекта); в
  `СформироватьПоПлатёжномуДокументу` — пропуск оснований типа

- Блокировка `ТоварыВНаличии` вместо взаиморасчётов — по
  `docs/rules-1c/locks-and-transactions.md`.
- `МестоХранения` обязательное (`FillChecking = ShowError`) и видимое на
  форме рядом с `Контрагент`.
- Ввод на основании `ПоступлениеТоваровУслуг` с переносом
  `ДатаВходящегоДокумента`/`НомерВходящегоДокумента`; исправить

  его реквизиты, несколько — пусто с сообщением.
- Отбор номенклатуры в ТЧ: 4 типа (`Товар, Продукция, Полуфабрикат, Сырье`).

### 5.7. Отчёты `РасчетыСПокупателями` / `РасчетыСПоставщиками` — S (решение № 7)
