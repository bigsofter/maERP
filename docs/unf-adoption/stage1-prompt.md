# Промпт волны У1: механизм версий и обновлений + описание изменений

Скопировать в новую сессию Claude Code в `~/Dev/maERP` целиком.

---

Выполни этап У1 плана `docs/UNF-ADOPTION.md` — механизм версий и
обновлений с описанием изменений. Прочитай сначала целиком раздел
«Общие принципы» и «Этап У1» этого плана — они являются постановкой;
ниже только уточнения по исполнению.

Образец архитектуры — БСП в выгрузке УНФ `build/unf_14_123/` (смотреть:
`CommonModules/ОбновлениеИнформационнойБазыУНФ/Ext/Module.bsl` — как
регистрируются обработчики; `InformationRegisters/ВерсииПодсистем.xml` —
структура регистра). Код УНФ не копировать — переписать минимальную
версию под maERP по плану.

Состав работ:

1. Подсистема `ОбновлениеПрограммы` (верхнего уровня, не включать в
   командный интерфейс разделов — механизм служебный, формы открываются
   из раздела Сервис/администрирования). Внутри:
   - РегистрСведений `ВерсииПодсистем`: измерение ИмяПодсистемы (Строка
     50), ресурс Версия (Строка 25). Независимый, без периодичности.
   - Общий модуль `ОбновлениеПрограммы` (Сервер): ядро — сравнение
     версий (функция сравнения «1.0.12.3» покомпонентно), выборка и
     выполнение обработчиков по возрастанию версий, запись версии,
     протоколирование каждого обработчика в журнал регистрации
     (ЗаписьЖурналаРегистрации, событие «ОбновлениеПрограммы»).
   - Общий модуль `ОбновлениеПрограммыОбработчики` (Сервер): единственная
     процедура `ПриДобавленииОбработчиковОбновления(Обработчики)` —
     таблица: Версия, Процедура (строка «Модуль.Процедура»),
     РежимВыполнения (Монопольно/Оперативно), НачальноеЗаполнение
     (Булево). Сами процедуры-обработчики — тоже здесь или в профильных
     модулях, вызов через Выполнить() по строке имени, как в БСП.
   - Точка входа: из `ПриНачалеРаботыСистемы` (ManagedApplicationModule,
     после хука СмокТест) — серверный вызов «требуется ли обновление»;
     если требуется: попытка УстановитьМонопольныйРежим(Истина), при
     неудаче — предупреждение и ЗавершитьРаботуСистемы для обычного
     пользователя; выполнение цепочки; снятие монопольного режима.
     Учесть, что в базе есть скрытый администратор и обычные
     пользователи — обновление выполняет первый вошедший с правами
     администратора, остальным до завершения — отказ во входе с внятным
     сообщением.
2. Миграция механизма волны 11.1:
   - Все шаги из `ОбновлениеДанныхВызовСервера` (27 упоминаний шагов)
     переоформить обработчиками с версиями «1.0.11.x» в новом механизме.
   - Обработчик-конвертер: прочитать константу
     `НомерВыполненногоЗаполненияДанных` и записать в `ВерсииПодсистем`
     стартовую версию так, чтобы уже выполненные на базах клиентов шаги
     не выполнились повторно, а невыполненные — выполнились.
   - После конвертации модуль `ОбновлениеДанныхВызовСервера` и константу
     удалить (вместе с местами вызова).
3. Описание изменений:
   - Общий макет `ОписаниеИзменений` (текстовый). Формат: строка
     `## 1.0.12.1` открывает секцию версии, далее строки-пункты.
     Заполнить реальными секциями по истории релизов из
     `docs/RELEASE.md`/`docs/RELEASING.md`/git-тегов — насколько
     восстановимо, минимум текущая версия.
   - Общая форма «Что нового»: показывает секции от «последней
     просмотренной» до текущей версии; отметка просмотра — в
     ХранилищеОбщихНастроек по пользователю. Показ — при первом входе
     после обновления (из той же точки входа, после успешного
     обновления), плюс команда открытия вручную в разделе Сервис.
   - Экспорт для хаба: функция, отдающая секцию версии структурой
     (версия, массив пунктов) + скрипт-заготовка `scripts/changelog.sh`
     (или .py), извлекающий секцию из макета выгрузки в JSON-файл
     `build/changelog-<версия>.json`. Отправку в хаб не делать (этап 12),
     формат JSON зафиксировать в комментарии скрипта.
   - В `docs/RELEASING.md` в чек-лист добавить шаг: «заполнить секцию
     ОписаниеИзменений для новой версии» (до сборки CF).
4. Версию конфигурации поднять (реквизит Version в Configuration.mdo),
   первый обработчик новой версии — конвертер из п.2.

Ограничения и правила:

- Строго следовать CLAUDE.md проекта: только `src/cf`, табуляция, до 140
  символов, директивы компиляции явно, экспортные методы с
  док-комментариями. Русские имена без префиксов. uuid УНФ не
  использовать.
- Не разрастать: никаких отложенных обработчиков, разделения данных,
  прогресс-баров, форм результатов обновления. Один регистр, два общих
  модуля, один макет, одна-две формы.
- Новые формы попадут в смок автоматически; если форма требует
  обязательных параметров — внести в ПропускаемыеФормы обработки СмокТест
  с причиной и в лист «Пропуски смока» `docs/TESTS.xlsx`.
- После правок: `scripts/lint.sh` из корня репо, новые замечания
  разобрать. Прогнать `scripts/smoke.sh` нельзя без обновлённой базы —
  в конце явно перечислить владельцу: что сделать в EDT (Refresh,
  проверка), что база требует обновления конфигурации, и что смок
  прогоняется после этого (креды не в файлах: SMOKE_USER/SMOKE_PWD в
  CLI).
- Коммиты: по смыслу (механизм; миграция 11.1; описание изменений;
  документация), сообщения на русском, без Co-Authored-By.
- По завершении: обновить статус этапа У1 в `docs/UNF-ADOPTION.md`,
  отметить снятие констант/модулей в `docs/TECHDEBT.md` если что-то
  осталось, отчёт — что сделано, что проверить владельцу.
