# Настройка среды разработки

Проверено на macOS (Apple M2 Pro, Darwin 25.5). Платформа 1С в `/opt/1cv8`,
версии `8.3.25.1560` и `8.5.1.1150`. Проект ведём на `8.5.1.1150`.

## Что установлено

Облачный лаунчер `1cedtstart` из `/Applications/1C/1CE`, сама IDE — в
`~/Library/Application Support/1C/1cedtstart/installations/`. Развёрнуты версии
`1C_EDT 2025.2` и `1C_EDT 2026.1`, рабочая — 2026.1 (Eclipse 4.30). Сборка
x86_64, на Apple Silicon идёт через Rosetta. Память уже поднята: в `1cedt.ini`
стоит `-Xmx4096m`.

`1cedtcli` в комплекте **есть** — `1cedt.app/Contents/Eclipse/1cedtcli`, — но на
этой машине он не запускается: обёртка ищет JVM через `/usr/libexec/java_home`,
зарегистрированной в системе JVM нет, ключ `-vm` она не понимает, `JAVA_HOME` не
подхватывает. Чтобы headless-экспорт заработал, JDK нужно зарегистрировать в
системе — симлинком в `/Library/Java/JavaVirtualMachines`, это требует прав
администратора.

Пока это не сделано, `scripts/edt-export.sh` неприменим: выгрузку проекта
делаем из GUI, Файл → Экспорт → Конфигурация в файлы. Остальная часть цепочки
(XML → база → CF → CFU) автоматизирована и идёт из терминала.

## Воркспейс и расположение проекта

Воркспейс — `~/Documents/EDT/maERP`, **вне репозитория**. Так и должно быть:
служебные каталоги Eclipse в git не нужны.

А вот сам проект обязан лежать **внутри репозитория**:

```
~/Documents/Dev/maERP/src/cf
```

Это единственное, что версионируется. Если при импорте оставить расположение
по умолчанию, проект окажется внутри воркспейса, и в git не попадёт ничего —
именно так и вышло с первым проектом `maERP_ib`.

## Настройки EDT

Окно → Параметры:

- **Кодировка** — UTF-8. Иначе кириллица в модулях побьётся.
- **Каталог платформы** — `/opt/1cv8`, версия по умолчанию `8.5.1.1150`.
- **Автоформатирование при сохранении — выключить.** Иначе EDT переформатирует
  модули, которые правил я, и диффы превратятся в шум.
- **Проверка модулей** — включить.

## Импорт конфигурации

EDT не умеет импортировать `.cf` напрямую, промежуточное звено — база.

```bash
scripts/ib-create.sh maerp_1.cf      # чистая база из CF
```

Либо, если есть выгрузка с данными:

```bash
scripts/ib-restore.sh drissotex.dt   # база из .dt
scripts/cf-load.sh maerp_1.cf        # поверх неё свежая конфигурация
```

Дальше в EDT:

1. Файл → Импорт → **Конфигурация 1С:Предприятие из информационной базы**.
2. Указать `build/ib` (файловая, путь к каталогу).
3. Имя проекта — `maERP`.
4. Снять галку «использовать расположение по умолчанию», указать
   `~/Documents/Dev/maERP/src/cf`.
5. Версия платформы проекта — `8.5.1`.

Импорт занимает от 20 минут до часа.

**Проверка, что импортировалось то самое.** Конфигурация в базе и конфигурация
в проекте расходятся молча. Надёжный способ — сверить проект с XML-выгрузкой той
же базы по контрольному объекту: у регистра `ВзаиморасчётыСПокупателямиНалоговый`
в старой конфигурации не было ни одного регистратора, в свежей их два.

```bash
grep -rl ВзаиморасчётыСПокупателямиНалоговый src/cf/*/src/Documents/*/*.mdo | wc -l
```

Ноль означает старую конфигурацию, импорт надо повторить.

Не привязывай такую проверку к конкретному документу: правку могли внести не
там, где ожидаешь. Здесь регистраторами оказались `НалоговаяНакладная` и
`НалоговаяНакладнаяПокупка`, а не `ВозвратОтПокупателяНалоговый`, на который
напрашивалась симметрия с контуром поставщиков.

## Обратное направление

Если правки делались в конфигураторе:

```bash
scripts/xml-dump.sh build/ib build/xml   # база -> XML конфигуратора
```

затем в EDT: Файл → Импорт → Конфигурация из файлов, указать `build/xml`.

## Цикл разработки

1. Я правлю `.bsl` / `.mdo` в `src/cf` и коммичу в `develop`.
2. Ты в EDT делаешь Refresh (F5) и смотришь проверку модулей.
3. Отладка — запуск из EDT на базе разработки.
4. Сборка поставки — см. [RELEASE.md](RELEASE.md).

Конфигуратор для сборки не нужен: пакетный режим `1cv8 DESIGNER` работает
headless, это проверено.
