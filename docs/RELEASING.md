# Релизы maERP

## Версионирование

Схема `1.0.X.Y` (свойство конфигурации `Version`):

- `1.0` — линейка продукта, меняется только при смене поколения (решение
  владельца).
- `X` — номер релиза; растёт на единицу с каждым релизом. Исторически
  стартовал с номера волны разработки (первый релиз — `1.0.11.*` после
  волны 11).
- `Y` — номер сборки внутри релиза: правки, не меняющие состава функций
  (хотфиксы к релизу), увеличивают только `Y`.

Версия проставляется в `Configuration.mdo` (`<version>`) до сборки CF;
тег в git — `v1.0.X.Y` на коммите слияния в `main`.

## Чек-лист релиза

1. Заполнить секцию новой версии в общем макете `ОписаниеИзменений`
   (`src/cf/src/CommonTemplates/ОписаниеИзменений/Template.txt`): заголовок
   `## <версия>` и пункты `- <текст>` — это единственный источник окна
   «Что нового» и выгрузки для хаба, заполняется до сборки CF.
2. `scripts/lint.sh` — без новых замечаний против
   `build/bsl-json-baseline.json` (сравнение по парам «файл, код»).
3. XML-проверка правленых файлов; в EDT — Refresh, синтаксический контроль
   и проверка ссылочной целостности, замечаний нет.
4. Обновить тестовую базу (`build/ib`) из EDT, принять реструктуризацию.
5. `scripts/smoke.sh` на обновлённой `build/ib` — итог «ТЕСТЫ ПРОЙДЕНЫ»
   (CheckConfig + смок «открыть все формы», регламент — `docs/TESTING.md`).
   Релиз с падающими тестами не собирается.
6. Прогон проверок владельцем: `docs/drissotex-analysis/wave5-check.md` …
   `wave10-check.md` (регрессия по контурам) и полный регресс режима
   совместимости (проведение, печать, РМК, обмены) — обязателен, пока
   в релиз входит поднятие `compatibilityMode`.
7. Проверка обновления на копии базы предыдущей версии: при первом входе
   администратора механизм `ОбновлениеПрограммы` поднимает версию в регистре
   `ВерсииПодсистем` до версии конфигурации, ранее выполненные заполнения
   данных не повторяются, показывается окно «Что нового»; в журнале
   регистрации по событию «Обновление программы» ошибок нет.
8. `Version` в `Configuration.mdo` = версия релиза; коммит.
9. `scripts/dist-build.sh <версия> [предыдущие .cf]` — собирает
   `build/dist/maERP-<версия>.cf` (и `.cfu` при наличии предыдущих
   релизов). Бинарники в git не попадают.
10. Merge `develop` → `main` (fast-forward или merge-коммит), тег
    `v<версия>`, push с тегами.
11. GitHub Release на теге: приложить `.cf`/`.cfu`, в описании — список
    изменений; JSON для хаба и оповещений — `scripts/changelog.sh <версия>`
    (`build/changelog-<версия>.json`).

## Примечания

- Сборка CF идёт из базы `build/ib`: пока EDT держит её агентом
  (`DESIGNER /AgentMode`), пакетный запуск невозможен — закрыть базу в EDT.
- Публикация релизов и оповещений через хаб tinycio — этап 12, сюда не
  входит.
