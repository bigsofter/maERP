# Релизы maERP

## Версионирование

Схема `2.0.X.Y` (свойство конфигурации `Version`). Правило владельца от
2026-08-26:

- `2.0` — линейка продукта. Меняется только при смене поколения (решение
  владельца); линейка `1.0` — предыдущее поколение, до перехода на
  подсистемы механизмов УНФ.
- `X` — номер релиза, растёт на единицу **при каждой публикации CF**
  (`scripts/dist-build.sh`, GitHub Release). Исторически стартовал с номера
  волны разработки (первый релиз — `1.0.11.*` после волны 11).
- `Y` — номер сборки. Растёт **на единицу при каждой передаче владельцу на
  тест**, даже если изменение крошечное: по нему база понимает, что нужно
  показать список изменений. Внутри нового релиза нумерация начинается с 1
  (`2.0.12.135` → после публикации CF → `2.0.13.1`).

**Список изменений обязателен для каждой сборки.** Любой этап или правка,
уходящая владельцу, попадает пунктом в секцию своей версии общего макета
`ОписаниеИзменений`
(`src/cf/src/CommonTemplates/ОписаниеИзменений/Template.txt`) — иначе после
обновления окно «Что нового» откроется пустым. Порядок для каждой передачи на
тест:

1. Поднять `Y` на единицу в `Configuration.mdo` (`<version>`).
2. Завести секцию `## <новая версия>` в макете и перечислить в ней всё, что
   вошло в эту сборку, словами пользователя, а не именами объектов.
3. Продублировать пункты **на всех языках конфигурации**: внутри секции блок
   `### ru`, `### fr`, `### en`, `### es`, в каждом — один и тот же список.
   Окно «Что нового» показывает закладку на каждый язык, при отсутствии блока
   подставляется основной язык.
4. Сообщить владельцу версию, на которую он обновляется.

**Макет ведётся от последней публикации CF.** В нём одновременно лежат секции
всех сборок, переданных владельцу после предыдущего CF (`2.0.12.1`, `2.0.12.2`,
`2.0.12.3`, …), и окно «Что нового» показывает их все целиком: владелец видит
не только последнюю правку, а весь накопленный список будущего релиза.
Секции ранее показанных сборок не удаляются и не скрываются.

При публикации CF накопленные секции переносятся из макета в `docs/CHANGELOG.md`
(история релизов), а макет начинается заново — с первой сборки нового релиза
(`2.0.13.1`).

Механизм `ОбновлениеПрограммы` при первом входе после обновления поднимает
версию базы и открывает «Что нового», если версия конфигурации выросла с
момента прошлого показа.

Версия проставляется в `Configuration.mdo` (`<version>`) до сборки CF;
тег в git — `v2.0.X.Y` на коммите слияния в `main`.

## Чек-лист релиза

1. Заполнить секцию новой версии в общем макете `ОписаниеИзменений`
   (`src/cf/src/CommonTemplates/ОписаниеИзменений/Template.txt`): заголовок
   `## <версия>` и пункты `- <текст>` — это единственный источник окна
   «Что нового» и выгрузки для хаба, заполняется до сборки CF.
2. `scripts/lint.sh` — без новых замечаний против
   `build/bsl-json-baseline.json` (сравнение по парам «файл, код»).
3. XML-проверка правленых файлов; в EDT — Refresh, синтаксический контроль
   и проверка ссылочной целостности, замечаний нет.
4. Обновить тестовую базу (`build/ib`) из EDT, принять реструктуризацию.
5. `scripts/smoke.sh` на обновлённой `build/ib` — итог «ТЕСТЫ ПРОЙДЕНЫ»
   (CheckConfig + смок «открыть все формы», регламент — `docs/TESTING.md`).
   Релиз с падающими тестами не собирается.
6. Прогон проверок владельцем: `docs/drissotex-analysis/wave5-check.md` …
   `wave10-check.md` (регрессия по контурам) и полный регресс режима
   совместимости (проведение, печать, РМК, обмены) — обязателен, пока
   в релиз входит поднятие `compatibilityMode`.
7. Проверка обновления на копии базы предыдущей версии: при первом входе
   администратора механизм `ОбновлениеПрограммы` поднимает версию в регистре
   `ВерсииПодсистем` до версии конфигурации, ранее выполненные заполнения
   данных не повторяются, показывается окно «Что нового»; в журнале
   регистрации по событию «Обновление программы» ошибок нет.
8. `Version` в `Configuration.mdo` = версия релиза; коммит.
9. `scripts/dist-build.sh <версия>` — собирает `build/dist/maERP-<версия>.cf`
   и `.cfu`. Без аргументов источниками обновления берутся **все** `maERP-*.cf`
   из каталога поставок, то есть и опубликованные релизы, и сборки, переданные
   на тест: клиент с любой из них обновляется одним файлом. Список можно задать
   явно аргументами. Бинарники в git не попадают, каталог поставок надо хранить —
   без старого `.cf` обновление с той версии больше не собрать.
10. Merge `develop` → `main` (fast-forward или merge-коммит), тег
    `v<версия>`, push с тегами.
11. GitHub Release **черновиком** на теге (`gh release create --draft`):
    приложить `.cf`/`.cfu`, описание взять из `scripts/release-notes.sh <версия>`
    (`build/release-notes-<версия>.md`); JSON для хаба и оповещений —
    `scripts/changelog.sh <версия>` (`build/changelog-<версия>.json`).
12. Владелец открывает черновик и жмёт Publish. Репозиторий публичный, поэтому
    опубликованный релиз и файлы поставки сразу доступны всем.

Шаги 8–11 выполняет Claude — но только после письменного «регресс пройден» от
владельца по шагам 6–7. Публикация (шаг 12) остаётся за владельцем: это
необратимое действие. Существующие релизы и теги Claude не правит и не удаляет.

## Языки описания релиза

Решение владельца от 2026-08-31. У GitHub Release одно тело описания и никакой
локализации: показать разный текст разным читателям нельзя. Поэтому все четыре
языка кладутся в одно описание — **английский основным текстом**, а русский,
французский и испанский под ним в сворачиваемых блоках `<details>`. Так первым
читается международный вариант, а владелец и клиенты открывают свой язык одним
кликом.

Собирает описание `scripts/release-notes.sh`: он берёт секции того же макета
`ОписаниеИзменений`, что и окно «Что нового», поэтому текст релиза и текст в
программе не расходятся. Макет ведётся от последней публикации CF, значит в
описание попадают ровно те сборки, которые входят в релиз.

Уже опубликованные релизы задним числом не переписываются.

## Примечания

- Сборка CF идёт из базы `build/ib`: пока EDT держит её агентом
  (`DESIGNER /AgentMode`), пакетный запуск невозможен — закрыть базу в EDT.
- Публикация релизов и оповещений через хаб tinycio — этап 12, сюда не
  входит.
