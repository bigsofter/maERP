# Автоматизированные тесты maERP

Тесты гоняются на живой базе (по умолчанию — тестовая база сборки `build/ib`,
она же drissotex-тест). Реестр тестов с покрытием — `docs/TESTS.xlsx`.

## Состав тестов

| Уровень | Что проверяет | Чем | Разрушает данные |
|---|---|---|---|
| 0. Статический анализ | Стиль и типовые ошибки BSL | `scripts/lint.sh` (BSL LS) | нет |
| 0.5. Сверка ссылок | Обращения к объектам, которых в конфигурации нет | `scripts/refcheck.py` | нет |
| 1. Проверка конфигурации | Ссылочную целостность метаданных, компилируемость модулей (тонкий клиент, сервер) | `scripts/smoke.sh`, шаг CheckConfig | нет |
| 2. Смок «открыть все формы» и «напечатать всё» | `ПриСозданииНаСервере` каждой формы — на новом объекте и на образце из базы; формирование каждой печатной формы | `scripts/smoke.sh`, шаг СмокТест | нет |
| 2.5. Headless-первый запуск | Пустая база из CF заполняется из JSON (организация, пользователи, служебный администратор), повтор ничего не создаёт, визард не откроется, смок под созданным администратором проходит | `scripts/initial-fill-test.sh <файл.cf>` | да — на своей базе `build/ib-initial`, которую пересоздаёт |
| 3. Жизненный цикл документов | Создание, запись и проведение ключевых документов, движения по регистрам: закупка, продажа с оплатой, возврат, выпуск продукции, переработка, зарплата, безналичные деньги, дополнительные реквизиты, отрасль | `scripts/doctests.sh`, обработка `ТестыДокументов` — каждый сценарий в транзакции с откатом | нет (откат) |
| 4. Сценарные UI-тесты | Клиентскую логику, обработчики, подборы | план: тест-клиент платформы / Vanessa | да — только на копии |

Уровни 0–3 реализованы. Уровень 4 добавляется, когда появится клиентская логика,
которая им реально ломается; решение фиксируется здесь и в `docs/TESTS.xlsx`.

Уровни 0 и 0.5 работают на исходниках и не требуют базы — их гоняю сразу после
правки модулей. Уровни 1–3 работают на базе `build/ib`, а её обновляет из EDT
владелец: без этого проверяется код прошлой сборки.

## Сверка ссылок (уровень 0.5)

```bash
scripts/refcheck.py
```

`Константы.Х`, `Перечисления.Х`, `РегистрыСведений.Х`, `БиблиотекаКартинок.Х`,
типы `Тип("ДокументСсылка.Х")`, полные имена в строках (`"ОбщаяФорма.Х"`,
`"Документ.Х.Макет.Y"`) и вызовы `ОбщийМодуль.Метод()` сверяются с деревом
метаданных `src/cf/src`. Всё это компилируется и проходит CheckConfig, но падает
в рантайме — а смок видит только то, что лежит на пути открытия формы.

Имена приводятся к NFC: macOS хранит имена каталогов в разложенном виде, и без
нормализации любое имя с «ё» или «й» выглядит несуществующим.

Принятые расхождения (стандартные картинки платформы, наследие бухгалтерского
контура) лежат в `scripts/refcheck-known.txt`; обновить файл целиком —
`scripts/refcheck.py --update-known`. Новое расхождение — ошибка: разбирается до
сдачи работы, а в файл попадает только вместе с записью причины в
`docs/TECHDEBT.md`.

## Как устроен смок-тест (уровень 2)

Обработка `СмокТест` (подсистема «Автотесты», см. ниже):

1. Клиент запускается с параметром `/C "СмокТест;<путь-к-отчёту>"`. Хук в
   `ПриНачалеРаботыСистемы` модуля приложения видит параметр, открывает форму
   обработки и пропускает обычную инициализацию клиента.
2. Первым делом в отчёт пишется строка `СТАРТ;<дата>` — по ней скрипт понимает,
   что клиент поднялся и прогон пошёл.
3. **Проход 1, формы.** Сервер собирает полные имена всех форм конфигурации
   (справочники, документы, журналы, отчёты, обработки, планы, регистры,
   критерии отбора, общие формы); формы только для мобильного устройства
   пропускаются. Клиент по каждому имени вызывает `ПолучитьФорму()` — форма не
   показывается, но её `ПриСозданииНаСервере` выполняется полностью.
4. **Проход 2, формы объектов на образцах.** Те же формы объектов, но открытые
   с параметром `Ключ` по образцу из базы: основная форма объекта каждого
   справочника, документа, плана видов характеристик и плана счетов, а у объектов
   с группами — ещё и основная форма группы. Образец берётся тот же, что и для
   печати (`ОбразецОбъекта`): последний проведённый документ, первый непомеченный
   элемент справочника, для формы группы — первая непомеченная группа. Если
   подходящего объекта в базе нет, форма даёт строку `ПРОПУСК` — заводить образцы
   умеет `scripts/fixtures.sh`. Проход добирает и те формы объектов, которые в
   проходе 1 стоят в пропусках: создание нового там запрещено бизнес-логикой или
   правами, а открыть существующий объект можно.
5. **Проход 3, печатные формы.** По каждому объекту из
   `ПечатныеФормы.ОбъектыСКомандамиПечати()` берётся один образец из базы
   (последний проведённый документ; для лидов — заказ покупателя по лиду) и
   формируется каждая печатная форма объекта через
   `ПечатныеФормы.СформироватьПечатныеФормы`. Проверяется, что модуль менеджера
   вернул табличный документ; пустой документ пишется строкой `ПУСТО` и ошибкой
   не считается. Печатных форм в конфигурации больше полусотни, и ни одна из них
   не открывается проходом по формам — до этого прохода они не проверялись ничем.
   Дополнительно в тексте сформированной формы ищется номер документа-образца:
   если его там нет, пишется строка `ПОДОЗРЕНИЕ` — форма сформировалась, но шапка
   может быть пустой (см. «Чего прогон не видит»). Это не ошибка прогона: список
   таких строк смотрится глазами, а печатные формы, где номера заведомо нет,
   заносятся в `ПечатныеФормыБезНомера()` вместе с причиной здесь. Сейчас там три формы:
   чек возврата от покупателя (обычного и налогового) печатает номер документа-основания,
   а не свой собственный, а Z-отчёт кассовой смены номера не печатает вовсе — в макете
   дата, касса, организация, операция и сумма.
6. В конце пишется отчёт и клиент завершает работу. При интерактивном открытии
   формы обработки (без параметра запуска) итог выводится в окно сообщений.

Все три прохода только читают данные, поэтому прогон безопасен и на рабочей базе
клиента — например, как приёмочный контроль после обновления.

### Чего прогон не видит

Зелёный прогон означает «форма открылась» и «печать не упала», а не «напечатано
правильно». Пустое поле в шапке для прогона неотличимо от заполненного: платформа
исключения не выдаёт. Отсюда проверка номера документа (строка `ПОДОЗРЕНИЕ`) — она
ловит самый частый случай, шапку, собранную из итоговой строки запроса без
агрегатных функций (`docs/TECHDEBT.md`). Всё остальное содержимое печати —
суммы, реквизиты организации, скидки — проверяется только глазами, по одной
готовой форме каждого вида перед сдачей релиза.

Пустая форма объекта была вторым слепым блоком: `ПолучитьФорму(Имя)` без параметров
выполняет `ПриСозданииНаСервере` на новом объекте, и ветки «только для записанного
объекта» проверены не были. Так мимо прогона прошла ошибка в
`Справочники.Номенклатура.КомплектИспользованВДокументах` (2026-08-27): для пустой
ссылки функция выходит по первой строке, а на существующем товаре падал запрос.
Закрыто проходом 2 — тем же формам передаётся `Ключ` по образцу из базы.
**Неосновные** формы объекта, которые подставляет `ОбработкаПолученияФормы`
(`ФормаЭлементаECommerce` номенклатуры и контрагентов, `ФормаДокументаECommerce`
заказа, `ФормаЭлементаЕдиница` и `ФормаЭлементаУпаковка`), проход 2 открывает по
явному списку `ДополнительныеФормыОбъектов()` в модуле менеджера: во время
выполнения отличить форму объекта от формы списка нельзя, поэтому список ведётся
руками — новая подстановка в `ОбработкаПолученияФормы` означает строку в нём.
Образец для форм единиц измерения подбирается по виду измеряемой величины
(`ОбразецПоУсловию`).

Смок не проверяет, что документ проводится и что движения правильные, — это
уровень 3 (см. «Тесты документов» ниже).

## Что лежит в конфигурации: подсистема «Автотесты»

Всё, что относится к тестам, собрано в отдельной подсистеме `Автотесты`:

- `Обработка.СмокТест` — прогон. В **модуле менеджера** серверная логика всех
  проходов: `ПроверяемыеФормы()` (состав форм и список пропусков),
  `ФормыОбъектовСОбразцами()` (основные формы объекта и группы с образцами к ним) и
  `ПрогнатьПечатныеФормы()` (образцы объектов, формирование, пропуски печати).
  В **модуле формы** — только клиентский цикл прогона и запись отчёта.
- `Обработка.ТестовыеДанные` — заполнение базы образцами объектов печати (модуль
  менеджера, своей формы нет; см. раздел про образцы ниже). ЗАПИСЫВАЕТ данные.
  Экспортирует `ПервыйЭлемент(ИмяСправочника)` — им пользуются и тесты документов.
- `Обработка.ТестыДокументов` — уровень 3. В **модуле менеджера** сценарии
  (`ИменаСценариев()`, `ВыполнитьСценарии()`, по функции `Сценарий<Имя>` на сценарий),
  данные сценариев, помощники создания документов и чтения регистров. В **модуле
  формы** — только запуск и отчёт. Данных не оставляет: транзакция каждого сценария
  откатывается.
- `ОбщийМодуль.АвтотестыКлиент` — `ОбработатьЗапускТеста()`: разбирает параметр
  запуска (`СмокТест;<отчёт>`, `ТестовыеДанные;<отчёт>` или `ТестыДокументов;<отчёт>`)
  и открывает форму прогона. Модуль управляемого приложения зовёт его одной строкой
  и о тестах больше ничего не знает.

Тем же приёмом (параметр `/C`, маркеры `СТАРТ;`/`ИТОГ;`, ожидание в `run-lib.sh`) устроен
headless-первый запуск — обработка `НачальноеЗаполнение` подсистемы «Обновление
программы», но это не тест, а механизм развёртывания (`docs/DEPLOY.md`); тест к нему —
`scripts/initial-fill-test.sh`.

Подсистема **не входит в командный интерфейс**: показывать пользователю нечего,
прогон запускают скрипты, а вручную обработка открывается через «Все функции».
Понадобится пункт меню — достаточно поставить `includeInCommandInterface` в
`Автотесты.mdo` и решить, каким ролям он виден.

Скрипты (`lint.sh`, `refcheck.py`, `smoke.sh`, `fixtures.sh`, `doctests.sh`) живут в `scripts/` рядом с
остальной сборочной обвязкой — в конфигурацию они не входят. Ожидание клиента и отчёта
при headless-запуске 1С — общая часть `scripts/run-lib.sh`.

## Алгоритм запуска и сбора ошибок

```bash
scripts/smoke.sh [каталог-базы]      # по умолчанию build/ib
```

База с пользователями: логин и пароль — только через переменные окружения
`SMOKE_USER` / `SMOKE_PWD` в момент запуска, в файлы и скрипты они не попадают.
Таймаут шага — `SMOKE_TIMEOUT` (по умолчанию 900 с).

Шаги скрипта и артефакты:

1. **CheckConfig** — `DESIGNER /CheckConfig -ConfigLogIntegrity
   -IncorrectReferences -ThinClient -Server`. Замечания — в
   `build/check-config.log`; непустой лог = провал шага. Если среди замечаний
   есть ошибка компиляции (позиция вида `{ОбщийМодуль.Имя.Модуль(859,37)}`),
   шаг 2 не запускается вовсе: клиент с несобирающимся модулем всё равно не
   поднимется, а прогон только съест таймаут.
2. **СмокТест** — `ENTERPRISE /C "СмокТест;build/smoke-report.txt"`. Формат
   отчёта, по строке на событие:
   - `СТАРТ;<дата>` — клиент дошёл до прогона;
   - `ОШИБКА;<что проверялось>;<описание в одну строку>` — форма не открылась
     или печатная форма не сформировалась;
   - `ПУСТО;<печатная форма>` — сформирована, но табличный документ пустой;
   - `ПРОПУСК;<что>;<причина>` — проверять не на чем (в базе нет объекта) или
     проверка исключена списком;
   - `ИТОГ;Всего=N;Ошибок=M;ПечатныхФорм=K;ОшибокПечати=L` — маркер завершения
     прогона (по нему скрипт понимает, что клиент отработал).
   Строки `СТАРТ` скрипт ждёт `SMOKE_START_TIMEOUT` секунд (по умолчанию 120):
   не дождался — снимает клиент и валит прогон, не тратя общий таймаут.
   Клиентский лог платформы — `build/smoke-client.log` (смотреть, если отчёт
   не появился: не найдена база, не прошла аутентификация и т.п.).

Скрипт не полагается на коды возврата `1cv8` (на macOS процесс-обёртка может
падать, пока работу делает дочерний процесс): он ждёт завершения процессов по
паттерну командной строки и признаков готовности в файлах. Итог — `ТЕСТЫ
ПРОЙДЕНЫ` / `ТЕСТЫ НЕ ПРОЙДЕНЫ` и код возврата 0/1.

### Разбор ошибок

- Каждая строка `ОШИБКА;` разбирается до причины: либо это дефект (чинится до
  релиза), либо форма легитимно не открывается без параметров — тогда она
  вносится в `ПропускаемыеФормы()` модуля формы обработки `СмокТест`
  с комментарием-причиной, и причина дублируется в реестре `docs/TESTS.xlsx`.
- Печатная форма, которую нельзя сформировать без параметров команды, вносится
  так же — в `ПропускаемыеПечатныеФормы()`. Строки `ПУСТО;` разбираются глазами:
  у образца могло не быть строк, но пустая форма у документа с данными — дефект.
- Строки `ПРОПУСК;Печать.<объект>;в базе нет ни одного объекта` — не ошибка, но
  и не покрытие: если объект важен, в базу заводится образец.
- Замечания CheckConfig разбираются все; допустимых «известных» замечаний нет —
  если такие появятся, для них заводится явный фильтр в `smoke.sh` с причиной.

## Образцы объектов для печати: обработка ТестовыеДанные

Проход печати проверяет печатную форму только там, где в базе есть хотя бы один
объект (то же и у прохода форм на образцах). На тестовой базе (копия drissotex) образцов не было у 22 объектов из 25 — их печать
не проверялась ничем, и в отчёте они писались строкой
`ПРОПУСК;Печать.<объект>;в базе нет ни одного объекта`.

Образцы заводит обработка `ТестовыеДанные` подсистемы «Автотесты»:

```bash
scripts/fixtures.sh [каталог-базы]      # по умолчанию build/ib
```

Скрипт **записывает данные** — документы остаются в базе. Запускать только на тестовой базе.

Как заполняется образец:

1. Объект, у которого образец уже есть, пропускается — обработка идемпотентна, повторный
   запуск ничего не создаёт.
2. Реквизиты-ссылки заполняются по метаданным: первый непомеченный элемент справочника
   (группы не берутся). Контрагент берётся вместе со своим договором — договор выбирается
   первым, поэтому пара заведомо согласована.
3. Особенности видов документов — хозяйственная операция, строки табличных частей, документ-
   основание — заданы явно в `ДовестиТоварныйОбразец`, `ДовестиДенежныйОбразец` и
   `ДовестиПрочийОбразец`. Новый документ с печатью — новое правило туда же.
4. Документ пробуется провести; если проведение не проходит (в тестовой базе нет остатков,
   не хватает связанных данных), он остаётся записанным: печати этого достаточно.
   В отчёте это видно — `проведен` или `записан без проведения`.
5. Комментарий образца — «Образец автотеста»: по нему видно, что документ заведён прогоном,
   и его можно найти отбором.

Отчёт `build/fixtures-report.txt`:

```
СОЗДАН;Документ.ОприходованиеТоваров;000000012;проведен
ОШИБКА;Документ.ВыплатаЗарплаты;<описание>
ИТОГ;Создано=N;Ошибок=M;Было=K
```

Обработка `ТестовыеДанные` своей формы не имеет: клиентским запускателем служит форма
`СмокТест` — она открывается с параметром `ТолькоТестовыеДанные`, потому что серверную
функцию модуля менеджера с клиента иначе не позвать.

Заполнение — разовый шаг: после него база держит образцы, и прогон печати закрывает все
печатные формы конфигурации. Пересоздали базу — прогнать `fixtures.sh` заново.

## Headless-первый запуск: тест initial-fill (уровень 2.5)

Базу клиента из хаба tinycio поднимает скрипт на сервере, без визарда первого запуска:
обработка `НачальноеЗаполнение` (подсистема «Обновление программы») заводит организацию,
пользователей и служебного администратора из JSON. Контракт — `docs/DEPLOY.md`.

```bash
scripts/dist-build.sh 2.0.14.11            # CF из обновлённой build/ib
scripts/initial-fill-test.sh build/dist/maERP-2.0.14.11.cf
```

Что делает тест (база `build/ib-initial` пересоздаётся, `build/ib` не трогается):

1. Пустая база из CF (`scripts/ib-create.sh`).
2. `scripts/initial-fill.sh` с образцом `scripts/initial-fill.example.json`, пароли
   подставляются случайные — только во временный payload с правами 600, удаляется на выходе.
   Проверка result-файла: `success`, `organization_created`, все `users[].created`,
   `support_admin_created` = `true`; `organizations_total` и `users_total` > 0 — это
   отрицание условия визарда «ноль организаций и ноль пользователей»; слова `password`
   в result нет.
3. Тот же payload второй раз под созданным администратором: успех, всё `created: false`
   (идемпотентность — раннер хаба вправе повторить задание).
4. `scripts/smoke.sh` на этой базе под созданным администратором — итог
   `ТЕСТЫ ПРОЙДЕНЫ`. `INITIAL_FILL_NO_SMOKE=1` пропускает шаг для быстрой проверки.

Образец payload задаёт отрасль «Строительство», поэтому тест сверяет и
`industry_attributes_created`: 4 после первого заполнения (реквизиты объекта
недвижимости у номенклатуры заведены), 0 после повтора.

Проверка визарда глазами остаётся за человеком: на пустой базе визард открывается,
на последнем шаге показывает пароль `tinycio-1c` один раз; на заполненной — не открывается.

## Тесты документов (уровень 3)

Обработка `ТестыДокументов` подсистемы «Автотесты» проводит ключевые документы и
сверяет движения по регистрам — то, чего смок не видит (форма открылась, а проводится
ли документ и правильно ли, он не знает).

```bash
scripts/doctests.sh [каталог-базы]      # по умолчанию build/ib
```

Запуск тот же, что у смока: `/C "ТестыДокументов;<отчёт>"`, маркеры `СТАРТ;` и
`ИТОГ;`, ожидание в `run-lib.sh`, доступ через `SMOKE_USER` / `SMOKE_PWD`. Отчёт
`build/doctests-report.txt`, по строке на сценарий:

- `СТАРТ;Сценариев=N` — клиент поднялся;
- `ОК;<сценарий>;<что проверено>`;
- `ОШИБКА;<сценарий>;<описание>` — не прошла проверка заполнения, проведение или
  сверка движений; в описании — текст исключения и сообщения пользователю из
  `ОбработкаПроведения` (причина отказа);
- `ПРОПУСК;<сценарий>;<причина>` — в базе нет условий для сценария;
- `ИТОГ;Сценариев=N;Ошибок=M;Пропущено=K`.

Как устроен сценарий:

1. **Данные заводятся заново** внутри транзакции сценария: контрагент (покупатель,
   поставщик и субподрядчик) с договорами обоих видов, склад, касса, банковский счёт,
   сотрудник, единица измерения, номенклатура трёх видов — товар, сырьё и продукция с
   технологической картой. Из базы берутся только первая организация, валюта
   регламентированного учёта и предопределённые элементы (ставка «Без НДС», типы
   оплаты, статьи ДДС). Свежие номенклатура и склад дают нулевые остатки, поэтому
   ожидаемые значения не зависят от содержимого базы, а по объекту расчётов сверяется
   долг только по своим документам. Наименования и комментарии помечены «Тест уровня 3».
2. **Документы** датируются на 100 секунд раньше текущего момента с шагом в секунду —
   порядок на оси времени регистров совпадает с порядком создания. Перед записью
   вызывается `ПроверитьЗаполнение()` — как это делает форма; затем запись с
   проведением. Количества и цены — в одном месте, `ЧислаСценариев()`, ожидаемые
   остатки считаются из них.
3. **Сверки** — запросы к остаткам и оборотам регистров (`ТоварыВНаличии`,
   `ТоварыВПереработке`, `ВзаиморасчётыСПокупателями`, `ВзаиморасчётыСПоставщиками`,
   `Продажи`, `ДенежныеСредстваОрганизаций`, `Зарплата`). Долг покупателя —
   положительный остаток, долг поставщику — отрицательный: так их читают
   `ПолучитьЗадолженностьКлиентовПоКлассификации` и
   `ПолучитьЗадолженностьПоставшиковПоКлассификации`, и так их гасят оплаты.
4. **Откат всегда**: и после успеха, и после ошибки. Прогон безопасен на копии базы
   клиента.

Сценарии первой очереди:

| Сценарий | Документы | Что сверяется |
|---|---|---|
| Закупка | Поступление товаров | остаток и себестоимость на складе, долг поставщику по документу |
| Продажа | Заказ покупателя → реализация по заказу → ПКО по реализации | основание и сумма реализации, остаток, количество/выручка/себестоимость в `Продажи`, долг покупателя до и после оплаты, деньги в кассе |
| ВозвратОтПокупателя | Реализация → возврат заполнением по реализации | товар вернулся той же партией (количество и себестоимость), продажи сторнированы, долг покупателя закрыт |
| ВыпускПродукции | Поступление сырья → выпуск по техкарте | списание сырья по карте, приход продукции по себестоимости сырья; ПРОПУСК при выключенной опции «Производство» |
| Переработка | Поступление сырья → передача в переработку → поступление из переработки заполнением по передаче | остатки на складе и у переработчика, себестоимость продукции с услугами, долг переработчику |
| Зарплата | Начисление → ведомость заполнением по начислению → РКО по ведомости | остаток по сотруднику после начисления и выплаты, сумма ведомости, деньги в кассе; ПРОПУСК, если дата начала расчёта зарплаты позже даты теста |
| БезналичныеДеньги | Поступление и реализация → поступление безналичных по реализации → списание поставщику по поступлению | оба долга закрыты, остаток на счёте |
| ДополнительныеРеквизиты | `УправлениеСвойствами` | реквизит и сведение заводятся идемпотентно, значения читаются по имени из табличной части и регистра |
| Отрасль | `НачальноеЗаполнениеВызовСервера.ПрименитьОтрасль` | «Строительство» заводит четыре реквизита и ставит константу, повтор — 0, «Торговля» — 0 |

**Новый документооборот — новый сценарий.** Разработка документа не считается
законченной без сценария здесь: имя в `ИменаСценариев()`, ветка в `СценарийПоИмени`,
функция `Сценарий<Имя>` и строка в таблице выше и в `docs/TESTS.xlsx`. Помощники
для этого уже есть: `НовыйДокумент`, `ДобавитьСтрокуТоваров`, `Провести`,
`ДокументЗакупки`, `ДокументРеализации`, `ОстатокТовара`, `ПроверитьРавенство`.

Чего уровень 3 не видит: клиентскую логику форм (обработчики `ПриИзменении`,
подборы, автозаполнение цен) — документы заполняются кодом. Это уровень 4.

## Регламент

1. **Перед сборкой релиза прокатываются все тесты**: `scripts/lint.sh` без
   новых замечаний против baseline, `scripts/refcheck.py` без новых расхождений,
   `scripts/smoke.sh` и `scripts/doctests.sh` на обновлённой `build/ib` с итогом
   `ТЕСТЫ ПРОЙДЕНЫ` и `scripts/initial-fill-test.sh` на собранном CF с итогом
   `ТЕСТ ПРОЙДЕН`. Это обязательный шаг чек-листа релиза (`docs/RELEASING.md`),
   релиз с падающими тестами не собирается.
2. **Новый функционал расширяет тесты.** Разработка формы, документа или
   команды не считается законченной, пока: новые формы проходят смок (они
   попадают в перебор автоматически — но прогон надо выполнить; неосновная форма
   объекта — строка в `ДополнительныеФормыОбъектов()`); для нового документооборота
   добавляется сценарий в `ТестыДокументов` (создание, запись, проведение, движения);
   изменения состава тестов фиксируются в `docs/TESTS.xlsx`.
3. После обновления базы клиента смок-прогон и тесты документов на ней —
   рекомендуемый приёмочный контроль (уровни 1–3 данные не меняют).
