# Автоматизированные тесты maERP

Тесты гоняются на живой базе (по умолчанию — тестовая база сборки `build/ib`,
она же drissotex-тест). Реестр тестов с покрытием — `docs/TESTS.xlsx`.

## Состав тестов

| Уровень | Что проверяет | Чем | Разрушает данные |
|---|---|---|---|
| 0. Статический анализ | Стиль и типовые ошибки BSL | `scripts/lint.sh` (BSL LS) | нет |
| 0.5. Сверка ссылок | Обращения к объектам, которых в конфигурации нет | `scripts/refcheck.py` | нет |
| 1. Проверка конфигурации | Ссылочную целостность метаданных, компилируемость модулей (тонкий клиент, сервер) | `scripts/smoke.sh`, шаг CheckConfig | нет |
| 2. Смок «открыть все формы» и «напечатать всё» | `ПриСозданииНаСервере` каждой формы; формирование каждой печатной формы | `scripts/smoke.sh`, шаг СмокТест | нет |
| 3. Создание/запись/проведение | Жизненный цикл ключевых документов, движения по регистрам | план: серверные тесты в транзакции с откатом | нет (откат) |
| 4. Сценарные UI-тесты | Клиентскую логику, обработчики, подборы | план: тест-клиент платформы / Vanessa | да — только на копии |

Уровни 0–2 реализованы. Уровни 3–4 добавляются, когда появится функционал,
который ими реально ломается; решение фиксируется здесь и в `docs/TESTS.xlsx`.

Уровни 0 и 0.5 работают на исходниках и не требуют базы — их гоняю сразу после
правки модулей. Уровни 1–2 работают на базе `build/ib`, а её обновляет из EDT
владелец: без этого проверяется код прошлой сборки.

## Сверка ссылок (уровень 0.5)

```bash
scripts/refcheck.py
```

`Константы.Х`, `Перечисления.Х`, `РегистрыСведений.Х`, `БиблиотекаКартинок.Х`,
типы `Тип("ДокументСсылка.Х")`, полные имена в строках (`"ОбщаяФорма.Х"`,
`"Документ.Х.Макет.Y"`) и вызовы `ОбщийМодуль.Метод()` сверяются с деревом
метаданных `src/cf/src`. Всё это компилируется и проходит CheckConfig, но падает
в рантайме — а смок видит только то, что лежит на пути открытия формы.

Имена приводятся к NFC: macOS хранит имена каталогов в разложенном виде, и без
нормализации любое имя с «ё» или «й» выглядит несуществующим.

Принятые расхождения (стандартные картинки платформы, наследие бухгалтерского
контура) лежат в `scripts/refcheck-known.txt`; обновить файл целиком —
`scripts/refcheck.py --update-known`. Новое расхождение — ошибка: разбирается до
сдачи работы, а в файл попадает только вместе с записью причины в
`docs/TECHDEBT.md`.

## Как устроен смок-тест (уровень 2)

Обработка `СмокТест` (подсистема «Автотесты», см. ниже):

1. Клиент запускается с параметром `/C "СмокТест;<путь-к-отчёту>"`. Хук в
   `ПриНачалеРаботыСистемы` модуля приложения видит параметр, открывает форму
   обработки и пропускает обычную инициализацию клиента.
2. Первым делом в отчёт пишется строка `СТАРТ;<дата>` — по ней скрипт понимает,
   что клиент поднялся и прогон пошёл.
3. **Проход 1, формы.** Сервер собирает полные имена всех форм конфигурации
   (справочники, документы, журналы, отчёты, обработки, планы, регистры,
   критерии отбора, общие формы); формы только для мобильного устройства
   пропускаются. Клиент по каждому имени вызывает `ПолучитьФорму()` — форма не
   показывается, но её `ПриСозданииНаСервере` выполняется полностью.
4. **Проход 2, печатные формы.** По каждому объекту из
   `ПечатныеФормы.ОбъектыСКомандамиПечати()` берётся один образец из базы
   (последний проведённый документ; для лидов — заказ покупателя по лиду) и
   формируется каждая печатная форма объекта через
   `ПечатныеФормы.СформироватьПечатныеФормы`. Проверяется, что модуль менеджера
   вернул табличный документ; пустой документ пишется строкой `ПУСТО` и ошибкой
   не считается. Печатных форм в конфигурации больше полусотни, и ни одна из них
   не открывается проходом по формам — до этого прохода они не проверялись ничем.
   Дополнительно в тексте сформированной формы ищется номер документа-образца:
   если его там нет, пишется строка `ПОДОЗРЕНИЕ` — форма сформировалась, но шапка
   может быть пустой (см. «Чего прогон не видит»). Это не ошибка прогона: список
   таких строк смотрится глазами, а печатные формы, где номера заведомо нет,
   заносятся в `ПечатныеФормыБезНомера()` вместе с причиной здесь.
5. В конце пишется отчёт и клиент завершает работу. При интерактивном открытии
   формы обработки (без параметра запуска) итог выводится в окно сообщений.

Оба прохода только читают данные, поэтому прогон безопасен и на рабочей базе
клиента — например, как приёмочный контроль после обновления.

### Чего прогон не видит

Зелёный прогон означает «форма открылась» и «печать не упала», а не «напечатано
правильно». Пустое поле в шапке для прогона неотличимо от заполненного: платформа
исключения не выдаёт. Отсюда проверка номера документа (строка `ПОДОЗРЕНИЕ`) — она
ловит самый частый случай, шапку, собранную из итоговой строки запроса без
агрегатных функций (`docs/TECHDEBT.md`). Всё остальное содержимое печати —
суммы, реквизиты организации, скидки — проверяется только глазами, по одной
готовой форме каждого вида перед сдачей релиза.

## Что лежит в конфигурации: подсистема «Автотесты»

Всё, что относится к тестам, собрано в отдельной подсистеме `Автотесты`:

- `Обработка.СмокТест` — прогон. В **модуле менеджера** серверная логика обоих
  проходов: `ПроверяемыеФормы()` (состав форм и список пропусков) и
  `ПрогнатьПечатныеФормы()` (образцы объектов, формирование, пропуски печати).
  В **модуле формы** — только клиентский цикл прогона и запись отчёта.
- `ОбщийМодуль.АвтотестыКлиент` — `ОбработатьЗапускТеста()`: разбирает параметр
  запуска и открывает форму прогона. Модуль управляемого приложения зовёт его
  одной строкой и о тестах больше ничего не знает.

Подсистема **не входит в командный интерфейс**: показывать пользователю нечего,
прогон запускают скрипты, а вручную обработка открывается через «Все функции».
Понадобится пункт меню — достаточно поставить `includeInCommandInterface` в
`Автотесты.mdo` и решить, каким ролям он виден.

Скрипты (`lint.sh`, `refcheck.py`, `smoke.sh`) живут в `scripts/` рядом с
остальной сборочной обвязкой — в конфигурацию они не входят.

## Алгоритм запуска и сбора ошибок

```bash
scripts/smoke.sh [каталог-базы]      # по умолчанию build/ib
```

База с пользователями: логин и пароль — только через переменные окружения
`SMOKE_USER` / `SMOKE_PWD` в момент запуска, в файлы и скрипты они не попадают.
Таймаут шага — `SMOKE_TIMEOUT` (по умолчанию 900 с).

Шаги скрипта и артефакты:

1. **CheckConfig** — `DESIGNER /CheckConfig -ConfigLogIntegrity
   -IncorrectReferences -ThinClient -Server`. Замечания — в
   `build/check-config.log`; непустой лог = провал шага. Если среди замечаний
   есть ошибка компиляции (позиция вида `{ОбщийМодуль.Имя.Модуль(859,37)}`),
   шаг 2 не запускается вовсе: клиент с несобирающимся модулем всё равно не
   поднимется, а прогон только съест таймаут.
2. **СмокТест** — `ENTERPRISE /C "СмокТест;build/smoke-report.txt"`. Формат
   отчёта, по строке на событие:
   - `СТАРТ;<дата>` — клиент дошёл до прогона;
   - `ОШИБКА;<что проверялось>;<описание в одну строку>` — форма не открылась
     или печатная форма не сформировалась;
   - `ПУСТО;<печатная форма>` — сформирована, но табличный документ пустой;
   - `ПРОПУСК;<что>;<причина>` — проверять не на чем (в базе нет объекта) или
     проверка исключена списком;
   - `ИТОГ;Всего=N;Ошибок=M;ПечатныхФорм=K;ОшибокПечати=L` — маркер завершения
     прогона (по нему скрипт понимает, что клиент отработал).
   Строки `СТАРТ` скрипт ждёт `SMOKE_START_TIMEOUT` секунд (по умолчанию 120):
   не дождался — снимает клиент и валит прогон, не тратя общий таймаут.
   Клиентский лог платформы — `build/smoke-client.log` (смотреть, если отчёт
   не появился: не найдена база, не прошла аутентификация и т.п.).

Скрипт не полагается на коды возврата `1cv8` (на macOS процесс-обёртка может
падать, пока работу делает дочерний процесс): он ждёт завершения процессов по
паттерну командной строки и признаков готовности в файлах. Итог — `ТЕСТЫ
ПРОЙДЕНЫ` / `ТЕСТЫ НЕ ПРОЙДЕНЫ` и код возврата 0/1.

### Разбор ошибок

- Каждая строка `ОШИБКА;` разбирается до причины: либо это дефект (чинится до
  релиза), либо форма легитимно не открывается без параметров — тогда она
  вносится в `ПропускаемыеФормы()` модуля формы обработки `СмокТест`
  с комментарием-причиной, и причина дублируется в реестре `docs/TESTS.xlsx`.
- Печатная форма, которую нельзя сформировать без параметров команды, вносится
  так же — в `ПропускаемыеПечатныеФормы()`. Строки `ПУСТО;` разбираются глазами:
  у образца могло не быть строк, но пустая форма у документа с данными — дефект.
- Строки `ПРОПУСК;Печать.<объект>;в базе нет ни одного объекта` — не ошибка, но
  и не покрытие: если объект важен, в базу заводится образец.
- Замечания CheckConfig разбираются все; допустимых «известных» замечаний нет —
  если такие появятся, для них заводится явный фильтр в `smoke.sh` с причиной.

**Человек (владелец):**

  без этого база не содержит свежих правок, и смок проверяет старый код;
- закрыть базу в EDT перед прогоном (агент EDT блокирует `build/ib`);
- запуск на базах клиентов (доступы — только у владельца);
- приёмка: ручной регресс по чек-листам `docs/drissotex-analysis/wave*-check.md`
  и решение «релизим/не релизим»;
- проверка обновления на копии базы предыдущей версии: механизм
  `ОбновлениеПрограммы` при первом входе администратора поднимает версию в
  регистре `ВерсииПодсистем`, ранее выполненные заполнения данных не
  повторяются, показывается «Что нового», в журнале регистрации по событию
  «Обновление программы» ошибок нет (шаг 7 чек-листа релиза).

## План: покрытие печати образцами данных

Второй проход смока проверяет печатную форму только там, где в базе есть хотя бы один
объект. На тестовой базе (копия drissotex) образцов нет у 22 объектов из 25 — их печать
не проверяется ничем:

| Объект | Печатных форм |
|---|---|
| `Документ.ВозвратОтПокупателя` | накладная возврата |
| `Документ.ВозвратОтПокупателяНалоговый` | накладная возврата |
| `Документ.ВыплатаЗарплаты` | ведомость |
| `Документ.ЗаказПоставщику` | заказ поставщику |
| `Документ.КассоваяСмена` | Z-отчёт |
| `Документ.КорректировкаДолга` | акт корректировки |
| `Документ.НалоговаяНакладная` | налоговая накладная |
| `Документ.НалоговаяНакладнаяПокупка` | налоговая накладная покупки |
| `Документ.ОприходованиеТоваров` | акт оприходования |
| `Документ.ОтгрузкаТовара` | накладная на отгрузку |
| `Документ.ПередачаВПереработку` | накладная на передачу |
| `Документ.ПеремещениеТоваров` | накладная на перемещение |
| `Документ.ПлатёжнаяВедомостьНаАванс` | ведомость на аванс |
| `Документ.ПоступлениеИзПереработки` | накладная на поступление |
| `Документ.ПредложениеПоставщика` | предложение |
| `Документ.ПриходныйКассовыйОрдер` | ордер, квитанция |
| `Документ.РасходныйКассовыйОрдер` | ордер |
| `Документ.СверкаВзаиморасчётов` | акт сверки |
| `Документ.СписаниеТоваров` | акт списания |
| `Документ.ТабельУчётаРабочегоВремени` | табель |
| `Документ.УстановкаЦенНоменклатуры` | прайс-лист |
| `РегистрСведений.Лиды` | заказ и накладная по лиду |

Что нужно: завести в `build/ib` по одному заполненному документу каждого вида (проведённому
там, где проведение обязательно) — тогда прогон закроет все печатные формы конфигурации,
а не только реализацию и заказ покупателя. Работа человека: данные заводятся руками
в тестовой базе, машина после этого только гоняет прогон. Пока образца нет, прогон пишет
строку `ПРОПУСК;Печать.<объект>;в базе нет ни одного объекта` — она и есть индикатор
непокрытого объекта, список выше сверяется по ней.

Альтернатива, если заводить данные руками не хочется: обработка-фикстура, создающая
минимальный комплект документов в транзакции с откатом. Её имеет смысл делать вместе
с уровнем 3 (создание/запись/проведение) — там понадобится ровно тот же комплект.

## Регламент

1. **Перед сборкой релиза прокатываются все тесты**: `scripts/lint.sh` без
   новых замечаний против baseline, `scripts/refcheck.py` без новых расхождений
   и `scripts/smoke.sh` на обновлённой `build/ib` с итогом `ТЕСТЫ ПРОЙДЕНЫ`. Это обязательный шаг чек-листа
   релиза (`docs/RELEASING.md`), релиз с падающими тестами не собирается.
2. **Новый функционал расширяет тесты.** Разработка формы, документа или
   команды не считается законченной, пока: новые формы проходят смок (они
   попадают в перебор автоматически — но прогон надо выполнить); для нового
   документооборота, когда появится уровень 3, добавляется тест
   создание/запись/проведение; изменения состава тестов фиксируются в
   `docs/TESTS.xlsx`.
3. После обновления базы клиента смок-прогон на ней — рекомендуемый
   приёмочный контроль (уровни 1–2 данные не меняют).
