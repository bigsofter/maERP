# Промпт этапа 12а: headless-первый запуск и контракт скриптов развёртывания

Скопировать в новую сессию Claude Code в `~/Dev/maERP` целиком. Парный промпт для
хаба — `docs/hub/tinycio-start-prompt.md`; сессии независимы, общий контракт — §5 плана
`../tinycio/docs/plans/feature-maerp-onboarding.md`.

---

Выполни этап 12а плана `docs/ROADMAP.md` (блок 11, «Онбординг клиента через хаб»,
находки — `docs/TECHDEBT.md`, раздел «Онбординг через хаб tinycio»). Сначала прочитай
целиком §5.3, §5.4 и §14 плана хаба `../tinycio/docs/plans/feature-maerp-onboarding.md`
— это контракт, под который делается работа; здесь только постановка по исполнению.

Цель: базу maERP можно развернуть для клиента **без единого интерактивного шага** —
скрипт на 1С-сервере создаёт базу из CF, запускает начальное заполнение из JSON,
и клиент при первом входе попадает в готовую программу, а не в визард. Попутно
закрывается развилка **Р3** (пароль скрытого администратора зашит в публичном репозитории).

Состав работ:

1. **Серверный модуль начального заполнения.** Логика визарда
   `ОбщаяФорма.ФормаПервогоЗапуска` (`СоздатьОрганизациюПервогоЗапуска`,
   `СоздатьПользователейПервогоЗапуска`, `СоздатьФизическоеЛицо`, создание скрытого
   администратора) переезжает из модуля формы в общий модуль
   `НачальноеЗаполнениеВызовСервера` (директивы явно). Вход — структура с теми же
   данными, что собирает визард: организация (наименование, вид, префикс, страна,
   валюта, язык), список пользователей (логин, пароль, ФИО, e-mail, язык, роли),
   параметры скрытого администратора. Визард после переезда зовёт этот модуль и
   работает как прежде — это проверяется регрессом.
2. **Обработка `НачальноеЗаполнение`** в подсистеме `ОбновлениеПрограммы` (в
   командный интерфейс не включать) с запуском через параметр
   `/C "НачальноеЗаполнение;<путь-к-payload.json>;<путь-к-result.json>"` по образцу
   `СмокТест` (`АвтотестыКлиент.ОбработатьЗапускТеста` → форма-запускатель →
   серверная функция модуля менеджера). Требования:
   - формат payload — JSON `initial_fill` из §5.3 плана хаба: `tenant_id`, `base_name`,
     `company{name, kind, country, currency, language}`, `owner{full_name, email, phone}`,
     `users[{login, full_name, email, language, roles, password}]`,
     `support_admin{login, password}`; лишние поля игнорировать, отсутствующие
     обязательные — ошибка с перечнем;
   - идемпотентность: повторный запуск на уже заполненной базе ничего не создаёт
     второй раз (организация по наименованию, пользователи по логину) и завершается
     успехом;
   - result-файл — JSON `{"organization_created": true, "users": [{"login": …,
     "created": true|false}]}`; пароли в result и в отчёт не попадают;
   - маркеры хода в отчёте, как у смока: `СТАРТ;` в начале, `ИТОГ;Успех=1|0;<текст>`
     в конце, затем `ЗавершитьРаботуСистемы` — `scripts/run-lib.sh` ждёт именно маркер,
     кодам возврата 1cv8 не верит;
   - запуск только тонким клиентом (толстый падает на компиляции общих модулей
     «Сервер + Вызов сервера», см. `scripts/smoke.sh`).
3. **Скрытый администратор `tinycio-1c`.** Пароль больше нигде не зашит: в headless-режиме
   берётся из `support_admin.password` payload'а, в визарде генерируется случайно
   (`Новый УникальныйИдентификатор` достаточно) и показывается один раз на последнем
   шаге с текстом «сохраните, повторно не показывается». Заодно убрать вторую зашитую
   учётную запись в `ПроцедурыРегламентныхЗаданий` (строка ~303, `AddAuthentication`):
   там уже есть константы `АдминистраторКластера`/`ПарольКластера` — использовать их или
   вырезать ветку, если она мертва на Linux (COM-объект `v83.COMConnector` — только
   Windows; решение отметить в TECHDEBT).
4. **Локальный dev-скрипт `scripts/initial-fill.sh <база> <payload.json>`** — обёртка над
   тонким клиентом по образцу `scripts/fixtures.sh` (`SMOKE_USER`/`SMOKE_PWD` не нужны:
   база пустая, входа без пароля достаточно; после заполнения — уже нет). Плюс
   `scripts/initial-fill.example.json` с образцом payload'а без реальных паролей.
   Серверный скрипт `initial-fill.sh` для раннера — вне git, его пишет владелец по этому
   образцу; в `docs/RELEASING.md` или новом `docs/DEPLOY.md` описать контракт: payload через
   файл с правами 600 во временном каталоге, удаляется скриптом после запуска, пароли в
   argv и логи не попадают.
5. **Тест.** В `scripts/smoke.sh` или отдельным шагом `docs/TESTING.md`: сценарий «пустая
   база из CF → `initial-fill.sh` с образцом → смок форм проходит, визард при входе не
   открывается» (проверка — `БрендированиеВызовСервера.ПолучитьКоличествоОрганизаций() > 0`
   после заполнения). Обновить `docs/TESTS.xlsx` по правилу «человек/машина».
6. **Свойства конфигурации** `Vendor`, `Copyright`, `VendorInformationAddress` в
   `Configuration.mdo` — сейчас цифры-заглушки на четырёх языках. Спроси у владельца
   значения; если ответа нет, ставь `TinyCIO`, `© TinyCIO`, `https://tinycio.com` на всех
   языках и отметь в отчёте.
7. **Документация и долг.** Закрыть Р3 в таблице развилок `docs/ROADMAP.md` и пункт «Пароль
   скрытого администратора» в блоке 1; в `docs/TECHDEBT.md` пометить находки раздела
   «Онбординг через хаб» как закрытые (первая и третья) с датой; новые находки — туда же.

Правила исполнения:

- Перед правкой `Form.form`, `.mdo`, запросов и макетов — `checklist` из MCP `tiny1c`
  (направления `core`, `greenfield`), по симптому — `lookup_rule`. Новую пойманную ошибку
  добавить правилом в tiny1C.
- После правки модулей — `scripts/lint.sh` и `scripts/refcheck.py`; замечания разобрать
  до сдачи. Синтаксическую проверку и Refresh в EDT делает владелец — сказать явно.
- Поднять `Y` версии в `Configuration.mdo` и завести секцию в общем макете
  `ОписаниеИзменений` с блоками ru/fr/en/es — формулировками для пользователя
  («Первый запуск: пароль служебного администратора больше не задан заранее» и т. п.).
- Один коммит — одно изменение, сообщения по-русски, без трейлера Co-Authored-By. Ветка
  `develop`, push — по слову владельца.
- Не трогать `build/`, `DT-INF/`, XML-выгрузки и `.cf`. `src/cf` — единственный источник.
- Что не делать: раннер, очередь, лендинг — это сторона хаба; продовые скрипты 1С-сервера
  — владелец; смену модели прав скрытого администратора (аутентификация ОС, выделенная
  роль) — не в этом этапе, только пароль.

В отчёте владельцу: версия, на которую он обновляется; что проверить руками (визард на
пустой базе, повторный headless-запуск, вход клиента без визарда); открытые вопросы.
