# Среда разработки 1С: EDT + VSCode + Claude Code

Пошаговое руководство под твою конфигурацию проекта.

**Топология (по твоим ответам):**

- **Dev-машина:** macOS (этот Mac) — здесь 1C:EDT, VSCode, Claude Code, локальная dev-ИБ.
- **Сервер:** отдельный **Windows-сервер** с 1С:Сервер + СУБД (MS SQL/PostgreSQL) — живая база, test, prod.
- **Код:** выгрузки в файлы ещё нет — нужна первичная выгрузка из живой базы.
- **Конфигурация:** самописная / снята с поддержки → можно править основную конфигурацию напрямую, расширения не обязательны.
- **Git/CI:** с нуля.

---

## 0. Важный контекст перед стартом

### 0.1. Расхождение с `ARCHITECTURE.md`

В корне проекта лежит `ARCHITECTURE.md`, который описывает **совсем другой** проект — greenfield web-ERP на Go + TypeScript (maERP). Это путь «писать ERP с нуля». Текущий запрос — настроить разработку **на 1С**. Это две взаимоисключающие стратегии: либо строим своё на Go/TS, либо ведём проект на платформе 1С. Прежде чем вкладываться в инфраструктуру, стоит зафиксировать на уровне команды, какой путь основной (а `ARCHITECTURE.md` — оставить как анализ отклонённой альтернативы или наоборот). Дальше руководство исходит из выбора «1С».

### 0.2. Ограничения macOS, которые определяют всю схему

| Что | На macOS | Вывод |
|---|---|---|
| 1C:EDT | Работает | IDE ставим на Mac ✅ |
| Тонкий/толстый клиент 1С | Работает | Можно запускать/отлаживать ИБ ✅ |
| Файловая ИБ | Работает | Локальная dev-база на Mac ✅ |
| **1С:Сервер** | **Нет** | Сервер только на Windows-сервере |
| **HTTP-сервисы 1С** | **Нет** | «Живой» MCP к базе публикуем **на Windows**, Mac подключается по сети |
| BSL Language Server, MCP-серверы (Java/Go/Node) | Работают | Линт и AI-тулинг — на Mac ✅ |

Ключевой нюанс: «живой» MCP-сервер к базе (feenlace/mcp-1c) требует HTTP-сервиса 1С, а он под macOS не поднимается. Решение — опубликовать HTTP-сервис **на Windows-сервере** (Apache/IIS), а бинарник MCP запускать на Mac с указанием сетевого URL. Либо использовать офлайн-режим MCP по выгрузке файлов (без запущенной базы).

### 0.3. Реалистичные ожидания от AI в 1С

По публичному эксперименту (Claude Code + 1С, янв–фев 2026, Денис Матаков / Никита Клементьев) и практике сообщества:

| Задача | Оценка | Комментарий |
|---|---|---|
| Анализ кодовой базы | Отлично | Находит регистры/документы/запросы, строит зависимости, указывает номера строк |
| Документирование | Отлично | Экономит десятки часов |
| Код-ревью (с линтером) | Хорошо | Находит ошибки транзакций, устаревшие методы |
| Планы и декомпозиция | Отлично | Структурирует крупные задачи |
| Небольшие доработки BSL | Средне | Синтаксис верный, логику нужно проверять |
| Новые обработки с нуля | Средне | Много итераций |
| **Формы (XML управляемых форм)** | **Плохо** | Невалидный XML / ошибки XDTO — формы делаем руками в EDT |
| Оптимизация запросов / транзакции | Плохо | Синтаксис ок, **логику ломает** — только под ревью |
| Методы БСП | Плохо | Их AI плохо знает — проверять по справке/коду |

Вывод: **AI — это аналитик, документатор и ассистент по ревью**, а ключевые решения, форма и сложная бизнес-логика остаются за разработчиком. Линтер (BSL LS) и MCP к платформенному API резко повышают качество — подключаем их обязательно.

## 1. Что установить

### На Mac (dev-машина)

1. **1С:Платформа для macOS** (8.3.20+, лучше 8.3.24/8.3.25+). Скачать с портала `releases.1c.ru` (нужна учётка ИТС/партнёра). Даёт тонкий клиент, возможность файловых ИБ и каталог платформы для справки.
2. **1C:EDT** — `https://edt.1c.ru` или через «1С:Установка EDT» (Ring). Версия 2024.x/2025.x. В комплекте идёт свой JDK.
3. **JDK 17+** (Temurin) — `https://adoptium.net`. Нужен для BSL Language Server и MCP-сервера alkoleft. Проверка: `java -version`.
4. **VSCode** — `https://code.visualstudio.com`.
5. **Node.js 18+** — `https://nodejs.org` (для части тулинга/скриптов). Проверка: `node --version`.
6. **Git** — `git --version` (обычно есть; иначе из Xcode CLT/Homebrew).
7. **Claude Code** — `npm install -g @anthropic-ai/claude-code` (или по официальной инструкции Anthropic).
8. *(опционально)* **Go 1.22+** — если будешь собирать feenlace/mcp-1c из исходников; можно обойтись готовым бинарником.
9. *(опционально)* **OneScript / vanessa-runner** — для скриптов автоматизации (`opm install vanessa-runner`).

### На Windows-сервере

1. **1С:Платформа** (та же версия, что на Mac — критично, версии платформы должны совпадать).
2. **1С:Сервер** + СУБД (MS SQL Server или PostgreSQL).
3. **Веб-сервер** Apache 2.4 или IIS — для публикации HTTP-сервиса (нужен «живому» MCP) и веб-клиента.
4. **Git** (если runner CI будет здесь).

> Важно про версии платформы: dev (Mac), test и prod (Windows) должны быть на **одной версии платформы** или с понятной политикой обновления. Расхождение версий платформы — частый источник «у меня работает, на проде нет».

## 2. Шаг 1 — Первичная выгрузка конфигурации в файлы

Сейчас есть только живая база, поэтому первый шаг делаем **на Windows** (Конфигуратор имеет полный доступ к серверной базе).

### Два формата выгрузки — это важно

| Формат | Кто делает | Кто понимает | Для чего |
|---|---|---|---|
| **`.cf`** (бинарь конфигурации) | Конфигуратор / `DumpCfg` | Конфигуратор, EDT (импорт) | Перенос конфигурации целиком |
| **XML конфигуратора** (`DumpConfigToFiles`) | Конфигуратор / `DumpConfigToFiles` | gitsync, BSL LS, feenlace `--dump` | Классический Git-формат, CI |
| **EDT-формат** | EDT (импорт) | только EDT | Рабочее дерево проекта в EDT |

EDT хранит проект в **своём** формате (не равен XML конфигуратора). Поэтому стратегия:

- **Рабочее дерево** ведём в **EDT-формате** (EDT — основная IDE: формы, метаданные, компиляция, отладка).
- При необходимости конвертируем EDT ↔ формат конфигуратора командами `ring edt` (для CI, для BSL LS, для MCP `--dump`).

### Сделать выгрузку (на Windows-сервере)

**Через Конфигуратор (GUI):**

1. Открыть базу в Конфигураторе.
2. `Конфигурация → Сохранить конфигурацию в файл…` → получаем `prod.cf`.
3. *(или для классического Git)* `Конфигурация → Выгрузить конфигурацию в файлы…` → папка с XML.

**Через командную строку (для будущей автоматизации):**

```bat
REM Выгрузка в .cf
"C:\Program Files\1cv8\8.3.25.XXXX\bin\1cv8.exe" DESIGNER ^
  /S "1c-server\prod_base" /N Администратор /P пароль ^
  /DumpCfg "D:\export\prod.cf"

REM Выгрузка в XML-файлы (формат конфигуратора)
"C:\Program Files\1cv8\8.3.25.XXXX\bin\1cv8.exe" DESIGNER ^
  /S "1c-server\prod_base" /N Администратор /P пароль ^
  /DumpConfigToFiles "D:\export\src"
```

Перенести `prod.cf` (или папку `src`) на Mac (Git, общая папка, scp).

## 3. Шаг 2 — Проект в EDT и dev-база

### Импорт в EDT (на Mac)

1. Запустить EDT, создать/выбрать **Workspace**.
2. `Файл → Импорт → 1C:Enterprise → Конфигурация (.cf)` (или импорт из информационной базы, если подключишься к серверной dev-копии). EDT сконвертирует в свой формат и проиндексирует.
3. Дождаться полной сборки (валидация EDT покажет ошибки/предупреждения).

### Локальная dev-ИБ на Mac

Для запуска и отладки заведи **файловую информационную базу** на Mac:

- В EDT: правый клик по проекту → `Запустить` / `Отладка` — EDT предложит создать/привязать ИБ.
- Либо через список баз 1С (тонкий клиент): «Добавить → Создание новой ИБ → без конфигурации (для разработки)», потом загрузить `prod.cf`.

Так у каждого разработчика — своя изолированная база, эксперименты не задевают сервер.

> Альтернатива: подключаться EDT к **серверной dev-базе** на Windows. Но файловая локальная база на Mac быстрее для итераций и отладки клиентского кода.

## 4. Шаг 3 — Git-репозиторий

Репозиторий 1С-конфигурации делаем **отдельным** от Go-проекта maERP (это разные продукты).

1. `git init` в корне EDT-проекта (или подключить EDT к удалённому репозиторию).
2. Положить `.gitignore`, `.gitattributes`, `.editorconfig` из стартового комплекта (см. `starter-kit/`).
3. Первый коммит — импортированное дерево EDT.
4. Ветвление: `master/main` (= prod), `develop` (интеграция), `feature/*` (задачи). Для самописной конфигурации это работает как в обычной разработке.

`.gitattributes` помечает бинарные артефакты 1С и нормализует переводы строк — без него Git «портит» некоторые файлы. Файл в комплекте.

## 5. Шаг 4 — Связка с VSCode

Разделение ролей (это ключ к удобству):

- **EDT** — формы (визуальный редактор), метаданные, синтаксический контроль на компиляции, отладка, выгрузка/загрузка в ИБ.
- **VSCode + Claude Code** — массовое редактирование BSL, рефакторинг, поиск/анализ, линт через BSL Language Server, генерация документации и обработок.

Обе IDE открывают **одну и ту же папку проекта** и работают через Git. Главное правило: **не редактировать один и тот же файл одновременно в EDT и VSCode** — сохраняй в одной, синхронизируй, потом переключайся.

### Настройка VSCode

1. Поставить расширение **Language 1C (BSL)** (`1c-syntax.language-1c-bsl`).
2. Скачать **BSL Language Server** JAR: `https://github.com/1c-syntax/bsl-language-server/releases` (например `bsl-language-server-X.X.X-exec.jar`), положить в удобный путь.
3. Положить `.vscode/settings.json`, `.vscode/extensions.json`, `.bslls.json` из стартового комплекта; в `settings.json` прописать путь к JAR и к Java.
4. Линтер подсветит ошибки/дубли/нарушения стиля прямо при сохранении (>100 диагностик).

> BSL LS лучше всего «видит» код в формате конфигуратора. Если рабочее дерево в EDT-формате — либо настраивай линт на BSL-файлы (они текстовые и в EDT тоже лежат как `.bsl`), либо периодически конвертируй в формат конфигуратора для глубокого анализа/CI. Для повседневной подсветки BSL-файлов EDT-формата расширение работает.

## 6. Шаг 5 — Claude Code + MCP-серверы

### 6.1. Установка Claude Code

```bash
npm install -g @anthropic-ai/claude-code
cd /путь/к/проекту-1С
claude
```

### 6.2. MCP-сервер №1 (обязательный, работает на Mac) — платформенный API

**alkoleft/mcp-bsl-platform-context** — даёт AI «Синтаксис-помощник» 1С: поиск методов/свойств/типов, сигнатуры, конструкторы. **Не требует запущенной базы.** Именно его подключение в эксперименте стало переломным моментом («AI перестал выдумывать функции платформы»).

- Требует JDK 17+ и путь к установленной платформе 1С (для чтения справки).
- Скачать JAR из Releases (`mcp-bsl-context-X.Y.Z.jar`) или собрать `./gradlew build`.

Конфиг — в `.mcp.json` стартового комплекта (Claude Code читает `.mcp.json` в корне проекта):

```json
{
  "mcpServers": {
    "1c-platform": {
      "command": "java",
      "args": [
        "-jar", "/Users/ivan-gurkin/tools/mcp-bsl-context.jar",
        "--platform-path", "/opt/1cv8/x86_64/8.3.25.XXXX"
      ]
    }
  }
}
```

> Путь `--platform-path` на macOS обычно вида `/opt/1C/v8.3/x86_64` или внутри `.app` платформы — уточни по факту установки.

### 6.3. MCP-сервер №2 (опциональный) — живая база

**feenlace/mcp-1c** — Go-бинарник, AI видит метаданные/формы/код **реальной** базы, выполняет запросы (только SELECT), читает журнал регистрации. 9 инструментов в бесплатной версии.

Два способа под твою топологию:

- **Онлайн (полный):** на Windows-сервере установить расширение (`mcp-1c --install`) и опубликовать HTTP-сервис (Apache/IIS). На Mac запустить бинарник с сетевым URL:
  ```json
  {
    "mcpServers": {
      "1c-base": {
        "command": "/Users/ivan-gurkin/tools/mcp-1c",
        "args": ["--base", "http://1c-server:8080/hs/mcp-1c"]
      }
    }
  }
  ```
- **Офлайн (без базы):** указать выгрузку в файлы — работает `search_code` без запущенной 1С:
  ```json
  { "mcpServers": { "1c-base": { "command": "/Users/ivan-gurkin/tools/mcp-1c", "args": ["--dump", "/путь/к/src"] } } }
  ```

Начни с офлайн-режима по выгрузке — он работает сразу и не требует возни с публикацией. Онлайн добавишь, когда поднимешь HTTP-сервис на сервере.

### 6.4. MCP-сервер №3 (опциональный) — EDT

**DitriXNew/EDT-MCP** — плагин-MCP **внутри EDT**, даёт AI доступ к workspace EDT (метаданные/проект в терминах EDT). Полезен, если хочешь, чтобы Claude видел проект «глазами EDT». Ставится как плагин EDT, поднимает локальный MCP-эндпоинт.

### 6.5. Claude Code Skills для 1С

**Desko77/claude-code-skills-1c** — 86 скилов + 17 правил + команды специально для 1С (формы, метаданные, расширения, обработки, роли, СКД, db-операции, веб-публикация). Установка:

Часть скриптов на PowerShell (Windows), но есть Python-альтернативы и `v8unpack` (распаковка `.cf/.cfe/.epf` без платформы). Особо полезны правила `1c-coding-standards.md`, `anti_patterns.md`, `query-optimization-tips.md`, `code-review-checklist.md`.

### 6.6. CLAUDE.md — правила проекта

В корне 1С-репозитория положи `CLAUDE.md` (есть в комплекте). Он фиксирует: русские имена, стандарты 1С, запрет на генерацию XML форм, обязательную проверку API через MCP, приоритет БСП, прогон через BSL LS. Это именно то, что в эксперименте превратило «выдумки» в рабочий код.

## 7. Шаг 6 — Доработка форм

**Главное правило: формы не генерируем AI как XML.** Управляемая форма 1С — это XML с XDTO-структурой, который AI стабильно ломает (ошибки загрузки в конфигуратор). Правильный поток:

1. **Claude/разработчик** проектирует: какие реквизиты формы, элементы, команды, обработчики событий нужны — и пишет **BSL-обработчики** (`&НаКлиенте`/`&НаСервере`) + текстовую инструкцию «что добавить на форму».
2. **Разработчик в EDT** открывает форму в **визуальном редакторе форм**: добавляет элементы, реквизиты, команды, расставляет свойства, привязывает события к обработчикам.
3. BSL-модуль формы при этом можно дорабатывать в VSCode/Claude (это обычный текст), но привязку «элемент → событие» делает EDT.

Почему так: разделение «логика (BSL, текст — можно AI) ↔ разметка формы (XML/XDTO — только редактор)». Модуль формы соблюдает клиент-серверное разделение директив компиляции — следи за этим (правило `form_module_rules.md` из набора Desko77).

> Экспериментально: в наборе Desko77 есть скилы `1c-form-compile`/`1c-form-edit` (форма из JSON DSL + сборка через `v8unpack`). Это может работать для простых форм, но для боевых форм самописной конфигурации надёжнее EDT. Пробуй DSL только на «песочнице».

В Конфигураторе (на Windows) редактор форм тоже доступен — если кому-то из команды удобнее там.

## 8. Шаг 7 — Отладка

### Клиентский и общий код — на Mac

1. В EDT: конфигурация запуска (`Запустить` / `Отладка`) на локальную файловую ИБ.
2. Ставь точки останова в BSL, запускай в режиме отладки — EDT-отладчик остановится, покажет стек, переменные, табло.
3. Альтернатива — отладчик Конфигуратора (на Windows), если предпочитаешь его.

### Серверный код — на Windows-сервере

Серверные процедуры исполняются в `rphost` на Windows-сервере, поэтому:

1. На сервере включить отладку: для серверной базы — в свойствах информационной базы/кластера разрешить отладку (протокол отладки, по умолчанию порт **1550**).
2. В EDT/Конфигураторе настроить **подключение к предмету отладки** по сети: указать сервер отладки (`debugServerURL`/адрес сервера и порт 1550), выбрать предмет (фоновое задание, сеанс, HTTP-сервис).
3. Сетевой доступ Mac → Windows-сервер по порту 1550 должен быть открыт (firewall).

Так можно отлаживать серверный код, исполняющийся на Windows, прямо из EDT на Mac.

> Для отладки фоновых заданий и HTTP-сервисов выбирай соответствующий тип предмета отладки и включай автоподключение.

## 9. Шаг 8 — Организация тест/прод

Минимально здоровый ландшафт — **три контура**:

```
 ┌─────────────┐    Git push / MR    ┌──────────────┐   приёмка    ┌──────────────┐
 │   DEV        │  ───────────────▶   │   TEST/QA    │  ─────────▶  │   PROD        │
 │ файловая ИБ  │   сборка .cf/.cfe   │ Windows-сервер│  окно,      │ Windows-сервер│
 │ на Mac (EDT) │                     │ копия prod    │  монопольно  │ боевая база   │
 └─────────────┘                     └──────────────┘              └──────────────┘
     каждый                              автодеплой                   ручной gate +
   разработчик                          из ветки                      бэкап перед
                                        develop/release               обновлением
```

Поток изменений (самописная конфигурация — обновлений вендора нет, можно менять основную конфигурацию):

1. **Dev:** правки в EDT/VSCode → коммит в `feature/*` → MR в `develop`.
2. **Сборка:** из исходников собираем `.cf` (или `.cfe`, если решите выносить часть в расширения).
3. **Test:** загрузка `.cf` в тестовую базу (копию прода), `/UpdateDBCfg`, прогон тестов и ручная приёмка.
4. **Prod:** в согласованное **окно обслуживания** — резервная копия (`/DumpIB`), блокировка сеансов / монопольный режим, загрузка `.cf`, `/UpdateDBCfg`, проверка, снятие блокировки.

Команды деплоя (Windows, командная строка):

```bat
REM Загрузить конфигурацию из .cf и обновить БД
"...\1cv8.exe" DESIGNER /S "1c-server\test_base" /N Админ /P пароль ^
  /LoadCfg "D:\build\app.cf" /UpdateDBCfg -Server

REM Резервная копия перед обновлением прод
"...\1cv8.exe" DESIGNER /S "1c-server\prod_base" /N Админ /P пароль ^
  /DumpIB "D:\backups\prod_2026-06-28.dt"
```

Сборка `.cf` из исходников (формат конфигуратора):

```bat
"...\1cv8.exe" DESIGNER /S "1c-server\build_base" /N Админ /P пароль ^
  /LoadConfigFromFiles "D:\repo\src" /DumpCfg "D:\build\app.cf"
```

Современная альтернатива `1cv8 DESIGNER` — утилита **`ibcmd`** (автономный сервер/операции без полноценного кластера), удобна для CI.

**Хранилище конфигурации vs Git.** Раз Git заводится с нуля и команда переходит на EDT — веди версионирование в **Git** (это и есть современный путь). Классическое Хранилище 1С (`.1ccr`) — если кто-то параллельно работает в Конфигураторе; связать Git и Хранилище можно через **gitsync**. Но для EDT-центричной команды Хранилище не обязательно.

## 10. Шаг 9 — CI/CD с нуля

Раз ничего нет — рекомендация: **GitLab или GitHub + self-hosted runner на Windows-сервере** (там, где есть платформа 1С для сборки/тестов).

Типовой пайплайн:

1. **lint** — прогон BSL Language Server (`--analyze`), quality-gate по ошибкам уровня Error.
2. **build** — сборка `.cf` из исходников (`/LoadConfigFromFiles` → `/DumpCfg` или `ibcmd`).
3. **test** — автотесты: **YaXUnit** (юнит-тесты BSL) и/или **Vanessa Automation** (сценарные/UI).
4. **deploy:test** — загрузка `.cf` в тестовую базу автоматически из `develop`/`release`.
5. **deploy:prod** — **ручной** запуск (manual gate) из защищённой ветки, с бэкапом перед обновлением.

Инструменты автоматизации сообщества: **vanessa-runner** (`vrunner`), **gitsync**, **OneScript** — оборачивают вызовы платформы в удобные команды для пайплайна. Пример lint-шага (BSL LS):

```bash
java -jar bsl-language-server.jar --analyze --src ./src \
  --reporter json --outputDir ./reports --configuration ./.bslls.json
```

Старт можно сделать «ручным CI»: скрипты `scripts/dump.sh|build.bat|deploy.bat` из комплекта + Makefile, а позже завернуть в GitLab CI / GitHub Actions.

## 11. Чеклист «первая неделя»

1. Согласовать стратегию: 1С vs Go-ERP из `ARCHITECTURE.md`.
2. Поставить платформу 1С (Mac + Windows, **одна версия**), EDT, JDK 17, VSCode, Node, Git, Claude Code.
3. На Windows: выгрузить `prod.cf` и `src` (XML) из живой базы.
4. На Mac: импортировать в EDT, создать локальную файловую dev-ИБ, проверить сборку проекта.
5. Завести Git-репозиторий 1С (отдельный), положить файлы из `starter-kit/`, первый коммит.
6. Настроить VSCode: расширение BSL + BSL Language Server (путь к JAR в `settings.json`), проверить линт.
7. Подключить Claude Code + MCP `1c-platform` (alkoleft) + `CLAUDE.md`; добавить скилы Desko77.
8. *(когда дойдут руки)* опубликовать HTTP-сервис на Windows и подключить feenlace/mcp-1c онлайн.
9. Поднять test-базу (копия прода) на Windows; отработать ручной деплой `.cf`.
10. Настроить отладку: локальную (Mac) и серверную (порт 1550 → Windows).
11. Заложить CI: lint → build → test → deploy:test (ручной prod).
