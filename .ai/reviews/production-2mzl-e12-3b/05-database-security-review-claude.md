### DB-1 · P2 · `ТоварыВПереработке.ПередачаВПереработку` без индекса, а новые запросы отбирают только по нему

**Где.** Индекс в `ТоварыВПереработке.mdo` есть только у измерений `Контрагент` и `Номенклатура`. У измерения
`ПередачаВПереработку` индекса нет. Отбор только по этому измерению идёт в трёх местах:
- `ЕстьСписаниеПоПередаче` — `ГДЕ Движения.ПередачаВПереработку = &Передача`;
- `ТекстЗапросаСтрокПередач`, таблица `ВТСписано` — `Движения.ПередачаВПереработку В (ВТДокументы)`.

В обоих случаях СУБД читает всю таблицу движений регистра.

**Где это горячо.**
1. `СтрокиПереработок` вызывается из `ДанныеТекущегоЗаказа` на **каждом** заказе на производство, даже без передач.
   Проверка «есть ли передачи» перед `ВТСписано` не делается. `ДанныеТекущегоЗаказа` вызывается при активизации строки
   заказа и после каждой записи строки нижних закладок, в том числе «во время ввода новой строки» (комментарий в модуле
   формы). Выходит полный просмотр движений переработки на каждое перемещение по списку заказов.
2. `ЕстьСписаниеПоПередаче` на одну запись строки передачи вызывается два-три раза:
   - `ТекстЗапретаДокументаСтроки` — до блокировки;
   - `ТекстЗапретаПравкиСтрокиПередачи` — **внутри транзакции**, когда уже взяты исключительные `ТоварыВНаличии`
     склада и `ТоварыВПереработке` переработчика;
   - `ВыполнитьСнятиеПередачи` — тоже внутри транзакции.

   Долгий просмотр под блокировкой задерживает проведение поступлений и передач того же переработчика и склада, а заодно
   реализаций, если номенклатура пересекается.

**Сценарий.** Клиент с активной давальческой переработкой (drissotex — текстиль, этапы у переработчиков) накопил
десятки тысяч строк движений. Оператор листает список заказов, и каждая строка даёт просмотр таблицы. Запись строки
передачи держит блокировку склада, пока идёт такой просмотр. Параллельная реализация с автовыпуском по тому же сырью
ждёт.

**Исправление (дёшево, без реструктуризации).** Добавить отбор по индексированному `Контрагент`. Расход по партии
передачи пишет только поступление того же переработчика: смену переработчика после расхода теперь запрещает
`ПередЗаписью`.
- В `ЕстьСписаниеПоПередаче` передавать или читать `Контрагент` передачи и добавить `И Движения.Контрагент = &Контрагент`.
  В `ПередЗаписью` брать прежнего контрагента из базы: `Прежние.Контрагент`, а не реквизит объекта.
- В `ВТСписано` добавить `И Движения.Контрагент В (ВЫБРАТЬ Д.Контрагент ИЗ Документ.ПередачаВПереработку КАК Д ГДЕ
  Д.Ссылка В (ВЫБРАТЬ Ссылка ИЗ ВТДокументы))`.
- Если `ВТДокументы` пуста, пакет можно не выполнять — хватит запроса на существование.

Альтернатива — индекс у измерения регистра. Это реструктуризация таблицы движений у клиента: данные она не меняет, но
тяжелее индексов у документов.

### DB-2 · P2 · Защиту партий передачи обходит форма документа, куда рабочее место само отправляет пользователя

**Где.**
- `ТекстЗапретаСписанияПередачи` отказывает с текстом «…уже поступала продукция из переработки: **правьте её в форме
  документа**».
- В форме передачи из новой защиты работает только `ПроверитьСменуОснованияИПереработчика`, и та лишь при смене
  `Основание`/`Контрагент`.
- Ни `ОбработкаПроведения`, ни отмена проведения передачи (платформенная, без `ОбработкаУдаленияПроведения`) не
  проверяют остаток `ТоварыВПереработке` по партии.

**Сценарий 1 (правка количества).**
1. Передача T отправила переработчику K 100 кг сырья M.
2. Проведённое поступление R списало по FIFO 80 кг партии T.
3. В рабочем месте правка T запрещена, и сообщение ведёт в форму.
4. В форме пользователь исправляет T на 50 кг и записывает её (перепроведение) или отменяет проведение.
5. Отказа нет: остаток партии T у K становится −30 или −80 кг.
6. Следующее поступление от K по FIFO берёт другие партии. Отрицательная партия T остаётся в остатках и искажает
   себестоимость продукции переработчика.

Сама дыра старая, до E12.3b. Но дифф её усиливает: оператора прямо направляют в форму, а начальная страница оператора
теперь — рабочее место.

**Сценарий 2 (гонка при смене переработчика, узкое окно).** `ПроверитьСменуОснованияИПереработчика` выполняется в
`ПередЗаписью`, до `Блокировка.Заблокировать()` проведения, то есть без блокировки.
1. `ПередЗаписью` T со сменой K→K2: расхода ещё нет, проверка проходит.
2. Параллельно R у K проводится и фиксирует расход партии T: остаток T у K ещё прежний.
3. Проведение T блокирует `ТоварыВПереработке` только по **новому** K2. Прежние движения у K удаляются без
   управляемой блокировки по K.
4. Итог — минус у K.

Вероятность низкая: нужна одновременная работа двух пользователей.

**Исправление.** Контроль остатка партии в самой передаче закрывает оба сценария и все пути: форму, рабочее место, обмен
без `Загрузка`.
- В `ОбработкаПроведения`: после `Движения.Записать()` под уже взятой блокировкой проверить, что
  `ТоварыВПереработке.Остатки(, ПередачаВПереработку = Ссылка)` не отрицателен. В блокировку добавить прежнего контрагента
  из базы, если он сменился.
- Добавить `ОбработкаУдаленияПроведения` с той же блокировкой: отказ, если по партии есть расход других регистраторов.
  Это тот же `ЕстьСписаниеПоПередаче`, но уже под блокировкой.

Если не сейчас — записать в TECHDEBT и **поменять текст сообщения**: не отправлять в форму как в безопасное место, а
писать «сначала отмените поступления из переработки по этой передаче».

### DB-3 · P3 · Предблокировка берёт только прежние материалы; новый материал блокируется позже, уже при проведении

**Где.** `ЗаблокироватьОстаткиПередачи(ДокОбъект)` вызывается до `ПрименитьДанныеСтрокиПередачи` и берёт
`ТоварыВНаличии(склад, ТЧТовары)`, затем `ТоварыВПереработке(K, ТЧТовары)` по строкам из базы.

**Корректность проверки не страдает.** Расход партий T возможен только по материалам, с которыми T проведена, а они уже
заблокированы. Поступление, списывающее T, ждёт.

**Порядок захвата при этом нарушается.** Когда строка добавляет новый материал M2 или меняет M1 на M2, вложенное
проведение передачи в той же транзакции дозапрашивает `ТоварыВНаличии(W, M2)`. В этот момент транзакция уже держит
`ТоварыВПереработке(K, M1)`. Получается порядок `ТоварыВПереработке`→`ТоварыВНаличии` — встречный порядку проведения
передачи. Пример взаимоблокировки: параллельная передача T2 со склада W к K с материалами {M1, M2}. Реальна она, только
если менеджер блокировок выдаёт значения одного `Заблокировать()` частично.

Данные не портятся: платформа снимает одну из транзакций с ошибкой, и оператор видит «Не записано».

**Исправление.** Источник предблокировки — `ДокОбъект.ТЧТовары` плюс `ДанныеСтроки.Материал`: таблица значений с
колонкой `Номенклатура`. Для удаления строк достаточно текущего источника.

### DB-4 · P3 · Смена основания передачи не пересчитывает стадии заказов и автовыпуск, хотя меняет «Выпущено»

**Где.** `ЗаказОснованияДокумента` и `ВТВыпущено` определяют заказ поступления через `ПередачаВПереработку.Основание`.
`ПроверитьСменуОснованияИПереработчика` запрещает смену, только если есть **расход партий**. Смена основания передачи
при уже проведённых поступлениях без расхода остаётся разрешённой. Например, у поступления нет строк сырья или
переработчик работал из своего материала. Передача в контур E8 не входит.

**Сценарий.**
1. Передача T с заказом O1, по ней проведено поступление R продукции P (10 шт.) без строк сырья.
2. Пользователь в форме меняет основание T на O2.
3. «Выпущено» у O1 уменьшается на 10, у O2 растёт на 10. Стадии и индикаторы обоих заказов остаются прежними до записи
   следующего документа контура.
4. Перепроведение реализации O2 уменьшит её автовыпуск.

**Исправление.** В `ПроверитьСменуОснованияИПереработчика` при смене `Основание` отказывать и при наличии проведённых
поступлений по передаче. Запрос по `ПоступлениеИзПереработки.Основание` теперь индексирован.

### DB-5 · P3 · Подзапрос «передачи со списанием» в `ТекстЗапросаДокументовДляВыбора`

**Где.** `НЕ Д.Ссылка В (ВЫБРАТЬ Движения.ПередачаВПереработку … ГДЕ Движения.Контрагент = &Поставщик …)`.
- Отбор по `Контрагент` индексирован, но без ограничения периода: подзапрос читает весь расход переработчика за всю
  историю, чтобы отсеять только сегодняшние передачи.
- Нет `И Движения.Активность`, в отличие от `ЕстьСписаниеПоПередаче` и `ВТСписано`. Признак у трёх запросов
  рассогласован.

**Исправление.** Добавить `И Движения.Активность` и `И Движения.Период >= &НачалоДня`: расход партии не может быть раньше
её прихода.

### Проверено, замечаний нет

- **Хуки E8 в поступлении.** Схема совпадает с `ВыпускПродукции`:
  - `ЗапомнитьЗаказыДокумента` вызывается в `ПередЗаписью` после `МожноРедактироватьДокумент` и при `Не Отказ`;
  - `ОбновитьСтадииПослеПроведения` — последняя строка после `Движения.Записать()`, история статусов блокируется
    последней;
  - `ОбновитьСтадииПриЗаписи` — в `ПриЗаписи`;
  - `ОбработкаУдаленияПроведения` → `ОтменитьПроведениеДокумента` с тем же набором `ЗаполнитьБлокировкуПроведения` в том
    же порядке (`ТоварыВПереработке`, затем `ТоварыВНаличии`/`ДополнительныеРасходы`);
  - без заказов на производство движения по-прежнему удаляет платформа.

  Двойного учёта в `ВТВыпущено` нет: основание поступления — либо заказ, либо передача, ветки взаимоисключающие.
- **Поступление против автовыпуска реализации.** Реализация блокирует `ТоварыВНаличии` по номенклатуре автовыпуска без
  склада. Поступление блокирует `ТоварыВНаличии(W, продукция)`, и эти блокировки пересекаются. Значит,
  `ВыпущеноИОтгруженоРанее` не читает поступление, проведённое параллельно с общей продукцией. `ТоварыВПереработке`
  реализация не берёт, нового цикла нет. Проведение поступления теперь берёт блокировку истории статусов последней, как
  все документы контура. Поэтому повтор правила порядка после записи реализации (`ЗаписатьОбъектДокумента`) видит
  параллельно проведённое поступление.
- **Транзакции рабочего места.**
  - `НачатьТранзакцию` / `Попытка … ОтменитьТранзакцию` оформлены по шаблону.
  - Отказ проверки внутри транзакции ничего не пишет и фиксирует пустую транзакцию.
  - Если внутри вложенного `Записать(Проведение)` произошло исключение, его перехватывает `ЗаписатьДокументСтроки`.
    `ЗафиксироватьТранзакцию` после этого падает, срабатывает `ОтменитьТранзакцию`, а текст причины сохраняется
    (`ОтметитьОтказТранзакции`).
  - Черновик нового документа пишется вне транзакции.
  - Внешних транзакций у вызывающих нет: серверный вызов формы.
  - Предблокировка передачи совпадает с проведением по составу (включая `ДополнительныеРасходы` из
    `УправляемыеБлокировки.ТоварыВНаличии`) и порядку.
- **Реструктуризация.** Индекс `Основание` у двух документов переработки — только индекс, данные не меняются. Тип
  составной, индекс строится по трём колонкам. Объёмы документов переработки малые, обновление занимает секунды в
  монопольном режиме, как любое CFU. uuid и типы не менялись.
- **Задним числом у клиента (решение владельца, записано в TECHDEBT).**
  - Стадии старых заказов меняются при первой записи документа контура.
  - Перепроведение старой реализации уменьшает автовыпуск.

  Дополнительно отмечу, чего в TECHDEBT нет. У старых заказов с поступлением, проведённым после реализации, рабочее
  место теперь не даёт править и проводить такие реализации (`ТекстЗапретаПорядкаВыпускаИОтгрузки`), и они пропадают из
  выбора документа отгрузки (`ВТПослеВыпуска`). Правка остаётся в форме. Стоит одной строкой добавить это в «Что нового»
  или в TECHDEBT.

## Безопасность — вердикт: `approve_with_changes`

P0, P1 и P2 нет. Одна находка P3, и она не из диффа.

**Может ли пользователь роли `ОператорПроизводства` этим путём получить или изменить данные, которые роли не
положены?** Нет. Путь вызова пройден:

- **Права.** У оператора на оба документа переработки есть Read, Insert, Update, Posting, UndoPosting и пометка. На
  `ТоварыВПереработке` и `ТоварыВНаличии` — Read и Update, на контрагентов — Read, на обработку — Use. RLS в роли нет,
  поэтому временные таблицы без `РАЗРЕШЕННЫЕ` ошибок не дадут. На `ВзаиморасчётыСПоставщиками` и `ДополнительныеРасходы`
  у роли только Read. Сначала я счёл это отказом проведения у оператора. Но у обоих документов переработки
  `postInPrivilegedMode` и `unpostInPrivilegedMode` = `true`, так что проведение и отмена от этих прав не зависят.
  Замечание снято.
- **Привилегированный режим.**
  - `ЕстьСписаниеПоПередаче`: параметр — только типизированная ссылка, наружу уходит один признак. Режим снимается при
    выходе из функции.
  - Вызывается она из `ПередЗаписью`, где у пользователя уже есть Update передачи, и из рабочего места. В рабочем месте
    `ТекстЗапретаСтатусаДокумента` и `ТекстЗапретаДокументаСтроки` сначала сверяют, что документ относится к текущему
    заказу (`Реквизиты.ЗаказКлиента`, чтение с правами пользователя), и только потом зовут привилегированную проверку.
  - Модуль менеджера регистра с клиента напрямую недоступен.
- **Серверная перепроверка данных клиента.**
  - Признак `Субподрядчик` перепроверяется на сервере дважды: `ТекстЗапретаЗначенийСтрокиПередачи` и
    `ОбработкаПроверкиЗаполнения` через `ПроверитьЗаполнение` в `ЗаписатьДокументСтроки`.
    `ПараметрыВыбора` в форме — только удобство.
  - Принадлежность документа заказу проверяется по базе. Тип документа — по списку `ВидыСтрокДокументов`.
  - Переработчик существующей передачи из строки не меняется: `Реквизиты.Контрагент <> ДанныеСтроки.Поставщик` даёт
    отказ, `ПрименитьДанныеСтрокиПередачи` `Контрагент` не пишет.
  - Склад новой передачи берётся из значений по умолчанию, а не из данных клиента.
  - Состояние списания перепроверяется под блокировкой.
  - Версия документа сверяется `ЗаблокированныйДокументСтроки`.
  - Серии и партии строк защищены на сервере (`ТекстЗапретаПравкиСтрокиПередачи`), а не только признаком
    `ТолькоПросмотр`.
- **Суммы.**
  - Строки передач цен и сумм не несут: `0 КАК Цена`, `0 КАК Сумма`, представление документа с суммой 0.
  - Колонки «Цена»/«Сумма» у закладки не выводятся.
  - Колонка «Поступления» показывает только номер, дату и статус.
  - Стоимость услуг в форме поступления скрыта формой — решение владельца, TECHDEBT.
- **Серверные вызовы.** Новых клиент-серверных точек, кроме существующего движка строк, нет.
  `ТекстЗаполнитеСтроку` — без контекста и без данных. `СоздатьПоступлениеИзПереработки` только открывает форму документа
  с основанием, дальше работают права пользователя.
- **Начальная страница.**
  - Рабочее место видно только роли `ОператорПроизводства`, у которой есть `Use` на обработку.
  - Дашборд оператору скрыт — экспозиция данных уменьшилась.
  - Пользователь с несколькими ролями видит объединение. Роли без `Use` рабочее место не получают, а права на данные
    проверяет сервер.
  - Из других ролей права на передачу есть только у `Кладовщик`, и у неё тоже есть Read на регистр. Ветка
    `ТекстЗапросаДокументовДляВыбора` без привилегий у неё не упадёт.
- **Секреты.** В диффе, включая `scripts/formgen/arm/gen6.py` и документацию, не обнаружены.

### SEC-1 · P3 · У оператора «без сумм» есть Read на `ВзаиморасчётыСПоставщиками` и `ДополнительныеРасходы` (вне диффа)

**Где.** `Roles/ОператорПроизводства/Rights.rights`. Проведение документов оператора идёт в привилегированном режиме:
`postInPrivilegedMode` у переработки, явный `УстановитьПривилегированныйРежим` у выпуска и закупок. Для проведения эти
права на чтение не нужны.

**Сценарий.** E12.3b направляет оператора вводить поступления из переработки, и бухгалтер вносит в них стоимость услуг.
Долг перед переработчиком на эту стоимость ложится в `ВзаиморасчётыСПоставщиками`. Суммы по нему оператор может получить
через любой отчёт или обработку, которые читают регистр с правами пользователя. Интерактивно список регистра не
открывается: права View нет.

**Исправление.** Проверить, какой код оператора читает эти регистры без привилегий. Если такого нет — снять Read. Иначе
записать в TECHDEBT рядом с пунктом «ОператорПроизводства видит оплату по индикатору».
