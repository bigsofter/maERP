### P1 — Правка поступления с несколькими сериями обходит проверку и искажает складские движения

**Место плана:** п. 5.3, 5.6, 13.

**Сценарий:** существует проведённое поступление: 10 единиц материала, `УказаноНесколькоСерий = Истина`, в `ТЧСерии` — 6 единиц серии S1 и 4 единицы S2. Пользователь уменьшает количество до 5 через АРМ. План меняет товарную строку, но не согласует распределение серий.

Это не обязательно вызовет отказ проведения. `СерииИРазмещение/Module.bsl:111–145` берёт количество первой серии из `ТЧСерии`, а последней отдаёт остаток: при сохранённом коде строки получатся **6 и −1**. Проверка соответствия находится в форме поступления (`Forms/ФормаДокумента/Module.bsl:40–43`), которую АРМ обходит. Объект непосредственно передаёт результат объединения в проведение (`ObjectModule.bsl:101–119`). Если же при правке изменится `КодСтроки`, связанные серии перестанут находиться.

**Правка:** до реализации определить серверное ограничение для строк с сериями. Минимальный безопасный вариант E12.2 — запретить в АРМ изменение материала, характеристики, упаковки и количества таких строк, направляя пользователя в форму документа. Сохранять код существующей строки; при удалении удалять связанные серии. Добавить регресс на изменение количества строки с двумя сериями и проверку движений по каждой серии. Ожидание исключения проведения эту защиту не заменяет.

### P1 — Пересчёт продукции по текущему дефициту переносит уже заказанное количество между изделиями

**Место плана:** п. 5.3 — продукция из первой строки `ДефицитЗаказа`.

**Сценарий:** изделия A и B требуют по 5 единиц одного материала. Первая строка заказа поставщику на 5 единиц получила продукцию A и проведена. Теперь дефицит A равен нулю, в `ДефицитЗаказа(Заказ)` остаётся B. Пользователь исправляет количество существующей строки с 5 на 6. По описанному алгоритму строка получает продукцию B: после перепроведения у A снова дефицит 5, а все 6 заказанных единиц относятся к B.

**Подтверждение:** `ПотребностиПроизводства/ManagerModule.bsl:171–184` возвращает только положительный текущий дефицит. `РаспределитьНаПродукцию`, строки 905–918, относит **всё** количество строки на явно заданную продукцию, не распределяя избыток.

**Правка:** при правке количества, цены и реквизитов документа сохранять прежнюю `Продукция`. Для новой строки зафиксировать способ выбора продукции: явная строка потребности либо пустая продукция с существующим распределением. Не использовать текущий дефицит как идентификатор существующей строки. В тест добавить два изделия с общим материалом и проверять движения отдельно по каждому после перепроведения.

### P1 — Материал и характеристика не определяют строку заказа поставщику однозначно

**Место плана:** п. 5.3 — выбор цены и `КодСтроки` поступления по материалу и характеристике.

**Сценарий:** заказ поставщику содержит две строки одного материала с одинаковой характеристикой: код 1 — 5 единиц для изделия A, код 2 — 5 единиц для B. Такие строки штатно возникают при закупке по потребности. Оператор вводит поступление всех 10 единиц. В данных АРМ нет идентификатора выбранной строки основания; присваивание одного из найденных кодов привяжет все 10 единиц только к A или только к B. Второе изделие останется без поступления в производственной потребности.

**Подтверждение:** `ПотребностиПроизводства/ManagerModule.bsl:475–489` получает продукцию по ключу строки основания, включающему код. При найденной продукции далее выполняется распределение всего количества на неё, а не между одинаковыми материалами.

**Правка:** копировать код основания только при однозначном соответствии. При нескольких совпадениях — либо выбирать конкретную строку основания с показом продукции и сохранять этот выбор, либо использовать явно предусмотренный путь без точной привязки с существующим распределением. Не подставлять произвольный совпавший код. Добавить сценарий поступления по заказу с двумя одинаковыми материалами для разных изделий.

### P1 — Цена строки основания копируется без пересчёта упаковки и режима НДС

**Место плана:** п. 5.2–5.3.

**Сценарий:** в заказе поставщику материал заказан коробками по 10 штук, цена коробки — 1 000. В поступлении оператор выбирает упаковку «штука» и вводит 10. План берёт цену совпавшей строки основания — 1 000 — без пересчёта. Поступление получает сумму **10 000 вместо 1 000**. Оператор со скрытыми суммами ошибку не увидит.

**Подтверждение:** `РаботаСДокументамиКлиентСервер/Module.bsl:30–60` рассчитывает сумму как цену, умноженную на количество упаковок. Пересчёт коэффициента предусмотрен планом только для прайса, но не для цены основания. Дополнительно новый документ получает `ЦенаВключаетНДС = Истина`, тогда как существующий заказ поставщику может содержать цены без НДС; штатное заполнение поступления копирует этот флаг из основания (`ПоступлениеТоваровУслуг/ObjectModule.bsl:5–11`).

**Правка:** цену основания нормализовать через коэффициент исходной упаковки и привести к целевой упаковке и режиму НДС документа-получателя. Для поступления по основанию согласовать режим НДС с основанием; для добавления в существующий документ учитывать его режим. Добавить проверки разных упаковок и обоих значений `ЦенаВключаетНДС`, включая ввод под оператором без видимых сумм.
