# План: E7 — потребности производства (maERP 2.0.15.15)

Бриф: `docs/plans/production-2mzl-e7-potrebnosti.md`. Основание: `docs/plans/production-2mzl.md`, E7 и обязательства
разделов E5 и E6. Конфигурация 1С 8.5.1, EDT-проект `src/cf`.

Решения владельца 2026-09-13 (вопросы брифа):
1. Этап сдаётся **одной сборкой** 2.0.15.15 (бриф предлагал две).
2. «Заказано» и «Пришло» сверх потребности — **фактическое количество**: дефицит уходит в минус, излишек виден в отчёте.
3. Закупка под продажу или под непроведённый заказ на производство **движений не пишет** (и не отказывает).
4. Без колонки «Продукция» — распределение **в порядке строк продукции** заказа клиента.

Редакция 2: учтены находки `architecture-critic` (`.ai/reviews/production-2mzl-e7/01b-architecture-critic.md`).
Правки сведены в раздел 12 и имеют приоритет над текстом разделов 1–11.

Отклонения от брифа отмечены **[отклонение]**.

## 0. Исследование (итог)

- **`ЗаказПоставщику.Основание`** (`DocumentRef.ЗаказПокупателя`) сейчас заполняет только ввод по предложению поставщика
  (`ObjectModule.bsl:73`). Ввод на основании заказа клиента (`ЗаполнитьПоЗаказуПокупателя`) основание **не ставит**, поля
  в форме нет, `ФормированиеЗаказовПоставщику` (создаёт и проводит) — тоже. Значит, «Заказано» по основанию сейчас
  не с чем связать: основание нужно ставить при вводе по заказу на производство и показать полем в форме.
- **Проверка E6 записи проведённого заказа** (`ПроверитьМатериалыПроведенногоЗаказа`) сравнивает составы **на единицу**
  (`СоставыПродукций` → `КоличествоЗаЕдиницу`). Проведённый заказ с другим количеством продукции записывается без
  перепроведения (материалы пересчитаны, состав на единицу тот же) — `Потребность` в регистре устарела бы.
- **`РаботаСДокументами.ПолучитьДокументРодительПоТипу`** идёт по цепочке `Основание` без ограничений: поступление
  по реализации (`Основание` — реализация, её основание — заказ клиента) дошло бы до заказа на производство. Для
  потребностей нужна явная функция с двумя допустимыми путями.
- **Тип `ДокументСсылка.ЗаказПокупателя` в `ПоступлениеТоваровУслуг.Основание`** безопасен для существующих движений:
  `ЗаказыПоставщикам` проверяет тип явно; `ТоварыВНаличии` читает основание только в оприходовании по реализации
  (по хозяйственной операции); `ВзаиморасчётыСПоставщиками` у поступления основание не читает;
  `ОбновитьСтатусЗаказаПоСвязанным` учитывает только реализацию, выпуск и переработку. Критерий отбора
  `СвязанныеДокументы` уже содержит `ПоступлениеТоваровУслуг.Основание` и тип `ЗаказПокупателя` — поступление появится
  в связанных документах заказа (желаемо).
- **Проведение.** Заказ поставщику, поступление и возврат: `posting` по умолчанию (Allow), `postInPrivilegedMode`,
  `РаботаСДокументами.УстановитьЗаписьВсехРегистров(Движения)`. У заказа клиента `registerRecords` нет,
  `ОбработкаПроведения` — страховка E6. Блокировка карт продукции берётся в `ПередЗаписью` при проведении — та же
  транзакция, что и `ОбработкаПроведения`, поэтому блокировка регистра в `ОбработкаПроведения` идёт после неё.
- **Права** (сверено скриптом по `Rights.rights`). Новый объект автоматически получают только `Администратор` и
  `Руководитель` (`setForNewObjects`). Заказ поставщику создают/проводят `Кладовщик`, `МенеджерПоЗакупкам`;
  поступление проводят `Кладовщик`, `МенеджерПоЗакупкам`, `ОператорПроизводства`, `Оператор`, `Логист`, `Казначей`;
  возврат — `Кладовщик`, `МенеджерПоЗакупкам`, `ОператорПроизводства`. Раздел «Производство» видят `Кладовщик` и
  `ОператорПроизводства`. Отчёт-образец `ТоварыВПереработке` доступен только `Кладовщик`.
- **Форма заказа поставщику**: без страниц, шапка `ГруппаШапка` → `ГруппаШапкаЛевая` (`Контрагент`, `Договор`) /
  `ГруппаШапкаПравая`; в `autoCommandBar` таблицы `ТЧТовары` уже есть кнопки `ЗаполнитьИзExcel` и
  `ПодобратьИзПредварительных` (образец для новой кнопки). У реквизита формы `Объект.ТЧТовары` есть доп. колонка `Остаток`.
- **Список поступлений**: произвольный запрос (`customQuery`, `Form.form:2655-2689`), таблица `Список` на странице
  `СтраницаОсновная` группы `ГруппаЗакладкиСписков`; кнопок внутри таблицы нет — добавляем только колонку (forms-009
  касается кнопок).
- **Отчёт-образец** `Reports/ТоварыВПереработке`: `.mdo` + `Templates/ОсновнаяСхемаКомпоновкиДанных/Template.dcs`,
  `defaultForm = CommonForm.ФормаОтчёта`, модулей нет.
- **Тесты уровня 3**: `ВыполнитьСценарий` оборачивает сценарий в транзакцию с откатом; помощники `НовыйДокумент`,
  `ДобавитьСтрокуТоваров`, `Провести`, `ЗаказПроведенияСценария`, `ДобавитьМатериалЗаказа`, `ПроверитьРавенство`.

## 1. Регистр `ПотребностиПроизводства`

`src/cf/src/AccumulationRegisters/ПотребностиПроизводства/ПотребностиПроизводства.mdo` — по образцу `ЗаказыПоставщикам`,
**новые uuid** (у объекта, `producedTypes`, измерений, ресурсов): `registerType` — остатки (умолчание, как у образца),
`dataLockControlMode = Managed`, `enableTotalsSplitting = true`, синонимы ×4.

| Поле | Вид | Тип |
|---|---|---|
| `Заказ` | измерение, `useInTotals` | `DocumentRef.ЗаказПокупателя` |
| `Продукция` | измерение | `CatalogRef.Номенклатура` |
| `Материал` | измерение | `CatalogRef.Номенклатура` |
| `Характеристика` | измерение | `CatalogRef.ХарактеристикиНоменклатуры` |
| `Потребность`, `Заказано`, `Пришло`, `ИзОстатка` | ресурсы | `DefinedType.Количество` (знаковый) |

Все движения — **приход** со знаком: отмена «пришло» возвратом — отрицательный приход (сторно). Контроля остатков нет.
`Configuration.mdo` — `<accumulationRegisters>` по алфавиту. Обработчика обновления нет, исторические документы не
перепроводятся.

### 1.1. Модуль менеджера регистра (`ManagerModule.bsl`)

Экспортные (с комментариями):
- `СформироватьДвижения(ДокОбъект)` — ветки по типу: заказ клиента, заказ поставщику, поступление, возврат поставщику.
  Всегда `Движения.ПотребностиПроизводства.Записывать = Истина` (пустой набор при перепроведении стирает старые движения).
- `ЗаказКлиентаЗакупки(Основание)` — `ДокументСсылка.ЗаказПокупателя` или `Неопределено`. Допустимые пути: основание —
  заказ клиента; основание — заказ поставщику, чьё основание — заказ клиента; для возврата — то же от поступления-основания.
  Возвращает заказ, **только если** он проведён и `Документы.ЗаказПокупателя.ЗаказПроводится(ВидОперации)`
  (решение 3). Реквизиты читаются одним запросом (`ОбщегоНазначения.ЗначенияРеквизитовОбъекта`).
- `ПотребностьЗаказаКлиента(ТЧТовары, ТЧМатериалы)` — таблица `Продукция, Материал, Характеристика, Потребность`: материалы
  с заполненной номенклатурой, продукция по `КодСтрокиПродукции` = `ТЧТовары.КодСтроки`, свёртка по базовому `Количество`.
  Работает и с табличными частями объекта, и с выгрузкой из базы — используется проведением и проверкой из п. 2.2.
- `ОстаткиПотребности(Заказ, ИсключитьРегистратор)` — таблица остатков по заказу **без движений документа**
  `ИсключитьРегистратор` (запрос к таблице движений: `Заказ = &Заказ И Регистратор <> &Регистратор`, сумма по ресурсам)
  плюс порядок продукции: `МИНИМУМ(ТЧТовары.НомерСтроки)` номенклатуры в заказе клиента. Остатки без периода: регистр
  не последовательный, при перепроведении свои движения ещё лежат в базе — поэтому исключение регистратора.
- `ДефицитЗаказа(Заказ, ИсключитьРегистратор)` — строки `Продукция, Материал, Характеристика, Количество` с
  `Потребность − Заказано > 0` в порядке строк продукции; для «Заполнить по потребности» и ввода на основании.
- Служебная `РаспределитьПоПродукции(Остатки, Строки, ИмяРесурса, Сторно)` — см. п. 1.2.

### 1.2. Распределение по продукции

Вход — строки закупки (`Материал, Характеристика, Продукция` (может быть пустой), `Количество`), остатки заказа (п. 1.1).
По каждой строке:
- материала с характеристикой нет в потребности заказа (ни у одной продукции) — строка движения не даёт;
- `Продукция` заполнена: есть строка потребности (`Продукция, Материал, Характеристика`) — всё количество на неё, нет —
  движения нет;
- `Продукция` пуста: строки потребности материала в порядке строк продукции; предел строки —
  `Потребность − Ресурс − уже распределено этим документом` (не меньше нуля); количество закрывает пределы по порядку,
  остаток сверх всех пределов — **на последнюю** строку (решение 2, фактическое).
- **Сторно** (возврат): порядок обратный, предел — `Пришло + уже сторнировано этим документом` (не меньше нуля),
  остаток — на последнюю строку обратного порядка (первую продукцию).

Накопители «распределено этим документом» общие для всех строк документа: две строки одного материала не
закрывают один и тот же дефицит дважды. Результат сворачивается по измерениям.

## 2. Заказ клиента на производство — `Потребность`

### 2.1. Движения
- `ЗаказПокупателя.mdo`: `<registerRecords>AccumulationRegister.ПотребностиПроизводства</registerRecords>`.
- `ObjectModule.bsl`, `ОбработкаПроведения`: после страховки E6 (`Если Отказ Тогда Возврат`) —
  `УправляемыеБлокировки.ПотребностиПроизводства(Блокировка, Ссылка)` → `Заблокировать()` → `СформироватьДвижения` →
  `Движения.Записать()`. Порядок блокировок: карты продукции (`ПередЗаписью`, E6) → регистр — одна транзакция. Регистрация
  карт в `ПередЗаписью` не трогается. Комментарий процедуры обновляется (движения появились).
- Отмена проведения — автоудаление движений платформой (`registerRecordsDeletion` по умолчанию, как у заказа поставщику).

### 2.2. Запись проведённого заказа без перепроведения
`ПроверитьМатериалыПроведенногоЗаказа` дополнительно сравнивает `ПотребностьЗаказаКлиента` текущих табличных частей и
сохранённой версии заказа (выгрузка `ТЧТовары`/`ТЧМатериалы` из базы, как `СоставыПроведенногоЗаказа`). Отличие — тот же
отказ «проведите заказ». Регистр не читается — прав на регистр у ролей, проводящих заказы (`Оператор`, `Клиент`,
`ЛичныйКабинет`, `PDV`, `ECommerce`), не требуется, привилегированного режима нет.

## 3. Заказ поставщику — `Заказано`

### 3.1. Метаданные
- `ТЧТовары.Продукция` (`CatalogRef.Номенклатура`, новый uuid, синонимы ×4, без проверки заполнения).
- `registerRecords` + `AccumulationRegister.ПотребностиПроизводства`.

### 3.2. Проведение (`ObjectModule.bsl`)
`Заказ = РегистрыНакопления.ПотребностиПроизводства.ЗаказКлиентаЗакупки(Основание)`. Заполнен — блокировка регистра по
заказу до чтения остатков, затем `СформироватьДвижения` (строки `ТЧТовары`: `Номенклатура → Материал`, `Характеристика`,
`Продукция`, базовое `Количество`; ресурс `Заказано`). Не заполнен — пустой набор (`Записывать = Истина` через
`УстановитьЗаписьВсехРегистров`). Обработка `ФормированиеЗаказовПоставщику` основание не ставит — движений нет,
поведение прежнее.

### 3.3. Ввод на основании заказа клиента (`ОбработкаЗаполнения`)
- Продажа — **как сейчас** (состав товаров, основание не ставится — прежнее поведение; см. TECHDEBT).
- Заказ на производство: основание = заказ. Без сформированной потребности (не проведён, или опция «Производство»
  выключена) — `ВызватьИсключение` с внятным текстом ×4 («Сначала проведите заказ клиента на производство: без
  проведения потребность в материалах не сформирована»). Проведён — строки из `ДефицитЗаказа(Заказ, пустая ссылка)`:
  `Номенклатура = Материал`, `Характеристика`, `Продукция`, `Количество = КоличествоУпаковок`, `Упаковка` —
  единица номенклатуры, ставка НДС номенклатуры, коды строк по порядку, цена — последний прайс поставщика; поставщик —
  общий основной поставщик материалов (тот же алгоритм, что у продажи — выносится в общую процедуру
  `ЗаполнитьСтрокиПоЗаказу(Строки)` модуля объекта). Дефицита нет — таблица пустая, сообщение «Потребность заказа уже
  заказана».

### 3.4. Форма документа
- Поле **«Заказ клиента»** (`Объект.Основание`) в `ГруппаШапкаЛевая` после `Договор`; видимость — опция «Производство»,
  на сервере в `ПриСозданииНаСервере` (bsl-009). Элемент копируется с поля `Договор` той же формы целиком (forms-001,
  workflow-005), id элементов — новые из пространства элементов, `<visible>true</visible>` явно.
- Колонка **`ТЧТоварыПродукция`** (`Объект.ТЧТовары.Продукция`) после `Номенклатура`: `<visible>` не ставится (скрыта,
  включается через «Ещё → Изменить форму», как «Техкарта» E5), `userVisible` по умолчанию.
- Команда формы **`ЗаполнитьПоПотребности`** и кнопка в `autoCommandBar` таблицы рядом с `ЗаполнитьИзExcel` (копия
  элемента-кнопки); видимость — опция «Производство», на сервере. Клиент: основание не заполнено — сообщение «Укажите
  заказ клиента на производство»; таблица не пуста — существующий вопрос об очистке; сервер: проверка
  `ЗаказКлиентаЗакупки` (иначе сообщение, как в п. 3.3), `ДефицитЗаказа(Основание, Объект.Ссылка)` — дефицит без
  собственных движений документа (строки перезаполняются целиком), заполнение той же процедурой, что в п. 3.3 (без смены
  поставщика), `ЗаполнитьОстаткиНаСервере`, `Модифицированность`.
  Логика заполнения строк — экспортная процедура модуля менеджера `ЗаполнитьПоПотребности(ТЧТовары, Строки,
  ЦенаВключаетНДС, Контрагент)` над коллекцией строк (данные формы и табличная часть объекта), как в E5.
- Реквизиты формы и элементы — разные пространства id; `<handlers>` у новой команды в `Form.form` обязательны.

## 4. Поступление товаров и услуг — `Пришло`

### 4.1. Метаданные
- `Основание`: + `DocumentRef.ЗаказПокупателя`; `basedOn` + `Document.ЗаказПокупателя`.
- `registerRecords` + `AccumulationRegister.ПотребностиПроизводства`.

### 4.2. Проведение
В существующую `Блокировка` (до `Заблокировать`) — `УправляемыеБлокировки.ПотребностиПроизводства`, если
`ЗаказКлиентаЗакупки(Основание)` заполнен. Движения `Пришло`: продукция строки — при основании «заказ поставщику»
из строки заказа поставщику с тем же `КодСтроки`, `Номенклатура`, `Характеристика` (колонка `Продукция`), иначе
распределение п. 1.2. Складские и расчётные движения не меняются.

### 4.3. Ввод на основании заказа клиента (`ОбработкаЗаполнения`)
Новая ветка: продажа или заказ без потребности — `ВызватьИсключение` (текст ×4). Иначе `Организация`, `Основание`,
строки материалов по `Заказано − Пришло > 0`; если по заказу ничего не заказано (сумма `Заказано` = 0) — по
`Потребность − Пришло > 0` (бриф). Упаковка, количества, ставка НДС — как в п. 3.3; `КоличествоПринято` /
`КоличествоУпаковокПринято` = количеству (как у загрузки из заказа поставщику — сверить при реализации). Цены
розничная/минимальная — существующий хвост `ОбработкаЗаполнения`.

### 4.4. Список поступлений
Поле запроса `ЗаказКлиента`: `ВЫБОР КОГДА Док.Основание ССЫЛКА Документ.ЗаказПокупателя ТОГДА Док.Основание
КОГДА Док.Основание ССЫЛКА Документ.ЗаказПоставщику ТОГДА ВЫРАЗИТЬ(Док.Основание КАК Документ.ЗаказПоставщику).Основание
КОНЕЦ`. Колонка `СписокЗаказКлиента` в таблице `Список` (копия колонки `Основание`/`Контрагент`), видимость — опция
«Производство» на сервере. После правки — `scripts/listcheck.py`, дифф `Form.form` целиком (workflow-009).

## 5. Возврат поставщику — сторно `Пришло`

`registerRecords` + регистр. `ЗаказКлиентаЗакупки(Основание)` (от поступления). В существующую блокировку — регистр.
Продукция строки — через поступление-основание → заказ поставщику (`КодСтроки`, номенклатура, характеристика), иначе
распределение со сторно (п. 1.2). Ресурс `Пришло` с минусом.

## 6. Блокировка — `УправляемыеБлокировки.ПотребностиПроизводства(Блокировка, Заказ)`

## 7. Отчёт `ПотребностиПроизводства`

`Reports/ПотребностиПроизводства` по образцу `ТоварыВПереработке`: новые uuid, `CommonForm.ФормаОтчёта`, схема с
запросом к `РегистрНакопления.ПотребностиПроизводства.Остатки`. Поля: `Заказ`, `Продукция`, `Материал`,
`Характеристика` (измерения), ресурсы `Потребность`, `Заказано`, `Пришло`, `ИзОстатка`, вычисляемые в запросе
`Дефицит = Потребность − Заказано` и `КЗаказу = ВЫБОР КОГДА Дефицит > 0 ТОГДА Дефицит ИНАЧЕ 0` (все — ресурсы СУММА).
Параметр `ТолькоДефицит` (Булево, по умолчанию Ложь, в пользовательских настройках): `ГДЕ НЕ &ТолькоДефицит ИЛИ
Потребность − Заказано > 0`. Вариант: группировки заказ → продукция → материал (+характеристика), заголовки ×4.
Проверка: смок «сформировать все отчёты» — нет; отчёт открывается смоком форм через общую форму. Разделы:
`Subsystems/Производство` `<content>Report.ПотребностиПроизводства</content>`; регистр в подсистемы не включается
(дубль пункта с отчётом, mdo-005). `Configuration.mdo` — `<reports>`.

## 12. Правки редакции 2 (architecture-critic)

Имеют приоритет над разделами 1–11.

### 12.1. Остатки заказа — без полного просмотра регистра (P2-4)
`ОстаткиПотребности(Заказ, ИсключитьРегистратор)`: `РегистрНакопления.ПотребностиПроизводства.Остатки(, Заказ = &Заказ)`

регистратора), свёртка. Таблица движений по `Заказ` не читается.

### 12.2. Распределение по продукции (P2-2, P2-3, P3-2, P3-3)
Вход — строки закупки и **таблица пределов** `Продукция, Материал, Характеристика, Предел` в порядке строк продукции.
Проходы:
1. строки с явной продукцией (колонка `Продукция` заказа поставщику или продукция строки-источника, п. 12.3): есть строка
   пределов с этой продукцией — всё количество на неё, накопитель строки растёт; нет — движения нет;
2. строки без продукции: строки пределов материала с характеристикой по порядку; свободный остаток строки —
   `Предел − накопитель` (не меньше нуля); количество закрывает остатки по порядку, излишек — на последнюю строку
   (решение 2). Строк пределов у материала нет — движения нет.

Источник пределов по документу:

| Документ | Пределы | Порядок |
|---|---|---|
| заказ поставщику | `ПотребностьОстаток − ЗаказаноОстаток` без своих движений, только строки с `Потребность > 0` | строки продукции заказа клиента |
| поступление по заказу поставщику с движениями «Заказано» | «Заказано» движений этого заказа поставщику (`Регистратор = &ЗаказПоставщику`) − «Пришло» других поступлений по нему | то же |
| поступление по заказу поставщику без движений «Заказано», поступление по заказу клиента | `ПотребностьОстаток − ПришлоОстаток` без своих движений, `Потребность > 0` | то же |
| возврат поставщику | «Пришло» движений поступления-основания (`Регистратор = &Поступление`) − сторно других возвратов по этому поступлению | **обратный** (излишек — на первую продукцию) |

У возврата предел — «пришло этим поступлением с учётом прошлых сторно − сторнировано этим возвратом ≥ 0»; движение —
отрицательное «Пришло». «Другие поступления/возвраты по основанию» — движения регистра, регистратор которых ссылается на
то же основание (запрос с `Регистратор ССЫЛКА Документ.… И Регистратор.Основание = &Основание И Регистратор <> &Ссылка`,
отбор по `Заказ`).

основания — движений нет. Кнопка «Подобрать из предварительных» в форме скрыта; сценарий «предварительный → итоговый →

### 12.4. Порядок проверки основания и блокировки (P3-1)
