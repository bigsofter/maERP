# План: E8 — стадии заказа клиента на производство (2.0.15.20)

Бриф `docs/plans/production-2mzl-e8-stadii.md`. Основание — план волны, этап E8, обязательства E6 и E7.

## 0. Решения владельца 2026-09-14

1. Одна сборка — 2.0.15.20.
2. Долг заказа = остаток `ВзаиморасчётыСПокупателями` по объекту «заказ» (аванс — минус) + остатки по реализациям
   на основании заказа; стадия «Ожидает оплаты» при сумме > 0.
3. Стадия всегда равна расчёту по текущим данным: отмена проведения и возвраты откатывают её, в истории новая запись.
4. Индикатор — пять кружков: обеспечение, поступление, выпуск, отгрузка, оплата; `○` 0, `◐` частично, `●` полностью.
5. Отмена проведения заказа клиента со связанными закупками разрешена, стадия «Черновик».
6. **Поздняя веха закрывает ранние** (отклонение от буквального каскада, вопрос задан по ходу исследования): материал
   со склада без закупки не держит заказ в «Заказ поставщику».

## 1. Каскад (ПроизводственныеЗаказы.РассчитатьСтадию)

Для заказа с `ВидОперации <> Производство` — `Неопределено` (продажи не трогаем).

1. не проведён или помечен на удаление → `Черновик`;
2. отгружено всё (по каждой паре номенклатура+характеристика строк товаров отгружено ≥ заказано, строк > 0):
   долг > 0 → `ОжидаетОплаты`, иначе `Выполнен`;
3. выпущено всё (по каждой производимой паре выпущено ≥ к выпуску, производимых строк > 0) → `ОжидаетОтгрузки`
   (ред. 3: раньше проверки потребности — поздняя веха, plan-review P3-6);
4. потребности нет (у заказа нет «Потребность» > 0 в `ПотребностиПроизводства`) → `ФормируетсяПотребность`;
5. по какой-то паре материал+характеристика `max(Заказано, Пришло) < Потребность` → `ЗаказПоставщику`
   (сумма по продукции — обязательство E7; пришедшее без заказа поставщику считается заказанным);
6. по какой-то паре `Пришло < Потребность` → `ВосполнениеПотребности`;
7. иначе → `ВПроизводстве`.

Производимые строки — строки товаров, у которых есть материалы (`ТЧМатериалы.КодСтрокиПродукции`); закупаемый товар в
заказе на производство выпуском не проверяется, только отгрузкой. Если производимых строк нет, п. 3 пропускается.
Индикатор честный: у выполненного заказа без закупок и выпуска — `○○○●●`.

Источники (все — количества в базовых единицах `Количество`):
- потребность, заказано, пришло — `РегистрНакопления.ПотребностиПроизводства` (физическая таблица, отбор по
  индексированному `Заказ`, знак по `ВидДвижения`, только активные) — `ИзОстатка` не учитывается до E9;
- выпущено — `Документ.ВыпускПродукции.ТЧГотоваяПродукция`, `Ссылка.Основание = &Заказ`, проведённые;
- отгружено — `Документ.РеализацияТоваровУслуг.ТЧТовары` (`Основание = &Заказ`, проведённые) минус
  `Документ.ВозвратОтПокупателя.ТЧТовары` (`Основание.Основание = &Заказ`, проведённые);
- долг — `ВзаиморасчётыСПокупателями.Остатки(, Контрагент В (контрагенты заказа и его реализаций) И ОбъектРасчётов В
  (заказ, реализации заказа))` — сумма `СуммаОстаток`; реализации — **все** с `Основание = Заказ`, независимо от
  проведения и пометки (plan-review P3-5: деньги на объекте помеченной реализации не выпадают); отбор по `Контрагент` —
  индексированное измерение;
- начислено — `Сумма` проведённых реализаций заказа минус `Сумма` проведённых возвратов от покупателя по ним;
- оплачено = `max(0, Начислено − Долг)` (ред. 2, critic P2-2): аванс ПКО «на основании заказа» ложится на объект «сам
  ПКО» и попадает в заказ только через зачёт авансов реализации — формула от долга видит его после зачёта, формула от
  оборотов платёжек не видела бы никогда. До отгрузки аванс по строке оснований на заказ даёт `Долг < 0` →
  `Оплачено = −Долг`; аванс «сам ПКО» до отгрузки индикатор не показывает (TECHDEBT).

**Контекст текущего документа.** Проведённость и данные записываемого документа берутся из параметра, а не из базы:
`Контекст = Структура(Документ, Проведён, ПометкаУдаления)`. Для документных источников условие
`(Т.Ссылка.Проведен И Т.Ссылка <> &Документ) ИЛИ (Т.Ссылка = &Документ И &ДокументПроведён)`; для заказа — его
`Проведён`/`ПометкаУдаления` из контекста, если `Документ = Заказ`. Табличные части документа к моменту пересчёта уже
записаны (объект пишется до `ПриЗаписи`/`ОбработкаПроведения`). Регистровые источники к моменту пересчёта отражают
новое состояние: при проведении — после явного `Движения.Записать()`, при отмене — после явной очистки (п. 3).

Доли (округление до 4 знаков, 0…1):
- `ДоляОбеспечения` = Σ min(max(Заказано, Пришло), Потребность) / Σ Потребность; 0 без потребности;
- `ДоляПоступления` = Σ min(Пришло, Потребность) / Σ Потребность; 0 без потребности;
- `ДоляВыпуска` = Σ min(выпущено, к выпуску) / Σ к выпуску по производимым парам; 0 без производимых строк;
- `ДоляОтгрузки` = Σ min(отгружено, заказано) / Σ заказано;
- `ДоляОплаты` = 1, если отгружено всё и долг ≤ 0; иначе min(Оплачено, База) / База, где База = max(Сумма заказа,
  Начислено), 0 при нулевой базе; при долге > 0 доля и символ не достигают 1 — `◐` (plan-review P3-4).

`Индикатор` — пять символов по точным (неокруглённым) значениям: числитель 0 → `○`, числитель ≥ знаменателя → `●`,
иначе `◐`; округляется только хранимая доля (critic P3-10). У оплаты `●` — только при полной отгрузке и долге ≤ 0.

`РассчитатьСтадию(Заказ, Контекст)` возвращает структуру (Стадия, пять долей, Индикатор, Долг, Оплачено) и ничего не
пишет — сценарий проверяет её без записи (урок E5–E7). Привилегированный режим сама **не включает**: вызывающий код
документа уже в нём, сценарий — под администратором; так долг не открывается ролям без права на регистр (P3-11).
Экспортная только для сценария (модуль серверный, с клиента недоступен; контекст — необязательный, по умолчанию
данные из базы); форма получает только стадию и индикатор из среза (`ДанныеСтадии`).

## 2. Запись истории (ПроизводственныеЗаказы.ОбновитьСтадию)

- Своей транзакции не открывает; вызывается только внутри транзакции записи документа.
- Не экспортная: вызывается процедурами документа из п. 3, контекст строится из `ДокОбъект`, а не принимается
  параметром (P3-11). Привилегированный режим включают три экспортные процедуры документа из п. 3 — в самом начале, с
  комментарием: `ПередЗаписью`, `ПриЗаписи` и `ОбработкаУдаленияПроведения` у реализации, ПКО, возврата и сертификата
  идут не в привилегированном режиме, а `PDV`, `МенеджерПоПродажам`, `MobileClient` не читают `ПотребностиПроизводства`,
  у `Казначей`, `Кладовщик`, `Логист`, `Оператор` нет права на регистр истории (critic P1-1). Модуль — только сервер,
  без «вызова сервера»: с клиента недоступен.
- Сначала исключительная управляемая блокировка `РегистрСведений.ИсторияЗаказовПокупателейПоСтатусам` по заказу, потом
  чтение источников и среза последних (так последний коммитящий видит закоммиченные данные остальных). Несколько
  заказов одного документа блокируются одним `Заблокировать()` в порядке `УникальныйИдентификатор()`.
- Запись — только если стадия, любая доля или индикатор отличаются от среза последних; период —
  `РаботаСДокументами.ПериодЗаписиСтатусаЗаказа`; менеджер записи, `Записать(Ложь)`.

## 3. Точки пересчёта и порядок блокировок

Общие процедуры модуля (объектные модули вызывают по одной строке):

- `ЗапомнитьЗаказыДокумента(ДокОбъект, РежимЗаписи)` — в `ПередЗаписью` после проверок, до записи: прежние заказы из
  базы и режим записи → `ДополнительныеСвойства`. Читаются только источники, которые пишет сам документ (P1-1):
  закупки — движения `ПотребностиПроизводства` по регистратору; реализация и денежные документы — движения
  `ВзаиморасчётыСПокупателями` по регистратору (объект-заказ или реализация → её `Основание`); выпуск и реализация —
  `Основание` из базы; возврат от покупателя — `Основание.Основание` из базы и движения взаиморасчётов. У нового
  документа — пусто. Свойство — `ПроизводственныеЗаказы.ИмяСвойства()` (`ПроизводственныеЗаказыДокумента`), не
  `РежимЗаписи`: реализация уже кладёт свой `РежимЗаписи` (plan-review P3-9). Для заказа клиента запоминается и вид
  операции из базы: фильтр «заказ на производство» — по старому **или** новому виду (plan-review P2-2). При
  `ОбменДанными.Загрузка` и при свойстве `СвойствоВыполняетсяФоновоеПерепроведение()` все три
  процедуры ничего не делают (P3-8). Фоновое восстановление последовательности может поменять «Пришло» старых
  поступлений (TECHDEBT E7) — стадия догонит при следующей записи, в «Найдено в E8».
- `ОбновитьСтадииДокумента(ДокОбъект, Проведён)` — прежние ∪ текущие заказы (текущие: движения по регистратору из базы
  после записи, реквизиты объекта), только заказы на производство (один запрос), блокировка, пересчёт каждого.
  Вызывается:
  - в конце `ОбработкаПроведения` после `Движения.Записать()` (`Проведён = Истина`) — история последней блокировкой;
  - в `ПриЗаписи`, если режим записи `Запись` и документ проведён (перезапись проведённого без перепроведения меняет
    табличные части выпуска, реализации, возврата и шапку заказа).
- `ОтменитьПроведениеДокумента(ДокОбъект, Блокировка)` — новый обработчик `ОбработкаУдаленияПроведения`: работает,
  только если в `ДополнительныеСвойства` есть отметка `ЗапомнитьЗаказыДокумента` с режимом `ОтменаПроведения`
  (plan-review P3-10: экспортная привилегированная процедура не стирает движения произвольного документа); если среди
  прежних заказов есть заказы на производство — `Блокировка.Заблокировать()` (набор готовит документ), затем
  `УстановитьЗаписьВсехРегистров` + `Движения.Записать()` (явная очистка всех движений до пересчёта, как в УНФ
  `РасходнаяНакладная`: иначе платформа удалила бы движения после пересчёта, под блокировкой истории), затем пересчёт
  (`Проведён = Ложь`). Без заказов на производство — ничего не делает, поведение продаж прежнее.
  Набор блокировок перед очисткой — тот же и в том же порядке, что при проведении (P2-3); документ выносит его в свою
  процедуру `ЗаполнитьБлокировкуПроведения(Блокировка)` и зовёт из `ОбработкаПроведения` и `ОбработкаУдаленияПроведения`:
  заказ клиента и заказ поставщику — `ПотребностиПроизводства`; поступление и возврат поставщику — складские регистры,
  взаиморасчёты с поставщиками, потребности (как сейчас); реализация, возврат от покупателя, ПКО, поступление
  безналичных, РКО, списание безналичных — их текущие блокировки (plan-review P2-1); `КорректировкаДолга` и
  `СертификатНаОплату` — без явной блокировки (как при проведении). `ОбработкаУдаленияПроведения` у всех 13 документов
  уже привилегирована (`unpostInPrivilegedMode`); явная установка режима в процедуре оставлена — безвредна.
  У заказа клиента карты продукции при отмене не блокируются: карта не пишется.
- В `ОбработкаПроведения` пересчёт — только `Если Не Отказ` (P3-9).

Документы (13): `ЗаказПокупателя`, `ЗаказПоставщику`, `ПоступлениеТоваровУслуг`, `ВозвратПоставщику`,
`ВыпускПродукции`, `РеализацияТоваровУслуг`, `ВозвратОтПокупателя`, `ПриходныйКассовыйОрдер`,
`ПоступлениеБезналичныхДенежныхСредств`, `РасходныйКассовыйОрдер`, `СписаниеБезналичныхДенежныхСредств`,
`КорректировкаДолга`, `СертификатНаОплату` — все, кто пишет `ВзаиморасчётыСПокупателями` или `ПотребностиПроизводства`
(кроме `КорректировкаРегистров`: ручная правка регистров, в TECHDEBT). У документов без `ПередЗаписью`/`ПриЗаписи`
обработчики добавляются. Порядок в транзакции: карты продукции → регистры документа (как сейчас) → история последней.

Заказ клиента:
- `ПередЗаписью` — `ЗапомнитьЗаказыДокумента` (сам заказ).
- `ПриЗаписи`: КП отмечается выигранным **первым** (P3-7: история — последняя запись транзакции); затем заказ на
  производство — только при режиме `Запись` → `ОбновитьСтадииДокумента`; продажа — нынешний алгоритм, но последняя
  запись с заполненным `Индикатор` (признак записи E8, в том числе `ВПроизводстве`) считается отсутствующей →
  `Новый`/`ВРаботе` (смена вида операции непроведённого заказа и смена вида вместе с отменой проведения —
  plan-review P2-2). Отмена проведения со сменой вида: `ОбработкаУдаленияПроведения` (фильтр по старому виду) чистит
  потребности, пересчёт у ставшего продажей заказа не пишет стадию, а `ПриЗаписи` той же записи уже написал `Новый` —
  порядок: `ПриЗаписи` раньше `ОбработкаУдаленияПроведения`, поэтому пересчёт для заказа, ставшего продажей, пропускается
  (стадия не пишется поверх `Новый`).
- `ОбработкаПроведения` — после `Движения.Записать()` пересчёт.
- `ОбработкаУдаленияПроведения` (новый) — блокировка потребностей, очистка, пересчёт → `Черновик`.

Ветвление старого расчёта: `РеализацияТоваровУслуг.ПриЗаписи` (Собран) и
`РаботаСДокументами.ОбновитьСтатусЗаказаПоСвязанным` (из выпуска, передачи/поступления переработки и обработчика
обновления) для заказа на производство ничего не пишут. Обработчик `ЗаполнитьПроизводственныеСтатусыЗаказов` так
перестаёт писать старые статусы заказам на производство — исторических стадий нет (решение 2).

Переменные модулей: новых `Перем` нет; локальные имена сверить скриптом с реквизитами 13 документов и регистра (bsl-010).

## 5. Интерфейс

- `ФормаДокумента` заказа: `ДекорацияСтатусаЗаказа` у заказа на производство — `ФорматированнаяСтрока` «стадия  ●●◐○○»
  с подсказкой-легендой на 4 языках; у продажи — прежняя строка статуса. Заполнение в `ПриСозданииНаСервере` и
  `ПослеЗаписиНаСервере` через `ПроизводственныеЗаказы.ДанныеСтадии(Заказ)` (чтение среза под пользователем; форма и так
  в привилегированном режиме — не меняем).
- `ФормаСписка`: в запрос — `Индикатор` из среза; в `НомерКартинкиОтгрузки`: `Черновик`, `ФормируетсяПотребность` → 0;
  `ЗаказПоставщику`, `ВосполнениеПотребности`, `ОжидаетОтгрузки` → 1 (`ВПроизводстве` уже 1); `ОжидаетОплаты`,
  `Выполнен` → 2; `НомерКартинкиОплаты`: `ОжидаетОплаты` → ?(`ДоляОплаты` > 0, 1, 2), `Выполнен` → 0. Колонка

## 8. Риски

- Порядок событий платформы: пересчёт не опирается на проведённость в базе у записываемого документа (контекст) и на
  момент автоудаления движений (явная очистка).
- Скан шапок по `Основание` у реализаций и выпусков — только при пересчёте заказа на производство.
- Оплата другим контрагентом по объекту заказа не попадёт в долг (отбор по контрагентам заказа и реализаций).
- Параллельные записи одного заказа сериализуются блокировкой истории; разные заказы не мешают друг другу.
- Заказы документа определяются до блокировки истории (P3-6): перепривязка реализации к другому заказу одновременно с
  оплатой по ней может оставить новый заказ без учёта платежа до следующей записи — принятый риск.
- У ПКО, РКО и безналичных после проведения срабатывает подписка `ПослеПроведенияДокументаОплаты`
  (`ПодпискиНаСобытия/Module.bsl:37-63`): перепроводит налоговые накладные уже под блокировкой истории, внутри
  `Попытка` — «история последней» для этих четырёх документов не строго; риск принят (налоговые накладные историю не
  пишут и заказ на производство не блокируют).
- Если платформа после `ОбработкаУдаленияПроведения` сама пишет пустые наборы у документов с `AutoDelete`, её неявные
  блокировки берутся после блокировки истории (P3-9) — остаточный риск, явная очистка делает наборы уже пустыми.
- Переработка (`ПоступлениеИзПереработки`) выпуском не считается; статусы волны 12 заказам на производство больше не
  пишутся (P3-12) — TECHDEBT.
- Аванс ПКО «на основании заказа» (объект — сам ПКО) до зачёта в реализации долю оплаты не двигает — TECHDEBT.
- Смок и сценарий идут под администратором: запись стадии из-под `PDV`, `Кладовщик`, `Казначей` проверяется ревью
  безопасности и ручной приёмкой.
