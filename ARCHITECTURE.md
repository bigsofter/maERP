# maERP на 1С:Предприятие — архитектура и организация разработки

> Смена стратегии: проект ведётся **на платформе 1С:Предприятие 8.3**, а не на собственном стеке Go + TypeScript. Прежний вариант (web-ERP с нуля на Go/TS) отклонён; при необходимости его описание доступно в истории Git. Этот документ — отправная точка для 1С-направления. Практическая настройка среды разработки вынесена в [`1c-dev-setup/README-1C-DEV.md`](1c-dev-setup/README-1C-DEV.md).

## Контекст

Нужен **универсальный учётный фундамент** (закупки, продажи, склад, заказы, бухучёт, ДДС, финансы, CRM, касса, сканеры, дашборды) и **отраслевые версии** поверх него (оптика, б/у телефоны, транспорт). Развёртывание — **on-premise / отдельный инстанс на клиента**. Команда — только своя, публичный SDK/маркетплейс не нужен.

Текущая стартовая точка: **самописная конфигурация, снятая с поддержки** (живая база на Windows-сервере), выгрузки в файлы ещё нет.

Цель — реализовать те же бизнес-задачи средствами 1С с минимумом дублирования между отраслевыми версиями и низкими издержками эксплуатации парка инсталляций.

---

## Почему 1С закрывает исходные задачи дешевле, чем свой стек

Многое из того, что в варианте на Go/TS пришлось бы писать руками, в 1С есть «из коробки»:

| Задача проекта | В собственном стеке | В 1С |
|---|---|---|
| Регистры остатков/оборотов | Проектировать и писать | Регистры накопления (native) |
| Двойная запись / проводки | Свой модуль accounting | Регистр бухгалтерии, план счетов |
| Документооборот | Универсальный модуль documents | Документы + последовательности + проведение |
| Касса / РМК | Отдельное приложение POS | РМК, рабочее место кассира |
| Сканеры/весы/ФР | Локальный агент + адаптеры | Подключаемое торговое оборудование, драйверы ФР |
| Отчёты/дашборды | Свой слой reports | СКД (система компоновки данных) |
| Права/роли | Свой auth | Роли, RLS, профили |
| Миграции схемы | goose/migrate | Реструктуризация при обновлении конфигурации БД |

Цена — привязка к платформе и её модели разработки, но для учётной ERP это, как правило, выгодный обмен.

## Ключевые архитектурные решения

### 1. Единое ядро + отраслевые расширения (.cfe)

Это 1С-аналог «модульного монолита + build-time-композиции» из исходной концепции:

- **Ядро** — основная конфигурация (общая для всех отраслей): номенклатура, склад, продажи, закупки, цены, бухучёт, ДДС, CRM, касса, оборудование, отчёты, права.
- **Отрасль** — отдельное **Расширение конфигурации** (`.cfe`) на каждую вертикаль: `optical` (медкарта, рецепты, диоптрии), `usedphones` (IMEI, % батареи, состояние, история ремонта), `transport` (маршруты, водители, путевые листы).
- **Инсталляция клиента** = ядро + нужное отраслевое расширение(я). Один ствол ядра, отраслевая специфика изолирована.

Почему расширения, а не форки основной конфигурации: один источник истины для ядра, отраслевые правки не «вмерзают» в общий код, обновление ядра раскатывается на все инсталляции независимо от отрасли. Прямое редактирование основной конфигурации допустимо (она снята с поддержки), но отраслевую дельту лучше держать в `.cfe` ради изоляции.

> Граница «что в ядре, что в расширении» — ключевое проектное решение. Базовый принцип: всё, что нужно ≥2 отраслям → в ядро; уникальное для одной отрасли → в её расширение. Расширение зависит от ядра, ядро об отрасли не знает.

### 2. Расширение ядра отраслью — механизмами платформы

1. **Заимствование объектов** в расширении + перехват методов (`Перед`/`После`/`Вместо`) — аналог hook points.
2. **Добавочные реквизиты/доп.сведения** (ПВХ) или реквизиты в расширении — расширение `Номенклатуры`/`Контрагента` без правки ядра.
3. **Свои объекты отрасли** (справочники/документы/регистры медкарты, IMEI-истории) в расширении, связь с объектами ядра по ссылкам.
4. **Подписки на события** проведения/записи — отраслевая реакция на документы ядра.

### 3. Развёртывание on-premise на клиента

- **Сервер:** 1С:Сервер на Windows или Linux + СУБД (MS SQL / PostgreSQL). Для Linux-инсталляций — контейнеризация (1С:Сервер + PostgreSQL в Docker/Compose).
- Один инстанс = одна организация/группа компаний (мультитенантность не нужна — изоляция через отдельные базы).
- **Розница/POS:** РМК; вопрос offline-режима кассы решается отдельно (см. открытые вопросы).

### 4. Учёт и данные

- Оперативный учёт — регистры накопления (остатки, продажи, расчёты с контрагентами).
- Бухгалтерия — регистр бухгалтерии + план счетов; проводки формируются при проведении документов.
- Себестоимость (FIFO/средневзвешенная/партионная) — политика на уровне организации.
- Идемпотентность операций кассы/сканеров — через контроль повторного проведения и бизнес-логику документов.

## Организация разработки

Подробности — в [`1c-dev-setup/README-1C-DEV.md`](1c-dev-setup/README-1C-DEV.md). Кратко:

- **IDE:** 1C:EDT (формы, метаданные, отладка) + VSCode (BSL, рефакторинг, анализ) на Mac; сервер/тест/прод — на Windows.
- **Версионирование:** Git (репозиторий конфигурации — отдельный от этого). Ядро и каждое отраслевое расширение — свои ветки/папки/репозитории, версии расширений привязаны к мажору ядра.
- **AI-ассистент:** Claude Code / VSCode-агенты + MCP-серверы (платформенный API, метаданные базы) + BSL Language Server. Применять для анализа, документирования, ревью; бизнес-логику, запросы и формы — под контролем разработчика.
- **Контуры:** Dev (файловая ИБ на Mac) → Test/QA (Windows, копия прода) → Prod (Windows). Выливка через сборку `.cf`/`.cfe` и обновление конфигурации БД, прод — в окно обслуживания с бэкапом.
- **Тестирование:** YaXUnit (юнит) и/или Vanessa Automation (сценарии) в CI.

## Дорожная карта (грубая)

1. **Фаза 0 — среда и фундамент.** Выгрузка живой базы в файлы, EDT-проект, Git, CI-каркас, dev-окружение. Аудит и документирование существующей самописной конфигурации (сильная сторона AI).
2. **Фаза 1 — ревизия ядра.** Выделить из текущей конфигурации «ядровые» подсистемы (склад, продажи, закупки, цены), навести порядок, покрыть тестами критичные участки.
3. **Фаза 2 — деньги.** Бухучёт, ДДС, касса/банк, отчётность (СКД).
4. **Фаза 3 — фронт-офис.** CRM, документооборот, дашборды, РМК.
5. **Фаза 4 — оборудование.** Сканеры/весы/ФР, оффлайн-касса (если решим, что нужна).
6. **Фаза 5 — первая отрасль.** Оптика как пилот отраслевого расширения → отрабатывает контракт «ядро + .cfe»; затем usedphones; затем transport.

## Открытые вопросы (зафиксировать до активной разработки)

1. **Стратегия подтверждена?** Окончательно ли выбрана 1С вместо собственного стека (этот документ исходит из «да»).
2. **Версия платформы** для dev/test/prod (единая) и политика обновления платформы.
3. **БСП.** Подключать ли Библиотеку стандартных подсистем к самописной конфигурации (даёт типовые механизмы, но это крупное вливание) или развивать свои механизмы.
4. **Граница ядро/расширение** для каждой отрасли — где именно проходит линия.
5. **Оффлайн-касса** обязательна на старте или достаточно online-РМК в локальной сети.
6. **Фискализация** — юрисдикции (РФ ФФД / др.), от этого зависят драйверы ФР и интеграции.
7. **Многовалютность / мультиорганизация** в одном инстансе — нужны или «один инстанс = одна группа компаний».
8. **Состояние текущей конфигурации** — насколько она годится как основа ядра vs переписывать подсистемы заново.
