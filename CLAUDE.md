# Правила работы над maERP

Тиражное решение на 1С:Предприятие 8.5.1, собственная конфигурация. Разработка
ведётся напрямую в основной конфигурации, не через расширения.

## Где исходники

Единственный источник правды — EDT-проект в `src/cf`: `.mdo` (метаданные) и
`.bsl` (модули). Правлю только их.

**Не трогаю:**
- `build/` — целиком артефакты сборки.
- `DT-INF/` внутри EDT-проекта — служебное EDT.
- `ConfigDumpInfo.xml` и прочие файлы XML-выгрузки — они генерируются.
- `.cf` в любом виде — бинарник, редактировать нечем.

## Код

- Встроенный язык 1С, русский. Кодировка UTF-8, отступ — табуляция.
- Длина строки — до 140 символов (правило из `.bslls.json`).
- Директивы компиляции проставляю явно, без опоры на умолчания.
- Экспортные методы общих модулей документирую комментарием: назначение,
  параметры, возвращаемое значение.
- Обращения к данным — через запросы, а не перебор выборок в цикле, если
  объём данных заранее не мал.

## Именование

Метаданные и переменные — на русском, как принято в 1С. Префикс в именах
метаданных **не используется** (решение от 2026-08-22): maERP — самостоятельная
тиражная конфигурация, а не дополнение к чужой, объединения с другими
конфигурациями не предполагается. Объекты, переносимые из конфигураций
клиентов (drissotex), создаю с их uuid — тогда данные клиента заходят в maERP
без конвертации.

## Проверка себя

После правки модулей — `scripts/lint.sh` и `scripts/refcheck.py` (сверка ссылок
на объекты метаданных: константы, перечисления, регистры, картинки, формы и
макеты в строковых именах, экспортные методы общих модулей). Замечания BSL LS и
новые расхождения сверки разбираю до того, как отдать работу. Синтаксическую проверку и проверку ссылочной целостности
метаданных делает EDT на стороне пользователя — о необходимости Refresh и
проверки в EDT сообщаю явно.

Автотесты на базе — `scripts/smoke.sh` (CheckConfig + смок «открыть все формы»
и «сформировать все печатные формы»), регламент и реестр — `docs/TESTING.md` и `docs/TESTS.xlsx`. Перед
сборкой релиза прокатываются все тесты — обязательный шаг чек-листа релиза.
Новый функционал расширяет тесты: правило и разделение «человек/машина» — в
`docs/TESTING.md`.

## Версия и список изменений

Правило владельца от 2026-08-26, подробности — `docs/RELEASING.md`.

- Схема версии — `2.0.X.Y`. `X` растёт при публикации CF, `Y` — **при каждой
  передаче владельцу на тест**, на единицу, без исключений.
- Перед каждой передачей на тест: поднимаю `Y` в `Configuration.mdo` и завожу
  секцию `## <версия>` в общем макете `ОписаниеИзменений`
  (`src/cf/src/CommonTemplates/ОписаниеИзменений/Template.txt`) — с блоками
  `### ru`, `### fr`, `### en`, `### es`: пункты пишу на всех четырёх языках,
  окно «Что нового» показывает закладку на каждый.
- В эту секцию попадает **каждый этап и каждая правка** сборки — формулировками
  для пользователя. Пустая или отсутствующая секция = владелец после обновления
  видит пустое окно «Что нового», это ошибка сдачи.
- Макет ведётся **от последней публикации CF**: секции всех сборок релиза лежат
  в нём одновременно и показываются владельцу целиком. Старые секции не чищу —
  их переносит в `docs/CHANGELOG.md` только публикация CF.
- В отчёте владельцу называю версию, на которую он обновляется.

## Git

- Рабочая ветка — `develop`, вся разработка идёт туда. В `main` попадают только
  релизные состояния, слиянием из `develop`.
- В git не попадают бинарники: `.cf`, `.cfu`, `.epf`, `.erf`, `.dt`, базы.
  Релизные файлы — в GitHub Releases.
- Один коммит — одно осмысленное изменение. Сообщения на русском.
- Импорт или переимпорт конфигурации из EDT — всегда отдельным коммитом, не
  смешивая с правками кода: иначе полезный дифф утонет в перегенерации.

## Выкладка релизов

Правило владельца от 2026-08-27. Получив от него письменное «регресс пройден»
(шаги 6–7 чек-листа в `docs/RELEASING.md`), делаю сам, без дополнительных
вопросов: merge `develop` → `main`, тег `v<версия>`, push с тегами, сборку
поставки и **черновик** GitHub Release с приложенными `.cf` и `.cfu`. Даю
владельцу ссылку — Publish жмёт он.

Описание релиза на GitHub — на всех четырёх языках в одном теле: английский
основным текстом, ru/fr/es в сворачиваемых блоках (локализации описаний у GitHub
нет). Собирает его `scripts/release-notes.sh` из того же макета, что и окно
«Что нового».

Без этого подтверждения ничего из перечисленного не начинаю. Опубликованные
релизы и существующие теги не правлю и не удаляю. Репозиторий `bigsofter/maERP`
публичный осознанно: опубликованный релиз виден всем.

## Сборка

Пакетный режим `1cv8 DESIGNER` работает headless из терминала — сборку CF и
выгрузки могу делать сам. EDT нужна для редактирования, проверки и импорта
конфигурации.

## Правила разработки 1С

В `docs/rules-1c/` лежит подмножество правил из comol/ai_rules_1c —
стиль кода, модули, формы, запросы, регистры, блокировки. Применяю их к
новому коду. При конфликте старшинство: этот файл → `docs/rules-1c/` → ИТС.
Осознанно отложенное — в `docs/TECHDEBT.md`, туда же добавляю новое.
